# wolf-macos

The macOS front-end: a native **AppKit** application (Swift) that renders the embedded Neovim character grid and forwards keyboard input, over the generated [swift-bridge](../wolf-ffi) surface. It is a thin native shell — native window chrome and a CoreText/CoreGraphics paint backend — over the unchanged, platform-agnostic [`wolf-core`](../wolf-core).

## Design decisions (locked)

- **Tahoe (macOS 26) and newer only** (`LSMinimumSystemVersion` / `minimum_os_version` = `26.0`).
- **AppKit, not SwiftUI.** Implementation language **Swift**; **Xcode 26+**.
- Build is **all-Bazel and authoritative**: `rules_swift` + `rules_apple` build the `.app`; `rules_xcodeproj` generates an **uncommitted** `.xcodeproj` for debugging/LLDB only (`.gitignore`d).
- Rust ↔ Swift via swift-bridge, confined to `wolf-ffi`; the generated bindings are committed.
- **Key translation lives in Rust.** Swift sends a structured `FfiKeyEvent`; `wolf-core` owns nvim notation.

## Modules and sources

### `Sources/WolfKeyMap/` — the pure key seam (no AppKit)

`WolfKeyMap.translate(keyCode:characters:charactersIgnoringModifiers:ctrl:shift:alt:meta:) -> FfiKeyEvent?` is the macOS analog of wolf-gnome's `gdk_key` seam: it takes exactly the data an `NSView.keyDown(_:)` pulls off an `NSEvent` and returns a generated `FfiKeyEvent?`. It imports only Foundation and the generated FFI struct, so it is unit-testable headlessly. It honors the **Shift contract**:

- Named keys (Return, Tab, arrows, F-keys, …) are recognized from `keyCode` first and KEEP the real `shift` flag (so wolf-core can emit `<S-Tab>`, …).
- Printable characters carry the already-shifted glyph in `ch` with `shift = false` (Shift+'a' → 'A', Shift+'1' → '!').
- When ctrl/alt/meta are held, the glyph comes from `charactersIgnoringModifiers` (lowercased), never the modifier-mangled `characters`.
- Bare modifier keys and unmodified control characters map to `nil`.

The module also holds `PickerSeam.swift` — a second AppKit-free seam (`public enum PickerSeam`, Foundation only, headlessly tested) that ports wolf-gnome's pure picker helpers:

- `isPickerTrigger(charactersIgnoringModifiers:command:) -> Bool` — the **Command+O** trigger predicate (`command && first scalar lowercased == "o"`; other modifiers ignored). Command-modified keys are not Neovim keybindings, so the chord does not consume a Neovim key.
- `nextSelection(current:delta:nRows:) -> Int?` — list navigation clamp (a port of wolf-gnome's `next_selection`; `nil` when there are no rows).
- `restoredIndex(resetToTop:prev:newLen:) -> Int?` — selection restore across streaming result batches (a port of `restored_index`).

The module also holds `PickerRefreshCoalescer.swift` — a Foundation-only, headlessly-tested (`PickerRefreshCoalescerTests`) seam that DEBOUNCES the picker's streaming-traversal refreshes. `public final class PickerRefreshCoalescer` exposes `static let refreshInterval: TimeInterval = 0.033` (~30 fps), an `init(schedule: (@escaping () -> Void) -> Void, perform: () -> Void)` with both closures injected (so tests drive it without a run loop and the live app schedules via `DispatchQueue.main.asyncAfter`), `request()`, and `cancelPending()`. `request()` COALESCES a burst of wakes into ONE trailing refresh: the first call arms the timer, subsequent calls while it is armed are dropped, and the fire clears the armed flag so a later wake re-arms — the load-bearing guarantee that the FINAL / complete traversal wake is never dropped (a later `request()` always reschedules). `cancelPending()` clears the flag (an already-armed timer still fires, but the picker's `refresh()` is a no-op once closed). This turns a large-tree traversal's hundreds of per-batch wakes into a bounded ~30 fps stream of full re-ranks instead of one full re-rank per batch.

The module also holds two more Foundation-only, headlessly-tested seams that cut the sidebar file tree's projection cost in a large repo (the three-layer performance fix; the `wolf-core` `TreeIndex` / `TreeIndexCache` is Layer 2, these are Layers 1 and 3):

- `TreeChildrenMemo.swift` — `public final class TreeChildrenMemo<Item>` (tested by `TreeChildrenMemoTests`), a per-directory memo of a directory's projected children. `init(project: @escaping (String) -> [Item])` injects the projection; `children(ofDir:) -> [Item]` computes via `project` on first lookup of a directory and returns the cached array thereafter, so `project` (and the FFI `children_of` it wraps) runs **at most once per directory** between invalidations — collapsing AppKit's numberOfChildren/child:index callback storm onto memory. `invalidate()` drops all cached arrays (keeping capacity). In `FileTreeView` the injected closure captures `self` weakly and reuses `itemsByRelPath` for stable identity, so the memo holds the SAME `TreeItem` instances.
- `TreeRefreshGate.swift` — `public final class TreeRefreshGate` (tested by `TreeRefreshGateTests`), a visibility + version gate. `init(isVisible:)`; `requestRefresh() -> Bool` returns true while visible and, while hidden, records a deferred catch-up and returns false; `setVisible(_:) -> Bool` returns true exactly once on a hidden→visible transition that had a deferred refresh (running one catch-up); `shouldReload(version:) -> Bool` returns true only when the snapshot version differs from the last reloaded one (recording it), so a redundant `reloadData()` at an unchanged version is skipped; `resetReloadTracking()` forgets the last version (used on reroot). This is what makes hiding the sidebar actually stop the outline work, and stops a full reload firing on every render wake.

The module also holds two more AppKit-free seams (Foundation only, headlessly tested by `ShortcutSeamTests` / `WindowIndexSeamTests`) backing the multi-window support:

- `ShortcutSeam.isNewWindowTrigger(charactersIgnoringModifiers:command:) -> Bool` — the **Command+N** new-window trigger predicate (`command && first scalar lowercased == "n"`), the sibling of `isPickerTrigger` matching "n" instead of "o". **NOTE: this seam is now DORMANT / UNWIRED.** New Window moved to the menu's **⇧⌘N** key-equivalent and plain **⌘N** is now the File > New (`:enew`) menu item, so the old `keyDown` Cmd-N interception was removed from `PaneContainerView`; the seam (and `ShortcutSeamTests`) are kept as a pure, still-passing seam but nothing calls `isNewWindowTrigger` in the live app.
- `WindowIndexSeam.nextFreeIndex(occupied: [Int]) -> Int` — the smallest non-negative integer not in `occupied`, so a new window reuses the lowest freed `state.json` slot (holes stay dense).

The module also holds `CommandSeam.swift` — an AppKit-free command-kind decode seam (Foundation only, headlessly tested by `CommandSeamTests`), the sibling of `PaneTree`'s `Orientation(ffi:)` / `FocusDir(ffi:)`: `public enum CommandKind` (all fourteen cases `newWindow`/`closeWindow`/`quitApplication`/`hideApplication`/`minimizeWindow`/`goToFile`/`openFile`/`openFolder`/`closePane`/`newBuffer`/`resetFontSize`/`increaseFontSize`/`decreaseFontSize`/`commandPalette`) with a guarded `init?(ffi: UInt8)` decoding the `wolf-ffi` `command_kind` discriminant (0..13 → cases, else `nil`). It decodes the FFI byte delivered in an `NSMenuItem.tag` (the native menu path) or by a drained `FfiCommand` (the nvim-drained path); both faces funnel through the one `CommandDispatcher`.

The module also holds `PaletteSeam.swift` — a pure, AppKit-free (Foundation only, headlessly tested by `PaletteSeamTests`) command-palette sibling of `PickerSeam`. `PaletteSeam.isPaletteTrigger(charactersIgnoringModifiers:command:) -> Bool` is the **Command+P** trigger predicate (`command && first scalar lowercased == "p"`, other modifiers ignored — "p" instead of `PickerSeam`'s "o"), and the nested `PaletteRowKind: UInt8` (`staticCommand = 0` / `switchWindow = 1` / `openRecent = 2`, with a guarded `init?(ffi:)`) mirrors `wolf-ffi`'s `mod palette_row_kind` (structurally the sibling of `StateSeam.ToolbarMode`). **NOTE: `isPaletteTrigger` is DORMANT / UNWIRED.** ⌘P is a menu key-equivalent that preempts `keyDown` (exactly like ⌘N / `ShortcutSeam`), so the View-menu **Command Palette…** item is the real trigger and nothing in `PaneContainerView.keyDown` calls `isPaletteTrigger`; the predicate (and `PaletteSeamTests`) are kept for consistency with `PickerSeam`.

The module also holds `PaneTree.swift` — a third AppKit-free seam (Foundation only, headlessly tested), a faithful port of wolf-gnome's pure `layout.rs` pane-layout tree. It exposes `PaneTree` (a reference type mutated in place) with `split` / `remove` / `leaves` / `paneRects` / `neighbor` / `layout`, the value types `Orientation` (`horizontal`/`vertical`), `FocusDir` (`left`/`right`/`up`/`down`), `Rect`, `PaneId`, and the recursive `PaneLayout` (`.leaf` / `.split(orientation:children:weights:)`). It uses `Double` (not `CGFloat`) so it pulls in no CoreGraphics, and `Orientation.init?(ffi:)` / `FocusDir.init?(ffi:)` decode the `wolf-ffi` discriminants (the contract guarded by `PaneTreeTests`). A SAME-orientation split FLATTENS into equal siblings while a PERPENDICULAR split nests — the N-ary frame model matching Neovim and the GNOME tree. The macOS `PaneContainerView` consumes `paneRects()` to paint each pane into a computed rectangle in a single flat view (rather than a tree of `NSSplitView`s).

The module also holds two more AppKit-free seams (Foundation only, `Double` not `CGFloat`, headlessly tested) that back the pane mouse/scroll wiring:

- `PaneGeometry.swift` — `public struct PaneGeometry`, the per-pane pixel↔cell mapping. It carries a distinct **GRID RECT** (where the Neovim grid is drawn) INSIDE the **PANE RECT**; `init(paneRect:cellWidth:cellHeight:maxCols:)` **caps the grid at `maxCols` columns and CENTERS it horizontally** when the pane is wider than that (equal side margins, `paintOffsetX = inset`), leaving a pane no wider than the cap unaffected (`gridRect == paneRect`, offsets `0`); `maxCols == nil` disables the cap. `PaneContainerView` passes `maxCols: 90` (hard-coded), so a grid wider than 90 columns is centered inside the pane with side margins. It derives `cols` / `rows` (`max(1, floor(gridRect.size / cell))`), `paintOffsetX` / `paintOffsetY` (the grid-rect origin minus the pane-rect origin — the centering inset when capped), and `cellAt(x:y:) -> (row, col)` which maps a pane-local point to a grid cell **clamped** into `[0, cols-1] × [0, rows-1]` (so a point in a margin or past an edge lands on the nearest edge cell).
- `ScrollAccumulator.swift` — `public struct ScrollAccumulator`, a pure signed pixel→line-step accumulator with a carried remainder. `consume(deltaY:cellHeight:) -> Int` returns the signed whole number of line steps for the delta (guarding `cellHeight <= 0` → `0`), keeping the sub-cell remainder for the next call so smooth trackpad scrolling accumulates; `reset()` clears the remainder. It is direction-agnostic (signed); the AppKit layer maps the sign to a scroll direction.
- `CellMetricsMath.swift` — `public enum CellMetricsMath`, a Foundation-only pure seam for the config-driven cell geometry (extracted so it is headlessly unit-tested by `CellMetricsMathTests`). `cellHeight(fontSize:lineHeightPercent:ascent:descent:leading:)` returns `round(fontSize * lineHeightPercent / 100)` — with a `lineHeightPercent <= 0` guard that falls back to the font's natural `ceil(ascent + descent + leading)` — and `baseline(cellHeight:ascent:descent:)` returns `ascent + (cellHeight - ascent - descent) / 2` (recentering the glyph within a taller cell). `CellMetrics` calls these with the config's line-height.
- `FontSizeSeam.swift` — `public enum FontSizeSeam`, Foundation only, the pure step+clamp math backing the View font-size commands (headlessly tested by `FontSizeSeamTests`). It owns the constants `minPointSize = 6`, `maxPointSize = 72`, `step = 1` (all `Double`) and `clamped(_:)`, `increased(_:) = clamped(current + step)`, `decreased(_:) = clamped(current - step)`. It owns ONLY the increment/clamp math; RESET (back to the window's stored default) is handled by the `WolfWindowController`, not the seam.

The module also holds `StateSeam.swift` — another AppKit-free seam (Foundation + CoreGraphics only, headlessly tested by `StateSeamTests`) backing the state-restore path: `StateSeam.ToolbarMode` (a `UInt8` raw-valued enum on the wolf-ffi `toolbar_mode` discriminant table — `iconAndText = 0`, `iconOnly = 1`, `textOnly = 2`; `init?(rawValue:)` returns `nil` for an unknown discriminant so restore leaves the toolbar at its default), `restoredWindowFrame(x:y:width:height:screenVisibleFrames:) -> CGRect?` (`nil` when the saved width/height is non-positive — the "unset" sentinel — or when the frame intersects NO screen visible frame, so a window is never restored fully offscreen), and `launchDecision(restored:home:isDirectory:) -> LaunchDecision` (the launch model — `.folder(cwd:)` when the restored cwd is non-empty AND still a directory, else `.emptyState(nvimCwd: home)` for an empty or deleted/replaced restored cwd; it NEVER returns the process working directory, replacing the old `launchCwd` fallback that polluted the recent-dirs MRU; the injected closure keeps the seam pure).

The Bazel `wolf_key_map` module compiles `KeyMap.swift`, `PickerSeam.swift`, `PickerRefreshCoalescer.swift`, `PaletteSeam.swift`, `ShortcutSeam.swift`, `WindowIndexSeam.swift`, `PaneTree.swift`, `PaneGeometry.swift`, `ScrollAccumulator.swift`, `CellMetricsMath.swift`, `FontSizeSeam.swift`, `GlyphStyle.swift`, `StateSeam.swift`, `TreeChildrenMemo.swift`, `TreeRefreshGate.swift`, and `CommandSeam.swift` together with the swift-bridge-generated Swift glue (which provides `FfiKeyEvent`, the `FfiMouseEvent` / `FfiScrollEvent` input structs, the `WolfCoreHandle` / `FfiFrame` wrappers, the `FfiFileSearch` / `FfiFileEntry` picker types, the `FfiLayoutIntent` / `FfiWinInfo` pane types, the `FfiCommand` command type, the `FfiCommandPalette` / `FfiCommandRow` command-palette types, and the `FfiState` / `FfiWindowState` restore types), so the rest of the app gets those types via `import WolfKeyMap`.

### `Sources/WolfMacOS/` — the AppKit application

- `main.swift` — entry point: `NSApplication.shared`, `.regular` policy, run.
- `AppMenu.swift` — builds and installs the native **NSMenu app menu bar** (net-new; there was no menu bar before). `AppMenu.install(target:) -> InstalledMenus` constructs the standard menus from wolf-macos's OWN hardcoded item description (it does NOT read the core registry over FFI yet — only the `command_kind` discriminant crosses the bridge) and RETURNS the `InstalledMenus { window; openRecent }` pair of dynamic submenus so the `AppDelegate` can rebuild both dynamic tails: **App** (About / Hide `⌘H` / Quit `⌘Q`), **File** (New `⌘N` / New Window `⇧⌘N` / separator / Go to File `⌘O` / Open File _(no shortcut)_ / Open Folder `⇧⌘O` / **Open Recent** _(dynamic submenu, no shortcut)_ / separator / Close `⌘W` / Close Window `⇧⌘W`), **View** (Reset Font Size `⌘0` / Increase Font Size `⌘=` / Decrease Font Size `⌘-` / separator / **Command Palette…** `⌘P` / separator / **Enter Full Screen** `⌃⌘F`), **Window** (Minimize `⌘M` / separator / a DYNAMIC list of one item per open window, titled with that window's full cwd). The item titles mirror `wolf_core::COMMAND_SPECS` (the ellipsis characters are single U+2026, e.g. "Command Palette…"). Every Wolf command item carries its FFI `command_kind` u8 in `NSMenuItem.tag`, targets the `AppDelegate`, and fires `#selector(AppDelegate.handleCommandMenuItem(_:))`. The private `commandItem(...)` helper takes a `modifiers: NSEvent.ModifierFlags = .command` parameter setting `keyEquivalentModifierMask`, so `⇧⌘N` / `⇧⌘O` / `⇧⌘W` use a lowercase key equivalent plus an explicit `[.command, .shift]` mask (NOT a capital letter). **New Window moved from `⌘N` to `⇧⌘N`** so plain `⌘N` is now File > New (`:enew`, a new empty buffer in the current window); **Close** (`⌘W`, the former "Close File") now runs `:close` (close the split, not the buffer) and Close Window stays `⇧⌘W`. **Command Palette…** (`⌘P`) is the new View item that opens the command palette overlay; its `Tag.commandPalette = 13` discriminant funnels through the usual `handleCommandMenuItem` path to `CommandDispatcher`. **Enter Full Screen is NET-NEW and is NOT a Wolf command** (a spec-vs-implementation deviation flagged per CLAUDE.md — no fullscreen item existed before): it is a STANDARD AppKit item whose action is `#selector(NSWindow.toggleFullScreen(_:))` with a `nil` target (routed to the key `NSWindow`) and mask `[.control, .command]` (`⌃⌘F`); it carries no `Tag` / `command_kind`, AppKit owns its validation + Enter/Exit title toggle, and `validateMenuItem` needs no change for it. The `Tag` enum holds the FFI `command_kind` discriminants `0..13` (`closePane = 8`, `newBuffer = 9`, `resetFontSize = 10`, `increaseFontSize = 11`, `decreaseFontSize = 12`, `commandPalette = 13`). The static `rebuildWindowMenu(_:controllers:target:)` clears the Window menu and rebuilds it — Minimize (`⌘M`) + separator, then one item per controller titled with its `currentCwd` (fallback "Wolf"), action `#selector(AppDelegate.raiseWindowMenuItem(_:))`, target the delegate, and `tag = windowIndex` — and the private `viewMenuItem(...)` builds the View-menu items. The File menu's **Open Recent** parent item carries a NATIVE dynamic `NSMenu` (like the Window menu, NOT a `Command` — an Open Recent entry is path-parameterized and does not fit the no-arg `command_kind` model), seeded with a disabled "No Recent Folders" placeholder so it is never empty; the static `rebuildOpenRecentMenu(_:recentDirs:target:)` (the sibling of `rebuildWindowMenu`) clears it and either re-adds that placeholder (empty MRU) or builds one item per recent-directory path titled with the full path, action `#selector(AppDelegate.openRecentMenuItem(_:))`, target the delegate, and `tag = ` the list index. The `Tag` enum / `command_kind` discriminants are UNCHANGED (Open Recent does not use the tag-as-`command_kind` path).
- `CommandDispatcher.swift` — the single funnel every command flows through. `CommandDispatcher.dispatch(_ kind: CommandKind, window: NSWindow?, coordinator: AppDelegate?, originatingCwd: String, controller: WolfWindowController?)` maps a decoded `CommandKind` to its native action: `.newWindow` → `coordinator?.makeNewWindow(originatingCwd:)`, `.closeWindow` → `window?.performClose`, `.quitApplication` → `NSApp.terminate`, `.hideApplication` → `NSApp.hide`, `.minimizeWindow` → `window?.miniaturize`, `.goToFile` → `controller?.openFilePicker()`, `.openFile` → `controller?.presentOpenFileDialog()`, `.openFolder` → `controller?.presentOpenFolderDialog()`, `.closePane` → `controller?.closePane()` (`:close`), `.newBuffer` → `controller?.newBuffer()` (`:enew`), `.resetFontSize` → `controller?.resetFontSize()`, `.increaseFontSize` → `controller?.increaseFontSize()`, `.decreaseFontSize` → `controller?.decreaseFontSize()`, `.commandPalette` → `controller?.openCommandPalette()`. Both the native-menu path (`handleCommandMenuItem`, targeting `NSApp.keyWindow`) and the nvim-drained path (`WolfWindowController.drainAndDispatchCommands`, targeting the draining controller's own window) route here, so a command has ONE implementation regardless of face. `controller` is the command's target window controller (the menu path finds the key window's controller via `controllers.first { $0.owns(key) }`; the nvim-drained path passes the originating controller itself), through which the four File commands reach that window's picker / core handle; it is `nil` when no controller owns the window. `originatingCwd` is the originating window's LIVE working directory (`handle.cwd()`), threaded through for legacy reasons but now IGNORED by `.newWindow`: `makeNewWindow(originatingCwd:)` always opens a new EMPTY-STATE window (no folder), so a drained `:WolfNewWindow` and the New Window menu item never inherit the frontmost window's cwd; the other commands ignore it too. The nvim-drained path passes the draining controller's own `currentCwd`; the menu path passes the key window's controller `currentCwd` (empty when no controller owns the key window).
- `AppDelegate.swift` — the app **coordinator** (also conforming to **`NSMenuItemValidation`** and **`NSMenuDelegate`**), now a thin manager over a collection of `WolfWindowController`s (one per OS window). At launch it does the once-only setup ONCE for the whole process: installs the three wake bridges (`WakeBridge` / `PickerWakeBridge` / `TreeWakeBridge`), installs the native menu bar (stashing the `AppMenu.install(target: self)` result — the Window `NSMenu` for `rebuildWindowMenu()` once the controllers exist, and the Open Recent `NSMenu`, whose `delegate` it sets to itself so the submenu rebuilds lazily), registers the bundled fonts (`FontRegistration.registerBundledFonts()`, CoreText-registers `Contents/Resources/fonts/*.ttf`, holding BOTH bundled families), loads the user config (`wolf_ffi_load_config()`), then measures the shared cell metrics (`CellMetrics.measured(config:)`) — so both "iA Writer Mono S" (the default) and "JetBrains Mono" resolve and the config drives the grid geometry. It then reads the saved application state (`wolf_ffi_load_state()`, BEFORE any core starts) and creates ONE `WolfWindowController` per saved window (its `windowIndex` == its list position), copying each saved window's facets OUT of the bridge's `RustVec<FfiWindowState>` immediately into a plain `RestoredWindowState` (element refs must not outlive the vec); with nothing saved it creates one default controller at index 0. **Launch is empty-state-aware:** each window's `(launchCwd, hasFolder)` is derived by feeding the (possibly empty/deleted) restored cwd through the pure `StateSeam.launchDecision(restored:home:isDirectory:)` (`home = FileManager.default.homeDirectoryForCurrentUser.path`) and mapping the result via the private `dir(_:)` helper — `.folder(cwd)` → `(cwd, hasFolder: true)`, `.emptyState(nvimCwd)` → `(nvimCwd, hasFolder: false)` — then handing both to `makeController(windowIndex:launchCwd:restored:hasFolder:)`. So a fresh launch with an empty state file, and a restored window whose saved cwd is `""` or no longer a directory, both open an EMPTY-STATE window (Wolf NEVER opens the process working directory); a valid saved cwd opens that folder. A startup-failure alert (`presentStartupFailureAndQuit`) fires only when the FIRST window's core fails. `makeNewWindow(originatingCwd:)` is the **New Window** (⇧⌘N) entry point: it IGNORES `originatingCwd` and ALWAYS opens a new empty-state window — it picks the first free slot via `WindowIndexSeam.nextFreeIndex(occupied:)`, builds `(launchCwd, hasFolder)` from `launchDecision(restoredCwd: "")` (always `.emptyState(home)`), and creates + `start()`s a controller with `restored: nil` (AppKit cascade placement). `handleCommandMenuItem(_:)` is the native menu-item entry point: it decodes the item's `tag` (an FFI `command_kind` byte set by `AppMenu`) into a `CommandKind` via `CommandKind(ffi:)`, finds the key window's controller (`controllers.first { $0.owns(NSApp.keyWindow) }`), and funnels through `CommandDispatcher.dispatch(..., window: NSApp.keyWindow, coordinator: self, originatingCwd:, controller:)` — passing that controller (so the File commands reach its picker / handle) and its `currentCwd` (empty when none owns the key window); note the New Window command ignores that cwd and always opens an empty-state window — the SAME dispatcher the nvim-drained command path uses. `removeController(_:)` drops a controller from the collection (called at window close). The **dynamic Window menu** is owned here: `rebuildWindowMenu()` (delegating to `AppMenu.rebuildWindowMenu(windowMenu, controllers:, target: self)`) runs at startup, in `makeNewWindow`, in `removeController`, and on `windowCwdDidChange(_:)` (the per-window cwd-change hook a controller fires only when its cwd actually changed), so the menu always lists one item per open window titled with its full cwd; `@objc raiseWindowMenuItem(_:)` maps the clicked item's `tag` (the window's `windowIndex`) to `controllers.first { $0.windowIndex == sender.tag }` and calls that controller's `raise()`. Three coordinator helpers back the **command palette**: `otherWindows(excluding:) -> [(index: Int, cwd: String)]` (every live controller EXCEPT the argument, mapped to `(windowIndex, currentCwd)` — the palette's "Switch to Window" candidate source, current window excluded), `controllerForCwd(_ path:) -> WolfWindowController?` (the first live controller whose `currentCwd == path` — the "Open Recent Folder" raise target), and `raiseWindow(windowIndex:)` (the "Switch to Window" action — `raiseWindowMenuItem`'s tag→controller→`raise()` logic exposed by index). The **dynamic Open Recent submenu** is rebuilt lazily via the `NSMenuDelegate` conformance rather than explicit lifecycle hooks: `menuNeedsUpdate(_:)` (guarded on `menu === openRecentMenu`) reads the key-window controller's `recentDirs()` (`controllers.first { $0.owns(NSApp.keyWindow) } ?? controllers.first`, `[]` when none), stashes it in the `recentDirs` field, and hands it to `AppMenu.rebuildOpenRecentMenu`, so the list is always fresh at menu-open time; `@objc openRecentMenuItem(_:)` bounds-guards `sender.tag`, resolves `recentDirs[sender.tag]`, and calls `changeDirectory(_:)` on the key-window controller (chdir — the same effect as Open Folder, with no panel). `validateMenuItem(_:)` (the `NSMenuItemValidation` conformance) is UNCHANGED — Open Recent items use `openRecentMenuItem(_:)` (not `handleCommandMenuItem`) so they fall through to `true`, and the placeholder's `action: nil` auto-disables it; it returns `true` for every item EXCEPT the `.closePane` (Close) command item, which is enabled only when the key window's controller `paneCount > 1` — so the last split cannot be closed (matching Neovim's E444); the dynamic window items short-circuit before the tag-as-`command_kind` cast because their action differs. `applicationShouldTerminateAfterLastWindowClosed` stays `true`. `applicationWillTerminate` re-pushes each STILL-LIVE window's snapshot at its own fixed `windowIndex` (NOT a dense re-index) and then prunes ghost slots via `state_set_window_count(highestLiveIndex + 1)` — truncating to the highest live index never drops a live higher slot, at the cost that a closed MIDDLE window's now-stale slot below the high-water mark survives (the documented v1 limitation below). This truncation runs only when at least one window is still open at quit (Cmd-Q); if the user closed every window one-by-one first, `controllers` is already empty and NO truncation runs. It then tears down the remaining controllers as a backstop.
- `WolfWindowController.swift` — owns ONE window's stack (moved out of the old `AppDelegate`): its `handle`, `window`, `paneContainer`, `tree`, `picker`, `palette`, `statePersistence`, fixed `windowIndex`, and per-window `wakeToken`. `start()` points wolf-core at the bundled Neovim (`WOLF_NVIM_BIN` via `setenv(..., 0)` so a dev override wins), resolves `init_lua` (honoring `WOLF_INIT_LUA`, else `Contents/Resources/init.lua`), calls `wolf_ffi_start(..., UInt16(windowIndex))`, reads `handle.wake_token()`, and **registers itself in `WindowRegistry` under that token** so wakes route back to this window; it then builds the pane container / sidebar / picker / overlay `CommandPaletteView` (built parallel to the picker, added as a `paneContainer` subview, with `palette.onActivate = { [weak self] row in self?.activatePaletteRow(row) }`) / centered "Open folder…" overlay (`EmptyStateView`) / window, wires `paneContainer.onPickerTrigger` to the picker (the old `paneContainer.onNewWindow` wiring is GONE — New Window is now the menu's ⇧⌘N item, not a Cmd-N keyDown interception) and the empty-state overlay's `onOpenFolder` to `presentOpenFolderDialog()`, restores the saved frame/toolbar only for a restored window (a fresh window keeps cascade placement), installs `StatePersistence`, installs a `sidebarVisibilityObservation` (a second `isCollapsed` KVO on `sidebarItem`, alongside `StatePersistence`'s disk-state one, with `.initial` so the tree is seeded immediately) that relays `!isCollapsed` into `tree?.setSidebarVisible(_:)` so the file tree's refresh gate defers/catches-up its outline work (invalidated in `teardown()`), sets itself as the window delegate, shows the window, and makes the pane container first responder. It carries a stored `hasFolder: Bool` init param that gates the empty state: the `EmptyStateView` is `isHidden = hasFolder`; the file tree is only `start()`ed when `hasFolder` (an empty-state window must not scan `home`); and the sidebar is set per `hasFolder` — an empty-state window (`hasFolder == false`) ALWAYS collapses the sidebar (ignoring any stored `sidebar_visible`), a restored FOLDER window honors `isCollapsed = !restored.sidebarVisible`, and a fresh folder keeps the default (visible). It owns its OWN per-window font state: `currentPointSize` / `defaultPointSize` (both seeded from `CellMetrics.defaultPointSize(config:)`, which honors `WOLF_FONT_PT` then `config.font_size`) and its own MUTABLE `CellMetrics` (seeded from the launch measurement, then re-measured and replaced by the View font-size commands — so each window's font size is independent). `onRenderWake()` drives `paneContainer.onRenderWake()`, then `tree.onRenderWake()` ONLY when `hasFolder` (an empty-state window never scans/reroots), then a transition check + `drainAndDispatchCommands()` (the private helper that drains this window's `handle.drain_commands()`, decodes each `FfiCommand.kind()` via `CommandKind(ffi:)`, and funnels through `CommandDispatcher.dispatch(..., window: window, coordinator: coordinator, originatingCwd: currentCwd, controller: self)` targeting THIS controller's own window — so a `:Wolf*` / `require('wolf')` command triggered in window A acts on window A), and — guarded by a stored `lastKnownCwd` — calls `coordinator?.windowCwdDidChange(self)` ONLY when the cwd actually changed, so the dynamic Window menu's per-window title stays current after a `:cd`. While `hasFolder == false` it also detects an nvim-initiated `:cd` OUT of the empty state: it baselines the first non-empty observed `handle.cwd()` (nvim reports `home` for an empty-state window) into a stored `initialCwd`, and when a later non-empty cwd differs from that baseline it calls the new idempotent `didOpenFolder()`, which flips `hasFolder = true`, hides the `EmptyStateView` overlay, and REVEALS the sidebar (`sidebarItem.isCollapsed = false`) so the next wake reroots the tree at the opened folder. A typed `:cd` to the SAME launch dir won't auto-transition (no cwd change) — the button is the intended path and always transitions. It also exposes `paneCount` (its `paneContainer.paneCount`, used by `AppDelegate.validateMenuItem` to disable Close on the last split) and `raise()` (`window.makeKeyAndOrderFront(nil)` + `NSApp.activate(...)`, called by the dynamic Window-menu items). It also exposes the **command** methods the dispatcher reaches through `controller`: `openFilePicker()` (opens the existing overlay via `picker?.open()`, the **Go to File** / `⌘O` action, mirroring the pane container's own picker trigger); `openCommandPalette()` (the **Command Palette** / `⌘P` action — gathers `coordinator?.otherWindows(excluding: self) ?? []` and calls `palette?.open(otherWindows:)`); the private `activatePaletteRow(_ row:)` that performs a chosen palette row's action by kind (`.staticCommand` → `CommandKind(ffi: row.commandKind)` then `CommandDispatcher.dispatch(..., window:, coordinator:, originatingCwd: currentCwd, controller: self)`; `.switchWindow` → `coordinator?.raiseWindow(windowIndex: Int(row.windowIndex))`; `.openRecent` → raise `coordinator?.controllerForCwd(row.path)` if one exists, else `changeDirectory(row.path)` — the three locked activation actions); `presentOpenFileDialog()` (a native `NSOpenPanel` — files only, no dirs, no multi-select, `directoryURL` seeded from `currentCwd` when non-empty — `beginSheetModal(for: window)`, and on `.OK` calls `handle.open(url.path)` then `refocusEditor()`); `presentOpenFolderDialog()` (the same sheet but directories only → `handle.chdir(url.path)`, then `didOpenFolder()` to optimistically transition out of the empty state, then `refocusEditor()`, so the sidebar follows the new live cwd); `closePane()` (`handle?.close_pane()`, i.e. `:close` — the split, not the buffer); `newBuffer()` (`handle?.new_buffer()`, i.e. `:enew`); and the three per-window **font-size** actions `resetFontSize()` / `increaseFontSize()` / `decreaseFontSize()`, each computing a new point size (reset → `defaultPointSize`; increase/decrease via the `FontSizeSeam` step+clamp) and calling the private `setPointSize(_:)` — which, when the size actually changed, re-measures `CellMetrics.measured(config:pointSize:)`, stores it, and calls `paneContainer.applyMetrics(metrics)` to reflow the grid to fit the UNCHANGED window frame (grid cols/rows recompute, `syncGridSizes` pushes to nvim, repaint). Font size is EPHEMERAL — per-window, NOT persisted to `state.json`; a fresh window (or ⌘N New Window) starts at the config default. It also exposes the **File > Open Recent** pair the coordinator reaches for the dynamic submenu: `recentDirs() -> [String]` (reads `handle.recent_dirs()`, converting each `RustString` via the `.as_str().toString()` `RustVec` idiom; `[]` when the handle is gone) and `changeDirectory(_ path:)` (`handle?.chdir(path)`, then `didOpenFolder()` to transition out of the empty state, then `refocusEditor()`, the same effect as Open Folder but with no panel). The private `refocusEditor()` returns first responder to the `paneContainer` so keystrokes reach Neovim after a sheet dismisses (the sheet closures capture `[weak self]`). `windowWillClose(_:)` → `teardown()`, which pushes a final snapshot + `state_flush()`, closes the tree + picker + palette sessions, `shutdown`s the core, unregisters from `WindowRegistry`, and asks the coordinator to drop it (idempotent, so the terminate-time backstop is safe). The `coordinator.removeController(self)` call is deferred to the next main-runloop turn (`DispatchQueue.main.async`), NOT run synchronously: during `windowWillClose` the coordinator's collection is the last strong reference to the controller, and the controller owns the window, so dropping it inline would deallocate the `NSWindow` while AppKit is still mid-close (its deferred close animation captures the window) — a use-after-free. Deferring keeps the window alive until AppKit's close transaction has finished.
- `WindowRegistry.swift` — the process-global, **main-thread-only** map from a core's per-window wake `token` (`UInt64`) to the owning `WolfWindowController`. The wake fires on a tokio worker thread with only a plain `Send` `u64`; the three `*WakeBridge` thunks hop onto the main thread and look the token up HERE (`controller(for:)`) to reach the right window. `register` / `unregister` / `controller(for:)`, no lock needed (every access is on the main thread).
- `MainWindow.swift` — the "Wolf" `NSWindow` (one per `WolfWindowController`). It sets `isReleasedWhenClosed = false` so ARC (the owning controller) is the SOLE owner of the window: AppKit's default `isReleasedWhenClosed == true` adds an unbalanced release on close that over-releases the ARC-held window, crashing later in the deferred close-animation dealloc (this is why closing a non-last window previously crashed). Its `contentViewController` is an `EditorSplitViewController`; the window uses a transparent `.fullSizeContentView` titlebar and a minimal unified `NSToolbar` (a sidebar toggle + an `NSTrackingSeparatorToolbarItem` aligned to the divider) vended by a retained `EditorToolbarDelegate`, with `allowsDisplayModeCustomization = true` (so the icon+text / icon-only / text-only context menu exists; the chosen mode is persisted per window in `state.json`). It retains the split view controller and exposes `sidebarItem` (so state restore can set — and `StatePersistence` can observe — `isCollapsed`). It measures the titlebar/toolbar chrome (`contentView.bounds.height − contentLayoutRect.height`) and sizes the content so the editor pane keeps its exact initial cols × rows below the titlebar, with the **cmdline strip as EXTRA height** (`rows·cellHeight + cmdlineStripHeight`, the 80-col width preserved), then pins the divider at `treePaneWidth` and makes the `PaneContainerView` the `initialFirstResponder`. `applyTitlebarBackground(rgb:set:)` applies the **`WolfTitlebar` theme color**: because the titlebar is transparent full-size-content-view, setting `NSWindow.backgroundColor` (sRGB from the packed rgb) recolors the titlebar over the editor pane (the sidebar keeps its vibrancy); the pristine `backgroundColor` is captured on the first themed application, and `set == false` (group absent/cleared) restores it — idempotent and reversible. `WolfTitlebar.fg` is carried through core → FFI but NOT applied this pass (AppKit exposes no public titlebar-text-color API with a system-drawn title).
- `EditorSplitViewController.swift` — the `NSSplitViewController` content controller: a leading `.sidebar` source-list split item (`NSSplitViewItem(sidebarWithViewController:)` → OS vibrancy + full-height under the titlebar; the higher holding priority is kept so the editor pane absorbs resizing) wrapping the `FileTreeView`, and a trailing content item wrapping the `PaneContainerView`, hosted by a small `HostViewController` (the content host pins the pane container below the `safeAreaLayoutGuide` so the titlebar/toolbar never obscures it). `pinDivider()` pins the sidebar at `treePaneWidth`; the `sidebarItem` accessor exposes the leading split item for state restore/persistence.
- `StatePersistence.swift` — the write-only state-persistence glue owned by each `WolfWindowController`: it observes its window's geometry (`didMove`, `didEndLiveResize`, and `didResize` — the last skipped during `inLiveResize`, so live-resize spam coalesces into the end-of-resize push while discrete resizes like zoom still push), the sidebar split item's `isCollapsed` (KVO), and the toolbar's `displayMode` (best-effort KVO — not documented-guaranteed, which is why the terminate-time snapshot is the correctness backstop), pushing each change over the wolf-ffi `state_set_*` bridge methods (which write at the handle's fixed `window_index`); `pushSnapshot()` pushes all three facets at once (called once right after the window opens and from the controller's `teardown()` / the coordinator's `applicationWillTerminate`). It performs NO file IO itself (the store's writer thread in wolf-core owns the file) and no restore (the controller applies the restored state before the window is shown); the embedded Neovim's cwd is persisted core-side (the `wolf_cwd` hook) with no involvement here. A toolbar `displayMode` of `.default` (the user never chose an explicit mode) — and a missing toolbar — clear the persisted mode (`set == false`), so restore leaves the system default alone.
- `PaneContainerView.swift` — the editor area's split-panes container (the macOS analog of wolf-gnome's `pane_view.rs` `PaneInner` + `PaneHandle`), and the editor area's first responder + single global key sink. It is a **single flat `NSView`** (flipped, the proven `GridView` pattern) that paints EVERY pane itself — deliberately NOT a tree of nested `NSSplitView`s. It owns the pure `WolfKeyMap.PaneTree` and a `panes: [PaneId: PaneBinding]` map (each binding is a Neovim `win` + its `boundGrid`, `nil` until resolved). `draw(_:)` computes every pane's rectangle via `PaneTree.paneRects(width, paneAreaHeight)` and, for each bound pane, clips+translates to that rect and paints the pane's window grid (cell backgrounds + CoreText glyphs — each glyph in the bold/italic/boldItalic face + with the underline/strikethrough decorations that `GlyphStyleResolver` derives from the cell's `flags()` + `special()`, the decorations stroked manually as `CGContext` lines in the resolved color since `CTLineDraw` ignores decoration-color attributes — plus the mode-aware cursor when `cursor_visible`); because each pane is painted **independently of Neovim**, an INACTIVE pane gets a translucent dim scrim (a front-end-only treatment that is awkward to express inside Neovim). Thin separators are stroked between adjacent panes, and the bottom one-row **cmdline strip** paints Neovim's command line: under `ext_multigrid` the command line / messages live on a dedicated MESSAGE grid (NOT grid 1), and the cursor moves onto it while the command line is open, so the strip paints the grid the cursor is on when that grid is neither grid 1 nor a window grid (its cursor row), falling back to grid 1's LAST row otherwise — keeping typed `:`/`/` input visible while the editor panes remain shown. `keyDown(_:)` checks `PickerSeam.isPickerTrigger` (→ `onPickerTrigger`) else runs `WolfKeyMap.translate` → `send_key` (keys go to nvim's current window globally). The old `onNewWindow` property and the `ShortcutSeam.isNewWindowTrigger` Cmd-N interception in `keyDown` have been REMOVED: Cmd-N is now the File > New menu item and the menu key-equivalents preempt `keyDown`, so leaving the interception would have wrongly opened a window on ⌘N. Its `metrics` is now a `var`; `applyMetrics(_:)` (`metrics = …; syncGridSizes(); needsDisplay = true`) reflows the grid to a newly-measured `CellMetrics` (the View font-size path — the window frame is unchanged, so cols/rows recompute), and `paneCount` (`tree.leaves().count`) exposes the live split count for `AppDelegate.validateMenuItem` (Close disabled on the last split). Each pane is painted by `paintGrid`, which first fills the whole pane rect with the grid's own `default_bg()` (so the side margins around a centered grid blend seamlessly into the grid background), paints the (possibly centered) grid at the geometry's paint offset, and dims the WHOLE pane — margins included — when it is inactive. **Mouse** is fully wired through per-pane `PaneGeometry` (each pane's `geometry(for:)`, `maxCols: 90` — the 90-column cap + horizontal centering): `mouseDown` hit-tests the pane rects, `focus_win`s the clicked pane (click-to-focus preserved), maps the point to a grid cell (`geo.cellAt`) and `send_mouse`s a LEFT PRESS on the pane's window grid; `mouseDragged` maps the (clamped) point on the drag's grid and sends a DRAG; `mouseUp` sends a RELEASE and clears the drag grid — so under nvim's `mouse=a` a press→drag→release positions the cursor and selects (visual mode). **Scroll** (`scrollWheel`) is hit-tested from the whole PANE rect (so the future side-margin still scrolls), accumulates `event.scrollingDeltaY` into discrete line steps via a per-view `ScrollAccumulator` (reset when the target grid changes), and `send_scroll`s that many UP/DOWN events on the pane's grid at the pointer cell (using `scrollingDeltaY`'s sign directly — it already reflects the user's natural-scroll setting, so `isDirectionInvertedFromDevice` is NOT re-applied, which would double-invert; a single commented flip point remains). **Synthetic scrollbars** are custom-drawn per pane in `draw(_:)` at the pane's RIGHT edge, driven by the frame's viewport (`topline` / `botline` / `linecount`, 0-based): the thumb size is the visible fraction and its offset is `topline / linecount` (underflow-safe, no `-1`); nothing is drawn when the whole buffer is visible. They follow the macOS "Show scroll bars" setting via `NSScroller.preferredScrollerStyle` — `.legacy` draws always (with a faint track), `.overlay` shows on scroll then fades — reacting live to `NSScroller.preferredScrollerStyleDidChangeNotification` (observer removed in `deinit`). The thumb is **non-interactive** (drag-the-thumb is deferred). On each render wake `onRenderWake()` mirrors `PaneInner::on_render_wake` one-for-one: ensure the initial pane (`pick_initial_window` port), apply drained intents (`drain_intents` → SPLIT creates/splits a pane bound to the new window + `grid_for_win`, FOCUS_DIR resolves `tree.neighbor` and calls `focus_win`), detect closed windows (the live-grid set from `windows()`), resolve pending grids, refresh the active pane (`active_win()`, else the pane whose grid matches `read_frame_for_grid(...).cursor_grid()`), then `syncGridSizes()` (resize grid 1 to the whole view and each bound pane's grid to its rect, but ONLY when the size differs from nvim's current — so it converges, with no resize-feedback loop), then applies the **`WolfTitlebar` theme** (`applyTitlebarTheme()` reads `theme_titlebar_bg()`, compares against a cached `(rgb, set)` pair, and only on change calls `MainWindow.applyTitlebarBackground` — no per-wake AppKit churn; the themed CURSOR needs no handling here, its colors arrive pre-resolved via `cursor_fill()`/`cursor_glyph()`), and a single `needsDisplay`. AppKit glue, so compile-verified + manual-smoke only.
- `FileTreeView.swift` — the file-tree sidebar `NSView` (an `NSOutlineView` in an `NSScrollView`, `.sourceList` style with a clear background so the `.sidebar` split item's vibrancy shows through — no own `NSVisualEffectView`, no group-row styling) fed by its OWN long-lived `FfiFileSearch` session (`start_tree_search`). The cwd is shown as a single **synthetic root node** (its basename, sentinel rel-path `""`), **expanded on init** with `children_of("")` beneath it and their subdirectories collapsed — the VS Code / Snacks model, **divergent from the GNOME tree** (macOS-only). The sidebar **follows nvim's live cwd**: `start()` roots from `handle.cwd()`, and `onRenderWake()` (editor wake) reads `cwd()` first and **re-roots** (rebuild the root + restart `start_tree_search()`) when it changed (`:cd`/`DirChanged`), mirroring how the picker re-queries `getcwd()`. A single click opens a file (`open(absPath)`, then refocus the editor `PaneContainerView`) or toggles a directory. The current buffer's row is bolded; `onRenderWake()` reveals it on change — expanding the synthetic root then its ancestor dirs (`wolf_ffi_ancestors_to_reveal`) top-down before locating the row, leaving `pendingReveal` set if its file hasn't streamed in; `refresh()` (tree wake) reloads rows preserving expansion and retries the pending reveal. Per-directory child projection is guarded by two `WolfKeyMap` seams so a large repo no longer pegs the main thread: a `TreeChildrenMemo<TreeItem>` caches each directory's `[TreeItem]` (built from `projectChildren(dir:)`, which still reuses `itemsByRelPath` for stable identity) so AppKit's numberOfChildren/child:index storm calls `children_of` at most once per directory per reload — the memo is invalidated on each reload and on `reroot`; and a `TreeRefreshGate` gates `refresh()` on visibility and snapshot `version()` — while the sidebar is collapsed all outline work is deferred and one catch-up runs when it reappears (relayed from `WolfWindowController`'s `sidebarItem.isCollapsed` KVO into `setSidebarVisible(_:)`), and `reloadData()` fires only when the snapshot version advanced (a pending reveal still retries at an unchanged version). `reroot` also `resetReloadTracking()`s the gate.
- `PickerView.swift` — the floating overlay `NSView` panel (a larger-font, focus-ring-less **search bar** — a rounded container with a magnifier `NSImageView` + a borderless `NSTextField`, built by hand rather than an `NSSearchField` whose text cell clips a large font — plus an `NSTableView` in an `NSScrollView`) shown over the editor. `open()` starts an `FfiFileSearch` session, makes the search field first responder, and does an initial `refresh()` so the picker opens already showing the empty-query MRU-first result seed (mirroring the GNOME picker); the panel height is **content-driven** — just the search field when there are no rows yet, growing with the results up to a capped, then-scrolling max; typing filters via `ranked` (ranking in Rust) and maps each `FfiFileEntry` into a file-agnostic `PickerRow` at the boundary (title = the entry's full working-directory-relative path (`display()`), payload = absolute path, icon = the Finder icon via `NSWorkspace`); Up/Down navigate (using `PickerSeam.nextSelection`), selection is restored across streaming batches (`PickerSeam.restoredIndex`); Enter or a double-click opens the selected row's payload (`open(path)`) and closes; Esc closes. Refreshes come by TWO paths: keystroke filtering (`controlTextDidChange`) and `open()` call `refresh()` DIRECTLY (immediate), while streaming-traversal wakes go through `scheduleRefresh()` — which requests a coalesced refresh via a lazily-built `PickerRefreshCoalescer` (scheduled with `DispatchQueue.main.asyncAfter`) so a large tree's burst of per-batch wakes collapses into a bounded ~30 fps stream of full re-ranks rather than one re-rank per batch; `close()` calls the coalescer's `cancelPending()`. Row alignment insets (icon aligned with the magnifier, title aligned with the typed text) are derived from the search-bar layout constants (the magnifier's inset and width). While open, the text field holds first-responder status, so `PaneContainerView.keyDown` does not fire and keys are not forwarded to Neovim.
- `PickerRow.swift` — a file-agnostic value type (`icon`, single-line `title`, opaque `payload`) describing one picker list row, so the same panel can back other selectors (e.g. a buffer selector: title = the buffer's path, payload = a buffer id/token). Only `activateSelection()` interprets the payload.
- `PickerRowCellView.swift` — a reusable `NSTableCellView` rendering any `PickerRow`: a leading `NSImageView` (small icon, aligned with the search magnifier) and a single title label (aligned with the typed text via the caller-injected insets), the icon's bottom pinned to the text baseline. Exposes `configure(with:)`, static layout constants/fonts, and `rowHeight(iconSize:titleFont:verticalPadding:)`.
- `CommandPaletteView.swift` — the floating **command-palette** overlay `NSView`, the sibling of `PickerView` (the proven picker is left untouched): the same search bar + `NSTableView`-in-`NSScrollView` chrome, navigated via `PickerSeam.nextSelection` / `restoredIndex` and rendered with `PickerRow` / `PickerRowCellView` (rows carry no icon), but backed by an opaque `FfiCommandPalette` session rather than an `FfiFileSearch`. Placeholder "Run a command…". `open(otherWindows: [(index: Int, cwd: String)])` creates the session via `handle.command_palette()`, feeds each OTHER window with `session.add_window(UInt16(...), cwd)`, focuses the search field, and does an initial `refresh()` (the empty-query MRU-first seed); `refresh()` calls `session.ranked(query, max)` and maps each `FfiCommandRow` into a module-internal `CommandPaletteRow { label; kind: PaletteSeam.PaletteRowKind; commandKind: UInt8; windowIndex: UInt16; path: String; mruKey: String }` (skipping any unknown `row_kind` via `PaletteRowKind(ffi:)`). `activateSelection()` (Enter / double-click) records the row's MRU key (`session?.record(row.mruKey)`), hands the row to `onActivate` (the controller's `activatePaletteRow`), then `close()`s; Esc closes. There is **NO wake bridge**: candidates are fixed at open (recent dirs + the added windows) and `ranked()` re-filters synchronously per keystroke. Compile-verified + manual-smoke only. (`CommandPaletteRow` is module-internal, not file-private, because `WolfWindowController.activatePaletteRow(_:)` — in another file — receives it through the `onActivate` closure; this is the one small deviation from the plan's "private value type".)
- `EmptyStateView.swift` — the "no folder open" empty-state overlay: a `final class EmptyStateView: NSView` that fills the `PaneContainerView` (pinned leading/trailing/top/bottom in `viewDidMoveToSuperview`) and holds one centered `NSButton` titled "Open folder…". It exposes `var onOpenFolder: (() -> Void)?` (the controller wires it to `presentOpenFolderDialog()`); toggled by the controller via `isHidden` (visible only while `hasFolder == false`); deliberately NEVER first responder so launch keystrokes reach the editor grid; `init?(coder:)` is unavailable (`fatalError`, never from a nib). Shown on a fresh first run, on every ⇧⌘N New Window, and on a restored window whose saved cwd was empty/deleted; clicking runs the SAME Open Folder path as the menu command, after which `didOpenFolder()` hides it and reveals the sidebar. Compile-verified + manual-smoke only; the empty-vs-folder decision is the headless `StateSeam.launchDecision` seam.
- `PickerWakeBridge.swift` — registers the picker's `extern "C"` wake (`wolf_ffi_set_filesearch_wake`) ONCE at launch and, on each wake, `DispatchQueue.main.async`es onto the main thread, looks the firing core's `token` up in `WindowRegistry`, and calls that window's `picker?.scheduleRefresh()` — the COALESCED refresh (via the picker's `PickerRefreshCoalescer`) rather than a direct `refresh()`, so a streaming traversal's per-batch wake burst debounces to ~30 fps (keystroke filtering stays immediate; a late wake after the picker closes / the window is gone is a harmless no-op).
- `TreeWakeBridge.swift` — registers the sidebar's `extern "C"` wake (`wolf_ffi_set_tree_wake`) ONCE at launch and, on each wake, `DispatchQueue.main.async`es onto the main thread, looks the `token` up in `WindowRegistry`, and calls that window's `tree?.refresh()` (a late wake after the tree closes / the window is gone is a harmless no-op).
- `CellMetrics.swift` — measures a monospaced `CTFont` from the resolved user config: `measured(config: FfiConfig)` measures at the config's default point size (delegating to the new internal `defaultPointSize(config:)`, which takes `config.font_size` unless the `WOLF_FONT_PT` env var OVERRIDES it), while `measured(config: FfiConfig, pointSize: Double)` measures at an ARBITRARY point size (the View font-size commands' re-measure path — each `WolfWindowController` owns its own metrics and re-measures here on reset/increase/decrease). Both use the family from `config.font_family` (case-insensitive match via `CTFontCopyFamilyName`, with a **Menlo** fallback when the family does not resolve — no longer the old "SF Mono → Menlo" default). The cell height and baseline are computed via the pure `CellMetricsMath` seam from `config.line_height` (the percentage), so a configured line-height widens the cell and recenters the baseline. `defaultPointSize(config:)` is the shared seed both the initial metrics and each window's font-size RESET target read (honoring `WOLF_FONT_PT`). It also derives and caches the **bold / italic / boldItalic faces** (via `CTFontCreateCopyWithSymbolicTraits`, falling back to the regular face when CoreText resolves no distinct face), exposed through `font(for: GlyphFace)` so the renderer picks a face per cell; `cellWidth` is measured from the REGULAR face only, so every face paints into the same fixed-cell slot (advance-width stability).
- `FontRegistration.swift` — registers the bundled fonts with CoreText. `FontRegistration.registerBundledFonts()` enumerates `Contents/Resources/fonts/*.ttf` (BOTH the `//bazel/jetbrains-mono` and `//bazel/ia-writer-mono` trees, which merge into the one `fonts/` dir) and registers them via `CTFontManagerRegisterFontURLs(.process)` so both `"iA Writer Mono S"` (the default) and `"JetBrains Mono"` resolve in `CellMetrics`. It **logs, never fails** on an absent `fonts/` dir (dev / Linux parity), and `AppDelegate` calls it at launch BEFORE loading the config and measuring. Compile-verified + manual-smoke only (font registration is not headlessly testable).
- `Cursor.swift` — cursor-shape rectangle geometry (ported from wolf-gnome's `cursor.rs`); the cursor colors (the `WolfCursor` theme override, else reverse video) are resolved in Rust and arrive via `cursor_fill()`/`cursor_glyph()`.
- `Color.swift` — packed `FfiColor` → `CGColor`, with white/black fallbacks mirroring wolf-gnome's `paint.rs`.
- `WakeBridge.swift` — registers the editor `extern "C"` render wake (`wolf_ffi_set_wake`) ONCE at launch; each wake `DispatchQueue.main.async`es onto the main thread, looks the firing core's `token` up in `WindowRegistry`, and calls that window's `WolfWindowController.onRenderWake()` (which drives `paneContainer.onRenderWake()` then, for a window that has a folder, `tree.onRenderWake()`). The pane container's `onRenderWake()` applies drained layout intents and then marks the single editor view for redisplay (`needsDisplay`), repainting every pane + the cmdline strip in one `draw(_:)`. The wake closures capture only the global `WindowRegistry` (no per-window state), so they stay `@convention(c)`.

## Threading

`wolf-core` runs tokio on its own thread(s) and fires a wake on `flush`. The wake is the registered `extern "C"` callback (see `wolf-ffi`); `WakeBridge` hops it onto the AppKit main thread and calls `setNeedsDisplay`, which triggers a `draw(_:)` that reads the current frame. The `WolfCoreHandle` is used only on the main thread (it is not `Send`).

## Known limitations (this increment)

**Multiple windows now supported** (each a top-level `NSWindow` backed by its OWN embedded Neovim / `WolfCoreHandle`), with **⇧⌘N** (File > New Window) ALWAYS opening a new EMPTY-STATE window (no folder — it ignores the frontmost window's cwd; nvim launches at home underneath and the window shows the centered "Open folder…" button with the sidebar hidden); plain **⌘N** is now File > New (`:enew`), a new empty buffer in the current window. The `AppDelegate` is a coordinator over a collection of `WolfWindowController`s; each window's wakes route back to it through the per-window `wakeToken` looked up in `WindowRegistry`, so two windows never clobber each other's redraws / picker / tree. Windows persist and restore independently (one `state.json` slot per window, keyed by the handle's fixed `window_index`); closing one leaves the others live, and closing the last quits. **Known v1 limitation — stale/duplicate window restoration (NOT data loss).** The terminate-time ghost cleanup truncates the persisted `windows` list to `highestLiveIndex + 1`, NOT a dense re-index, and a closed window never removes its own slot. Two consequences follow, both bounded by the session's concurrent-window count: (1) if the user closes a NON-LAST (middle) window and then quits cleanly with other windows still open, that middle slot is below the high-water mark, so it survives with its last-saved (now stale) state and is restored as a stale/duplicate window on the next launch; (2) if the user closes EVERY window one-by-one (rather than Cmd-Q with windows still open), `controllers` is empty at terminate so NO truncation runs at all, and every slot any window ever used that session is restored as a window on the next launch. Within a running session holes are still reused lowest-first on the next Cmd-N (`WindowIndexSeam.nextFreeIndex`); the stale restoration only manifests across a quit/relaunch. A future dense re-index at terminate (or removing a window's slot on close) would tighten this.
