# wolf-macos

The macOS front-end: a native **AppKit** application (Swift) that renders the embedded Neovim character grid and forwards keyboard input, over the generated [swift-bridge](../wolf-ffi) surface. It is a thin native shell — native window chrome and a CoreText/CoreGraphics paint backend — over the unchanged, platform-agnostic [`wolf-core`](../wolf-core).

## Design decisions (locked)

- **Tahoe (macOS 26) and newer only** (`LSMinimumSystemVersion` / `minimum_os_version` = `26.0`).
- **AppKit, not SwiftUI.** Implementation language **Swift**; **Xcode 26+**.
- Build is **all-Bazel and authoritative**: `rules_swift` + `rules_apple` build the `.app`; `rules_xcodeproj` generates an **uncommitted** `.xcodeproj` for debugging/LLDB only (`.gitignore`d).
- Rust ↔ Swift via swift-bridge, confined to `wolf-ffi`; the generated bindings are committed.
- **Key translation lives in Rust.** Swift sends a structured `FfiKeyEvent`; `wolf-core` owns nvim notation.

## Modules and sources

### `Sources/WolfKeyMap/` — the pure key seam (no AppKit)

`WolfKeyMap.translate(keyCode:characters:charactersIgnoringModifiers:ctrl:shift:alt:meta:) -> FfiKeyEvent?` is the macOS analog of wolf-gnome's `gdk_key` seam: it takes exactly the data an `NSView.keyDown(_:)` pulls off an `NSEvent` and returns a generated `FfiKeyEvent?`. It imports only Foundation and the generated FFI struct, so it is unit-testable headlessly. It honors the **Shift contract**:

- Named keys (Return, Tab, arrows, F-keys, …) are recognized from `keyCode` first and KEEP the real `shift` flag (so wolf-core can emit `<S-Tab>`, …).
- Printable characters carry the already-shifted glyph in `ch` with `shift = false` (Shift+'a' → 'A', Shift+'1' → '!').
- When ctrl/alt/meta are held, the glyph comes from `charactersIgnoringModifiers` (lowercased), never the modifier-mangled `characters`.
- Bare modifier keys and unmodified control characters map to `nil`.

The module also holds `PickerSeam.swift` — a second AppKit-free seam (`public enum PickerSeam`, Foundation only, headlessly tested) that ports wolf-gnome's pure picker helpers:

- `isPickerTrigger(charactersIgnoringModifiers:command:) -> Bool` — the **Command+O** trigger predicate (`command && first scalar lowercased == "o"`; other modifiers ignored). Command-modified keys are not Neovim keybindings, so the chord does not consume a Neovim key.
- `nextSelection(current:delta:nRows:) -> Int?` — list navigation clamp (a port of wolf-gnome's `next_selection`; `nil` when there are no rows).
- `restoredIndex(resetToTop:prev:newLen:) -> Int?` — selection restore across streaming result batches (a port of `restored_index`).

The module also holds `PickerRefreshCoalescer.swift` — a Foundation-only, headlessly-tested (`PickerRefreshCoalescerTests`) seam that DEBOUNCES streaming-traversal refreshes, SHARED by BOTH the file picker (`PickerView`) and the file-tree sidebar (`FileTreeView`). The name is historical (it was introduced for the picker), but the seam is generic — both stream a large traversal and would otherwise re-do O(N) work per batch, so the tree reuses it verbatim. `public final class PickerRefreshCoalescer` exposes `static let refreshInterval: TimeInterval = 0.033` (~30 fps), an `init(schedule: (@escaping () -> Void) -> Void, perform: () -> Void)` with both closures injected (so tests drive it without a run loop and the live app schedules via `DispatchQueue.main.asyncAfter`), `request()`, and `cancelPending()`. `request()` COALESCES a burst of wakes into ONE trailing refresh: the first call arms the timer, subsequent calls while it is armed are dropped, and the fire clears the armed flag so a later wake re-arms — the load-bearing guarantee that the FINAL / complete traversal wake is never dropped (a later `request()` always reschedules). `cancelPending()` clears the flag (an already-armed timer still fires, but the caller's `refresh()` is a no-op once closed). This turns a large-tree traversal's hundreds of per-batch wakes into a bounded ~30 fps stream of full re-ranks (picker) / reloads (tree) instead of one per batch.

The module also holds two more Foundation-only, headlessly-tested seams that cut the sidebar file tree's projection cost in a large repo (the three-layer performance fix; the `wolf-core` `TreeIndex` / `TreeIndexCache` is Layer 2, these are Layers 1 and 3):

- `TreeChildrenMemo.swift` — `public final class TreeChildrenMemo<Item>` (tested by `TreeChildrenMemoTests`), a per-directory memo of a directory's projected children. `init(project: @escaping (String) -> [Item])` injects the projection; `children(ofDir:) -> [Item]` computes via `project` on first lookup of a directory and returns the cached array thereafter, so `project` (and the FFI `children_of` it wraps) runs **at most once per directory** between invalidations — collapsing AppKit's numberOfChildren/child:index callback storm onto memory. `invalidate()` drops all cached arrays (keeping capacity). In `FileTreeView` the injected closure captures `self` weakly and reuses `itemsByRelPath` for stable identity, so the memo holds the SAME `TreeItem` instances.
- `TreeRefreshGate.swift` — `public final class TreeRefreshGate` (tested by `TreeRefreshGateTests`), a visibility + version gate. `init(isVisible:)`; `requestRefresh() -> Bool` returns true while visible and, while hidden, records a deferred catch-up and returns false; `setVisible(_:) -> Bool` returns true exactly once on a hidden→visible transition that had a deferred refresh (running one catch-up); `shouldReload(version:) -> Bool` returns true only when the snapshot version differs from the last reloaded one (recording it), so a redundant `reloadData()` at an unchanged version is skipped; `resetReloadTracking()` forgets the last version (used on reroot). This is what makes hiding the sidebar actually stop the outline work, and stops a full reload firing on every render wake.

The module also holds `CommandSeam.swift` — an AppKit-free command-kind decode seam (Foundation only, headlessly tested by `CommandSeamTests`), the sibling of `PaneTree`'s `Orientation(ffi:)` / `FocusDir(ffi:)`: `public enum CommandKind` (all twenty-three cases `newWindow`/`closeWindow`/`quitApplication`/`hideApplication`/`minimizeWindow`/`goToFile`/`openFile`/`openFolder`/`closePane`/`newBuffer`/`resetFontSize`/`increaseFontSize`/`decreaseFontSize`/`commandPalette`/`copy`/`paste`/`bufferPicker`/`newTab`/`preview`/`edit`/`terminal`/`previewInBrowser`/`fullWidth`) with a guarded `init?(ffi: UInt8)` decoding the `wolf-ffi` `command_kind` discriminant (0..22 → cases, else `nil` — so `CommandKind(ffi: 22) == .fullWidth` and `CommandKind(ffi: 23) == nil`; `CommandKind` is a plain, non-`RawRepresentable` enum, so the contract is asserted through `init?(ffi:)` rather than `.rawValue`). The module also holds `PreviewSeam.swift` — a pure, AppKit-free Markdown-preview placement seam (Foundation only, headlessly tested by `PreviewSeamTests`), the sibling of `CommandSeam` / `FontSizeSeam`. `PreviewSeam.placementMode(paneCount: Int, activePaneIsPreview: Bool = false, otherPreviewPaneCount: Int = 0) -> String` is the pure placement decision threaded into core's `open_preview(mode)` (requirement 4 / OD3): `<= 1` pane → `"split_right"` (a NEW pane to the right, reusing the `:vsplit` `wolf_layout` intent path — unconditional, a degenerate `0` also falls here); EXACTLY two panes where the active pane is an editor and the OTHER pane already shows a preview (`paneCount == 2 && !activePaneIsPreview && otherPreviewPaneCount == 1`) → `"reuse_preview_pane"` (reuse that other preview pane rather than clobbering the active editor); and otherwise (`> 1`, incl. two panes with the reuse condition unmet) → `"active"` (replace the ACTIVE pane's buffer). The two new inputs default (`false` / `0`), preserving the original two-mode behavior for single-input callers. It also carries the nested pure value type `PreviewLoad` (`Equatable`, `sourceBufnr: Int64` + `sourceTick: UInt64` — the per-window reload key) and the pure helper `winsNeedingReload(current: [Int64: PreviewLoad], loaded: [Int64: PreviewLoad]) -> [Int64]`, which returns the preview WINDOW handles whose bound source `PreviewLoad` differs from what was last loaded (first bind, a CHANGED source buffer even at an equal tick, or an advanced tick). It is now WIRED into the live gate — both `PaneContainerView` gate sites call it — so a preview window reloads when its bound source BUFFER or tick changed, fixing the reused-preview-pane stale render (a single preview window rebound A→B previously kept rendering A because two fresh files share a `changedtick`).

The module also holds `EditSeam.swift` — a pure, AppKit-free Markdown-**edit** placement seam (Foundation only, headlessly tested by `EditSeamTests`), the INVERSE of `PreviewSeam` and its sibling. `EditSeam.placementMode(paneCount: Int, activePaneIsPreview: Bool = true, otherEditorPaneCount: Int = 0) -> String` is the pure placement decision threaded into core's `edit_source(mode)` (OD3 / D3), which navigates the active preview pane back to its SOURCE file: `<= 1` pane → `"split_left"` (a NEW editor pane on the LEFT with the preview kept on the right — reusing the `:vsplit` `wolf_layout` intent path, the source bound into the ORIGINAL window; a degenerate `0` also falls here); EXACTLY two panes where the active IS a preview and the OTHER pane is a non-preview editor (`paneCount == 2 && activePaneIsPreview && otherEditorPaneCount == 1`) → `"reuse_editor_pane"` (edit the source in that other editor pane and focus it); and otherwise (`> 1`, incl. two panes with the reuse condition unmet) → `"active"` (replace the preview in the ACTIVE pane). The two extra inputs default (`true` / `0`). `PaneContainerView` derives the seam's inputs from its pane layout (`editPlacementInputs()`, the mirror of `previewPlacementInputs()`, counting the non-preview editor panes other than the active window), and `WolfWindowController.editSource()` feeds them through the seam and hands the mode to `handle.edit_source(mode)`.

The module also holds `PreviewLinkSeam.swift` — a pure, AppKit-free Markdown-preview **link-classification** seam (Foundation only, headlessly tested by `PreviewLinkSeamTests`), the sibling of `PreviewSeam`. ALL link-routing branching lives here so the `PreviewNavigationDelegate` glue stays thin. `PreviewLinkSeam.Action` (`Equatable`: `.openInBrowser(URL)` / `.scrollToFragment(String)` / `.previewFile(path: String, fragment: String?)`) is the classification result; `classify(url:sourcePath:)` (plan §A) routes a non-`file` scheme (http/https/mailto/…) to `.openInBrowser`, a same-file `#anchor` to `.scrollToFragment` (O1 — JS-scroll, not a native navigation), a same-file no-fragment link and any cross-file link to `.previewFile` (comparing `standardizedFileURL.path` so `/a/./x.md` normalizes); `scrollIntoViewJS(fragmentId:)` synthesizes the `getElementById(...).scrollIntoView(true)` snippet (honoring `scroll-margin-top`) with a hand-written Foundation-only JSON escaper. The `WKNavigationDelegate` glue that calls `NSWorkspace.open` / `evaluateJavaScript` lives in `PreviewNavigationDelegate.swift` (below).

The module also holds the two **terminal-drawer** seams, both Foundation-only and headlessly tested (`DrawerLayoutTests` / `DrawerFocusSeamTests`), both reusing `PaneTree.swift`'s `Rect` / `PaneId` value types so they need no new geometry model. `DrawerLayout.swift` is the pure drawer geometry: `DrawerLayout(paneAreaHeight:hasDrawer:weight:)` splits the pane area into `editorHeight` (which the `PaneTree` tiles over) and `drawerHeight` (`round(paneAreaHeight * weight)`, clamped so `editorHeight` is never negative), with `DrawerLayout.defaultWeight` the fixed ~1/3 matching the `wolf_toggle_terminal` Lua helper's `botright <lines/3>split` (FD3 — no divider-drag resize this pass) and `drawerRect(width:) -> Rect?` vending the full-width bottom strip at `y == editorHeight` (`nil` when no drawer). `DrawerFocusSeam.swift` is the pure editor↔drawer focus-target selection the drawer needs because it is deliberately NOT a `PaneTree` leaf, so `PaneTree.neighbor` cannot resolve it: `DrawerFocusSeam.bottomMostLeaf(_ rects:)` picks the greatest `y + h` (ties → smallest `x`, then smallest `PaneId`), and `DrawerFocusSeam.drawerUpTarget(lastEditorPane:leaves:rects:)` is the `<C-w>k` target — the MRU editor pane when it is still a live leaf, else the `bottomMostLeaf` fallback. `PaneContainerView` wires both into `paneRects()` / `applyFocus()`; that AppKit glue is compile + manual-smoke only.

The module also holds `PaletteSeam.swift` — a pure, AppKit-free (Foundation only, headlessly tested by `PaletteSeamTests`) command-palette sibling of `PickerSeam`. `PaletteSeam.isPaletteTrigger(charactersIgnoringModifiers:command:) -> Bool` is the **Command+P** trigger predicate (`command && first scalar lowercased == "p"`, other modifiers ignored — "p" instead of `PickerSeam`'s "o"), and the nested `PaletteRowKind: UInt8` (`staticCommand = 0` / `switchWindow = 1` / `openRecent = 2`, with a guarded `init?(ffi:)`) mirrors `wolf-ffi`'s `mod palette_row_kind`. **NOTE: `isPaletteTrigger` is DORMANT / UNWIRED.** ⌘P is a menu key-equivalent that preempts `keyDown` (exactly like ⌘N / `ShortcutSeam`), so the View-menu **Command Palette…** item is the real trigger and nothing in `PaneContainerView.keyDown` calls `isPaletteTrigger`; the predicate (and `PaletteSeamTests`) are kept for consistency with `PickerSeam`.

The module also holds `PaneTree.swift` — a third AppKit-free seam (Foundation only, headlessly tested), a port of wolf-gnome's pure `layout.rs` pane-layout tree. It exposes `PaneTree` (a reference type mutated in place) with `split` / `remove` / `leaves` / `paneRects` / `neighbor` / `layout`, the value types `Orientation` (`horizontal`/`vertical`), `FocusDir` (`left`/`right`/`up`/`down`), `Rect`, `PaneId`, and the recursive `PaneLayout` (`.leaf` / `.split(orientation:children:weights:)`). It uses `Double` (not `CGFloat`) so it pulls in no CoreGraphics, and `Orientation.init?(ffi:)` / `FocusDir.init?(ffi:)` decode the `wolf-ffi` discriminants (the contract guarded by `PaneTreeTests`). The TOPOLOGY still matches `layout.rs` EXACTLY — a SAME-orientation split inserts a flat sibling after the target, a PERPENDICULAR split nests (the N-ary frame model matching Neovim and the GNOME tree) — but the **WEIGHT POLICY divergence and the DIVIDER API are deliberate macOS-only additions** (gnome has no weight mutation): a same-orientation split RE-EQUALIZES the row/column to `1/n` each — matching the gnome port, where `:vsplit`/`:split` redistributes to equal shares (a fresh two-child split is 0.5/0.5) — and the ONE remaining divergence from gnome is REMOVE, which RE-NORMALIZES survivors PROPORTIONALLY (so a user-resized layout survives an adjacent pane closing), and the new `Divider` struct + `dividers(width:height:)` / `setPairFraction(path:boundary:leftFraction:)` / static `rebuilt(from:firstLeafId:)` drive interior-divider drag-to-resize and full layout persistence/restore (weight-preservation + the divider API are covered by `PaneTreeWeightsTests`). The macOS `PaneContainerView` consumes `paneRects()` to paint each pane into a computed rectangle in a single flat view (rather than a tree of `NSSplitView`s) plus `dividers()` / `setPairFraction()` to resize by dragging.

The module also holds the three pure divider/persistence seams that back the drag-to-resize + pane-layout persistence feature, all Foundation-only and headlessly tested:

- `DividerHitTest.swift` — `public enum DividerHitTest`, the pure divider PICKING seam. `hit(_ dividers: [PaneTree.Divider], point:, tolerance:) -> PaneTree.Divider?` returns the nearest divider whose zero-thickness line is within `tolerance` AND whose point falls within the divider's span (else `nil`). `PaneContainerView.mouseDown` calls it against `PaneTree.dividers()` before forwarding to nvim. Tested by `DividerHitTestTests`.
- `DividerDragSeam.swift` — `public enum DividerDragSeam`, the pure divider-drag CLAMP (it needs cell size + pixel spans, so it lives here not in the pixel-free `PaneTree`). `clampedLeftFraction(pairStart:pairSpan:pointerPos:orientation:cellWidth:cellHeight:minCols:minRows:leadingOverhead:trailingOverhead:) -> Double` maps a pointer position to a clamped left-child fraction, keeping neither adjacent pane below the per-side minimum (`minCols * cellWidth + overhead` / `minRows * cellHeight + overhead`), a too-small pair yielding the midpoint `0.5`. `PaneContainerView.mouseDragged` feeds it `minCols: 10` / `minRows: 3` (the 3-row / 10-column floor). Tested by `DividerDragSeamTests`.
- `PaneLayoutCodec.swift` — the pure codec bridging the `PaneTree` layout to the persistable + FFI shapes. `public enum SavedPaneNode: Hashable` (`.leaf(path:preview:)` / `.split(orientation:weights:children:)`, plus `leafCount` and the `isEmptyLeaf` predicate) is the serializable mirror keyed by per-leaf buffer path plus a per-leaf `preview` flag (a `preview` leaf's `path` is the SOURCE Markdown file's abs path, restored via `wolf_preview_file` not `:edit`); `isEmptyLeaf` is `true` ONLY for a `.leaf(path: "", preview: false)` (an unnamed, non-preview lone pane) and is what `layoutSnapshot()` checks to SUPPRESS persisting a layout for an empty-state lone pane — a lone pane showing a file or a preview leaf is NOT empty, and a `.split` is never empty; `public enum PaneLayoutCodec` holds `encode(_:paths:previews:)` (leaf ids → buffer paths, marking a leaf a preview when its id is in the `previews` set), `postOrderTokens(_:)` / `decodeTokens(_:)` (the post-order token stream the FFI push-builder replays — the leaf token carries the `preview` flag — and its inverse), and `specJSON(_:)` (the JSON `runtime/nvim/init.lua`'s `wolf_rebuild_layout` decodes; a leaf is `{ "leaf": true, "path": …, "preview": true|false }`). `PaneContainerView.layoutSnapshot()` calls `encode`, `AppDelegate.snapshotNow` replays `postOrderTokens` into the FFI push-builder, and the restore path passes `specJSON` to `WolfCoreHandle.rebuild_layout`. Tested by `PaneLayoutCodecTests`.

The module also holds two more AppKit-free seams (Foundation only, `Double` not `CGFloat`, headlessly tested) that back the pane mouse/scroll wiring:

- `PaneGeometry.swift` — `public struct PaneGeometry`, the per-pane pixel↔cell mapping. It carries a distinct **GRID RECT** (where the Neovim grid is drawn) INSIDE the **PANE RECT**; `init(paneRect:cellWidth:cellHeight:maxCols:)` **caps the grid at `maxCols` columns and CENTERS it horizontally** when the pane is wider than that (equal side margins, `paintOffsetX = inset`), leaving a pane no wider than the cap unaffected (`gridRect == paneRect`, offsets `0`); `maxCols == nil` disables the cap. `PaneContainerView` passes `maxCols: 90` (hard-coded), so a grid wider than 90 columns is centered inside the pane with side margins. It derives `cols` / `rows` (`max(1, floor(gridRect.size / cell))`), `paintOffsetX` / `paintOffsetY` (the grid-rect origin minus the pane-rect origin — the centering inset when capped), and `cellAt(x:y:) -> (row, col)` which maps a pane-local point to a grid cell **clamped** into `[0, cols-1] × [0, rows-1]` (so a point in a margin or past an edge lands on the nearest edge cell).
- `ScrollAccumulator.swift` — `public struct ScrollAccumulator`, a pure signed pixel→line-step accumulator with a carried remainder. `consume(deltaY:cellHeight:) -> Int` returns the signed whole number of line steps for the delta (guarding `cellHeight <= 0` → `0`), keeping the sub-cell remainder for the next call so smooth trackpad scrolling accumulates; `reset()` clears the remainder. It is direction-agnostic (signed); the AppKit layer maps the sign to a scroll direction.
- `CellMetricsMath.swift` — `public enum CellMetricsMath`, a Foundation-only pure seam for the config-driven cell geometry (extracted so it is headlessly unit-tested by `CellMetricsMathTests`). `cellHeight(fontSize:lineHeightPercent:ascent:descent:leading:)` returns `round(fontSize * lineHeightPercent / 100)` — with a `lineHeightPercent <= 0` guard that falls back to the font's natural `ceil(ascent + descent + leading)` — and `baseline(cellHeight:ascent:descent:)` returns `ascent + (cellHeight - ascent - descent) / 2` (recentering the glyph within a taller cell). `CellMetrics` calls these with the config's line-height.
- `FontSizeSeam.swift` — `public enum FontSizeSeam`, Foundation only, the pure step+clamp math backing the View font-size commands (headlessly tested by `FontSizeSeamTests`). It owns the constants `minPointSize = 6`, `maxPointSize = 72`, `step = 1` (all `Double`) and `clamped(_:)`, `increased(_:) = clamped(current + step)`, `decreased(_:) = clamped(current - step)`. It owns ONLY the increment/clamp math; RESET (back to the window's stored default) is handled by the `WolfWindowController`, not the seam.

The module also holds `StatusbarLayout.swift` — an AppKit-/CoreText-free seam (Foundation only, headlessly tested by `StatusbarLayoutTests`) computing the per-pane statusbar strip's vertical layout: `StatusbarLayout(primaryFontSize:secondaryFontSize:verticalPadding:lineGap:)` sizes each line at `ceil(fontSize * 1.25)` (a pinned `lineFactor`), places the primary (filename) line at `verticalPadding` and the secondary (path) line one `lineGap` below its bottom, and sizes the total `height` to leave a matching `verticalPadding` beneath the secondary line — exposing `height`, `primaryLineTop`, `primaryLineHeight`, `secondaryLineTop`, `secondaryLineHeight`. `PaneContainerView` derives the reserved strip height + the two line rects from it; the on-screen bg fill / NSString drawing / truncation are AppKit glue.

The module also holds `EditorInset.swift` — an AppKit-free seam (Foundation only, `Double` not `CGFloat`, reusing `Rect` from `PaneTree.swift`, headlessly tested by `EditorInsetTests`) that computes the **PER-PANE 20pt text-grid inset**: `public struct EditorInset` insets each pane's text grid by `padding` on the left/right, and by `statusbarHeight + padding` on top (the statusbar strip sits flush at the pane's top) / `padding` on the bottom. It owns `static let padding: Double = 20` — the single source of truth (points) consumed by BOTH `PaneContainerView` and `MainWindow`. `init(paneWidth:paneHeight:statusbarHeight:padding:)` derives the PANE-LOCAL `gridRect: Rect` (origin at the pane's top-left): `x = padding`, `y = statusbarHeight + padding`, `w = max(0, paneWidth − 2*padding)`, `h = max(0, paneHeight − statusbarHeight − 2*padding)` — only `w` / `h` clamp to a non-negative floor (so a pane narrower than `2*padding`, or shorter than `statusbarHeight + 2*padding`, never yields negative grid dimensions), while `x` / `y` are FIXED offsets and are NOT clamped. The **per-pane statusbar** (`paintStatusbar`) fills the strip with the macOS titlebar background (the window's own `backgroundColor`, kept in sync with the `WolfTitlebar` theme by `MainWindow.applyTitlebarBackground`, else `theme_titlebar_bg()` / the editor fallback), then draws the pane's base filename (primary line) and display path (secondary, smaller line) from `handle.pane_status_for_grid(grid)` (`filename()` / `display_path()`) via `NSString.draw(in:withAttributes:)` with a `.byTruncatingTail` style; the text is horizontally aligned to the grid text (left edge `gridRect.minX + geo.paintOffsetX`, right edge at the grid right edge) even though the strip bg fills the full strip width, the strip height + line rects come from the pure `StatusbarLayout` (font sizes derived from the grid's `CTFont`), the colors are the themed titlebar fg (secondary at a lower alpha) when set else `labelColor` / `secondaryLabelColor`, and an unnamed buffer shows `[No Name]` with no path line. This statusbar text is the SOLE active/inactive indicator: the active pane's filename is drawn **bold at full strength**, while an inactive pane's filename is regular-weight and both statusbar lines are DIMMED (the themed alphas scaled by `statusbarInactiveAlpha` = 0.5; the non-themed case steps each system label color down one tier). Because the grid is sized from the reduced grid rect, `syncGridSizes` gives nvim the REDUCED rows the grid actually paints into, and the synthetic scrollbar track spans the grid rect (never over the strip). **Mouse** is fully wired through per-pane `PaneGeometry` (each pane's `geometry(for:)`, `maxCols: 90` — the 90-column cap + horizontal centering): `mouseDown` hit-tests the pane rects, `focus_win`s the clicked pane (click-to-focus preserved), maps the point to a grid cell (`geo.cellAt`) and `send_mouse`s a LEFT PRESS on the pane's window grid; `mouseDragged` maps the (clamped) point on the drag's grid and sends a DRAG; `mouseUp` sends a RELEASE and clears the drag grid — so under nvim's `mouse=a` a press→drag→release positions the cursor and selects (visual mode). **Interior dividers are DRAGGABLE to resize:** `mouseDown` FIRST hit-tests `editorDividers()` (`tree.dividers(width:height:)` over the editor `DrawerLayout`, drawer excluded) via `DividerHitTest.hit(..., tolerance: dividerHitTolerance)`; The thumb is **non-interactive** (drag-the-thumb is deferred). Inactive preview panes are no longer dimmed, and it removes web views for no-longer-preview / closed windows (`removePreviewWebView`, a no-leak teardown). **OCCLUSION SKIP:** a pane whose grid rect is FULLY covered by an opaque, loaded, attached preview web view does not paint its grid at all — `draw`'s pane loop samples the live web view into an `OccluderGeometry` (via `previewOccluder(forWin:)`, reading `isHiddenOrHasHiddenAncestor` / `superview === self && window != nil` / `alphaValue` / the `previewLoadedWins` set) and asks the pure `WolfKeyMap.PaneOcclusion.isFullyOccluded(gridRect:by:)`; when it answers `true`, `paintPane` is called with `paintsGrid: false` and returns after the statusbar, **skipping BOTH `paintGrid` AND the `handle.read_frame_for_grid(grid)` FFI call** (skipping the frame read — a whole cell vector across the bridge, one Rust `String` clone per cell — is a material part of the saving, so it is deliberately NOT hoisted above the branch). `drawCursor` is reachable only from `paintGrid` and is therefore skipped too, which is CORRECT: an occluded pane is a preview pane and its cursor is already invisible under the web view. Everything else is UNAFFECTED — the statusbar strip sits OUTSIDE `gridRect` and always paints, and the whole-`bounds` editor-background fill, `drawDividers`, `drawScrollbars` (whose independent `previewNamesByGrid` preview suppression is deliberately NOT coupled to occlusion) and `refreshOverlays` are untouched. `previewLoadedWins` (the `hasLoadedContent` input) is set on a window's FIRST `didFinish` and deliberately NOT cleared on a later reload — WebKit keeps displaying the previous document while the next loads, so clearing it per reload would resume painting the scratch grid under an already-opaque web view on every keystroke, pure paint/unpaint flicker — and it IS cleared in `removePreviewWebView`, which is what restores painting immediately when a preview closes. Correctness for every other geometry change is STRUCTURAL rather than bookkeeping: the containment test has tolerance EXACTLY 0.0 against the same `gridRect(ofPane:)` expression `syncPreviewWebViews` assigns to the web view, so any out-of-sync geometry (mid-live-resize, just after a split, just before a close) fails containment and the grid paints. **This replaces a long-standing wrong assumption in this file's own docs**, which described the preview pane's blank scratch grid as painting underneath "occluded, cheap". - `WakeBridge.swift` — registers the editor `extern "C"` render wake (`wolf_ffi_set_wake`) ONCE at launch; each wake `DispatchQueue.main.async`es onto the main thread, looks the firing core's per-PROJECT `token` up in `WindowRegistry`, and calls `project(for: token)?.onWake()`, which fans the wake out to the project's CURRENT view (`currentView?.onRenderWake()`) — other views hold their last paint. The view's `onRenderWake()` drives `paneContainer.onRenderWake()` then, for a window that has a folder, `tree.onRenderWake()`. ## Building

```sh
bazel build //crates/wolf-macos:WolfRelease     # the OPTIMIZED (-c opt) .app — build this for real use
bazel build //crates/wolf-macos:Wolf            # the DEVELOPMENT .app bundle, -Onone (pinned nvim bundled in)
bazel test  //crates/wolf-macos:WolfKeyMapTests  # the pure WolfKeyMap seams (key, picker, pane, state, command, frame-stats, …)
bazel test  //crates/wolf-macos:bundle_layout_test  # asserts the .app resource layout
bazel run   //crates/wolf-macos:WolfRelease     # launch the optimized .app
bazel run   //crates/wolf-macos:xcodeproj       # generate the (uncommitted) Xcode project
```

`:Wolf` is the fast-iteration DEVELOPMENT build (fastbuild, Swift `-Onone`, Rust unoptimized) and is what the test targets and the Xcode project build against; it is substantially slower at runtime. `:WolfRelease` is the one to build for real use, for installing, and for any performance measurement. Its `.app` path must be resolved from `bazel cquery --output=files //crates/wolf-macos:WolfRelease`, never from `bazel-bin`. See [Building Wolf](../../build.md) for the measured penalty and the exact `cquery` recipe.

`release.bzl` defines the **`opt_bundle`** rule that `:WolfRelease` instantiates. Compilation mode is a CONFIGURATION rather than an attribute, so no `alias` or `macos_application` wiring can change it; `opt_bundle` therefore applies a Starlark **outgoing-edge transition** to its single `bundle` dep, setting `//command_line_option:compilation_mode` to `opt` so the entire subgraph below it (both Swift modules, all Rust crates, the treesitter parsers) is rebuilt optimized without `-c opt` on the command line. It forwards only `DefaultInfo` (the opt-configured `Wolf.zip` plus default runfiles) — deliberately NOT `AppleBundleInfo` / `MacosApplicationBundleInfo` / `AppleExecutableBinaryInfo`, since nothing consumes them here and forwarding Apple providers from a non-Apple rule invites rules_apple to treat the target as an embeddable bundle. The `.app` itself is not a Bazel artifact at all: without `--define=apple.experimental.tree_artifact_outputs` (this repo does not set it) rules_apple leaves `Wolf_archive-root/Wolf.app` on disk as an undeclared sibling of the zip. The rule IS executable: it symlinks the transitioned `macos_application`'s own runner into its predeclared output and forwards the dep's runfiles, which is how that runner locates `Wolf.zip` — the runner's `%app_path%` is a bare CWD-relative runfiles path, so it unzips the bundle into a temp dir and invokes `Contents/MacOS/Wolf` directly, inheriting environment and stdio (dropping the runfiles merge, or passing `--nobuild_runfile_links` / `--enable_runfiles=false`, breaks it). `bazel run //crates/wolf-macos:WolfRelease` therefore launches the optimized app. Direct exec of `"$APP/Contents/MacOS/Wolf"` remains the path for frame-stats measurement, because `bazel run` executes a temporary unzipped copy at a path that changes every launch, re-unzips the whole bundle each time, and interleaves the app's stderr with Bazel's client output. The rule name is kept generic so it could move to `bazel/` later without a rename.

**Formatting the Swift sources:** the advisory `swift-format` targets in [`//tools/lint`](../../tools/lint/README.md) cover this package's hand-written Swift (`Sources/WolfKeyMap`, `Sources/WolfMacOS`, `Tests/WolfKeyMapTests`, enumerated by the `:swift_format_srcs` filegroup here) and EXCLUDE the machine-generated swift-bridge bindings under [`crates/wolf-ffi/generated/`](../wolf-ffi): `bazel test //tools/lint:swift_format` (check) / `bazel run //tools/lint:swift_format.fix` (format in place).

The `.app` bundles a pinned Neovim 0.12.3 tree at `Contents/Resources/nvim/` and the captive `init.lua` at `Contents/Resources/init.lua` (downloaded hermetically by the `//bazel/nvim` module extension — see [`bazel/nvim/README.md`](../../bazel/nvim/README.md) and [Building Wolf](../../build.md)), so a double-clicked `.app` runs with no shell environment. It also bundles the **vendored orlando plugin** at `Contents/Resources/orlando/` (downloaded + sha256-pinned by the `//bazel/orlando` module extension — see [`bazel/orlando/README.md`](../../bazel/orlando/README.md)); this sibling of `init.lua` is loaded by `init.lua` itself (which self-locates the `orlando/` dir and sources it), **not** by Swift. It likewise bundles the **vendored lighthouse colorscheme** at `Contents/Resources/lighthouse/` (downloaded + sha256-pinned by the `//bazel/lighthouse` module extension — see [`bazel/lighthouse/README.md`](../../bazel/lighthouse/README.md)); unlike orlando (a plugin that is auto-sourced), lighthouse is a colorscheme (`colors/lighthouse.lua`) that `init.lua` self-locates and **activates** (prepend to `runtimepath`, then `vim.o.background = "dark"` + `vim.cmd.colorscheme("lighthouse")`), **not** Swift. It also bundles **TWO vendored fonts** into the single `Contents/Resources/fonts/` directory — **JetBrains Mono** (the four static desktop TTF faces `JetBrainsMono-{Regular,Italic,Bold,BoldItalic}.ttf` plus `OFL.txt`, from the `//bazel/jetbrains-mono` module extension — see [`bazel/jetbrains-mono/README.md`](../../bazel/jetbrains-mono/README.md)) and **iA Writer Mono S** (the four static faces `iAWriterMonoS-{Regular,Italic,Bold,BoldItalic}.ttf` plus `LICENSE.md`, from the `//bazel/ia-writer-mono` module extension — see [`bazel/ia-writer-mono/README.md`](../../bazel/ia-writer-mono/README.md)). Both are downloaded + sha256-pinned; both TreeArtifacts use an inner `fonts/` dir, so `rules_apple` merges them into the one `Contents/Resources/fonts/` (their file sets are disjoint, no collision). Unlike the nvim-side assets, the fonts are consumed by **Swift**, not `init.lua`: `FontRegistration.swift` CoreText-registers every TTF at launch so `CellMetrics` resolves both families — **iA Writer Mono S is the config-driven DEFAULT**, JetBrains Mono is bundled + registered but non-default, and Menlo is the fallback when the configured family does not resolve. `bundle_layout_test` asserts that resource layout over the built `.app`, including the orlando resource files, `Contents/Resources/lighthouse/colors/lighthouse.lua`, the four bundled JetBrains Mono TTFs + `OFL.txt` (checks (k)–(o)), and the four bundled iA Writer Mono S TTFs + `LICENSE.md` (checks (p)–(t)) at `Contents/Resources/fonts/`. The icon is verified by build success plus a manual Dock/Finder smoke check only.

## Frame-time instrumentation (dev-only)

The front-end carries an **off-by-default** frame-time measurement surface for finding where main-thread time goes on the keystroke-to-pixel path. The instrumentation itself is measurement only — recording a sample never changes what is painted (the occlusion skip described above is a separate, deliberate render-behavior change in this same crate, not a side effect of measuring) — and it is split the same way every other seam in this crate is: the pure, headlessly-tested aggregation (`WolfKeyMap/FrameStats.swift` — the eight buckets `ctrl.wake` / `cont.wake` / `draw` / `prev.reload` / `prev.render` / `prev.html` / `draw.pane` / `draw.prev` — the last two partition the per-pane `paintPane` work inside a single `draw`, `draw.pane` timing an ordinary editor pane and `draw.prev` a preview pane, selected by whether that pane's grid is a Markdown-preview scratch buffer, so their counts are per-pane-per-frame and their sum is bounded ABOVE by `draw` rather than equal to it, because `draw` also covers the background fill, dividers and scrollbars, roughly 1.6 ms of a measured 45.8 ms `draw` — the exact counters plus a bounded 4096-sample percentile window, nearest-rank percentiles, and the fixed-width `diff`-able report table) lives apart from the process-global glue (`WolfMacOS/FrameMetrics.swift` — the once-only enable check, the monotonic `DispatchTime` clock reads, the `.common`-mode report `Timer`, and the stderr / optional-file writes). `WOLF_FRAME_STATS=1` turns it on, `WOLF_FRAME_STATS_INTERVAL` sets the report period (default 5 s), and `WOLF_FRAME_STATS_FILE` additionally appends each report to a file. With the flag unset the entire cost at each instrumented call site is one `Bool` test; with it set, per sample it is one clock read, one integer subtraction, a few integer accumulates and one array-slot write — no locks, and the snapshot lock is never held. All of its state is **main-thread-only** (enforced by a DEBUG-only `dispatchPrecondition` in `FrameMetrics`). Two caveats when reading a report: the `prev.html` bucket times ONLY the synchronous `loadHTMLString` call, not the async WebKit parse/layout/paint it queues; and `wakes/key` is a counter ratio, hence an upper bound, not real attribution. The `FrameMetrics` glue and every call site are compile-verified + manual-smoke only (no macOS UI test target exists); the pure seam is covered by `FrameStatsTests`. See [Building Wolf](../../build.md) for the exact terminal invocation — a double-clicked `Wolf.app` inherits `launchd`'s stderr and shows nothing.

## Threading

`wolf-core` runs tokio on its own thread(s) and fires a wake on `flush`. The wake is the registered `extern "C"` callback (see `wolf-ffi`); `WakeBridge` hops it onto the AppKit main thread and calls `setNeedsDisplay`, which triggers a `draw(_:)` that reads the current frame. The `WolfCoreHandle` is used only on the main thread (it is not `Send`).

## Known limitations (this increment)

**Multiple windows now supported** under a **one-Neovim-per-PROJECT** model: a `Project` is one captive Neovim shared by N views, each view (a top-level `NSWindow`) bound to one nvim **TABPAGE**; only the focused view live-updates while the others hold their last painted frame until refocused. **⇧⌘N** (File > New Window) ALWAYS opens a new EMPTY-STATE window — a NEW project (a fresh nvim) with one view — no folder (it ignores the frontmost window's cwd; nvim launches at home underneath and the window shows the centered "Open folder…" button with the sidebar hidden); plain **⌘N** is now File > New, a new empty buffer in the current window named the next free `Untitled N.md` (markdown-typed, unsaved, via `wolf_new_untitled`). The `AppDelegate` is a coordinator over `projects: [Project]` + `controllers: [WolfWindowController]` (views); each project's wakes route back through its per-PROJECT `wakeToken` looked up in `WindowRegistry` (token→`Project`), which fans the wake out to its CURRENT view, so two projects never clobber each other's redraws / picker / tree. Closing a view runs `:tabclose` on its tabpage; the project's nvim shuts down only when its LAST view closes. Each view's cwd is its tabpage's `:tcd` (per-view, via `InputEvent::Chdir` → `:tcd`); a view becoming key drives `project.setCurrent` (a `set_current_tabpage` switch) then a refocus rebind that re-derives the pane→grid bindings on the preserved `PaneTree` (nvim WINDOW handles survive the switch, only grid ids churn), gated on `handle.active_tabpage() == tabpageHandle` (`Snapshot.current_tabpage`). The coordinator OWNS the whole-tree state snapshot (a coalesced ~150ms walk of every window/tab group, committed via the `wolf-ffi` snapshot builder) — there is NO per-window `state.json` slot any more (the `windowIndex` / `WindowIndexSeam` / `state_set_*` per-index model is gone); the ghost-slot v1 limitation is retired with it (an unparseable old flat `state.json` is simply ignored and clobbered on exit). Closing one window/tab leaves the others live, and closing the last quits. **Per-window native tabs (Tahoe `NSWindowTabGroup`) have landed**: a shared `tabbingIdentifier` merges every Wolf window into one tab group, **⌘T** (File > New Tab / `:WolfNewTab`, or the native "+" via `newWindowForTab:`) opens a new tab inheriting the current window's folder, and tear-off / drag-to-merge / drag-to-reorder are the native default. A new tab (`⌘T`) is a new VIEW of the KEY window's SAME project (a new tabpage in that shared nvim). Each tab's title is its active buffer's basename (disambiguated on a collision) via the pure `TabTitleSeam`. Restore is **two-phase group-by-cwd** (project identity is NOT persisted): the pure `RestoreSeam.plan` groups the saved `(window, tab, cwd)` tree into projects (one per distinct real cwd, MERGED across windows; each empty-state / deleted-dir tab its OWN project, OD5), Phase A materializes each project + its views, then Phase B assembles the OS windows/tab-groups from the saved geometry (anchor the first surviving view's frame, `addTabbedWindow` the rest, each tab's sidebar per its saved `TabState.sidebar_visible`). A runtime project whose views `:tcd`'d to different dirs is SPLIT on restore; same-dir tabs from different runtime nvims are MERGED — every restored project is uniform-cwd. The multi-window/tab eyeball checklist: ⇧⌘N opens a second EMPTY-STATE standalone window; ⌘T opens a new tab in the current window's tab group inheriting its cwd; the native "+" does the same; tear-off makes a standalone window and drag-merge re-groups; reorder persists; each tab's label is its active-buffer basename; restore reopens the groups with geometry + per-tab sidebar; terminate writes the whole tree.
