# wolf-macos

The macOS front-end: a native **AppKit** application (Swift) that renders the embedded Neovim character grid and forwards keyboard input, over the generated [swift-bridge](../wolf-ffi) surface. It is a thin native shell — native window chrome and a CoreText/CoreGraphics paint backend — over the unchanged, platform-agnostic [`wolf-core`](../wolf-core).

## Design decisions (locked)

- **Tahoe (macOS 26) and newer only** (`LSMinimumSystemVersion` / `minimum_os_version` = `26.0`).
- **AppKit, not SwiftUI.** Implementation language **Swift**; **Xcode 26+**.
- Build is **all-Bazel and authoritative**: `rules_swift` + `rules_apple` build the `.app`; `rules_xcodeproj` generates an **uncommitted** `.xcodeproj` for debugging/LLDB only (`.gitignore`d).
- Rust ↔ Swift via swift-bridge, confined to `wolf-ffi`; the generated bindings are committed.
- **Key translation lives in Rust.** Swift sends a structured `FfiKeyEvent`; `wolf-core` owns nvim notation.

## Modules and sources

### `Sources/WolfKeyMap/` — the pure key seam (no AppKit)

`WolfKeyMap.translate(keyCode:characters:charactersIgnoringModifiers:ctrl:shift:alt:meta:) -> FfiKeyEvent?` is the macOS analog of wolf-gnome's `gdk_key` seam: it takes exactly the data an `NSView.keyDown(_:)` pulls off an `NSEvent` and returns a generated `FfiKeyEvent?`. It imports only Foundation and the generated FFI struct, so it is unit-testable headlessly. It honors the **Shift contract**:

- Named keys (Return, Tab, arrows, F-keys, …) are recognized from `keyCode` first and KEEP the real `shift` flag (so wolf-core can emit `<S-Tab>`, …).
- Printable characters carry the already-shifted glyph in `ch` with `shift = false` (Shift+'a' → 'A', Shift+'1' → '!').
- When ctrl/alt/meta are held, the glyph comes from `charactersIgnoringModifiers` (lowercased), never the modifier-mangled `characters`.
- Bare modifier keys and unmodified control characters map to `nil`.

The module also holds `PickerSeam.swift` — a second AppKit-free seam (`public enum PickerSeam`, Foundation only, headlessly tested) that ports wolf-gnome's pure picker helpers:

- `isPickerTrigger(charactersIgnoringModifiers:ctrl:shift:) -> Bool` — the **Shift+Control+P** trigger predicate (`ctrl && shift && first scalar lowercased == "p"`; alt/meta ignored). Deliberately non-conflicting so every Neovim key, including `<C-p>`, is preserved.
- `nextSelection(current:delta:nRows:) -> Int?` — list navigation clamp (a port of wolf-gnome's `next_selection`; `nil` when there are no rows).
- `restoredIndex(resetToTop:prev:newLen:) -> Int?` — selection restore across streaming result batches (a port of `restored_index`).

The module also holds `PaneTree.swift` — a third AppKit-free seam (Foundation only, headlessly tested), a faithful port of wolf-gnome's pure `layout.rs` pane-layout tree. It exposes `PaneTree` (a reference type mutated in place) with `split` / `remove` / `leaves` / `paneRects` / `neighbor` / `layout`, the value types `Orientation` (`horizontal`/`vertical`), `FocusDir` (`left`/`right`/`up`/`down`), `Rect`, `PaneId`, and the recursive `PaneLayout` (`.leaf` / `.split(orientation:children:weights:)`). It uses `Double` (not `CGFloat`) so it pulls in no CoreGraphics, and `Orientation.init?(ffi:)` / `FocusDir.init?(ffi:)` decode the `wolf-ffi` discriminants (the contract guarded by `PaneTreeTests`). A SAME-orientation split FLATTENS into equal siblings while a PERPENDICULAR split nests — the N-ary frame model matching Neovim and the GNOME tree. The macOS `PaneContainerView` consumes `paneRects()` to paint each pane into a computed rectangle in a single flat view (rather than a tree of `NSSplitView`s).

The module also holds two more AppKit-free seams (Foundation only, `Double` not `CGFloat`, headlessly tested) that back the pane mouse/scroll wiring:

- `PaneGeometry.swift` — `public struct PaneGeometry`, the per-pane pixel↔cell mapping. It carries a distinct **GRID RECT** (where the Neovim grid is drawn) INSIDE the **PANE RECT**; `init(paneRect:cellWidth:cellHeight:maxCols:)` **caps the grid at `maxCols` columns and CENTERS it horizontally** when the pane is wider than that (equal side margins, `paintOffsetX = inset`), leaving a pane no wider than the cap unaffected (`gridRect == paneRect`, offsets `0`); `maxCols == nil` disables the cap. `PaneContainerView` passes `maxCols: 100` (hard-coded), so a grid wider than 100 columns is centered inside the pane with side margins. It derives `cols` / `rows` (`max(1, floor(gridRect.size / cell))`), `paintOffsetX` / `paintOffsetY` (the grid-rect origin minus the pane-rect origin — the centering inset when capped), and `cellAt(x:y:) -> (row, col)` which maps a pane-local point to a grid cell **clamped** into `[0, cols-1] × [0, rows-1]` (so a point in a margin or past an edge lands on the nearest edge cell).
- `ScrollAccumulator.swift` — `public struct ScrollAccumulator`, a pure signed pixel→line-step accumulator with a carried remainder. `consume(deltaY:cellHeight:) -> Int` returns the signed whole number of line steps for the delta (guarding `cellHeight <= 0` → `0`), keeping the sub-cell remainder for the next call so smooth trackpad scrolling accumulates; `reset()` clears the remainder. It is direction-agnostic (signed); the AppKit layer maps the sign to a scroll direction.

The Bazel `wolf_key_map` module compiles `KeyMap.swift`, `PickerSeam.swift`, `PaneTree.swift`, `PaneGeometry.swift`, and `ScrollAccumulator.swift` together with the swift-bridge-generated Swift glue (which provides `FfiKeyEvent`, the `FfiMouseEvent` / `FfiScrollEvent` input structs, the `WolfCoreHandle` / `FfiFrame` wrappers, the `FfiFileSearch` / `FfiFileEntry` picker types, and the `FfiLayoutIntent` / `FfiWinInfo` pane types), so the rest of the app gets those types via `import WolfKeyMap`.

### `Sources/WolfMacOS/` — the AppKit application

- `main.swift` — entry point: `NSApplication.shared`, `.regular` policy, run.
- `AppDelegate.swift` — points wolf-core at the **bundled** Neovim (sets `WOLF_NVIM_BIN` to `Contents/Resources/nvim/bin/nvim` only if a developer hasn't already exported it, via `setenv(..., 0)`), resolves `init_lua` (honoring a `WOLF_INIT_LUA` override, else the bundled `Contents/Resources/init.lua`; the vendored orlando plugin sits beside it at `Contents/Resources/orlando/` and the vendored lighthouse colorscheme at `Contents/Resources/lighthouse/`, both loaded/activated by `init.lua` itself, not Swift) + cwd, calls `wolf_ffi_start`, installs `WakeBridge` / `PickerWakeBridge` / `TreeWakeBridge`, builds the window + the editor-area `PaneContainerView` (registered with `WakeBridge.registeredPaneView`), builds/starts/holds the sidebar `FileTreeView` (registering it with `WakeBridge.registeredTree` and `TreeWakeBridge.registeredTree`), builds/holds the overlay `PickerView` as a subview of the pane container's editor area (wiring `PaneContainerView.onPickerTrigger` to open it), makes the pane container first responder, terminates after the last window, and on terminate `close`s the tree + picker sessions then `shutdown`s the core.
- `MainWindow.swift` — the single "Wolf" `NSWindow`. Its `contentViewController` is an `EditorSplitViewController`; the window uses a transparent `.fullSizeContentView` titlebar and a minimal unified `NSToolbar` (a sidebar toggle + an `NSTrackingSeparatorToolbarItem` aligned to the divider) vended by a retained `EditorToolbarDelegate`. It measures the titlebar/toolbar chrome (`contentView.bounds.height − contentLayoutRect.height`) and sizes the content so the editor pane keeps its exact initial cols × rows below the titlebar, with the **cmdline strip as EXTRA height** (`rows·cellHeight + cmdlineStripHeight`, the 80-col width preserved), then pins the divider at `treePaneWidth` and makes the `PaneContainerView` the `initialFirstResponder`.
- `EditorSplitViewController.swift` — the `NSSplitViewController` content controller: a leading `.sidebar` source-list split item (`NSSplitViewItem(sidebarWithViewController:)` → OS vibrancy + full-height under the titlebar; the higher holding priority is kept so the editor pane absorbs resizing) wrapping the `FileTreeView`, and a trailing content item wrapping the `PaneContainerView`, hosted by a small `HostViewController` (the content host pins the pane container below the `safeAreaLayoutGuide` so the titlebar/toolbar never obscures it). `pinDivider()` pins the sidebar at `treePaneWidth`.
- `PaneContainerView.swift` — the editor area's split-panes container (the macOS analog of wolf-gnome's `pane_view.rs` `PaneInner` + `PaneHandle`), and the editor area's first responder + single global key sink. It is a **single flat `NSView`** (flipped, the proven `GridView` pattern) that paints EVERY pane itself — deliberately NOT a tree of nested `NSSplitView`s. It owns the pure `WolfKeyMap.PaneTree` and a `panes: [PaneId: PaneBinding]` map (each binding is a Neovim `win` + its `boundGrid`, `nil` until resolved). `draw(_:)` computes every pane's rectangle via `PaneTree.paneRects(width, paneAreaHeight)` and, for each bound pane, clips+translates to that rect and paints the pane's window grid (cell backgrounds + CoreText glyphs + the mode-aware cursor when `cursor_visible`); because each pane is painted **independently of Neovim**, an INACTIVE pane gets a translucent dim scrim (a front-end-only treatment that is awkward to express inside Neovim). Thin separators are stroked between adjacent panes, and the bottom one-row **cmdline strip** paints Neovim's command line: under `ext_multigrid` the command line / messages live on a dedicated MESSAGE grid (NOT grid 1), and the cursor moves onto it while the command line is open, so the strip paints the grid the cursor is on when that grid is neither grid 1 nor a window grid (its cursor row), falling back to grid 1's LAST row otherwise — keeping typed `:`/`/` input visible while the editor panes remain shown. `keyDown(_:)` checks `PickerSeam.isPickerTrigger` (→ `onPickerTrigger`) else runs `WolfKeyMap.translate` → `send_key` (keys go to nvim's current window globally). Each pane is painted by `paintGrid`, which first fills the whole pane rect with the grid's own `default_bg()` (so the side margins around a centered grid blend seamlessly into the grid background), paints the (possibly centered) grid at the geometry's paint offset, and dims the WHOLE pane — margins included — when it is inactive. **Mouse** is fully wired through per-pane `PaneGeometry` (each pane's `geometry(for:)`, `maxCols: 100` — the 100-column cap + horizontal centering): `mouseDown` hit-tests the pane rects, `focus_win`s the clicked pane (click-to-focus preserved), maps the point to a grid cell (`geo.cellAt`) and `send_mouse`s a LEFT PRESS on the pane's window grid; `mouseDragged` maps the (clamped) point on the drag's grid and sends a DRAG; `mouseUp` sends a RELEASE and clears the drag grid — so under nvim's `mouse=a` a press→drag→release positions the cursor and selects (visual mode). **Scroll** (`scrollWheel`) is hit-tested from the whole PANE rect (so the future side-margin still scrolls), accumulates `event.scrollingDeltaY` into discrete line steps via a per-view `ScrollAccumulator` (reset when the target grid changes), and `send_scroll`s that many UP/DOWN events on the pane's grid at the pointer cell (using `scrollingDeltaY`'s sign directly — it already reflects the user's natural-scroll setting, so `isDirectionInvertedFromDevice` is NOT re-applied, which would double-invert; a single commented flip point remains). **Synthetic scrollbars** are custom-drawn per pane in `draw(_:)` at the pane's RIGHT edge, driven by the frame's viewport (`topline` / `botline` / `linecount`, 0-based): the thumb size is the visible fraction and its offset is `topline / linecount` (underflow-safe, no `-1`); nothing is drawn when the whole buffer is visible. They follow the macOS "Show scroll bars" setting via `NSScroller.preferredScrollerStyle` — `.legacy` draws always (with a faint track), `.overlay` shows on scroll then fades — reacting live to `NSScroller.preferredScrollerStyleDidChangeNotification` (observer removed in `deinit`). The thumb is **non-interactive** (drag-the-thumb is deferred). On each render wake `onRenderWake()` mirrors `PaneInner::on_render_wake` one-for-one: ensure the initial pane (`pick_initial_window` port), apply drained intents (`drain_intents` → SPLIT creates/splits a pane bound to the new window + `grid_for_win`, FOCUS_DIR resolves `tree.neighbor` and calls `focus_win`), detect closed windows (the live-grid set from `windows()`), resolve pending grids, refresh the active pane (`active_win()`, else the pane whose grid matches `read_frame_for_grid(...).cursor_grid()`), then `syncGridSizes()` (resize grid 1 to the whole view and each bound pane's grid to its rect, but ONLY when the size differs from nvim's current — so it converges, with no resize-feedback loop) and a single `needsDisplay`. AppKit glue, so compile-verified + manual-smoke only.
- `FileTreeView.swift` — the file-tree sidebar `NSView` (an `NSOutlineView` in an `NSScrollView`, `.sourceList` style with a clear background so the `.sidebar` split item's vibrancy shows through — no own `NSVisualEffectView`, no group-row styling) fed by its OWN long-lived `FfiFileSearch` session (`start_tree_search`). The cwd is shown as a single **synthetic root node** (its basename, sentinel rel-path `""`), **expanded on init** with `children_of("")` beneath it and their subdirectories collapsed — the VS Code / Snacks model, **divergent from the GNOME tree** (macOS-only). The sidebar **follows nvim's live cwd**: `start()` roots from `handle.cwd()`, and `onRenderWake()` (editor wake) reads `cwd()` first and **re-roots** (rebuild the root + restart `start_tree_search()`) when it changed (`:cd`/`DirChanged`), mirroring how the picker re-queries `getcwd()`. A single click opens a file (`open(absPath)`, then refocus the editor `PaneContainerView`) or toggles a directory. The current buffer's row is bolded; `onRenderWake()` reveals it on change — expanding the synthetic root then its ancestor dirs (`wolf_ffi_ancestors_to_reveal`) top-down before locating the row, leaving `pendingReveal` set if its file hasn't streamed in; `refresh()` (tree wake) reloads rows preserving expansion and retries the pending reveal.
- `PickerView.swift` — the floating overlay `NSView` panel (an `NSSearchField` + an `NSTableView` in an `NSScrollView`) shown over the editor. `open()` starts an `FfiFileSearch` session and makes the search field first responder; typing filters via `ranked` (ranking in Rust); Up/Down navigate (using `PickerSeam.nextSelection`), selection is restored across streaming batches (`PickerSeam.restoredIndex`); Enter or a double-click calls `open(path)` and closes; Esc closes. While open, the search field holds first-responder status, so `PaneContainerView.keyDown` does not fire and keys are not forwarded to Neovim.
- `PickerWakeBridge.swift` — registers the picker's `extern "C"` wake (`wolf_ffi_set_filesearch_wake`) and, on each wake, `DispatchQueue.main.async`es onto the main thread to call `PickerView.refresh()` (a late wake after the picker closes is a harmless no-op).
- `TreeWakeBridge.swift` — registers the sidebar's `extern "C"` wake (`wolf_ffi_set_tree_wake`) and, on each wake, `DispatchQueue.main.async`es onto the main thread to call `FileTreeView.refresh()` (a late wake after the tree closes is a harmless no-op).
- `CellMetrics.swift` — measures a monospaced `CTFont` (SF Mono → Menlo fallback; `WOLF_FONT_PT` override).
- `Cursor.swift` — cursor-shape rectangle geometry (ported from wolf-gnome's `cursor.rs`); reverse-video colors are resolved in Rust.
- `Color.swift` — packed `FfiColor` → `CGColor`, with white/black fallbacks mirroring wolf-gnome's `paint.rs`.
- `WakeBridge.swift` — registers the `extern "C"` wake thunk (`DispatchQueue.main.async { registeredPaneView?.onRenderWake(); registeredTree?.onRenderWake() }`). The pane container's `onRenderWake()` applies drained layout intents and then marks the single editor view for redisplay (`needsDisplay`), repainting every pane + the cmdline strip in one `draw(_:)`.

## Building

```sh
bazel build //crates/wolf-macos:Wolf            # the .app bundle (pinned nvim bundled in)
bazel test  //crates/wolf-macos:WolfKeyMapTests  # the pure key seam + the pure picker seam
bazel test  //crates/wolf-macos:bundle_layout_test  # asserts the .app resource layout
bazel run   //crates/wolf-macos:xcodeproj       # generate the (uncommitted) Xcode project
```

The `.app` bundles a pinned Neovim 0.12.3 tree at `Contents/Resources/nvim/` and the captive `init.lua` at `Contents/Resources/init.lua` (downloaded hermetically by the `//bazel/nvim` module extension — see [`bazel/nvim/README.md`](../../bazel/nvim/README.md) and [Building Wolf](../../build.md)), so a double-clicked `.app` runs with no shell environment. It also bundles the **vendored orlando plugin** at `Contents/Resources/orlando/` (downloaded + sha256-pinned by the `//bazel/orlando` module extension — see [`bazel/orlando/README.md`](../../bazel/orlando/README.md)); this sibling of `init.lua` is loaded by `init.lua` itself (which self-locates the `orlando/` dir and sources it), **not** by Swift. It likewise bundles the **vendored lighthouse colorscheme** at `Contents/Resources/lighthouse/` (downloaded + sha256-pinned by the `//bazel/lighthouse` module extension — see [`bazel/lighthouse/README.md`](../../bazel/lighthouse/README.md)); unlike orlando (a plugin that is auto-sourced), lighthouse is a colorscheme (`colors/lighthouse.lua`) that `init.lua` self-locates and **activates** (prepend to `runtimepath`, then `vim.o.background = "dark"` + `vim.cmd.colorscheme("lighthouse")`), **not** Swift. `bundle_layout_test` asserts that resource layout over the built `.app`, including the orlando resource files and `Contents/Resources/lighthouse/colors/lighthouse.lua`.

## Threading

`wolf-core` runs tokio on its own thread(s) and fires a wake on `flush`. The wake is the registered `extern "C"` callback (see `wolf-ffi`); `WakeBridge` hops it onto the AppKit main thread and calls `setNeedsDisplay`, which triggers a `draw(_:)` that reads the current frame. The `WolfCoreHandle` is used only on the main thread (it is not `Send`).

## Known limitations (this increment)

Single window only; no native command line / messages / popup menu, and no theming. (The **file picker** — Shift+Control+P — the **file-tree sidebar**, **native split panes** with a bottom **cmdline strip**, and now **mouse / scroll input + per-pane synthetic scrollbars** have all landed; the editor area is now at or ahead of parity with the GNOME shell, which still defers mouse/scroll.) The app now **bundles its own pinned Neovim 0.12.3** + the captive `init.lua` in `Contents/Resources/`, so double-clicking `Wolf.app` works with no shell environment; the `WOLF_NVIM_BIN` and `WOLF_INIT_LUA` development overrides are still honored (an exported value wins). The editor area is a **native pane view**: a single flat `PaneContainerView` that paints every pane itself — it computes each pane's rectangle from the pure `WolfKeyMap.PaneTree` port (`paneRects()`) and paints that pane's window grid into the rect, with a bottom **cmdline strip** painting Neovim's command-line / message grid — under `ext_multigrid` the command line lives on a dedicated message grid (NOT grid 1) that the cursor moves onto, so the strip paints the grid the cursor is on when it is neither grid 1 nor a window grid (falling back to grid 1's last row), keeping the editor panes visible instead of swapping the whole view to grid 1. Because each pane is painted independently of Neovim, an INACTIVE pane gets a translucent dim scrim — a front-end-only treatment that is awkward to express inside Neovim itself. It carries the **same split-pane v1 limitations** as the GNOME shell: only windows opened via the overridden split commands (`<C-w>s`/`v`, `:split`/`:vsplit`) get a pane (`:help` / quickfix / preview / `:diffsplit` windows do not); the cmdline strip shows only a SINGLE row (the message grid's cursor row, or grid 1's last row), so multi-row prompts (`press-ENTER`, `:messages`, a long wrapped `:`-command) are truncated until native `ext_messages` lands; and floating / external windows are ignored. **Divider drag-to-resize is deferred** — splits are equal-weighted (parity with wolf-gnome's v1 divider limitation), and a window resize re-equalizes. A tree of nested `NSSplitView`s would have given divider drag for free, but at the cost of the fragile nested-view compositing that did not render reliably; painting one flat view is the proven `GridView` pattern. The AppKit pane-view glue (`PaneContainerView` — pane-rect painting, the inactive-pane dim, the cmdline strip, click-to-focus, mouse press/drag/release, `scrollWheel`, the custom-drawn synthetic scrollbars, `syncGridSizes`, and the `onRenderWake()` orchestration) is **compile-verified and manual-smoke only** (no headless window server); the pure layout / mouse / scroll decisions live in `WolfKeyMap` — `PaneTree`, and now `PaneGeometry` (pixel↔cell mapping) + `ScrollAccumulator` (scroll-delta accumulation) — which **are** headlessly unit-tested (`//crates/wolf-macos:WolfKeyMapTests`, incl. `PaneGeometryTests` / `ScrollAccumulatorTests`), and the FFI surface it drives (`drain_intents` / `windows` / `grid_for_win` / `active_win` / `focus_win` / `resize_grid` / `read_frame_for_grid`, plus `send_mouse` / `send_scroll` and the `FfiFrame` viewport accessors) **is** covered by the real-nvim `//crates/wolf-ffi:panes` and `//crates/wolf-ffi:mouse_scroll` tests. The max-column-width / centered-grid that `PaneGeometry`'s grid-rect-inside-pane-rect readies is **implemented**: the grid is capped at a hard-coded **100 columns** and centered inside a wider pane, the side margins painted in the grid's own `default_bg` so they blend seamlessly, while the scrollbar stays pinned at the PANE's right edge (out in the right margin, with a visible gap between the grid's right edge and the scrollbar). A pane no wider than 100 columns is unaffected (the grid fills it). Making the 100-column cap configurable is a possible future enhancement, not deferred work. The scrollbar **thumb-drag is deferred** (the thumb is non-interactive). The pane-view eyeball checklist: launch = one editor pane + a thin bottom strip, typing reaches nvim, the editor holds first responder; `:vsplit`/`<C-w>v` = two EQUAL side-by-side panes both live (the pre-existing pane NOT blanked), a third vsplit = three equal columns; `:split`/`<C-w>s` = stacked panes; `<C-w>h/j/k/l` = the active (un-dimmed) pane + cursor move to the geometric neighbour; clicking a pane makes it active (cursor + typing land there) while the inactive panes are dimmed; divider drag is deferred (equal splits), and a window resize re-equalizes; `:close`/`<C-w>c` = the pane disappears, a sibling reclaims the space, survivors stay live; cmdline mode (`:`, `/`) shows in the bottom strip with the editor panes STILL visible; the picker (Shift+Ctrl+P) still overlays the editor and refocuses on close; the file tree opens into the active pane and refocuses; clicking inside a pane positions the cursor there and a click-drag selects (visual mode); the scroll wheel / trackpad scrolls the pane under the pointer (direction per the system natural-scroll setting); a per-pane scrollbar tracks the position/size at the pane's right edge, always-visible under "Show scroll bars: Always" and fading under "When scrolling", updating live when that setting changes; a pane wider than 100 columns shows a 100-column grid centered with equal side margins (painted in the grid's own background so the seam is invisible) while the scrollbar stays at the pane's right edge out in the margin, and a pane narrower than 100 columns has its grid fill the whole pane. Per-cell glyph **text attributes** (bold/italic/underline/undercurl/strikethrough) are resolved and packed by `wolf-ffi` but are NOT yet consumed in painting (only per-cell fg/bg + the mode-aware cursor are painted this increment). Live `draw(_:)` and `keyDown:` are not yet exercised by an automated test (no headless window server); the testable logic is isolated in `WolfKeyMap` and the `wolf-ffi` bridge tests. The AppKit picker UI (the panel rendering, the `NSSearchField` first-responder transfer, the `doCommandBy` routing, table selection, and the dispatched picker-wake reload) is **compile-verified and manual-smoke only**; its pure seam (`PickerSeam`) is headlessly unit-tested and its FFI surface (`FfiFileSearch` / `FfiFileEntry` / `open`) is covered by `//crates/wolf-ffi:file_search`. The AppKit **file-tree sidebar** UI (the `NSOutlineView` data source / delegate, the synthetic cwd-root node expanded-on-init, the live-cwd re-root on each render wake, single-click open / toggle, and the reveal + bold of the current buffer) is likewise **compile-verified and manual-smoke only** (it needs a window server); note its presentation **diverges from GNOME** — macOS shows the cwd as a single root node (VS Code / Snacks model) and follows nvim's live cwd, whereas the GNOME tree shows `children_of("")` directly and is unchanged. Its pure projection lives in `wolf_core::tree` (headlessly unit-tested under `//crates/wolf-core:wolf_core_lib_test`) and its FFI surface (`start_tree_search` / `children_of` / `rel_path_for` / `FfiTreeNode` / `current_file` / `cwd` / `wolf_ffi_ancestors_to_reveal`) is covered by `//crates/wolf-ffi:tree_search`. The window/VC/appearance glue that gives the sidebar its **standard macOS source-list look** — the `EditorSplitViewController` (`NSSplitViewController`) with a `.sidebar` split item, the translucent full-height vibrancy under the transparent `.fullSizeContentView` titlebar, the minimal unified `NSToolbar` (sidebar toggle + tracking separator), and the editor pane pinned below the titlebar — is likewise **compile-verified and manual-smoke only** (it needs a window server): the eyeball checklist is a translucent full-height sidebar under the titlebar, source-list selection styling, the toolbar toggle collapsing/expanding the sidebar with the tracking separator staying aligned to the divider, the editor still ~80 × 24 with the picker overlaying it, tree click / reveal / expand + live-cwd re-root working, and the editor holding first responder so typing reaches nvim on launch. The live nvim→FFI round-trip **is** covered on the macOS Bazel host: the `//crates/wolf-ffi:bridge_smoke` test passes under `bazel test`, exercising the full round-trip (start, type, observe the grid, resize, shut down) against the bundled/pinned Neovim 0.12.3. The GUI window rendering itself (and Finder double-click) is still not headlessly asserted.
