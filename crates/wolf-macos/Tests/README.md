# wolf-macos/Tests

The Swift tests for the macOS front-end. The Bazel target is `//crates/wolf-macos:WolfKeyMapTests`; it runs regardless of `WOLF_NVIM_BIN` (it needs no Neovim) and covers the pure seams — the key seam (`KeyMapTests.swift`), the picker seam (`PickerSeamTests.swift`), the command-palette seam (`PaletteSeamTests.swift`), the pane-layout seam (`PaneTreeTests.swift`), the per-pane geometry seam (`PaneGeometryTests.swift`), the scroll-accumulator seam (`ScrollAccumulatorTests.swift`), the glyph-style seam (`GlyphStyleTests.swift`), the state-restore seam (`StateSeamTests.swift`), the command-decode seam (`CommandSeamTests.swift`), the Markdown-preview placement seam (`PreviewSeamTests.swift`), the Markdown-edit placement seam (`EditSeamTests.swift`), the Markdown-preview link-classification seam (`PreviewLinkSeamTests.swift`), the font-size seam (`FontSizeSeamTests.swift`), the per-pane statusbar vertical-layout seam (`StatusbarLayoutTests.swift`), the per-pane statusbar horizontal text-span seam (`StatusbarTextSpanTests.swift`), the new-window trigger seam (`ShortcutSeamTests.swift`), the tab-title seam (`TabTitleSeamTests.swift`), the editor-inset seam (`EditorInsetTests.swift`), the picker-panel positioning seam (`PickerPanelSeamTests.swift`), the group-by-cwd restore seam (`RestoreSeamTests.swift`), and the appearance-decode seam (`AppearanceSeamTests.swift`).

## `WolfKeyMapTests/KeyMapTests.swift`

Pure, headless `XCTest` coverage of the AppKit-free `WolfKeyMap.translate(...)` seam — the macOS analog of wolf-gnome's headless `gdk_key` tests. It exercises the function with scalar inputs only (no `NSEvent`, no window, no event loop) — exactly the data an `NSView.keyDown(_:)` pulls off an `NSEvent` — and asserts the **Shift contract**, which must match `wolf-core/src/input.rs`:

- a plain printable char maps to `Char` with all flags false;
- a shifted printable (`Shift+a` → `A`, `Shift+1` → `!`) delivers the already-shifted glyph in `ch` with `shift = false` (Swift never sets `shift` on a `Char`);
- named keys (Return, Escape, Tab, forward-delete, the arrows, Home/End/PageUp/ PageDown, F1/F5) are recognized from `keyCode` and **keep** the real `shift` (`Shift+Tab`, `Shift+Left` stay `shift = true`);
- ctrl/alt/meta combos take the glyph from `charactersIgnoringModifiers` (lowercased) — `Ctrl+w` → `w` (not U+0017), `Alt+x` → `x`, `Cmd+s` → `s`, `Ctrl+Shift+w` → `w` with `shift = false`;
- bare modifier keys and unmodified control characters map to `nil`.

The test pins the `Kind` discriminants and the `kVK_*` virtual key codes (notably Backspace = `kVK_Delete` 0x33 and forward-delete = `kVK_ForwardDelete` 0x75) so they stay in lockstep with the Rust `FfiKeyEvent` `kind` scheme and the Swift `WolfKeyMap`.

## `WolfKeyMapTests/PaneGeometryTests.swift`

Pure, headless `XCTest` coverage of the AppKit-free `WolfKeyMap.PaneGeometry` seam (`@testable import WolfKeyMap`, reusing `PaneTreeTests`' `eps` / `approx` style with a non-square `8 × 16` cell so column and row math are distinguishable). Cases: with `maxCols == nil` `gridRect == paneRect` and both paint offsets are `0`; `cols` / `rows` derive from the cell size (`800 × 480` at `8 × 16` → `100 × 30`, a sub-cell pane clamps to `1 × 1`); `cellAt` maps an interior point (`3.5 × 2.5` cells → `col 3, row 2`); `cellAt` clamps a left/top-margin point to `(0, 0)`; clamps a far-corner point to `(cols-1, rows-1)` (the off-by-one edge guard); and subtracts a non-zero pane origin (an origin-relative point maps correctly, the pane origin maps to `(0, 0)`). It also covers the **max-column cap + centering**: a pane WIDER than the cap caps `cols` to the cap (e.g. `100`) and centers the `gridRect` (equal side margins, `paintOffsetX` = the centering inset); a pane NARROWER than the cap is unaffected (`gridRect == paneRect`, offset `0`); an EXACT-boundary pane produces no margin; and `cellAt` on a centered grid clamps points in the left/right side margins to the nearest edge column while mapping an interior point through the paint offset.

## `WolfKeyMapTests/ScrollAccumulatorTests.swift`

Pure, headless `XCTest` coverage of the AppKit-free `WolfKeyMap.ScrollAccumulator` seam (`@testable import WolfKeyMap`), the signed pixel→line-step accumulator with a carried remainder. Cases: a whole `±cellHeight` of `deltaY` yields exactly `±1` step; two sub-cell (`0.6h`) nudges yield `0` then `1` (crossing at `1.2h`); the remainder carries across calls (`1.5h` → `1` step + a `0.5h` remainder, then a further `0.5h` completes another step); a sign change reverses (`+1.5h` → `+1` step + `+0.5h` remainder, then `-2h` → remainder `-1.5h` → `-1` step); and a zero (non-positive) `cellHeight` short-circuits to `0` (no divide-by-zero / infinite loop).

## `WolfKeyMapTests/StatusbarTextSpanTests.swift`

Pure, headless `XCTest` coverage of the AppKit-/CoreGraphics-free `WolfKeyMap.StatusbarTextSpan` seam (`@testable import WolfKeyMap`, reusing `StatusbarLayoutTests`' `eps` + `assertInvariants` style) — the per-pane statusbar's HORIZONTAL text-span math, the sibling of the vertical `StatusbarLayoutTests` above. Pane kind arrives as a plain `PaneContentKind` enum, so no Neovim state participates and the rest is rect arithmetic. Thirteen tests, with the wide-pane offsets DERIVED the way `PaneGeometry` derives them (`max(0, (gridWidth − min(gridWidth, 90 * cellWidth)) / 2)` at a representative `cellWidth == 8`, so `1400 → 340`) rather than made up: editor + preview on a narrow pane (below the cap there is no offset, so the fix is a no-op and both kinds coincide); editor on a wide pane (`left == gridLeft + paintOffsetX`, `width == gridWidth − paintOffsetX`, and — the top regression guard — `left + width == gridLeft + gridWidth`, pinning that the editor's right edge stays at `gRect.maxX`); preview on a wide pane (`left == gridLeft`, ignoring `paintOffsetX`, `width == gridWidth`, both edges on the uncentered grid rect); the **kind-difference invariant** (`editor.left − preview.left == paintOffsetX` on a wide pane, identical spans on a narrow one) — the assertion that most directly encodes the bug; a non-zero `gridLeft` (`20` and a `512` right-hand split) proving `left` is ABSOLUTE, never pane-local; and the degenerate / defensive edges — a zero-width grid, a pane narrower than `2 * padding` (whose grid width `EditorInset` clamps to 0 while its unclamped grid origin sits past the pane's right edge), a `paintOffsetX` larger than the grid (editor `width` floors at 0, `left` clamps to the right edge; preview unaffected), a negative `paintOffsetX` (clamps to 0), and exactly at the 90-column cap (no offset, both kinds identical — `paintOffsetX` is CONTINUOUS across the threshold, so no jump as a window is dragged across it). A universal-invariants sweep (`width >= 0`, `left >= gridLeft`, `left + width <= gridLeft + max(0, gridWidth)`) runs both kinds over every case incl. a negative grid width, and a final **editor sweep across the cap threshold** (below / just below / exactly at / just above / far above, at two `gridLeft`s) checks the `.editor` branch against the LEGACY expression written out longhand — an independent check, not the seam's own arithmetic — so "editor panes are bit-identical" is pinned across the whole threshold, not at a single point.

What these tests CANNOT prove: that the statusbar text origin and the LIVE `WKWebView` frame coincide on screen is an integration property spanning `paintStatusbar`, `syncPreviewWebViews`, and the markdown CSS's zero left padding. The tests pin only the shared arithmetic both consumers derive from; the guarantee that a pane is never drawn with `.preview` alignment while it has no webview comes from `syncPreviewWebViews` writing the pane-kind map and the webview frames in the SAME pass, and does NOT extend to frame freshness (a webview frame can lag a resize or font-size change until the next wake — pre-existing, documented in that function's doc comment). The remainder rests on visual review: open a preview in a window wider than 90 columns and confirm the statusbar filename's left edge sits on the first heading's left edge. Note that in a vertical split each pane is typically narrower than 90 cells, so `paintOffsetX == 0` and the two kinds coincide — the bug and the fix are only observable on WIDE panes, and a reviewer testing in a split may see no difference.
