# wolf-macos/Sources

The Swift sources for the macOS front-end, split into two modules. See the crate [`README.md`](../README.md) for the design decisions and the build workflow.

## `WolfKeyMap/` — the pure key seam (no AppKit)

Five deliberately AppKit-free files, so they are unit-testable headlessly (the macOS analog of wolf-gnome's `gdk_key`, pure picker, and pure pane-layout seams). The Bazel `wolf_key_map` module compiles them together with the swift-bridge-generated Swift glue, so the rest of the app gets the generated types (`FfiKeyEvent`, `FfiMouseEvent`, `FfiScrollEvent`, `WolfCoreHandle`, `FfiFrame`, `FfiFileSearch`, `FfiFileEntry`, `FfiTreeNode`, `FfiLayoutIntent`, `FfiWinInfo`, the free `wolf_ffi_ancestors_to_reveal`, …) via `import WolfKeyMap`.

- **`KeyMap.swift`** — `WolfKeyMap.translate(keyCode:characters:charactersIgnoringModifiers:ctrl:shift:alt:meta:) -> FfiKeyEvent?`. It imports only Foundation and the generated FFI struct. Named keys (Return, Tab, arrows, F-keys, …) are recognized from the virtual `keyCode` first and **keep** the real `shift` flag; printable characters carry the already-shifted glyph in `ch` with `shift = false`; when ctrl/alt/meta are held the glyph comes from `charactersIgnoringModifiers` (lowercased); bare modifiers and unmodified control characters return `nil`. The `Kind` discriminants mirror `wolf_core::Key`'s variant order (and the Rust `key_event_from_ffi`).
- **`PickerSeam.swift`** — `public enum PickerSeam`, Foundation only, ports wolf-gnome's pure picker helpers: `isPickerTrigger(charactersIgnoringModifiers:ctrl:shift:) -> Bool` (the **Shift+Control+P** trigger — `ctrl && shift && first scalar lowercased == "p"`, alt/meta ignored — deliberately non-conflicting so every Neovim key including `<C-p>` is preserved), `nextSelection(current:delta:nRows:) -> Int?` (list-nav clamp, port of `next_selection`), and `restoredIndex(resetToTop:prev:newLen:) -> Int?` (selection restore across streaming result batches, port of `restored_index`).
- **`PaneTree.swift`** — a Foundation-only port of wolf-gnome's pure `layout.rs` pane-layout tree, `import Foundation` ONLY (it uses `Double`, not `CGFloat`, so it pulls in no CoreGraphics and stays in the headless test bundle). Public API: `typealias PaneId = UInt64`; `enum Orientation { horizontal, vertical }` and `enum FocusDir { left, right, up, down }` (each with an `init?(ffi:)` decoding the `wolf-ffi` discriminants); `struct Rect`; the `indirect enum PaneLayout { .leaf(PaneId); .split(orientation:children:weights:) }`; and `final class PaneTree` (a reference type, mutated in place) with `init(root:)`, `split(_:_:_:)`, `remove(_:)`, `leaves()`, `paneRects(width:height:)`, `neighbor(_:_:width:height:)`, and `layout()`. The free helpers (`splitIn`, `removeIn`, `normalize`, `collectLeaves`, `collectRects`, `directionalDistance`, `xOverlap`, `yOverlap`, `equalize`) are ported exactly: a SAME-orientation split inserts after the target then re-equalizes (FLATTENING into equal siblings), a PERPENDICULAR split nests, `remove` never empties the tree and re-equalizes / collapses a single child, and `neighbor` uses strictly-positive cross-axis overlap with stable DFS order. The macOS `PaneContainerView` consumes `paneRects()` to paint each pane into a computed rectangle — a single flat view, not an `NSSplitView` tree. Headlessly unit-tested by `PaneTreeTests` (a 1:1 port of the `layout.rs` suite + a discriminant-contract test).
- **`PaneGeometry.swift`** — `public struct PaneGeometry`, Foundation only (`Double`, reusing `Rect` from `PaneTree.swift`), the per-pane pixel↔cell mapping seam. It holds a **GRID RECT** inside a **PANE RECT**; `init(paneRect:cellWidth:cellHeight:maxCols:)` with `maxCols: Int? = nil` today ALWAYS yields `gridRect == paneRect`. The `maxCols` parameter reserves a FUTURE max-column-width / centered grid (a narrower, centered grid rect) so all coordinate mapping already routes through this seam — but the capping is **DEFERRED / not implemented** (architected-for only; `nil` everywhere). It exposes `cols` / `rows` (`max(1, floor(gridRect.size / cell))`), `paintOffsetX` / `paintOffsetY` (grid-rect origin − pane-rect origin, `0` today), and `cellAt(x:y:) -> (row, col)` mapping a pane-local point to a grid cell **clamped** into `[0, cols-1] × [0, rows-1]` (a margin / past-edge point lands on the nearest edge cell). Headlessly unit-tested by `PaneGeometryTests`.
- **`ScrollAccumulator.swift`** — `public struct ScrollAccumulator`, Foundation only, a pure signed pixel→line-step accumulator with a carried remainder. `consume(deltaY:cellHeight:) -> Int` returns the signed whole line steps for the delta (guarding `cellHeight <= 0` → `0`) and keeps the sub-cell remainder across calls so smooth trackpad scrolling accumulates; `reset()` clears it. Direction-agnostic (signed); the AppKit layer maps the sign to a scroll direction. Headlessly unit-tested by `ScrollAccumulatorTests`.

## `WolfMacOS/` — the AppKit application

The `wolf_macos_lib` module: the native shell that links AppKit / CoreText / CoreGraphics and depends on `:wolf_key_map` and the `wolf-ffi` archive.

- **`main.swift`** — the entry point: `NSApplication.shared`, install the `AppDelegate`, `.regular` activation policy, `app.run()`.
- **`AppDelegate.swift`** — resolves `init_lua` (a `WOLF_INIT_LUA` override, else the bundled `Contents/Resources/init.lua`) and the cwd, calls `wolf_ffi_start`, installs the `WakeBridge`, `PickerWakeBridge`, and `TreeWakeBridge`, builds the window + the editor-area `PaneContainerView` (registering it with `WakeBridge.registeredPaneView`), builds/starts/holds the sidebar `FileTreeView` (registering it with BOTH `WakeBridge.registeredTree` — for current-file reveal on the render wake — and `TreeWakeBridge.registeredTree` — for row rebuilds on the tree wake), builds/holds the overlay `PickerView` over the pane container's editor area (wiring `PaneContainerView.onPickerTrigger` to open it), makes the pane container first responder, terminates after the last window, and on terminate `close`s the tree + picker sessions before `shutdown`ing the core (showing a fatal alert if the core fails to start).
- **`MainWindow.swift`** — the single "Wolf" `NSWindow`. Its `contentViewController` is an `EditorSplitViewController`; the window uses a transparent `.fullSizeContentView` titlebar (`titlebarAppearsTransparent = true`, `titleVisibility = .visible`) and a minimal unified `NSToolbar` (`toolbarStyle = .unified`) vended by a retained `EditorToolbarDelegate` (`.toggleSidebar`, an `NSTrackingSeparatorToolbarItem` bound to the split divider, and `.flexibleSpace`; the delegate is held in a `let` because `NSToolbar.delegate` is weak). After the content VC + toolbar are attached, it measures the titlebar/toolbar chrome (`contentView.bounds.height − contentLayoutRect.height`) and sets the content size to `treePaneWidth + dividerThickness + cols·cellWidth` × `rows·cellHeight + cmdlineStripHeight + chrome` so the editor PANE keeps its exact initial cols × rows below the titlebar with the **cmdline strip as EXTRA height** (the OCR-checked 80-col grid is undisturbed); it then pins the divider at `treePaneWidth` and sets `initialFirstResponder = paneContainer`. `.toggleSidebar` routes up the responder chain to the split VC (no wiring).
- **`EditorSplitViewController.swift`** — the `NSSplitViewController` backing the window content: a leading `.sidebar` split item (`NSSplitViewItem(sidebarWithViewController:)` → OS vibrancy, full-height under the titlebar, collapsible, with the higher holding priority that makes the EDITOR pane absorb resizing — NOT lowered) wrapping the `FileTreeView`, and a trailing content item wrapping the `PaneContainerView`; `minThickness` / `maxThickness` bound the sidebar width and `pinDivider()` pins it at `MainWindow.treePaneWidth`. Both panes are hosted by a small `HostViewController`: the SIDEBAR host adopts the `FileTreeView` directly as its `view` (so the `.sidebar` material fills the pane), while the CONTENT host pins the `PaneContainerView` leading/trailing/bottom to a container and its **top to the container's `safeAreaLayoutGuide.topAnchor`**, so the editor is not obscured by the transparent titlebar/toolbar. Compile-verified + manual-smoke only (no window server).
- **`FileTreeView.swift`** — the file-tree sidebar `NSView` (an `NSOutlineView` in an `NSScrollView`), fed by an `FfiFileSearch` session started via `start_tree_search`. The cwd itself is shown as a single **synthetic root node** (`makeRoot(_:)`: a directory `TreeItem` whose name is the cwd's basename, with the sentinel rel-path `""`, kept OUT of `itemsByRelPath`); `children(of:)` branches explicitly — `nil` → `[rootItem]`, a `TreeItem` → `children_of(relPath)` (the root's `""` → `children_of("")`). Real children are cached as identity-stable `TreeItem`s by `relPath` in `itemsByRelPath`. The outline uses the standard `.sourceList` style (which drives the sidebar row metrics — no explicit `rowHeight`) and draws a **clear background** (`outlineView.backgroundColor = .clear`, `scrollView.drawsBackground = false`); the vibrancy material comes from the enclosing `.sidebar` split item, so the view adds **no own `NSVisualEffectView`** (avoiding double vibrancy). The synthetic cwd root stays a normal selectable/expandable row (no `isGroupItem` group-row styling). The root is **expanded on init** (`refresh()` calls `expandItem(rootItem)` once, guarded by `didInitialExpand`, after the root has streamed children) with its subdirectories collapsed — the VS Code / Snacks model, **divergent from the GNOME tree**. A single click opens a file (`handle.open(absPath)` then refocus the editor `PaneContainerView`) or toggles a directory. The sidebar **follows nvim's live cwd**: `start()` roots from `handle.cwd().toString()`; `onRenderWake()` (editor wake) reads `cwd()` FIRST and, when it changed, `reroot(to:)` (rebuild the root, restart `start_tree_search()`, clear `itemsByRelPath`, reset `didInitialExpand`, re-arm `pendingReveal = currentFileAbs`), THEN reads `current_file()`, guards on `lastCurrent`, and on a change re-bolds + reveals. `refresh()` (tree wake) reloads rows preserving expansion + retries `pendingReveal`; `reveal` expands the synthetic root, then the ancestor dirs (`wolf_ffi_ancestors_to_reveal`, top-down) before `row(forItem:)`, leaving `pendingReveal` set when `rel_path_for` returns `""`. NSOutlineView glue is exercised by manual smoke only (it needs a window server), like the picker.
- **`PaneContainerView.swift`** — the editor area's split-panes view (the macOS analog of wolf-gnome's `pane_view.rs`), and the editor area's first responder + single global key sink. It is a **single flat `NSView`** (flipped, the proven `GridView` pattern) that paints EVERY pane itself — deliberately NOT a tree of nested `NSSplitView`s, which composited unreliably when stacked under the source-list split. It owns the pure `WolfKeyMap.PaneTree` and a `panes: [PaneId: PaneBinding]` map (each `PaneBinding` is a Neovim `win` + its `boundGrid`, `nil` until resolved). `draw(_:)` computes every pane's rectangle via `PaneTree.paneRects(width, paneAreaHeight)` and, for each bound pane, clips+translates to that rect and paints the pane's window grid (cell backgrounds + CoreText glyphs + the mode-aware cursor when `cursor_visible`); each pane is drawn **independently of Neovim**, so an INACTIVE pane gets a translucent dim scrim (`inactiveDim`) — a front-end-only treatment that is awkward to express inside Neovim. Thin separators are stroked between adjacent panes, and the bottom one-row **cmdline strip** paints Neovim's command line: under `ext_multigrid` the command line / messages live on a dedicated MESSAGE grid (NOT grid 1), positioned at the bottom via `msg_set_pos` (which the core drops), and the cursor moves onto it while the command line is open — so the strip identifies that grid as "the grid the cursor is on that is neither grid 1 nor a window grid" and paints its cursor row (with the cursor), falling back to grid 1's LAST row otherwise. `keyDown(_:)` checks `PickerSeam.isPickerTrigger` (→ `onPickerTrigger`) else runs `WolfKeyMap.translate` → `send_key` (keys go to nvim's current window globally). **Mouse / scroll** route through a per-pane `PaneGeometry` (`geometry(for:)`, `maxCols: nil`): `mouseDown` `focus_win`s the clicked pane (click-to-focus preserved) and `send_mouse`s a LEFT PRESS at `geo.cellAt(point)` on that pane's grid; `mouseDragged` / `mouseUp` send DRAG / RELEASE on the drag's grid (clamped), so `mouse=a` gives cursor-position + visual selection. `scrollWheel` hit-tests from the whole PANE rect (future side-margin still scrolls), accumulates `scrollingDeltaY` into line steps via a `ScrollAccumulator` (reset on grid change), and `send_scroll`s UP/DOWN on the pane's grid at the pointer cell (using `scrollingDeltaY`'s sign directly — it already reflects the user's natural-scroll setting, so `isDirectionInvertedFromDevice` is NOT re-applied, which would double-invert; a single commented flip point remains). **Synthetic scrollbars** are custom-drawn per pane in `draw(_:)` at each pane's right edge from the frame viewport (`topline` / `botline` / `linecount`, 0-based; thumb offset `topline / linecount`, underflow-safe, nothing drawn when the whole buffer is visible), following `NSScroller.preferredScrollerStyle` (`.legacy` always + faint track / `.overlay` fade after scroll) and reacting to `NSScroller.preferredScrollerStyleDidChangeNotification` (observer removed in `deinit`); the thumb is **non-interactive** (drag deferred). `onRenderWake()` mirrors GNOME's orchestration: `ensureInitialPane` (a `pick_initial_window` port — prefer `active_win()` if it is a real window grid `>= 2` and not hidden, else the lowest visible window grid from `windows()`, reusing the tree's root `firstPaneId`), `applyIntents` (`drain_intents` → SPLIT splits the `from`/active pane in the tree and binds a new pane to the new window via `grid_for_win` — 0 → pending; FOCUS_DIR resolves `tree.neighbor` and calls `focus_win`), `detectCloses` (the live-grid set from `windows()`; a pane whose bound grid vanished is removed, never below one leaf), `resolvePendingGrids`, `updateActivePane` (the pane whose `win == active_win()`, else whose bound grid `== read_frame().cursor_grid()`), then `syncGridSizes` (resize grid 1 to the whole view and each bound pane's grid to its rect, but ONLY when the size differs from nvim's current — so it converges, no resize-feedback loop) and a `needsDisplay`. **Divider drag-to-resize is deferred** (splits are equal-weighted, parity with wolf-gnome's v1 divider limitation; `NSSplitView` would have given drag for free but at the cost of the fragile nesting). AppKit glue, so compile-verified + manual-smoke only.
- **`PickerView.swift`** — the floating overlay `NSView` panel (an `NSSearchField`
  - an `NSTableView` in an `NSScrollView`) shown over the editor, fed by an `FfiFileSearch` session over the FFI. `open()` starts the session and makes the search field first responder; typing filters via `ranked` (ranking in Rust), Up/Down navigate (`PickerSeam.nextSelection`) with selection restored across streaming batches (`PickerSeam.restoredIndex`), Enter or a double-click calls `open(path)` and closes, Esc closes. While open the search field is first responder, so `PaneContainerView.keyDown` does not fire and keys are not forwarded to Neovim.
- **`PickerWakeBridge.swift`** — registers the picker's `extern "C"` wake (`wolf_ffi_set_filesearch_wake`) and, on each streaming-traversal wake, `DispatchQueue.main.async`es onto the main thread to call `PickerView.refresh()` (a late wake after the picker closes is a harmless no-op). It mirrors `WakeBridge`, but drives the picker independently of editor repaints.
- **`TreeWakeBridge.swift`** — registers the sidebar's `extern "C"` wake (`wolf_ffi_set_tree_wake`) and, on each streaming-traversal wake, `DispatchQueue.main.async`es onto the main thread to call `FileTreeView.refresh()` (a late wake after the tree closes is a harmless no-op). The clone of `PickerWakeBridge` for the tree's own long-lived `start_tree_search` session.
- **`CellMetrics.swift`** — measures a monospaced `CTFont` (advance width, ascent + descent + leading, baseline) for SF Mono with a Menlo fallback, `WOLF_FONT_PT` overridable. (Per-cell text attributes are packed by `wolf-ffi` but not yet painted, so only the base font is used.)
- **`Cursor.swift`** — pure cursor-rectangle geometry (block / horizontal / vertical bar from `cursor_shape` + `cursor_cell_percentage`), ported from wolf-gnome's `cursor.rs`; the reverse-video fill/glyph colors are resolved in Rust.
- **`Color.swift`** — converts a packed `FfiColor` (`0x00RRGGBB` + `set`) to a `CGColor`, applying the white/black fallbacks that mirror wolf-gnome's `paint.rs`.
- **`WakeBridge.swift`** — registers the `extern "C"` wake thunk with the core (`wolf_ffi_set_wake`); on each wake it `DispatchQueue.main.async`es onto the AppKit main thread, calls the registered `PaneContainerView.onRenderWake()` (which applies drained layout intents and marks every pane + the cmdline strip for redisplay — the wake → dispatch-to-main → orchestrate-and-redraw realization, replacing the old single-`GridView` `needsDisplay` nudge), then calls the registered `FileTreeView.onRenderWake()` so the sidebar reveals + bolds the current buffer (a `current_file` change rides the render wake, not a separate traversal batch).
