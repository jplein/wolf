# wolf-gnome

The GTK 4 / libadwaita platform front-end for Wolf, the Markdown editor that embeds Neovim (see [`architecture.md`](../../architecture.md), esp. the front-end section and decision 2 on native paint). It consumes [`wolf-core`](../wolf-core/README.md) as a normal Rust crate dependency.

## Scope

This crate is a **runnable single-window GTK 4 / libadwaita application**. The window is one `adw::ApplicationWindow` (with an `adw::HeaderBar`) whose content is a horizontal `gtk::Paned`: a **file-tree sidebar** on the left (see [The file-tree sidebar](#the-file-tree-sidebar)) and, on the right, a **native pane view** inside a `gtk::Overlay` that also hosts the file picker and the empty state. The pane view is a tree of nested `gtk::Paned`s — one `gtk::DrawingArea` per Neovim window, driven by a pure `PaneTree` layout — plus a bottom **cmdline strip** that paints the native command line / messages from the folded `Snapshot::cmdline` / `Snapshot::toast` (under `ext_messages`, grid 1 empties and `cmdheight=0`; the Adw completion popup + multi-line toast are deferred for GTK, OD4). **Split panes** work: split (`<C-w>s`/`v`, `:split`/`:vsplit`), close (`<C-w>c`), focus moves (`<C-w>h/j/k/l`), and divider drag-to-resize, driven by `wolf-core`'s layout-intent channel.

The window also carries a GNOME **primary menu** (the header bar's hamburger `gtk::MenuButton`, see [The primary menu](#the-primary-menu)), an **empty state** shown when no project is open (see [The empty state](#the-empty-state)), and a **command drain**: `WolfCore::drain_commands()` runs on every render wake and each queued `Command` is dispatched through the pure, total `command_action::ui_action_for` mapping. The menu, the [keyboard accelerators](#keyboard-accelerators) and the drained commands all resolve through the same `gio` action namespace, so they cannot drift apart. Files are opened by the built-in **file picker** (textbox + fuzzy-matched list, see [The file picker](#the-file-picker)), by the sidebar, from within Neovim (`:e`), or by the menu's native **Open File… / Open Folder…** `gtk::FileDialog`s. There are still **no save / save-as dialogs** — saving is from within Neovim (`:w`, `:saveas`).

The application is built on top of pure, widget-free **seams** that can also be verified _headlessly_, with no display server, no window, and no event loop:

- `gdk_key` — GDK keyval + modifier state → `wolf_core::KeyEvent`.
- `paint` — render one `wolf_core::Grid` (+ its highlight table) onto a Cairo context.
- `grid_size_for` — pixel size + measured cell size → grid `(cols, rows)`.
- `cell_at` (`geometry.rs`, beside `grid_size_for`) — a pointer position in pane-local pixels + the cell size + the live grid extent → the grid cell `(row, col)` it lands on, clamped to the nearest edge cell.
- `mouse_input` / `scroll_threshold` / `ScrollAccumulator` / `PaneScroll` / `scroll_steps` (`mouse.rs`) — the whole pointer-translation rulebook: a GDK button number + modifier state → `wolf_core::MouseButton` plus the three modifier bools Neovim's mouse grammar actually carries; the per-`gdk::ScrollUnit` "one line step" threshold; the carried, signed sub-threshold scroll remainder, and that remainder paired with the grid it belongs to so a change of target grid discards it; and the signed step count → `wolf_core::ScrollDirection` + a positive repeat count. See [The seams](#the-seams).
- `PaneTree` (`layout.rs`) — the pure **N-ary frame** pane-layout tree (split/remove/leaves/pane_rects/neighbor), matching Neovim's window model: a frame is a leaf or an oriented split of N children with per-child weights; a split in the SAME orientation as its containing frame FLATTENS into an equal-sized sibling row/column, while a PERPENDICULAR split nests, and removing a pane re-equalizes and collapses/merges back to a canonical tree. Unit-tested headlessly; `pane_view.rs` is the only place that turns it into widgets.
- `cursor_rect` / `cursor_colors` (`cursor.rs`) — the cursor's shape geometry and its `(fill, glyph)` color pair (the `WolfCursor` app-theme group when set, else reverse video), computed without GTK.
- `ACTION_TABLE` / `MENU_SECTIONS` / `action_for_key` / `parse_accel` / `forbidden_reason` (`actions.rs`) — the whole action namespace as data: every action name, its accelerator, its `Command` correspondence and menu placement, the live chord matcher, and the checker that mechanically enforces "no Neovim key becomes unreachable". See [Keyboard accelerators](#keyboard-accelerators).
- `ui_action_for` (`command_action.rs`) — the TOTAL `wolf_core::Command` → `UiAction` mapping the command drain dispatches through. The `match` has no `_` arm, so a new core command is a compile error here until it is classified.
- `launch_decision` / `reroot_ready` (`workspace.rs`) — whether a project is open (and where the captive Neovim starts), and when a pending Open Folder re-root has settled. See [The empty state](#the-empty-state).
- `liveness_ui` / `overlay_message` / `restart_outcome` / `reopen_order` / `restart_button_rect` (`liveness_ui.rs`) — the whole crash/stall recovery rulebook as pure data: the TOTAL `wolf_core::Liveness` → `(overlay mode, auto_restart, paint)` mapping the wake drain gates on, the message each overlay mode carries, what follows a `WolfCore::restart_nvim()` call (whose `Ok(false)` is a no-op, not a failure), the order the captured Tier-1 files are reopened in with the ACTIVE one last, and the derived geometry of the "Restart Neovim" button — one function shared by the widget builder and the cage smoke so the two cannot drift. See [Crash and stall recovery](#crash-and-stall-recovery).
- `next_selection` / `restored_index` (`picker.rs`) — the file-private list-navigation clamp/preserve helpers, unit-tested headlessly.
- `children_of` / `ancestors_to_reveal` / `node_rel_path` / `rel_path_for` (`tree.rs`) — the pure hierarchical projection of the picker's flat file list into the file-tree sidebar's per-directory children + reveal helpers, unit-tested headlessly.

These stay free functions — plus the plain value types `PaneTree`, `ScrollAccumulator` and `PaneScroll` — independent of any widget, which is exactly what makes them testable without a display. The application wiring that binds them to a live [`wolf_core::WolfCore`] lives in [`src/app.rs`](src/README.md) and the thin binary entry point in [`src/main.rs`](src/README.md).

## Running

After editing `flake.nix` the already-loaded direnv environment is stale, so run through `nix develop --command`, which re-evaluates the flake:

```sh
nix develop --command cargo run -p wolf-gnome
```

This needs a display (a Wayland or X11 session), or it can be run under the headless smoke compositor (see [The headless smoke test](#the-headless-smoke-test)). It requires `WOLF_NVIM_BIN` to point at the pinned Neovim (the devShell exports it; nvim is never taken from `PATH`). The font size defaults to **14.0 pt** and can be overridden via the `WOLF_FONT_PT` environment variable (the smoke test sets it to `28` so glyphs are large enough to OCR). The font family is `DejaVu Sans Mono`, the GApplication id is `org.wolf.Wolf`, and the default window is 1200×640 (widened from the editor-only default to leave the editor pane its usual width after the 250 px file-tree sidebar).

## Architecture wiring

`app::run` builds an `adw::Application`, and on `activate` `build_ui` constructs the window and attaches a freshly started `WolfCore`:

- **Wake marshalling.** `WolfCore` runs Neovim on its own tokio runtime and fires a single `WakeFn` on a tokio worker thread when a new frame is ready. Because that thread cannot touch GTK, the wake only `try_send`s onto a bounded `async-channel` (capacity 1, which coalesces a burst of flushes — a dropped "full" send just means a redraw is already pending). A `glib::spawn_future_local` task on the GTK main thread drains the channel and, per signal, calls `shell.on_liveness_wake()` **first** — the crash/stall liveness read, which also reports whether painting this wake is worth anything — then, only if it said yes, `panes.on_render_wake()` and `tree.on_render_wake()`, and finally `shell.on_render_wake()`. The shell's command drain runs **last** on purpose: a drained `close_window` tears the core down, so the pane view and the tree must have had their turn first. It also runs **ungated**, in all three liveness states, so a `close_window` queued in the instant before a crash is not stranded behind an opaque overlay. Coalescing at capacity 1 is safe for the liveness read specifically because liveness is level-triggered (an atomic read) rather than edge-triggered; see [Crash and stall recovery](#crash-and-stall-recovery).
- **Pane view + draw.** The editor area is the native pane view (`pane_view.rs`). On each wake it creates/splits/closes panes from `WolfCore::drain_intents`, resolves each pane's bound grid via `grid_for_win`, marks the active pane from `Snapshot.active_win` (fallback: the cursor's grid), and queues redraws. Each pane's draw func paints ITS window grid via the pure `paint` seam; the pane that owns the cursor's grid also draws a **mode-aware cursor** at the cursor cell. The shape comes from the current mode's `ModeInfo.shape` (a block in normal mode, a thin vertical/horizontal bar in insert/replace), drawn **opaque** via `cursor_rect`. The `(fill, glyph)` colors come from `cursor_colors`: the **`WolfCursor` app-theme group** (`Snapshot.theme.cursor`, from the `wolf_theme` notification) is honored first and unconditionally when its bg is set (fill = theme bg, glyph = theme fg or the cell bg); otherwise **reverse video** applies — the mode's cursor highlight is honored only when that yields a visibly distinct pair, else the underlying cell is inverted. (There is no GNOME titlebar application: the Adw header bar keeps its current behavior; `WolfTitlebar` is macOS-only for now.) For a block cursor the cell's glyph is redrawn in the inverted color; a bar cursor leaves it untouched. The bottom **cmdline strip** (`draw_cmdline`) paints natively from `Snapshot::cmdline` / `Snapshot::toast` (not grid 1): an active command line (`firstc` + text + a caret at the byte `pos`) so typed `:`/`/` input stays visible, or the LAST toast line when idle so the emptied grid 1 never shows blank. The Adw completion popup + multi-line toast are deferred (OD4).
- **Input.** Two key controllers sit on the window. The first, installed by `shell::AppShell::install_chord_controller`, is **capture-phase**: it resolves the event against `actions::action_for_key` and, on a hit, activates that action and returns `Propagation::Stop`. The second, installed by `app::wire_keys`, carries **no** phase (i.e. Bubble) and routes each key through the pure `gdk_key` seam; a `Some` result is sent via `WolfCore::send_input` and the event is consumed (`Propagation::Stop`), a `None` is left to propagate. Because capture runs first, a chord Wolf binds is never ALSO forwarded to Neovim — that is the whole point of the phase split (see [Keyboard accelerators](#keyboard-accelerators)). Keys reach nvim's current window globally. **Pointer input, unlike keys, is per-pane** and lives in `pane_view.rs`: every pane `DrawingArea` carries three controllers. (1) A `gtk::GestureDrag` restricted to `gdk::BUTTON_PRIMARY` drives the whole press → drag → release sequence. Press calls `WolfCore::focus_win` (via the unchanged `on_pane_clicked`) **first** and only then `send_mouse(MouseAction::Press)` — both ride the same ordered input channel, so nvim sees the focus change before the press by construction — and it PINS the target grid AND the GDK button number, so every subsequent drag/release event targets the grid the sequence started in even after the pointer leaves the pane, and reports the button the press established rather than re-reading it (the modifiers, by contrast, are re-read live on every callback — macOS parity). GTK delivers drag update/end as OFFSETS from the start point, so the absolute point is `start_point() + offset`; it is forwarded unconditionally on every callback (no throttling, no changed-cell dedupe), and a point outside the widget is not rejected — `cell_at` clamps it to the nearest edge cell, which is what makes drag-past-the-edge selection work. One gesture rather than a `GestureClick` plus something else, because a `GtkGesture` takes an implicit grab on the sequence and keeps delivering after the pointer leaves the widget. (2) A `gtk::EventControllerScroll` subscribed to `VERTICAL` only feeds our own per-pane `PaneScroll` (not GTK's `DISCRETE` accumulation) and emits that many discrete `ScrollEvent`s; it returns `Propagation::Stop` and **never changes focus** — no `focus_win`, no active-pane change, no `grab_focus`. (3) A `gtk::EventControllerMotion` whose only job is to record the last widget-local pointer position, because GTK's `scroll` signal carries no coordinates of its own and the scroll handler needs a cell to aim at. **GTK keyboard focus never lands on a pane area:** pane areas are deliberately not `focusable` and nothing grabs focus on them — a click parks GTK focus on the persistent cmdline strip instead. The inner `gtk::Paned` dividers ARE focusable (GTK sets that in `gtk_paned_init` and we cannot change it) and are rebuilt on every pane-tree rebuild, so `rebuild_pane_area` additionally returns focus to the strip whenever it is about to destroy the widget holding it. See [`src/README.md`](src/README.md) for the click-then-close focus wedge both prevent — which is no longer a structural argument only: it is now executed end to end by the cage smoke `click_then_close_keeps_keyboard_input_alive_under_cage`, and reverting the fix makes it go red (see [`tests/README.md`](tests/README.md)).
- **Commands / menu.** `shell::AppShell` installs one `gio::SimpleAction` per implemented row of `actions::ACTION_TABLE` (`win.*` on the window, `app.*` on the application), builds the primary menu from `actions::MENU_SECTIONS`, and on each wake settles a pending Open Folder re-root and then drains `WolfCore::drain_commands()`. Each drained `Command` goes through the total `command_action::ui_action_for`; a command that is not implemented on GTK is **printed with its recorded reason**, never silently dropped.
- **Resize.** Each pane's `connect_resize` maps its pixel allocation to a grid size via the pure `grid_size_for` seam and calls `WolfCore::resize_grid` for that pane's grid (then resizes the outer grid via `WolfCore::resize`); the authoritative sizes come back via core's `grid_resize`. Dragging a `gtk::Paned` divider drives the same path.
- **Lifecycle.** `WolfCore` is non-`Send`; it lives only on the main thread in an `Rc<RefCell<Option<WolfCore>>>`, shared by the draw/key/resize/close closures. Closing the window takes the core out (in its own statement, to release the `RefCell` borrow) and runs `WolfCore::shutdown` for a clean teardown. Only the `WakeFn` ever crosses a thread boundary. If `WolfCore::start` fails, the error is logged and no window is built.

## The file-tree sidebar

The left pane of the `gtk::Paned` is a file-tree sidebar (implemented in [`src/tree_view.rs`](src/README.md), built on the pure [`src/tree.rs`](src/README.md) projection). It lists the working directory as a hierarchy and tracks the file being edited:

- **Same source as the picker.** It is populated by a long-lived `wolf_core::FileSearch` started at build time (except in the [empty state](#the-empty-state), where no project is open and the search only starts once an Open Folder settles) — the exact mechanism the picker uses (the streaming `ignore` traversal seeded by the MRU; `.git/`/`.wolf/`/ `.gitignored` excluded consistently). The tree is a hierarchical projection of that flat file list: directories are derived from file paths, and only directories that (transitively) contain a listed file appear. It streams in as the traversal progresses.
- **Layout.** A `gtk::ListView` over a `gtk::TreeListModel` + `gtk::TreeExpander` (the modern, non-deprecated tree widgets). The **top level is expanded by default**; all other directories start collapsed.
- **Single-click.** A single click on a **file** opens it (`InputEvent::Open`, recorded in the MRU) and returns focus to the editor; a single click on a **directory** toggles its expansion.
- **Highlight + reveal the current file.** The file currently being edited (from `wolf_core::Snapshot::current_file`, delivered on the render wake) is shown in bold and **revealed**: its ancestor directories are expanded, its row is selected, and it is scrolled into view. This happens after **both** picker navigation and Neovim-driven navigation (e.g. `:e`), since core tracks the active buffer via an autocmd regardless of how it changed.

The pure, headlessly-tested seams are in `tree.rs` (`children_of`, `ancestors_to_reveal`, `node_rel_path`, `rel_path_for`); the GTK wiring in `tree_view.rs` cannot be unit-tested headlessly and is exercised by the `tree_sidebar_shows_files_under_cage` smoke (see [`tests/README.md`](tests/README.md)).

**v1 limitation:** a `current_file` change rebuilds the tree's root store, which collapses any manual nested expansion (the reveal re-expands the path to the new current file, but other manually-opened directories are not restored).

## The file picker

The window has a built-in file picker (implemented in [`src/picker.rs`](src/README.md)). It has no trigger predicate of its own: it is opened by the **`win.go-to-file`** action, which is reachable three ways — the **Ctrl+Shift+O** chord, the primary menu's "Go to File…" item, and the header-bar **Open** button. It floats over the editor as an `Overlay` child: a search textbox over a results list.

What that chord costs, precisely: only the terminal-style Ctrl+Shift **alias** for `<C-o>`. `<C-o>` itself is still typed as plain Ctrl+O, which Wolf never binds, so **no Neovim key becomes unreachable** — see [Keyboard accelerators](#keyboard-accelerators) for the invariant and why the older claim that this chord was "non-conflicting" was wrong.

- **Filtering.** Typing fuzzy-matches against the file list (a streaming traversal of the cwd, seeded by the MRU cache — both provided by `wolf-core`). The query is split on whitespace into terms; matching is **case-insensitive** and an entry is kept only when EVERY term is a subsequence of its path (terms are order-independent). **MRU files rank first**; among the rest, a term that starts a path component is preferred over one that merely starts a word, which is preferred over a contiguous substring, which beats a scattered subsequence (scores summed across terms). An empty or all-whitespace query lists all files (MRU-first). The actual ranking is `wolf_core::rank_matches`; the picker only renders the top results.
- **Navigation + activation.** `Up`/`Down` move the list selection (focus stays in the textbox, so typing keeps working; selection is preserved as streamed results arrive). `Enter` (or clicking a row) opens the selected file; `Esc` closes the picker. While it is open, all keys go to the picker and are not forwarded to Neovim.
- **Open + MRU.** Selecting a file sends it through `wolf-core` as `InputEvent::Open { path }`, which Neovim loads via `:e`; the core's input pump records the open in the MRU cache, so it ranks first next time. There is no separate "select" path.

The pure, headlessly-tested seams here are the navigation clamp/preserve helpers `next_selection` / `restored_index`; the chord itself is resolved by `actions::action_for_key` (also unit-tested), and the full end-to-end behavior is covered by the picker cage smokes (see [`tests/README.md`](tests/README.md)).

## Keyboard accelerators

The complete Linux accelerator scheme lives in one place, as data: `ACTION_TABLE` in [`src/actions.rs`](src/README.md). It covers the whole parity effort, not just what is bound today, so later units (command palette, buffer picker, project search, nav history, terminal drawer) consume it rather than re-deriving it.

### The invariant

> **No Neovim key becomes unreachable.**
>
> Every chord Wolf binds is a chord whose _Neovim meaning is still typeable another way_. Concretely: a `Ctrl+Shift+<letter>` accelerator gives up only the **terminal-style Ctrl+Shift alias** for `<C-letter>`. Under `wolf-gnome`'s own encoder (`gdk_key` forces `shift: false` on printables, `wolf_core::key_to_notation` emits `S-` only for non-`Char` keys) `Ctrl+Shift+P` encodes to `<C-P>`, which `nvim_replace_termcodes` makes **byte-identical** to `<C-p>`. `<C-p>` itself is still delivered by plain **Ctrl+P**, which Wolf never binds, and `wolf-gnome` cannot emit `<C-S-p>` at all — so no distinct Neovim key is lost.
>
> **What is given up, stated plainly:** the Ctrl+Shift alias. A user who habitually types `Ctrl+Shift+P` expecting `<C-p>` must type plain `Ctrl+P`. Nothing else.
>
> **What is never given up:** a bare `Ctrl+<letter>` accelerator (that _would_ make `<C-letter>` unreachable), any `Super` chord, and any `Alt+<letter>` chord.

An earlier revision of this document and of `src/picker.rs` described the picker's chord as "deliberately non-conflicting — every Neovim key, including `<C-p>`, is preserved", and as living "in Neovim's free key space". That was **wrong** and is deleted: `Ctrl+Shift+P` is not a distinct Neovim key at all, so the picker shadowed an alias rather than nothing. The invariant above is the precise, defensible replacement.

`parse_accel` + `forbidden_reason` enforce the invariant **mechanically** over `ACTION_TABLE`, and the `actions.rs` unit tests run them over every row — including the Reserved ones, so a chord that would shadow a Neovim key fails the tests when it is reserved, not months later when a unit finally binds it.

### Why `Ctrl+Shift+<letter>`

- **`Ctrl+<letter>` is unavailable.** There is effectively no `Ctrl+<letter>` free in all Neovim modes, and in a `terminal` buffer every key except `CTRL-\` is forwarded to the job — and Wolf ships a terminal drawer.
- **Alt and Super are unavailable for _forwarding_, and Super is a live defect.** An unmapped Alt chord splits into `<Esc>` + the base key (insert-mode `<A-p>` pastes the unnamed register); an unmapped Super chord drops the modifier in normal mode (`<D-j>` moves the cursor) and inserts the literal text `<D-p>` in insert mode. Neither is a usable namespace for keys we intend nvim to see. A _captured_ Alt chord is safe, which is why `<Alt>Left` / `<Alt>Right` are reserved for nav history.
- **The genuinely free key space is too small and too unidiomatic** to carry a ~20-row menu: `<C-Space>`, `<C-;>`, `<C-,>`, `<C-.>`, `<C-/>`, `<C-=>`, `<C-->`, and `F2`..`F12`. It is used where it _is_ idiomatic (font size).
- **`Ctrl+Shift+<letter>` is the GNOME answer to exactly this problem.** GNOME Terminal binds Ctrl+Shift+C/V/T/N/W precisely because a terminal owns `Ctrl+<letter>`; VS Code on Linux uses Ctrl+Shift+P/E/F. Wolf is a Neovim host, i.e. structurally a terminal-shaped app. The namespace costs only the alias and buys the whole idiom.
- **The rule is memorable:** _take the macOS chord and replace ⌘ with Ctrl+Shift._ ⌘P→Ctrl+Shift+P, ⌘O→Ctrl+Shift+O, ⌘E→Ctrl+Shift+E, ⌘N→Ctrl+Shift+N. That is what makes later units mechanical instead of a list of exceptions.

### How a chord is actually matched (not by GTK)

Wolf matches its own chords in a **capture-phase `gtk::EventControllerKey`** installed on the window by `shell::AppShell::install_chord_controller`, which resolves the delivered keyval + modifier state through the pure `actions::action_for_key(keyval, state)` seam, activates the resulting action, and returns `Propagation::Stop`.

It does **not** rely on GTK's own accelerator matching. `set_accels_for_action` is still called, but **only so `gio::Menu` renders the chord label next to its menu item.** The reason is empirical: `gdk_key_event_matches` is keymap-aware — it re-translates the event's keycode through the display's current keymap and compares levels — and `wtype`, the only way the cage smokes can type, uploads a fresh single-keycode keymap per keystroke. Under that harness `GdkKeyEvent::matches` returns `KeyMatch::None` even for a trigger built from the event's OWN keyval and modifier state, so **no** chord fired and every one was forwarded to Neovim instead. An explicit capture-phase, local-scope `gtk::ShortcutController` with a `KeyvalTrigger` from `gtk::accelerator_parse` failed the same way. Matching the delivered keyval and modifiers directly is keymap-independent, so it works under `wtype` and on a real keyboard alike.

**Documented as unknown:** whether GTK's own keymap-aware matching works on a real keyboard could not be tested here (this machine has no interactive session). If it does, only ONE activation still results: both controllers live on the window in the capture phase and both claim the event, and a widget stops running a phase's controllers once one has handled it.

The capture phase itself is still the right place for an independent reason: `gtk_window_set_application` installs the application accels as a `GTK_PHASE_CAPTURE`, `GTK_SHORTCUT_SCOPE_GLOBAL` controller, and `app::wire_keys`'s key controller has no phase (Bubble), so a chord Wolf claims is guaranteed not to also reach Neovim. It is the _matching_ that moved out of GTK, not the phase.

`action_for_key` compares the three modifiers Wolf's accel grammar knows (Ctrl / Shift / Alt) **exactly** — an accelerator that does not name Shift must not fire while Shift is held — and **deliberately ignores every other modifier bit**, so `Ctrl+Shift+Super+O` still activates `win.go-to-file`. That is a decision, not an oversight: an unintercepted Super chord is actively harmful (nvim drops the modifier in normal mode and inserts literal `<D-x>` text in insert mode), so intercepting it is strictly better than forwarding it. The key comparison is case-insensitive on letters, because whether a shifted letter arrives as `o` or `O` depends on the keymap.

**Accelerators are global, including while an overlay is open.** The chord controller sits on the **window** in the capture phase, so it runs before the picker's own capture-phase controller on the picker box; it carries no `picker.is_open()` guard. Ctrl+Shift+N / W / Q therefore fire while the file picker is open — which the deleted `is_picker_trigger` branch, living in the bubble-phase controller behind a `picker.is_open()` early return, did not do. This is intended: an accelerator is an application-level command, and a user pressing Quit with an overlay up means Quit. The picker's own keys (`Esc`, `Up`/`Down`, `Enter`, and ordinary typing) are unaffected — none of them is a bound chord, so `action_for_key` returns `None` and the event proceeds to the picker exactly as before.

### The table

GTK accel syntax: modifiers are `<Control>` / `<Shift>` / `<Alt>` — never `<Primary>` (in GTK4 it is a plain synonym for `<Control>`, so it reads as if it meant ⌘ while binding exactly the chord bare-Ctrl is refused for) and never `<Super>`. Key parts are **names**, not symbols (`minus`, `equal`, `grave`, `0`), and `gtk_accelerator_parse` lowercases them, so **`<Control>P` ≡ `<Control>p`**: uppercasing does NOT imply Shift, which must always be spelled `<Shift>`. `parse_accel` accepts exactly that subset and returns `None` for anything else — including `<Super>` and `<Primary>`, which therefore never reach `forbidden_reason` at all. `forbidden_reason` rejects the chords that DO parse but would break the invariant: a bare `Ctrl+<letter>` and `Alt+<letter>`.

| macOS accelerator | Linux accelerator                  | Action                                                  | Neovim key it must not shadow       |
| ----------------- | ---------------------------------- | ------------------------------------------------------- | ----------------------------------- |
| ⌘P                | `<Control><Shift>p` — **reserved** | Command Palette (`win.command-palette`)                 | `<C-p>`                             |
| ⌘O                | `<Control><Shift>o` — **bound**    | Go to File / file picker (`win.go-to-file`)             | `<C-o>`                             |
| ⇧⌘O               | — (primary menu + button)          | Open Folder… (`win.open-folder`)                        | — (no chord)                        |
| —                 | — (primary menu)                   | Open File… (`win.open-file`)                            | — (no chord)                        |
| ⌘N                | `<Control><Shift>n` — **bound**    | New untitled buffer (`win.new-buffer`)                  | `<C-n>`                             |
| ⇧⌘N               | — (deferred)                       | New Window (`app.new-window`)                           | — (no chord)                        |
| ⌘T                | `<Control><Shift>t` — **reserved** | New Tab (`win.new-tab`)                                 | `<C-t>`                             |

Reading the last column: **every `<C-letter>` there is still typed as plain `Ctrl+<letter>`, which Wolf never binds** — that is the invariant above, applied row by row. The two `<Alt>` rows are the inverse case: `<A-Left>` / `<A-Right>` have no default Neovim mapping, and CAPTURING them is precisely what prevents the destructive `<Esc>` + arrow split an unmapped forwarded Alt chord produces. The nav-history rows are front-end-only — there is no `Command` variant behind them — so they are declared for the namespace's sake and dispatch nothing.

**Bound this unit:** exactly four — `win.go-to-file`, `win.new-buffer`, `win.close-pane`, `app.quit`. A **reserved** row's chord is neither registered with `set_accels_for_action` nor matched by `action_for_key`; both of those follow mechanically from `status`, because each iterates `bound_bindings()`.

Its action also happens not to be installed today, but **that part is incidental, not enforced**: `install_actions` filters on `ui_action_for(command)` not being `Deferred` / `NoGnomeEquivalent`, never on `status`. The two filters agree only because every Reserved row's command is currently `Deferred`. Two consequences for a later unit: implementing a Reserved row's command makes its action install itself, but the chord **still does nothing until its `status` is flipped to `Bound`**; and `MENU_SECTIONS` keeping Reserved items out — so the menu never shows an item that does nothing — is a separate guarantee, enforced by the `menu_never_lists_a_reserved_action` unit test rather than by the install filter.

**Assumption note (honestly labelled).** `<C-0>` and the Ctrl+backquote chord (`<Control>grave`) were **not** part of the verified free-key enumeration. Neither has an `index.txt` entry, and macOS already binds ⌃-backquote for the terminal drawer, which is the whole basis for assuming they are free. If either turns out to carry a built-in Neovim meaning, it must move into the `Ctrl+Shift+<letter>` namespace before the later unit binds it. **No chord bound today depends on either assumption.**

**A second thing to check before promoting a Reserved row.** `action_for_key` compares Shift **exactly** — an accel that does not name `<Shift>` will not match an event that carries it. `<Control>equal` and `<Control>grave` name no `<Shift>`, so on any keyboard layout where `=` or `` ` `` is itself a shifted glyph, the real event arrives with `SHIFT_MASK` set and the chord **silently never fires**. Nothing catches this today, because `action_for_key` only ever scans the four Bound rows and all four are plain letters. A unit promoting `<Control>equal` / `<Control>grave` / `<Control>0` must verify the delivered modifier state on the layouts it cares about, and either spell `<Shift>` or relax the comparison for punctuation keys.

**Known wart: a disabled action falls through.** `gio::SimpleAction::set_enabled(false)` is the documented global escape hatch, and it is what the empty state uses to disable `win.go-to-file` (there is no project to pick a file from). A disabled action's accelerator does not activate AND the event falls through — and `install_chord_controller` deliberately reproduces that behaviour by checking `action_is_enabled` before activating. So **in the empty state Ctrl+Shift+O reaches Neovim as `<C-O>` ≡ `<C-o>`.** Accepted, not fixed.

## The primary menu

The header bar's right side carries a GNOME **primary menu**: a `gtk::MenuButton` (`open-menu-symbolic`, tooltip "Main menu") whose model is built by `shell::build_menu_model()` from `actions::MENU_SECTIONS`. This is the GNOME-idiomatic equivalent of the macOS application menu bar; it mirrors that menu's _capabilities_, not its AppKit specifics.

Three sections, each rendered with a separator:

1. **New** (`win.new-buffer`), **Open Folder…** (`win.open-folder`), **Open File…** (`win.open-file`), **Go to File…** (`win.go-to-file`)
2. **Close** (`win.close-pane`), **Close Window** (`win.close-window`)
3. **Quit Wolf** (`app.quit`)

Every label is `Command::spec().title` from the shared registry, and a unit test asserts that — a registry rename cannot silently leave the GTK menu behind. Another asserts that no menu item points at a `Reserved` action: **the menu never shows an item that does nothing.**

**`win.` vs `app.` — the namespace choice.** Actions are `win.`-scoped by default and `app.`-scoped only when they are genuinely application-wide — `app.quit`, plus `app.new-window`, which is declared in `ACTION_TABLE` but neither installed nor listed (its command classifies as `Deferred`, since `wolf-gnome` is single-window). The reason is forward-looking: `wolf-gnome` is single-window today, but "Multiple windows" is a live feat-list row. A `win.` action is resolved against the window that owns it, so when a second window appears, "Close" and "Go to File…" already mean _this_ window with no rework; had they been `app.`-scoped they would have to be re-scoped and re-tested at that point. `gio::Menu` resolves an action name against the window's / application's action muxer at popup time, so a menu model can be built before the actions are installed.

Buttons deliberately use `connect_clicked` + `WidgetExt::activate_action(...)` rather than the `action-name` property: a widget whose `action-name` refers to a not-yet-installed action renders insensitive, and explicit activation sidesteps that ordering footgun entirely.

## The empty state

When no project is open, the window shows an `adw::StatusPage` ("No folder open" / "Open a folder to start editing." / an **Open Folder…** button) on an opaque, full-bleed `gtk::Box` added via `overlay.add_overlay(...)`, so the editor `DrawingArea` keeps its full allocation and no spurious 1×1 grid resize happens behind it.

**What "no project" means on Linux.** `wolf-gnome` has no `state.json` restore (that feat-list row is unticked), so — unlike macOS, whose `StateSeam.launchDecision` consults a restored cwd — the decision is derived from the **process working directory** by the pure `workspace::launch_decision`. It returns `Folder { cwd }` only when the process cwd is known, is a directory, is **not** the home directory, and is **not** `/`. Otherwise `EmptyState { nvim_cwd }`, where `nvim_cwd` is the home directory when that is a real directory, else `/` (`FALLBACK_CWD`). The rationale: a terminal launch (`cargo run` from a project) yields a real project directory, while a desktop-launcher / `.desktop` launch yields `$HOME` or `/`, which is exactly "no project". Treating `$HOME` as a project would also point the sidebar's `FileSearch` at the whole home tree — the pathological case `wolf_core::files::SearchBounds` exists to prune. `app.rs` canonicalizes both paths before calling, so the comparisons are plain `==`.

In the empty state: the captive Neovim still starts (at `nvim_cwd`), the **sidebar is hidden** (`set_visible(false)` is the load-bearing half — the `gtk::Paned` divider position is only advisory) and **no `FileSearch` starts** (`tree_view::build` takes a `start` flag), the header Open button is insensitive, and **`win.go-to-file` is disabled** — with the fall-through wart noted above.

Clicking **Open Folder…** (or choosing it from the primary menu) opens a `gtk::FileDialog` folder chooser. On success the shell sends `InputEvent::Chdir { path }` and records the canonicalized path as a **pending re-root**; it does _not_ re-root the sidebar synchronously, because `start_file_search` resolves its root from `live_cwd()`, which only updates once nvim reports `DirChanged` — a synchronous re-root would re-root at the OLD cwd. Each subsequent wake calls `workspace::reroot_ready(pending, live)`; when that returns `true` the empty state is cleared and `TreeHandle::reroot()` restarts the traversal.

**Known limitation: only `win.go-to-file` is disabled.** `set_empty_state` desensitizes the header Open button and that one action, and nothing else. `win.new-buffer` and `win.close-pane` stay live, as do the primary menu's "New" and "Close" items — so **Ctrl+Shift+N in the empty state really does create an untitled buffer, behind the opaque status page, where the user cannot see it.** The buffer is real and survives; it becomes visible as soon as a folder is opened and the empty state clears. This is a wart, recorded rather than fixed in this unit: the honest options (disable the whole implemented-action set in the empty state, or drop the overlay once any editing action fires) are behaviour changes that deserve their own review and their own smoke, not a late patch.

**Scope note:** `reroot` is driven only from the Open Folder path. A user-typed `:cd` still does not re-root the sidebar, so the feat-list row "Sidebar re-roots on Neovim's live cwd" stays honestly unticked.

## Crash and stall recovery

`wolf-core` reports the captive Neovim's health as a three-state `Liveness` (`Alive` / `NotResponding` / `Dead`) and offers `restart_nvim()` plus an RPC-free per-tabpage open-file mirror (`open_files_for_tabpage`). `wolf-gnome` reads `liveness()` **at the top of every wake**, before any painting, and acts on it. All of the decisions live in the pure `liveness_ui.rs` seam; `crash_overlay.rs` holds the widgets and `shell.rs` the orchestration. See [`src/README.md`](src/README.md) for the module-level detail.

**The three-state mapping.**

- **`Alive`** — hide the overlay, paint normally, and reset the automatic-attempt counter (so a later, unrelated crash gets its own attempt rather than inheriting an exhausted one).
- **`Dead`** — show the crash overlay ("Neovim crashed — restarting…" while an automatic attempt is still permitted, "Neovim crashed — automatic restart failed" once the budget is spent), skip the paint, and schedule **one** automatic in-place restart.
- **`NotResponding`** — show "Neovim stopped responding", skip the paint, and do nothing else. A wedged Neovim is **never** restarted automatically: `restart_nvim` force-kills the process, so everything not already in a swap file is lost, and that decision belongs to the user's button press alone. The core can also clear the state by itself when the RPC finally returns.

**The overlay.** A full-bleed, **opaque** `gtk::Box` (the `background` style class, exactly like the empty state), added as an `Overlay` child above both the picker and the empty state — a crashed core must not leave the picker's Open, or the empty state's Open Folder, reachable underneath, since both would send into a dead nvim. Being opaque is the point: it hides the frozen last frame, so "Neovim died" is distinguishable from "Neovim is idle". It swallows mouse clicks by virtue of being a visible, allocated overlay child, and it never takes keyboard focus. The **"Restart Neovim" button is present in BOTH modes** — a fallback while a dead core auto-restarts, the primary action for a wedged one — and it drives exactly the same restart function the automatic path does.

**Why the automatic restart is deferred by 50 ms.** `WolfCore::restart_nvim` is synchronous, so running it inside the wake handler would block the GTK main loop for the whole respawn with the overlay shown but never presented — the exact defect macOS has, where the crash overlay is never drawn on the success path. A `glib::idle_add_local_once` does **not** fix it under GDK/Wayland (measured: every capture still showed the frozen pre-crash frame, because GDK's frame clock has no _ready_ paint source at the moment the handler returns while a plain idle does); a real 50 ms timer does (every capture showed the crash message). It fires once per crash and adds no polling.

**One automatic attempt, then the button.** `MAX_AUTO_RESTART_ATTEMPTS` is 1. The cap exists solely to stop a retry loop against a permanently failing respawn — `restart_nvim`'s error path re-marks the core `Dead` and fires another wake, which would otherwise re-enter forever (measured with the cap removed: **75 attempts in 4 seconds**). It is not a limit on the user: an explicit button press resets the counter. The documented consequence is that a failed **manual** restart costs one extra automatic respawn and flickers "…restart failed" → "…restarting…" → "…restart failed". That is bounded rather than a loop, and deliberate — resetting only on an `Alive` reading would refuse a user whose press raced a failing automatic attempt.

**What a successful restart restores.** The Tier-1 open-file mirror is captured **before** the call (a respawn wipes it), then reopened afterwards with every non-active file first and the **active path LAST**, because reopening is a sequence of `InputEvent::Open`s on one ordered channel and the last one opened is the one that ends up focused. The pane view is reset first, which is load-bearing rather than cosmetic: the fresh Neovim re-attaches at the config's 80×24, and only a `::resize` on a pane `DrawingArea` tells the core otherwise — GTK emits one only when an allocation changes, so without destroying the old area the fresh Neovim would keep an 80×24 grid inside a 45×14 pane for the rest of the session. Unsaved edits come back through Neovim's own swap files: the respawn reuses the same durable per-project swap dir, so the fresh nvim finds the dead owner's swap and `runtime/nvim/init.lua`'s `SwapExists` autocmd recovers it silently. Finally a transient, click-through "Neovim was restarted" banner is flashed for four seconds — it is **independent of liveness**, because the fresh nvim's `Alive` wake clears the overlay immediately and without a separate channel the user would see no confirmation at all.

**What is NOT restored, stated plainly.** Only the Tier-1 _file set_. The pane **topology** is not restored: a crash while the window was split comes back as one pane, and the dead nvim's stale window/grid entries linger in the snapshot (no `win_close` / `grid_destroy` is ever sent for a killed process) — harmlessly, because no pane is bound to them. Cursor and scroll position are not restored either. None of that is a Linux-only gap; macOS restores no more.

**`NotResponding` cannot currently be reached from `wolf-gnome`, and no test pretends otherwise.** `wolf-core` marks a stall only from `block_on_rpc`'s timeout arm — i.e. only when the front-end issues a synchronous RPC that elapses the budget. Every `WolfCore` method this crate calls is non-blocking, so the intersection with `api.rs`'s sixteen `block_on_rpc` sites is **empty**, and `SIGSTOP`ing the captive nvim under the running app can never produce a stall. The mapping and the message selection are table-tested headlessly, and `crates/wolf-core/tests/nvim_liveness.rs` covers the core side against a genuinely wedged Neovim; what has **no** end-to-end coverage on Linux is the stall overlay's _presentation_. No smoke was written for it, because faking one would have meant adding a blocking call to the front-end purely to satisfy a test — and that would put a five-second main-loop stall on every redraw against a wedged nvim. This changes the moment the buffer picker (`list_buffers`), Copy (`copy_visual_selection`) or the Markdown preview (`render_preview`) land here; the paint gate is already written so that unit inherits it.

**Two cage smokes cover the rest end to end** — `nvim_crash_recovers_and_reopens_the_file_under_cage` (SIGKILL the nvim child, recover, reopen, recover the unsaved edit from the swap file, flash the banner, same grid size) and `crash_overlay_and_restart_button_recover_under_cage` (a deliberately failing respawn so the overlay dwells, asserting it is opaque, that the attempt cap holds, and that clicking the button recovers). See [`tests/README.md`](tests/README.md).

## The seams

### `gdk_key` (from [`input`](src/input.rs))

```rust
pub fn gdk_key(keyval: gdk::Key, state: gdk::ModifierType) -> Option<wolf_core::KeyEvent>
```

This is the exact shape of a future `gtk::EventControllerKey` `key-pressed` callback, kept as a free function so it can be unit-tested without a display (`gdk::Key` constants are compile-time; the printable path reads `keyval.to_unicode()`).

Mapping:

- **Named keys** (resolved first, since their `to_unicode()` is often a control char): `Return` & `KP_Enter` → `Enter`; `Escape` → `Esc`; `Tab` & `ISO_Left_Tab` → `Tab`; `BackSpace` → `Backspace`; `Delete` → `Delete`; `Left`/`Right`/`Up`/`Down`; `Home`/`End`; `Page_Up`/`Page_Down` → `PageUp`/`PageDown`; the contiguous `F1..=F12` range → `Key::F(n)`.
- **Printable fallback**: any other keyval whose `to_unicode()` yields a non-control char → `Key::Char(c)`.

Modifier masks: `ctrl` = `CONTROL_MASK`, `shift` = `SHIFT_MASK`, `alt` = `ALT_MASK`, `meta` = `SUPER_MASK`.

**Shift-glyph contract:** GDK already delivers the _shifted_ glyph in the keyval (Shift+`a` arrives as the `A` keyval, `to_unicode()` = `'A'`). So the printable branch **always sets `shift = false`** and lets the glyph carry the case — this matches `wolf_core::KeyEvent`, where `shift` is ignored for `Key::Char`. **Named keys keep the real `shift`** (so `<S-Tab>`, `<S-Left>`, `<S-F5>`). The X11 quirk `ISO_Left_Tab` _is_ Shift+Tab, so it maps to `Key::Tab` with `shift = true` even if the platform did not also set the SHIFT mask.

Returns `None` for: bare modifier / lock keys (`Shift_L/R`, `Control_L/R`, `Alt_L/R`, `Meta_L/R`, `Super_L/R`, `Hyper_L/R`, `Caps_Lock`, `Shift_Lock`, `Num_Lock`, `Scroll_Lock`); and any keyval whose `to_unicode()` is absent or a control character.

### `paint` + `CellMetrics` (from [`render`](src/render.rs))

```rust
pub struct CellMetrics { pub cell_w: f64, pub cell_h: f64, pub baseline: f64, pub font: pango::FontDescription }
impl CellMetrics { pub fn for_font(cr: &cairo::Context, family: &str, size_pt: f64) -> Self }
pub fn paint(cr: &cairo::Context, grid: &wolf_core::Grid, highlights: &wolf_core::HighlightTable, metrics: &CellMetrics)
```

`paint` is pure and widget-free: it paints ONE grid (under `ext_multigrid` the front-end paints a single window grid at a time, so it takes the `Grid` + its `HighlightTable` rather than a whole `Snapshot`) onto **any** Cairo surface — an offscreen `ImageSurface` in tests, a `DrawingArea`'s context in production.

`CellMetrics::for_font` measures a monospace cell using `cr` only to obtain a Pango context (its surface size is irrelevant): `cell_w` from Pango's approximate char width (exact for monospace), `cell_h` = ascent + descent, `baseline` = ascent.

Per-cell algorithm:

1. Resolve the highlight via `wolf_core::HighlightTable::resolve` (which has already applied `reverse` and the editor defaults).
2. Pick fg/bg, falling back to a built-in `FALLBACK_FG` (white) / `FALLBACK_BG` (black) when even the defaults are unset. 8-bit channels are divided by 255 to Cairo's 0.0–1.0 range.
3. **Always fill the cell's background rectangle** — this keeps wide-trailing / never-painted cells aligned. The Cairo `Result` is handled, not dropped.
4. If `cell.text` is empty (a wide-char trailing placeholder or never-painted cell) skip glyph rendering; otherwise lay the text out with Pango/pangocairo and draw it in fg.

Attributes applied: **bold**, _italic_, and single **underline**. Undercurl and strikethrough are deferred. No system theme is queried (deferred).

### `grid_size_for` + `cell_at` (from [`geometry`](src/geometry.rs))

```rust
pub fn grid_size_for(width_px: i32, height_px: i32, cell_w: f64, cell_h: f64) -> (u16, u16)
pub fn cell_at(x: f64, y: f64, cell_w: f64, cell_h: f64, cols: u16, rows: u16) -> (u32, u32)
```

`grid_size_for` is the resize handler's pure pixel-to-grid math, kept GTK/pango-free so it is unit-testable headlessly. `cols = floor(width_px / cell_w)`, `rows = floor(height_px / cell_h)`, each clamped to `[1, u16::MAX]`. As a resize guard, the **whole** result collapses to `(1, 1)` if either pixel dimension is non-positive or either cell size is degenerate (zero, negative, NaN, or infinite).

`cell_at` is the pointer half of the same conversion and lives in the same file on purpose: the composition guarantee — that a cell it produces is always inside the grid `grid_size_for` asked for — is proved in one place, and made executable by the `cell_at_never_exceeds_grid_size_for` unit test. It returns **`(row, col)`**, matching `wolf_core::MouseEvent`'s field order and macOS's `PaneGeometry.cellAt`, never `(x, y)`. `col = clamp(floor(x / cell_w), 0, cols - 1)` and `row = clamp(floor(y / cell_h), 0, rows - 1)`; a point **outside** the grid maps to the NEAREST EDGE CELL rather than being rejected, and that clamp is exactly what makes drag-past-the-edge selection extend to the last row/column instead of stalling. The whole result collapses to `(0, 0)` when `cell_w`/`cell_h` is non-finite or `<= 0.0`, or when `cols` or `rows` is `0`. A NaN coordinate has no direction, so that axis is treated as `0.0`; an infinite coordinate DOES have a direction, so it clamps to the nearest edge like any other out-of-range point. The clamp happens in `f64` space before the cast, so the truncating cast to `u32` is saturating-safe by construction.

`(x, y)` are **already pane-local** — GTK gesture/motion callbacks deliver widget-local coordinates, and `pane_view::draw_pane` paints cell `(row, col)` at `(col * cell_w, row * cell_h)` from the `DrawingArea`'s own origin — so there is no grid-origin subtraction here. `wolf-gnome` has no editor insets, no 90-column cap, no centering and no per-pane status bar, all of which are separate, still-unticked feat-list rows; **do not import the macOS `gridRect` / `paintOffset` machinery.** If any of those rows is ever implemented, this function grows a grid-origin parameter, and that is the tripwire.

### `mouse` (from [`mouse.rs`](src/mouse.rs))

```rust
pub struct MouseInput { pub button: wolf_core::MouseButton, pub ctrl: bool, pub shift: bool, pub alt: bool }
pub fn mouse_input(button: u32, state: gdk::ModifierType) -> Option<MouseInput>
pub fn scroll_threshold(unit: gdk::ScrollUnit, cell_h: f64) -> f64
pub struct ScrollAccumulator { /* private signed remainder */ }
impl ScrollAccumulator {
    pub const fn new() -> Self
    pub fn consume(&mut self, delta: f64, threshold: f64) -> i32
    pub fn reset(&mut self)
}
pub struct PaneScroll { /* private: a ScrollAccumulator + the last target grid */ }
impl PaneScroll {
    pub const fn new() -> Self
    pub fn steps_for(&mut self, grid: u64, delta: f64, threshold: f64) -> i32
}
pub fn scroll_steps(steps: i32) -> Option<(wolf_core::ScrollDirection, u32)>
```

The pointer analogue of `gdk_key`: GDK value types in, `wolf_core` input values out, with no widget, no display and no event loop, so every rule is unit-tested headlessly in the module's own `#[cfg(test)] mod tests`. It performs no pixel-to-cell conversion and never reads a snapshot — the cell comes from `cell_at` and the grid from the live snapshot — which is what keeps every rule here decidable from its arguments alone. `PaneScroll` is handed a grid id, but only as an opaque identity token it compares for equality; it never resolves one.

- **`mouse_input`** — only `gdk::BUTTON_PRIMARY` (1) is forwarded; **every other button number returns `None`**. That is deliberate parity with macOS, which overrides only `mouseDown` / `mouseDragged` / `mouseUp`: right-click context menus and middle-click paste are separate, unimplemented features on **both** platforms. `GtkGestureSingle`'s default `button` is already `GDK_BUTTON_PRIMARY` (and `pane_view` sets it explicitly), so in practice the gesture never fires for another button — the `None` arm is defence-in-depth plus the one place the decision is recorded and tested. Modifiers: `ctrl` ← `CONTROL_MASK`, `shift` ← `SHIFT_MASK`, `alt` ← `ALT_MASK`. **`SUPER_MASK` is ignored, not forwarded**, and so is every other bit (`LOCK_MASK`, the button masks): Neovim has no meta mouse modifier — `wolf_core::input::apply_mouse` builds only `"C-"`, `"S-"` and `"A-"` — so forwarding one would be meaningless.
- **`scroll_threshold`** — how much delta, in whatever unit GDK reported, constitutes one line step. `gdk::ScrollUnit::Wheel` returns `1.0`: a wheel delta is already expressed in detents, so one detent is one step regardless of cell height. `gdk::ScrollUnit::Surface` returns `cell_h` when that is finite and `> 0.0`: a surface delta is in pixels, so one cell height is one step. A degenerate `cell_h` under `Surface`, and every other unit, return `1.0`. `gdk::ScrollUnit` is `#[non_exhaustive]` and carries an `__Unknown(i32)` variant, so a catch-all arm is forced, and it falls back to the WHEEL threshold **on purpose**: guessing WHEEL for a pixel-shaped delta makes scrolling over-sensitive, which is immediately visible and recoverable by the user, whereas guessing SURFACE for a detent-shaped delta would need roughly `cell_h` detents per line — i.e. scrolling would be dead. Over-sensitive beats dead.
- **`ScrollAccumulator`** — carries the signed sub-threshold remainder between calls indefinitely, so a run of trackpad nudges crosses a boundary exactly once and a direction reversal is symmetric. `consume` returns the signed count of whole thresholds newly crossed. A non-finite `delta`, or a non-finite or non-positive `threshold`, returns `0` and leaves the carry **untouched** (a rejected call must be indistinguishable from no call — a poisoned NaN remainder would kill scrolling for the rest of the session); if adding `delta` makes the remainder itself non-finite it is zeroed rather than kept; and the returned count is clamped to `[-256, 256]`, with the carry DROPPED when the clamp bites, so a garbage delta cannot keep firing forever. It is `Copy`, so `pane_view` can keep one per pane in a `Cell` and never hold a borrow across a `WolfCore` call; `reset` clears the carry, and deciding WHEN it must be cleared is deliberately not this type's job — `PaneScroll` owns that. **Deliberate divergence from macOS:** `ScrollAccumulator.swift` uses two unbounded `while` loops that are `O(delta / threshold)`; this is arithmetic (truncate toward zero, then clamp), `O(1)`, with identical semantics for every realistic input. The ported unit-test table pins that equivalence, and its `1e300` case would never finish under the loop form.
- **`PaneScroll`** — a `ScrollAccumulator` plus the grid it was last applied to: one pane's whole scroll bookkeeping as a pure value. `steps_for(grid, delta, threshold)` discards the carried remainder FIRST when `grid` differs from the grid of the previous call, then returns exactly what `consume` returns; every other rule is the accumulator's, sequenced and never re-implemented. **"The previous call" means the previous call to `steps_for`, accepted or not** — a call `consume` rejects still names a grid and still records it, so a rejected event on a different grid ends the old grid's carry just as an accepted one would. There is **no manual reset**: a grid change is the only way the carry clears. The rule matters because the remainder is a fraction of a line _of one particular grid_, so letting half a line follow the pointer into the pane it just entered would make that pane's first event jump by a step it did not earn. macOS keeps this rule in the view (`PaneContainerView.scrollWheel`'s `if grid != lastScrollGrid { reset() }`), and `wolf-gnome` did too until it was pulled down here: in the GTK glue it needed a live display, and at the time pointer input had no end-to-end coverage on Linux at all, so a rule left there was a rule nothing verified. Pointer input now HAS cage coverage (four smokes, see [`tests/README.md`](tests/README.md)), but the placement is unchanged and still right: the rule is decidable from its arguments, and discriminating it end to end would need two panes and a pointer that scrolls across both, which no smoke does.
- **`scroll_steps`** — `0` → `None`; `steps > 0` → `Some((ScrollDirection::Down, n))`; `steps < 0` → `Some((ScrollDirection::Up, n))`, where `n` is `steps.unsigned_abs()` (total, where a plain `-steps` would panic in a debug build on `i32::MIN`).

  **The sign convention here is the OPPOSITE of macOS's, and that is correct.** AppKit's `scrollingDeltaY > 0` means "show earlier content" (the viewport moves toward line 1), so `crates/wolf-macos` maps a positive step count to `Up`. GDK's smooth-scroll `dy > 0` corresponds to `GDK_SCROLL_DOWN` — the viewport moves toward the END of the buffer — so `wolf-gnome` maps a positive step count to `Down`. And `ScrollDirection::Down` is pinned against real Neovim (by `crates/wolf-ffi/tests/mouse_scroll.rs`) to strictly INCREASE `win_viewport.topline`, which is precisely what a positive GDK `dy` must do. A reader cross-checking `PaneContainerView.swift` will find this backwards; it is supposed to look backwards, and flipping it would make GTK scrolling run the wrong way while every macOS test stayed green. The `scroll_direction_is_inverted_from_macos` unit test exists solely to make that un-flippable by accident.

## Building and testing

After editing `flake.nix` the already-loaded direnv environment is stale (it has no GTK), so the build gate is to run everything through `nix develop --command`, which re-evaluates the flake:

```sh
nix develop --command cargo build -p wolf-gnome
nix develop --command cargo test  -p wolf-gnome
```

`cargo test -p wolf-gnome` now includes the twenty cage smokes described below, which is why it is slow. These two commands are a narrow iteration loop; the authoritative full check is the Linux verification gate in [`build.md`](../../build.md), "The Linux verification gate".

The devShell provides the GTK toolchain (`gtk4`, `cairo`, `pango`, `glib`, `gdk-pixbuf`, `graphene`, `harfbuzz`) and pins a deterministic font: it points `FONTCONFIG_FILE` at a generated copy of [`testdata/fonts.conf`](testdata/fonts.conf) exposing **only** DejaVu Sans Mono (no host font dirs), so Pango measurement / Cairo rasterization is reproducible.

The round-trip test spawns **real Neovim** (no mocks, per project policy) located via `WOLF_NVIM_BIN` (also exported by the devShell). See [`tests/README.md`](tests/README.md).

### The headless smoke test

A suite of twenty end-to-end tests launches the real application under a headless Wayland compositor and confirms it actually draws a window a human could see. They are **not** `#[ignore]`d: they run as part of `cargo test -p wolf-gnome` and of the Linux verification gate. To run just them:

```sh
nix develop --command cargo test -p wolf-gnome --test smoke_headless
```

That target reports **`21 passed`**, not `20`, and takes a **measured 89 seconds** (it was ~71 s at eighteen smokes). Alongside the twenty smokes the same file carries one pure, compositor-free guard, `sidebar_filler_names_cannot_satisfy_any_smoke_assertion`, which asserts that no sidebar-filler fixture filename can contain a substring a smoke's OCR assertion looks for — otherwise that smoke would pass green forever on the sidebar row alone. It needs no toolchain and runs in microseconds. See [`tests/README.md`](tests/README.md).

They require the flake's smoke toolchain (`cage`, `wtype`, `grim`, `tesseract` and [`wolf-pointer-inject`](../../tools/wolf-pointer-inject/README.md) on `PATH`), a set and writable `XDG_RUNTIME_DIR` (where the Wayland socket lives), and `WOLF_NVIM_BIN`. Each runs its whole scenario inside `cage`, drives the window with `wtype`, screenshots the live window with `grim`, and OCRs it with `tesseract --psm 11` ("sparse text" mode, needed for the light-on-dark editor grid). The base smoke types `hello` in insert mode and asserts the OCR loosely contains it; further smokes cover the file picker (two), the file-tree sidebar, the five split-pane operations (vertical split, horizontal split, the three-pane same-orientation split that guards the N-ary flatten, focus move, and close pane), the command-drain surface (the empty state, the Ctrl+Shift+N new-untitled-buffer chord, `:q` closing the focused pane, `:qa` closing the window — the load-bearing end-to-end proof of the drain, which asserts only that the process is gone and so captures no screenshot — and the Ctrl+Shift+W close-pane chord), **pointer input** (four: click-to-position, drag-to-select including the out-of-widget clamp, wheel scroll, and the click-then-close focus-wedge regression), and **crash recovery** (two: SIGKILLing the captive Neovim and recovering, and a deliberately failing respawn whose dwelling overlay is then dismissed by clicking its "Restart Neovim" button). Missing preconditions fail loud rather than silently skipping. See the full list in [`tests/README.md`](tests/README.md).

**Five of the twenty smokes inject real pointer events.** They run `wolf-pointer-inject` — this repo's own long-lived `zwlr_virtual_pointer_v1` client, built from `tools/` by `flake.nix` — inside cage before the app, which is what keeps `WL_SEAT_CAPABILITY_POINTER` on under cage's headless wlroots backend, and drive it over a FIFO with a poll-for-ack protocol. So the GTK gesture → `WolfCore` translation described under [Architecture wiring](#architecture-wiring) is **now verified end to end on this machine**: a real `wl_pointer.button` positions the Neovim cursor at exactly the predicted cell, a button-held move emits `drag-update` and selects the predicted range (with the release outside the pane clamping to column 1), a real `wl_pointer.axis` detent moves the viewport by exactly one line, and clicking a pane and then closing it leaves keyboard input alive. Each was demonstrated RED with its controller neutered and green when restored. Three of those four assert on files the captive Neovim writes about its own state rather than on OCR. The fifth is the crash-overlay smoke, which needs the injector for a different reason: the "Restart Neovim" button is the only way to observe that the overlay is interactive at all, and its click point is derived from the same `restart_button_rect` the widget builder realises rather than hardcoded. The precise, unsoftened list of what is still unproven — `record_pointer`, the `drag_grid` / `drag_button` press-pinning, and the strict press-ordering — is in [`tests/README.md`](tests/README.md), "Pointer injection: how it works and why it is built this way".

## gtk-rs versions

The gtk-rs crates are one coherent gtk-rs release set: `gtk4` 0.11.x / `gdk4` 0.11.x / `libadwaita` 0.9.x with `cairo-rs` / `pango` / `pangocairo` 0.22.x. (In the gtk-rs ecosystem the gtk4-rs repo and the "core" repo are released together but carry different minor numbers; the invariant is "one coherent release set", not "one identical minor" — mismatched `-sys` minors fail to link. `libadwaita` 0.9 carries no version feature, targeting the system GTK already present.) These are built against the flake's GTK 4.22, cairo 1.18, and pango 1.57. `cairo-rs` enables the `png` feature for the `#[ignore]`d golden-regeneration dev-aid test.

`gtk4` enables the **`v4_12`** feature, which the file-tree sidebar's `gtk::ListView::scroll_to` (used by reveal to scroll the current file into view) requires. This raises the minimum **system GTK to 4.12**; the flake's GTK 4.22 satisfies it. The feature is `wolf-gnome`-only and does not affect `wolf-core`'s GUI denylist.

## Deferred to later phases

The window, the file picker, the file-tree sidebar, native split panes, the primary menu, the empty state, the command drain, mouse + vertical scroll input, and [crash/stall recovery](#crash-and-stall-recovery) exist, but the following remain deferred:

- **Save / save-as dialogs.** The menu's native Open File… / Open Folder… `gtk::FileDialog`s exist, but saving is still from within Neovim (`:w`, `:saveas`), so the feat-list's "Native file dialogs (open / save / save-as)" row stays unticked.
- **Seventeen of the twenty-six registry commands are classified `Deferred`.** They are drained and reach `command_action::ui_action_for`, which prints the recorded blocker rather than dropping them; each reason is distinct and auditable. Eight dispatch today, and `HideApplication` is `NoGnomeEquivalent` (GNOME has no application-level hide — the shell owns window visibility) and never will be implemented.
- **The Super / unbound-Alt forwarding defect.** `input::gdk_key` maps `SUPER_MASK` → `meta` → `<D-…>`, and an unmapped Super chord in Neovim drops the modifier in normal mode and inserts literal `<D-x>` text in insert mode. Likewise an unbound `Alt+<letter>` is forwarded and splits into `<Esc>` + the base key. Both are pre-existing and independent of the accelerator design; dropping Super and dropping unbound Alt is a later unit's job. Logged here so it is not re-derived.
- **Restoring the pane layout across a Neovim restart.** Crash recovery restores the Tier-1 file set only, so a crash while the window was split comes back as a single pane; cursor and scroll position are not restored either. macOS restores no more. See [Crash and stall recovery](#crash-and-stall-recovery).
- **No About dialog** (`adw::AboutWindow`), and no window-title or unified-toolbar work.
- Theming (querying the OS theme and pushing it into Neovim).
- **What is still missing from pointer input.** Click-to-position, drag-to-select and vertical scroll / trackpad input are wired (see [Architecture wiring](#architecture-wiring) and [The seams](#the-seams)), but: **horizontal scroll is not handled** — the scroll controller subscribes to `VERTICAL` only, which is parity with macOS, where `scrollWheel` ignores `deltaX` too; **only the primary button is forwarded** — `mouse_input` refuses every other button number, so there is no right-click context menu and no middle-click paste on either platform; and **momentum / kinetic scrolling is not special-cased** — the `KINETIC` flag is not set and the `decelerate` signal is not connected, again matching macOS. The **synthetic per-pane scrollbar** driven by `win_viewport` is a separate, still-unticked feat-list row: scroll INPUT reaches Neovim, but nothing draws a scrollbar.
- The Adw **completion popup** (`ext_popupmenu`) and a **multi-line scrollable message toast** (`ext_messages`). Core attaches with all three UI extensions (`ext_cmdline` + `ext_popupmenu` + `ext_messages`) and folds them, and GTK now paints the command line natively from `Snapshot::cmdline` in the bottom strip (a single row: `firstc` + text + caret, or the last toast line when idle) — but per OD4 the popup and the multi-line toast are deferred, so GTK shows no completion popup and only the final toast line (macOS has both as native overlays).
- HiDPI scale handling (the cell-measurement probe is 96-dpi).
- IME / `IMContext` composition input.
- Floating windows (`win_float_pos`) and windows opened by non-overridden paths (`:help`, quickfix, preview, `:diffsplit`) — see the split-pane known limitations in [`src/README.md`](src/README.md).
- A GTK **buffer-picker** overlay (parity with the macOS `BufferPickerView`, ⌘E). Deferred like the command-palette overlay: `Command::BufferPicker` now LANDS in the drain and is classified `Deferred` with its blocker printed, `Ctrl+Shift+E` is reserved for it in `ACTION_TABLE`, and the pure `wolf_core::rank_buffers` / `WolfCore::list_buffers` / `switch_buffer` API is already linked — only the GTK overlay is missing.

## Note on the GUI denylist

The `wolf-core` "no GUI toolkit in the dependency tree" denylist does **not** apply to this crate — GTK is allowed here. It still holds for `wolf-core`, because the dependency goes `wolf-gnome` → `wolf-core`, never the reverse, so GTK never enters core's tree.
