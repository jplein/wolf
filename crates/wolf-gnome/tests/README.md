# wolf-gnome/tests

Tests for the seams and the windowed application. They split into **headless** checks (no display, no nvim), two **real-Neovim** end-to-end tests (no mocks, per project policy — the key round-trip and the mouse/scroll seams), and eighteen **headless-compositor** cage smoke tests that launch the real window (one window-render smoke, two file-picker smokes, one file-tree-sidebar smoke, five split-pane smokes — vertical split, horizontal split, a three-pane same-orientation split, focus move, close pane — five command-drain smokes: the empty state, the Ctrl+Shift+N new-untitled-buffer chord, `:q` closing the focused pane, `:qa` closing the window, and the Ctrl+Shift+W close-pane chord — and four **pointer** smokes: click-to-position, drag-to-select, wheel scroll, and the click-then-close focus-wedge regression) plus one pure guard on the smokes' own fixture, which needs no compositor. Everything runs through `nix develop --command` so the GTK toolchain, the pinned font, and `WOLF_NVIM_BIN` are present:

```sh
nix develop --command cargo test -p wolf-gnome
```

The default run **does** include all eighteen cage smokes, and they are the slowest part of the suite — see [the smoke test section](#smoke_headlessrs--windowed-app--picker--tree--panes--commands--pointer-real-compositor). They are part of the Linux verification gate; see [`build.md`](../../../build.md), "The Linux verification gate", for the authoritative full check.

## `geometry.rs` unit tests — `grid_size_for` and `cell_at` (headless)

The pure pixel-to-grid geometry is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/geometry.rs`](../src/geometry.rs)), needing no GTK, display, or nvim.

**`grid_size_for`.** A table-driven `grid_size_for_table` covers the typical exact-division case (`800×592` with `8×16` cells → `100×37`), flooring of partial cells (`17×17` → `2×1`), the min-1 clamp for tiny/zero/negative dims, the whole-result collapse to `(1, 1)` for degenerate cell sizes (zero/negative/NaN/ infinite, including a single-axis NaN), and the upper clamp of `i32::MAX` dims to `u16::MAX`. A second test, `grid_size_for_independent_axes`, proves cols and rows are computed separately (wide-but-short and narrow-but-tall grids).

**`cell_at`** adds two more tests in the same module:

- `cell_at_table` — the pointer → cell contract, row by row. Cell centres map to their own cell; an exact cell boundary belongs to the HIGHER cell while a hair below it does not (`floor`, pinned from both sides); a point far outside in either direction clamps to the nearest EDGE cell rather than being rejected (the drag-past-the-edge behaviour), including the one-axis-only case; a `1×1` grid collapses every point in the plane to `(0, 0)`; a degenerate `cell_w`/`cell_h` (zero, negative, NaN, infinite) or a zero-extent `cols`/`rows` collapses the WHOLE result to `(0, 0)`; and a `u16::MAX × u16::MAX` grid probed at `1e12` saturates at index `65534` rather than wrapping. Three rows pin the non-finite **coordinate** rule, which is two rules and not one: **NaN has no direction, so its axis is treated as `0.0`, while `+inf` / `-inf` DO have a direction and clamp to the last / first cell** like any other out-of-range point. Every assertion message re-states that the return is `(row, col)`, not `(x, y)`.
- `cell_at_never_exceeds_grid_size_for` — the composition guarantee, made executable. For each of four widget/cell shapes (typical `800×592` at `8×16`; tiny `3×3`, where `grid_size_for` clamps up to `1×1`; huge `i32::MAX` at `1×1`, where it saturates at `u16::MAX`; and a non-integer `9.37×19.51` cell) it computes `(cols, rows) = grid_size_for(...)` and then asserts `col < cols && row < rows` for seven probe points: far outside negatively, the origin, the centre, a hair inside the bottom-right corner, exactly the corner, far outside positively, and NaN in both axes. This is what lets `pane_view` pass a pointer position straight into a `wolf_core::MouseEvent` with no bounds check of its own.

## `mouse.rs` unit tests (in `src/mouse.rs`, headless)

The pure pointer-translation rulebook is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/mouse.rs`](../src/mouse.rs)), needing no GTK, display, or nvim — `gdk::ModifierType` and `gdk::ScrollUnit` are plain value types, exactly like the ones `input.rs`'s headless tests already use. Nine tests — eight below, plus the convention guard at the end:

- `mouse_input_table` — every modifier combination the seam honours (none, Ctrl, Shift, Alt, all three), and then the rows that are the actual point: **`SUPER_MASK` alone yields all-false rather than leaking through as anything**, `SUPER_MASK | CONTROL_MASK` yields ctrl only, and `LOCK_MASK` (Caps) is likewise ignored — Neovim's mouse grammar is only `"C-"` / `"S-"` / `"A-"`, so a bit outside it must be dropped, not translated. The refusal rows cover middle, secondary, button `0`, and the thumb buttons `8` / `9`, plus secondary-with-Ctrl, so a refused button stays refused no matter what is held down.
- `scroll_threshold_table` — `Wheel` returns the detent threshold whatever the cell height is (including a degenerate `0.0`); `Surface` returns `cell_h` when it is usable and falls back to the detent threshold when it is `0.0`, negative, NaN or infinite; and `__Unknown(7)` — the arm that `gdk::ScrollUnit`'s `#[non_exhaustive]` forces — falls back to the detent threshold too, pinning the documented "over-sensitive beats dead" choice. The test carries a scoped `#[allow(clippy::float_cmp, reason = …)]`: every expected value is exactly representable and is returned unmodified rather than computed with, so an epsilon comparison would weaken the assertion without making it more correct.
- `scroll_accumulator_table` — scenarios, not single calls: each case applies an ordered list of `Consume` / `Reset` ops to one fresh accumulator, which is what makes the CARRY observable. The macOS-ported rows (one whole cell → one step; two 0.6-cell nudges crossing exactly once; a 1.5-cell leftover carrying into the next call; a symmetric direction reversal; `reset` clearing the carry; exactly one cell three times running with no drift; one step per detent) pin behavioural equivalence with the Swift original. The GTK-specific hardening rows pin what the Swift does **not** have: a zero threshold returns `0`, does not hang, and does not break the next call; negative / NaN / infinite thresholds return `0` and leave the carry untouched, proved by a following nudge that still crosses exactly one boundary; NaN / `+inf` / `-inf` deltas likewise leave the carry unpoisoned; two finite `1e308` deltas whose SUM overflows the remainder to infinity get it zeroed rather than poisoned; and a `1e300` delta saturates at `±MAX_STEPS_PER_EVENT` and DROPS the carry, so it cannot keep firing. The two `1e300` rows also assert a timing property no `assert!` can state — under the macOS `while`-loop formulation they would iterate ~`1e300` times and the test would never return, so **if this test hangs, the arithmetic form has been replaced by a loop.**
- `scroll_accumulator_new_matches_default` — `new()` and `Default::default()` must agree, because `PaneScroll` reaches the type through both (`PaneScroll::new()` builds it with `new()`, the `Default` derive builds it through the derive) and a disagreement would give one pane a phantom carry.
- `pane_scroll_table` — the same scenario shape one level up, over `PaneScroll::steps_for(grid, delta, threshold)`, with **no `Reset` op at all**: `PaneScroll` exposes no manual reset, and a grid CHANGE being the only way to clear the carry is precisely the property under test. The no-reset rows prove nothing is cleared that should not be (a first call on a fresh value is honoured in full; the same grid carries across calls; a direction reversal on one grid is not a grid change). The reset rows prove the rule from four angles: a grid change discards a sub-step carry; changing BACK also resets, so the rule is "differs from the previous call" and not "never seen before"; the leftover a WHOLE-step call parks is dropped by a grid change too; and — the contract detail most easily lost in a refactor — **a call `consume` REJECTS still counts as a call**, so a NaN-delta event naming a different grid ends the old grid's carry exactly as an accepted one would. The remaining rows pin that every `ScrollAccumulator` guard (the non-finite delta/threshold rejections and the `±MAX_STEPS_PER_EVENT` clamp) passes straight through unchanged.
- `grid_change_discards_the_carry` — the same rule stated on its own so a failure NAMES it rather than pointing at a table row: two 0.6-cell nudges on DIFFERENT grids must both return `0`, and a third on the second grid must return `1` (so the reset did not break the accumulator). This rule used to live in `pane_view.rs::on_pane_scroll` — GTK glue, which needs a live display, so at the time nothing in the suite could execute it. Moving it into `mouse::PaneScroll` is what made it testable at all, and it is still the right home now that the cage pointer smokes exist: a per-grid carry rule needs two panes and a pointer that scrolls across both, which no smoke does yet (see [What is still unproven](#what-is-still-unproven)), and it is decidable from its arguments so it is far better pinned headlessly regardless.
- `pane_scroll_new_matches_default` — `PaneScroll::new()` and `Default::default()` must agree in BOTH fields: a non-zero carry is a phantom step, and a non-`None` `last_grid` would make the first real scroll event on that pane a spurious grid CHANGE.
- `scroll_steps_table` — `0` → `None`, `±1` and `±7` → the expected direction and magnitude, and `i32::MIN` → `Some((Up, 2_147_483_648))`, pinning that `unsigned_abs` is total where a plain `-x` would panic in a debug build.

Plus one non-table test whose only job is to make a convention un-flippable: **`scroll_direction_is_inverted_from_macos`**. It asserts `scroll_steps(1) == Some((Down, 1))` and `scroll_steps(-1) == Some((Up, 1))`, under a block comment explaining that AppKit maps a positive delta to `Up` while GDK's `dy > 0` is `GDK_SCROLL_DOWN`, and that `ScrollDirection::Down` is pinned against real Neovim (by [`crates/wolf-ffi/tests/mouse_scroll.rs`](../../wolf-ffi/tests/mouse_scroll.rs)) to strictly increase `win_viewport.topline`. Without it, someone cross-reading `PaneContainerView.swift` could "correct" the mapping, break GTK scrolling entirely, and leave every macOS test green — because macOS never runs this code.

## `cursor.rs` unit tests (in `src/cursor.rs`, headless)

The pure cursor geometry and color logic is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/cursor.rs`](../src/cursor.rs)), needing no GTK, display, or nvim. A table-driven `cursor_rect_table` covers the geometry per shape: `Block` always returns the full cell (ignoring `cell_percentage`); `Vertical` is a left bar of full height whose width is `cell_percentage` of `cell_w` (default `0.25`), floored to `MIN_BAR_PX` for tiny percentages and capped at `cell_w` for out-of-range ones; `Horizontal` is the analogous bottom bar against `cell_h` (anchored to the bottom edge). Deliberately non-square cells and a non-zero origin keep width/height math and offsets distinguishable. `named_constants_match_contract` pins `MIN_BAR_PX` / `DEFAULT_CELL_PCT` / `PCT_DENOM`.

A second group covers `cursor_colors` over hand-built `Snapshot`s: the **honor** path (a mode cursor highlight with distinct fg + bg → `(bg, fg)`, including with editor defaults set); the **inversion** path (bg-only, fg-only, `attr_id` `None`, out-of-range `mode_idx`, and empty `mode_infos` all fall through to `(cell_fg, cell_bg)` without panicking); the **guard** cases where a degenerate honored pair must NOT be honored (fill equal to the underlying cell background, or fill equal to glyph) and instead inverts; and the **fallback** case where unset cell colors reach the white/black `FALLBACK_FG` / `FALLBACK_BG`.

## `picker.rs` unit tests (in `src/picker.rs`, headless)

The picker's pure seams are unit-tested **inside their own module** (a `#[cfg(test)] mod tests` in [`src/picker.rs`](../src/picker.rs)), needing no GTK, display, or nvim:

- `next_selection_table` — down/up within range, clamp at both ends with NO wrap, empty list → `None`, single row, and out-of-range/negative `current` clamped.
- `restored_index_table` — empty list → `None` regardless of reset/prev; reset → `Some(0)`; preserve in range; preserve clamped when `prev` exceeds the new len; preserve with no prev defaults to `0`.

## `actions.rs` unit tests (in `src/actions.rs`, headless)

The whole action namespace is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/actions.rs`](../src/actions.rs)), needing no GTK, display, or nvim — `gdk::Key` and `gdk::ModifierType` are plain value types, and keyvals are built with the same `key_from_char` helper used by `gdk_key.rs` (which is what lets a case spell the SHIFTED glyph `'O'` a real keymap delivers for Ctrl+Shift+O):

- `every_accel_parses` — `parse_accel` returns `Some` for every declared accelerator. It first asserts the table declares at least one accelerator at all, so an emptied `ACTION_TABLE` cannot make every per-row test below pass vacuously.
- `accels_use_key_names_not_symbols` — the `<Control>-` vs `<Control>minus` trap: no key part may be a single punctuation character, and each must be either all-lowercase or one of the known named keys (`Left` / `Right`). `gtk_accelerator_parse` lowercases key names, so an uppercase spelling does NOT imply Shift.
- `no_accel_makes_a_neovim_key_unreachable` — `forbidden_reason` is `None` for every row (including the Reserved ones), **plus** explicit negative cases proving the checker bites: `<Control>p`, `<Super>n`, `<Primary>p` and `<Alt>p` are all refused, while `<Alt>Left` is accepted. (Which mechanism refuses a chord is an implementation detail — `<Super>` / `<Primary>` fail `parse_accel`'s grammar, `<Control>p` / `<Alt>p` parse and are refused by `forbidden_reason` — so the test asserts the composed contract.)
- `accels_are_unique` — no accelerator string is declared twice; a duplicate means one action silently never fires.
- `action_names_are_valid` — every action matches `^(app|win)\.[a-z0-9]+(-[a-z0-9]+)*$`. `gio` rejects a malformed name with a runtime warning, not a compile error, so this is the only cheap place to catch a typo.
- `bound_set_is_exactly_this_unit` — the `Bound` rows are exactly `win.go-to-file`, `win.new-buffer`, `win.close-pane`, `app.quit`, and each really has a chord to register.
- `action_for_key_table` (20 rows) — the LIVE matcher, and therefore user-visible behaviour, since `shell::AppShell::install_chord_controller` calls it from a capture-phase controller: each of the four bound chords fires in BOTH letter cases (a case-sensitive comparison would mean the chord never fires on real hardware while a lowercase-only test still passed); a bare `Ctrl+<letter>` does NOT fire, so `<C-o>` / `<C-n>` / `<C-w>` / `<C-q>` still reach Neovim; a Reserved row does NOT fire; the Ctrl/Shift/Alt match is EXACT (adding Alt misses); and a modifier bit outside the grammar is IGNORED, pinned from both sides — `Super+Shift+o` → `None` (Super can never supply the missing Ctrl) while **`Ctrl+Shift+Super+o` → `win.go-to-file`**. That last row is deliberate: an unintercepted Super chord is actively harmful, since Neovim drops the modifier in normal mode and inserts literal `<D-x>` text in insert mode, so intercepting it is strictly better than forwarding it.
- `key_name_matches_table` (21 rows) — every key-NAME shape `ACTION_TABLE` uses, including the named-key and punctuation-name branches that `action_for_key` cannot otherwise reach today (all four bound rows are single letters, while a later unit promotes exactly those Reserved rows). The negative rows are the point: an unknown name is `false` rather than a guess, and a punctuation name against a non-printable keyval (whose `to_unicode()` is `None`) is `false` rather than a panic.
- `command_action_round_trip` — command ↔ action is a bijection over the rows that carry a command.
- `menu_items_reference_declared_actions` — every `MenuItemSpec.action` is in `ACTION_TABLE` (a `gio::Menu` item naming an unknown action renders INSENSITIVE at popup time — a silent, visual-only failure). It also asserts `MENU_SECTIONS` is non-empty and no section is empty.
- `menu_never_lists_a_reserved_action` — a Reserved action is not installed this unit, so a menu item pointing at one would appear and do nothing.
- `menu_labels_match_the_registry` — where a menu item's action maps to a command, its label equals `Command::spec().title`, so a registry rename cannot silently desync the GTK menu.

## `command_action.rs` unit tests (in `src/command_action.rs`, headless)

The total `Command` → `UiAction` mapping is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/command_action.rs`](../src/command_action.rs)):

- `ui_action_table` — one row per `Command` variant in discriminant order, pinning the classification. Its length is asserted equal to `wolf_core::COMMAND_SPECS.len()`, which is what makes the table non-vacuous: a newly appended core command cannot be absorbed silently. Rows pin the CLASS for the two unimplemented variants, not their reason strings — duplicating ~18 sentences here would make a wording tweak look like a behaviour regression.
- `every_registered_command_maps` — walks `COMMAND_SPECS` and asserts each command appears in the table exactly once. Belt-and-braces for the totality guard: the `_`-free match already makes a new variant a compile error, but that evaporates the moment anyone adds a catch-all arm, whereas this check walks the registry rather than the match.
- `dispatched_commands_are_the_expected_set` — the commands whose action is neither `Deferred` nor `NoGnomeEquivalent` are exactly the eight this unit dispatches (`close_pane`, `close_window`, `go_to_file`, `minimize_window`, `new_buffer`, `open_file`, `open_folder`, `quit_application`), by registry `id` so the failure message names a row a reader can grep for. Nothing quietly promoted, nothing quietly demoted.
- `unimplemented_reasons_are_distinct_and_non_empty` — every `Deferred` / `NoGnomeEquivalent` reason is non-empty, reads as a mid-sentence clause (an ALL-CAPS opener such as "GNOME" is allowed, since the reason is interpolated into `"wolf-gnome: command {cmd:?} not dispatched: {reason}"`), and is UNIQUE — so no two rows of the README's command table can collapse into one indistinguishable entry, and a future pedantic `clippy::match_same_arms` run stays clean.

## `workspace.rs` unit tests (in `src/workspace.rs`, headless)

The launch decision and the re-root settle are unit-tested **inside their own module** (a `#[cfg(test)] mod tests` in [`src/workspace.rs`](../src/workspace.rs)). `launch_decision` takes `is_dir` as an injected predicate, so these need no temp directories and no real `$HOME`:

- `launch_decision_table` — a real project dir that is neither home nor `/` → `Folder`; `cwd == home` → `EmptyState { home }` (the desktop-launcher shape); `cwd == "/"` → `EmptyState { home }`; no process cwd at all → `EmptyState { home }`; a cwd the injected `is_dir` rejects → `EmptyState { home }`; `home == None` with a real project cwd → still `Folder`; `home == None` with an unusable cwd → `EmptyState { FALLBACK_CWD }`; and `home` set but not a directory → `EmptyState { FALLBACK_CWD }`.
- `reroot_ready_table` — `pending` `None` → false; `live` `None` → false; neither known → false; equal → true; a still-old `live` → false; a **trailing separator is NOT a difference** (`Path: PartialEq` compares components, so `/a/b/` == `/a/b` — the implementation is a plain `==` and must not be hand-rolled into a byte comparison); but an unnormalized `..` **is** a difference, which is exactly why callers canonicalize first.

## `layout.rs` unit tests (in `src/layout.rs`, headless)

The pure **N-ary frame** pane-layout tree (`PaneTree`, matching Neovim's window model) is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/layout.rs`](../src/layout.rs)), needing no GTK, display, or nvim — twenty tests covering:

- **construction / split** — `new` is a single leaf; a `Vertical` split yields two leaves side by side and a `Horizontal` split stacks them; `pane_rects` tiles the bounds for both; a perpendicular nested split produces the expected nested rectangles.
- **flatten vs. nest (the N-ary frame model)** — a split whose orientation MATCHES the containing frame FLATTENS into an equal-sized sibling row/column (a row `[P1, P2]` vsplit on `P1` becomes equal thirds `[P1, P3, P2]`, not a nested 25/25/50; repeated same-orientation vsplits stay flat at four equal columns), while a PERPENDICULAR split (an hsplit of a row member) NESTS into a sub-frame.
- **remove / collapse / re-equalize** — removing a leaf collapses its sibling (and a sibling _subtree_) into the parent's slot; removing a flat-row member re-equalizes the survivors (nvim `equalalways`); a now-1-child split collapses into its sole child; a surviving same-orientation split merges upward into the parent; removing the last pane is a no-op.
- **neighbor** — basic Left/Right (`Vertical`) and Up/Down (`Horizontal`) neighbours, a nested 2x2 case, a flat row of three, and `None` for an unknown pane.
- **ordering** — `leaves` and `pane_rects` enumerate in a stable DFS order.

## `gdk_key.rs` — input translation (headless, table-driven)

Table-driven unit tests for `wolf_gnome::gdk_key`, layout-independent: assertions cover only letter casing and named keys, never shifted-punctuation unicode (which is keyboard-layout dependent and would be flaky). These need no display server and no nvim — `gdk::Key` constants are compile-time and printable keyvals are built via the local `key_from_char` helper.

Cases cover: the Enter/Return family (incl. `KP_Enter`), `ISO_Left_Tab` + SHIFT → `Tab { shift: true }`, arrows, `Home`/`End`, `PageUp`/`PageDown`, `F1`/`F5`/`F12`, printable chars with the shift contract (`'a'` and `'A'` both → `Char(..)` with `shift: false`, `'<'`), modifiers on named keys (`Ctrl+Left`, `Ctrl+Shift+Left`), modifiers on printables (`Super+s`, `Alt+x`, `Ctrl+a` carries the base letter + ctrl, never a raw control char), and the `None` cases (`Shift_L`, `Control_L`, `Super_L`, `Caps_Lock`).

## `paint_golden.rs` — paint (headless, offscreen)

Builds a deterministic 4×2 `Snapshot` via core's public constructors (`Snapshot::new`, `HighlightTable::set_defaults`/`define`, `Grid::set_cell`), including one defined `hl_id` with distinct fg/bg and a wide-trailing empty-text cell. It measures `CellMetrics` against a throwaway 1×1 probe surface, sizes a real offscreen `ImageSurface` (ARGB32) to exactly the grid, paints, and samples pixels.

**Primary gate — structural ARGB center-sampling** (always on; deliberately _not_ a whole-image hash, which is too brittle across freetype/fontconfig):

- Known background fills are rasterizer-independent, so the center of the defined-bg empty cell and a default-bg cell are asserted for **exact** equality.
- The empty wide-trailing cell's interior is sampled at several inset points and must be background-only (verifying the "skip the glyph" path).
- The glyph cell's rect must contain at least one non-background pixel (the glyph was actually drawn).

Pixel reads assume little-endian ARGB32 (in-memory byte order `B, G, R, A`), which holds on the x86_64 Linux target.

**Dev aid (not part of the gate)** — `regenerate_png_golden` is `#[ignore]`d; it writes `tests/testdata/paint_golden.png` via `ImageSurface::write_to_png` (which needs the `cairo-rs` `png` feature). Run it explicitly:

```sh
nix develop --command cargo test -p wolf-gnome --test paint_golden \
    -- --ignored regenerate_png_golden
```

It is now the **only** `#[ignore]`d test in the whole repo, so a bare `cargo test -p wolf-gnome -- --ignored` runs nothing but this golden rewrite.

Font determinism relies on the pinned `DejaVu Sans Mono` exposed via `FONTCONFIG_FILE` (set by the flake devShell from [`testdata/fonts.conf`](../testdata/fonts.conf)).

## `roundtrip_nvim.rs` — end-to-end (real Neovim)

Exercises the full input seam against a real, hermetic Neovim (no mocks): `gdk_key` translates GDK keyvals → `InputEvent::Key` → `WolfCore` → nvim, then the snapshot is asserted. It enters insert mode, types `"Hello"` (the leading `H` is fed as the already-uppercased keyval _with_ the SHIFT mask, exercising the shift-glyph contract end-to-end), leaves insert mode with `Escape`, waits for and drains flushes, and asserts row 0 contains the word. Requires `WOLF_NVIM_BIN` (`common::require_nvim_bin` fails loud if unset).

## `mouse_nvim.rs` — the mouse/scroll seams end-to-end (real Neovim)

Two `#[test]`s that drive the pure pointer seams into a real `WolfCore` and a real, hermetic Neovim. What the GTK glue would do inside a `gtk::GestureDrag` / `EventControllerScroll` callback, this file does by hand: `wolf_gnome::cell_at` turns a pane-local pixel point into a grid cell, `mouse::mouse_input` encodes the button + modifiers, `mouse::{scroll_threshold, ScrollAccumulator, scroll_steps}` turn a delta into discrete steps, and the results go through `WolfCore::send_mouse` / `send_scroll`. It needs no real font and no GTK: the seams are pure, so locally-declared `CELL_W = 8.0` / `CELL_H = 16.0` exercise exactly the arithmetic the glue performs with the measured `render::CellMetrics`.

**This file is no longer the only pointer coverage, and it deliberately does not overlap with the rest.** It drives the pure **seams** — `cell_at`, `mouse_input`, the accumulator, `send_mouse` / `send_scroll` — into a real core and a real Neovim, with no GTK controller anywhere in the picture. The four cage pointer smokes below drive the GTK **glue**: whether `gtk::GestureDrag` and `gtk::EventControllerScroll` fire from a real `wl_pointer` event at all, whether `drag-update` is emitted, whether the offsets reconstruct the absolute point, and which `gdk::ScrollUnit` a real wheel event reports. Neither can answer the other's question, so neither duplicates the other; see [Pointer injection](#pointer-injection-how-it-works-and-why-it-is-built-this-way) below.

Shared setup (`start_with_filled_buffer`) starts the core, waits for the attach flush, polls for a live editor **window** grid (`>= 2`, not hidden — mouse and scroll must never target grid 0/1), fills the buffer via `:put =map(range(1,200), 'printf(''%05d'', v:val)')`, and parks the view at line 1. Two empirical constraints are carried over verbatim in substance from [`crates/wolf-ffi/tests/mouse_scroll.rs`](../../wolf-ffi/tests/mouse_scroll.rs) and commented in place: the lines must be **5 characters wide**, because `:put =range(1,200)` yields 1-char lines and a click at column 2 would clamp to end-of-line and defeat the exact-column assertion; and a literal double quote **cannot** appear inside `:put =<expr>` (Neovim strips it as the start of an Ex comment, giving `E115`), so the format string is quoted with doubled single quotes.

- **`mouse_press_drag_release_selects_via_seams`** — asserts `cell_at` maps the centre pixel of cell `(5, 2)` back to `(5, 2)` **before** anything is sent, which is what proves the rest of the test exercises the intended cell rather than whatever nvim happened to do; sends a `Press` there and polls until the cursor sits at exactly that grid-local `(row, col)`; then computes a drag point **40 cells beyond the right/bottom edge**, asserts `cell_at` clamps it to exactly `(rows - 1, cols - 1)` — that clamp is the whole reason drag-past-the-edge selection works — and sends `Drag`; asserts the selected `ModeInfo` name contains `visual` (name-based, following `crates/wolf-core/tests/input_keys.rs`, so it is not coupled to nvim's `mode_info_set` ordering); sends `Release` at the same point and asserts the selection SURVIVES it and that the cursor moved DOWN from the press row (directional on purpose — nvim clamps to the last BUFFER line, not the last grid row). It closes with a negative control: `mouse_input(gdk::BUTTON_SECONDARY, ..)` must be `None`, so no right-click can ever reach Neovim.
- **`scroll_seam_moves_viewport_via_wolfcore`** — drives a real `ScrollAccumulator`: with the `Surface` threshold, one 0.6-cell nudge must return `0` and the second must return `1` (the sub-cell carry, through the real type rather than a reimplementation of it); a 5-cell delta must encode as `ScrollDirection::Down` with `count >= 1`, and sending that many `ScrollEvent`s must strictly **increase** `win_viewport.topline`; a negative delta must encode as `Up` and strictly **decrease** it — with an explicit precondition that the preceding down-scroll left `topline > 0`, so the decrease assertion is falsifiable rather than trivially true. It ends by asserting `scroll_threshold(ScrollUnit::Wheel, CELL_H) == 1.0`, so one detent is one step whatever the cell height is, driven through the same code path. It carries a scoped `#[allow(clippy::float_cmp, reason = …)]` for that single exactly-representable comparison.

**Requirements and wiring.** A real, pinned Neovim located via `WOLF_NVIM_BIN`; `common::require_nvim_bin()` **panics rather than skipping** if it is unset, per project policy. `cargo test` auto-discovers every `tests/*.rs`, and **`crates/wolf-gnome` has no `BUILD.bazel` at all**, so there is no Bazel `rust_test` target to add for this file — unlike `crates/wolf-core` / `crates/wolf-ffi`, where CLAUDE.md's "every new test file must be wired into a target" rule bites. The test's own module doc says so too, so nobody goes looking for one.

## `smoke_headless.rs` — windowed app + picker + tree + panes + commands + pointer (real compositor)

Eighteen `#[test]` cage smokes that prove the whole stack actually draws a window, drives the file picker, populates the file-tree sidebar, creates / focuses / closes native split panes, dispatches drained commands (the empty state, the accelerators, `:q` and `:qa`), and — since this branch — **routes real pointer events through `pane_view.rs`'s gesture and scroll controllers**: a click positions the Neovim cursor at the predicted cell, a button-held move selects a range (including a release outside the pane), a wheel detent moves the viewport by exactly one line, and clicking a pane and then closing it does not wedge keyboard input. They run in the **default** suite: the compositor and OCR toolchain they need comes from the flake devShell, so a normal `cargo test` run _inside `nix develop`_ does have it, and `require_smoke_env` fails loud if it does not. To run them:

```sh
nix develop --command cargo test -p wolf-gnome --test smoke_headless
```

That target reports **`19 passed`**, not `18`: the file also carries one pure, compositor-free guard, `sidebar_filler_names_cannot_satisfy_any_smoke_assertion` (last bullet below), which does **not** call `require_smoke_env` and needs none of the toolchain. The whole target takes about **71 seconds** on this host (measured 71.0-71.6 s across three runs, at nineteen tests; it was 35.27 s at fifteen).

**Serialization (`CAGE_LOCK`).** Each smoke launches its own `cage` compositor, and two compositors started concurrently contend for the same Wayland socket under `XDG_RUNTIME_DIR` (lockfile error), which would fail both under the default parallel harness. So all eighteen smokes acquire a shared `static CAGE_LOCK: Mutex<()>` for their whole body, forcing serial execution; poisoning is recovered from (`into_inner`) so one panicking test does not cascade into the others. This serialization is why the smokes are the slowest part of the suite. **The four pointer smokes deliberately live in this same file for that reason.** A separate `tests/pointer_smoke.rs` was considered and rejected: each `tests/*.rs` is its own crate and its own PROCESS, so an in-process `static Mutex` cannot serialize across them at all, and moving `CAGE_LOCK` into `tests/common/mod.rs` would not help either — that module is compiled separately into every integration-test binary, so it would produce N independent mutexes rather than one shared one. It would look like a fix and serialize nothing. A separate file would therefore need real cross-process locking (an `flock` under `XDG_RUNTIME_DIR`, with its own stale-lock and poisoning story) to keep two `cage` instances off one socket — new machinery and a new failure mode, for smokes that are the same shape as the existing fourteen and want exactly the same serialization.

**Mechanism (common to all eighteen).** Each locates the built binary via `CARGO_BIN_EXE_wolf-gnome` and runs its interactive scenario as one `sh -c` string **inside `cage`** (the headless wlroots compositor) so that `wtype` and `grim` inherit cage's `WAYLAND_DISPLAY` (cage exports it only to its child process tree). The scenario launches the app in the background, polls (not a fixed sleep) until the window maps, drives it via `wtype`, captures the live window with `grim` to a PNG under `XDG_RUNTIME_DIR`, then OCRs it on the host with `tesseract … stdout --psm 11` ("sparse text" mode — the default page-segmentation mode returns empty on the sparse light-on-dark editor grid). The app is launched with `WOLF_FONT_PT=28` so glyphs are large enough to OCR, and a stale screenshot is removed first so a previous run cannot make a test pass. The one exception is `colon_qa_closes_the_window_under_cage`, which captures no image at all: its assertion is a property of the process table, so it calls neither `grim` nor `tesseract`.

**Mechanism (the four pointer smokes only).** They additionally start [`wolf-pointer-inject`](../../../tools/wolf-pointer-inject/README.md) inside cage **before** the app — so the seat already carries `WL_SEAT_CAPABILITY_POINTER` when GTK does its first `wl_seat` roundtrip and calls `get_pointer` at bind time — wait for its `ready extents=<W>x<H> …` line, and then drive it over a FIFO with a poll-for-ack protocol: every `motion` / `press` / `release` / `axis` command is followed by an `ok <n>` that the helper prints only **after** a `wl_display_roundtrip`, so an ack means "the compositor has processed this event" rather than "the bytes left our buffer". All of that plumbing lives in one shared `POINTER_PREAMBLE` string rather than being pasted four times. The scenarios keep the FIFO's write end open on fd 3 for their whole lifetime (each `echo` would otherwise close it and hand the helper a spurious EOF), and a `trap`ped `cleanup()` kills the helper first and the app second, so the app's shutdown is never racing a pointer event. Distinct scenario exit codes: `11` the app died before the window mapped, `12` the helper never became ready, `13` a helper command was not acked within budget, `14` a Neovim readback file never appeared, `15` the helper died mid-scenario.

**Three of the four pointer smokes assert on files the captive Neovim writes about its own state**, not on OCR: `printf('%d %d', line('.'), col('.'))`, `visualmode()` plus `'<` / `'>`, and `line('w0')`, each `writefile`d to an absolute path passed in from Rust and then polled for. Those are exact integers. OCR is fine for "did this word render" and is structurally incapable of "did the cursor land at exactly line 12, column 25"; an integer readback also cannot be satisfied by a sidebar row or an `:e` toast, and it fails with `expected (9, 12), got (5, 1)` instead of a wall of misread glyphs. `grim` still runs in all four and the PNG is still retained for post-mortem; `tesseract` runs only in the wedge smoke, where the OCR pair carries real corroborating signal. Each readback file is removed before the run and asserted absent, exactly as the stale PNG is — evidence that could be a previous run's leftover is not evidence.

**No pointer smoke hardcodes a magic pixel.** The Rust side measures `cell_w` / `cell_h` exactly (a 1x1 `cairo::ImageSurface` probe through `CellMetrics::for_font`, with the same family and the same parsed `SMOKE_FONT_PT` the app is launched with, so the two cannot drift), clicks once at the probe point, reads `(l0, c0)` back out of Neovim, and expresses every later target as `round(PROBE + D * cell)` with the assertion on the exact **delta**. That is origin-independent. The derived pane origin is then checked as a loud, self-checking precondition — a band whose tolerance is `12.0` px, deliberately under `20.0` so a `+20,+20` surface offset would FAIL, plus a `cell_w` / `cell_h` phase allowance that is unavoidable and must not be grown to make a failing run pass. Its failure message names the four candidate causes in order: a GTK4 CSD / shadow-margin offset appearing under cage, an `adw::HeaderBar` height change, an `app::TREE_PANE_WIDTH` or `gtk::Paned` divider change, and a cage output-size change.

**Every one of the eighteen launches in a FRESH temp working directory** (`make_temp_cwd()`, passed to the `cage` command as its `current_dir`), not in the repo. That isolation is mandatory, not tidiness. The app derives `CoreConfig.cwd` from `std::env::current_dir()`, and the captive Neovim keeps a **durable, per-project swap directory keyed on that cwd** (`wolf_core::state::swap_dir_for` → `state_dir()/swap/<hash of cwd>`), which deliberately outlives the process so a fresh nvim can recover a crashed one's unsaved edits. Every scenario ends by `kill`ing the app, so its nvim never cleans up. At a **fixed** cwd those two facts compose into a self-poisoning test: run _N_ leaves a stale `%…%Untitled.md.swp` behind and run _N+1_ finds it at startup, where naming the startup buffer `<cwd>/Untitled.md` collides with it inside `nvim_buf_set_name` and raises a blocking ATTENTION dialog that eats the first keystroke — so the smoke goes red for whatever change happens to be in flight, and points at the wrong cause. A fresh cwd makes each run idempotent. (The product-level guard for that swap collision is deliberate, headless and lives in [`crates/wolf-core/tests/swap_recovery.rs`](../../wolf-core/tests/swap_recovery.rs), `stale_untitled_swap_does_not_block_a_fresh_start`.) A side benefit: the app no longer traverses the entire repository through `FileSearch` on launch, and no longer writes into the working tree. That last point has one deliberate exception, `window_renders_typed_text_under_cage`, which writes nine tiny marker `.md` files into its own temp cwd purely so the tree sidebar has rows of text to draw — the repo listing used to supply that page density accidentally, and OCR has always depended on it (see that test's bullet below for the measurement). The temp dirs are **not** auto-deleted, to aid post-mortem inspection; each run therefore also leaves one new `state_dir()/swap/<hash>/` holding at most one `.swp`, which is harmless because no future run resolves to that hash.

- **`sidebar_filler_names_cannot_satisfy_any_smoke_assertion`** — the one test in this file that is **not** a cage smoke. It is pure: no compositor, no `require_smoke_env`, no `CAGE_LOCK`, no subprocess, microseconds to run, so it still guards the fixture on a machine without the smoke toolchain. It reads two const tables and asserts that no `SIDEBAR_FILLER_FILES` name contains any term in `ASSERTED_OCR_TERMS` — the table of every substring the smokes assert OCR must or must not contain, built from the OCR consts themselves rather than re-typed literals so it cannot drift. Fourteen of the eighteen smokes appear there. FOUR contribute no term at all, on purpose: `colon_qa_closes_the_window_under_cage`, which captures no image, and the click, drag and scroll pointer smokes, whose assertions are on files the captive Neovim writes about its own state rather than on pixels — so no fixture filename can help or hurt them. (The fourth pointer smoke, the wedge regression, does OCR and does contribute.) The terms are `hello`, `pickertarget`, `picktwo` / `pickone`, `treenode`, `paneleft` / `paneright`, `htopfile` / `hbotfile`, `focusone` / `focustwo` / `zzleft`, `closekeep` / `closegone`, `triaone` / `tribtwo` / `tricthree`, `folder`, `zzfresh`, `newbufbase`, `quitkeep`, `quitgone`, `chordkeep`, `chordgone`, and — added with the pointer-harness unit — `wedgestay` and `wedgeclick`. The must-NOT-contain terms are listed deliberately: a filler row carrying one would make its smoke fail SPURIOUSLY rather than pass vacuously — the opposite symptom, but the same fixture bug. Were a filler ever named `fillhello.md`, the sidebar would render `hello` on a row of its own, `window_renders_typed_text_under_cage`'s assertion would be satisfied by that row, and the smoke would pass green forever with an editor pane that drew nothing — the silent false positive `CLAUDE.md` warns about, and one that is invisible in review because the fixture and the assertion it can defeat sit a thousand lines apart. It also pins that every asserted term is lowercase (OCR output is lowercased before every `contains`, so an uppercase const could never match, which would make the filename check vacuous too) and that the filler names are distinct (duplicates collapse on disk and would silently thin the page density). A fixture that can disarm the assertion it exists to support needs an executable guard, not prose.

Required toolchain + env for the **eighteen cage smokes** (all from the flake devShell smoke toolchain, and now **gate-required** rather than optional): `cage`, `wtype`, `grim`, `tesseract` and `wolf-pointer-inject` on `PATH`; `WOLF_NVIM_BIN` set; and a set, writable `XDG_RUNTIME_DIR`. `wolf-pointer-inject` is the odd one out and deliberately so: it is not an upstream nixpkgs package but **this repo's own tool**, built from [`tools/wolf-pointer-inject/`](../../../tools/wolf-pointer-inject/README.md) by `flake.nix`, so `command -v wolf-pointer-inject` succeeding can only mean the flake provided it. Only the four pointer smokes use it, but `REQUIRED_TOOLS` demands it unconditionally: a devShell missing it is an unprovisioned devShell. Per project policy `require_smoke_env` **fails loud** (not a silent skip) on any missing precondition, since absence means the smoke toolchain was not provisioned. A stale screenshot is removed first so a previous run cannot make the test pass. The nineteenth test needs none of this.

**NOTE:** the smoke test asserts only the typed `hello`, not the cursor; cursor geometry and color are covered by the pure `cursor.rs` unit tests above plus visual confirmation (OCR is too fragile to couple to the cursor).

### Fixture naming: a smoke's own files can disarm its assertion

**The rule, and it is a convention rather than a changelog entry: when a smoke asserts on a file's CONTENT, that file's NAME must not contain the asserted word.**

The file-tree sidebar renders every file in the cwd by name, and nvim's `:e` toast echoes the filename too. So a fixture whose name contains the smoke's own OCR term satisfies the assertion whether or not the feature under test did anything — a permanent silent false positive, not a flake.

Two pre-existing smokes were passing exactly that way and are now fixed:

- **`picker_opens_and_loads_selected_file_under_cage`** shipped a `pickertarget.md` fixture against the asserted `pickertarget`. That is not a theory: during the command-drain unit's broken-accelerator run — GTK's keymap-aware accel matching never fired under `wtype`, so Ctrl+Shift+O was forwarded to Neovim instead of opening the picker — this smoke **passed green while the picker demonstrably never opened**. Fixed by renaming the fixture to `ptarget.md` (and the query to `ptarget`); the heading `# PICKERTARGET` and the asserted term are unchanged, so the word now lives ONLY in the buffer and only a rendered buffer can satisfy the assertion.
- **`vertical_split_shows_two_panes_under_cage`** shipped `paneleft.md` / `paneright.md` against `paneleft` / `paneright`, so BOTH assertions were satisfiable by sidebar rows alone: the smoke would have passed green if `<C-w>v` had never split anything. Fixed by the same rename shape (`pleft.md` / `pright.md`), terms unchanged.

Both changes **strengthen** the tests; nothing was weakened, no assertion or OCR const moved. `picker_arrow_navigation_selects_second_match_under_cage` was checked and does not share the defect (`pick1.md` / `pick2.md` against `picktwo` / `pickone` — it failed correctly during the broken run), and every other smoke was audited and is clean.

The **one deliberate exception** is `tree_sidebar_shows_files_under_cage`, where `treenode.md` carries the asserted `treenode` on purpose: there the sidebar row IS the feature under test. That exception is also why `sidebar_filler_names_cannot_satisfy_any_smoke_assertion` cannot simply be widened to cover fixture names — generalizing it would need an explicit opt-out list. The guard therefore covers the FILLER filenames only, and this rule covers the rest by convention; the gap is recorded in the guard's own doc comment.

### Vacuity is not only a fixture-naming problem: the drag smoke's false premise

The cases above are all "the fixture can satisfy the assertion". This one is different and joins the same running record: **the assertion was fine, and the premise underneath it was false.**

The first version of `drag_selects_a_range_under_cage` was **vacuous with respect to `drag-update`**. With `pane_view.rs::on_pane_drag` neutered to an immediate no-op it passed **3/3**. The premise stated in its own doc comment and in its failure message — "Vim enters visual mode only on a drag, never on a press+release at two different cells" — is **FALSE for nvim 0.12.2**, and was measured directly:

```text
press+release only : visualmode="v" marks="3 4 8 13" cursor="8 13"
press+drag+release : visualmode="v" marks="3 4 8 13" cursor="8 13"
```

Byte-identical. A `<LeftRelease>` at a cell different from the press enters charwise visual mode by itself, so `on_pane_release` alone reproduces the exact Neovim state the original drag asserted, and neutering `on_pane_drag` could not make it red.

The damage was partial rather than total: the out-of-widget clamp (Drag B) was still meaningful, because `on_pane_release` also runs `drag_point` -> `start_point() + offset` -> `cell_at`. What was unproven was specifically **that `drag-update` is ever emitted at all**.

The fix **added** an assertion rather than weakening one: the round-trip **Drag Z**, whose press and release are at the SAME cell. With `drag-update` the outbound sweep starts visual mode anchored at the probe, the return sweep walks the cursor back, and the selection collapses to one cell — `visualmode() == "v"` with `'<` == `'>`. Without it, nvim sees `<LeftMouse>` then `<LeftRelease>` at one cell, no movement, no selection: `visualmode()` is `""` and the marks are `0 0 0 0`. That is a clean, exact discriminator built from the readback idiom the smoke already used. Verified red 2/2 with `on_pane_drag` neutered, then green 9/9 with zero flakes across five isolated runs, one post-restore run and three full-suite runs.

The general lesson, and the reason this is recorded next to the fixture-naming rule rather than in a changelog: **a red-run demonstration is a deliverable, not a formality.** Both defects were invisible in review and both were caught only by deliberately breaking the code under test and checking that the test noticed. The `:qa` smoke carries the same shape of hazard from a third direction — a process that vanishes because the GTK main loop panicked looks exactly like one that shut down cleanly, which is why that smoke asserts a ZERO exit status and gives "exited, but non-zero" its own distinct exit code rather than folding it into "still alive".

### Pointer injection: how it works and why it is built this way

This section is a **record of what was built and measured**, not a lament. Until this branch, pointer input had no end-to-end coverage at all and this file said so at length. It now has four cage smokes, and what follows is why they take the shape they do and what the harness actually measured.

**The wlroots fact that dictates everything.** Under `cage` with `WLR_BACKENDS=headless` there are no real input devices, and wlroots advertises `WL_SEAT_CAPABILITY_POINTER` on the seat **only while some pointer device exists** (cage's own `seat.c` `update_capabilities`). So a tool that creates a virtual pointer, injects, and exits flips the capability on and back off again before any client can bind `wl_pointer`. The injector must be **long-lived** — one `zwlr_virtual_pointer_v1` held open for the whole scenario — and that single requirement is what rules out every off-the-shelf option below.

**`wlrctl` was tried and is PROVEN not to work.** This is a measurement, reproduced identically across three runs, not a prediction. Every `wlrctl` invocation is a separate short-lived process; the GTK client's own `WAYLAND_DEBUG=1` log shows `wl_seat.capabilities(3)` -> `get_pointer` -> `capabilities(2)` -> `wl_pointer.release()` **59 microseconds apart, inside one dispatch batch**, so the client never holds a live `wl_pointer` when the button events fire and wlroots drops them: **zero `wl_pointer.button` events reached the client in a whole plain-`wlrctl` run.** All three calls still exited `0` — an exit code from `wlrctl` says nothing whatsoever about delivery, which is the same vacuous-success shape the [fixture-naming](#fixture-naming-a-smokes-own-files-can-disarm-its-assertion) rule guards against in another form. `wlrctl` 0.2.2 also has no press/release split (its `click` is atomic, in one process), so even if it delivered it could not drive a drag. **It must stay out of `flake.nix`:** shipping it in the toolchain would advertise a capability that does not exist.

**`ydotool` cannot reach cage at all.** It writes to a uinput kernel device, and `WLR_BACKENDS=headless` (with `WLR_LIBINPUT_NO_DEVICES=1`) means cage consumes **no** kernel input devices, so nothing `ydotool` writes is ever read. `/dev/uinput` being ACL-writable is not the blocker; the headless backend is.

**sway was investigated and REJECTED.** It cannot do this either. It is a wlroots compositor, so the seat-capability fact above applies unchanged; its `swaymsg … cursor` commands **report success while delivering nothing**, the same exit-code-says-nothing shape as `wlrctl`; and it has **no axis verb at all**, so the wheel smoke could not be expressed under it even in principle. Two claims that circulated from that investigation are **sway findings and do not apply under cage**, and are withdrawn here so nobody re-derives them: the "+20,+20 client-side-decoration offset" (under cage the measurement is **zero offset** — see below) and "`wtype` loses keystrokes" (not observed under cage, where all eighteen smokes drive the app with `wtype`). sway is out of scope; do not add it.

**What was built instead: [`wolf-pointer-inject`](../../../tools/wolf-pointer-inject/README.md).** A small committed C program in `tools/wolf-pointer-inject/`, built by `flake.nix` with `stdenv.mkDerivation` + `wayland-scanner` over the `wlr-protocols` XML and put on the devShell `PATH`. It creates exactly one `zwlr_virtual_pointer_v1` at startup and holds it for the whole scenario (which is what keeps the seat's pointer capability on), then reads `motion` / `press` / `release` / `axis` / `sync` / `quit` commands from stdin one per line and acks each one after a `wl_display_roundtrip`. Every event group ends with a `wl_pointer.frame`, which is mandatory rather than decorative: GTK's Wayland backend buffers pointer events and only turns them into `GdkEvent`s on `frame`, so without it the compositor delivers bytes and GTK delivers nothing. Its README is the authoritative record of the grammar, the ack protocol, the coordinate model and the exit codes; do not restate them here.

**Measured on this host, 2026-08-02** — these are the provenance for the constants in `smoke_headless.rs`, and nothing here was rounded or assumed:

- **cage output size `1280x720`.** Read from the helper's `ready` line, copied into a file and asserted by the Rust side, never assumed (1280x720 is wlroots' headless default, not a contract).
- **Helper readiness line: `ready extents=1280x720 manager_version=2 outputs=1`.** cage advertises `zwlr_virtual_pointer_v1` **version 2**, so the pointer is created with `create_virtual_pointer_with_output`, which pins `motion_absolute`'s coordinate space to that one output rather than to the implicit layout.
- **CSD / surface-coordinate offset under cage: NONE.** `motion 640 360` arrives at the GTK client surface-local as `640.00000000, 360.00000000`, with `xdg_toplevel.configure(1280, 720, …)`. The origin band below is kept anyway as a tripwire for a FUTURE GTK / libadwaita / cage change, not because an offset exists today.
- **`cell_w` = `22.4765625`, `cell_h` = `44.0`** at `WOLF_FONT_PT=28` with the `FONTCONFIG_FILE`-pinned DejaVu Sans Mono.
- **`winwidth(0)` = `45`, `winheight(0)` = `14`.** The 30-character `:put` fixture therefore does not soft-wrap (15 columns of margin), which matters because `runtime/nvim/init.lua` sets `wrap` and `linebreak`: a line wider than the pane would break the screen-row-to-buffer-line correspondence every delta assertion depends on. If the pane ever narrows below ~35 columns, shrink the fixture — never the assertion.
- **Probe pixel `(640, 360)` maps to Neovim `line 8, col 18`**, which satisfies every geometry precondition at once.
- **Derived pane origin `(257.8984375, 52.0)`**, with `PANE_ORIGIN_TOLERANCE_PX = 12.0`. The derived value carries the probe click's unknown sub-cell phase (measured spread across three probe points: 15.2 px in x, 16 px in y — under `cell_w` and `cell_h` respectively), which is why the band adds `cell_w` / `cell_h` as a phase allowance on top of the tolerance.
- **`gdk::ScrollUnit` reported by a real cage/wlroots wheel event: `Wheel`, with `|dy| == 1.0` per detent.** `axis 15.0 1` arrives at the client as `axis_source(0)` (WHEEL) + `axis_relative_direction(0, 0)` + `axis_value120(0, 120)` + `axis(t, 0, 15.0)` + `frame()`. With `:set mousescroll=ver:1`, `line('w0')` went `1` -> `4` over three down detents and back to `1` over three up: **one detent is exactly one line.** This closes the "scroll SENSITIVITY is unmeasured" item this file used to carry, and the assertion is exact with no fallback branch.
- **`--test smoke_headless` reports `19 passed`** in about **71 seconds** (measured 71.0-71.6 s across three runs).
- **`cargo test --workspace`** emits 92 `test result:` lines, all `ok` — **654 passed, 0 failed** — and the only `ignored` anywhere is the permitted `regenerate_png_golden`.

**A diagnostic trap worth writing down.** libwayland's CLIENT-side `WAYLAND_DEBUG` output prints `interface#id.event` with a **`#`**, not `@`. A grep for `wl_pointer@[0-9]+\.(enter|motion|button|axis)` silently matches nothing and reads exactly like "zero events were delivered". Use `#`.

#### `POINTER_STEP`: a pacing knob, and why it is load-bearing

`POINTER_PREAMBLE` defines `POINTER_STEP=0.2` and an `hstep` helper (`hsend` followed by that sleep), and every in-gesture pointer command of the drag body uses `hstep` rather than `hsend`. The reason is **Neovim's API**, not GTK and not this repo: `nvim_input_mouse(button, action, modifier, grid, row, col)` transports only the BUTTON CODE through the typeahead, while the position rides on the globals `mouse_grid` / `mouse_row` / `mouse_col`, which the API handler overwrites the moment the call is serviced. Measured against nvim 0.12.2, three RPCs landing 0.4 ms apart all resolved at the LAST position. Before pacing, the drag smoke was 6/8 and 7/8 in isolation and failed 2 of 3 full-suite runs; after pacing it was 15/15 in isolation plus clean full-suite runs. Pacing also stops GDK's motion compression from folding the intermediate waypoints into a single `drag-update`. **No assertion was touched to achieve that. If the drag smoke ever flakes again, raise `POINTER_STEP` — never touch an assertion.**

#### The focus-wedge fix is now executed, and what Run B does and does not show

`click_then_close_keeps_keyboard_input_alive_under_cage` is the first execution of `df3bb3d`. **The fix works.** The three-part revert was run and the full 2x2 matrix isolated:

```text
configuration                          | result
---------------------------------------|---------------------------------------------
revert (1) `.focusable(true)` only      | green
revert (2) `area.grab_focus()` only     | green
revert (1)+(2), guard intact  (Run B)   | ALIVE1 ok, ALIVE2 ok, OCR FAILS -- pane blank
revert (1)+(2)+(3)            (Run A)   | ALIVE1 ok, ALIVE2 ABSENT -- the wedge
```

**Run A** (all three parts reverted — `.focusable(true)` restored on the pane `DrawingArea`, `on_pane_clicked` grabbing focus onto the clicked pane's own area, and `rebuild_pane_area`'s `focus_inside_pane_area()` return-focus guard neutered) is the headline red evidence: `$ALIVE1` is written and `$ALIVE2` is absent. Keys reached Neovim before the pane close and stopped after — the wedge, exactly as described.

**Run B** (reverting only the two structural parts, leaving the `rebuild_pane_area` guard intact) has **both `ALIVE` assertions passing**. That is the finding: the guard is **load-bearing**, and keyboard input survives on it alone. This converts `rebuild_pane_area`'s return-focus guard from "cheap insurance against a reachable-tomorrow defect" into a measured fact — it had never been executed by anything before.

**Run B is NOT green overall, and must not be recorded as such.** The run fails, because that deliberately-broken configuration renders the surviving pane **blank** (screenshot inspected: sidebar and header draw, editor pane empty), so the OCR corroboration fails. That is a **second, separate defect of a broken build**, not the wedge. It was reproduced twice. The guard's load-bearingness is evidenced by the two `ALIVE` assertions passing, **not** by a green overall run.

One limitation of the evidence, stated plainly: the wedge's red demonstration was performed against the first pass of this file and was **not** re-run after the drag smoke's Drag Z was added. Its assertion predicate is provably unchanged (same `alive2_present` predicate, same message opening, shifted down by Drag Z's insertion) and only the message tail changed, so the evidence is "provably still applicable" rather than freshly re-run. Every other pointer smoke's red evidence is fresh.

#### What is still unproven

Being scrupulous about this is the point of the section. **PROVEN by the four smokes:**

- **`gtk::GestureDrag` fires from a real `wl_pointer` event**, and `on_pane_press` -> `send_pane_mouse` -> `cell_at` maps a real widget-local coordinate to the predicted cell (click smoke, exact delta).
- **`drag-update` is emitted during a button-held move** (drag smoke, Drag Z — the round trip; an empty `visualmode()` with marks `0 0 0 0` is the clean negative).
- **`offset_x` / `offset_y` reconstruct the absolute point via `start_point() + offset`, and the gesture keeps delivering after the pointer leaves the pane**, with `cell_at` clamping the out-of-widget point rather than the event being dropped (drag smoke, Drag B: release over the sidebar, column clamps to 1).
- **`gtk::EventControllerScroll` fires from a real `wl_pointer.axis` frame**, and the unit and magnitude it reports are now measured and pinned (scroll smoke).
- **The click-then-close focus wedge is gone** — as a **composite** with the `rebuild_pane_area` guard, not as the `focusable(false)` half in isolation. See the honest scope note on that smoke's bullet.
- **`rebuild_pane_area`'s return-focus-to-the-strip guard is now executed** on every pane close in the wedge smoke, and Run B shows it is load-bearing.

**STILL UNPROVEN, and the reasons matter:**

- **The strict press -> `focus_win` -> `send_mouse(Press)` ORDERING.** That `focus_win` fires on a click IS proven — the wedge smoke's `<C-w>c` closes the pane that was CLICKED, which the OCR pair corroborates. The strict ordering remains **unobservable**, because Neovim's own `<LeftMouse>` also moves the current window, so no readback can distinguish "focus arrived first" from "the press moved it". It stays guaranteed **by construction**: both ride the same ordered input channel. Do not tick this.
- **`record_pointer`.** The scroll smoke cannot discriminate it: `on_pane_scroll` names the target grid explicitly, so a stuck `(0.0, 0.0)` recorded pointer would still scroll the right window and the smoke would still pass. Nothing here tests that the motion controller's recorded position is ever used correctly.
- **`drag_grid` / `drag_button` press-pinning.** No smoke drags from one pane into another: the three that drag run with a single pane (Drag B leaves the pane only for the sidebar, which is not another grid), and the one smoke that has a split only clicks. So the pin is never discriminating — there is no other grid for a wandering drag to be retargeted to. The test that WOULD prove it: split vertically, press in the LEFT pane, drag into the RIGHT pane, release, and assert the selection stayed in the left pane's buffer. That is a future unit, not this one.
- **`gtk::EventControllerMotion`** more generally: its `connect_motion` / `connect_enter` handlers exist only to feed `record_pointer`, so the item above covers them. No smoke asserts on anything the motion controller produces.

### Deliberate test gaps

Three things the GTK front-end's behaviour deliberately does **not** smoke, with what covers them instead:

- **The primary menu popover is not smoked.** `wtype` cannot click the header-bar `MenuButton`, and keyboard-navigating to it is too fragile to be worth the flake. It is covered by the pure `actions.rs` menu tests (every item references a declared, implemented, non-Reserved action; every label matches the registry title) plus the fact that three of its seven items' actions are proven end-to-end by the accelerator and `:qa` smokes.
- **The `gtk::FileDialog`s (Open Folder… / Open File…) are not smoked.** There is no portal backend under `cage`, so the dialog cannot be driven at all. Their callback bodies are trivial; the empty state's _presentation_ is smoked.
- **The sidebar re-root after Open Folder is not smoked** (same reason). `workspace::reroot_ready` is unit-tested, and `TreeHandle::reroot` reuses the already-smoked `FileSearch` refresh path.

## The `key_from_char` helper

`gdk_key.rs`, `roundtrip_nvim.rs` and `src/actions.rs`'s `mod tests` each define a small `key_from_char(c: char) -> gdk::Key` helper, because gdk4-rs has no `Key::from_unicode`. It builds the keyval exactly as GDK would from a Unicode scalar:

```rust
use gdk::glib::translate::from_glib;
fn key_from_char(c: char) -> gdk::Key { unsafe { from_glib(gdk::unicode_to_keyval(c as u32)) } }
```

This is test-side only and does not change `gdk_key`'s contract: printables still carry the exact glyph, and `gdk_key` reads `keyval.to_unicode()` and sets `shift: false` for `Key::Char`.
