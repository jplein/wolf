# wolf-gnome/tests

Tests for the seams and the windowed application. They split into **headless** checks (no display, no nvim), two **real-Neovim** end-to-end tests (no mocks, per project policy — the key round-trip and the mouse/scroll seams), and twenty-three **headless-compositor** cage smoke tests that launch the real window (one window-render smoke, two file-picker smokes, one file-tree-sidebar smoke, five split-pane smokes — vertical split, horizontal split, a three-pane same-orientation split, focus move, close pane — five command-drain smokes: the empty state, the Ctrl+Shift+N new-untitled-buffer chord, `:q` closing the focused pane, `:qa` closing the window, and the Ctrl+Shift+W close-pane chord — four **pointer** smokes: click-to-position, drag-to-select, wheel scroll, and the click-then-close focus-wedge regression — two **crash-recovery** smokes: a SIGKILLed Neovim that restarts and reopens its files, and a deliberately failing respawn whose dwelling crash overlay is dismissed by clicking its "Restart Neovim" button — and three **state-persistence** smokes: a three-pane layout and a lone open file each surviving a quit-and-relaunch, plus the window title rendering the working directory) plus four pure guards on the smokes' own fixtures and harness, which need no compositor. Everything runs through `nix develop --command` so the GTK toolchain, the pinned font, and `WOLF_NVIM_BIN` are present:

```sh
nix develop --command cargo test -p wolf-gnome
```

The default run **does** include all twenty-three cage smokes, and they are the slowest part of the suite — see [the smoke test section](#smoke_headlessrs--windowed-app--picker--tree--panes--commands--pointer--crash-recovery--state-persistence-real-compositor). They are part of the Linux verification gate; see [`build.md`](../../../build.md), "The Linux verification gate", for the authoritative full check.

## `geometry.rs` unit tests — `grid_size_for` and `cell_at` (headless)

The pure pixel-to-grid geometry is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/geometry.rs`](../src/geometry.rs)), needing no GTK, display, or nvim.

**`grid_size_for`.** A table-driven `grid_size_for_table` covers the typical exact-division case (`800×592` with `8×16` cells → `100×37`), flooring of partial cells (`17×17` → `2×1`), the min-1 clamp for tiny/zero/negative dims, the whole-result collapse to `(1, 1)` for degenerate cell sizes (zero/negative/NaN/ infinite, including a single-axis NaN), and the upper clamp of `i32::MAX` dims to `u16::MAX`. A second test, `grid_size_for_independent_axes`, proves cols and rows are computed separately (wide-but-short and narrow-but-tall grids).

**`cell_at`** adds two more tests in the same module:

- `cell_at_table` — the pointer → cell contract, row by row. Cell centres map to their own cell; an exact cell boundary belongs to the HIGHER cell while a hair below it does not (`floor`, pinned from both sides); a point far outside in either direction clamps to the nearest EDGE cell rather than being rejected (the drag-past-the-edge behaviour), including the one-axis-only case; a `1×1` grid collapses every point in the plane to `(0, 0)`; a degenerate `cell_w`/`cell_h` (zero, negative, NaN, infinite) or a zero-extent `cols`/`rows` collapses the WHOLE result to `(0, 0)`; and a `u16::MAX × u16::MAX` grid probed at `1e12` saturates at index `65534` rather than wrapping. Three rows pin the non-finite **coordinate** rule, which is two rules and not one: **NaN has no direction, so its axis is treated as `0.0`, while `+inf` / `-inf` DO have a direction and clamp to the last / first cell** like any other out-of-range point. Every assertion message re-states that the return is `(row, col)`, not `(x, y)`.
- `cell_at_never_exceeds_grid_size_for` — the composition guarantee, made executable. For each of four widget/cell shapes (typical `800×592` at `8×16`; tiny `3×3`, where `grid_size_for` clamps up to `1×1`; huge `i32::MAX` at `1×1`, where it saturates at `u16::MAX`; and a non-integer `9.37×19.51` cell) it computes `(cols, rows) = grid_size_for(...)` and then asserts `col < cols && row < rows` for seven probe points: far outside negatively, the origin, the centre, a hair inside the bottom-right corner, exactly the corner, far outside positively, and NaN in both axes. This is what lets `pane_view` pass a pointer position straight into a `wolf_core::MouseEvent` with no bounds check of its own.

## `mouse.rs` unit tests (in `src/mouse.rs`, headless)

The pure pointer-translation rulebook is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/mouse.rs`](../src/mouse.rs)), needing no GTK, display, or nvim — `gdk::ModifierType` and `gdk::ScrollUnit` are plain value types, exactly like the ones `input.rs`'s headless tests already use. Nine tests — eight below, plus the convention guard at the end:

- `mouse_input_table` — every modifier combination the seam honours (none, Ctrl, Shift, Alt, all three), and then the rows that are the actual point: **`SUPER_MASK` alone yields all-false rather than leaking through as anything**, `SUPER_MASK | CONTROL_MASK` yields ctrl only, and `LOCK_MASK` (Caps) is likewise ignored — Neovim's mouse grammar is only `"C-"` / `"S-"` / `"A-"`, so a bit outside it must be dropped, not translated. The refusal rows cover middle, secondary, button `0`, and the thumb buttons `8` / `9`, plus secondary-with-Ctrl, so a refused button stays refused no matter what is held down.
- `scroll_threshold_table` — `Wheel` returns the detent threshold whatever the cell height is (including a degenerate `0.0`); `Surface` returns `cell_h` when it is usable and falls back to the detent threshold when it is `0.0`, negative, NaN or infinite; and `__Unknown(7)` — the arm that `gdk::ScrollUnit`'s `#[non_exhaustive]` forces — falls back to the detent threshold too, pinning the documented "over-sensitive beats dead" choice. The test carries a scoped `#[allow(clippy::float_cmp, reason = …)]`: every expected value is exactly representable and is returned unmodified rather than computed with, so an epsilon comparison would weaken the assertion without making it more correct.
- `scroll_accumulator_table` — scenarios, not single calls: each case applies an ordered list of `Consume` / `Reset` ops to one fresh accumulator, which is what makes the CARRY observable. The macOS-ported rows (one whole cell → one step; two 0.6-cell nudges crossing exactly once; a 1.5-cell leftover carrying into the next call; a symmetric direction reversal; `reset` clearing the carry; exactly one cell three times running with no drift; one step per detent) pin behavioural equivalence with the Swift original. The GTK-specific hardening rows pin what the Swift does **not** have: a zero threshold returns `0`, does not hang, and does not break the next call; negative / NaN / infinite thresholds return `0` and leave the carry untouched, proved by a following nudge that still crosses exactly one boundary; NaN / `+inf` / `-inf` deltas likewise leave the carry unpoisoned; two finite `1e308` deltas whose SUM overflows the remainder to infinity get it zeroed rather than poisoned; and a `1e300` delta saturates at `±MAX_STEPS_PER_EVENT` and DROPS the carry, so it cannot keep firing. The two `1e300` rows also assert a timing property no `assert!` can state — under the macOS `while`-loop formulation they would iterate ~`1e300` times and the test would never return, so **if this test hangs, the arithmetic form has been replaced by a loop.**
- `scroll_accumulator_new_matches_default` — `new()` and `Default::default()` must agree, because `PaneScroll` reaches the type through both (`PaneScroll::new()` builds it with `new()`, the `Default` derive builds it through the derive) and a disagreement would give one pane a phantom carry.
- `pane_scroll_table` — the same scenario shape one level up, over `PaneScroll::steps_for(grid, delta, threshold)`, with **no `Reset` op at all**: `PaneScroll` exposes no manual reset, and a grid CHANGE being the only way to clear the carry is precisely the property under test. The no-reset rows prove nothing is cleared that should not be (a first call on a fresh value is honoured in full; the same grid carries across calls; a direction reversal on one grid is not a grid change). The reset rows prove the rule from four angles: a grid change discards a sub-step carry; changing BACK also resets, so the rule is "differs from the previous call" and not "never seen before"; the leftover a WHOLE-step call parks is dropped by a grid change too; and — the contract detail most easily lost in a refactor — **a call `consume` REJECTS still counts as a call**, so a NaN-delta event naming a different grid ends the old grid's carry exactly as an accepted one would. The remaining rows pin that every `ScrollAccumulator` guard (the non-finite delta/threshold rejections and the `±MAX_STEPS_PER_EVENT` clamp) passes straight through unchanged.
- `grid_change_discards_the_carry` — the same rule stated on its own so a failure NAMES it rather than pointing at a table row: two 0.6-cell nudges on DIFFERENT grids must both return `0`, and a third on the second grid must return `1` (so the reset did not break the accumulator). This rule used to live in `pane_view.rs::on_pane_scroll` — GTK glue, which needs a live display, so at the time nothing in the suite could execute it. Moving it into `mouse::PaneScroll` is what made it testable at all, and it is still the right home now that the cage pointer smokes exist: a per-grid carry rule needs two panes and a pointer that scrolls across both, which no smoke does yet (see [What is still unproven](#what-is-still-unproven)), and it is decidable from its arguments so it is far better pinned headlessly regardless.
- `pane_scroll_new_matches_default` — `PaneScroll::new()` and `Default::default()` must agree in BOTH fields: a non-zero carry is a phantom step, and a non-`None` `last_grid` would make the first real scroll event on that pane a spurious grid CHANGE.
- `scroll_steps_table` — `0` → `None`, `±1` and `±7` → the expected direction and magnitude, and `i32::MIN` → `Some((Up, 2_147_483_648))`, pinning that `unsigned_abs` is total where a plain `-x` would panic in a debug build.

Plus one non-table test whose only job is to make a convention un-flippable: **`scroll_direction_is_inverted_from_macos`**. It asserts `scroll_steps(1) == Some((Down, 1))` and `scroll_steps(-1) == Some((Up, 1))`, under a block comment explaining that AppKit maps a positive delta to `Up` while GDK's `dy > 0` is `GDK_SCROLL_DOWN`, and that `ScrollDirection::Down` is pinned against real Neovim (by [`crates/wolf-ffi/tests/mouse_scroll.rs`](../../wolf-ffi/tests/mouse_scroll.rs)) to strictly increase `win_viewport.topline`. Without it, someone cross-reading `PaneContainerView.swift` could "correct" the mapping, break GTK scrolling entirely, and leave every macOS test green — because macOS never runs this code.

## `cursor.rs` unit tests (in `src/cursor.rs`, headless)

The pure cursor geometry and color logic is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/cursor.rs`](../src/cursor.rs)), needing no GTK, display, or nvim. A table-driven `cursor_rect_table` covers the geometry per shape: `Block` always returns the full cell (ignoring `cell_percentage`); `Vertical` is a left bar of full height whose width is `cell_percentage` of `cell_w` (default `0.25`), floored to `MIN_BAR_PX` for tiny percentages and capped at `cell_w` for out-of-range ones; `Horizontal` is the analogous bottom bar against `cell_h` (anchored to the bottom edge). Deliberately non-square cells and a non-zero origin keep width/height math and offsets distinguishable. `named_constants_match_contract` pins `MIN_BAR_PX` / `DEFAULT_CELL_PCT` / `PCT_DENOM`.

A second group covers `cursor_colors` over hand-built `Snapshot`s: the **honor** path (a mode cursor highlight with distinct fg + bg → `(bg, fg)`, including with editor defaults set); the **inversion** path (bg-only, fg-only, `attr_id` `None`, out-of-range `mode_idx`, and empty `mode_infos` all fall through to `(cell_fg, cell_bg)` without panicking); the **guard** cases where a degenerate honored pair must NOT be honored (fill equal to the underlying cell background, or fill equal to glyph) and instead inverts; and the **fallback** case where unset cell colors reach the white/black `FALLBACK_FG` / `FALLBACK_BG`.

## `picker.rs` unit tests (in `src/picker.rs`, headless)

The picker's pure seams are unit-tested **inside their own module** (a `#[cfg(test)] mod tests` in [`src/picker.rs`](../src/picker.rs)), needing no GTK, display, or nvim:

- `next_selection_table` — down/up within range, clamp at both ends with NO wrap, empty list → `None`, single row, and out-of-range/negative `current` clamped.

## `actions.rs` unit tests (in `src/actions.rs`, headless)

The whole action namespace is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/actions.rs`](../src/actions.rs)), needing no GTK, display, or nvim — `gdk::Key` and `gdk::ModifierType` are plain value types, and keyvals are built with the same `key_from_char` helper used by `gdk_key.rs` (which is what lets a case spell the SHIFTED glyph `'O'` a real keymap delivers for Ctrl+Shift+O):

- `every_accel_parses` — `parse_accel` returns `Some` for every declared accelerator. It first asserts the table declares at least one accelerator at all, so an emptied `ACTION_TABLE` cannot make every per-row test below pass vacuously.
- `accels_use_key_names_not_symbols` — the `<Control>-` vs `<Control>minus` trap: no key part may be a single punctuation character, and each must be either all-lowercase or one of the known named keys (`Left` / `Right`). `gtk_accelerator_parse` lowercases key names, so an uppercase spelling does NOT imply Shift.
- `no_accel_makes_a_neovim_key_unreachable` — `forbidden_reason` is `None` for every row (including the Reserved ones), **plus** explicit negative cases proving the checker bites: `<Control>p`, `<Super>n`, `<Primary>p` and `<Alt>p` are all refused, while `<Alt>Left` is accepted. (Which mechanism refuses a chord is an implementation detail — `<Super>` / `<Primary>` fail `parse_accel`'s grammar, `<Control>p` / `<Alt>p` parse and are refused by `forbidden_reason` — so the test asserts the composed contract.)
- `accels_are_unique` — no accelerator string is declared twice; a duplicate means one action silently never fires.
- `action_names_are_valid` — every action matches `^(app|win)\.[a-z0-9]+(-[a-z0-9]+)*$`. `gio` rejects a malformed name with a runtime warning, not a compile error, so this is the only cheap place to catch a typo.
- `bound_set_is_exactly_this_unit` — the `Bound` rows are exactly `win.go-to-file`, `win.new-buffer`, `win.close-pane`, `app.quit`, and each really has a chord to register.
- `action_for_key_table` (20 rows) — the LIVE matcher, and therefore user-visible behaviour, since `shell::AppShell::install_chord_controller` calls it from a capture-phase controller: each of the four bound chords fires in BOTH letter cases (a case-sensitive comparison would mean the chord never fires on real hardware while a lowercase-only test still passed); a bare `Ctrl+<letter>` does NOT fire, so `<C-o>` / `<C-n>` / `<C-w>` / `<C-q>` still reach Neovim; a Reserved row does NOT fire; the Ctrl/Shift/Alt match is EXACT (adding Alt misses); and a modifier bit outside the grammar is IGNORED, pinned from both sides — `Super+Shift+o` → `None` (Super can never supply the missing Ctrl) while **`Ctrl+Shift+Super+o` → `win.go-to-file`**. That last row is deliberate: an unintercepted Super chord is actively harmful, since Neovim drops the modifier in normal mode and inserts literal `<D-x>` text in insert mode, so intercepting it is strictly better than forwarding it.
- `key_name_matches_table` (21 rows) — every key-NAME shape `ACTION_TABLE` uses, including the named-key and punctuation-name branches that `action_for_key` cannot otherwise reach today (all four bound rows are single letters, while a later unit promotes exactly those Reserved rows). The negative rows are the point: an unknown name is `false` rather than a guess, and a punctuation name against a non-printable keyval (whose `to_unicode()` is `None`) is `false` rather than a panic.
- `command_action_round_trip` — command ↔ action is a bijection over the rows that carry a command.
- `menu_items_reference_declared_actions` — every `MenuItemSpec.action` is in `ACTION_TABLE` (a `gio::Menu` item naming an unknown action renders INSENSITIVE at popup time — a silent, visual-only failure). It also asserts `MENU_SECTIONS` is non-empty and no section is empty.
- `menu_never_lists_a_reserved_action` — a Reserved action is not installed this unit, so a menu item pointing at one would appear and do nothing.
- `menu_labels_match_the_registry` — where a menu item's action maps to a command, its label equals `Command::spec().title`, so a registry rename cannot silently desync the GTK menu.

## `command_action.rs` unit tests (in `src/command_action.rs`, headless)

The total `Command` → `UiAction` mapping is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/command_action.rs`](../src/command_action.rs)):

- `ui_action_table` — one row per `Command` variant in discriminant order, pinning the classification. Its length is asserted equal to `wolf_core::COMMAND_SPECS.len()`, which is what makes the table non-vacuous: a newly appended core command cannot be absorbed silently. Rows pin the CLASS for the two unimplemented variants, not their reason strings — duplicating ~18 sentences here would make a wording tweak look like a behaviour regression.
- `every_registered_command_maps` — walks `COMMAND_SPECS` and asserts each command appears in the table exactly once. Belt-and-braces for the totality guard: the `_`-free match already makes a new variant a compile error, but that evaporates the moment anyone adds a catch-all arm, whereas this check walks the registry rather than the match.
- `dispatched_commands_are_the_expected_set` — the commands whose action is neither `Deferred` nor `NoGnomeEquivalent` are exactly the eight this unit dispatches (`close_pane`, `close_window`, `go_to_file`, `minimize_window`, `new_buffer`, `open_file`, `open_folder`, `quit_application`), by registry `id` so the failure message names a row a reader can grep for. Nothing quietly promoted, nothing quietly demoted.
- `unimplemented_reasons_are_distinct_and_non_empty` — every `Deferred` / `NoGnomeEquivalent` reason is non-empty, reads as a mid-sentence clause (an ALL-CAPS opener such as "GNOME" is allowed, since the reason is interpolated into `"wolf-gnome: command {cmd:?} not dispatched: {reason}"`), and is UNIQUE — so no two rows of the README's command table can collapse into one indistinguishable entry, and a future pedantic `clippy::match_same_arms` run stays clean.

## `workspace.rs` unit tests (in `src/workspace.rs`, headless)

The launch decision and the re-root settle are unit-tested **inside their own module** (a `#[cfg(test)] mod tests` in [`src/workspace.rs`](../src/workspace.rs)). `launch_decision` takes `is_dir` as an injected predicate, so these need no temp directories and no real `$HOME`:

- `launch_decision_table` — seventeen rows in two blocks. The **pre-restore** eight are re-run verbatim with `restored: None`, and that is the **compatibility proof made executable**: a real project dir that is neither home nor `/` → `Folder`; `cwd == home` → `EmptyState { home }` (the desktop-launcher shape); `cwd == "/"` → `EmptyState { home }`; no process cwd at all → `EmptyState { home }`; a cwd the injected `is_dir` rejects → `EmptyState { home }`; `home == None` with a real project cwd → still `Folder`; `home == None` with an unusable cwd → `EmptyState { FALLBACK_CWD }`; and `home` set but not a directory → `EmptyState { FALLBACK_CWD }`. Every one of them must still hold unchanged, because the `restored` parameter is a strict superset of the old rule rather than a change to it. The **restore** nine then pin the new half: the restored project opens when the process cwd is home, is `/`, is absent, or is not a directory; **a usable process cwd WINS over an equally usable restored cwd** (the Linux ordering rule, stated as its own row); a restored cwd that is not a directory falls back to `EmptyState { home }`; a restored cwd equal to `home` or to `/` is refused **by the same predicate** as a process cwd would be (which is what stops a hand-edited `state.json` from pointing `FileSearch` at the whole filesystem); and a restored cwd is still usable when `home` is unknown.
- `reroot_ready_table` — `pending` `None` → false; `live` `None` → false; neither known → false; equal → true; a still-old `live` → false; a **trailing separator is NOT a difference** (`Path: PartialEq` compares components, so `/a/b/` == `/a/b` — the implementation is a plain `==` and must not be hand-rolled into a byte comparison); but an unnormalized `..` **is** a difference, which is exactly why callers canonicalize first.

## `state_seam.rs` unit tests (in `src/state_seam.rs`, headless)

The whole application-state rulebook — what is restored at launch and what is persisted on each wake — is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/state_seam.rs`](../src/state_seam.rs)), needing no GTK, no display, no nvim, no temp directory and no real `$HOME`: every input is injected, including `is_dir`. Eleven tests:

- `restore_plan_table` — the whole `RestorePlan` value per scenario: no saved state at all → identical to a bare `launch_decision`, with `layout: None` and `window_size: None`; a saved directory that still exists while the process cwd is home → `Folder { saved }` **with** the layout attached; a saved directory that is gone → `EmptyState` and the **layout dropped**; saved `windows: []`; saved `tabs: []`; and a saved tab whose `layout` is already `None`. Asserting the whole struct rather than a field at a time is what stops a regression in one member hiding behind the others.
- `a_layout_is_never_restored_into_a_different_project` — the rule stated on its own so a failure names it: a usable process cwd that differs from the saved cwd yields `Folder { process }` with `layout: None`. Its counterpart `a_layout_is_restored_when_the_process_cwd_is_the_saved_project` proves the guard is not simply "never attach a layout", which is the way this pair could otherwise both pass vacuously.
- `window_size_is_independent_of_the_cwd_decision` — the saved size is restored whether the plan lands in `Folder` or in `EmptyState`; the two axes do not interact.
- `restored_window_size_table` — `(0,0)`, a negative in either axis, NaN in either axis, `±inf` and `1e18` all collapse the WHOLE result to `None` (never a per-axis partial answer); `(1200.0, 640.0)` → `Some((1200, 640))`; and a fractional pair rounds. The `1e18` row is the one that pins the `i32::try_from` path rather than a saturating cast.
- `persistable_layout_table` — an empty lone leaf → `None`; a NAMED lone leaf → `Some(Leaf)`; a PREVIEW lone leaf → `Some(Leaf)`; a split of two empty leaves → `Some(Split)`. Rows two and four are the single-pane regression from both sides: an arity guard would return `None` for row two and `Some` for row four, i.e. exactly inverted on the two rows that matter.
- `snapshot_cwd_table` + `the_empty_state_persists_no_cwd` — `empty = true` persists `""` for every live/launch combination; `empty = false` with a live cwd persists the live one; `empty = false` with none persists the launch cwd (so quitting before the first `DirChanged` does not forget the project). The second test states the empty-state half over the whole domain, because persisting nvim's fallback cwd would turn every desktop-launcher start into "a project at `$HOME`" on the next launch.
- `may_snapshot_table` + `only_alive_with_a_bound_pane_may_snapshot` — all three `Liveness` values × `bound_panes ∈ {0, 1, 3}` × `reported_windows ∈ {0, 1}`, asserting its own row count so a row that quietly went missing cannot hide, plus the rule stated over the whole domain with the failure mode named: a snapshot taken while nvim is dead or before the first pane binds persists `layout: None` and **destroys the user's saved layout**. This is the one table in the crate whose purpose is preventing data loss rather than a wrong pixel.
- `snapshot_state_is_one_window_one_tab` — exactly `windows.len() == 1` and `tabs.len() == 1`; `x == 0.0 && y == 0.0`, pinned so nobody "fixes" the unpersisted window position by filling it with a plausible-looking coordinate; and `sidebar_visible` round-trips, so the field cannot silently rot out of the file while it is written-but-never-read.

## `pane_layout.rs` unit tests (in `src/pane_layout.rs`, headless)

The codec between the live `PaneLayout` (leaf IDs) and the persisted `wolf_core::PaneNode` (leaf PATHS) is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/pane_layout.rs`](../src/pane_layout.rs)). Eight tests, several of which exist to make one specific historical bug un-reintroducible:

- `encode_maps_ids_to_paths` — a mapped id becomes its path; an **unmapped** id becomes `""` (macOS parity); nested split orientation and weights are preserved verbatim; `preview` is always `false`.
- `is_empty_leaf_table` — `Leaf{"", false}` → true; `Leaf{"", true}` → false; `Leaf{"/a", false}` → false; `Leaf{"/a", true}` → false; and **`Split[Leaf{"",false}, Leaf{"",false}]` → false**, the anti-arity row.
- `arity_is_never_the_predicate` — **the headless twin of the single-pane regression**, stated on its own so a failure NAMES the rule rather than pointing at a table row: `is_empty_leaf` is `false` for a named leaf at leaf count 1, and `false` for a split of two empty leaves at leaf count 2. Any arity-shaped predicate gets both of those backwards.
- `leaf_paths_dfs_matches_the_spec_order` and `decode_preserves_leaf_order_for_an_asymmetric_tree` — over the exact `Vertical[ Horizontal[a, b], c ]` tree `pane_layout_survives_relaunch_under_cage` builds, pinning the DFS assumption that smoke's exact-readback assertion depends on. A symmetric tree could not distinguish a correct order from a transposed one, which is why the fixture is asymmetric.
- `decode_allocates_contiguous_ids_from_first_leaf_id` — ids are allocated sequentially in DFS order, so `leaf_ids[i]` really is the pane for `handles[i]`.
- `decode_round_trips_encode` — `encode` → `decode` → `PaneTree::layout()` equals the original shape **and the original NON-EQUAL weights `[0.25, 0.75]`**. The non-equal vector is deliberate: nothing on Linux can produce one yet (divider drag is unimplemented), so this is the only place the weight round-trip is exercised at all — see [What is still unproven](#what-is-still-unproven). It carries a scoped `#[allow(clippy::float_cmp, reason = …)]` on the `mouse::scroll_threshold_table` precedent; every expected weight is exactly representable and returned unmodified.
- `decode_rejects_malformed` — a 0-child split, a 1-child split, a weights/children length mismatch, a NaN weight, a negative weight, an all-zero weight vector, `MAX_RESTORE_LEAVES + 1` leaves and `MAX_RESTORE_DEPTH + 1` depth all yield `None`. This is a **crash guard, not tidiness**: `pane_view::build_chain` indexes `children[0]` unconditionally, so a zero-child split reaching the widget layer is a panic, and the two caps stop a hand-edited `state.json` from asking nvim for hundreds of windows at launch.

## `title.rs` unit tests (in `src/title.rs`, headless)

The window-title seam is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/title.rs`](../src/title.rs)). Three tests:

- `display_title_table` — an empty cwd → `""`; an all-whitespace cwd → `""`; an empty `home` → verbatim; `home == "/"` (which normalizes to `""`) → verbatim; `cwd == home` → `"~"`; `cwd == home + "/"` → `"~/"`; a `home` with a trailing slash behaving exactly as one without; a cwd under home → `"~/rest"`; a cwd sharing no prefix → verbatim; and **`/Users/janet/x` against home `/Users/jane` → verbatim**. - `window_title_falls_back_to_wolf` — an empty or whitespace cwd yields `"Wolf"`, everything else yields `display_title`'s value, and `WINDOW_TITLE_FALLBACK == "Wolf"` (the same string `app.rs`'s window builder seeds, so the title cannot flicker between two spellings).
- `home_is_never_read_from_the_environment` — the injected-`home` determinism property made executable: `display_title("/x", "")` is `"/x"` regardless of the process `$HOME`. The one impure `$HOME` read in the crate stays in `workspace::home_dir`, and `shell.rs` captures it once at build time.

## `persistence.rs` (no unit tests, and none are missing)

[`src/persistence.rs`](../src/persistence.rs) carries **no `#[cfg(test)] mod tests`**, deliberately and for the same reason `crash_overlay.rs` carries none: it holds no rules. Every decision it acts on lives in `state_seam.rs` / `pane_layout.rs`, which are tabled above; what is left is gathering live values from a `WolfCore`, a `gtk::ApplicationWindow` and a `PaneHandle` and handing them to `StateStore::set_snapshot`, none of which is reachable without a display and a running Neovim. Its coverage is therefore the two relaunch cage smokes below plus those tables. One property it owns alone is worth naming, because nothing tests it directly: **borrow discipline**. `flush_on_close` runs inside `close-request`, which then does `core.borrow_mut().take()`, so every core borrow in the module is taken and dropped in its own statement. ## `liveness_ui.rs` unit tests (in `src/liveness_ui.rs`, headless)

The crash/stall recovery rulebook is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/liveness_ui.rs`](../src/liveness_ui.rs)), needing no GTK, no display and no nvim — `wolf_core::Liveness` is a plain `Copy` value type. Eleven tests; the sibling `crash_overlay.rs` has **none and can have none**, because it is entirely GTK widget construction, which is why its coverage is a cage smoke.

- `liveness_ui_table` — one row per `(liveness, may_auto_restart)` combination, asserting the WHOLE `LivenessUi` value. It asserts its own row count against `3 × 2`, so a row that quietly went missing cannot hide behind the five that remain, and it pins that `Alive` and `NotResponding` are byte-identical across both budget values — a regression that made `Alive` stop painting once the cap was reached would freeze a perfectly healthy editor and nothing else in the crate would notice.
- `only_dead_auto_restarts` — the same rule stated over the whole domain rather than per row, so a failure NAMES it: exactly one of the six inputs may request an automatic restart. This is one of the two rules the crash smoke discriminates end to end, and reverting `liveness_ui`'s `(Dead, true)` row was measured to fail it in ~0.5 s headlessly as well as ~89 s under cage.
- `not_responding_never_auto_restarts` — pinned separately because it is the one place a "just restart it" simplification would silently destroy a user's work: `restart_nvim` force-kills the process, so a wedged-but-recoverable Neovim loses everything not already in a swap file.
- `overlay_message_table` — the message each mode carries, that the two `Crashed` variants are DISTINCT (an identical string would make the `retrying` flag invisible), and the OCR cross-satisfaction guard **made executable**: both crash messages contain `crashed`, neither they nor the button label contain `restarted`, the stall message contains neither, and the banner contains `restarted` but not `crashed`. Without that last positive half every "must not contain" assertion above it would be idle.
- `restart_outcome_table` + `refresh_never_requests_an_auto_restart` — how `WolfCore::restart_nvim`'s result is classified given that its `Ok(false)` is a no-op rather than a failure, plus the infinite-respawn-loop guard: a `Refresh` may never carry `auto_restart: true`, or a persistently failing respawn would retry from INSIDE the restart path and bypass the attempt cap entirely.
- `reopen_order_table` + `active_is_always_last` — active last; active absent from the set; active `None`; an empty set; EVERY occurrence of the active path filtered rather than just the first; non-active relative order preserved; non-active duplicates KEPT (not deduplicating is a decision, not an oversight). `active_is_always_last` states the rule over every row, and additionally that the active path appears exactly once. Reverting `reopen_order` to push the active path first was measured to fail it with a message naming the rule.
- `restart_button_rect_table` + `restart_button_rect_is_inside_the_overlay` — the button geometry, over real cage-sized allocations, both inclusive lower bounds, and degenerate inputs in each axis independently (zero, negative, NaN, `±inf`), all collapsing the WHOLE result to `(0, 0, 0, 0)` rather than a partial rect. The containment property mirrors `geometry.rs`'s `cell_at_never_exceeds_grid_size_for` and is what discriminates the width guard: without it an overlay narrower than the button yields a negative `x` and the cage smoke would click outside the window. Both carry a scoped `#[allow(clippy::float_cmp, reason = …)]` on the `mouse::scroll_threshold_table` precedent — every expected component is a hand-derived halving or sum of small integer constants, exactly representable and returned unmodified.
- `named_constants_match_contract` — pins the four geometry constants plus `MAX_AUTO_RESTART_ATTEMPTS` and `BANNER_VISIBLE_SECS` (mirroring `cursor.rs`'s test of the same name), so a smoke that derives a pixel from them cannot be silently retargeted and the banner's lifetime cannot be quietly lengthened to make a racing capture pass.

## `app.rs` wake-channel unit tests (in `src/app.rs`, headless)

Three tests that make the wake bridge's **safety argument executable**. The bounded wake channel silently DROPS a wake fired while it is full, `wolf_core::liveness::mark_dead` fires exactly once, and a dead Neovim produces no further redraw wakes at all — so the crash overlay appears only because a dropped wake implies a still-queued one, which implies a full handler run after the drop, which (because `mark_dead` stores `Dead` **before** waking, and liveness is a level-triggered atomic read) observes the death.

- `a_dropped_wake_implies_a_pending_wake` — fill the channel, assert the next `try_send` is `Err(Full)`, assert a `try_recv` then yields `Ok(())`. That implication is the whole argument.
- `consuming_a_wake_frees_the_slot_before_the_handler_runs` — fill, `try_recv` once, assert a subsequent send succeeds; pins that the handler body runs against an empty slot, so a wake fired DURING a handler run is not lost either.
- `wake_channel_capacity_is_at_least_one` — guards against a `bounded(0)`, which `async-channel` panics on.

All three read the production `WAKE_CHANNEL_CAP` rather than a literal `1`, which is why they live in `app.rs`'s own module and not under `tests/`: raising the capacity must not be able to turn them into tests of something else. They guard specifically against a future change to `async-channel`'s bounded semantics — a ring buffer that dropped the OLD item instead of refusing the new one would silently invalidate the argument and there would be no other tripwire.

## `layout.rs` unit tests (in `src/layout.rs`, headless)

The pure **N-ary frame** pane-layout tree (`PaneTree`, matching Neovim's window model) is unit-tested **inside its own module** (a `#[cfg(test)] mod tests` in [`src/layout.rs`](../src/layout.rs)), needing no GTK, display, or nvim — twenty-three tests covering:

- **construction / split** — `new` is a single leaf; a `Vertical` split yields two leaves side by side and a `Horizontal` split stacks them; `pane_rects` tiles the bounds for both; a perpendicular nested split produces the expected nested rectangles.
- **flatten vs. nest (the N-ary frame model)** — a split whose orientation MATCHES the containing frame FLATTENS into an equal-sized sibling row/column (a row `[P1, P2]` vsplit on `P1` becomes equal thirds `[P1, P3, P2]`, not a nested 25/25/50; repeated same-orientation vsplits stay flat at four equal columns), while a PERPENDICULAR split (an hsplit of a row member) NESTS into a sub-frame.
- **remove / collapse / re-equalize** — removing a leaf collapses its sibling (and a sibling _subtree_) into the parent's slot; removing a flat-row member re-equalizes the survivors (nvim `equalalways`); a now-1-child split collapses into its sole child; a surviving same-orientation split merges upward into the parent; removing the last pane is a no-op.
- **neighbor** — basic Left/Right (`Vertical`) and Up/Down (`Horizontal`) neighbours, a nested 2x2 case, a flat row of three, and `None` for an unknown pane.
- **ordering** — `leaves` and `pane_rects` enumerate in a stable DFS order.
- **`from_layout` (three tests, added with state persistence)** — `from_layout_round_trips_layout` composes it against `layout()` over the existing test trees (a single leaf, a 2-leaf vertical, a flat row of three, a nested perpendicular); `from_layout_does_not_reshape` proves a **same-orientation nested split survives verbatim** with `leaves()` order unchanged, which is the property the restore path's handle-to-leaf zip depends on and which `split()` would normalize away; and `from_layout_rejects_broken_invariants` covers 0-child, 1-child, a length mismatch, NaN, negative and zero-sum weights, all `None`. The rejection test is a crash guard — `pane_view::build_chain` indexes `children[0]` — and it overlaps `pane_layout::decode_rejects_malformed` deliberately: the invariants belong to the type that owns them, and the codec's cap checks belong to the codec.

## `paint_golden.rs` — paint (headless, offscreen)

Builds a deterministic 4×2 `Snapshot` via core's public constructors (`Snapshot::new`, `HighlightTable::set_defaults`/`define`, `Grid::set_cell`), including one defined `hl_id` with distinct fg/bg and a wide-trailing empty-text cell. It measures `CellMetrics` against a throwaway 1×1 probe surface, sizes a real offscreen `ImageSurface` (ARGB32) to exactly the grid, paints, and samples pixels.

**Primary gate — structural ARGB center-sampling** (always on; deliberately _not_ a whole-image hash, which is too brittle across freetype/fontconfig):

- Known background fills are rasterizer-independent, so the center of the defined-bg empty cell and a default-bg cell are asserted for **exact** equality.
- The empty wide-trailing cell's interior is sampled at several inset points and must be background-only (verifying the "skip the glyph" path).
- The glyph cell's rect must contain at least one non-background pixel (the glyph was actually drawn).

Pixel reads assume little-endian ARGB32 (in-memory byte order `B, G, R, A`), which holds on the x86_64 Linux target.

**Dev aid (not part of the gate)** — `regenerate_png_golden` is `#[ignore]`d; it writes `tests/testdata/paint_golden.png` via `ImageSurface::write_to_png` (which needs the `cairo-rs` `png` feature). Run it explicitly:

```sh
nix develop --command cargo test -p wolf-gnome --test paint_golden \
    -- --ignored regenerate_png_golden
```

It is now the **only** `#[ignore]`d test in the whole repo, so a bare `cargo test -p wolf-gnome -- --ignored` runs nothing but this golden rewrite.

Font determinism relies on the pinned `DejaVu Sans Mono` exposed via `FONTCONFIG_FILE` (set by the flake devShell from [`testdata/fonts.conf`](../testdata/fonts.conf)).

## `mouse_nvim.rs` — the mouse/scroll seams end-to-end (real Neovim)

Two `#[test]`s that drive the pure pointer seams into a real `WolfCore` and a real, hermetic Neovim. What the GTK glue would do inside a `gtk::GestureDrag` / `EventControllerScroll` callback, this file does by hand: `wolf_gnome::cell_at` turns a pane-local pixel point into a grid cell, `mouse::mouse_input` encodes the button + modifiers, `mouse::{scroll_threshold, ScrollAccumulator, scroll_steps}` turn a delta into discrete steps, and the results go through `WolfCore::send_mouse` / `send_scroll`. It needs no real font and no GTK: the seams are pure, so locally-declared `CELL_W = 8.0` / `CELL_H = 16.0` exercise exactly the arithmetic the glue performs with the measured `render::CellMetrics`.

**This file is no longer the only pointer coverage, and it deliberately does not overlap with the rest.** It drives the pure **seams** — `cell_at`, `mouse_input`, the accumulator, `send_mouse` / `send_scroll` — into a real core and a real Neovim, with no GTK controller anywhere in the picture. The four cage pointer smokes below drive the GTK **glue**: whether `gtk::GestureDrag` and `gtk::EventControllerScroll` fire from a real `wl_pointer` event at all, whether `drag-update` is emitted, whether the offsets reconstruct the absolute point, and which `gdk::ScrollUnit` a real wheel event reports. Neither can answer the other's question, so neither duplicates the other; see [Pointer injection](#pointer-injection-how-it-works-and-why-it-is-built-this-way) below.

Shared setup (`start_with_filled_buffer`) starts the core, waits for the attach flush, polls for a live editor **window** grid (`>= 2`, not hidden — mouse and scroll must never target grid 0/1), fills the buffer via `:put =map(range(1,200), 'printf(''%05d'', v:val)')`, and parks the view at line 1. Two empirical constraints are carried over verbatim in substance from [`crates/wolf-ffi/tests/mouse_scroll.rs`](../../wolf-ffi/tests/mouse_scroll.rs) and commented in place: the lines must be **5 characters wide**, because `:put =range(1,200)` yields 1-char lines and a click at column 2 would clamp to end-of-line and defeat the exact-column assertion; and a literal double quote **cannot** appear inside `:put =<expr>` (Neovim strips it as the start of an Ex comment, giving `E115`), so the format string is quoted with doubled single quotes.

- **`mouse_press_drag_release_selects_via_seams`** — asserts `cell_at` maps the centre pixel of cell `(5, 2)` back to `(5, 2)` **before** anything is sent, which is what proves the rest of the test exercises the intended cell rather than whatever nvim happened to do; sends a `Press` there and polls until the cursor sits at exactly that grid-local `(row, col)`; then computes a drag point **40 cells beyond the right/bottom edge**, asserts `cell_at` clamps it to exactly `(rows - 1, cols - 1)` — that clamp is the whole reason drag-past-the-edge selection works — and sends `Drag`; asserts the selected `ModeInfo` name contains `visual` (name-based, following `crates/wolf-core/tests/input_keys.rs`, so it is not coupled to nvim's `mode_info_set` ordering); sends `Release` at the same point and asserts the selection SURVIVES it and that the cursor moved DOWN from the press row (directional on purpose — nvim clamps to the last BUFFER line, not the last grid row). It closes with a negative control: `mouse_input(gdk::BUTTON_SECONDARY, ..)` must be `None`, so no right-click can ever reach Neovim.
- **`scroll_seam_moves_viewport_via_wolfcore`** — drives a real `ScrollAccumulator`: with the `Surface` threshold, one 0.6-cell nudge must return `0` and the second must return `1` (the sub-cell carry, through the real type rather than a reimplementation of it); a 5-cell delta must encode as `ScrollDirection::Down` with `count >= 1`, and sending that many `ScrollEvent`s must strictly **increase** `win_viewport.topline`; a negative delta must encode as `Up` and strictly **decrease** it — with an explicit precondition that the preceding down-scroll left `topline > 0`, so the decrease assertion is falsifiable rather than trivially true. It ends by asserting `scroll_threshold(ScrollUnit::Wheel, CELL_H) == 1.0`, so one detent is one step whatever the cell height is, driven through the same code path. It carries a scoped `#[allow(clippy::float_cmp, reason = …)]` for that single exactly-representable comparison.

**Requirements and wiring.** A real, pinned Neovim located via `WOLF_NVIM_BIN`; `common::require_nvim_bin()` **panics rather than skipping** if it is unset, per project policy. `cargo test` auto-discovers every `tests/*.rs`, and **`crates/wolf-gnome` has no `BUILD.bazel` at all**, so there is no Bazel `rust_test` target to add for this file — unlike `crates/wolf-core` / `crates/wolf-ffi`, where CLAUDE.md's "every new test file must be wired into a target" rule bites. The test's own module doc says so too, so nobody goes looking for one.

## `smoke_headless.rs` — windowed app + picker + tree + panes + commands + pointer + crash recovery + state persistence (real compositor)

Twenty-three `#[test]` cage smokes that prove the whole stack actually draws a window, drives the file picker, populates the file-tree sidebar, creates / focuses / closes native split panes, dispatches drained commands (the empty state, the accelerators, `:q` and `:qa`), **routes real pointer events through `pane_view.rs`'s gesture and scroll controllers** (a click positions the Neovim cursor at the predicted cell, a button-held move selects a range including a release outside the pane, a wheel detent moves the viewport by exactly one line, and clicking a pane and then closing it does not wedge keyboard input), **survives the death of the captive Neovim** (a SIGKILLed nvim leaves the app alive, raises an opaque crash overlay, restarts in place, reopens the Tier-1 files with the active one focused, recovers an unsaved edit out of the dead process's swap file, and hands the fresh Neovim a grid of the same size), and — since this branch — **survives a QUIT**: the tab's pane-split tree and its open file are written to `state.json` and rebuilt on the next launch, and the header bar renders the working directory. They run in the **default** suite: the compositor and OCR toolchain they need comes from the flake devShell, so a normal `cargo test` run _inside `nix develop`_ does have it, and `require_smoke_env` fails loud if it does not. To run them:

```sh
nix develop --command cargo test -p wolf-gnome --test smoke_headless
```

That target reports **`27 passed`**, not `23`: the file also carries four pure, compositor-free guards (`sidebar_filler_names_cannot_satisfy_any_smoke_assertion`, `temp_cwd_name_cannot_satisfy_any_smoke_assertion`, `restore_fixture_names_cannot_satisfy_their_own_assertions` and `cage_is_only_spawned_through_the_isolating_helper`, the last four bullets below), none of which calls `require_smoke_env` or needs any of the toolchain. The whole target takes a **measured 104.02 seconds** on this host at twenty-seven tests (it was `21 passed` in 89.14 s, ~71 s at nineteen, and 35.27 s at fifteen). The two relaunch smokes account for most of the increase, and structurally so: each runs **two full app launches** inside its single `cage` instance.

**Serialization (`CAGE_LOCK`).** Each smoke launches its own `cage` compositor, and two compositors started concurrently contend for the same Wayland socket under `XDG_RUNTIME_DIR` (lockfile error), which would fail both under the default parallel harness. So all twenty-three smokes acquire a shared `static CAGE_LOCK: Mutex<()>` for their whole body, forcing serial execution; poisoning is recovered from (`into_inner`) so one panicking test does not cascade into the others. The two relaunch smokes run their **two app launches inside ONE `cage` instance** (one scenario string, two sequential `"$WOLF_BIN" &` blocks) precisely so this stays true: no second compositor is ever started, and `CAGE_LOCK`'s semantics are unchanged. This serialization is why the smokes are the slowest part of the suite. **The pointer and crash-recovery smokes deliberately live in this same file for that reason.** A separate `tests/pointer_smoke.rs` was considered and rejected: each `tests/*.rs` is its own crate and its own PROCESS, so an in-process `static Mutex` cannot serialize across them at all, and moving `CAGE_LOCK` into `tests/common/mod.rs` would not help either — that module is compiled separately into every integration-test binary, so it would produce N independent mutexes rather than one shared one. It would look like a fix and serialize nothing. A separate file would therefore need real cross-process locking (an `flock` under `XDG_RUNTIME_DIR`, with its own stale-lock and poisoning story) to keep two `cage` instances off one socket — new machinery and a new failure mode, for smokes that are the same shape as the ones already there and want exactly the same serialization.

**Mechanism (common to all twenty-three).** Each locates the built binary via `CARGO_BIN_EXE_wolf-gnome` and runs its interactive scenario as one `sh -c` string **inside `cage`** (the headless wlroots compositor) so that `wtype` and `grim` inherit cage's `WAYLAND_DISPLAY` (cage exports it only to its child process tree). The scenario launches the app in the background, polls (not a fixed sleep) until the window maps, drives it via `wtype`, captures the live window with `grim` to a PNG under `XDG_RUNTIME_DIR`, then OCRs it on the host with `tesseract … stdout --psm 11` ("sparse text" mode — the default page-segmentation mode returns empty on the sparse light-on-dark editor grid). A stale screenshot is removed first so a previous run cannot make a test pass. The one exception is `colon_qa_closes_the_window_under_cage`, which captures no image at all: its assertion is a property of the process table, so it calls neither `grim` nor `tesseract`.

**`cage_command` is the ONE place the compositor is spawned, and it sets four environment variables every smoke must have.** Callers chain only their own scenario-specific `.env(...)` additions on top; `cage_is_only_spawned_through_the_isolating_helper` enforces the single-place property mechanically, because a smoke that built its own `cage` invocation would silently lose all four.

- **`WOLF_FONT_PT` = `SMOKE_FONT_PT` (28)** — glyphs large enough for `tesseract`, and the exact number `cell_metrics_for_smoke` measures against, so the app and the test cannot drift.
- **`WOLF_STATE_DIR` = `smoke_state_dir(cwd)`** — a **sibling** of the temp cwd named `<cwd>-state`. A sibling and not a child, because a child would be walked by the app's own `FileSearch` (which excludes only `.git/` and `.wolf/`), putting `state.json` and every `swap/<hash>/*.swp` into the sidebar and the picker and changing the page density every OCR assertion is calibrated against. It is also what makes the two relaunch smokes possible at all: both launches inside one scenario get the same directory, so the second reads exactly the `state.json` the first wrote.
- **`HOME` = `smoke_home(cwd)`, the cwd's PARENT** — an OCR **determinism control**, not tidiness; see the page-determinism finding below. Two smokes deliberately override it (the empty-state smoke points `HOME` at the cwd itself to fire `launch_decision`'s `cwd == home` branch; the title smoke points it at its nested project's parent), and both still render a CONSTANT title.
- **`XDG_CACHE_HOME` = `smoke_shader_cache_dir()`** — ONE directory shared by every smoke of a `cargo test` invocation, the direct counterweight to the `HOME` redirect: redirecting `HOME` also redirected `$HOME/.cache`, so mesa rebuilt ~4.9 MB of shader cache on **every** launch. Measured, 20 iterations per cell: at `SETTLE = 0.25` a warm cache is 20/20 and a cold one 0/20; the cold threshold is only crossed at 0.35. Sharing warms it once per invocation, so 26 of the 27 tests run warm. It does **not** carry across invocations — the path lives under `TMPDIR`, which `nix develop --command` rewrites every time (measured: 100 iterations produced 100 distinct caches) — and that is acceptable rather than a defect, because `SETTLE = 1.0` is ~2.9× the measured cold threshold and the deliberately-cold arm passed 100/100. The tripwire: that argument holds only while `SETTLE` carries that margin. **Do not make this directory per-smoke to match its neighbours** — a shader cache is content-addressed and purely derived, so it cannot carry a fixture, a buffer, an MRU row, a swap file or a `state.json` between smokes; making it per-smoke is exactly the change that reintroduced the flake, and it reintroduces it invisibly.

**Mechanism (the five smokes that inject pointer events).** Four of them are the pointer smokes proper; the fifth is `crash_overlay_and_restart_button_recover_under_cage`, which needs a real click on the overlay's "Restart Neovim" button. They additionally start [`wolf-pointer-inject`](../../../tools/wolf-pointer-inject/README.md) inside cage **before** the app — so the seat already carries `WL_SEAT_CAPABILITY_POINTER` when GTK does its first `wl_seat` roundtrip and calls `get_pointer` at bind time — wait for its `ready extents=<W>x<H> …` line, and then drive it over a FIFO with a poll-for-ack protocol: every `motion` / `press` / `release` / `axis` command is followed by an `ok <n>` that the helper prints only **after** a `wl_display_roundtrip`, so an ack means "the compositor has processed this event" rather than "the bytes left our buffer". All of that plumbing lives in one shared `POINTER_PREAMBLE` string rather than being pasted five times. The scenarios keep the FIFO's write end open on fd 3 for their whole lifetime (each `echo` would otherwise close it and hand the helper a spurious EOF), and a `trap`ped `cleanup()` kills the helper first and the app second, so the app's shutdown is never racing a pointer event. Distinct scenario exit codes: `11` the app died before the window mapped, `12` the helper never became ready, `13` a helper command was not acked within budget, `14` a Neovim readback file never appeared, `15` the helper died mid-scenario.

**Mechanism (the two crash-recovery smokes only).** Both must find and kill the **captive Neovim child**, never the app, and both do it with a `/proc` scan built from `sed` alone — `FIND_NVIM_PID_HELPER` — rather than `pgrep` / `ps`, deliberately: adding `procps` would mean a `flake.nix` change and its Darwin-eval obligation for no benefit. The scan reads each `/proc/<pid>/status` for `Name:` and `PPid:` and demands **exactly one** match (`Name: nvim`, `PPid` = the app), exiting `17` otherwise, because a kill aimed at an unidentified target makes nothing downstream mean anything; the app itself is never a candidate (its own `Name:` is `wolf-gnome`) and it has no other children. Two details are load-bearing and were found the hard way. **Zombies must be filtered**: `kill -0` succeeds on a zombie and `/proc/<pid>` still exists for one, so without also reading `State:` and treating `Z*` as gone, the "the app is still alive" assertion could pass on a dead-but-unreaped app and the "the killed nvim left the process table" poll would time out as exit `18` on exactly the red runs whose predicted symptom is exit `19`. And **the full `/proc` scan costs 2.58 s** on this host (three `sed` forks per process), enough that one scan between the restart and the screenshot ate most of the banner's four-second life — hence an `app_children()` fast path reading `/proc/<pid>/task/<pid>/children`, with the full scan kept as a fallback. Shared exit codes: `16` **the app died with its Neovim** (the worst possible failure of this feature, and one that must never be confused with anything else), `17` not exactly one live `nvim` child, `18` the SIGKILLed Neovim never left the process table, `19` recovery timed out (`bufname('%')` never named the fixture again). The overlay smoke adds `20`: an automatic respawn attempt happened that should not have.

**Three of the four pointer smokes proper assert on files the captive Neovim writes about its own state**, not on OCR: `printf('%d %d', line('.'), col('.'))`, `visualmode()` plus `'<` / `'>`, and `line('w0')`, each `writefile`d to an absolute path passed in from Rust and then polled for. Those are exact integers. OCR is fine for "did this word render" and is structurally incapable of "did the cursor land at exactly line 12, column 25"; an integer readback also cannot be satisfied by a sidebar row or an `:e` toast, and it fails with `expected (9, 12), got (5, 1)` instead of a wall of misread glyphs. `grim` still runs in all four and the PNG is still retained for post-mortem; `tesseract` runs only in the wedge smoke, where the OCR pair carries real corroborating signal. Each readback file is removed before the run and asserted absent, exactly as the stale PNG is — evidence that could be a previous run's leftover is not evidence.

**No pointer smoke hardcodes a magic pixel.** The Rust side measures `cell_w` / `cell_h` exactly (a 1x1 `cairo::ImageSurface` probe through `CellMetrics::for_font`, with the same family and the same parsed `SMOKE_FONT_PT` the app is launched with, so the two cannot drift), clicks once at the probe point, reads `(l0, c0)` back out of Neovim, and expresses every later target as `round(PROBE + D * cell)` with the assertion on the exact **delta**. That is origin-independent. The derived pane origin is then checked as a loud, self-checking precondition — a band whose tolerance is `12.0` px, deliberately under `20.0` so a `+20,+20` surface offset would FAIL, plus a `cell_w` / `cell_h` phase allowance that is unavoidable and must not be grown to make a failing run pass. Its failure message names the four candidate causes in order: a GTK4 CSD / shadow-margin offset appearing under cage, an `adw::HeaderBar` height change, an `app::TREE_PANE_WIDTH` or `gtk::Paned` divider change, and a cage output-size change.

**Every one of the twenty-three launches in a FRESH temp working directory** (`make_temp_cwd()`, passed to the `cage` command as its `current_dir`), not in the repo. That isolation is mandatory, not tidiness. The app derives `CoreConfig.cwd` from `std::env::current_dir()`, and the captive Neovim keeps a **durable, per-project swap directory keyed on that cwd** (`wolf_core::state::swap_dir_for` → `state_dir()/swap/<hash of cwd>`), which deliberately outlives the process so a fresh nvim can recover a crashed one's unsaved edits. That property is no longer only a rationale: `nvim_crash_recovers_and_reopens_the_file_under_cage` depends on it directly, since the restart reuses the same `NvimConfig` and therefore the same swap dir, which is what lets the fresh Neovim find the SIGKILLed one's swap file and recover the `unsavedburst` marker. Every scenario ends by `kill`ing the app, so its nvim never cleans up. At a **fixed** cwd those two facts compose into a self-poisoning test: run _N_ leaves a stale `%…%Untitled.md.swp` behind and run _N+1_ finds it at startup, where naming the startup buffer `<cwd>/Untitled.md` collides with it inside `nvim_buf_set_name` and raises a blocking ATTENTION dialog that eats the first keystroke — so the smoke goes red for whatever change happens to be in flight, and points at the wrong cause. A fresh cwd makes each run idempotent. (The product-level guard for that swap collision is deliberate, headless and lives in [`crates/wolf-core/tests/swap_recovery.rs`](../../wolf-core/tests/swap_recovery.rs), `stale_untitled_swap_does_not_block_a_fresh_start`.) A side benefit: the app no longer traverses the entire repository through `FileSearch` on launch, and no longer writes into the working tree. That last point has deliberate exceptions, all of the same kind: `window_renders_typed_text_under_cage` writes nine tiny marker `.md` files into its own temp cwd purely so the tree sidebar has rows of text to draw — the repo listing used to supply that page density accidentally, and OCR has always depended on it (see that test's bullet below for the measurement) — and the three state-persistence smokes drop the same nine, for the same reason, alongside their own fixtures. The temp dirs are **not** auto-deleted, to aid post-mortem inspection.

**The temp cwd is `<unique>/project`, and both halves of that shape are load-bearing.** The unique parent carries the pid and a nanosecond timestamp (`TEMP_CWD_PREFIX`); the child's name is the FIXED `TEMP_CWD_BASENAME`. Since the header bar renders the app's working directory, the directory NAME became page text — and because `cage_command` hands the unique parent to the app as `HOME`, `title::display_title` abbreviates it away and every smoke's title is the constant **`~/project`**. See the page-determinism finding below for why a run-varying title is not survivable.

**Where the smokes' own durable state now goes, and how that is proved.** `WOLF_STATE_DIR` was NOT set on the cage command before the state-persistence unit, so every smoke run wrote its per-project swap directory and the three MRU sqlite files into the **developer's real `~/.local/state/wolf/`**. That was tolerable only while nothing durable was at stake. It stopped being tolerable the moment `wolf-gnome` started writing `state.json`: without an override, a smoke run would READ the developer's real saved window size, working directory and pane layout at launch — so it would not start from a clean slate, and would not be reproducible — and OVERWRITE them at quit with a throwaway one-pane temp-cwd layout. `cage_command` therefore sets `WOLF_STATE_DIR` on **every** smoke, the guard keeps that single-place, and `single_pane_file_survives_relaunch_under_cage`'s assertion 4 is the behavioural check that it holds (see its bullet). The measured result of a full `--test smoke_headless` run: **zero bytes** written into the real state dir — no `state.json` appeared, the swap-directory count was unchanged, and all three MRU files' mtimes were unchanged to the nanosecond. Residual writes under a full `cargo test --workspace` come from `wolf-ffi`'s integration tests and two `wolf-gnome` non-smoke integration tests, which are pre-existing and outside this file.

Assertions: the dwell OCR **contains** `crashed`; the dwell OCR does **not** contain `bounceback` — **the overlay is opaque and full-bleed**, a guarantee nothing else in this repo proves (the empty-state smoke asserts presence only), and non-vacuous in the other direction because the sidebar is _not_ covered and still renders the `bfile.md` row; the post-click OCR contains `bounceback`; and exactly **one** automatic respawn attempt was made. **No magic pixel:** the click point comes from `wolf_gnome::restart_button_rect` — the same function the widget builder realises as size requests — composed with the cage extents and the derived pane origin, guarded by three self-checking preconditions and then re-derived after the run from the run's own measured extents. **Two of its five reverts did not go red as first written, and both were fixed rather than explained away.** The attempt cap was completely untested, because `assert_no_nvim_respawn` counted children named `nvim` and a refused wrapper exits **before** its `exec` (so it is never named `nvim`): the wrapper now logs each refusal and the assertion demands exactly one, after which the `u32::MAX` build reproduced **75 attempts in 4 s** against the capped build's 1. And the button geometry was untested, because the click was derived at the rect's **centre** and `set_size_request` is only a minimum on a `halign(Center)` button: pixel-scanned, the correct builder renders `x 605..924` and the 40 px builder `x 669..861`, **both centred on `x 765`**. The click is now derived a tenth in from the rect's LEFT edge (`x 641`), which is 36 px inside a correct button and 28 px clear of the natural-width one.
- **`pane_layout_survives_relaunch_under_cage`** — the pane-split TREE survives a quit and relaunch. Run 1 opens `rleft.md` (`# RESTOREALFA`), `<C-w>v`, opens `rright.md` (`# RESTORECHARLIE`) in the new pane, `<C-w>h` back, `<C-w>s`, opens `rmid.md` (`# RESTOREBRAVO`) — an asymmetric `Vertical[ Horizontal[rleft, rmid], rright ]` whose DFS leaves are `[rleft, rmid, rright]` — then `:qa`, polling `kill -0` until the process is gone and requiring a ZERO exit. - **`single_pane_file_survives_relaunch_under_cage`** — the GTK-side regression guard for the macOS single-pane persistence bug, and the highest-value test of the state-persistence unit. Run 1 opens `szulu.md` (`# SOLOZULU`) with **no split** and quits; a decoy `salfa.md` (`# SOLOALFA`), alphabetically first, is never opened. The scenario FREEZES run 1's `state.json` into a copy before run 2 can overwrite it. **Assertion 1 is the regression assertion, and it is on the FILE not on pixels:** `wolf_core::load_state` parses that frozen copy and demands `windows[0].tabs[0].layout == Some(Leaf { path, preview: false })` with a non-empty `path` whose file NAME is exactly `szulu.md`. The name rather than the whole path is deliberate — `/tmp` may resolve through a symlink on this host, so nvim's reported `abs_path` need not be string-equal to anything the test could construct — but it is not weakened to "layout is `Some`": an arity guard yields `layout: null`, and an empty-path leaf cannot satisfy it either. **No pixel can distinguish "the layout was saved and restored" from "the layout was never saved but the file came back another way"**, which is the entire reason this assertion exists. **Assertion 2 (exact):** the restored `bufname('%')` tail is exactly `szulu.md`. **Assertion 3 (corroboration):** OCR contains `solozulu` and does **not** contain `soloalfa` — the decoy kills the "it reopened the first file it found" hypothesis, which would give `salfa.md` on both counts. **Assertion 4 is the state-dir isolation block**, in four parts: the TEST process must have no `WOLF_STATE_DIR` of its own (otherwise the whole check is self-referential and passes no matter what the app did); the smoke's own state dir holds a non-empty `state.json`, proving the app honoured the variable; **neither `$HOME`-derived fallback directory** (`$HOME/.local/state/wolf`, `$HOME/.local/share/wolf`, under the temp `HOME` `cage_command` supplies) holds a `state.json`, which is a POSITIVE proof that `state_dir()` resolved the variable rather than `$HOME`; and the developer's REAL `state.json` is byte-identical across the run, including the normal case where it does not exist at all and must still not exist afterwards. The last two are complementary rather than redundant: a leak lands inside the temp tree when `$XDG_STATE_HOME` is unset and outside it when it is set, and one arm catches each. The failure message names the one benign cause — a real Wolf running concurrently in another terminal — before any other conclusion. **Red-run reverts — TWO, both one-liners, and both were run**, because they isolate the two halves of the original bug and must fail DISTINGUISHABLY. _(a) The SAVE-side arity guard_ (`persistable_layout` gated on `leaf_count(..) < 2`): measured as predicted — assertion 1 panicked first and the frozen copy carried the tab with `cwd`, `sidebar_visible` and **no `layout` key at all** (serde skips `None`), which is precisely the on-disk shape of the macOS bug. _(b) The RESTORE-side arity guard_ (`request_layout_rebuild` wrapped in `leaf_count(&layout) > 1`): measured as predicted and distinguishably — assertion 1 **PASSED** (the frozen copy carried the correct single leaf) and the panic moved to assertion 2, `left: "Untitled.md" right: "szulu.md"`. Different assertion, different line, different frozen-file content, and assertion 2's own message ("assertion 1 above already proved it WAS saved correctly … this points squarely at the restore side") named the injected defect correctly.
- **`window_title_shows_the_working_directory_under_cage`** — a single-launch smoke with **no keyboard interaction**: settle, `grim`, OCR. It builds two NESTED temp directories so the `~` abbreviation is exercised rather than merely "a title was set" — the cage command runs in `<base>/titlehome-parent/titlezulu` with `HOME` set to `<base>/titlehome-parent` — and drops the nine `SIDEBAR_FILLER_FILES` into the project for page density (fixture, not assertion: the title alone is thin). **Assertion 1:** OCR contains `titlezulu`, which can only come from the header-bar title — the sidebar lists file names, `:e` toasts name files, and no fixture is named that (mechanically enforced). **Assertion 2:** OCR does **not** contain `titlehome`, i.e. the home prefix was abbreviated to `~` rather than rendered. Without the feature the title is the hardcoded `"Wolf"` from `app.rs`'s window builder. **Red-run revert (one line):** delete the `set_title` call in `shell.rs::refresh_title`. Measured as predicted — the OCR dump embedded in the failure message read `®`, `wolf`, `-`, then the nine filler names, with no `titlezulu` anywhere. The pre-authorized contingency (an `XDG_CONFIG_HOME` with a large `gtk-font-name`, should the theme-font title ever prove too small for `tesseract`) was **not** needed: both terms resolve correctly at `SMOKE_FONT_PT`. **No assertion may be weakened to avoid using it** — in particular assertion 2 must not be dropped.
- **`sidebar_filler_names_cannot_satisfy_any_smoke_assertion`** — the first of four tests in this file that are **not** cage smokes. It is pure: no compositor, no `require_smoke_env`, no `CAGE_LOCK`, no subprocess, microseconds to run, so it still guards the fixture on a machine without the smoke toolchain. It reads two const tables and asserts that no `SIDEBAR_FILLER_FILES` name contains any term in `ASSERTED_OCR_TERMS` — the table of every substring the smokes assert OCR must or must not contain, built from the OCR consts themselves rather than re-typed literals so it cannot drift. Nineteen of the twenty-three smokes appear there. FOUR contribute no term at all, on purpose: `colon_qa_closes_the_window_under_cage`, which captures no image, and the click, drag and scroll pointer smokes, whose assertions are on files the captive Neovim writes about its own state rather than on pixels — so no fixture filename can help or hurt them. (The fourth pointer smoke, the wedge regression, does OCR and does contribute.) The terms are `hello`, `pickertarget`, `picktwo` / `pickone`, `treenode`, `paneleft` / `paneright`, `htopfile` / `hbotfile`, `focusone` / `focustwo` / `zzleft`, `closekeep` / `closegone`, `triaone` / `tribtwo` / `tricthree`, `folder`, `zzfresh`, `newbufbase`, `quitkeep`, `quitgone`, `chordkeep`, `chordgone`, `wedgestay` and `wedgeclick` (added with the pointer-harness unit); then — added with the crash-recovery unit — **four more**: `bounceback` (the crash fixture's heading, which lives only in its CONTENT — the file is named `bfile.md`), `restarted` (the "Neovim was restarted" banner), `crashed` (the crash overlay's message) and `unsavedburst` (the marker that exists only in the dead Neovim's swap file) — and, with the state-persistence unit, **seven more**: `restorealfa` / `restorebravo` / `restorecharlie` (the three relaunch headings, whose files are named `rleft.md` / `rmid.md` / `rright.md`), `solozulu` (present) and `soloalfa` (**absent** — the never-opened decoy), and `titlezulu` (present) and `titlehome` (**absent** — the home segment that must be abbreviated to `~`). Four of those fifteen are asserted in BOTH directions, which is why their listing matters as much as the others': `bounceback` must be PRESENT after a recovery and ABSENT during the crash overlay's dwell (that absence is what proves the overlay is opaque), and `unsavedburst` must be present after the recovery and absent from the pre-crash control. A filler row carrying either would satisfy one half and fail the other — a real proof turned into a spurious red, the same fixture bug from the other side. `crashed` and `restarted` are additionally kept apart from each other by an executable check in `liveness_ui.rs`'s own unit tests, not by this table: neither crash message nor the button label may contain `restarted`, and the banner may not contain `crashed`, or the two crash smokes could cross-satisfy each other. The must-NOT-contain terms are listed deliberately: a filler row carrying one would make its smoke fail SPURIOUSLY rather than pass vacuously — the opposite symptom, but the same fixture bug. Were a filler ever named `fillhello.md`, the sidebar would render `hello` on a row of its own, `window_renders_typed_text_under_cage`'s assertion would be satisfied by that row, and the smoke would pass green forever with an editor pane that drew nothing — the silent false positive `CLAUDE.md` warns about, and one that is invisible in review because the fixture and the assertion it can defeat sit a thousand lines apart. It also pins that every asserted term is lowercase (OCR output is lowercased before every `contains`, so an uppercase const could never match, which would make the filename check vacuous too) and that the filler names are distinct (duplicates collapse on disk and would silently thin the page density). A fixture that can disarm the assertion it exists to support needs an executable guard, not prose.

- **`temp_cwd_name_cannot_satisfy_any_smoke_assertion`** — the same invariant aimed at a SECOND fixture: the two fixed components of every `make_temp_cwd` path. It exists because the temp directory's NAME became page text the moment the header bar started rendering the working directory — in the theme font, dark-on-light, i.e. the most legible text on the page. A basename of `folder` would satisfy `empty_state_shows_open_folder_button_under_cage` from the header bar alone, with no status page drawn at all. It checks `TEMP_CWD_BASENAME` (the part that IS drawn, as `~/project`) and `TEMP_CWD_PREFIX` (normally abbreviated away, checked anyway: if the abbreviation ever regresses the FULL path is drawn, and a prefix carrying an asserted term would turn that clean red into a mysterious pass — or a mysterious spurious failure — in a different smoke entirely). It additionally asserts the basename is exactly ONE ordinary path segment, because the whole determinism fix rests on that (an empty value or `.` would collapse cwd and `HOME` into one directory, which also flips every smoke into `launch_decision`'s `EmptyState` branch; a separator or a `..` moves the level `HOME` is taken from); and it proves the variable `{pid}-{nanos}` tail is harmless by asserting every OCR term contains an ASCII letter, rather than claiming so in a comment. It is a separate test from the filler guard so the two failures stay separately diagnosable — one says "rename a filler file", the other "rename the temp-directory basename or prefix". It does **not** check `std::env::temp_dir()` itself, which is a property of the host rather than of this fixture.
- **`restore_fixture_names_cannot_satisfy_their_own_assertions`** — the same invariant aimed at a THIRD fixture: `RELAUNCH_FIXTURE_NAMES`, the files the three state-persistence smokes create in their own working directories (including their readback files, which land in the same cwd and are drawn by the sidebar too). The filler guard inspects `SIDEBAR_FILLER_FILES` and nothing else, and its own doc comment records the gap it cannot cover — a smoke whose fixture file is named after the word that smoke asserts, which is exactly how `picker_opens_and_loads_selected_file_under_cage` once passed green while the picker provably never opened. The three new smokes assert on file CONTENT while dropping fixtures into a cwd the sidebar lists BY NAME, so they are precisely in that hazard class. It also enforces distinctness (from each other and from the filler names — they share one temp cwd, so a collision silently overwrites a fixture with another's contents), and it makes the title smoke's deliberate EXEMPTION executable rather than prose: `TITLE_PROJECT_DIR` must contain `TITLE_OCR_PRESENT` (the header bar rendering it is the whole point) and `TITLE_HOME_DIR` must contain `TITLE_OCR_ABSENT` (without which the must-NOT-contain assertion holds trivially and proves nothing), **plus the crossed pair** — the project name must not carry the absent term and the home name must not carry the present one, where a mistake really would be fatal.
- **`cage_is_only_spawned_through_the_isolating_helper`** — the mechanical enforcement of "every smoke's environment comes from `cage_command`". It reads this file's own source with `include_str!` and asserts the compositor-spawn needle appears **exactly once**. What an extra occurrence costs is spelled out in the failure message: that smoke inherits the test process's environment, so its app resolves `state_dir()` to the developer's REAL `~/.local/state/wolf/`, reads their real `state.json` at launch and overwrites it at quit; it also inherits the developer's real `HOME`, so the header bar draws the full run-varying temp path and the page stops being reproducible; and it loses `XDG_CACHE_HOME`, costing ~4.9 MB of shader rebuild inside the fixed `SETTLE` budget. The last two surface as an OCR flake in some **other** smoke, which is worse than the first in one respect: it looks like a flake in whatever change happens to be in flight rather than like a missing `.env` line. **Two details are load-bearing and must not be "simplified".** The needle is built from fragments (`concat!("Command::new(\"", "cage", "\")")`) so that this file never contains it contiguously outside `cage_command` — spelled as one literal, the const's own line would match itself, the count would be two, and the guard would be red forever no matter how correct the code was. And the count is asserted from BOTH sides: at least one, so a needle that matches nothing (someone renames the binary, or rustfmt splits the call across lines) cannot satisfy it vacuously, and at most one, so the invariant holds. Relaxing the count to `<= 1` is the tempting fix for a permanently-red guard and is exactly the vacuity shape recorded below.

Required toolchain + env for the **twenty-three cage smokes** (all from the flake devShell smoke toolchain, and now **gate-required** rather than optional): `cage`, `wtype`, `grim`, `tesseract` and `wolf-pointer-inject` on `PATH`; `WOLF_NVIM_BIN` set; and a set, writable `XDG_RUNTIME_DIR`. `wolf-pointer-inject` is the odd one out and deliberately so: it is not an upstream nixpkgs package but **this repo's own tool**, built from [`tools/wolf-pointer-inject/`](../../../tools/wolf-pointer-inject/README.md) by `flake.nix`, so `command -v wolf-pointer-inject` succeeding can only mean the flake provided it. Only five smokes use it, but `REQUIRED_TOOLS` demands it unconditionally: a devShell missing it is an unprovisioned devShell. Neither the crash smokes nor the state-persistence smokes add a tool of their own — the `/proc` scan that finds the Neovim child is built from `sed`, deliberately, so that `procps` never has to enter `flake.nix` and drag a Darwin-eval obligation along with it, and the relaunch smokes reuse `cage` / `wtype` / `grim` / `tesseract` unchanged. Per project policy `require_smoke_env` **fails loud** (not a silent skip) on any missing precondition, since absence means the smoke toolchain was not provisioned. A stale screenshot is removed first so a previous run cannot make the test pass. The four pure guards need none of this.

**NOTE:** the smoke test asserts only the typed `hello`, not the cursor; cursor geometry and color are covered by the pure `cursor.rs` unit tests above plus visual confirmation (OCR is too fragile to couple to the cursor).

### Fixture naming: a smoke's own files can disarm its assertion

**The rule, and it is a convention rather than a changelog entry: when a smoke asserts on a file's CONTENT, that file's NAME must not contain the asserted word.**

The file-tree sidebar renders every file in the cwd by name, and nvim's `:e` toast echoes the filename too. So a fixture whose name contains the smoke's own OCR term satisfies the assertion whether or not the feature under test did anything — a permanent silent false positive, not a flake.

Two pre-existing smokes were passing exactly that way and are now fixed:

- **`picker_opens_and_loads_selected_file_under_cage`** shipped a `pickertarget.md` fixture against the asserted `pickertarget`. That is not a theory: during the command-drain unit's broken-accelerator run — GTK's keymap-aware accel matching never fired under `wtype`, so Ctrl+Shift+O was forwarded to Neovim instead of opening the picker — this smoke **passed green while the picker demonstrably never opened**. Fixed by renaming the fixture to `ptarget.md` (and the query to `ptarget`); the heading `# PICKERTARGET` and the asserted term are unchanged, so the word now lives ONLY in the buffer and only a rendered buffer can satisfy the assertion.
- **`vertical_split_shows_two_panes_under_cage`** shipped `paneleft.md` / `paneright.md` against `paneleft` / `paneright`, so BOTH assertions were satisfiable by sidebar rows alone: the smoke would have passed green if `<C-w>v` had never split anything. Fixed by the same rename shape (`pleft.md` / `pright.md`), terms unchanged.

Both changes **strengthen** the tests; nothing was weakened, no assertion or OCR const moved. `picker_arrow_navigation_selects_second_match_under_cage` was checked and does not share the defect (`pick1.md` / `pick2.md` against `picktwo` / `pickone` — it failed correctly during the broken run), and every other smoke was audited and is clean.

The **one deliberate exception** is `tree_sidebar_shows_files_under_cage`, where `treenode.md` carries the asserted `treenode` on purpose: there the sidebar row IS the feature under test. That exception is also why `sidebar_filler_names_cannot_satisfy_any_smoke_assertion` cannot simply be widened to cover fixture names — generalizing it would need an explicit opt-out list. The guard therefore covers the FILLER filenames only, and this rule covers the rest by convention; the gap is recorded in the guard's own doc comment.

### Vacuity is not only a fixture-naming problem: the drag smoke's false premise

The cases above are all "the fixture can satisfy the assertion". This one is different and joins the same running record: **the assertion was fine, and the premise underneath it was false.**

The first version of `drag_selects_a_range_under_cage` was **vacuous with respect to `drag-update`**. With `pane_view.rs::on_pane_drag` neutered to an immediate no-op it passed **3/3**. The premise stated in its own doc comment and in its failure message — "Vim enters visual mode only on a drag, never on a press+release at two different cells" — is **FALSE for nvim 0.12.2**, and was measured directly:

```text
press+release only : visualmode="v" marks="3 4 8 13" cursor="8 13"
press+drag+release : visualmode="v" marks="3 4 8 13" cursor="8 13"
```

Byte-identical. A `<LeftRelease>` at a cell different from the press enters charwise visual mode by itself, so `on_pane_release` alone reproduces the exact Neovim state the original drag asserted, and neutering `on_pane_drag` could not make it red.

The damage was partial rather than total: the out-of-widget clamp (Drag B) was still meaningful, because `on_pane_release` also runs `drag_point` -> `start_point() + offset` -> `cell_at`. What was unproven was specifically **that `drag-update` is ever emitted at all**.

The fix **added** an assertion rather than weakening one: the round-trip **Drag Z**, whose press and release are at the SAME cell. With `drag-update` the outbound sweep starts visual mode anchored at the probe, the return sweep walks the cursor back, and the selection collapses to one cell — `visualmode() == "v"` with `'<` == `'>`. Without it, nvim sees `<LeftMouse>` then `<LeftRelease>` at one cell, no movement, no selection: `visualmode()` is `""` and the marks are `0 0 0 0`. That is a clean, exact discriminator built from the readback idiom the smoke already used. Verified red 2/2 with `on_pane_drag` neutered, then green 9/9 with zero flakes across five isolated runs, one post-restore run and three full-suite runs.

The general lesson, and the reason this is recorded next to the fixture-naming rule rather than in a changelog: **a red-run demonstration is a deliverable, not a formality.** Both defects were invisible in review and both were caught only by deliberately breaking the code under test and checking that the test noticed. The `:qa` smoke carries the same shape of hazard from a third direction — a process that vanishes because the GTK main loop panicked looks exactly like one that shut down cleanly, which is why that smoke asserts a ZERO exit status and gives "exited, but non-zero" its own distinct exit code rather than folding it into "still alive".

**Two more joined the record with the crash-recovery unit, and both are the "the premise was false" shape rather than the fixture shape.** They were found the same way, by running every revert instead of sampling.

- **The automatic-restart cap was completely untested.** `assert_no_nvim_respawn` counted the app's children named `nvim`, and the fixture that induces a failing respawn is a `/bin/sh` wrapper that exits **before** its `exec` — so it is never named `nvim`, an unbounded retry loop was structurally invisible to the check, and the scenario's exit code for "a respawn happened that should not have" was unreachable. Setting `MAX_AUTO_RESTART_ATTEMPTS = u32::MAX` left the smoke **fully green**. The fix was to make the wrapper log each refusal and assert on **exactly one** line after the quiet window; the same revert then reported **75 attempts in 4 seconds** against the capped build's 1 — which is also, in its own right, the evidence for why the cap exists.
- **The restart button's geometry was untested.** The click was derived at the button rect's **centre**, and `set_size_request` is only a MINIMUM on a `halign(Center)` widget — so a button that requested a wrong width still rendered centred on the same point. Shrinking `RESTART_BUTTON_WIDTH` from 320 to 40 in the builder left the smoke **fully green**. Pixel-scanned: the correct builder renders `x 605..924` and the 40 px builder `x 669..861` (the label's natural width), **both centred on `x 765`**, and even the three-quarter point at `x 845` is still inside the narrow one. The fix was to derive the click a tenth in from the rect's LEFT edge rather than at its centre. The honest limit of that fix is written down rather than glossed: it discriminates only widths below ~248 px, and the button's height not at all.

Both are the same lesson as the drag smoke's, from a new direction: a check can be aimed at the right property and still be looking somewhere the defect cannot appear.

**A third shape joined the record with the state-persistence unit, and it is neither of the above: a PRODUCT change made an existing, correct smoke stochastic.** The new window title renders the app's working directory, and `make_temp_cwd` built that name from `temp_dir()` + the pid + a 19-digit nanosecond timestamp — so the captured page became **different on every run**, and `window_renders_typed_text_under_cage` went stochastic at roughly 2% (2 failures in ~93 runs) with the documented ligature signature. Measured, five consecutive captures per arm:

```text
arm                                        | five capture md5s          | size
-------------------------------------------|----------------------------|------------------------
title drawing the run-varying temp path     | all five DIFFERENT         | 34.2-35.0 KB, varying
`set_title` suppressed (the base page)      | 5ea4d070... x5, identical  | 26074 x5
```

This also falsifies a claim the plan for that unit carried: that more page text "can only help" tesseract's page-density calibration. It is wrong in sign — more text helps only when it is the SAME text every run. **The fix was to make the rendered title CONSTANT rather than to widen a margin**: `make_temp_cwd` returns `<unique>/project` and `cage_command` sets `HOME` to `<unique>`, so `title::display_title` abbreviates the varying prefix away and every smoke's header bar renders exactly `~/project`. `SIDEBAR_FILLER_COUNT` was deliberately **not** raised — raising it could not have fixed this, because the defect was page VARIABILITY and not page sparsity. The lesson, and the reason it sits beside the other two: a green suite is not evidence that a feature is test-neutral, because a feature can change the fixture every OCR assertion is implicitly calibrated against.

### Pointer injection: how it works and why it is built this way

This section is a **record of what was built and measured**, not a lament. Until this branch, pointer input had no end-to-end coverage at all and this file said so at length. It now has four cage smokes, and what follows is why they take the shape they do and what the harness actually measured.

**The wlroots fact that dictates everything.** Under `cage` with `WLR_BACKENDS=headless` there are no real input devices, and wlroots advertises `WL_SEAT_CAPABILITY_POINTER` on the seat **only while some pointer device exists** (cage's own `seat.c` `update_capabilities`). So a tool that creates a virtual pointer, injects, and exits flips the capability on and back off again before any client can bind `wl_pointer`. The injector must be **long-lived** — one `zwlr_virtual_pointer_v1` held open for the whole scenario — and that single requirement is what rules out every off-the-shelf option below.

**`wlrctl` was tried and is PROVEN not to work.** This is a measurement, reproduced identically across three runs, not a prediction. Every `wlrctl` invocation is a separate short-lived process; the GTK client's own `WAYLAND_DEBUG=1` log shows `wl_seat.capabilities(3)` -> `get_pointer` -> `capabilities(2)` -> `wl_pointer.release()` **59 microseconds apart, inside one dispatch batch**, so the client never holds a live `wl_pointer` when the button events fire and wlroots drops them: **zero `wl_pointer.button` events reached the client in a whole plain-`wlrctl` run.** All three calls still exited `0` — an exit code from `wlrctl` says nothing whatsoever about delivery, which is the same vacuous-success shape the [fixture-naming](#fixture-naming-a-smokes-own-files-can-disarm-its-assertion) rule guards against in another form. `wlrctl` 0.2.2 also has no press/release split (its `click` is atomic, in one process), so even if it delivered it could not drive a drag. **It must stay out of `flake.nix`:** shipping it in the toolchain would advertise a capability that does not exist.

**`ydotool` cannot reach cage at all.** It writes to a uinput kernel device, and `WLR_BACKENDS=headless` (with `WLR_LIBINPUT_NO_DEVICES=1`) means cage consumes **no** kernel input devices, so nothing `ydotool` writes is ever read. `/dev/uinput` being ACL-writable is not the blocker; the headless backend is.

**sway was investigated and REJECTED.** It cannot do this either. It is a wlroots compositor, so the seat-capability fact above applies unchanged; its `swaymsg … cursor` commands **report success while delivering nothing**, the same exit-code-says-nothing shape as `wlrctl`; and it has **no axis verb at all**, so the wheel smoke could not be expressed under it even in principle. Two claims that circulated from that investigation are **sway findings and do not apply under cage**, and are withdrawn here so nobody re-derives them: the "+20,+20 client-side-decoration offset" (under cage the measurement is **zero offset** — see below) and "`wtype` loses keystrokes" (not observed under cage, where every smoke drives the app with `wtype`). sway is out of scope; do not add it.

**What was built instead: [`wolf-pointer-inject`](../../../tools/wolf-pointer-inject/README.md).** A small committed C program in `tools/wolf-pointer-inject/`, built by `flake.nix` with `stdenv.mkDerivation` + `wayland-scanner` over the `wlr-protocols` XML and put on the devShell `PATH`. It creates exactly one `zwlr_virtual_pointer_v1` at startup and holds it for the whole scenario (which is what keeps the seat's pointer capability on), then reads `motion` / `press` / `release` / `axis` / `sync` / `quit` commands from stdin one per line and acks each one after a `wl_display_roundtrip`. Every event group ends with a `wl_pointer.frame`, which is mandatory rather than decorative: GTK's Wayland backend buffers pointer events and only turns them into `GdkEvent`s on `frame`, so without it the compositor delivers bytes and GTK delivers nothing. Its README is the authoritative record of the grammar, the ack protocol, the coordinate model and the exit codes; do not restate them here.

#### `POINTER_STEP`: a pacing knob, and why it is load-bearing

`POINTER_PREAMBLE` defines `POINTER_STEP=0.2` and an `hstep` helper (`hsend` followed by that sleep), and every in-gesture pointer command of the drag body uses `hstep` rather than `hsend`. The reason is **Neovim's API**, not GTK and not this repo: `nvim_input_mouse(button, action, modifier, grid, row, col)` transports only the BUTTON CODE through the typeahead, while the position rides on the globals `mouse_grid` / `mouse_row` / `mouse_col`, which the API handler overwrites the moment the call is serviced. Measured against nvim 0.12.2, three RPCs landing 0.4 ms apart all resolved at the LAST position. Before pacing, the drag smoke was 6/8 and 7/8 in isolation and failed 2 of 3 full-suite runs; after pacing it was 15/15 in isolation plus clean full-suite runs. Pacing also stops GDK's motion compression from folding the intermediate waypoints into a single `drag-update`. **No assertion was touched to achieve that. If the drag smoke ever flakes again, raise `POINTER_STEP` — never touch an assertion.**

#### The focus-wedge fix is now executed, and what Run B does and does not show

`click_then_close_keeps_keyboard_input_alive_under_cage` is the first execution of `df3bb3d`. **The fix works.** The three-part revert was run and the full 2x2 matrix isolated:

```text
configuration                          | result
---------------------------------------|---------------------------------------------
revert (1) `.focusable(true)` only      | green
revert (2) `area.grab_focus()` only     | green
revert (1)+(2), guard intact  (Run B)   | ALIVE1 ok, ALIVE2 ok, OCR FAILS -- pane blank
```

**Run A** (all three parts reverted — `.focusable(true)` restored on the pane `DrawingArea`, `on_pane_clicked` grabbing focus onto the clicked pane's own area, and `rebuild_pane_area`'s `focus_inside_pane_area()` return-focus guard neutered) is the headline red evidence: `$ALIVE1` is written and `$ALIVE2` is absent. Keys reached Neovim before the pane close and stopped after — the wedge, exactly as described.

**Run B** (reverting only the two structural parts, leaving the `rebuild_pane_area` guard intact) has **both `ALIVE` assertions passing**. That is the finding: the guard is **load-bearing**, and keyboard input survives on it alone. This converts `rebuild_pane_area`'s return-focus guard from "cheap insurance against a reachable-tomorrow defect" into a measured fact — it had never been executed by anything before.

**Run B is NOT green overall, and must not be recorded as such.** The run fails, because that deliberately-broken configuration renders the surviving pane **blank** (screenshot inspected: sidebar and header draw, editor pane empty), so the OCR corroboration fails. That is a **second, separate defect of a broken build**, not the wedge. It was reproduced twice. The guard's load-bearingness is evidenced by the two `ALIVE` assertions passing, **not** by a green overall run.

One limitation of the evidence, stated plainly: the wedge's red demonstration was performed against the first pass of this file and was **not** re-run after the drag smoke's Drag Z was added. Its assertion predicate is provably unchanged (same `alive2_present` predicate, same message opening, shifted down by Drag Z's insertion) and only the message tail changed, so the evidence is "provably still applicable" rather than freshly re-run. Every other pointer smoke's red evidence is fresh.

#### What is still unproven

Being scrupulous about this is the point of the section. **PROVEN by the four smokes:**

- **`gtk::GestureDrag` fires from a real `wl_pointer` event**, and `on_pane_press` -> `send_pane_mouse` -> `cell_at` maps a real widget-local coordinate to the predicted cell (click smoke, exact delta).
- **`drag-update` is emitted during a button-held move** (drag smoke, Drag Z — the round trip; an empty `visualmode()` with marks `0 0 0 0` is the clean negative).
- **`offset_x` / `offset_y` reconstruct the absolute point via `start_point() + offset`, and the gesture keeps delivering after the pointer leaves the pane**, with `cell_at` clamping the out-of-widget point rather than the event being dropped (drag smoke, Drag B: release over the sidebar, column clamps to 1).
- **`gtk::EventControllerScroll` fires from a real `wl_pointer.axis` frame**, and the unit and magnitude it reports are now measured and pinned (scroll smoke).
- **The click-then-close focus wedge is gone** — as a **composite** with the `rebuild_pane_area` guard, not as the `focusable(false)` half in isolation. See the honest scope note on that smoke's bullet.
- **`rebuild_pane_area`'s return-focus-to-the-strip guard is now executed** on every pane close in the wedge smoke, and Run B shows it is load-bearing.

**STILL UNPROVEN, and the reasons matter:**

- **The strict press -> `focus_win` -> `send_mouse(Press)` ORDERING.** That `focus_win` fires on a click IS proven — the wedge smoke's `<C-w>c` closes the pane that was CLICKED, which the OCR pair corroborates. The strict ordering remains **unobservable**, because Neovim's own `<LeftMouse>` also moves the current window, so no readback can distinguish "focus arrived first" from "the press moved it". It stays guaranteed **by construction**: both ride the same ordered input channel. Do not tick this.
- **`record_pointer`.** The scroll smoke cannot discriminate it: `on_pane_scroll` names the target grid explicitly, so a stuck `(0.0, 0.0)` recorded pointer would still scroll the right window and the smoke would still pass. Nothing here tests that the motion controller's recorded position is ever used correctly.
- **`drag_grid` / `drag_button` press-pinning.** No smoke drags from one pane into another: the three that drag run with a single pane (Drag B leaves the pane only for the sidebar, which is not another grid), and the one smoke that has a split only clicks. So the pin is never discriminating — there is no other grid for a wandering drag to be retargeted to. The test that WOULD prove it: split vertically, press in the LEFT pane, drag into the RIGHT pane, release, and assert the selection stayed in the left pane's buffer. That is a future unit, not this one.
- **`gtk::EventControllerMotion`** more generally: its `connect_motion` / `connect_enter` handlers exist only to feed `record_pointer`, so the item above covers them. No smoke asserts on anything the motion controller produces.

**STILL UNPROVEN in crash/stall recovery**, added by that unit and stated with the same discipline:

- **The `NotResponding` overlay's PRESENTATION.** Nothing in `wolf-gnome` issues a synchronous RPC, so `wolf-core` can never mark a stall while the GTK app is the only client — `SIGSTOP`ing the captive Neovim under the running app produces nothing. The three-state mapping and the message selection ARE table-tested headlessly in `liveness_ui.rs`, and `crates/wolf-core/tests/nvim_liveness.rs::stall_marks_not_responding` covers the core side against a genuinely wedged Neovim; what has no coverage is the widget path for that one mode. **No smoke was written and none should be faked**: manufacturing a stall would have meant adding a blocking call to the front-end purely to satisfy a test, which would also put a five-second main-loop stall on every redraw against a wedged nvim. This is a limitation of the front-end's call pattern, not of the core, and it lifts the moment the buffer picker, Copy or the Markdown preview land on GTK.
- **The `crashed`-present assertion has no revert that exercises it in isolation.** Measured in pass 5: B1 (never `set_visible(true)`) exits `19` at the recovery poll before the dwell OCR is ever read, because the button lives inside the overlay so a never-shown overlay is also a never-shown button; and B2 fails the same assertion, but for the OPACITY defect. It is a real assertion with no isolated red run of its own, and it is recorded that way rather than presented as discriminating one of the five reverts.
- **`bounceback` does NOT discriminate the reopen order.** The plan predicted a clean OCR split (`bounceback` absent, `restarted` present); the measured revert exits `19` at the scenario's own recovery poll instead, which is order-sensitive because it waits for `bufname('%')` to name the fixture. **The poll is the discriminator; the OCR term is corroboration**, and no measured run has ever got far enough to look at it.
- **The button-width check discriminates only widths below ~248 px.** The button is `halign(Center)`, so it spans `765 ± W/2` with `W = max(requested, natural ≈ 193)`, and the left-edge-inset click at `x 641` misses only when `W < 248`. It catches the documented 40 px revert with 55 px to spare, but it would **not** catch a shrink from 320 to 260 — widths in `(248, 320)` are undiscriminated, and the button's **HEIGHT** is undiscriminated entirely.
- **The unsaved-edit assertion has no isolated revert of its own.** Reverting the restart makes it red along with everything else via exit `19`; reverting the reopen order makes it absent alongside `bounceback`. What it independently discriminates is a different axis: that the reopened buffer is the SWAP-RECOVERED one rather than a clean re-read from disk. A future change that reopened into a fresh per-process swap dir, or answered `SwapExists` with `e` instead of `r`, would leave every other assertion in that smoke green.

**STILL UNPROVEN in application-state persistence**, added by that unit and stated with the same discipline:

- **Restoring the window SIZE is unprovable under cage.** `cage` forces the toplevel to the output size, so a restored `default_width` / `default_height` never takes visible effect and no screenshot can show one. The seam is table-tested headlessly (`state_seam::restored_window_size_table`, including every unset-sentinel row) and `app::build_ui` demonstrably reads it into the window builder, but the APPLICATION of it — that a relaunched window really comes back the size it was — has no end-to-end coverage on Linux. **No smoke was faked for it.** Window POSITION is a different matter and is not a gap at all: it is deliberately never persisted (Wayland gives a client neither its own position nor screen geometry), and `snapshot_state_is_one_window_one_tab` pins the `0.0` so that stays deliberate.
- **NON-EQUAL pane weights are never produced today, so nothing observes them being applied.** Divider drag-to-resize is unimplemented on Linux, so every weight the save path writes is an equal share, and **no smoke can distinguish "the saved weights were applied to the dividers" from "the equal-share default was recomputed"** — the two agree numerically. The restore path DOES apply saved weights, and the round trip is pinned headlessly by `pane_layout::decode_round_trips_encode` over a deliberately non-equal `[0.25, 0.75]`; only the PIXELS are unproven. Do not read `pane_layout_survives_relaunch_under_cage` as covering weights: it covers topology, identity and order. When divider drag lands, the persistence format, encoder, decoder and tests all stay as they are — only the source of the weights changes.
- **`sidebar_visible` is written and never read back**, so no test can observe it being applied, because nothing applies it. That is a deliberate product decision (`win.toggle-sidebar` is `Reserved`, so a user cannot produce `false`, and honouring a hand-edited `false` would hide the sidebar irrecoverably), and the unit test asserts only that the snapshot side keeps writing the field so it cannot silently rot out of the file.
- **`may_snapshot`'s data-loss guard is table-tested but never induced end to end.** No smoke arranges a wake in which nvim is dead, or no pane is bound, or `win_buffers` is still empty, and then checks that the previously-saved layout survived. The whole domain IS covered headlessly (`may_snapshot_table` plus `only_alive_with_a_bound_pane_may_snapshot`), and inducing the race under cage would be timing-dependent rather than deterministic, so it is recorded here rather than approximated.
- **The stall overlay's PRESENTATION remains unproven, but its unreachability claim has narrowed.** `rebuild_layout` is now the ONE `block_on_rpc` this front-end issues, so a wedged nvim **at launch** can genuinely mark the core `NotResponding` — which no version of `wolf-gnome` before this unit could do. No smoke induces it, and the "there is no stall smoke because a stall is not expressible" note below is therefore now half true: it is still not expressible for a RUNNING app (`SIGSTOP`ing the captive nvim under one produces nothing), and it is expressible only inside the launch window.

### Deliberate test gaps

Things the GTK front-end's behaviour deliberately does **not** smoke, with what covers them instead:

- **The primary menu popover is not smoked.** `wtype` cannot click the header-bar `MenuButton`, and keyboard-navigating to it is too fragile to be worth the flake. It is covered by the pure `actions.rs` menu tests (every item references a declared, implemented, non-Reserved action; every label matches the registry title) plus the fact that three of its seven items' actions are proven end-to-end by the accelerator and `:qa` smokes.
- **The `gtk::FileDialog`s (Open Folder… / Open File…) are not smoked.** There is no portal backend under `cage`, so the dialog cannot be driven at all. Their callback bodies are trivial; the empty state's _presentation_ is smoked.
- **The sidebar re-root after Open Folder is not smoked** (same reason). `workspace::reroot_ready` is unit-tested, and `TreeHandle::reroot` reuses the already-smoked `FileSearch` refresh path.
- **There is no stall / `SIGSTOP` smoke, and no `NotResponding` smoke of any kind.** Not a scheduling decision. It used to be **not expressible** at all, because nothing in `wolf-gnome` issued the synchronous RPC that is the only thing which can mark a stall; since the state-persistence unit there is exactly one — `WolfCore::rebuild_layout`, at most once per launch — so the honest statement is now narrower: a stall is unreachable for a RUNNING app (`SIGSTOP`ing the captive nvim under one still produces nothing) and reachable only inside the launch window, which no smoke induces. `crates/wolf-core/tests/nvim_liveness.rs` covers `stall_marks_not_responding` and `stall_then_recovery_clears_not_responding` headlessly against a real wedged Neovim, and the GTK-side classification is table-tested in `liveness_ui.rs`. See "What is still unproven" above.
- **There is no _separate_ GTK smoke for unsaved-edit recovery**, but there is an assertion. `crates/wolf-core/tests/swap_recovery.rs::restart_recovers_unsaved_untitled_buffer` already covers the mechanism headlessly and deterministically, including the reopen order and the silent `SwapExists` recovery. Rather than duplicate it with a flakier cage version, `nvim_crash_recovers_and_reopens_the_file_under_cage` — which already makes an unsaved edit and SIGKILLs Neovim — asserts the marker on a PIXEL after the recovery and its absence in the pre-crash control. That adds the one thing a headless core test structurally cannot have: the GTK front-end in the loop, driving the reopen itself. It races nothing, because the scenario `:preserve`s the edit and then polls a readback written by a LATER command on the same ordered input stream — an ordering argument, not a timing guess, which matters because `'updatecount'` defaults to 200 typed characters and the edit is 13.

## The `key_from_char` helper

`gdk_key.rs`, `roundtrip_nvim.rs` and `src/actions.rs`'s `mod tests` each define a small `key_from_char(c: char) -> gdk::Key` helper, because gdk4-rs has no `Key::from_unicode`. It builds the keyval exactly as GDK would from a Unicode scalar:

```rust
use gdk::glib::translate::from_glib;
fn key_from_char(c: char) -> gdk::Key { unsafe { from_glib(gdk::unicode_to_keyval(c as u32)) } }
```

This is test-side only and does not change `gdk_key`'s contract: printables still carry the exact glyph, and `gdk_key` reads `keyval.to_unicode()` and sets `shift: false` for `Key::Char`.
