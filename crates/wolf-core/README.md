# wolf-core

The platform-agnostic Rust core of Wolf, a Markdown editor that embeds Neovim as its editing engine. Core contains everything Neovim-related and draws no pixels: it spawns a hermetic, pinned `nvim --embed`, attaches as an `ext_linegrid` + `ext_multigrid` UI, folds the entire `redraw` event stream into a multigrid render-state snapshot, surfaces a Neovim→shell layout-intent channel (for native split panes), accepts abstract input events, and signals the front-end (via a single wake callback) when a new frame is ready.

See the workspace docs for context: [`architecture.md`](../../architecture.md) (esp. §8 and the core↔front-end contract) and [`build.md`](../../build.md).

## The one hard rule

> **`wolf-core` must compile with no GUI toolkit in its dependency tree.**

Enforced by a `cargo tree` denylist check:

```sh
cargo tree -e no-dev -p wolf-core
```

No occurrence of any of these is permitted:

```
gtk gtk4 glib gdk4 cairo cairo-rs pango libadwaita
objc objc2 cocoa core-graphics winit wgpu skia-safe softbuffer
```

The file picker adds two dependencies — `rusqlite` (with the `bundled` feature, which vendors SQLite via `cc`) for the MRU cache and `ignore` (ripgrep's pure-Rust walker) for the traversal. Both are deliberately GUI-free: they pull **no** GUI toolkit into core's tree, so the denylist above is unchanged (the command and the denied-crate list stay exactly as written) and stays clean. The flake also needs no change (no system SQLite/libgit2 to provision).

The `config` module adds three more dependencies — `serde` (with `derive`) and `serde_yaml` (0.9) for the `wolf-config.yaml` (de)serialization and `dirs` (5) for resolving the platform preferences directory. All three are deliberately GUI-free: they pull **no** GUI toolkit into core's tree, so the denylist above is unchanged (the command and the denied-crate list stay exactly as written) and stays clean.

The `state` module adds one more dependency — `serde_json` (1) for the pretty-printed `state.json` (de)serialization (it reuses `serde` and `dirs` from the `config` module). It is likewise deliberately GUI-free, so the denylist above is unchanged and stays clean.

The `markdown` module adds `pulldown-cmark` (and its companion `pulldown-cmark-escape`) for the Markdown → HTML preview render, plus `pulldown-latex` (which adds only `bumpalo`) for the LaTeX → MathML math render. All are pure Rust and deliberately GUI-free: they pull **no** GUI toolkit into core's tree, so the denylist above is unchanged (the command and the denied-crate list stay exactly as written) and RE-VERIFIED clean — following the same precedent as `rusqlite`/`ignore`/`serde`. (Re-run the `cargo tree` / `bazel query` check above after any dependency change.)

## Building under Bazel (macOS)

On macOS `wolf-core` builds with Bazel (via bazelisk) rather than Cargo; the target label is `//crates/wolf-core:wolf_core`. Its dependencies come from the same `Cargo.toml`/`Cargo.lock` as the Cargo build, consumed through `rules_rust`'s `crate_universe` (with `rules_rust` downloading a pinned `rustc`). The one hard rule above still holds under Bazel: `wolf-gnome` is given no Bazel target, so no GUI toolkit enters `wolf-core`'s Bazel dependency graph. The Bazel-equivalent denylist check is a `bazel query` over the resolved deps:

```sh
bazel query 'deps(//crates/wolf-core:wolf_core)' | grep -iE \
  'gtk|gdk|glib|cairo|pango|adwaita|objc|cocoa|core-graphics|winit|wgpu|skia|softbuffer' \
  || echo clean
```

See [`build.md`](../../build.md) for the full macOS build and repin workflow.

## Public API surface

Re-exported from the crate root (`wolf_core::…`):

### Lifecycle — `WolfCore` (from [`api`](src/api.rs))

- `WolfCore::start(cfg: CoreConfig, wake: WakeFn) -> Result<WolfCore, CoreError>` — builds a multi-thread tokio runtime, spawns the captive Neovim, wires `wake` into the redraw handler, attaches as an `ext_linegrid` + `ext_multigrid` UI, and (after attach) installs current-file tracking (so `Snapshot.current_file` follows the active buffer), per-window buffer tracking (so `Snapshot.buffers` follows each window's buffer path via `wolf_buffers`, backing the macOS per-pane statusbar), the split-panes layout overrides (so split/focus chords emit `wolf_layout` intents and `wolf_active_win` tracks the active pane), directory tracking (`wolf_cwd`), theme tracking (so `Snapshot.theme` follows the `WolfCursor` / `WolfTitlebar` groups via `wolf_theme`), the command registrations (so `:Wolf<Pascal>` Ex-commands and `require('wolf').<snake>()` Lua calls emit `wolf_command`), the tabpage tracking + lifecycle helpers (`wolf_setup_tabs`, so `Snapshot.current_tabpage` follows the current tabpage via `wolf_tabpage`, the nvim-internal tabpage nav/creation is locked out per OD4, and the `wolf_create_tabpage`/`wolf_close_tabpage`/`wolf_tab_cwd` helpers are defined), the buffer-picker view tracking (`wolf_setup_view_tracking`, which installs the in-nvim per-pane view cache and the `wolf_switch_buffer` helper; it emits nothing back to core), and — last — the Markdown preview tracking (`wolf_setup_preview`, so `Snapshot.previews` follows the preview windows via `wolf_preview` and `Snapshot.markdown_ticks` follows each source's `changedtick` via `wolf_markdown_dirty`, backing the macOS web-view preview panes).
- `read_snapshot(&self) -> SnapshotReadGuard` — owned read guard over the current render-state `Snapshot` (the front-end holds it for a paint, then drops it). `Deref`s to `Snapshot`; its lifetime is independent of `&self`.
- `send_input(&self, event: InputEvent)` — non-blocking; enqueues the event on an ordered FIFO channel applied by a single consumer task. Errors are logged, not returned (FFI-shaped fire-and-forget).
- `resize(&self, cols: u16, rows: u16)` — enqueues an `InputEvent::Resize` (the outer/global grid) on the same ordered channel, so it never races pending keystrokes.
- `resize_grid(&self, grid: u64, cols: u16, rows: u16)` — enqueues an `InputEvent::ResizeGrid` (a single per-window grid), same ordered channel.
- `drain_intents(&self) -> Vec<LayoutIntent>` — consumes the pending `wolf_layout` intents (splits / focus-direction moves) the front-end applies on each wake.
- `drain_commands(&self) -> Vec<Command>` — consumes the pending `wolf_command` commands (user-triggered `:Wolf<Pascal>` Ex-commands / `require('wolf')` Lua calls) the front-end maps to native actions on each wake. Unlike intents there is no emit-on-attach, so this is empty right after start.
- `focus_win(&self, win: i64)` — enqueues an `InputEvent::FocusWin` (click-to-focus or a resolved focus move) on the ordered channel.
- `send_mouse(&self, ev: MouseEvent)` — enqueues an `InputEvent::Mouse` (click / drag / release) on the ordered channel; applied via `nvim_input_mouse` targeting `MouseEvent::grid` with grid-local row/col.
- `send_scroll(&self, ev: ScrollEvent)` — enqueues an `InputEvent::Scroll` (wheel / trackpad) on the ordered channel; applied via `nvim_input_mouse("wheel", …)` targeting `ScrollEvent::grid`.
- `copy_visual_selection(&self) -> Option<String>` — the BLOCKING copy path: `runtime.block_on`s `NvimProcess::yank_visual_selection` (a mode-guarded yank of the current visual selection over RPC), returning the yanked text or `None` when nvim is not in visual mode (or the selection is empty / the RPC fails). The front-end writes the returned string to the system clipboard. It must be blocking because Copy needs a synchronous return value, unlike the fire-and-forget input events.
- `paste(&self, text: String)` — enqueues an `InputEvent::Paste { text }` on the ordered channel; applied via `nvim_paste` (correct in normal/insert/visual/cmdline modes). The front-end reads the string from the system clipboard first.
- `shutdown(self) -> Result<(), CoreError>` — cleanly quits the captive Neovim and tears down the runtime.
- `mru_recent(&self) -> Vec<FileEntry>` — the most-recently-opened files (newest first), pruning any whose backing file no longer exists. Reads the per-cwd store for the captive Neovim's LIVE cwd (the tracked cell, falling back to the configured `cwd`), so the entries' `display` strings relativize against the same directory the picker is rooted at. See `MruStore::recent`.
- `recent_dirs(&self) -> Vec<PathBuf>` — the GLOBAL recent directories (newest first, capped at `RECENT_DIRS_LIMIT = 20`). These are the directories the captive Neovim has changed into (the "open folder" command or a typed `:cd`/`:lcd`/`:tcd`), recorded from the `wolf_cwd` fold point (`apply_cwd`) into the always-on `<state_dir>/folder-mru.sqlite`. Empty when the store is disabled (`state_dir()` unresolved) or unreadable. Reuses the existing `rusqlite` dependency — no new dep. See `RecentDirs::recent`.
- `command_mru(&self) -> CommandMru` — a cheap `Arc`-backed clone of the always-on GLOBAL command-palette MRU (`<state_dir>/command-mru.sqlite`, capped at `COMMAND_MRU_LIMIT = 100`), keyed on an opaque command KEY string. Unlike `recent_dirs`, NOTHING auto-records into it — only an explicit palette `record()` writes to it (it is NOT wired into the redraw handler), so a fresh store reads back EMPTY. The command palette reads/records through it; the pure `rank_palette` (below) ranks candidates against `command_mru.recent()`. See `CommandMru`.
- `pane_status(&self, grid: u64) -> PaneStatus` — the macOS per-pane statusbar strings (base `filename` + `display_path`) for the window drawing into `grid`. It joins `grid` → `WinInfo.win` → `Snapshot.buffers` under a read guard that is DROPPED before it reads `live_cwd()` (mirroring `mru_recent`), then formats the buffer path via the pure `pane_status` over the live cwd and the canonicalized home directory; a window with no matching buffer (unnamed, or a grid with no window) yields `NO_NAME` (`[No Name]`) with an empty display path. See the pure `pane_status` / `PaneStatus` / `NO_NAME` re-exports (from [`pane_status`](src/pane_status.rs)).
- `display_path(&self, abs_path: &str) -> String` — the cwd/home-relative DISPLAY string for a single absolute path (just the `PaneStatus.display_path` half — the filename is derived separately by the caller), formatted via the same pure `pane_status` over `live_cwd()` and the canonicalized home; an empty `abs_path` yields an empty display path. Backs the Markdown-preview pane's SECONDARY statusbar line: `WolfCoreHandle::previews` calls it on each `PreviewInfo.source_path` to fill `FfiPreview::source_display_path()`, so a preview pane shows its source's display path beneath the `Preview: <basename>` line, mirroring an editor pane.
- `start_file_search(&self, wake: WakeFn) -> FileSearch` — starts a streaming file search rooted at the captive Neovim's live working directory (`getcwd()`), falling back to the configured cwd (see "The file-search session" below).
- `list_buffers(&self) -> Vec<BufInfo>` — the BLOCKING buffer-picker snapshot: `runtime.block_on`s `NvimProcess::list_buffers` (a `getbufinfo({'buflisted': 1})` query over RPC), returning the captive nvim's `buflisted` buffers as `BufInfo { bufnr, name, lastused, modified }` (an RPC error logs and yields an empty list). The buffer picker seeds a fresh session from this snapshot + the live cwd and MRU-orders/ranks it via `rank_buffers` (below). Blocking, like `copy_visual_selection`, because the picker needs the candidates synchronously at open.
- `switch_buffer(&self, win: i64, bufnr: i64)` — enqueues an `InputEvent::SwitchBuffer { win, bufnr }` on the ordered channel (so it never races pending keystrokes); applied via the `init.lua` `wolf_switch_buffer` helper — a window-scoped `nvim_win_set_buf` (NOT `:edit`) plus per-pane view restoration. The front-end resolves the active window (over the FFI, `WolfCoreHandle::switch_buffer(bufnr)`).
- `create_tabpage(&self, cwd: Option<&Path>) -> i64` — the BLOCKING tabpage-create: `runtime.block_on`s the `wolf_create_tabpage` helper (`tabnew`, plus `:tcd` when `cwd` is `Some`), returning the new tabpage's stable HANDLE (`0` on error, so the caller can drop the would-be view). Backs the project/tabpage-per-view model (each macOS view = one nvim tabpage of a shared project nvim).
- `cwd_for_tabpage(&self, handle: i64) -> Option<PathBuf>` — the BLOCKING per-tabpage cwd query (`getcwd(-1, n)` via `wolf_tab_cwd`), canonicalized; `None` on error / a closed handle. AUTHORITATIVE for a NON-current view's cwd (the gap `live_cwd()` — current view only — cannot cover). Contrast the cheap `Snapshot.current_tabpage` live gate.
- `current_tabpage(&self) -> i64` — the BLOCKING `nvim_get_current_tabpage` (`0` on error) — the authoritative first-view bind read at bind time (vs the cheap `Snapshot.current_tabpage` gate).
- `set_current_tabpage(&self, handle: i64)` — enqueues an `InputEvent::SetTabpage { handle }` on the ordered channel; applied via `nvim_set_current_tabpage`. The front-end drives every tabpage switch when a view becomes key.
- `close_tabpage(&self, handle: i64)` — enqueues an `InputEvent::CloseTabpage { handle }` on the ordered channel; applied via the `wolf_close_tabpage` helper (`<n>tabclose` under `pcall`). Used for a non-last view close; the front-end shuts the whole core down for the LAST view instead.
- `is_markdown_active(&self) -> bool` — a cheap, synchronous main-thread read of `Snapshot::is_markdown_active()` (`current_filetype == "markdown"`, fed out-of-band via `wolf_current_file`). Gates the Preview command in the front-end (the Copy/visual-mode precedent). `false` after shutdown.
- `is_preview_active(&self) -> bool` — a cheap, synchronous main-thread read of `Snapshot::is_preview_active()` (`current_is_preview`, fed out-of-band via the `wolf_current_file` notification's 3rd bool arg — a preview buffer emits `("", "", true)`, so markdown-active and preview-active are never both true). Gates the Edit command in the front-end, the mirror of `is_markdown_active`. `false` after shutdown.
- `open_preview(&self, mode: &str) -> i64` — the BLOCKING preview-open: `runtime.block_on`s the `wolf_open_preview` helper, returning the preview scratch buffer's number (`0` on error or when the active buffer is not Markdown). `mode` is chosen by the front-end via `PreviewSeam.placementMode`: `"split_right"` (single pane → new pane to the right, reusing the `:vsplit` `wolf_layout` intent path), `"active"` (multi pane → replace the active pane's buffer via `nvim_win_set_buf`), or `"reuse_preview_pane"` (exactly two panes with the OTHER pane already a preview → bind into that OTHER preview window, leaving the active editor untouched, falling back to `"active"` when there is none). The front-end learns the new/reused pane + the source↔preview mapping on the next wake (via `wolf_preview`), so no synchronous window handle is needed.
- `edit_source(&self, mode: &str) -> i64` — the BLOCKING edit-source (Preview's INVERSE): `runtime.block_on`s the `wolf_edit_source` helper, navigating the active preview pane back to its SOURCE Markdown file and returning the source buffer's number (`0` on error or when the active pane is not a preview). `mode` is chosen by the front-end via `EditSeam.placementMode`: `"split_left"` (single pane → new editor pane to the LEFT, the source bound into the original window, reusing the `:vsplit` `wolf_layout` intent path), `"reuse_editor_pane"` (two panes with the OTHER pane a non-preview editor → bind the source into + focus that pane, falling back to the current), or `"active"` (else → replace the preview in the active pane). Binds by source bufnr when valid (no disk re-read, no MRU churn); the front-end learns the pane rebind on the next wake.
- `render_preview(&self, source_bufnr: i64) -> String` — the BLOCKING preview render: `runtime.block_on`s `NvimProcess::render_preview` (reads the SOURCE buffer's lines, joins them, and renders via `markdown::render_html` with the fixed `PreviewTheme::Default`), returning the themed HTML document the front-end web view loads (empty string on error, like `list_buffers`). Called on each wake for any preview pane whose source tick advanced.
- `preview_file(&self, win: i64, path: &str) -> i64` — the BLOCKING **link follow**: `runtime.block_on`s `NvimProcess::preview_file` (the `wolf_preview_file` helper), repointing the preview window `win` at the Markdown file at absolute `path` (a linked file the user clicked in the preview) and returning the linked file's SOURCE bufnr (`> 0`), or `0` when `path` is empty, unreadable, or not Markdown (or on error). `path` is ABSOLUTE — resolved by the front-end from WebKit's `file://` URL; core does NO relative resolution. On `0` the front-end applies its own O3 fallback (hand an existing-but-non-previewable file to the OS default app; no-op if missing).

`CoreConfig { init_lua: PathBuf, cols: u16, rows: u16, cwd: PathBuf }` — `cwd` is the picker's FALLBACK search root, the location of the MRU cache's pre-warmed store (`<cwd>/.wolf/mru.sqlite`), and the directory the captive Neovim is launched in. The picker's LIVE search root AND its MRU store both follow the captive Neovim's `getcwd()`; the configured `cwd` is used only when that query fails or returns an unusable path. `CoreError` is `Runtime(io::Error)`, `Nvim(NvimError)`, or `Mru(MruError)` (the `Mru` variant is retained for the public surface but `start` no longer produces it — per-cwd stores open lazily and gracefully).

### File picker — search session + ranking

- `FileSearch` (from [`files`](src/files.rs)) — a live search session. `read(&self) -> FileSearchReadGuard` (owned guard, `Deref`s to a state owning `entries: Vec<FileEntry>`, `complete: bool`, `version: u64`); `cancel(&self)` stops the background traversal, and `Drop` cancels too.
- `FileEntry { path: PathBuf, display: String, mru_rank: Option<u32> }` — an absolute `path` (to `Open`), a `display` (relative to the root, what the UI shows + ranks), and the MRU rank (`Some(0)` = most recent, `None` = not in MRU).
- `rank_matches(query: &str, entries: &[FileEntry]) -> Vec<Match>` (from [`rank`](src/rank.rs)) — pure fuzzy match + ranking: empty query = all entries MRU-first; non-empty = case-insensitive subsequence match, MRU-first then a filename-word strict-prefix preference. `Match { index, key: MatchKey }`.
- `MruStore` / `MruError` / `MRU_LIMIT` (from [`mru`](src/mru.rs)) — the SQLite MRU cache. Front-ends normally reach it via `mru_recent()` / `start_file_search` rather than directly.
- `rank_palette(recent_dirs, windows, command_mru_recent, query, max) -> Vec<PaletteRow>` (from [`palette`](src/palette.rs)) — the pure command-palette analog of `rank_matches`, which it REUSES for the fuzzy match + MRU-first ordering. It assembles the candidate rows (every `COMMAND_SPECS` row except `CommandPalette` → a `Static` row; one `PaletteWindow` → `SwitchWindow` row, labeled "Untitled" for an empty cwd; one recent dir → `OpenRecent` row), ranks them against `command_mru_recent`, and truncates to `max`. `PaletteRow { display, mru_key, kind: PaletteRowKind, command, window_index, path }`, `PaletteRowKind` (`Static`/`SwitchWindow`/`OpenRecent`), and `PaletteWindow { index, cwd }` are the value types; `CommandMru` / `COMMAND_MRU_LIMIT` (from [`command_mru`](src/command_mru.rs)) back the MRU. Front-ends reach this over the FFI as the `FfiCommandPalette` session rather than calling it directly.

### Buffer picker — candidate assembly + ranking (from [`buffer_picker`](src/buffer_picker.rs))

The palette-shaped counterpart to the file picker: candidates are FIXED at open (a blocking `WolfCore::list_buffers` snapshot), re-filtered synchronously, with NO streaming and no wake. This module is pure (IO-free) and headlessly testable, exactly like `palette`.

- `BufInfo { bufnr: i64, name: String, lastused: i64, modified: bool }` — one open buffer as queried from Neovim (`getbufinfo({'buflisted': 1})`): its handle, full name (absolute path, or `""` unnamed), the `lastused` MRU key, and the modified flag.
- `BufferRow { bufnr: i64, display: String, modified: bool }` — one assembled + ranked row: the buffer handle to switch to, the display label (also the string ranked against the query), and the modified flag for the row chrome.
- `rank_buffers(buffers: &[BufInfo], cwd: Option<&Path>, query: &str, max: usize) -> Vec<BufferRow>` — MRU-orders the buffers by `lastused` DESC (a stable sort tie-broken by `bufnr` ASC, so the current buffer lands first and IS included), projects each to a display string, and ranks them best-first by REUSING `rank_matches` (an empty query lists all buffers MRU-first). The display is the cwd-relative remainder when the name is under `cwd`, else the absolute name verbatim (no `~`-home fold), else `NO_NAME` (`[No Name]`) for an unnamed buffer. Core stays view-agnostic — scroll/cursor restoration lives entirely in `init.lua` (see `wolf_switch_buffer`). Front-ends reach this over the FFI as the `FfiBufferPicker` session rather than calling it directly.

### Wake callback — `WakeFn` (from [`redraw`](src/redraw.rs))

`type WakeFn = Arc<dyn Fn() + Send + Sync>`. Invoked once per `flush`, after the snapshot lock is dropped. May run on a tokio worker thread, so the front-end is responsible for marshalling onto its UI thread.

### Input — the `InputEvent` family (from [`input`](src/input.rs))

`InputEvent` = `Key(KeyEvent) | Mouse(MouseEvent) | Scroll(ScrollEvent) | Resize { cols, rows } | ResizeGrid { grid, cols, rows } | FocusWin { win } | Open { path } | Save | SaveAs { path } | Chdir { path } | SetTabpage { handle: i64 } | CloseTabpage { handle: i64 } | ClosePane | NewBuffer | Paste { text: String } | SwitchBuffer { win: i64, bufnr: i64 }`. `Chdir` applies as `:tcd` (the TAB-LOCAL cwd — each view/tabpage owns its own working directory, so no view ever issues a global `:cd` that would move every view of the shared nvim). `SetTabpage` / `CloseTabpage` (fed by `WolfCore::set_current_tabpage` / `close_tabpage`) drive tabpage switch/close via `nvim_set_current_tabpage` / the `wolf_close_tabpage` helper. `Paste` is applied via `nvim_paste` (fed by `WolfCore::paste`, the clipboard-paste face; the yank half of copy is the blocking `copy_visual_selection` rather than an input event, since it returns text). `SwitchBuffer` (fed by `WolfCore::switch_buffer`, the buffer-picker activation face) invokes the `init.lua` `wolf_switch_buffer(win, bufnr)` helper over `nvim_exec_lua` — a window-scoped `nvim_win_set_buf` plus per-pane view restoration, atomic in one Lua call. Supporting types: `KeyEvent`, `Key`, `MouseEvent { button, action, grid, row, col, ctrl, shift, alt }`, `MouseButton`, `MouseAction`, `ScrollEvent { direction, grid, row, col }`, `ScrollDirection`. `MouseEvent`/`ScrollEvent` carry a target `grid: u64` with GRID-LOCAL row/col, so under `ext_multigrid` a front-end targets the pane's window grid (`>= 2`) rather than the global grid 0.

`key_to_notation(&KeyEvent) -> String` translates a key event into Neovim notation (`<CR>`, `<Esc>`, `<C-w>`, …). Modifier order is `C-`, `S-`, `A-`, `D-`. **Shift contract:** for `Key::Char`, deliver the already-shifted glyph in the char and leave `shift = false`; `S-` is emitted only for named keys.

### Layout intents (from [`layout`](src/layout.rs))

`LayoutIntent` = `Split { orientation: SplitOrientation, from: i64, win: i64 } | FocusDir { dir: FocusDir, from: i64 }`, with `SplitOrientation` (`Horizontal`/`Vertical`) and `FocusDir` (`Left`/`Right`/`Up`/`Down`). These are parsed from the captive nvim's `wolf_layout` notifications and consumed via `WolfCore::drain_intents`; the shell uses them to own a native split-pane layout. A CLOSE has no intent (nvim performs a guarded `nvim_win_close`, observed via the `win_close` redraw event).

### Commands (from [`command`](src/command.rs))

A `Command` is a no-parameter, no-return user action: `NewWindow`, `CloseWindow`, `QuitApplication`, `HideApplication`, `MinimizeWindow`, `GoToFile`, `OpenFile`, `OpenFolder`, `ClosePane`, `NewBuffer`, `ResetFontSize`, `IncreaseFontSize`, `DecreaseFontSize`, `CommandPalette`, `Copy`, `Paste`, `BufferPicker`, `NewTab`, `Preview`, `Edit` (the variant order is the APPEND-ONLY discriminant contract shared with `wolf-ffi` and the macOS front-end; `ClosePane` is the former `CloseFile` renamed in place at 8, `NewBuffer`..`DecreaseFontSize` are appended at 9..12, `CommandPalette` at 13, `Copy`(14) / `Paste`(15) past it, `BufferPicker`(16), `NewTab`(17), `Preview`(18), and `Edit`(19) appended last). `COMMAND_SPECS: &[CommandSpec]` is the canonical registry — 20 rows, one per command, in variant order, carrying the canonical snake_case `id`, the PascalCase `ex_command` (`:Wolf<Pascal>`), a `title`, and a `MenuGroup` (`App`/`File`/`Window`/`View`/`Edit`, the `View` group carrying the three font-size commands, `CommandPalette` — id `command_palette`, `:WolfCommandPalette`, title "Command Palette…" — `BufferPicker` — id `buffer_picker`, `:WolfBufferPicker`, title "Buffer Picker…" — `Preview` — id `preview`, `:WolfPreview`, title "Preview" — and `Edit` — id `edit`, `:WolfEdit`, title "Edit Source", Preview's inverse — the `Edit` menu group carrying `Copy` (id `copy`, `:WolfCopy`, title "Copy") and `Paste` (id `paste`, `:WolfPaste`, title "Paste"), and the `File` group additionally carrying `NewTab` — id `new_tab`, `:WolfNewTab`, title "New Tab"). ONE canonical id derives both faces; the id→ex_command mapping is stored explicitly as data (no transform code). `Command::from_id(id) -> Option<Command>` resolves the `wolf_command` payload; `Command::spec(self) -> &CommandSpec` returns the row. Commands are ONLY user-triggered (no emit-on-attach) and are consumed via `WolfCore::drain_commands`. This module is pure data + enums (no GUI toolkit).

### Markdown preview — `markdown` (from [`markdown`](src/markdown.rs))

The pure, GUI-free, IO-free Markdown → themed-HTML renderer for the preview pane (requirement 6): the front-end web view just loads the `String` this module produces. Like `rank` it touches NO GUI toolkit and NO filesystem — a `&str` → `String` transform, headlessly unit-testable — and adds the `pulldown-cmark` + `pulldown-latex` dependencies (re-verified denylist-clean above). See the CSS/font assets in [`src/markdown/README.md`](src/markdown/README.md) and the math/font decisions in [`preview-math-and-fonts-decisions.md`](../../preview-math-and-fonts-decisions.md). Re-exported from the crate root:

- `render_html(source: &str, theme: PreviewTheme) -> String` — renders `source` Markdown to a complete themed HTML document (with the forward-compatible position markers embedded), wrapped as `<!doctype html><html><head><meta charset="utf-8"><style>{INTER_FONT_FACE}{MATH_FONT_FACE}{BASE_CSS}{MATH_CSS}{theme_css}</style></head><body class="wolf-markdown">{body}</body></html>`. Every heading carries an `id` (`ENABLE_HEADING_ATTRIBUTES` — an explicit `# Title {#custom-id}` honored verbatim, else a GitHub-style Unicode-preserving auto-slug, deduplicated in document order), so the front-end preview's anchor links can scroll to a heading. `ENABLE_MATH` is also on: `$…$` inline and `$$…$$` display LaTeX render to native MathML (see "Math rendering" below).
- `PreviewTheme` — the preview HTML/CSS themes. One variant ships this cut (`PreviewTheme::Default`, a fixed dark theme — OD5); the enum + `theme_css` + `include_str!`'d CSS files are structured so more themes and a config-driven selector drop in later. `Default` is also the `Default` impl.
- `theme_css(theme: PreviewTheme) -> &'static str` — the CSS for `theme` (embedded AFTER the structural `BASE_CSS` + `MATH_CSS`, each `include_str!`'d from `src/markdown/themes/<theme>.css`; `BASE_CSS` from `src/markdown/base.css` carries the `.wolf-src` marker rule + baseline layout, with its `body.wolf-markdown` stack now `"Inter"`-fronted; `MATH_CSS` from `src/markdown/math.css` carries the MathML styling adapted from pulldown-latex's `styles.css`).
- `MARKER_COLUMN_STRIDE: usize = 100` — the per-column marker stride (a named const, no magic number).

**Math rendering + inlined fonts.** With `ENABLE_MATH` on, the render chain is `offset_iter → HeadingIdAssigner → MathRenderer → MarkerInjector → html::push_html`. `MathRenderer` (BETWEEN `HeadingIdAssigner` and `MarkerInjector`) converts each `$…$` / `$$…$$` LaTeX fragment to inline MathML via `pulldown_latex::mathml::push_mathml` and emits it as `Event::InlineHtml` — so the `<math>` markup passes through un-escaped AND `MarkerInjector` never lands a `wolf-src` marker inside math (`is_block_start` never matches `InlineHtml`). Display math carries `display="block"`; malformed LaTeX degrades to a `<merror>` node (never a panic). WebKit (macOS Tahoe 26+) / WebKitGTK (GNOME 50+) render the MathML natively — no client-side JS. The document `<style>` ALSO inlines two `@font-face` data URIs so preview rendering is self-contained: `INTER_FONT_FACE` (the Inter variable roman woff2, one `@font-face` spanning `font-weight: 100 900`, fronting the body stack) and `MATH_FONT_FACE` (the bundled Latin Modern Math woff2, pinned to all `<math>` by `MATH_CSS`). Both fonts are committed pre-encoded as single-line base64 sidecars and `concat!`/`include_str!`'d at compile time (no runtime encode, no base64 crate). See [`src/markdown/README.md`](src/markdown/README.md).

**The marker/anchor scheme (built now; JS + cursor signal DEFERRED).** The emitted HTML carries invisible per-line and per-100-column position markers so a later cursor-follow scroll can find the line being edited. Each marker is an empty inline span, exactly `<span class="wolf-src" id="wl-{L}-{C}" data-line="{L}" data-col="{C}"></span>` (double-quoted `id`, a real `</span>` close — NOT self-closing): `L` is the 1-based hard buffer line (matches nvim `line('.')`), `C` is the 0-based CHARACTER column (OD4 — a character offset, NOT a byte offset, so multibyte lines resolve correctly). A marker `(L, 0)` is emitted for EVERY hard line `1..=line_count`, plus `(L, 100)`, `(L, 200)`, … for each multiple of `MARKER_COLUMN_STRIDE` strictly less than the line's character length. Markers are injected ONLY immediately before block-level `Start` tags (never inside inline content or a `<pre><code>`), so a block's interior line markers COLLAPSE to immediately before that block's opening tag — every `wl-{L}-0` id still EXISTS but resolves to the block top (a container like a `List` collapses all its items' interior markers to the container top; the accepted v1 collapse granularity). The forward-compat contract (a Neovim→web-view cursor-position signal + the JS that finds `#wl-{L}-{C}`, falling back to `#wl-{L}-0`, converting nvim's byte column to a character column) is DESIGNED but NOT built here; this module only guarantees the markers are present from day one.

**Heading slug ids (built now).** With `ENABLE_HEADING_ATTRIBUTES` on, `render_html` also emits an `id` on every heading. An explicit `# Title {#custom-id}` id is honored verbatim; otherwise an auto-slug is computed from the heading text (the in-order concat of every `Text` + `Code` event) by the §SLUG algorithm — Unicode-lowercase, then keep `is_alphanumeric`/`-`, map whitespace to `-` (NON-collapsing), drop everything else, falling back to `"section"` when empty, and deduplicated in document order against a shared count map (a second `"foo"` → `"foo-1"`; explicit ids are registered in the same map so later auto-slugs suffix around them). These ids are what the macOS preview's anchor-link handling scrolls to; `base.css` gives headings `scroll-margin-top: 2rem` so the target clears the top edge.

### Render state (from [`render`](src/render.rs))

`Snapshot` — the **multigrid** render model: `grids: HashMap<u64, Grid>` (the outer grid 1 holds the command line / messages; window content lives on grids `>= 2`), `windows: HashMap<u64, WinInfo>` (per-window layout/viewport keyed by grid id), `highlights`, `cursor` (with the grid it lives on), `mode_infos`, `active_win: Option<i64>` (the active window, via `wolf_active_win`), `current_tabpage: i64` (the current tabpage handle, `0` = unknown, via `wolf_tabpage` — the cheap refocus-rebind gate for the macOS project/tabpage-per-view model; only the current tabpage's windows appear in `windows`, no `seq` bump), `current_file`, `buffers: HashMap<i64, PathBuf>` (the per-window buffer-path map, keyed by the Neovim window handle — each an absolute canonicalized buffer path, unnamed windows ABSENT — updated out-of-band via the `wolf_buffers` notification, WHOLESALE-replaced on each emit so stale/closed windows vanish, no `seq` bump; the macOS front-end joins grid → window → path via `WolfCore::pane_status`), `theme: ThemeColors` (the `WolfCursor` / `WolfTitlebar` app-theme colors, via `wolf_theme`; each channel `Option<Rgb>`, all-`None` when a group is absent or cleared), `current_filetype: String` (the active buffer's `vim.bo.filetype`, via `wolf_current_file` — empty when unknown, no `seq` bump), `current_is_preview: bool` (whether the active buffer is a preview scratch buffer, via the `wolf_current_file` notification's 3rd bool arg — `false` by default, no `seq` bump), `previews: HashMap<i64, PreviewInfo>` (per-preview-window source info, keyed by the preview WINDOW handle, WHOLESALE-replaced via `wolf_preview`, no `seq` bump), `markdown_ticks: HashMap<i64, u64>` (per-source-buffer `changedtick`, keyed by the SOURCE buffer number, upserted via `wolf_markdown_dirty`, no `seq` bump), and `seq`. Accessors: `active_grid()`/`active_grid_id()`, `grid(id)`/`grid_mut(id)`, `active_viewport()`, `grid_for_win(win)`, `is_visual_mode()` (true when the cursor's cached `ModeInfo.name == "visual"`, i.e. `v`/`V`/`<C-v>` — excludes `"visual_select"`; gates the macOS Copy menu item over the FFI), `is_markdown_active()` (true iff `current_filetype == "markdown"`; mirrors `is_visual_mode`'s "resolve one field, match a string" shape — gates the macOS Preview menu item over the FFI), `is_preview_active()` (returns `current_is_preview`; the mirror of `is_markdown_active` — gates the macOS Edit menu item over the FFI, and a preview buffer's `("", "", true)` emit keeps the two mutually exclusive). Plus `Grid`, `Cell`, `HighlightTable`, `HlAttr`, `ResolvedStyle`, `DefaultColors`, `Rgb`, `Cursor`, `CursorShape`, `ModeInfo`, `Viewport`, `WinInfo`, `ThemeGroup`/`ThemeColors`, `PreviewInfo { source_bufnr: i64, source_path: PathBuf }` (where a preview pane's source Markdown lives), and the lock-guarded `SharedSnapshot`. See [`src/README.md`](src/README.md) for per-type detail.

`Snapshot.current_file: Option<PathBuf>` is the absolute, canonicalized path of the buffer currently being edited in nvim (`None` for an unnamed buffer). It is updated out-of-band from the redraw stream by the `wolf_current_file` notification (a `BufEnter`/`BufWinEnter`/`BufFilePost`/`FileType` autocmd installed after attach — see "How core embeds Neovim") and the wake fires after each change (it does NOT bump `seq`). The front-end reads it to highlight and reveal the current file in its file tree (the GNOME sidebar uses exactly this). The SAME notification carries a second argument — `vim.bo.filetype` — folded into `Snapshot.current_filetype`, which drives `Snapshot::is_markdown_active()` (the Preview command's enable gate), and a third boolean argument folded into `Snapshot.current_is_preview`, which drives `Snapshot::is_preview_active()` (the Edit command's enable gate). Preview scratch buffers (`b:wolf_preview_source`) are SKIPPED as a real file by this autocmd (they report an empty path + filetype but the preview flag `true`), so the scratch name never leaks into `current_file` / the statusbar while `is_preview_active` still tracks them.

`Snapshot.previews: HashMap<i64, PreviewInfo>` (keyed by the preview WINDOW handle) and `Snapshot.markdown_ticks: HashMap<i64, u64>` (keyed by the SOURCE buffer number) drive the Markdown preview. The `wolf_preview` notification (a window-scan autocmd) WHOLESALE-replaces `previews` with one `PreviewInfo { source_bufnr, source_path }` per window showing a `b:wolf_preview_source` scratch buffer, so closed preview windows drop out; the `wolf_markdown_dirty` notification upserts a `[source_bufnr, changedtick]` into `markdown_ticks`. Neither bumps `seq`. The front-end joins a preview's `source_bufnr` to its live tick to decide when to re-pull rendered HTML via `WolfCore::render_preview`. See "How core embeds Neovim".

### User preferences — `config` (from [`config`](src/config.rs))

A GUI-toolkit-free reader for the user-level `wolf-config.yaml` preferences file (font family / size / line-height). It is standalone — it does not hang off `WolfCore` — and is exposed to the macOS front-end over the `wolf-ffi` bridge (`wolf_ffi_load_config` / `FfiConfig`).

- `WolfConfig { font_family: String, font_size: f64, line_height: f64 }` — the resolved configuration. `line_height` is the PERCENTAGE of the font size (`130` = 130%).
- `preferences_dir() -> Option<PathBuf>` — the platform preferences directory. It honors a `WOLF_CONFIG_DIR` environment override FIRST (a test/determinism hook); otherwise it is `dirs::preference_dir()/"Wolf"` (`~/Library/Preferences/Wolf`) on macOS and `dirs::config_dir()/"wolf"` (`~/.config/wolf`) on Linux. Both platform paths are resolved in code even though only macOS consumes prefs this increment.
- `default_config() -> WolfConfig` — font-family `"iA Writer Mono S"`, line-height `130`, and a platform-specific font-size (14 on macOS, 10 on Linux, via `cfg!`).
- `load_or_create(dir: &Path) -> WolfConfig` — **infallible** (defaults-on-error). Reads `<dir>/wolf-config.yaml`: when the file is ABSENT it creates the parent and writes the serialized defaults, returning them; when it PARSES it returns the parsed config; when it is present but malformed / the wrong shape it logs a `tracing::warn!` and returns the defaults WITHOUT overwriting the user's file (it only ever writes when the file is absent).

The on-disk schema has a top-level `config:` key with kebab-case fields:

```yaml
config:
  font-family: "iA Writer Mono S"
  font-size: 14
  line-height: 130
```

### Application state — `state` (from [`state`](src/state.rs))

A GUI-toolkit-free persistence layer for the application-state TREE (a list of windows, each with geometry plus its ordered list of tabs; each tab carries its own working directory + sidebar visibility), written to a pretty-printed **`state.json`** in the platform state directory. It is exposed to the macOS front-end over the `wolf-ffi` bridge (`wolf_ffi_load_state` / `FfiState` for the pre-start restore read; the `wolf_ffi_state_snapshot_*` builder free functions for the live whole-tree write). The front-end OWNS all writes: the coordinator walks its live windows/tabs and submits the whole tree; core no longer mirrors cwd into a store (`attach_state_store` is gone).

- `WolfState { windows: Vec<WindowState> }` — the whole persisted state: a TREE of windows, one entry per open OS window (a native tab group is one window with several tabs).
- `WindowState { x, y, width, height: f64, tabs: Vec<TabState> }` — one window's geometry plus its ordered tabs. Geometry is in `f64` points, interpreted by the writing front-end (macOS stores `NSWindow.frame`, AppKit bottom-left global coordinates); a non-positive `width`/`height` is the "unset" sentinel (restore treats the geometry as absent). There is NO `#[serde(default)]` on `tabs`, so an OLD flat (pre-tabs) file carrying a window-level `cwd`/`sidebar_visible` and no `tabs` fails deserialization and is silently ignored (no migration path).
- `TabState { cwd: String, sidebar_visible: bool }` — one tab's state (a tab is one VIEW = one nvim tabpage; project membership is NOT persisted, so restore rebuilds projects by grouping tabs by cwd). `cwd` is the absolute canonicalized path the view's tabpage reported (its tab-local `:tcd`), or `""` when not yet reported / the empty state (restore validates it is a non-empty existing directory before use); `sidebar_visible` defaults to `true`.
- `state_dir() -> Option<PathBuf>` — the platform state directory, parallel to `preferences_dir()`. It honors a `WOLF_STATE_DIR` environment override FIRST (a test/determinism hook); otherwise it is `dirs::data_dir()/"Wolf"` (`~/Library/Application Support/Wolf`) on macOS and `dirs::state_dir()/"wolf"` (`~/.local/state/wolf`, falling back to `dirs::data_dir()`) on Linux.
- `load_state(dir: &Path) -> Option<WolfState>` — **infallible and strictly read-only** (the silently-ignore contract): it NEVER creates, rewrites, or deletes the file. An absent file is a silent `None`; ANY other failure — unreadable, unparseable, wrong shape, missing the required `tabs` list, or a `version` other than `1` — logs a `tracing::warn!` and returns `None`, leaving the on-disk bytes untouched (all-or-nothing, matching the `config` precedent). Unknown extra fields are tolerated, so newer writers do not break older readers.
- `StateStore` — the live, cloneable store handle. `open(dir: &Path)` (explicit directory — the injection seam; production callers pass `state_dir()`) loads the existing file per `load_state` (defaults on `None`) and spawns ONE dedicated writer thread (`wolf-state-writer`) that serializes ALL disk writes. `set_snapshot(next: WolfState)` replaces the whole tree: under a brief mutex it compares `next` against the current tree and — ONLY when it differs — swaps it in, bumps the generation, and wakes the writer (an identical snapshot is a no-op, so a redundant re-submit causes no disk churn); the writer sleeps a short coalesce delay (~100 ms, so a burst produces one write), then atomically replaces the file via a sibling tmp file + rename — a crash never leaves a partial file. `state()` returns a clone of the in-memory truth; `flush(timeout) -> bool` blocks until every pending write has been ATTEMPTED (write errors log but still count, so flush cannot hang on a read-only disk). All operations are infallible (log-not-fail). The writer thread exits on its own once every handle is dropped and nothing is pending. The old granular per-index setters (`set_geometry`/`set_cwd`/`set_sidebar_visible`/`truncate_windows`) are GONE.

Concurrency notes: opening the SAME directory twice in one process is unsupported (two writer threads would race on the shared tmp file — open ONE store and clone it instead; the `wolf-ffi` bridge realizes exactly this with a process-wide `SHARED_STORE` the snapshot builder commits into); concurrent Wolf PROCESSES are out of scope — the last writer wins, but each write is atomic so the file is never torn.

The on-disk schema (`version` is `1`; any other version — or an old flat window with no `tabs` — is silently ignored):

```json
{
  "version": 1,
  "windows": [
    {
      "x": 128.0,
      "y": 64.0,
      "width": 1180.0,
      "height": 760.0,
      "tabs": [
        { "cwd": "/Users/alice/projects/notes", "sidebar_visible": true },
        { "cwd": "/Users/alice/projects/docs", "sidebar_visible": false }
      ]
    }
  ]
}
```

## How core embeds Neovim

- **Generic untyped RPC.** All calls go through `Neovim::call` with `rmpv::Value` arguments, and the `redraw` stream is consumed as raw `Vec<rmpv::Value>`. This insulates core from `nvim-rs` 0.9.2's older typed API vs. Neovim 0.12.
- **`ext_linegrid` + `ext_multigrid`.** `nvim_ui_attach` is called with `ext_linegrid = true`, `ext_multigrid = true`, and `rgb = true`; `ext_multigrid` is what gives each Neovim window its own grid so the shell can own a native split-pane layout. `ext_cmdline`/`ext_messages`/`ext_popupmenu` remain deferred.
- **`WOLF_NVIM_BIN` discovery.** The binary is located _only_ via the `WOLF_NVIM_BIN` env var (exported by the flake devShell), never `PATH` and never `/nix/store` scanning.
- **Hermetic launch.** `nvim --embed --clean -u runtime/nvim/init.lua -i NONE -n` with `NVIM_APPNAME=wolf` and isolated `XDG_{CONFIG,DATA,STATE,CACHE}_HOME` under a private temp dir, so the captive editor cannot read the user's config/state.
- **Current-file tracking.** Immediately after `ui_attach`, core calls `setup_current_file_tracking`: it reads its own RPC channel id from `nvim_get_api_info` and invokes `_G.wolf_setup_current_file_tracking(chan)` (in `runtime/nvim/init.lua`) over `nvim_exec_lua`, which registers a `BufEnter`/`BufWinEnter`/`BufFilePost`/`FileType` autocmd that `rpcnotify`s `wolf_current_file` with `expand('%:p')`, `vim.bo.filetype`, AND a 3rd boolean marking a preview buffer (plus one initial emit); a `b:wolf_preview_source` scratch buffer is skipped as a real file but emits `("", "", true)`. The handler folds each notification into `Snapshot.current_file` + `Snapshot.current_filetype` + `Snapshot.current_is_preview` and wakes the front-end.
- **Per-window buffer tracking.** After current-file tracking, core calls `setup_buffer_tracking` (the same channel-id-via-`nvim_get_api_info` pattern), which invokes `_G.wolf_setup_buffer_tracking(chan)` (in `runtime/nvim/init.lua`). That registers `BufEnter`/`BufWinEnter`/`BufFilePost`/`WinEnter`/`WinNew`/`WinClosed` autocmds that `rpcnotify` `wolf_buffers` with a list of `[win, nvim_buf_get_name(buf)]` pairs for ALL windows of the current tabpage (plus one initial emit). The handler folds each notification WHOLESALE into `Snapshot.buffers` (win handle → canonicalized buffer path, unnamed windows skipped) and wakes the front-end (no `seq` bump), so the macOS per-pane statusbar can join a grid → window → buffer path via `WolfCore::pane_status`.
- **Split-panes layout overrides.** After current-file tracking, core calls `setup_layout`, which (the same channel-id-via-`nvim_get_api_info` pattern) invokes `_G.wolf_setup_layout(chan)` (in `runtime/nvim/init.lua`). That rebinds the `<C-w>` split/close/focus chords and the `:split`/`:vsplit`/`:close` Ex-commands to `rpcnotify` `wolf_layout` intents, and registers a `WinEnter` autocmd that `rpcnotify`s `wolf_active_win`. The handler parses each `wolf_layout` into a `LayoutIntent` on a drainable queue and folds `wolf_active_win` into `Snapshot.active_win`.
- **Theme tracking.** After directory tracking, core calls `setup_theme_tracking`, which (the same channel-id pattern) invokes `_G.wolf_setup_theme_tracking(chan)` (in `runtime/nvim/init.lua`). That registers a `ColorScheme` autocmd that `rpcnotify`s `wolf_theme` with the effective `WolfCursor` / `WolfTitlebar` highlight-group colors (read with `link = false`; four flat scalars, `-1` = unset; plus one initial emit so the startup colorscheme is picked up). The handler folds each notification into `Snapshot.theme` and wakes the front-end (no `seq` bump).
- **Command registration.** After theme tracking, core calls `setup_commands`, which (the same channel-id pattern) invokes `_G.wolf_setup_commands(chan, commands)` (in `runtime/nvim/init.lua`), passing the `COMMAND_SPECS` list as `[id, ex_command]` pairs. That seeds `package.loaded['wolf']` (so `require('wolf')` resolves under `--clean`) and, per pair, registers a `require('wolf').<id>()` Lua function and a `:<ex_command>` user command (`nargs=0, force=true`), each `rpcnotify`ing `wolf_command '<id>'`. The handler resolves the id via `Command::from_id`, pushes onto a drainable queue, and wakes the front-end (no `seq` bump). No autocmd (user-triggered only).
- **Tabpage tracking + lifecycle (project/tabpage-per-view).** After command registration, core calls `setup_tabs`, which (the same channel-id pattern) invokes `_G.wolf_setup_tabs(chan)` (in `runtime/nvim/init.lua`). That registers `TabEnter`/`TabNewEntered` autocmds that `rpcnotify` `wolf_tabpage` with `nvim_get_current_tabpage()` (plus one initial emit), which the handler folds into `Snapshot.current_tabpage`; it LOCKS OUT nvim-internal tabpage navigation/creation (OD4 — the `gt`/`gT`/`<C-w>gt`/`<C-w>gT`/`<C-PageUp>`/`<C-PageDown>` chords → `<Nop>` and the typed `:tabnew`/`:tabnext`/`:tabprevious`/`:tabonly`/`:tabclose`/`:tabmove` Ex-commands, but NOT `:tcd`/`:lcd`/`:cd`), since Wolf owns ALL tabpage lifecycle; and it defines the `wolf_create_tabpage` / `wolf_close_tabpage` / `wolf_tab_cwd` helpers the `create_tabpage`/`close_tabpage`/`cwd_for_tabpage` methods drive. `wolf_buffers` (per-window buffers) and `wolf_cwd` (directory tracking) are current-tabpage-scoped — they report the FOCUSED view's windows/cwd, which is exactly what the front-end needs; a non-current view's cwd is read on demand via `cwd_for_tabpage`.
- **Buffer-picker view tracking.** After tabpage setup, core calls `setup_view_tracking`, which invokes `_G.wolf_setup_view_tracking()` (in `runtime/nvim/init.lua`) over a bare `nvim_exec_lua` with NO channel id and NO payload. Unlike the other `setup_*` helpers it emits NO `rpcnotify`: it only maintains an in-nvim `(winid, bufnr) -> winsaveview()` cache (via `BufLeave`/`WinLeave`/`WinClosed` autocmds) and defines the `_G.wolf_switch_buffer(win, buf)` helper that reads it. Core stays view-agnostic — no scroll/cursor payload crosses the boundary. The blocking `list_buffers()` query (`getbufinfo({'buflisted': 1})`, decoding each map's `bufnr`/`name`/`lastused`/`changed`, skipping malformed entries) that seeds the picker is a separate one-shot RPC, not an autocmd.
- **Preview tracking.** Last of all, after view tracking, core calls `setup_preview` (the same channel-id-via-`nvim_get_api_info` pattern), which invokes `_G.wolf_setup_preview(chan)` (in `runtime/nvim/init.lua`). That registers the `WolfPreview` augroup: a `WinEnter`/`BufWinEnter`/`WinNew`/`WinClosed`/`BufWinLeave` window-scan that `rpcnotify`s `wolf_preview` with `[preview_win, source_bufnr, source_abs_path]` triples for every window showing a `b:wolf_preview_source` scratch buffer (plus one initial emit), and markdown-guarded `TextChanged`/`TextChangedI`/`BufWritePost` autocmds that `rpcnotify` `wolf_markdown_dirty` with `[source_bufnr, changedtick]`. The handler folds the first WHOLESALE into `Snapshot.previews` and upserts the second into `Snapshot.markdown_ticks`, waking the front-end (no `seq` bump). The blocking preview render/open RPCs — `render_preview(source_bufnr)` (reads the source buffer's lines and renders via `markdown::render_html`), `open_preview(mode)` (runs the `wolf_open_preview` helper), and `edit_source(mode)` (Preview's inverse, runs the `wolf_edit_source` helper) — are separate one-shot RPCs, not autocmds.

## The file-search session

The picker drives a `FileSearch` session that mirrors the render-state snapshot+wake mechanism rather than streaming callbacks across the boundary:

- `start_file_search(wake)` first resolves the traversal root to the captive Neovim's **live working directory** (`getcwd()`, queried over RPC via a brief `runtime.block_on`), so the picker follows wherever Neovim is (`:cd`/`:lcd`/ `:tcd`); if that query fails or returns an unusable path it falls back to the configured `cwd`. It then seeds the MRU cache **synchronously** into the shared `FileSearchState` (so the very first `read()` already shows recent files), then spawns the `ignore`-crate traversal on the core's tokio runtime (`spawn_blocking`, since the walk is blocking IO). **The MRU seed follows nvim's live cwd:** it is taken from the per-cwd store at `<resolved-root>/.wolf` (the SAME resolved search root the traversal uses), so seeded entries lie inside the search root and their `display` strings are root-relative — per-project MRU isolation, never absolute and never relative to a stale configured cwd. (The write path is symmetric: the input pump records each `InputEvent::Open` into the per-cwd store for nvim's live cwd, tracked out-of-band via the `wolf_cwd`/`DirChanged` notification.)
- The traversal streams discovered files into the shared state in batches, bumping `version` and firing the same `wake` callback after each batch (and once more on `complete`) — exactly the marshal-onto-the-UI-thread-then-read pattern the front-end already implements for redraws.
- The front-end reads the current entries via the owned `FileSearchReadGuard`, ranks them with `rank_matches`, and renders. Dropping (or `cancel`-ing) the `FileSearch` stops the traversal (e.g. closing the picker or starting a new search).
- **Opening a file records the MRU.** Selection feeds `InputEvent::Open { path }` through the normal input channel; the ordered input pump records each drained `Open` into the `MruStore` (synchronously, never across an `.await`), so no separate "select" call exists and `input.rs` stays storage-free.

## Threading and locking model

- Core owns a **multi-thread tokio runtime on its own thread(s)**; the `nvim-rs` handler receives `redraw` notifications there.
- A **single `parking_lot::RwLock`** guards the snapshot. The redraw handler takes the write lock **once per whole batch**, never holds it across an `.await`, and fires the wake callback only **after** the lock is dropped (on `flush`).
- The write lock is acquired cooperatively (`write_async`, a `try_write` retry loop yielding to the scheduler) so a front-end holding a read guard cannot pin a worker thread.
- Input is delivered through an **ordered FIFO channel** to a single consumer task, which fuses a run of consecutive `Key` events into one `nvim_input` call. This keeps keystrokes in order and makes a burst produce a single redraw flush.

## Phase 1 scope and what is deferred

In scope: hermetic pinned Neovim, `ext_linegrid` + `ext_multigrid` redraw → multigrid snapshot, the Neovim→shell layout-intent channel (native split panes), abstract input translation, the FFI-shaped surface, and headless verification.

Deferred to later phases: full `wrapNeovim` plugin baking (treesitter grammars, `marksman` LSP, formatter), native cmdline/messages/popupmenu (`ext_cmdline`/ `ext_messages`/`ext_popupmenu`), theming, and the non-layout intents (open/save dialogs, window title). The layout intents (split/focus) and the GTK (`wolf-gnome`) front-end are realized; the macOS (`wolf-macos`) front-end and its swift-bridge bindings (in the `wolf-ffi` crate) are realized — a **multi-window** AppKit shell over the swift-bridge surface, with one captive Neovim per **PROJECT** shared by N views (each view = one nvim TABPAGE), native panes, the picker, the file tree, mouse/scroll, and bundled Neovim.
