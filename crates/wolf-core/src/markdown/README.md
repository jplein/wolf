# wolf-core/src/markdown

The CSS and font assets that [`crate::markdown`](../markdown.rs) `include_str!`s into the preview HTML document it renders. None of the files in this directory (or its `assets/` subdirectory) are Markdown docs, so they are NOT prettier-formatted. `render_html` assembles the document `<style>` block from them in the fixed order `{INTER_FONT_FACE}{MATH_FONT_FACE}{base.css}{math.css}{theme.css}` (see [`../markdown.rs`](../markdown.rs) and [`../README.md`](../README.md)).

## `base.css`

The structural + marker CSS shared by every preview theme, embedded BEFORE the selected theme's CSS. It owns three things:

- **The `.wolf-src` marker rule** — a zero-size, invisible, non-selectable inline anchor (`width: 0; height: 0; overflow: hidden; visibility: hidden; pointer-events: none`). Each source-position marker span the renderer injects carries this class; the rule guarantees the markers take no layout space and never affect the rendered body. See the marker/anchor scheme in [`../README.md`](../README.md). Its `font-size: 0` and `line-height: 0` are load-bearing now that the body sets `line-height` as a LENGTH (see below): a marker that lost its own `line-height: 0` would inherit a hard 24px and inject visible blank lines throughout the document. Do not touch this rule.
- **Structural layout** — margins, headings, code/table/blockquote framing, list padding, `scroll-margin-top: 48px` on `h1..h6` (2 baselines of clearance above a heading scrolled into view by an anchor link; the body itself has no padding, so this is the only thing keeping a jumped-to heading off the pane's top edge), and the `body.wolf-markdown` font stack. That stack is **Inter-fronted**: `font-family: "Inter", -apple-system, BlinkMacSystemFont, "Segoe UI", Helvetica, Arial, sans-serif` — `"Inter"` (supplied by the inlined `INTER_FONT_FACE`) first, with the system fallback retained behind it. A theme layers colors on top; `base.css` carries structure only.
- **A 24px baseline grid** governing every vertical dimension in the file — see below.

### The baseline grid

The unit is **24px** (16px body text × 1.5), declared once as the documented token `--wolf-baseline: 24px` on `body.wolf-markdown` and written `B` below. The header comment of [`base.css`](base.css) is the authoritative spec; this section duplicates it deliberately so the grid reads without opening the CSS.

**`line-height` is a LENGTH, not a ratio.** `body.wolf-markdown` sets `line-height: 24px`, not a unitless `1.5`. A unitless number re-multiplies against each _descendant's_ own `font-size`, so inline `<code>` at `0.875em`, `<small>`, and superscripts would each produce a different line box and fall off the grid. A length inherits as the _computed_ 24px regardless of descendant font-size. The cost is that any element wanting different leading must say so explicitly — only `h1`/`h2` (48px) and `pre` (24px, stated anyway) do.

**The invariant.** Every element's vertical margin is 0 or a whole multiple of 24px, AND every element's border-box height (content + padding + border) is a whole multiple of 24px. The invariant is closed under margin collapsing — collapsing takes `max(a, b)`, and the max of two multiples of 24 is a multiple of 24 — which is why border compensation always folds the border into _padding_ or an explicit _height_, never into a margin.

**The type scale.**

| element  | font-size | line-height | margin-top | margin-bottom  |
| -------- | --------- | ----------- | ---------- | -------------- |
| body / p | 16px      | 24px (1B)   | `p`: 0     | `p`: 24px (1B) |
| `h1`     | 32px      | 48px (2B)   | 48px (2B)  | 24px (1B)      |
| `h2`     | 24px      | 48px (2B)   | 48px (2B)  | 24px (1B)      |
| `h3`     | 20px      | 24px (1B)   | 48px (2B)  | 0              |
| `h4`     | 18px      | 24px (1B)   | 24px (1B)  | 0              |
| `h5`     | 16px      | 24px (1B)   | 24px (1B)  | 0              |
| `h6`     | 14px      | 24px (1B)   | 24px (1B)  | 0              |

`h1`/`h2` preserve the previously rendered sizes exactly (`2em` / `1.5em` of 16px), so this is not also a visual resize of the two most-seen headings. `h3`–`h6` previously fell through to UA defaults (18.7 / 16 / 13.3 / 10.7px, where `h5` equalled body text and `h6` was illegibly small); the 20/18/16/14 ramp is smooth and bottoms out legibly, with `h6` distinguished by weight 600 rather than by being tiny. `h2` takes 48px leading because the only other grid-legal value at a 24px font is 24px (ratio 1.0), where wrapped lines nearly touch. Every heading has strictly more space above than below (48>24, 48>0, 24>0), and `h3`–`h6` with `margin-bottom: 0` hug the content they introduce. Collapsing does the section spacing for free: `p { margin-bottom: 24px }` against `h2 { margin-top: 48px }` collapses to `max(24, 48) = 48 = 2B`.

**Border compensation.** `hr` gets an explicit 24px border-box height that absorbs the rule structurally, with the rule drawn as `border-top` and `margin: 24px 0 0` → `24 + 24 + 0 = 48px = 2B`; margins alone could not fix the old 1px-height `hr`, since an `hr` before an `h2` collapses to 48 and re-exposes the 1px. For `th`/`td` under `border-collapse: collapse` adjacent rows SHARE one border, so an N-row table has N+1 horizontal lines and the row pitch is `12 (padding-top) + 24 (line-height) + 11 (padding-bottom) + 1 (shared border) = 48px = 2B` (47 is odd, so the padding cannot be split evenly; the 12/11 asymmetry is imperceptible). The whole table is `47N + (N+1) = 48N + 1`; the trailing 1px is the table's own bottom outer border, which has no next row to share with, so `table { margin-bottom: 23px }` brings the total to `48N + 24` = exactly `2N+1` baselines. No compensation is needed for `blockquote` (it has no border on any edge and its vertical padding is 0, so its border-box height is just the sum of its on-grid children), `pre` (no border), or inline `code` (vertical padding on an inline box paints background but does not grow the line box).

**Edge rules — and why their selectors are not just `:first-child` / `:last-child`.** The first block must have `margin-top: 0` and the last block `margin-bottom: 0`. The body has no padding, so an unreset 48px `margin-top` on the opening block goes one of two ways. Either it collapses out through the body's top edge — parent–child collapsing is unblocked with no `border-top`, no `padding-top`, no clearance and no BFC — displacing the whole document 48px; note this is a POSITIONAL symptom only, not a visible color gap, because neither `base.css` nor any theme sets a background on `html`, so per CSS background propagation the body's background paints the entire canvas including the escaped margin. Or, if a leading `.wolf-src` anchor's anonymous block box blocks the collapse-through, the 48px instead sits INSIDE the body between that anonymous box and the heading. Which way it resolves depends on whether that anonymous box is self-collapsing (a function of the anonymous container's inherited 24px strut, not the span's own `line-height: 0`) — engine-dependent territory, and it does not matter: both outcomes put the opening heading 48px down and defeat the flush-to-edge body. A mirrored argument covers the last block. 48 is still a multiple of 24, so the GRID SWEEP CANNOT SEE THIS BUG — only the DOM-level edge tests can. The obvious spelling is INERT here: the scroll-sync `.wolf-src` anchors are real elements in the body, flushed before the first block's opening tag and (for any source ending in a newline) after the last block's closing tag, so those structural pseudo-classes land on a zero-size anchor with no margin to zero while the real block keeps its margin. The shipped rules therefore SKIP the anchors — `> *:not(.wolf-src):not(*:not(.wolf-src) ~ *)` ("not an anchor, and no non-anchor sibling precedes it") and `> *:not(.wolf-src):not(:has(~ *:not(.wolf-src)))` ("not an anchor, and no non-anchor sibling follows it"). Both forms are UNBOUNDED in the length of the anchor run they skip, and each lives in its OWN rule because both are Selectors 4 (complex `:not()` argument, `:has()`): an engine missing either must drop just that rule rather than invalidate a shared selector list. The naive `> *:last-child` ALSO ships, ahead of the general last-block rule — not as an alternative chosen over the general form, but as a harmless partial fallback that happens to be correct for the one case where the source does not end in a newline (no trailing anchor, so `:last-child` is the real block); the general rule below it covers every case, including that one. Do not "simplify" them back to the bare structural form, and do not try to fix it from the `.wolf-src` side instead — `:first-child` is structural, so no display/size change on the anchor would help.

**Documented residuals.** (1) A table immediately followed by any block whose `margin-top` exceeds 23px collapses the table's 23px against that larger margin, re-exposing the 1px — that is every heading (`h1`–`h3` at 48px, `h4`–`h6` at 24px) and `hr` (24px); a following paragraph, list, `pre`, or blockquote (`margin-top: 0`) is exact. The error is constant, not accumulating. (2) Images and display MathML are ACCEPTED drift: their intrinsic heights are not grid-quantized and there is no CSS-only way to snap them. No JS re-snapping is used anywhere in the document.

**Horizontal dimensions are deliberately NOT grid-constrained.** The grid is vertical only. The 32px list indent, the 16px cell padding, and the 24px blockquote inset are chosen for looks, not for the grid. Do not "fix" them to multiples of 24. The body itself is flush to the pane edges by design (`padding: 0`); any inset belongs to the preview pane chrome.

**Literal px, not `calc(var(--wolf-baseline) * n)`.** `--wolf-baseline` is declared as the documented token, but every other value in the file is a literal integer px. The grid audit test asserts that values are whole multiples of 24, which it can do against `48px` but not against a `calc()` expression (there it could only string-match syntax, proving nothing about the number); the compensated values 23/12/11 are not clean multiples anyway and would become `calc(… - 1px)`, hiding the compensation; and `calc()` buys no configurability today, since there is a single `PreviewTheme` and no user config surface. Everything is px rather than rem/em on purpose: `rem` resolves against a root font-size this document never sets, so a WebKit minimum-font-size preference or OS text scaling could silently detune the grid. The `base.css` header is the single source of truth for the arithmetic — do not add per-declaration comments restating it.

### Code-block syntax highlighting requires NO CSS change

Fenced code blocks carry treesitter syntax highlighting (mirroring the captive Neovim), but this is delivered ENTIRELY as inline `<span style="color:#RRGGBB;font-weight:bold;…">` runs written into the `<pre><code>` interior by `markdown.rs` — no CSS file changed. The inline `style=` on a child `<span>` overrides the inherited `pre code` color per the cascade, so the `pre`/`code` framing rules and the 24px baseline grid above are unaffected (vertical padding on an inline `<span>` paints no line-box growth). There is no generated stylesheet and no CSS class for highlighting. See [`../../../../preview-code-block-syntax-highlighting-decisions.md`](../../../../preview-code-block-syntax-highlighting-decisions.md).

## `themes/default.css`

The one shipped preview theme (`PreviewTheme::Default`), embedded AFTER `base.css`. Its CSS declares `color-scheme: light dark;` and carries a dark default palette plus a `@media (prefers-color-scheme: light)` block (light background `#f4f4f4`), so the preview follows the app's resolved dark/light appearance automatically (the web view inherits `NSApp.effectiveAppearance`) with no FFI change — while still NOT being wired to the live nvim colorscheme. The `PreviewTheme` enum + `theme_css` + this `include_str!`'d file are structured so more themes and a config-driven selector can drop in later; for now selection is a hardcoded `PreviewTheme::Default`.

One consequence of `base.css`'s baseline grid reaches into this file: `hr` is colored via `border-top-color`, NOT `background-color`, in both the dark block and the `@media (prefers-color-scheme: light)` block. `base.css` gives the rule an explicit 24px grid height so its 1px is absorbed structurally, and this file is emitted AFTER `base.css` — a `background-color` here would win the cascade and fill that 24px box with a solid bar instead of a hairline.

## `math.css`

The MathML styling for pulldown-latex's `<math>` output, embedded (via the `MATH_CSS` const) AFTER `base.css`, alongside the inlined `@font-face` rules. It is **adapted from pulldown-latex's `styles.css`** (MIT, carloskiki/pulldown-latex) with three changes:

1. **All `@font-face` rules dropped.** Upstream's faces used relative `url('font/…')` paths that do not resolve in the inlined preview document; `markdown.rs` supplies the math font itself as an inlined base64 `data:` URI `@font-face` (`MATH_FONT_FACE`), and the upstream `mtext` font rule was dropped with the faces it referenced.
2. **The MathML `@namespace m` prefix removed** and every `m|…` selector rewritten to its plain element/class form (WebKit / WebKitGTK render the un-namespaced math DOM pulldown-latex emits).
3. **A final font pin appended** — `math, math * { font-family: "Latin Modern Math", math; }` — so all math content resolves to the bundled Latin Modern Math font, never a host-installed one.

(Its top comment also notes it must never contain the literal `<math` open-tag sequence, so a test scanning the document for the first such tag finds the rendered body, not this file's comment.)

## `assets/`

The vendored fonts, each committed three ways: the raw woff2 (provenance), a single-line base64 sidecar (`*.woff2.b64`, the file the code actually `include_str!`s), and the license text.

| File                     | Bytes  | Upstream source                                                                                                                            | License                                                  |
| ------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| `inter-variable.woff2`   | 352240 | rsms/inter v4.1 release asset `web/InterVariable.woff2`                                                                                    | SIL OFL 1.1 (`inter-OFL.txt`)                            |
| `latinmodern-math.woff2` | 387976 | pulldown-latex repo `font/latinmodern-math.woff2` (`raw.githubusercontent.com/carloskiki/pulldown-latex/main/font/latinmodern-math.woff2`) | GUST GFL v1.0 (`latinmodern-math-GUST-FONT-LICENSE.txt`) |

**How they reach the document.** `markdown.rs` builds the `INTER_FONT_FACE` and `MATH_FONT_FACE` consts at COMPILE time with `concat!` + `include_str!` of the `.b64` sidecars, wrapping each in a `@font-face { … src: url('data:font/woff2;base64,<b64>') format('woff2') }` rule — zero runtime base64 encoding, and no base64 crate dependency. Inter declares the full variable weight axis (`font-weight: 100 900`); Latin Modern Math is pinned to all `<math>` content by `math.css`.

**Single-line invariant.** Each `.woff2.b64` MUST stay a single line (produced with `base64 -i f.woff2 | tr -d '\n' > f.woff2.b64`). A newline inside the base64 would break the `data:` URI. Only the roman Inter variable face is bundled (no separate italic file), so italic body text is faux-italic; the lmroman text faces pulldown-latex ships were deliberately NOT vendored (Wolf bundles ONE math font).

**Bazel note.** Because the `.b64` sidecars are `include_str!`'d at compile time, `crates/wolf-core/BUILD.bazel`'s `compile_data` glob must include `src/markdown/assets/*.b64` (alongside `src/markdown/**/*.css`). The raw woff2 and license texts are provenance-only and are not needed by rustc. See [`../../../../build.md`](../../../../build.md).

See [`preview-math-and-fonts-decisions.md`](../../../../preview-math-and-fonts-decisions.md) for the decisions behind bundling and inlining these assets.
