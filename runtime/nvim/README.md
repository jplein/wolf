# runtime/nvim

The in-repo Neovim configuration for Wolf's captive editor. It is version-controlled alongside the code that depends on it, so editor behavior is pinned to the core.

## `init.lua`

Loaded by the captive Neovim that `wolf-core` spawns:

```
nvim --embed --clean -u runtime/nvim/init.lua -i NONE
```

`--clean` already skips the user's config, plugins, and shada; core additionally pins `NVIM_APPNAME=wolf` and the `XDG_*` dirs away from the user's from the spawning side (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)). The former `-n` launch flag has been REMOVED: `-n` forces `updatecount = 0`, which disables swap-file writing entirely and would make the crash-recovery of unsaved edits (below) impossible. `init.lua` itself sets options that make the captive editor **crash-recoverable**, **Markdown-only**, and **deterministic for headless rendering tests**.

What it sets and why:

- **Swap-file crash recovery of unsaved edits (`swapfile = true`)** — swap files are now ON always (the former `swapfile = false` is gone), so a crashed nvim's unsaved edits survive into a fresh respawn of the same project. They live in a DURABLE, Wolf-owned, PER-PROJECT swap directory rather than next to the user's files: when `vim.env.WOLF_SWAP_DIR` is non-empty, `opt.directory = swap_dir .. "//"`. `WOLF_SWAP_DIR` is exported by core (resolved like [`state.rs::state_dir()`](../../crates/wolf-core/src/state.rs), STABLE across respawns of the same project — see [`swap_dir_for`](../../crates/wolf-core/src/state.rs)), and the trailing `//` makes nvim encode the FULL path into each swap-file name (so identically-named files in different dirs never collide) AND DROPS the default leading `.` entry (which would otherwise land a `.swp` next to the file). Neovim's default `updatecount` / `updatetime` are kept (the `-n` flag that would have zeroed `updatecount` was removed). **Other hermetic settings** — `shadafile = "NONE"`, `undofile = false`, `backup = false`, `writebackup = false` — still hold; only swap changed. **Unsaved-edit loss window (documented limit):** a SIGKILL / OOM skips Neovim's `preserve_exit`, so only edits synced to the swap BEFORE the kill (per the default `updatetime` / `updatecount`) are recoverable — recovery is "as close as possible", not guaranteed to the last keystroke. **Unnamed buffers are out of scope for Tier-1 restore** (only file-backed buffers are mirrored — see `wolf_setup_open_files` below).
- **Recovery-aware `SwapExists` policy (the `WolfSwap` augroup)** — the autocmd must NEVER surface the blocking E325 "swap file exists" prompt, and (unlike the old blanket `swapchoice = "e"`) it now RECOVERS a crashed nvim's edits when it can. It reads `vim.v.swapname`, `vim.fn.swapinfo(swapname)`, and `local uv = vim.uv or vim.loop`, then decides whether the swap's owner is DEAD: a non-table / `info.error` swap (stale/unreadable) is dead; an `info.host` present and `~= vim.fn.hostname()` (written on ANOTHER machine, so the pid cannot be probed) is UNCERTAIN → not dead; a numeric `info.pid > 0` is probed with `uv.kill(pid, 0)` (signal 0 succeeds iff the process is alive → ALIVE; `ESRCH` / any failure → DEAD); anything else (no usable owner pid) is dead. A DEAD owner sets `vim.v.swapchoice = "r"` (silently RECOVER the unsaved edit) plus a `vim.schedule`d `pcall(vim.fn.delete, swapname)` to clean up the consumed swap after recovery; a LIVE / UNCERTAIN owner sets `vim.v.swapchoice = "e"` (edit the clean on-disk copy anyway). No blocking prompt is ever raised.
- **External-file reload (`autoread`)** — `autoread = true` plus a `WolfAutoRead` augroup whose autocmd runs `:checktime` on `FocusGained`, `BufEnter`, `CursorHold`, and `CursorHoldI`. This is the read-side complement to the hermetic write-side settings above: a file edited from OUTSIDE the editor (`prettier --write`, which this repo runs after every Markdown edit, or a `git checkout`) is reloaded into its buffer rather than leaving the user staring at stale text until a manual `:e`. `autoread` alone only re-reads on some of Neovim's own triggers, so the augroup DRIVES `:checktime` on the events that matter — buffer entry (switching back to a backgrounded buffer that changed, e.g. focusing the editor pane after using the terminal drawer), idle (`CursorHold`/`CursorHoldI`, the eventual catch-all after `updatetime`), and `FocusGained` (focus regain — the "edit externally, come back" flow). **`FocusGained` is live on macOS:** the macOS front-end forwards OS app focus into the captive Neovim via `nvim_ui_set_focus` — `AppDelegate.applicationDidBecomeActive` pushes focus GAINED (and `applicationWillResignActive` pushes focus LOST so each activate is a genuine transition, since nvim only fires `FocusGained` on a real unfocused→focused edge) through `WolfCore::set_ui_focus` → the `SetUiFocus` input event → `nvim_ui_set_focus`. So reactivating Wolf (e.g. Dock click) after an external tool changed the file fires `FocusGained` → `:checktime` → instant-on-refocus reload. GNOME does not wire this yet (no window-active signal forwarded to core), so on Linux the reload is driven by `BufEnter` and `CursorHold`/`CursorHoldI` until the same `set_ui_focus` call is wired there. The **guard** is `:checktime`'s own contract: it re-reads ONLY a buffer whose in-editor copy is UNMODIFIED, so a user's unsaved edits are never clobbered — a buffer changed on BOTH sides falls through to Neovim's normal `W12` warning instead of a silent overwrite. It is also **harmless on special buffers**: `:checktime` is a no-op on a buffer with no associated file, so the `buftype=terminal` drawer and the `buftype=nofile` preview scratch are unaffected; the callback is additionally `pcall`-wrapped and `silent!`ed so a special buffer can neither raise nor pollute the deterministic grid. `updatetime` is left at its default (4000ms) — lowering it globally has side effects, and the buffer-entry / idle paths already cover the common flow.
- **Clean initial grid** — `shortmess += "I"` suppresses the intro message so it does not pollute the first frame.
- **True color** — `termguicolors = true`, so `hl_attr_define` / `default_colors_set` carry RGB values the front-ends paint directly.
- **Chrome-free, deterministic grid** — `number = false`, `signcolumn = "no"`, `ruler = false`, `showcmd = false`, `laststatus = 0` (the front-end draws its own chrome).
- **Soft-wrap (word boundaries)** — `wrap = true` with `linebreak = true`, so long Markdown lines wrap at spaces/punctuation rather than running off-screen or breaking mid-word. Determinism-sensitive rendering tests keep their content within the grid width, so column assertions stay stable.
- **Smooth scroll** — `smoothscroll = true`, so scrolling (mouse wheel, `<C-e>`/`<C-d>`) moves by SCREEN line rather than jumping past a whole wrapped logical line — pairs with soft-wrap to keep long wrapped Markdown lines from skipping fragments while scrolling.
- **Mouse** — `mouse = "a"`; the front-end translates OS mouse events into core input, which forwards them to Neovim.
- **Completion popup presentation** — `wildoptions:append("pum")`, so command-line completion presents as a VERTICAL popup (`popupmenu_show`, which the native `ext_popupmenu` completion popup anchors above the command line) rather than the horizontal wildmenu. Wolf attaches the UI with `ext_linegrid` + `ext_multigrid` + `ext_popupmenu` + `ext_messages` (+ `rgb`); `ext_messages` IMPLICITLY enables `ext_cmdline` and forces `cmdheight=0`, so the outer grid 1 empties (there is no grid-drawn command-line strip) and the front-ends paint the command line / completion popup / messages natively from `Snapshot.cmdline` / `Snapshot.pum` / `Snapshot.toast` (see [`src/redraw.rs`](../../crates/wolf-core/src/redraw.rs)). The attach flags are set core-side in [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `ui_attach`, not in `init.lua`.
- **Markdown** — `.md` files are mapped to the `markdown` filetype, and `syntax on` enables built-in syntax highlighting so the grid carries varied `hl_id`s.
- **Vendored orlando plugin (conditional load)** — `init.lua` self-locates its own directory and looks for a sibling `orlando/` tree. When present — the case in the macOS `.app` bundle, where `//bazel/orlando` lands the plugin at `Contents/Resources/orlando/` next to this `init.lua` — it is prepended to `runtimepath` and `plugin/orlando.lua` is sourced deterministically (necessary because `--clean` does not scan plugin dirs, so a plain `runtimepath` prepend alone would not auto-source it; orlando guards on `vim.g.loaded_orlando`, so the explicit source is safe). When absent (Linux/cargo, and any test that does not stage it) the whole block is a strict no-op — no `runtimepath` change, no error. orlando's markdown `wrap_indent` is **additive** to the wrap / linebreak / smoothscroll settings above (it also sets `wrap` / `linebreak` / `breakindent`), so it is harmless alongside them.
- **Vendored lighthouse colorscheme (conditional activation)** — `init.lua` self-locates its own directory and looks for a sibling `lighthouse/` tree. When present — the case in the macOS `.app` bundle, where `//bazel/lighthouse` lands the colorscheme at `Contents/Resources/lighthouse/` next to this `init.lua` — it is prepended to `runtimepath`, then `vim.o.background = "dark"` is set and `vim.cmd.colorscheme("lighthouse")` is run to activate it. Unlike orlando, lighthouse is a **colorscheme** (`colors/lighthouse.lua`), NOT a plugin: a colorscheme on `runtimepath` is inert until it is explicitly selected, so putting the dir on `runtimepath` alone does nothing — `init.lua` must ALSO activate it (`:colorscheme` finds `colors/lighthouse.lua` on `runtimepath`, so no explicit source of the colors file is needed). Ordering matters: this activation runs **after** `syntax on`, because both `:colorscheme` and `syntax on` clear/redefine highlight groups, so the colorscheme must win by running last; `vim.o.background` is set **before** `:colorscheme` so a dual-variant scheme reads it. When absent (Linux/cargo, and any test that does not stage it) the whole block is a strict no-op — no `runtimepath` change, no `:colorscheme` call, no error. Switching dark/light from the OS appearance preference is now **implemented**: the front-end pushes the resolved appearance to nvim via `:set background=…` (`WolfCoreHandle::set_background`) at launch and, in `auto` mode, live whenever the OS toggles (driven by the user-level `appearance` config key). The hardcoded `vim.o.background = "dark"` here is the **pre-push fallback** (the value shown until the front-end's first push); its comment at ~106-107 notes the same.
- **Vendored treesitter markdown highlighting + fenced-code injection (conditional enablement)** — `init.lua` self-locates its own directory and looks for sibling trees. When the `nvim-treesitter/` queries provider is present — the case in the macOS `.app` bundle, where `//bazel/nvim-treesitter` + `//bazel/treesitter-parsers` land `Contents/Resources/nvim-treesitter/` and `…/parsers/` next to this `init.lua` — the block **enables treesitter**: it prepends `nvim-treesitter/` (the `queries/<lang>/highlights.scm` + `queries/markdown/injections.scm` provider) to `runtimepath`, then prepends `parsers/` (so nvim resolves `<rtp>/parser/<lang>.so` for the embedded fenced languages) and the inert `nvim-treesitter-textobjects/` tree, each only if it independently exists. `markdown` / `markdown_inline` parsers already ship with nvim, so they are NOT re-vendored. It does NOT call nvim-treesitter's `.setup{}` (its `:TSInstall` machinery is non-deterministic under `--clean`); the plugin is used purely as an on-`runtimepath` query provider. A `WolfTreesitter` augroup registers a `FileType=markdown` autocmd that runs a **pcall-wrapped** `vim.treesitter.start(buf)` (a query-loader incompatibility degrades to `syntax on` rather than raising), plus an emit-once loop over already-loaded markdown buffers — so `:e doc.md` lights markdown highlighting AND routes fenced blocks (e.g. a ` ```go ` block) through the injections query on `runtimepath`. The injection is **core-native, capture-based**: it comes from nvim-treesitter's `main`-branch `queries/markdown/injections.scm`, which is why the plugin is pinned to `main` (master's `#set-lang-from-info-string!` predicate is incompatible with nvim 0.12.3's query-match API — see [`bazel/nvim-treesitter/README.md`](../../bazel/nvim-treesitter/README.md)). When the `nvim-treesitter/` sibling is absent (Linux/cargo, and any test that does not stage it) the whole block is a strict no-op — no `runtimepath` change, no autocmd, no error, and `syntax on` remains the highlight source. The `nvim-treesitter-textobjects/` tree is bundled-but-**inert**: it is only prepended to `runtimepath` (no source, no `.setup{}`, no keymaps).

### Current-file tracking — `_G.wolf_setup_current_file_tracking(chan)`

`init.lua` defines a global helper that `wolf-core` invokes over RPC **after** `ui_attach`, passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_current_file_tracking`). It is the front-end's only way to learn the active buffer's path, which the GNOME file-tree sidebar uses to highlight and reveal the current file (including after a Neovim-driven `:e`), plus the active buffer's **filetype**, which drives `Snapshot.is_markdown_active()` (the Preview command's enable gate), a **preview flag**, which drives `Snapshot.is_preview_active()` (the Edit command's enable gate), and a **full-width flag**, which drives `Snapshot.is_full_width_active()` (the "Use full width for content" menu checkmark).

The helper:

- creates a `WolfCurrentFile` augroup (`clear = true`, so re-invoking is idempotent);
- registers a `BufEnter` / `BufWinEnter` / `BufFilePost` / `FileType` autocmd whose callback does `vim.rpcnotify(chan, "wolf_current_file", vim.fn.expand("%:p"), vim.bo.filetype, false, vim.b[buf].wolf_full_width == true)` — i.e. notifies core of the active buffer's absolute path, its filetype, a 3rd boolean marking whether it is a preview buffer (`false` for a normal buffer), AND a 4th boolean carrying the buffer's `b:wolf_full_width` flag, on every buffer switch / rename / FileType detection (`FileType` is in the event list so the filetype tracks the active buffer even when detection lands after the buffer switch);
- emits once immediately (the same `rpcnotify`) so the startup buffer is reflected without waiting for a buffer switch;
- exposes its local `emit` closure as `_G.wolf_emit_current_file` (it closes over `chan`) so `wolf_open_preview` can re-emit it at its end. `wolf_open_preview` calls BOTH `_G.wolf_emit_previews` and `_G.wolf_emit_current_file` after any placement (all modes), so the front-end learns a background-window (reuse) rebind AND the current buffer's true filetype is re-asserted — otherwise the transient `BufEnter` / `BufWinEnter` events the background `nvim_win_set_buf` fires while the preview scratch buffer is momentarily current would leave `wolf_current_file("", "", true, full_width)` as the last emission and `Snapshot.is_markdown_active()` stuck false.

An **unnamed buffer** yields an empty string from `expand("%:p")`, which core maps to "no current file" (`Snapshot.current_file = None`). Core canonicalizes any non-empty path before storing it, folds the second arg into `Snapshot.current_filetype`, folds the third (boolean) arg into `Snapshot.current_is_preview`, and folds the fourth (boolean) arg into `Snapshot.current_is_full_width`. A **preview scratch buffer** (carrying `b:wolf_preview_source`, below) is **SKIPPED as a real file** but reports itself as a preview: the callback short-circuits to `vim.rpcnotify(chan, "wolf_current_file", "", "", true, full_width)` for it — where `full_width` is the SOURCE buffer's `b:wolf_full_width` flag (OQ-1), so the checkmark tracks the DOCUMENT rather than the scratch — so core never sees the `Preview: <name>` scratch name as a real current file and never reports markdown-active for the (non-markdown) preview pane, while `Snapshot.is_preview_active()` becomes true (the Edit command's gate) — markdown-active and preview-active are never both true. The channel id is passed as a Lua **vararg** (`...`) from the `nvim_exec_lua` call, never interpolated into the code string.

### Per-window buffer tracking — `_G.wolf_setup_buffer_tracking(chan)`

A global helper that `wolf-core` invokes over RPC **after** `ui_attach` and current-file tracking, passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_buffer_tracking`). Where current-file tracking reports a single GLOBAL active-buffer path, this reports what EVERY window of the current tabpage is showing — so the macOS front-end can draw a **per-pane statusbar** keyed by window handle AND core can derive a **per-pane navigation-history target**.

The helper:

- creates a `WolfBuffers` augroup (`clear = true`, so re-invoking is idempotent);
- registers a `BufEnter` / `BufWinEnter` / `BufFilePost` / `WinEnter` / `WinNew` / `WinClosed` / **`TermOpen`** autocmd whose callback ARMS a coalesced emit (below); the scan iterates `nvim_list_wins()` and builds a list of FIVE-element tuples `{ win, nvim_buf_get_name(buf), buf, is_terminal, is_drawer }` (via `nvim_win_get_buf(win)`), SKIPPING any window whose buffer carries `b:wolf_preview_source` (below), then does `vim.rpcnotify(chan, "wolf_buffers", list)`;
- emits once immediately so the startup window layout is reflected without a change;
- exposes its `emit` closure as `_G.wolf_emit_buffers` so `wolf_suppress_buffers` can re-emit the settled state once a multi-step window build finishes.

The tuple elements:

1. `win` — the window handle (the map key on both sides).
2. `name` — `nvim_buf_get_name(buf)`; absolute for a file buffer, EMPTY for an unnamed one.
3. `buf` — the buffer NUMBER, so core can track an unnamed buffer's identity (`Untitled { bufnr }`) across navigation.
4. `is_terminal` — `vim.bo[buf].buftype == "terminal"`.
5. `is_drawer` — whether this is the per-project terminal DRAWER, which is EXCLUDED from navigation history (a `:terminal` in a NORMAL split is NOT). Read from the BUFFER tag (`b:wolf_terminal`, set at drawer creation and carried by the shared terminal buffer forever) OR'd with the WINDOW tag (`w:wolf_terminal`, set on the drawer window right after its split) — belt-and-braces, so the drawer stays identifiable even if the shared terminal buffer is ever surfaced elsewhere.

Core folds the payload into TWO sibling maps. `Snapshot.buffers` (win handle → canonicalized buffer path) is UNCHANGED — element 2 only, empty names SKIPPED — so an unnamed window is absent and reports `[No Name]` with an empty path. The parallel `Snapshot.win_buffers` (win handle → `WinBuffer { bufnr, path, is_terminal, is_drawer }`) keeps EVERY window, with `path = nil` for an unnamed one, and is what the navigation-history fold derives from. Both are WHOLESALE-REPLACED on each emit so stale/closed windows drop out (neither bumps `seq`; the emit wakes the front-end). A **preview scratch pane** (`b:wolf_preview_source`) is omitted from the list entirely, so core never tracks the bogus scratch name as a real per-window path — the front-end overlays a web view and paints its own `Preview: <name>` statusbar for it — and this skip is ALSO what keeps `win_buffers` and `previews` DISJOINT, which the history fold relies on. `WinClosed` fires while the closing window is still listed by `nvim_list_wins()`, but re-emitting the full current set is still correct: the survivor set replaces the previous one wholesale. A legacy 2-element tuple still decodes core-side (`bufnr: 0`, both flags `false`). The channel id is passed as a Lua **vararg** (`...`), never interpolated into the code string.

**Emits are COALESCED, not synchronous.** Each autocmd only ARMS an emit; the actual window scan + `rpcnotify` runs ONCE, on the next event-loop tick, via `vim.schedule` (an already-armed emit is dropped, and the scheduled callback reads the LATEST state when it runs, so no emit is lost). This is LOAD-BEARING for the per-pane navigation history, which pushes an entry on every observed CHANGE and so must never see a half-built window. `:terminal` fires `BufEnter` (a brand-new UNNAMED buffer), then `BufFilePost` (the name is now `term://…`), and only sets `buftype = "terminal"` by **`TermOpen`** — which is why `TermOpen` had to join the augroup; emitting on each would push `Untitled{n}`, then `Edit("term://…")`, then `Terminal{n}` — three history entries for one user action, whereas coalesced core sees only the settled `Terminal{n}`. Likewise a `botright split` (the terminal drawer) fires `WinNew`/`WinEnter` with the new window still showing the PREVIOUS buffer. Coalescing also collapses the 2–4 identical emits a plain `:e file` produces into one, which keeps stale in-flight notifications from racing a back/forward move. (nvim still fires the driving autocmds across SEVERAL ticks for one navigation, which per-tick coalescing cannot merge — core carries a matching emit-level change filter for that; see `NavHistory::observe`.)

**Mid-build suppression — `_G.wolf_buffers_suppressed` + `_G.wolf_suppress_buffers(fn)`.** A module-level flag, consulted by `emit()` at BOTH arm time and delivery time (a suppressed region may open after an emit was already armed): while it is true, `emit()` returns immediately without notifying core. It exists because a multi-step window build fires `WinNew`/`WinEnter`/`BufEnter` SYNCHRONOUSLY, mid-build, at points where the new window still shows the PREVIOUS buffer or the drawer's terminal buffer is not yet tagged `b:wolf_terminal` — and because core's history fold pushes on every observed CHANGE, an intermediate WRONG emit persists in the pane's stack even if a later emit is correct. The emits must therefore be SUPPRESSED, not corrected afterwards. **LOAD-BEARING:** whoever sets the flag must clear it on EVERY exit path including errors, or per-window buffer tracking dies for the rest of the session — so callers use `_G.wolf_suppress_buffers(fn)`, which sets the flag, runs `fn` under `pcall`, RESTORES the previous value, re-emits ONCE (so core sees the fully-built final state), and only then re-raises any error `fn` raised. It nests safely: the previous value is saved/restored and only the OUTERMOST call re-emits. `_G.wolf_toggle_terminal`'s OPEN path is its one caller (see the terminal-drawer section); the HIDE path needs no suppression — the drawer window is gone, `win_close` prunes it, and the surviving panes' buffers are unchanged, so no push occurs.

### Per-window full-width tracking — `_G.wolf_setup_full_width(chan)`

A global helper that `wolf-core` invokes over RPC **after** `ui_attach` and buffer tracking, passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_full_width`). It reports the **full-width flag** (`b:wolf_full_width`) of the buffer shown in EVERY window of the current tabpage, so the macOS front-end can thread each editor pane's content-width mode (full vs the ~90-char default, centered) into its geometry keyed by window handle.

The helper:

- creates a `WolfFullWidth` augroup (`clear = true`, so re-invoking is idempotent);
- registers a `BufEnter` / `BufWinEnter` / `WinEnter` / `WinNew` / `WinClosed` autocmd whose callback iterates `nvim_list_wins()` and builds a list of `{ win, vim.b[buf].wolf_full_width == true }` pairs (via `nvim_win_get_buf(win)`), then does `vim.rpcnotify(chan, "wolf_full_width", list)`;
- emits once immediately so the startup layout is reflected without a change;
- exposes its local `emit` closure as `_G.wolf_emit_full_width` (it closes over `chan`) so `wolf_toggle_full_width` can re-emit after flipping the flag — a background flip fires no window event.

Core folds the payload into the sibling `Snapshot.full_width` map (win handle → bool), WHOLESALE-REPLACING it on each emit so stale/closed windows drop out (it does NOT bump `seq`; it wakes the front-end); a window ABSENT from the map defaults to `false`. Unlike buffer tracking, preview scratch panes are NOT skipped — a preview pane's own flag is irrelevant (the front-end frames the preview off the SOURCE flag via `wolf_preview`), and an absent window defaults to `false` anyway. The channel id is passed as a Lua **vararg** (`...`), never interpolated into the code string.

### Directory tracking — `_G.wolf_setup_dir_tracking(chan)`

A third global helper that `wolf-core` invokes over RPC **after** `ui_attach`, current-file tracking, and layout setup, again passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_dir_tracking`). It lets core follow Neovim's live working directory so the file picker's global MRU cache (`state_dir()/file-mru.sqlite`) filters to the right project `directory` for BOTH seeding the picker and recording opened files.

The helper:

- creates a `WolfDir` augroup (`clear = true`, so re-invoking is idempotent);
- registers a `DirChanged` autocmd (`pattern = "*"`, covering `:cd` / `:lcd` / `:tcd`) whose callback does `vim.rpcnotify(chan, "wolf_cwd", vim.fn.getcwd())` (no second arg) — i.e. notifies core of the new working directory on every directory change;
- emits once immediately with a distinguishing `true` second arg (`vim.rpcnotify(chan, "wolf_cwd", vim.fn.getcwd(), true)`) so the startup cwd is reflected without a `:cd`.

Core stores this in a sibling `TrackedCwd` cell (NOT the render snapshot, and it does NOT bump the snapshot `seq`), since nvim's cwd is not render state — the `:cd` that triggered it already produces its own redraw flush. The channel id is passed as a Lua **vararg** (`...`), never interpolated into the code string.

The `true` flag on the one-shot INITIAL emit marks it as the passive launch/startup cwd. Core still TRACKS it (updating the `TrackedCwd` cell so `live_cwd` reflects nvim's working directory) but does NOT persist it to `state.json` or record it in the recent-dirs MRU — the launch cwd is not a directory the user opened. Only genuine `DirChanged` events (unflagged — every real `:cd` / `:lcd` / `:tcd`, including the Open-Folder chdir) are mirrored to the per-window state store and recorded in the MRU.

### Theme tracking — `_G.wolf_setup_theme_tracking(chan)`

A fourth global helper that `wolf-core` invokes over RPC **after** `ui_attach`, current-file tracking, layout setup, and directory tracking, again passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_theme_tracking`). It lets a colorscheme drive two app-level colors via the optional highlight groups **`WolfCursor`** (bg = app cursor fill, fg = glyph color) and **`WolfTitlebar`** (bg = macOS titlebar background; fg carried for future title-text coloring). These groups are never painted on the grid, so the redraw stream never carries them — this notification is the only way core learns them.

The helper:

- creates a `WolfTheme` augroup (`clear = true`, so re-invoking is idempotent);
- registers a `ColorScheme` autocmd (`pattern = "*"`, covering `:colorscheme` and `:set background=...`, which re-sources the active scheme) whose callback reads both groups via `pcall(vim.api.nvim_get_hl, 0, { name = ..., link = false })` — `link = false` so a linked group resolves to its target's effective attributes — and does `vim.rpcnotify(chan, "wolf_theme", cursor.fg or -1, cursor.bg or -1, titlebar.fg or -1, titlebar.bg or -1)`;
- emits once immediately (the same `rpcnotify`) so the startup colorscheme is reflected without a theme change.

The payload is **four flat scalars** (each a packed `0xRRGGBB` color or `-1` for an unset channel) rather than a table: an absent/cleared group yields an empty Lua table from `nvim_get_hl`, whose msgpack encoding is ambiguous (map vs. array), so flat scalars with a `-1` sentinel sidestep that entirely (nvim colors are 24-bit, making `-1` unambiguous). Core folds this into `Snapshot.theme` (waking the front-end, no `seq` bump). The pinned lighthouse colorscheme defines both groups. The channel id is passed as a Lua **vararg** (`...`), never interpolated into the code string.

### Split-panes layout — `_G.wolf_setup_layout(chan)`

A second global helper that `wolf-core` invokes over RPC **after** `ui_attach` and current-file tracking, again passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_layout`). Under the split-panes design the **SHELL owns the pane layout**, so Neovim's split / close / focus chords and the `:split` / `:vsplit` / `:close` Ex-commands (plus the `:q` quit family, below) are rebound to report layout **intents** over `rpcnotify` rather than (or in addition to) performing the native window op. The GNOME front-end consumes these intents to create, destroy, and focus native panes.

The asymmetry (decision D4):

- **SPLIT** — `do_split(orient)` captures the window current BEFORE the split, performs the real `:split` (`orient == "h"`, stacked / Horizontal divider) or `:vsplit` (`"v"`, side-by-side / Vertical divider) so nvim creates the window + grid and emits `win_pos`, then `rpcnotify`s `wolf_layout { action = "split", orientation, from, win }` so the shell learns the orientation, the origin window, and the new window.
- **CLOSE** — `do_close()` performs a guarded `nvim_win_close(0, false)` only when more than one window remains in the tab page (so it never closes the last window); the shell observes the removal via the `win_close` redraw event, so **no intent** is emitted.
- **QUIT** — `do_quit({ write, force, all })` routes the `:q` family (`q` / `quit` / `wq` / `x` / `xit` and their banged variants) into the same pane/window model. Write variants (`wq` / `x` / `xit`) run `:write` / `:write!` FIRST and ABORT the quit if the write fails (native parity — a failed `:wq` must not close). With more than one window in the tab page it performs a guarded `nvim_win_close(0, force)` — like CLOSE, **no intent** is emitted (the shell observes the `win_close` redraw event); `force = true` (from a banged `:q!`) discards unsaved changes, `force = false` refuses to discard them (a bare E37 is swallowed by the `pcall`, so the pane silently stays open). On the LAST pane it fires the existing `close_window` registry command (`wolf_command "close_window"`) so the front-end closes the window — EXCEPT a plain `:q` on a MODIFIED buffer, which is REFUSED with a native-style `E37` echo (an unsaved-changes guard preventing data loss; `:q!` overrides). The **`all` flag** brings the quit-ALL family (`qa` / `qall` / `quitall` / `wqa` / `wqall` / `xa` / `xall` and their banged forms) into scope: when `all` is true `do_quit` SKIPS the pane-count check so control ALWAYS takes the close-window branch — the whole front-end window closes (via `wolf_command "close_window"`) regardless of how many panes are open — with the SAME write / force / current-buffer-modified (E37) semantics as `:q`'s last-pane branch. The modified guard stays scoped to the current buffer (`vim.bo.modified`), matching `:q`; it is NOT expanded to scan all panes. On a single pane `:qa` and `:q` are therefore identical (both close the window).
- **FOCUS move** — `do_focus(dir)` is a PURE intent: it does NOT change nvim focus, only `rpcnotify`s `wolf_layout { action = "focus_dir", dir, from }`; the shell resolves the neighbour in its own layout and drives the focus change.
- **DRAWER OPEN** — `emit_drawer(win)` is a report-only intent: it `rpcnotify`s `wolf_layout { action = "drawer_open", win }` (no `from` / `orientation`) for the terminal-drawer window `wolf_toggle_terminal` has already created. The shell renders the drawer as a full-width, root-bottom pane held OUTSIDE its pure `PaneTree`. HIDING the drawer is a guarded `nvim_win_close` the shell observes via `win_close` (no drawer-close intent) — the same asymmetry as CLOSE.

The five helpers are also exposed as globals (`_G.wolf_do_split` / `wolf_do_close` / `wolf_do_quit` / `wolf_do_focus` / `wolf_emit_drawer`) so the Ex-command abbreviations can call them and `wolf_toggle_terminal` can emit the drawer intent over this setup's layout channel (`wolf_emit_drawer` only exists once `wolf_setup_layout` has run, so `wolf_toggle_terminal` calls it under a `if _G.wolf_emit_drawer` guard). `_G.wolf_do_quit` is exposed for symmetry with `wolf_do_close`; the `:q`-family user commands below capture `do_quit` as a closure directly rather than through the global.

Bindings the helper installs:

- **Normal-mode chords (the robust primary path)** via `vim.keymap.set` with `noremap` (so a focus chord is genuinely a no-op on nvim — a pure intent): `<C-w>s` / `<C-w><C-s>` → split `h`; `<C-w>v` / `<C-w><C-v>` → split `v`; `<C-w>c` / `<C-w>q` → close; `<C-w>h` / `<C-w><Left>` → focus left; `<C-w>j` / `<C-w><Down>` → down; `<C-w>k` / `<C-w><Up>` → up; `<C-w>l` / `<C-w><Right>` → right.
- **Terminal-mode chords** so the drawer is keyboard-navigable WITHOUT first leaving terminal-insert: `<C-w>h` / `<C-w>j` / `<C-w>k` / `<C-w>l` → the SAME pure `focus_dir` intent (left / down / up / right), fired from the drawer window (`from` = the terminal window). A `t`-mode function RHS fires the intent without forwarding `<C-w>` to the shell; in practice `<C-w>k` bridges drawer → editor (the others are handled front-end-side, since a full-width drawer has nothing beside it, so `h`/`l` are no-ops there). **TRADEOFF (documented):** these maps SHADOW the shell's `<C-w>` word-erase inside the terminal — accepted per the user's request for a keyboard-navigable drawer.
- **Terminal re-entry autocmd** — a `WolfTerminalInsert` augroup (`clear = true`) with a `WinEnter` / `BufWinEnter` autocmd that `startinsert`s when the entered window shows a `b:wolf_terminal` + `buftype == 'terminal'` buffer, so focusing INTO the drawer via `<C-w>j` re-enters terminal-insert (VS Code parity). Matched on the drawer's identity, so it does NOT yank back from a deliberate `<C-\><C-n>` (same window, no `WinEnter`).
- **Ex-command overrides** via `cnoreabbrev` (the fragile, WHOLE-WORD-only path, guarded by `getcmdtype() == ':'` so it never fires inside a search or a larger command): `split` / `sp` / `new` → split `h`; `vsplit` / `vs` / `vnew` → split `v`; `close` → close; the quit family `q` / `quit` → `WolfQuit`, `wq` / `x` / `xit` → `WolfWriteQuit`; and the quit-ALL family `qa` / `qall` / `quitall` → `WolfQuitAll`, `wqa` / `wqall` / `xa` / `xall` → `WolfWriteQuitAll`. (`:new` / `:vnew` are treated as plain splits.) The quit-family abbrev targets are four INTERNAL `nvim_create_user_command`s — `WolfQuit` (write = false) and `WolfWriteQuit` (write = true) for the `:q` family, plus `WolfQuitAll` (write = false, all = true) and `WolfWriteQuitAll` (write = true, all = true) for the `:qa` family, all `{ bang = true, nargs = 0 }` — NOT registry commands (they are Lua-only plumbing, never added to the `Command` enum / FFI, and distinct from the registry-generated `:WolfClosePane` / `:WolfCloseWindow`). Only the BARE word is abbreviated: `!` is not a keyword character, so typing `:q!` fires the bare-`q` abbrev (`getcmdline() == 'q'` still true), expands `q` → `WolfQuit`, and the trailing `!` rides through to `:WolfQuit!` — a valid banged invocation whose callback maps `o.bang` → `force`. The `:qa` family works the same way (the trailing `!` rides through to `:WolfQuitAll!` / `:WolfWriteQuitAll!`), and because `a` is a keyword character `:qa` forms a distinct word that never triggers the bare-`q` abbrev — no collision with `q` / `wq` / `x`. That is why there are intentionally NO `q!` / `quit!` / `wq!` / `qa!` / `wqa!` abbrevs (they would be dead/broken).
- **Active-window tracking** — a `WolfLayout` augroup with a `WinEnter` autocmd that `rpcnotify`s `wolf_active_win` with `nvim_get_current_win()`, emitting once immediately so the startup window is reflected. Core folds this into `Snapshot.active_win`. (Current-file tracking already follows focus via `BufEnter`, so `current_file` tracks the active pane with no extra work.)

Core tolerates any malformed `wolf_layout` payload (it parses to `None` and is dropped). The channel id is passed as a Lua **vararg**, never interpolated.

### Commands — `_G.wolf_setup_commands(chan, commands)`

The last global helper that `wolf-core` invokes over RPC, **after** `ui_attach`, current-file tracking, layout setup, directory tracking, and theme tracking, passing core's own RPC channel id AND the command list (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_commands`). A **command** is a no-parameter, no-return user action. Unlike layout intents, commands are **only user-triggered** (there is no autocmd and no emit-on-attach). `commands` is a list of `{id, ex_command}` pairs — the canonical registry Rust passes in from `wolf-core`'s `COMMAND_SPECS` (e.g. `{"close_window", "WolfCloseWindow"}`). ONE canonical snake_case `id` derives both faces.

The helper:

- seeds `package.loaded["wolf"] = wolf_tbl` — **required** so `require("wolf")` resolves under `--clean` (Lua's `require` consults `package.loaded` first; a plain global would NOT satisfy `require`);
- for each `{id, ex_command}` pair: sets `wolf_tbl[id] = function() vim.rpcnotify(chan, "wolf_command", id) end` (the **Lua face**, `require("wolf").<id>()`) AND calls `vim.api.nvim_create_user_command(ex_command, <same callback>, { nargs = 0, force = true })` (the **Ex-command face**, `:<ex_command>`).

Both faces `rpcnotify` the same `wolf_command` channel with the canonical `id`; core resolves it via `Command::from_id`, folds it onto a drainable queue (no `seq` bump), and wakes the front-end, which maps each command to a native action (on macOS via the NSMenu / `CommandDispatcher`). An unknown id is dropped by core. The captive nvim stays hermetic: only Wolf's own bundled config uses these faces this cut — a user-config keybinding hook is **deferred**. The channel id and command list are passed as Lua **varargs**, never interpolated.

### Tabpage tracking + lifecycle — `_G.wolf_setup_tabs(chan)` and the tabpage helpers

Realizing the **project/tabpage-per-view** model (one captive Neovim = one PROJECT, shared by N front-end views, each view bound to one nvim **TABPAGE**), `init.lua` defines module-level tabpage helpers plus a setup helper `wolf-core` invokes over RPC **after** command registration, passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_tabs`). Wolf owns ALL tabpage lifecycle (create / close / switch) from the front-end.

`_G.wolf_setup_tabs(chan)`:

- creates a `WolfTabs` augroup (`clear = true`) with a `TabEnter` / `TabNewEntered` autocmd that `rpcnotify`s `wolf_tabpage` with `nvim_get_current_tabpage()`, plus one initial emit — so core's `Snapshot.current_tabpage` tracks the current tabpage (the cheap refocus gate the macOS front-end polls);
- registers a SECOND autocmd in the same `WolfTabs` augroup — on `DirChanged` / `TabNewEntered` / `TabClosed`, plus one initial emit — running an `emit_tab_cwds()` closure that iterates `nvim_list_tabpages()`, maps each handle to its NUMBER via `nvim_tabpage_get_number` (`pcall`) and reads its tab-local cwd via `getcwd(-1, n)` (`pcall`; falls back to the global cwd for a tab never `:tcd`'d), and `rpcnotify`s `wolf_tab_cwds` with a list of `[tabpage_handle, cwd]` pairs for ALL tabpages. Core WHOLESALE-REPLACES its `Snapshot.tab_cwds` map from this (a closed tab drops out — `TabClosed` cannot report the closed handle, so the replacement is how they are pruned), letting `WolfCore::cwd_for_tabpage` be a cheap snapshot read (no blocking RPC), authoritative even for a NON-current view;
- **locks out (OD4)** the nvim-internal tabpage NAVIGATION chords by `vim.keymap.set`-ing `gt` / `gT` / `<C-w>gt` / `<C-w>gT` / `<C-PageUp>` / `<C-PageDown>` → `<Nop>` (a user switching a tabpage out from under a view would desync the front-end-authoritative current view);
- **best-effort intercepts** the typed tabpage CREATION / mutation Ex-commands `:tabnew` / `:tabnext` / `:tabprevious` / `:tabonly` / `:tabclose` / `:tabmove` via `cnoreabbrev <expr>` (guarded by `getcmdtype() == ':'` and a WHOLE-WORD `getcmdline()` match, expanding to an empty command line so `<CR>` is a no-op) — a user-typed `:tabnew` would create an ORPHAN tabpage no view is bound to. The per-view cwd commands `:tcd` / `:tcd!` / `:lcd` / `:cd` are DELIBERATELY NOT caught: they are different WORDS from the `:tab*` commands, so the whole-word abbrevs never fire on them (`:tcd` is how each view sets its own cwd).

The module-level helpers (defined regardless of setup ordering) that `wolf-core`'s tabpage methods drive over `nvim_exec_lua`:

- `_G.wolf_create_tabpage(cwd)` — `tabnew`, then `:tcd fnameescape(cwd)` when `cwd` is non-empty (an empty/nil `cwd` leaves the new tab at the global cwd — the empty-state view), returning the new tabpage's STABLE handle (`nvim_get_current_tabpage()`).
- `_G.wolf_close_tabpage(handle)` — resolves the STABLE handle to its CURRENT tabpage NUMBER (numbers renumber as tabs open/close) and runs `<n>tabclose` inside a `pcall`, swallowing a last-tabpage `E784` (the front-end never closes the LAST view — the project shuts the whole nvim down instead); a stale/invalid handle degrades to a no-op via the guarding `pcall`.

**Residual v1 limitations (accepted, per OD4):** the lockout is best-effort — obscure typed variants / user-defined command abbreviations of the `:tab*` commands (or scripted `nvim_*` tabpage calls) are NOT caught, so a determined user could still create/switch/close a tabpage out from under the front-end. `:tcd`/`:lcd`/`:cd` are intentionally left open. The channel id is passed as a Lua **vararg**, never interpolated.

### Pane-layout rebuild — `_G.wolf_rebuild_layout(spec_json)`

A module-level global (defined alongside the tabpage helpers) that backs the macOS front-end's pane-layout RESTORE: `WolfCore::rebuild_layout` invokes it over `nvim_exec_lua("return wolf_rebuild_layout(...)", [spec_json])`, passing the spec as a Lua **vararg** (a JSON STRING, never interpolated) that the helper `vim.json.decode`s. It realizes a saved pane-split tree in the current tabpage's single starting window and RETURNS the resulting window handles in DFS/leaf order (a malformed / undecodable `spec_json` returns `{}`).

The decoded `spec` is the same shape `PaneLayoutCodec.specJSON` emits: a **leaf** is `{ leaf = true, path = "<abs path or empty>", preview = true|false }`; a **split** is `{ orientation = "v"|"h", weights = {...}, children = {...} }`. A recursive `realize(node)`:

- for a **leaf**: when `preview == true` and `path` is non-empty, recreates a Markdown preview of that SOURCE file IN the current window via `wolf_preview_file(win, path)` (bufadd/bufload/markdown-gate + `nvim_win_set_buf`, converting the window into a preview WITHOUT creating/destroying it, so the handle is intact for DFS correspondence; a missing/non-md source degrades to the inherited buffer but still returns the handle); else when `path` is non-empty, `:edit fnameescape(path)`; else leaves the window on its inherited unnamed buffer — and returns `{ current_win }`;
- for a **split** of `n` children, creates `n` region windows starting from the current window — each new one placed to the RIGHT (`rightbelow vsplit` for `orientation == "v"`) or BELOW (`rightbelow split` otherwise) of the previous, so regions read left-to-right / top-to-bottom (**child 0 first**) — then recurses into each region in order, gathering the DFS leaf handles.

nvim produces only the WINDOW COUNT + TOPOLOGY + per-window BUFFER; pane SIZES are irrelevant here (the front-end drives them from its own weights via `syncGridSizes`). The **child-0-first** region order is load-bearing: it MUST match the front-end `PaneTree.rebuilt`'s DFS leaf order so each returned handle zips to its rebuilt leaf.

### Tier-1 open-file mirror — `_G.wolf_setup_open_files(chan)`

Backing the **crash/stall restart's file restore**, `wolf-core` invokes this over RPC after the tabpage setup, passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_open_files`). It notifies core of the file-backed buffers open in the project so the mirror survives nvim death Rust-side, and the front-end can reopen those files after a crash-restart respawns the nvim.

The helper installs a `WolfOpenFiles` augroup (`clear = true`) with a `BufEnter` / `BufWinEnter` / `BufWritePost` / `BufFilePost` / `BufDelete` / `WinEnter` / `TabEnter` / `TabNewEntered` / `TabClosed` autocmd (plus one initial emit) that `rpcnotify`s `wolf_open_files` with a list of `{ tp_handle, active_path, files }` triples, one per tabpage over `nvim_list_tabpages()`. Core WHOLESALE-REPLACES its `Snapshot.open_files` map (tabpage handle → `TabFiles { active, files }`) from this (no `seq` bump; it wakes the front-end), read per-tabpage by [`WolfCore::open_files_for_tabpage`](../../crates/wolf-core/README.md) BEFORE a restart.

**KNOWN Tier-1 LIMITATION (implemented deviation — global file set):** `files` is the whole nvim instance's file-backed buflisted buffer set — `vim.fn.getbufinfo({ buflisted = 1 })` filtered to non-empty names that are NOT preview scratch buffers (`b:wolf_preview_source`) and not unnamed. Because `getbufinfo` is GLOBAL to the nvim instance (buffers are shared across tabpages), this SAME file set is attached to EVERY tabpage triple; only `active_path` (the tabpage's active window's buffer name, empty for an unnamed buffer) is genuinely per-tabpage. The upside is robustness — the set survives an `:edit` that hides (but keeps listed) an earlier buffer, which a per-window scan would miss. The consequence, accepted for Tier-1: a **multi-view / multi-tabpage project restart reopens every project file in every view** (each view's active/focused file is still correct, since `active_path` is per-tabpage). Per-tab file attribution is deferred beyond Tier-1.

### Buffer-picker view tracking — `_G.wolf_setup_view_tracking()`

The FINAL global helper `wolf-core` invokes over RPC, **after** command registration and tabpage setup (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `setup_view_tracking`). It backs the buffer picker's **per-pane scroll/cursor restoration**, and it is a deliberate ASYMMETRY with every helper above: it takes **NO channel id** and emits **NO `rpcnotify`** — it maintains an in-nvim view cache and defines the switch helper that reads it, so **no view/scroll payload ever crosses the FFI boundary** and core stays view-agnostic (it is NOT an out-of-band notification into the snapshot).

The helper holds an upvalue `local view_cache = {}` keyed `view_cache[win][buf] = winsaveview()` (a per-`(winid, bufnr)` cache — each pane remembers its OWN scroll of a shared buffer), and:

- creates a `WolfView` augroup (`clear = true`, so re-invoking is idempotent);
- registers a `BufLeave` / `WinLeave` autocmd that captures the view of the pane/buffer being LEFT: `win = nvim_get_current_win()`, `buf = nvim_win_get_buf(win)`, `view_cache[win][buf] = vim.fn.winsaveview()`;
- registers a `WinClosed` autocmd that PRUNES a closed window's whole cache (`view_cache[tonumber(ev.match)] = nil`, keyed on the closing window id);
- defines `_G.wolf_switch_buffer(win, buf)` (closing over `view_cache`), the helper `wolf-core`'s `InputEvent::SwitchBuffer` invokes via `nvim_exec_lua("wolf_switch_buffer(...)", [win, bufnr])`.

`_G.wolf_switch_buffer(win, buf)` does a **window-scoped** `nvim_win_set_buf(win, buf)` (NOT `:edit` — so it does not disturb `current_file` / the file-MRU or re-read from disk), then restores the pane's view keyed on `(win, buf)`: if `view_cache[win][buf]` exists it `nvim_win_call`s `winrestview(cached)`, ELSE it forces the top of the buffer (`winrestview{ lnum = 1, col = 0, topline = 1, leftcol = 0 }`). There is **NO per-`bufnr` fallback**: a buffer seen only in OTHER panes opens at the top, never borrowing another pane's scroll. The whole body is wrapped in `pcall`, so a stale `bufnr` degrades to a no-op — and it now **RETURNS that `pcall`'s `ok` flag** (`true` on success, `false` when the bind or the view restore threw). Every pre-existing caller (`InputEvent::SwitchBuffer`, over a bare `nvim_exec_lua` chunk with no `return`) IGNORES the value, so this only ADDS information; `wolf_history_set_buf` (below) CONSUMES it, so a silently failed bind is reported to core as a `0` rather than a false success. The macOS `BufferPickerView` activation reaches this through `WolfCoreHandle::switch_buffer(bufnr)` (which resolves the active window live).

### Navigation-history helpers — `_G.wolf_history_set_buf(win, bufnr)` and `_G.wolf_history_open(win, path)`

Two module-level globals defined immediately AFTER `wolf_setup_view_tracking` (so `_G.wolf_switch_buffer` exists to delegate to). `wolf-core` calls them over `nvim_exec_lua` from `WolfCore::history_back` / `history_forward` / `history_jump` to move ONE pane to a previously-visited target (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `history_open` / `history_set_buf`). Like `wolf_switch_buffer` they take **NO channel id**. Both are **WINDOW-SCOPED** (`nvim_win_set_buf` via `wolf_switch_buffer`, plus that pane's saved-view restore), **NEVER `:edit`** — no disk re-read, no `current_file` / file-MRU churn — and both return the bufnr actually bound (`> 0`) or `0`; core turns a `0` into a history-cursor REVERT, so a target that no longer exists never silently drifts the pane. A `Preview` history target does NOT go through these — it re-uses the existing `_G.wolf_preview_file` link-follow path.

**`_G.wolf_history_set_buf(win, bufnr)`** binds `bufnr` into `win` and restores that pane's saved view for it. It returns `0` when either handle is nil/zero, when `nvim_win_is_valid(win)` or `nvim_buf_is_valid(bufnr)` fails (most commonly a buffer `:bwipeout`ed since it was recorded), or when the BIND ITSELF failed. That last case matters: `wolf_switch_buffer` wraps its whole body in `pcall`, so an `nvim_win_set_buf` that throws AFTER the validity checks — the cmdwin is open, the window is `'winfixbuf'`, or the outgoing buffer is modified and cannot be abandoned — is silent; propagating `wolf_switch_buffer`'s `ok` flag as a `0` is what makes core revert the cursor instead of leaving it pointing at a pane that never moved. (`wolf_switch_buffer` now RETURNS that flag; every pre-existing caller ignores the value, so this only ADDS information.) On success it calls `_G.wolf_emit_previews()` + `_G.wolf_emit_current_file()` (both guarded, both idempotent), mirroring `wolf_preview_file` / `wolf_edit_source`, then returns `bufnr`.

**`_G.wolf_history_open(win, path)`** binds the buffer for the ABSOLUTE `path` into `win`, loading it if needed, and delegates the bind + view restore + re-emits to `wolf_history_set_buf`. It returns `0` for a nil/empty path or an invalid window. Resolution is two steps, in this order:

1. Scan `nvim_list_bufs()` for an ordinary FILE buffer (`buftype == ""`, which skips preview scratch panes, terminals and quickfix — none of which is ever an `Edit` target — and keeps the `resolve()` calls off non-file names) whose `nvim_buf_get_name(b)` EQUALS, or `vim.fn.resolve()`s to, `path`; `bufload` it and use it. `path` was canonicalized by `std::fs::canonicalize` core-side, so under a symlinked project root (`~/Projects` → `/Volumes/work/projects`) it can differ from the name nvim kept, and `bufadd` alone would then bind a DIFFERENT buffer re-read from disk — unsaved edits invisible, and a `bufload` against a live swapfile can raise nvim's ATTENTION prompt. (nvim closes most of that gap itself — `buflist_new` matches an existing buffer by FILE ID, so a divergent name still finds the same buffer whenever the file exists on disk — but a NEVER-WRITTEN buffer has no file id and is matched by name only, which is exactly the unsaved case. This scan makes the rebind independent of which mechanism applies.)
2. Only if nothing matched, `vim.fn.bufadd(path)` + `bufload`.

**LOAD-BEARING:** rebinding the EXISTING buffer — never a fresh one — is what makes navigating back to an unsaved `Untitled N.md` (which HAS a real cwd-joined name, see `wolf_name_untitled` below) restore that same MODIFIED buffer rather than reading a file that was never written to disk. A file that has since been DELETED from disk still binds successfully, as an empty `[New]` buffer — exactly what a plain `:e missing.md` does — so Back to a deleted file reports success rather than reverting.

### Anonymous-buffer naming — `_G.wolf_next_untitled`, `_G.wolf_name_untitled`, `_G.wolf_new_untitled`, `_G.wolf_name_untitled_current`, and the `WolfUntitled` `VimEnter` autocmd

Every new/empty editable buffer is given a real, UNSAVED markdown name so the in-app preview gate (`wolf_open_preview`, which no-ops unless `filetype == "markdown"`) passes and the front-end shows a real title instead of `[No Name]`.

**`_G.wolf_next_untitled(cwd, exclude_buf, extra_collision) -> (name, abspath)`** is the pure name generator. It loops `i = 1, 2, 3, …`, forming `name = (i == 1) and "Untitled.md" or ("Untitled " .. i .. ".md")` — index 1 is the un-numbered `Untitled.md`, so the literal `Untitled 1.md` is NEVER generated — and `abspath = cwd .. "/" .. name`. It returns the first index colliding with neither a file/dir on disk (`(vim.uv or vim.loop).fs_stat(abspath) ~= nil`) NOR any existing buffer's name (any valid `b ~= exclude_buf` in `nvim_list_bufs()`, listed OR unlisted / loaded OR unloaded — all can trigger E95 — whose `nvim_buf_get_name(b) == abspath`). The OPTIONAL `extra_collision(abspath) -> bool` predicate (nil for Cmd-N / `Chdir`) counts as an ADDITIONAL collision source; only the `VimEnter` startup naming passes one (swap-existence). Without it the walk does NOT inspect `.swp` swap files. A defensive `< 10000` upper bound with an `hrtime`-suffixed fallback name guards against a runaway loop.

**`_G.wolf_name_untitled(buf, extra_collision)`** names `buf` with the first free Untitled name in `getcwd()` (forwarding the optional `extra_collision` predicate) and sets `vim.bo[buf].filetype = "markdown"`. It does NOT write to disk and does NOT touch `buftype` / `bufhidden` / `swapfile` — the buffer stays a normal, modifiable, `:w`-able document. `nvim_buf_set_name` is `pcall`-wrapped; on an E95 race (the name got taken between the collision walk and the set) it retries the next index (the now-colliding buffer is picked up by the next walk, so the index advances), bailing gracefully after a few attempts rather than raising. Naming fires `BufFilePost` + `FileType`, so the existing current-file / per-window trackers re-emit the new name with no extra wiring.

**`_G.wolf_new_untitled()`** runs `:enew` then `wolf_name_untitled(current buf)`. `wolf-core`'s `InputEvent::NewBuffer` invokes it via `nvim_exec_lua("wolf_new_untitled()")`. Because a named buffer stays buflisted by default (and `:enew` does not wipe it), an earlier `Untitled.md` remains listed, so repeated calls walk the collision sequence `Untitled.md` → `Untitled 2.md` → `Untitled 3.md`.

**`_G.wolf_name_untitled_current(extra_collision)`** is a GUARDED re-home of the CURRENT buffer: it proceeds only when `buftype == ""`, `modified == false`, the buffer is not a preview scratch (`b:wolf_preview_source == nil`), and its name is either empty OR an existing Untitled name (`Untitled.md` / `Untitled N.md`) that is NOT yet on disk — so a real, saved file is never renamed. It forwards the optional `extra_collision` predicate to the naming path (nil from `Chdir`; the swap check only from `VimEnter`). `wolf-core`'s `InputEvent::Chdir` invokes it via `nvim_exec_lua("wolf_name_untitled_current()")` after the `:tcd`, so opening a folder from the empty state re-homes the untouched anonymous buffer to `Untitled.md` in the opened folder.

The module-level **`WolfUntitled` `VimEnter` autocmd** covers first-launch and launch-on-folder: when exactly one buffer is listed it calls `wolf_name_untitled_current(_G.wolf_untitled_swap_exists)`, so the startup buffer becomes `Untitled.md` (in the launch cwd). The guard keeps it off crash-recovery-restored buffers and off a real file opened from the command line.

The STARTUP naming (and ONLY the startup naming) additionally treats an existing Wolf-owned swap file for a candidate name as a collision, via the `extra_collision` predicate threaded through `wolf_name_untitled_current` → `wolf_name_untitled` → `wolf_next_untitled` (nil, i.e. no swap check, for Cmd-N and `Chdir`). **`_G.wolf_untitled_swap_exists(abspath)`** scans `WOLF_SWAP_DIR` and matches on `swapinfo().fname == abspath` — the same swap identity Neovim's own `SwapExists` machinery uses, robust to the `dir//` path-mangled swap filenames. This closes the **restart-shadow** risk: after a crash-restart the fresh nvim names its startup buffer WITHOUT loading it (so `nvim_buf_set_name` never triggers the swap check), and if a crashed nvim left a swap for `<cwd>/Untitled.md`, naming this buffer the same name would shadow the Tier-1 reopen `:e <cwd>/Untitled.md` (it would just switch to the already-named empty buffer, `SwapExists` never fires, unsaved edits lost). Treating the swap as a collision names the fresh startup buffer `Untitled 2.md` instead, so the reopen recovers the crashed edit cleanly into its own buffer. A normal first launch (no pre-existing swap) still yields `Untitled.md`.

### Markdown preview — `_G.wolf_ensure_preview_buf`, `_G.wolf_open_preview(mode)`, `_G.wolf_edit_source(mode)`, `_G.wolf_preview_file(win, path)`, and `_G.wolf_setup_preview(chan)`

Realizing the **live-updating Markdown preview** (OD1 = Design S: a preview pane is a real nvim scratch buffer, not a synthetic front-end pseudo-pane), `init.lua` defines a shared scratch-buffer helper, a module-level open helper `wolf-core`'s `open_preview` drives over `nvim_exec_lua`, an INVERSE edit helper `wolf-core`'s `edit_source` drives the same way, a link-follow helper `wolf-core`'s `preview_file` drives the same way, plus a setup helper `wolf-core` invokes over RPC **LAST** (after `wolf_setup_view_tracking`), passing core's own RPC channel id (see [`src/nvim.rs`](../../crates/wolf-core/src/nvim.rs)'s `render_preview` / `open_preview` / `edit_source` / `preview_file` / `setup_preview`).

**`_G.wolf_ensure_preview_buf(source_buf, source_path)`** creates (or reuses) the preview scratch buffer for `source_buf` (whose absolute path is `source_path`) and returns its bufnr. Factored out of `wolf_open_preview` so `wolf_preview_file` can build the same kind of preview buffer for a file the user navigated to via a link. An upvalue map `_G.wolf_preview_bufs[source_buf] = preview_buf` (keyed by the SOURCE buffer number) makes re-invoking on the same source REUSE its preview buffer; on a miss (or a since-invalidated buffer) it creates one via `nvim_create_buf(true, true)` — `listed = true` (so it surfaces in the buffer picker) + `scratch = true` (the `buftype = nofile` / `bufhidden = hide` / `swapfile = false` defaults) — names it `Preview: <cwd-relative path>` (the cwd-relative path via `fnamemodify(source_path, ":.")`, e.g. `Preview: crates/wolf-macos/README.md`; a file at the cwd root collapses to a bare basename) via `pcall(nvim_buf_set_name, ...)` with an **E95 fallback** to `Preview: <cwd-relative path> (<source_bufnr>)` on a collision with ANOTHER buffer (two sources sharing a cwd-relative path), sets `b:wolf_preview_source` (the source's abs path) + `b:wolf_preview_source_bufnr`, sets `modifiable = false`, and records the reuse-map entry.

**`_G.wolf_open_preview(mode)`** opens (or reuses) the preview pane for the ACTIVE source buffer and returns the preview scratch buffer's number:

- **Markdown gate** — a no-op returning `0` unless `vim.bo.filetype == "markdown"` (the same signal that gates `Snapshot.is_markdown_active()`), so a non-markdown active buffer never opens a preview.
- **Cursor re-emit, BEFORE any placement branch** — immediately after the gate resolves `source_buf`, it calls `_G.wolf_emit_markdown_cursor(source_buf)` (guarded by an `if` so it is a no-op when `wolf_setup_preview` has not run). **The ordering is load-bearing:** for `"split_right"` / `"active"` the placement below does `nvim_win_set_buf(0, preview_buf)`, making the preview SCRATCH the current buffer — emitting after that would hit `emit_cursor`'s preview-scratch guard and bail, leaving the freshly opened preview with no anchor (`source_cursor_line() == 0`) until the user's next cursor move. Emitting first means a newly opened preview scrolls straight to where the user is. (`wolf_preview_file` deliberately does NOT re-emit: its source buffer is a background `bufadd` / `bufload` with no window and no meaningful cursor — see the `win_gettype()` guard below.)
- **Create-or-reuse scratch buffer** — delegated to `_G.wolf_ensure_preview_buf(source_buf, source_path)` (above): the reuse map, the `nvim_create_buf(true, true)` listed+scratch buffer, the `Preview: <cwd-relative path>` naming with its E95 fallback, the `b:wolf_preview_source` / `b:wolf_preview_source_bufnr` vars (what the path-based trackers SKIP and what `wolf_setup_preview`'s window-scan reads), and `modifiable = false` all live in that shared helper.
- **Placement** — a three-way branch on `mode`. For `"split_right"` it first `wolf_do_split("v")` (reusing the layout helper's Vertical-split intent path, so the shell creates + binds a new pane on the RIGHT) then `nvim_win_set_buf(0, preview_buf)`. For `"reuse_preview_pane"` it scans the CURRENT tabpage (`nvim_tabpage_list_wins(0)`) for the OTHER window (`win ~= nvim_get_current_win()`) whose buffer carries a non-empty `b:wolf_preview_source`, binds the preview buffer into that window (`nvim_win_set_buf(target, preview_buf)`) and leaves the active/current window UNTOUCHED — falling back to a current-window bind (`nvim_win_set_buf(0, preview_buf)`, the `"active"` behavior) when no such other preview window exists. For `"active"` (and any unknown mode) it just `nvim_win_set_buf(0, preview_buf)` (replacing the current window's content). It returns `preview_buf` in every branch.

**`_G.wolf_edit_source(mode)`** is the INVERSE of `wolf_open_preview`: it navigates the ACTIVE preview pane back to its SOURCE Markdown file and returns the source buffer's number:

- **Preview gate** — reads `b:wolf_preview_source` (the source's abs path) / `b:wolf_preview_source_bufnr` off the CURRENT buffer and returns `0` immediately unless the current buffer is a preview (the same signal that gates `Snapshot.is_preview_active()`), so a non-preview active pane never navigates.
- **Bind helper** — a local `edit_into(win)` prefers `nvim_win_set_buf(win, source_bufnr)` when the source bufnr is valid (a window-scoped switch — NO disk re-read, NO MRU churn, like `wolf_switch_buffer`), else `nvim_set_current_win(win)` + `:edit fnameescape(source_path)`. **No MRU is recorded.**
- **Placement** — a three-way branch on `mode`. For `"split_left"` it captures `orig = nvim_get_current_win()`, runs `wolf_do_split("v")` (reusing the Vertical-split intent path), `edit_into(orig)`, then `nvim_set_current_win(orig)` — because `PaneTree` inserts the new leaf AFTER the target, binding the source into `orig` puts the EDITOR on the LEFT and the preview on the RIGHT. For `"reuse_editor_pane"` it scans `nvim_tabpage_list_wins(0)` for the first non-current window whose buffer has `b:wolf_preview_source == nil` (a non-preview editor), then `edit_into(target)` + `nvim_set_current_win(target)` (falling back to the current window when none). For `"active"` (and any unknown mode) it `edit_into(0)`, replacing the preview in the current window.
- **Re-emit** — after any placement it re-emits `_G.wolf_emit_previews()` + `_G.wolf_emit_current_file()` (idempotent) and returns the source bufnr.

**`_G.wolf_preview_file(win, path)`** repoints the preview window `win` at the Markdown file `path` (an ABSOLUTE path, resolved by the front-end from a clicked `file://` link), replacing that pane's current preview with a preview of the linked file, and returns the linked file's SOURCE bufnr (`> 0`) on success or `0` on failure. It does NO relative-path resolution — `path` is already absolute:

- **Guards** — returns `0` immediately when `path` is nil/empty or `vim.fn.filereadable(path) == 0` (a missing file).
- **Load + markdown gate** — `bufadd(path)` + `bufload(source_buf)`, then gates the buffer: if its `filetype` is not already `markdown`, asks `vim.filetype.match({ buf = source_buf, filename = path })` and sets `filetype = markdown` when it matches, else returns `0` (a non-markdown file is not previewable — the front-end applies its own O3 fallback).
- **Create-or-reuse + bind** — calls `_G.wolf_ensure_preview_buf(source_buf, source_path)` (the shared helper above) for the linked file's preview buffer, then binds it into `win` via `nvim_win_set_buf(win, preview_buf)` when `win` is nonzero and `nvim_win_is_valid`, else falls back to the current window (`nvim_win_set_buf(0, ...)`).
- **Re-emit** — calls `_G.wolf_emit_previews()` (so the front-end learns the pane now previews the linked file) and `_G.wolf_emit_current_file()` (re-asserting the active source pane's filetype), both idempotent, then returns `source_buf`.

**`_G.wolf_setup_preview(chan)`** installs the `WolfPreview` augroup (`clear = true`, so re-invoking is idempotent):

- a window-scan on `WinEnter` / `BufWinEnter` / `WinNew` / `WinClosed` / `BufWinLeave` whose callback iterates `nvim_list_wins()`, and for each window whose buffer carries a non-empty `b:wolf_preview_source` builds a `{ win, source_bufnr, source_path, source_full_width }` tuple (`source_bufnr` from `b:wolf_preview_source_bufnr or -1`; `source_full_width` the SOURCE buffer's `b:wolf_full_width == true`, `false` when the bufnr is invalid), then does `vim.rpcnotify(chan, "wolf_preview", list)` — one tuple per open preview window. Core WHOLESALE-REPLACES `Snapshot.previews` (keyed by the preview WINDOW handle, the 4th element folded into `PreviewInfo.source_full_width` so the front-end frames the pane capped or full-width by the SOURCE buffer's flag) so closed preview windows drop out. It emits once immediately so an already-open preview is reflected without a window event. The scan closure is exposed as `_G.wolf_emit_previews` (it closes over `chan`) so `wolf_open_preview`, `wolf_edit_source` and the two `wolf_history_*` helpers can re-emit it at their end after a window-scoped bind. (An earlier comment claimed a background-window `nvim_win_set_buf` fires NO window event; probed against the pinned nvim 0.12.3 it DOES — binding into a non-current window leaves focus alone and fires `BufEnter` + `BufWinEnter`, both of which are in this augroup and in the `wolf_buffers` one. The explicit re-emits are RETAINED anyway: they are idempotent — every handler wholesale-replaces its map — and they make the update independent of which events a particular bind happens to fire and of autocmd ordering.)
- markdown-guarded `TextChanged` / `TextChangedI` / `BufWritePost` autocmds whose callback, only when `vim.bo[ev.buf].filetype == "markdown"`, does `vim.rpcnotify(chan, "wolf_markdown_dirty", ev.buf, vim.api.nvim_buf_get_changedtick(ev.buf))` — the `[source_bufnr, changedtick]` live-update signal. Core upserts the tick into `Snapshot.markdown_ticks`; the front-end joins a preview's `source_bufnr` to its tick to decide when to re-pull rendered HTML (via the blocking `WolfCore::render_preview`, debounced through `PickerRefreshCoalescer`).
- `CursorMoved` / `CursorMovedI` / `BufEnter` / `BufWinEnter` autocmds whose callback runs the local closure `emit_cursor(ev.buf)`, which — when FIVE guards all pass — does `vim.rpcnotify(chan, "wolf_markdown_cursor", buf, line, char_col)`: **three FLAT scalars**, mirroring `wolf_markdown_dirty`'s flat `(bufnr, tick)` shape rather than a table, which sidesteps the empty-Lua-table map-vs-array msgpack ambiguity `wolf_setup_theme_tracking` already documents. `line` is `vim.fn.line(".")` (1-based) and `char_col` is `vim.fn.charcol(".") - 1`, clamped at `0`. **`charcol()` is `col()`'s CHARACTER-index twin** — it returns the 1-based CHARACTER index, so subtracting 1 yields directly the 0-based CHARACTER column the `wl-{L}-{C}` marker scheme wants, with **no** byte→character conversion anywhere downstream. (In insert mode past end-of-line `charcol('.')` returns `char_len + 1`, so `char_col == char_len`, one past the last character; the front-end rounds down to a multiple of 100 and falls back, so that is benign.) Core UPSERTS the triple into `Snapshot.markdown_cursors` keyed by the SOURCE bufnr — the same key space as `markdown_ticks` and `PreviewInfo.source_bufnr` — and the front-end joins a preview to its source's cursor to scroll the matching `wl-{line}-{col}` marker into view. The five guards, in order: (1) `buf` is non-nil and `nvim_buf_is_valid`; (2) `buf == nvim_get_current_buf()` — load-bearing, because `line('.')` / `charcol('.')` read the CURRENT WINDOW's cursor, so reporting for a non-current buffer would emit the wrong position; this is what makes the un-winid'd `charcol('.')` unambiguous; (3) `vim.fn.win_gettype() == ""` — see below; (4) `vim.bo[buf].filetype == "markdown"`; (5) `vim.b[buf].wolf_preview_source == nil`, the preview-scratch guard, a deliberate **ASYMMETRY** with the sibling dirty autocmd above (which excludes preview scratches only INCIDENTALLY, because a `nofile` scratch never runs filetype detection so its filetype stays `""`) — here it is EXPLICIT, so a future `:filetype detect` on a `Preview: foo.md`-named scratch can never leak a cursor whose line numbers describe the RENDERED text rather than the source. The closure is exposed as `_G.wolf_emit_markdown_cursor` (it closes over `chan`, exactly like `_G.wolf_emit_previews`) so `wolf_open_preview` can re-emit before it binds, and it is called ONCE at setup beside `emit_previews()` so the startup buffer's cursor is known without waiting for a move.
  - **Why the two BUFFER-ENTRY events, and why the `win_gettype()` guard exists because of them** — both are non-obvious and easy for a refactor to drop. `CursorMoved` / `CursorMovedI` are the steady-state signal, but they are NOT sufficient: probed against the pinned nvim, `:edit foo.md` fires `CursorMoved` BEFORE filetype detection has run (so guard 4 bails) and no further `CursorMoved` fires until the user actually moves — a Markdown buffer that is opened and merely LOOKED at would report no cursor at all, leaving a bound preview with no anchor. `BufEnter` / `BufWinEnter` both fire AFTER detection with the buffer current and its filetype set; the emit is idempotent (core upserts), so their overlap costs one extra notify per open. But those same two events ALSO fire from `vim.fn.bufload()` — which `wolf_preview_file` uses to load a link-navigated source in the background, and which `nvim_buf_call` uses generally — inside nvim's synthetic **AUTOCMD window**, where the target buffer is genuinely current so guards 1, 2, 4 and 5 ALL pass. Measured against the pinned nvim 0.12.3 that window reports `win_gettype() == "autocmd"` and a FABRICATED line 1 / col 1 cursor belonging to no user pane, so without guard 3 a background-loaded source would report a bogus `(1, 0)` anchor for a buffer whose cursor is genuinely UNKNOWN — defeating the front-end's `source_cursor_line() == 0` sentinel (which is what tells it to leave a freshly bound preview's scroll position alone) and fighting the `#anchor` jump of a cross-file link. Only a NORMAL window (`win_gettype() == ""`) carries a real cursor; the guard also rejects floating/popup, command-line, quickfix and loclist windows.

None of the three notifications bumps `seq`; all three wake the front-end. The rendered HTML itself is produced CORE-side by the GUI-free `wolf_core::markdown` module — `init.lua` never renders Markdown, only names the scratch buffer and reports the source, its dirty tick, and its cursor position (and it does no scrolling either — every scroll decision and every line of injected JS lives in the macOS `WolfKeyMap.PreviewScrollSeam`). The channel id is passed as a Lua **vararg** (`...`), never interpolated into the code string, consistent with the other `wolf_setup_*` helpers.

### Code-block syntax highlighting — `_G.wolf_highlight_code_blocks(blocks)`

A **module-level** global (defined regardless of setup ordering, and NOT inside the conditional treesitter block, so it exists on EVERY platform) that backs the Markdown preview's fenced-code-block syntax highlighting. `wolf-core` (crate `nvim.rs`'s `highlight_code_blocks`) invokes it over `nvim_exec_lua("return wolf_highlight_code_blocks(...)", …)` with ONE argument — an array of `{ text, lang }` pairs (`lang` is `""` when the fence declares none) — and it highlights the WHOLE batch in one RPC round-trip, returning an array `results` of the SAME length. It takes **NO channel id** and emits **NO `rpcnotify`**: the highlight data is the return value of a single blocking call, not an out-of-band notification. See [`../../preview-code-block-syntax-highlighting-decisions.md`](../../preview-code-block-syntax-highlighting-decisions.md).

**Return shape.** `results[i]` is either:

- the scalar `false` — the i-th block is NOT highlightable (no/unknown language, missing parser, missing `highlights` query, a parse failure, or no resolved spans at all), OR
- an array of fixed **7-element span tuples** `{ row, start_col, end_col, fg, bold, italic, underline }`. A span is a single-line, non-overlapping BYTE-column run: `row` is 0-based within the block text (`text` split on `"\n"`), `start_col`/`end_col` are 0-based half-open byte columns, `fg` is a packed `0xRRGGBB` integer or `-1` (no foreground), and the three attributes are Lua booleans.

**The `false` sentinel.** The helper NEVER returns an empty Lua table for a block — msgpack cannot tell an empty array from an empty map — so a non-highlightable OR empty-result block is the scalar `false`, and each span is always a full 7-element array. This is the same map-vs-array ambiguity sidestep the `wolf_theme` payload uses (flat scalars + a `-1` sentinel).

**Per-block work (`highlight_one(text, lang)`).** Returns `false` immediately when `lang` is nil/empty, when `vim.treesitter.get_string_parser(text, lang)` fails, when `vim.treesitter.query.get(lang, "highlights")` is nil, or on a parse failure. Otherwise it walks `query:iter_captures` over the parsed root:

- **Capture → color resolution.** Each capture NAME is resolved via `pcall(vim.api.nvim_get_hl, 0, { name = "@"..name, link = false })` — `link = false` so a linked group resolves to its target's effective attributes (the same pattern `wolf_setup_theme_tracking` uses). On an EMPTY result and a DOTTED name it retries against successively trimmed prefixes (`@function.call` → `@function`), matching treesitter's group fallback. A group with no foreground AND no emphasis resolves to `nil` and is skipped (so there is never an empty `<span style="">`). Resolutions are cached per capture name.
- **Precedence.** Captures are applied into a per-line, per-byte winner map; a later capture overwrites an incumbent when its `metadata.priority` is higher, or when priority ties and it appears later in iteration order (matching nvim's "later capture wins at equal priority"). The winning bytes are then coalesced into non-overlapping runs of one identical style; un-won bytes are plain gaps (no span emitted).

Each per-block call is `pcall`-wrapped, so a runtime error degrades that block to `false` rather than failing the batch.

**Platform degradation.** Because the helper is defined at module level (not inside the conditional treesitter block), it exists on Linux/cargo too — where there are no vendored parsers/queries, so `get_string_parser` / `query.get` find nothing and every block self-degrades to `false`. `wolf-core` maps that to the plain `<pre><code>` render. The rendered HTML itself is still produced CORE-side by the GUI-free `wolf_core::markdown` module; `init.lua` only supplies the per-token spans.

### Terminal drawer — `_G.wolf_toggle_terminal()`

A module-level global (defined regardless of setup ordering, alongside `wolf_create_tabpage` / `wolf_close_tabpage`) that backs the **Terminal** command (id `terminal`, `:WolfTerminal`, `` ⌃` ``). Like the tabpage helpers it takes **NO channel id** and `wolf-core`'s `InputEvent::ToggleTerminal` invokes it over `nvim_exec_lua("wolf_toggle_terminal()", [])` (no args). It changes editor state directly, and — on the OPEN path — ALSO reports the new drawer window via `_G.wolf_emit_drawer` (a `wolf_layout { action = "drawer_open", win }` intent over `wolf_setup_layout`'s channel), which is what makes the drawer VISIBLE front-end-side; the HIDE path stays intent-less (the front-end observes the `nvim_win_close` via `win_close`).

It realizes a **per-project terminal BUFFER + per-tabpage drawer WINDOW** model (see [architecture.md](../../architecture.md) §10). Because a Neovim buffer is GLOBAL to the nvim while a window belongs to a tabpage:

- the terminal BUFFER is a single shared buffer for the whole nvim instance (= one PROJECT), identified by the buffer-local var `b:wolf_terminal` AND `buftype == 'terminal'` (both required, so a stale tagged non-terminal buffer never matches);
- the drawer WINDOW is per-tabpage — toggling in one tabpage never touches another's window, though invoking Terminal from a second tabpage opens a second window onto the SAME shared buffer.

The toggle logic:

1. **Find** the tagged terminal buffer by scanning `nvim_list_bufs()` for a valid buffer with `vim.b[b].wolf_terminal` and `vim.bo[b].buftype == "terminal"`.
2. **Hide (persist)** — if a window in the CURRENT tabpage (`nvim_tabpage_list_wins(0)`) shows that buffer, close it with `nvim_win_close(w, false)` and return. `force = false` is safe: a terminal buffer is never `'modified'`, and the drawer is never the sole window, so this cannot hit "can't close last window". Closing the WINDOW keeps the terminal buffer + shell job alive (VS Code behavior — a hidden terminal is not killed).
3. **Open / recreate** — otherwise open a full-width bottom split ~1/3 tall (`vim.cmd("botright " .. height .. "split")`, `height = math.max(1, math.floor(vim.o.lines / 3))`, the `math.max(1, …)` guarding a 0-height terminal on a tiny screen). The WHOLE build runs inside `wolf_suppress_buffers(function() … end)` (above), because `botright split` fires `WinNew`/`WinEnter` SYNCHRONOUSLY with the new window still showing the PREVIOUS buffer, and on the fresh path `:terminal` fires `BufEnter` BEFORE `b:wolf_terminal` is set — both would feed the drawer window into core's navigation history, which the drawer is EXCLUDED from, and an intermediate wrong push persists even if a later emit is correct. The flag is cleared even if a step errors, and ONE emit of the fully-tagged final state follows. Immediately after the split it tags the drawer WINDOW `vim.w.wolf_terminal = true`, so it is identifiable as the drawer from that point on regardless of which buffer ends up bound into it (the `wolf_buffers` tuple ORs this with the buffer tag). Then: if the shared buffer still exists, show it (`nvim_win_set_buf(0, termbuf)`); if it is gone (the user `:q`'d / exited the shell), create a fresh one with `vim.cmd("terminal")` and tag it `vim.b.wolf_terminal = true`. **Default the drawer to full width** — capture the buffer actually bound into the drawer window (`local termwin_buf = nvim_get_current_buf()`, the reused `termbuf` on the persisted path or the freshly-created terminal buffer `:terminal` entered) and set `vim.b[termwin_buf].wolf_full_width = true`, so the terminal is full-width by DEFAULT (the third window type — alongside editor and preview — to use the per-buffer `b:wolf_full_width` mechanism above; still user-toggleable via `:WolfFullWidth`). Then REPORT the new window: `local w = nvim_get_current_win()` and, under the `if _G.wolf_emit_drawer` guard, `wolf_emit_drawer(w)` — the `drawer_open` layout intent the front-end renders the drawer pane from (the `botright split` performs the real window op; this intent is what makes it VISIBLE). Then RE-EMIT the state channels the full-width default rides so the front-end picks it up on the SAME wake — guarded `_G.wolf_emit_current_file()` (the View-menu checkmark for the focused terminal, via `wolf_current_file`'s 4th arg → `Snapshot.is_full_width_active`) and guarded `_G.wolf_emit_full_width()` (the drawer window's pane geometry, via the per-window `wolf_full_width` channel → `Snapshot.full_width`) — an explicit re-emit is needed because the per-window `wolf_full_width` and current-file autocmds fire when the terminal buffer is ENTERED, BEFORE `b:wolf_full_width` is set on it. Finally `startinsert` focuses the terminal in insert mode (VS Code style); on a hide, `nvim_win_close` returns focus to the editor automatically.

### Full-width toggle — `_G.wolf_toggle_full_width()`

A module-level global (defined alongside `wolf_toggle_terminal`) that backs the **Use full width for content** command (id `full_width`, `:WolfFullWidth`, View menu). Like `wolf_toggle_terminal` it takes **NO channel id** and `wolf-core`'s `InputEvent::ToggleFullWidth` invokes it over `nvim_exec_lua("wolf_toggle_full_width()", [])` (no args). It flips the buffer-local `b:wolf_full_width` on the **EFFECTIVE buffer** and re-emits the three state channels the toggle affects:

1. **Resolve the effective buffer** — the current buffer, UNLESS it is a preview scratch (it carries `b:wolf_preview_source_bufnr`, and that bufnr is a valid buffer), in which case the SOURCE buffer is targeted (OQ-1) — so toggling from a preview resizes the visible preview AND keeps the document's editor + preview views consistent (per-buffer = per-document).
2. **Flip** — `vim.b[buf].wolf_full_width = not (vim.b[buf].wolf_full_width == true)`.
3. **Re-emit** — guarded (each emitter only exists once its setup helper has run): `_G.wolf_emit_current_file()` (the menu checkmark via `Snapshot.is_full_width_active`), `_G.wolf_emit_full_width()` (the per-window editor-pane geometry via `Snapshot.full_width`), and `_G.wolf_emit_previews()` (the preview-pane framing via `PreviewInfo.source_full_width`). A background flag flip fires no window event, so these explicit re-emits are how the front-end learns to resize the content on the next wake.

There is NO global "full width by default" mechanism — this toggle and the terminal drawer's per-buffer default (`wolf_toggle_terminal` seeds `b:wolf_full_width = true` on the terminal buffer, above) are the only things that set the flag, and the browser preview ignores it entirely (it is always ~90-char centered). See [`../../full-width-decisions.md`](../../full-width-decisions.md).

## Deferred

Plugin baking is no longer fully deferred: **orlando** is the first vendored plugin (bundled into the macOS `.app` via `//bazel/orlando`, loaded conditionally as described above), and **lighthouse** is the second vendored asset — a **colorscheme** (bundled via `//bazel/lighthouse`, activated conditionally as described above). A Markdown LSP (e.g. `marksman`) and a formatter remain **deferred to a later phase** (full plugin baking via `wrapNeovim`). Phase 1 otherwise relies on Neovim's built-in markdown syntax highlighting and the `markdown` / `markdown_inline` treesitter parsers, which is enough to exercise the redraw/highlight pipeline and its tests.

The macOS `.app` **ships** (via `//bazel/nvim-treesitter`, `//bazel/nvim-treesitter-textobjects`, and `//bazel/treesitter-parsers`) the nvim-treesitter + textobjects plugins and a curated set of host-compiled treesitter parsers at `Contents/Resources/nvim-treesitter/`, `…/nvim-treesitter-textobjects/`, and `…/parsers/parser/<lang>.so`. On macOS, treesitter markdown **highlighting and fenced-code-block injection are now ENABLED** by the conditional block described above (`vim.treesitter.start` on markdown buffers, with core-native capture-based markdown injections from nvim-treesitter's `main` branch on `runtimepath`); the parsers' ABI compatibility with the pinned Neovim is proven by `//crates/wolf-ffi:treesitter_parser_abi`, and the live highlighter + go-injection are proven by `//crates/wolf-ffi:treesitter_highlight`. Still **deferred** to later changes: the **Linux/Nix vendoring path** for these three artifacts (mirroring how orlando/lighthouse were vendored Bazel-only first), wiring **nvim-treesitter-textobjects keymaps** (the plugin stays bundled-but-inert), and a Markdown **LSP / formatter**.
