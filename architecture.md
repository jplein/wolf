# Architecture

Wolf is a Markdown editor that embeds Neovim as its editing engine. The GUI is a **front-end for Neovim**, not an editor in its own right: Neovim owns all editor state (buffer, cursor, modes, syntax, undo, file I/O), and Wolf renders what Neovim tells it to render and forwards input back.

## Guiding principle

There is one hard rule everything else follows from:

> **`wolf-core` must compile with no GUI toolkit in its dependency tree.**

All the Neovim-specific work — and it is the large majority of the work — lives in `wolf-core` and is shared verbatim across platforms. Each platform front-end is a thin shell: native window chrome, native file dialogs, a paint backend, and OS-event translation. If a type from GTK or AppKit ever appears in core, the boundary has leaked.

## Components

### wolf-core

Platform-agnostic Rust. Contains everything Neovim-related and all app logic that is not inherently platform-specific.

Responsibilities:

- Spawn and supervise the captive `nvim --embed` process; speak msgpack-RPC to it via [`nvim-rs`](https://github.com/KillTheMule/nvim-rs).
- Attach as a UI (`nvim_ui_attach` with `ext_linegrid` + `ext_multigrid` + `rgb`) and handle the entire `redraw` event stream, including the multigrid window events (`grid_resize`/`grid_line`/… carrying a grid id, plus `win_pos`, `win_viewport`, `win_hide`, `win_close`, `grid_destroy`).
- Maintain the **multigrid render-state model** — the in-memory description of what should be on screen: MULTIPLE cell grids keyed by grid id, with per-window grids and the outer grid (grid 1) holding the command line / messages (see "The core↔front-end contract").
- Own a **Neovim→shell intent channel**: the captive nvim's split/focus chords and Ex-commands are overridden (in the bundled `init.lua`) to `rpcnotify` `wolf_layout` (and `wolf_active_win`) messages; core parses these into `LayoutIntent`s on a drainable queue (`WolfCore::drain_intents`) and tracks the active window (`Snapshot.active_win`), so the front-end can own the native pane layout.
- Translate abstract input events (key, mouse, scroll, resize) into Neovim input (`nvim_input`, `nvim_input_mouse`) and Ex commands.
- Own app-level semantics: open/save (delegated to Neovim), recent files, and the hermetic launch/isolation of the captive Neovim.
- Maintain a **most-recently-used (MRU) file cache** — a small SQLite database at `<cwd>/.wolf/mru.sqlite` — recording every opened file and pruning entries whose backing file has been deleted. Reads are synchronous (the cache loads instantly). The cache is **per-project**: it follows the captive Neovim's live working directory (the `wolf_cwd`/`DirChanged`-tracked cwd), so both seeding the picker and recording opens target `<nvim-cwd>/.wolf/mru.sqlite` and `display` strings stay relative to the active project.
- Drive an **asynchronous, streaming file-list traversal** of the working directory (the picker's source): a `FileSearch` session that seeds the MRU synchronously then walks the tree on the tokio runtime (via the `ignore` crate — respecting `.gitignore`, excluding `.git/`/`.wolf/`, including untracked files, plain files and symlinks-to-files only), streaming results to the front-end. A pure ranking function orders results (case-insensitive, MRU-first, with a filename-word strict-prefix preference).
- Track the **currently-edited file** and expose it on the snapshot (`Snapshot.current_file`), updated via the `wolf_current_file` autocmd notification (see "The core↔front-end contract"), so a front-end can highlight and reveal it (e.g. in a file-tree sidebar) after either picker- or Neovim-driven navigation.

Responsibilities it explicitly does **not** have: deciding what text or colors appear (Neovim does), drawing pixels (the front-ends do), or knowing about windows, menus, or dialogs (only that it may _request_ them via intents).

### wolf-ffi

The swift-bridge boundary crate (Rust). It is the seam between the platform-agnostic core and the macOS front-end: it holds the single `#[swift_bridge::bridge]` module and the hand-written Rust glue behind it, and depends on `wolf-core` as a normal crate. It is built both as a `staticlib` (the archive the `.app` links through the generated Swift) and as an `rlib` (so a Rust integration test can drive the same surface headlessly, with no Swift present).

swift-bridge is **confined to this crate** — `wolf-core` gains no new dependency and stays GUI-free, and the Linux/GTK front-end keeps consuming `wolf-core` directly. The bridge surface re-shapes core's API for FFI: a structured `FfiKeyEvent` (mapped into a `wolf_core::KeyEvent` in Rust so nvim notation stays core's job), an opaque per-frame `FfiFrame` whose cells are resolved against the highlight table in Rust (never re-resolved in Swift), and an opaque main-thread-only `WolfCoreHandle`. The picker is fed the same way: a `start_file_search()` session handle (`FfiFileSearch` / `FfiFileEntry`) whose ranking runs in Rust, plus an `open(path)` input. The file-tree sidebar reuses that session shape: a separate `start_tree_search()` handle exposes the **same** pure hierarchical projection (`wolf_core::tree`) over the bridge — `FfiFileSearch::children_of(dir)` → opaque `FfiTreeNode`s, `rel_path_for(abs)`, the free `wolf_ffi_ancestors_to_reveal(rel)`, and `WolfCoreHandle::current_file()` for the reveal. The **split-pane** surface is bridged the same way: `WolfCoreHandle::read_frame_for_grid(grid)` (per-grid paint-ready frames, so each pane paints its own window grid and a bottom strip paints outer grid 1 — `FfiFrame` gains `grid_id()` / `cursor_grid()` and a **per-grid** `cursor_visible`), `drain_intents()` → opaque `FfiLayoutIntent`s, `windows()` → opaque `FfiWinInfo`s, `grid_for_win(win)`, `active_win()`, `focus_win(win)`, and `resize_grid(grid, cols, rows)`. `FfiLayoutIntent` / `FfiWinInfo` are opaque (Vectorizable) for the same reason `FfiTreeNode` is, and their discriminant tables (`intent_kind` SPLIT=0 / FOCUS_DIR=1, `orientation` HORIZONTAL=0 / VERTICAL=1, `focus_dir` LEFT/RIGHT/UP/DOWN = 0/1/2/3) are the single source of truth shared with the Swift `PaneTree` port and the test suites. The wake crosses the boundary as a globally registered `extern "C"` callback (`wolf_ffi_set_wake`), not an `extern "Swift"` symbol, so the headless Rust test still links; a second registered wake (`wolf_ffi_set_filesearch_wake`) drives the picker, and a third (`wolf_ffi_set_tree_wake`) drives the sidebar, both independently. The user-level preferences are bridged the same standalone way: the free `wolf_ffi_load_config()` (no live session, does not hang off `WolfCoreHandle`) returns an opaque `FfiConfig` (`font_family()` / `font_size()` / `line_height()`) delegating to `wolf_core`'s GUI-free `config` module (`preferences_dir().map(load_or_create).unwrap_or_else(default_config)`), which the macOS front-end reads once at launch to drive the cell metrics. The generated Swift + C bindings are **committed** under `crates/wolf-ffi/generated/` and refreshed by an explicit Bazel codegen target. See [`crates/wolf-ffi/README.md`](crates/wolf-ffi/README.md).

### Platform front-ends: wolf-gnome, wolf-macos

The UI layer. Each one:

- Paints the render-state model produced by core.
- Provides native window chrome: title bar / header bar / menus, scrolling, file dialogs.
- Translates OS input events into core's abstract input events.
- Queries the OS theme/accent color and pushes it into Neovim's highlight groups (so selection, etc., match the native look — see "Theming").
- Bridges its native event loop to core's async runtime.

#### wolf-gnome

Rust, using GTK 4 and libadwaita. Consumes `wolf-core` as a **normal Rust crate dependency**. Should feel like a GNOME application.

**Phase status.** The windowed application now exists: an `adw::ApplicationWindow` (with an `adw::HeaderBar`) whose editor area is a **native pane view** — a tree of nested `gtk::Paned`s, one `gtk::DrawingArea` per Neovim window, driven by a pure `PaneTree` layout — with a bottom **cmdline strip** that paints the outer grid (where the command line / messages live under `ext_multigrid`). The layout is an **N-ary frame model** (matching Neovim): a split in the SAME orientation as its containing frame FLATTENS into equal-sized siblings (so vsplitting one of two side-by-side panes yields three equal columns, not a 25/25/50 nesting), while a PERPENDICULAR split nests. The pure seams (`gdk_key`, `paint`, `grid_size_for`), verified headlessly without a display, are wired onto a live `WolfCore`: each pane paints its own window grid via Cairo/Pango and the pane owning the cursor's grid overlays a mode-aware cursor (a block in normal mode, a thin bar in insert mode, driven by `ModeInfo.shape`), drawn opaque with reverse-video colors so it is reliably visible; key input flows through a `gtk::EventControllerKey` to nvim's current window globally; each pane / divider resize maps pixels to a grid size and calls `WolfCore::resize_grid`; on each wake the front-end drains `WolfCore::drain_intents` to create/split/close/focus panes and reads `Snapshot.active_win` to mark the active pane; and the core's wake is marshalled from its tokio worker thread onto the GTK main thread (via an `async-channel` drained by `glib::spawn_future_local`) to trigger redraws. Splits (`<C-w>s`/`v`, `:split`/`:vsplit`), close (`<C-w>c`), focus moves (`<C-w>h/j/k/l`), and divider drag-to-resize all work. A built-in **file picker** (opened with **Ctrl+Shift+P** or a header-bar Open button) floats over the editor as a textbox + fuzzy-matched list, fed by core's streaming `FileSearch` + ranking and opening the selected file into the active pane via the `open(path)` intent (recorded in the MRU); there are still no native file dialogs, and saving is from within Neovim. A **file-tree sidebar** occupies the left of a `gtk::Paned` (the pane view on the right): a `gtk::ListView` + `gtk::TreeListModel` populated by the **same** `FileSearch` mechanism as the picker (a hierarchical projection of that flat file list), where a single click opens a file, the top level is expanded by default, and the file being edited is highlighted and revealed (ancestors expanded + scrolled into view) after both picker and Neovim `:e` navigation via `Snapshot.current_file`. Still deferred: native file dialogs, theming, mouse/scroll input, a NATIVE command line / messages / popup menu (`ext_cmdline` / `ext_messages` / `ext_popupmenu` as Adw widgets — the cmdline strip renders the grid-drawn command line in the meantime), floating windows, and HiDPI scale handling. See the known-limitations note in [`crates/wolf-gnome/README.md`](crates/wolf-gnome/README.md).

#### wolf-macos

Swift, using AppKit. Consumes `wolf-core` through the generated **swift-bridge** surface in [`wolf-ffi`](#wolf-ffi). Should feel like a macOS application.

**Phase status.** The windowed application now exists: a **single-window AppKit shell** whose editor area is a **native pane view**, at parity with the GNOME shell. An `NSApplication` + `AppDelegate` resolves `init_lua` and the cwd, starts the core via `wolf_ffi_start`, and builds one `NSWindow` ("Wolf", sized from the measured cell metrics × the initial 80×24) whose editor area is a `PaneContainerView`. That container is a **single flat `NSView`** (flipped, so grid row/col map directly to points) that paints EVERY pane itself — deliberately NOT a tree of nested `NSSplitView`s, which composited unreliably; painting one flat view is the proven `GridView` pattern. It drives its painting from a pure `PaneTree` layout (a Foundation-only Swift port of wolf-gnome's `layout.rs`, living in the headlessly-tested `WolfKeyMap` module): each `draw(_:)` computes every pane's rectangle via `PaneTree.paneRects` and, for each bound pane, clips+translates to that rect and paints the pane's window grid via `read_frame_for_grid` — filling every cell's background, drawing its glyph via CoreText/CoreGraphics in the per-cell foreground color (both colors resolved from wolf-core's highlight table in Rust), and overlaying a **mode-aware reverse-video cursor** (a block, horizontal, or vertical bar driven by `cursor_shape`, with the fill/glyph colors also resolved in Rust, ported from wolf-gnome's `cursor.rs`) — but only on the pane owning the cursor's grid (per-grid `cursor_visible`). Because each pane is painted **independently of Neovim**, an INACTIVE pane gets a translucent **dim scrim** — a front-end-only treatment that is awkward to express inside Neovim itself — and thin separators are stroked between adjacent panes. A one-row **cmdline strip** along the bottom of the same view paints Neovim's command line: under `ext_multigrid` the command line / messages live on a dedicated MESSAGE grid (NOT grid 1; positioned via `msg_set_pos`, which the core drops) that the cursor moves onto while the command line is open, so the strip paints the grid the cursor is on when that grid is neither grid 1 nor a window grid (its cursor row), falling back to grid 1's last row otherwise — keeping typed `:`/`/` input visible. A click hit-tests the pane rects and focuses that pane's window. On each render wake the container drains `WolfCore::drain_intents` to create / split / close / focus panes and reads `active_win()` to mark the active (non-dimmed) pane, `syncGridSizes` maps grid 1 + each pane rect to a grid size and calls `resize` / `resize_grid` (only when the size differs from nvim's, so it converges), and key input flows through the container (the editor area's first responder + global key sink) to nvim's current window globally. Splits (`<C-w>s`/`v`, `:split`/`:vsplit`), close (`<C-w>c`), and focus moves (`<C-w>h/j/k/l`) all work; **divider drag-to-resize is deferred** — splits are equal-weighted (a tree of `NSSplitView`s would have given drag for free, but at the cost of the fragile nested-view compositing). The layout is the same **N-ary frame model** as GNOME (matching Neovim): a split in the SAME orientation as its containing frame FLATTENS into equal-sized siblings, while a PERPENDICULAR split nests. Font metrics are **config-driven**: the font-family, font-size, and line-height come from the user-level `wolf-config.yaml` preferences file (read in the GUI-free `wolf-core` `config` module, bridged to Swift as `wolf_ffi_load_config()` / `FfiConfig`), with **two fonts bundled** into the `.app` at `Contents/Resources/fonts/` and both CoreText-registered at launch (`FontRegistration.swift`) — **iA Writer Mono S** (the config default) and **JetBrains Mono** (bundled + registered but non-default) — a **Menlo** fallback when the configured family does not resolve, and `WOLF_FONT_PT` still overriding the point size (parity with gnome). `AppDelegate` registers the bundled fonts, loads the config, then measures the cell metrics from it, in that order.

The redraw path mirrors gnome's, realized natively: core fires its wake on a tokio worker thread; `WakeBridge` (the registered `extern "C"` callback) hops it onto the AppKit main thread with `DispatchQueue.main.async` and calls the registered `PaneContainerView`'s `onRenderWake()` (a one-for-one port of wolf-gnome's `pane_view.rs::on_render_wake`: ensure the initial pane, apply drained layout intents, detect closed windows, resolve pending grids, refresh the active pane, sync grid sizes, then mark the single editor view for redisplay — repainting every pane + the cmdline strip in one `draw(_:)`), which drives the next paint. Input flows the other way: the container's `keyDown(_:)` pulls the `keyCode`/`characters`/`charactersIgnoringModifiers` + modifiers off the `NSEvent`, runs them through the **pure, AppKit-free** `WolfKeyMap.translate` seam into a structured `FfiKeyEvent`, and calls `send_key` — so the Shift contract is honored once, in Rust (`key_to_notation`), exactly as on Linux. View resizes map the current bounds to a `(cols, rows)` grid size and call `resize`. The captive Neovim is hermetic and **bundled inside the `.app`**: a pinned Neovim 0.12.3 tree at `Contents/Resources/nvim/` and the captive `init.lua` at `Contents/Resources/init.lua` (decision 8). `AppDelegate` points wolf-core at the bundled `nvim/bin/nvim` by setting `WOLF_NVIM_BIN` (only if a developer hasn't already exported it) and launches against the bundled `init.lua` (overridable via `WOLF_INIT_LUA`) — so a double-clicked `.app` runs with no shell environment.

A built-in **file picker** is realized (parity with gnome's): **Shift+Control+P** opens a floating overlay panel (an `NSSearchField` + `NSTableView`) over the editor, fed by core's streaming `FileSearch` session over the FFI (`start_file_search` / `ranked` / `open`, with ranking staying in Rust). The deliberately non-conflicting chord preserves every Neovim key (including `<C-p>`); typing filters the cwd's files (respecting `.gitignore`, MRU-first, case-insensitive, filename-word strict-prefix), Up/Down navigate, Enter (or a double-click) opens the selected file via the `open(path)` input event (recorded in the MRU), and Esc closes. While open the search field is first responder, so keys are not forwarded to Neovim.

A built-in **file-tree sidebar** is also realized (parity with gnome's), with the standard macOS source-list look: the window's `contentViewController` is an `NSSplitViewController` (`EditorSplitViewController`) whose leading split item is a `.sidebar` source-list item wrapping the `NSOutlineView` (`.sourceList` style, clear background) and whose trailing item wraps the editor `PaneContainerView`. The sidebar's translucent **full-height vibrancy** (the OS source-list material) extends under a **transparent `.fullSizeContentView` titlebar** + a minimal unified `NSToolbar` (a sidebar toggle and an `NSTrackingSeparatorToolbarItem` aligned to the divider); the editor pane is pinned **below the titlebar** (its host pins the grid's top to the safe-area guide) so it keeps its exact `cols` × `rows` cell size (the OCR-checked 80-col grid is undisturbed). It is fed by core's **same** streaming `FileSearch` over the FFI, but via its own long-lived `start_tree_search()` session and the pure hierarchical projection (`children_of` / `rel_path_for` / `ancestors_to_reveal`, all in `wolf_core::tree`): the cwd itself is shown as a single **synthetic root node** (its basename), **expanded on init**, with its immediate children (`children_of("")`) visible beneath it and their subdirectories collapsed — the VS Code / Snacks explorer model, **divergent from the GNOME tree** (which shows `children_of("")` directly at the root with no cwd node). The sidebar **follows Neovim's live working directory**: on each editor render wake it reads `WolfCoreHandle::cwd()` (nvim's already-canonicalized cwd, exposed over the FFI) and, when it changed (`:cd`/`DirChanged`), **re-roots** the tree — rebuilding the synthetic root and restarting `start_tree_search()` — mirroring how the picker re-queries `getcwd()` on each open. A single click opens a file (then refocuses the editor) or toggles a directory, and the buffer being edited is bolded and revealed (ancestors expanded + scrolled into view) after both picker- and Neovim-`:e`-driven navigation, driven by `current_file()` read on each editor wake (the cwd is checked first, so a simultaneous cwd + buffer change reveals into the new tree).

The same **"Split panes — known v1 limitations"** (below) apply on macOS as on GNOME: only windows opened via the overridden split commands get a pane; the cmdline strip shows only a SINGLE row of the command-line / message grid (multi-row prompts truncate); focus-direction moves use the tree's idealized split ratios; and floating / external windows are ignored. macOS additionally **defers divider drag-to-resize** — splits are equal-weighted (parity with GNOME's v1 divider limitation), since the editor area is a single flat painting view rather than an `NSSplitView` tree.

**Mouse, scroll, and synthetic scrollbars** are realized on macOS (still deferred on GNOME). Mouse input is **grid-targeted**: `PaneContainerView` maps a pane-local point to a grid cell through a per-pane `PaneGeometry` seam and forwards a press / drag / release via `send_mouse` targeting that pane's WINDOW grid (`>= 2`) with grid-local coordinates, so under nvim's `mouse=a` a click positions the cursor and a click-drag selects (click-to-focus is preserved). This required threading a real `grid` id through the core mouse/scroll path (`nvim_input_mouse` previously hardcoded grid 0) — see the cross-cutting change in [wolf-core](#wolf-core) / [wolf-ffi](#wolf-ffi). Scroll (wheel / trackpad) is hit-tested from the whole pane rect (so a future side-margin still scrolls), accumulated into discrete line steps by a pure `ScrollAccumulator` seam, and forwarded via `send_scroll`; per **decision 5** the scroll is just input — Neovim scrolls itself. The **scrollbar is synthesized per pane from `win_viewport`** (decision 5): a custom-drawn indicator at each pane's right edge whose thumb size/offset comes from the frame's 0-based `topline` / `botline` / `linecount` viewport, following the macOS "Show scroll bars" setting (`NSScroller.preferredScrollerStyle`: `.legacy` always-visible / `.overlay` fade, reacting to `preferredScrollerStyleDidChangeNotification`); the thumb is non-interactive (drag deferred). The pixel↔cell `PaneGeometry` seam carries a distinct GRID RECT inside the PANE RECT, and the **max-column-width / centered grid it readies is now realized on macOS**: a grid wider than a hard-coded **90 columns** is capped and CENTERED inside the pane, the side margins painted in the grid's own background so they blend seamlessly, while the scrollbar stays pinned at the PANE's right edge (out in the right margin). The `PaneGeometry` / `ScrollAccumulator` seams are headlessly unit-tested in `WolfKeyMapTests`; the FFI mouse/scroll + viewport surface is covered by the real-nvim `//crates/wolf-ffi:mouse_scroll` test; the AppKit event wiring + scrollbar drawing is compile-verified + manual-smoke only.

Per-cell glyph **text attributes** are now painted on macOS: `wolf-ffi` resolves and packs bold/italic/underline/undercurl/strikethrough (`FfiCell::flags()`) plus the **special** (underline) color (`FfiCell::special()`), and the renderer consumes them — the pure `GlyphStyleResolver` seam maps a cell's flags to a `GlyphFace` (drawn with the matching cached bold/italic/boldItalic `CTFont`, all sharing the regular advance width for a fixed-cell grid) and to underline/strikethrough strokes drawn **manually** as `CGContext` lines in the resolved color (special when set, else fg; undercurl folds into a straight underline this pass), because `CTLineDraw` paints decorations only in the foreground color. Still deferred for macOS (the same list as gnome, minus mouse/scroll — now realized on macOS (above) though still deferred on GNOME): theming, a native command line / messages / popup menu (`ext_cmdline` / `ext_messages` / `ext_popupmenu` as AppKit widgets — until then, the grid-drawn command line shows in the cmdline strip), HiDPI edge cases, and a true curly undercurl (a straight underline for now). The mouse-scrollbar **thumb-drag** is also deferred (the thumb is non-interactive); the **max-column-width / centered grid** is now realized (a hard-coded 90-column cap, centered with margins painted in the grid background — see above). The pinned Neovim is now bundled into the `.app` (above), and the live nvim→FFI→`read_frame` round-trip **is** covered by a passing automated test on the macOS Bazel host: `//crates/wolf-ffi:bridge_smoke` passes under `bazel test`, driving start → type → grid-reflects-the-typed-char → resize → shutdown against the bundled/pinned Neovim. (The GUI window rendering and Finder double-click are still not headlessly asserted.) See [`crates/wolf-macos/README.md`](crates/wolf-macos/README.md).

## Architectural decisions

### 1. Core↔front-end boundary: swift-bridge on macOS, direct crate on Linux

Swift cannot import a Rust crate directly, so the macOS side needs a generated binding regardless. We use [`swift-bridge`](https://github.com/chinedufn/swift-bridge), which produces idiomatic Swift from an annotated bridge module in `wolf-core`. Linux/GTK, being Rust, links `wolf-core` directly with no FFI.

Consequence — and a design constraint: the **front-end-facing API of `wolf-core` must be expressible over swift-bridge** (FFI-friendly: plain structs, slices, handles, and callbacks — no Rust-only generics or trait objects across the line). The GTK front-end consumes that same API directly. This keeps a single front-end-facing surface rather than two divergent ones.

We rejected a uniform C-ABI on both platforms: it would cost Linux its type safety and async ergonomics for symmetry we don't need, since the boundary is defined once in Rust either way.

### 2. Rendering: native paint per platform

The render-state model is toolkit-agnostic; each front-end paints it natively: Cairo/Pango in GTK on Linux, CoreText/CoreGraphics in AppKit on macOS. This gives the best native text rendering on each OS. The cell-painting loop is written twice, but it is small once the render-state model exists.

We rejected a shared portable canvas (skia/wgpu): it would force surface handles (GL/Metal) across the FFI and sacrifice native text quality. The render-state model is kept behind a clean interface, so a shared renderer could be introduced later without touching core's logic if the duplication ever justifies it.

### 3. Neovim is embedded as a child process over stdio

Core launches `nvim --embed` and communicates over its stdin/stdout via msgpack-RPC. No sockets, no shared user Neovim instance.

### 4. Neovim owns the document model

There is no separate document representation in Wolf. Open is `nvim.command("edit <path>")`; save is `"write"` / `"saveas"`. Because Markdown is plain text, Neovim's buffer _is_ the document model. The grid is a projection of the visible viewport, never the whole file.

### 5. Scrolling belongs to Neovim; the scrollbar is synthesized

The grid is sized to the **visible viewport** only (resized via `nvim_ui_try_resize` when the widget resizes). Scroll gestures are forwarded to Neovim as input; Neovim scrolls itself and emits `grid_scroll`. A native scrollbar's position and range are driven by the `win_viewport` event (`topline`/`botline`/`curline`/`linecount`, all 0-based buffer line indices with `botline` one-past-the-last-visible). The editor widget is **not** placed in a scrolled-window that owns a tall child. **macOS now realizes this**: `PaneContainerView` draws a synthetic per-pane scrollbar from each pane's `win_viewport` (over the FFI's `FfiFrame` viewport accessors) at the pane's right edge, following the system "Show scroll bars" setting — scroll input goes to Neovim, the scrollbar is purely a viewport-driven projection. GNOME still defers the scrollbar.

### 6. Syntax highlighting is whatever Neovim produces

The front-ends are semantically dumb: a cell carries an `hl_id`, which resolves (via the `hl_attr_define` / `default_colors_set` table) to RGB + attributes, which get painted. All highlighting — treesitter, LSP semantic tokens, diagnostics, `Visual`/`Search` — is decided inside Neovim and arrives pre-resolved. To change or extend highlighting you configure Neovim, never the renderer.

### 7. UI extensions: grid-drawn for v1 (with `ext_multigrid` for native panes)

For v1 we enable `ext_linegrid` + `ext_multigrid` (+ `rgb`). The command line, messages, and completion menu still render into the grid, terminal-style — but because `ext_multigrid` moves window content onto per-window grids (`>= 2`), the command line / messages now live on the OUTER grid (grid 1). The front-end paints each window grid in its own pane and paints grid 1's content in a dedicated **cmdline strip** along the bottom of the editor area, so typed `:`/`/` input stays visible. This is the least work, is fully functional, and is consistent across platforms.

Going native later (`ext_cmdline` + `ext_messages` + `ext_popupmenu`, rendered as Adw/AppKit widgets) is an additive change: it touches the front-ends and adds events to core's render-state model, but does not change the core architecture. `ext_multigrid` is what lets the shell own a native split-pane layout (decision below).

### 8. The captive Neovim is hermetic, pinned, and Markdown-only

Wolf ships its own Neovim, tuned for Markdown and nothing else (markdown + markdown_inline treesitter grammars, a Markdown LSP such as `marksman`, an optional formatter — and nothing else). It must not read the user's `~/.config/nvim`, plugins, or shada.

Launch isolation (both platforms): `nvim --embed --clean -u <bundled init.lua>`, with `NVIM_APPNAME` and the `XDG_*`/state dirs pinned away from the user's, and shada/swap disabled. The `init.lua` lives **in this repo** and is referenced by the build, so editor behavior is version-controlled alongside the code that depends on it.

Delivery:

- **Linux (NixOS):** `wrapNeovim` / `neovimUtils.makeNeovimConfig` builds a single wrapped `nvim` with the plugin set baked into the runtimepath and the LSP/ formatter binaries on its `PATH` (`makeWrapper --prefix PATH`). The whole closure ships together.
- **macOS (REALIZED):** the `.app` bundles a pinned Neovim **0.12.3** — the official macOS release tree (`bin/nvim` + `lib/nvim/parser` treesitter parsers, including `markdown` and `markdown_inline`, + `share/nvim/runtime`) — at `Contents/Resources/nvim/`, alongside the captive `init.lua` at `Contents/Resources/init.lua`. Bazel downloads and verifies the release hermetically (sha256-pinned via the `//bazel/nvim` module extension, assembled into a structure-preserving `TreeArtifact` with `aspect_bazel_lib`'s `copy_to_directory`). At launch the GUI points wolf-core at that absolute bundled binary: `AppDelegate` sets `WOLF_NVIM_BIN` to `Contents/Resources/nvim/bin/nvim` **only if it is not already set** (`setenv(..., 0)`, so a developer's exported `WOLF_NVIM_BIN` still wins) before starting the core — never `nvim` from the user's `PATH`. So a double-clicked `.app` runs its own Neovim with no shell environment. The `.app` also bundles the **vendored orlando** plugin (the first vendored plugin) at `Contents/Resources/orlando/`, downloaded + sha256-pinned by the `//bazel/orlando` module extension and assembled the same way (pure Lua, arch-independent — no `select()`); the captive `init.lua` self-locates that sibling `orlando/` dir and sources it when present (a strict no-op when absent), so no Swift is involved in loading it. It also bundles the **vendored lighthouse** colorscheme at `Contents/Resources/lighthouse/`, downloaded + sha256-pinned by the `//bazel/lighthouse` module extension and assembled the same way (pure Lua, arch-independent — no `select()`); because a colorscheme is inert on `runtimepath` until selected, the captive `init.lua` self-locates that sibling `lighthouse/` dir and **activates** it when present (prepend to `runtimepath`, then `vim.o.background = "dark"` + `vim.cmd.colorscheme("lighthouse")`, after `syntax on`; a strict no-op when absent), again with no Swift involved. Both are **Bazel-only for now** — the Linux path will vendor them separately later. Full `wrapNeovim`-style plugin baking beyond that — a `marksman` LSP, a formatter — remains deferred; see below.)

**Phase status.** The Neovim binary is pinned and hermetic from day one: on Linux, via the flake devShell (core locates it only through `WOLF_NVIM_BIN`, never `PATH`, never `/nix/store` scanning); on macOS, via the bundled `Contents/Resources/nvim/bin/nvim` (above), which `AppDelegate` exports as `WOLF_NVIM_BIN` unless overridden. Either way core launches it `--embed --clean -u runtime/nvim/init.lua` with `-i NONE -n`, pinning `NVIM_APPNAME=wolf` and the `XDG_*` dirs under a private temp dir. The **orlando** plugin is the first vendored plugin (macOS Bazel bundle, via `//bazel/orlando`, loaded by the captive `init.lua`), and the **lighthouse** colorscheme is the second vendored asset (macOS Bazel bundle, via `//bazel/lighthouse`, activated — not just sourced — by the captive `init.lua`); full `wrapNeovim` plugin baking beyond that (the `marksman` Markdown LSP, a formatter) is **deferred to a later phase**, and vendoring is Bazel-only for now (the Linux path vendors them separately later). The current build runs the pinned binary with the repo's `init.lua` and the treesitter `markdown`/`markdown_inline` parsers the release carries. Bundling is **arm64-tested** on the dev host; the x86_64 tree is wired via `select()` but untested.

### 9. The macOS UI: AppKit, Swift, Tahoe-only, all-Bazel — locked

The macOS front-end's foundations are fixed (these are load-bearing — do not relitigate them casually):

- **Tahoe (macOS 26) and newer only.** `Info.plist`'s `LSMinimumSystemVersion` and the `macos_application` `minimum_os_version` are both `"26.0"`.
- **AppKit, not SwiftUI.** A custom `NSView` paints the grid (decision 2).
- **Swift**, built with **Xcode 26+** (Swift features that require Xcode 26 are permitted).
- **The Bazel build is authoritative.** `rules_swift` + `rules_apple` build the `.app` (code-signed, min OS 26.0). `rules_xcodeproj` can generate an `.xcodeproj` for debugging/LLDB only — it is **uncommitted** (`.gitignore`d) and never the source of truth; Bazel remains the one build.
- **Rust ↔ Swift via swift-bridge, confined to `wolf-ffi`** (decision 1), with the generated Swift + C bindings **committed** under `crates/wolf-ffi/generated/`.
- **Key translation lives in Rust.** Swift sends a structured `FfiKeyEvent` over the bridge; `wolf-core::key_to_notation` stays the single source of nvim notation (the Shift contract is honored once, in Rust).
- **The snapshot is marshalled as an opaque per-frame handle** (`FfiFrame`), resolved against the highlight table in Rust — never re-resolved in Swift.

Resolved Bazel pins (highest BCR releases that declare Bazel-8 compatibility, keep `apple_support >= 2.6.1`, and support Xcode 26 / the Tahoe SDK): **`rules_swift` 3.6.1, `rules_apple` 4.5.3, `rules_xcodeproj` 4.1.0**, and **`swift-bridge` / `swift-bridge-build` 0.1.59** on the Cargo side (`apple_support` stays 2.6.1).

## The core↔front-end contract

The boundary is intentionally narrow and FFI-shaped (decision 1). Two directions:

### Output: render state (core → front-end)

Core maintains a snapshot of everything needed to draw a frame:

- The cell grids: under `ext_multigrid` a map of grid id → grid (each cell: char(s) + `hl_id`). The outer grid (grid 1) holds the command line / messages; editor window content lives on grids `>= 2`.
- The per-window layout: grid id → `WinInfo` (window handle, position, size, viewport, hidden flag), learned from `win_pos` / `win_viewport`.
- The highlight table: `hl_id → {fg, bg, special, bold, italic, underline…}`, plus default colors.
- Cursor: the grid it lives on + grid position + shape/mode (from cached `mode_info_set`, updated on `mode_change`).
- Viewport info for the scrollbar (`win_viewport`), per window.
- The **active window** (`Snapshot.active_win: Option<i64>`), tracked via the `wolf_active_win` notification, so the front-end can mark the active pane.
- The **current file**: the absolute, canonicalized path of the buffer being edited (`Snapshot.current_file: Option<PathBuf>`, `None` for an unnamed buffer).

Core does not push pixels or per-event callbacks across the boundary. Instead it applies `redraw` batches to the snapshot and, on `flush`, signals the front-end that a new frame is ready (a "redraw needed" wake — see threading). The front-end then reads the current snapshot on its UI thread and paints.

The current file is tracked **out-of-band** from the redraw stream: after attaching, core installs a `BufEnter`/`BufWinEnter`/`BufFilePost` autocmd (in the bundled `init.lua`, set up over RPC with core's channel id) that `rpcnotify`s a `wolf_current_file` notification carrying `expand('%:p')`. The handler folds it into `Snapshot.current_file` and fires the same wake (it does not advance the redraw-frame counter). This is what lets a front-end highlight and reveal the active file even when the buffer changed from inside Neovim (e.g. `:e`).

Three other facets are tracked out-of-band the same way (each its own autocmd → `rpcnotify` → redraw-handler fold, none advancing the redraw-frame counter): the **active window** via `wolf_active_win` (a `WinEnter` autocmd → `Snapshot.active_win`), **layout intents** via `wolf_layout` (the rebound split/focus chords → a drainable `LayoutIntent` queue), and the captive Neovim's **working directory** via `wolf_cwd` (a `DirChanged` autocmd covering `:cd`/`:lcd`/`:tcd`, emitting once at setup). The cwd is stored in a sibling `TrackedCwd` cell (NOT the snapshot — nvim's cwd is not render state, and the triggering `:cd` already flushes via the redraw path, so `wolf_cwd` fires no extra wake). Core reads that cell so the MRU cache follows nvim's live cwd (below).

### Output: file-search session (core → front-end)

The file picker reuses the same snapshot+wake shape rather than a bespoke channel. `WolfCore::start_file_search(wake)` returns a `FileSearch` handle whose `read()` exposes an owned snapshot of the results collected so far (`entries`, `complete`, `version`); the MRU seed is present synchronously, and the background traversal streams more in, bumping `version` and firing the **same wake callback** after each batch. The traversal is rooted at the captive Neovim's **live working directory** (`getcwd()`, queried over RPC each time a search starts), so the picker follows wherever Neovim is (`:cd`/`:lcd`/`:tcd`); it falls back to the configured `cwd` if that query fails. The **MRU seed follows the same live cwd**: core keeps a per-cwd cache of MRU stores (keyed by canonical cwd) and seeds from the store at `<resolved-root>/.wolf`, the SAME root the traversal walks — so seeded entries lie inside the search root and their `display` strings are root-relative (per-project MRU isolation, no leaking a different project's recents and no absolute-path display). The front-end reads + ranks + repaints exactly as it does for redraws (the query is tokenized on whitespace into terms that are AND-matched, order-independent, against each path; see `wolf_core::rank_matches`). Dropping (or cancelling) the handle stops the traversal. Selection feeds back in as an `open(path)` input event (below), which core also records in the MRU — into the per-cwd store for nvim's live cwd (the `wolf_cwd`-tracked cell), keeping the write path symmetric with the seed.

macOS consumes this same session over the FFI: `WolfCoreHandle::start_file_search()` returns an opaque `FfiFileSearch` whose `ranked(query, max)` runs the ranking in Rust and hands back the top-N entries, `open(path)` issues the `Open` input event, and a **second** globally-registered wake (`wolf_ffi_set_filesearch_wake`, parallel to the editor wake) drives a picker refresh on each traversal batch independently of editor repaints. The macOS **file-tree sidebar** consumes the very same shape via its own `start_tree_search()` session: the projection methods `children_of(dir)` (→ opaque `FfiTreeNode`s) and `rel_path_for(abs)` plus the free `wolf_ffi_ancestors_to_reveal(rel)` all delegate to the pure `wolf_core::tree` module (the single source of truth, shared with wolf-gnome), and a **third** registered wake (`wolf_ffi_set_tree_wake`) drives the sidebar's row rebuilds; the current-file reveal rides the editor wake (reading `WolfCoreHandle::current_file()`), and the same editor wake reads `WolfCoreHandle::cwd()` — nvim's live, already-canonicalized working directory (a cheap synchronous read of the `wolf_cwd`-tracked cell, NOT the render snapshot) — to re-root the sidebar on `:cd`/`DirChanged`. The snapshot+wake shape is identical; see [`crates/wolf-ffi/README.md`](crates/wolf-ffi/README.md).

### Output: intents (core → front-end)

Things only the platform can do, requested abstractly: "show an open dialog," "show a save dialog for an unnamed buffer," "set the window title to X," "the buffer is modified / clean." The front-end fulfills these with native widgets and feeds results back in as input.

The **layout intent channel is realized** for split panes. The captive nvim's split/focus chords and Ex-commands are overridden (in the bundled `init.lua`) to `rpcnotify` a `wolf_layout` message; core parses each into a `LayoutIntent` — `Split { orientation, from, win }` or `FocusDir { dir, from }` — and queues it for `WolfCore::drain_intents`, which the front-end drains on each wake. The asymmetry (decision D4): a SPLIT is performed by nvim (it really creates the window + grid and emits `win_pos`) AND reported so the shell learns the orientation and which pane to split; a FOCUS move is a PURE intent (nvim does not change focus — the shell resolves the neighbour in its own layout and calls `focus_win`); a CLOSE is performed by nvim (guarded against closing the last window) and observed via the `win_close` redraw event (no intent). The shell owns the GTK `Paned` geometry and binds each pane to a Neovim window + its grid, sizing each grid to its pane.

macOS consumes this same channel over the FFI: `WolfCoreHandle::drain_intents()` returns opaque `FfiLayoutIntent`s (a SPLIT carries `orientation` + `from` + `win`; a FOCUS_DIR carries `dir` + `from`), `windows()` returns opaque `FfiWinInfo`s and `grid_for_win` / `active_win` track the live grids and active window, and `focus_win` / `resize_grid` feed resolved focus moves and per-pane resizes back in. Each pane reads its grid through `read_frame_for_grid` (the per-grid `FfiFrame` carries `grid_id` / `cursor_grid` and a per-grid `cursor_visible`), and the cmdline strip reads the message/command-line grid the same way — under `ext_multigrid` Neovim renders the command line onto a dedicated message grid (not grid 1), which the strip identifies as the grid the cursor is on that is neither grid 1 nor a window grid (falling back to grid 1). The discriminant tables (`intent_kind`, `orientation`, `focus_dir`) are the single source of truth shared between `wolf-ffi`, the Swift `PaneTree` port, and the test suites.

### Input: events (front-end → core)

`key`, `mouse`, `scroll`, `resize(cols, rows)`, `resize_grid(grid, cols, rows)` (per-pane), `focus_win(win)` (click-to-focus / resolved focus moves), `open(path)`, `save`, `save_as(path)`, and theme-color updates. Core translates these into Neovim RPC calls. Key events are translated to Neovim notation (`<Esc>`, `<C-w>`, `<S-…>`, `<CR>`, modifiers) on the way in.

## Threading and event-loop model

`nvim-rs` is async (tokio); the platform UIs run their own event loops (glib on Linux, the AppKit/CFRunLoop on macOS). They must not block each other.

- Core owns a tokio runtime on its own thread(s). The `nvim-rs` handler receives `redraw` notifications there and updates the render-state snapshot (behind a lock or via an internal channel).
- On `flush`, core invokes a front-end-registered **wake callback**. The callback is responsible for marshalling onto the UI thread — `glib` idle/channel source on Linux, dispatch-to-main on macOS — and there triggering a paint (`queue_draw` / `setNeedsDisplay`) that reads the snapshot.
- Input flows the other way as plain calls into core, which hands them to the tokio side to issue RPC.

The wake mechanism is the one piece each front-end implements; the snapshot and the RPC are entirely in core.

## Theming

To make native selection/colors match the OS, the front-end reads the live theme (Adwaita named colors / accent on Linux; `NSColor`/appearance on macOS), converts to RGB, and pushes it into Neovim's highlight groups via `nvim_set_hl` (e.g. `Visual`, default fg/bg). It re-applies on theme/accent change. The renderer stays dumb; Neovim re-emits `hl_attr_define` and the grid repaints.

## Build

See [Building Wolf](build.md). In brief: on Linux (NixOS), `wolf-core` + `wolf-gnome` build with Cargo under Nix. On macOS, the **Rust core** builds with **Bazel** (driven by **bazelisk**), with `rules_rust`/`crate_universe` consuming the same `Cargo.toml`/`Cargo.lock` and `rules_rust` downloading a pinned `rustc`; the C/link toolchain (apple_support) deliberately uses the **host Xcode SDK** rather than the older SDK shipped inside Nix (this matters for the bundled SQLite that `rusqlite` compiles via `cc`). The macOS path now builds `wolf-core`, the `wolf-ffi` swift-bridge crate, **and** the `wolf-macos` AppKit `.app` (`bazel build //crates/wolf-macos:Wolf`) on the Xcode 26 / Tahoe SDK via `rules_swift` + `rules_apple` (with `rules_xcodeproj` for an uncommitted debug project). The build also **bundles a pinned Neovim 0.12.3** (downloaded hermetically by the `//bazel/nvim` module extension and assembled with `aspect_bazel_lib`'s `copy_to_directory`) plus the captive `init.lua`, the **vendored orlando plugin** (via the `//bazel/orlando` module extension), and the **vendored lighthouse colorscheme** (via the `//bazel/lighthouse` module extension, activated by `init.lua`) into `Contents/Resources/`, so the packaged app no longer needs `WOLF_NVIM_BIN` to run (a developer's exported `WOLF_NVIM_BIN` / `WOLF_INIT_LUA` still wins).

### Split panes — known v1 limitations

The first split-panes cut is deliberately scoped; these are intentional, each with a clear future direction (see also [`crates/wolf-gnome/README.md`](crates/wolf-gnome/README.md)):

- **Only windows opened via the overridden split commands get a pane.** Panes come from `wolf_layout` `Split` intents, emitted only by the rebound chords / Ex-commands. A window created by a non-overridden path (`:help`, the quickfix / location list, a preview window, `:diffsplit`) still gets a grid + `WinInfo` but no pane, so its content is not shown. _Future:_ auto-pane any unbound window grid.
- **The cmdline strip shows only the outer grid's last row**, so multi-row prompts (`press-ENTER`, `:messages`, a long wrapped `:`-command) are truncated until native `ext_messages` lands.
- **Focus-direction moves use the tree's idealized split ratios** (`0.5`), not the actual dragged divider positions, so `<C-w>h/j/k/l` can pick a different neighbour than the pixel geometry after a manual drag.
- **Floating and external windows are ignored** (`win_float_pos` / `win_external_pos` / `msg_set_pos` are dropped), so they do not appear as panes.
