# Architecture

Wolf is a Markdown editor that embeds Neovim as its editing engine. The GUI is a **front-end for Neovim**, not an editor in its own right: Neovim owns all editor state (buffer, cursor, modes, syntax, undo, file I/O), and Wolf renders what Neovim tells it to render and forwards input back.

## Guiding principle

There is one hard rule everything else follows from:

> **`wolf-core` must compile with no GUI toolkit in its dependency tree.**

All the Neovim-specific work — and it is the large majority of the work — lives in `wolf-core` and is shared verbatim across platforms. Each platform front-end is a thin shell: native window chrome, native file dialogs, a paint backend, and OS-event translation. If a type from GTK or AppKit ever appears in core, the boundary has leaked.

## Components

### wolf-core

Platform-agnostic Rust. Contains everything Neovim-related and all app logic that is not inherently platform-specific.

Responsibilities:

- Spawn and supervise the captive `nvim --embed` process; speak msgpack-RPC to it via [`nvim-rs`](https://github.com/KillTheMule/nvim-rs).
- **Detect a crashed or stalled captive Neovim and recover it PER PROJECT** (so the front-end window never freezes forever on its last frame silently dropping input). Core keeps a lock-free three-state LIVENESS (`Liveness { Alive, NotResponding, Dead }`, exposed as `WolfCore::liveness()`): a supervisor task owns the io loop and marks the nvim **`Dead`** on unexpected process death (stdout EOF, crash OR clean — suppressed only for an intentional shutdown), and the RPC-timeout chokepoint (`block_on_rpc`) escalates a repeated RPC timeout to **`NotResponding`** (a stall) and auto-clears it back to `Alive` on the next successful RPC (never resurrecting `Dead`). nvim's stderr is captured to the log. `WolfCore::restart_nvim()` restarts the captive Neovim IN PLACE (force-kill + reap the old child, respawn in the same cwd + config, re-run the full setup chain) and reports whether an actual restart happened. The captive nvim continuously mirrors its file-backed open buffers per tabpage (`Snapshot.open_files` / `WolfCore::open_files_for_tabpage`, fed by the `wolf_open_files` autocmd) so the front-end can capture them BEFORE a restart wipes the mirror and reopen them afterward — **Tier-1 open-file restore** (cursor/scroll + unnamed buffers out of scope). Unsaved edits survive a crash via Neovim's built-in **swap files**: `'swapfile'` is ON, `'directory'` is a durable per-project swap dir (`state::swap_dir_for`, STABLE across respawns so a fresh nvim finds the dead nvim's swap), and a recovery-aware `SwapExists` autocmd silently recovers a DEAD owner's edits (`v:swapchoice="r"`) while a LIVE/other-host owner edits the clean copy (`"e"`) — never a blocking prompt. Known limits: SIGKILL/OOM skips `preserve_exit` (a bounded loss window since the last swap sync), and the GLOBAL open-file mirror over-reopens across a multi-view restart. Only the macOS front-end surfaces this (crash/stall overlay + "Restart Neovim" button); it is NOT yet wired into the GTK front-end.
- Attach as a UI (`nvim_ui_attach` with `ext_linegrid` + `ext_multigrid` + `ext_popupmenu` + `ext_messages` + `rgb`; `ext_messages` implicitly enables `ext_cmdline` and forces `cmdheight=0`) and handle the entire `redraw` event stream, including the multigrid window events (`grid_resize`/`grid_line`/… carrying a grid id, plus `win_pos`, `win_viewport`, `win_hide`, `win_close`, `grid_destroy`) and the native command-line / popup / message events (`cmdline_show`/`_pos`/`_hide`, `popupmenu_show`/`_select`/`_hide`, `msg_show`/`msg_clear`/`msg_history_show`).
- Maintain the **multigrid render-state model** — the in-memory description of what should be on screen: MULTIPLE cell grids keyed by grid id, with per-window grids and the outer grid (grid 1, now emptied under `cmdheight=0`), plus the native command line / completion popup / message toast folded into `Snapshot.cmdline` / `Snapshot.pum` / `Snapshot.toast` (see "The core↔front-end contract").
- Own a **Neovim→shell intent channel**: the captive nvim's split/focus chords and Ex-commands are overridden (in the bundled `init.lua`) to `rpcnotify` `wolf_layout` (and `wolf_active_win`) messages; core parses these into `LayoutIntent`s on a drainable queue (`WolfCore::drain_intents`) and tracks the active window (`Snapshot.active_win`), so the front-end can own the native pane layout.
- Own a **Neovim→shell command channel** (generalizing the intent channel): a canonical, GUI-free command registry (`wolf_core::command` — `Command` + `COMMAND_SPECS`, one canonical snake_case id deriving both a `:Wolf<Pascal>` Ex-command and a `require('wolf').<snake>()` Lua function). `init.lua`'s `_G.wolf_setup_commands` registers both faces so a user-triggered command `rpcnotify`s `wolf_command`; core folds the id into a `Command` on a drainable queue (`WolfCore::drain_commands`), which the front-end maps to a native action. Commands are user-triggered only (no emit-on-attach). See "Output: commands" under the core↔front-end contract.
- Translate abstract input events (key, mouse, scroll, resize) into Neovim input (`nvim_input`, `nvim_input_mouse`) and Ex commands.
- Own app-level semantics: open/save (delegated to Neovim), recent files, and the hermetic launch/isolation of the captive Neovim.
- Maintain a **most-recently-used (MRU) file cache** — a single global SQLite database at `state_dir()/file-mru.sqlite` — recording every opened file and pruning entries whose backing file has been deleted. Reads are synchronous (the cache loads instantly). The cache is **per-project by directory FILTER**: every row carries the project `directory` it was recorded under, and both seeding the picker and recording opens use the captive Neovim's live working directory (the `wolf_cwd`/`DirChanged`-tracked cwd) as that `directory` scope, so `recent(directory)` returns only the active project's files and their `display` strings stay relative to it.
- Maintain a **global recent-directories MRU cache** (`wolf_core::recent_dirs`) — a single SQLite database at `<state_dir>/folder-mru.sqlite` (macOS `~/Library/Application Support/Wolf`, `WOLF_STATE_DIR` overrides), parallel to the per-project MRU above but GLOBAL and keyed on the directory path. Every directory the captive Neovim changes into — via the "open folder" command or a typed `:cd`/`:lcd`/`:tcd` — is moved-or-added to the top from the same `wolf_cwd`/`DirChanged` fold point, newest-first and capped at `RECENT_DIRS_LIMIT` (20). The passive launch/initial cwd is deliberately EXCLUDED: the one-shot setup-time `wolf_cwd` emit is flagged and tracked-only, so it never records into this MRU — only directories the user actually opened appear in Open Recent. The store is **always-on** (constructed once at `WolfCore::start` from `state_dir()`, not attached like `StateStore`) and deliberately transient/disposable: any open/schema/query failure silently deletes the sqlite file (plus its `-wal`/`-shm` sidecars) and recreates the schema — never an error, only a `tracing::debug!` log. `WolfCore::recent_dirs()` reads it back (it also feeds the command palette below).
- Maintain a **global command-palette MRU cache** (`wolf_core::command_mru`) — a single SQLite database at `<state_dir>/command-mru.sqlite`, a near-clone of the recent-directories MRU but keyed on an OPAQUE command KEY string (a static command's registry `id`, or a dynamic `switch_window:<cwd>` / `open_recent:<path>` key) and capped at `COMMAND_MRU_LIMIT` (100). Unlike the two MRUs above, NOTHING auto-records into it: it is wired into `WolfCore::start` (always-on, or `CommandMru::disabled()` when `state_dir()` cannot be resolved) but is deliberately NOT cloned into the redraw handler, so a fresh store reads back EMPTY — only an explicit command-palette activation (`record(key)`, over the FFI) writes to it, floating recently-used commands to the top. Same lazy-creation / delete-and-recreate self-heal as the recent-directories MRU. `WolfCore::command_mru()` hands out a cheap `Arc`-backed clone the palette reads/records through, and the pure `wolf_core::palette::rank_palette` assembles the palette candidate rows (all `COMMAND_SPECS` except `CommandPalette` + one row per OTHER open window + one per recent dir) and ranks them MRU-first by reusing `rank_matches` unchanged.
- Drive an **asynchronous, streaming file-list traversal** of the working directory (the picker's source): a `FileSearch` session that seeds the MRU synchronously then walks the tree on the tokio runtime (via the `ignore` crate — respecting `.gitignore`, excluding `.git/`/`.wolf/`, including untracked files, plain files and symlinks-to-files only), streaming results to the front-end. A pure ranking function orders results (case-insensitive, MRU-first, with a filename-word strict-prefix preference).
- Assemble the **buffer-picker** candidates (`wolf_core::buffer_picker`) — a palette-shaped counterpart to the file picker but with candidates FIXED at open (no streaming). A blocking `WolfCore::list_buffers()` query snapshots the captive nvim's `buflisted` buffers (`getbufinfo({'buflisted': 1})` → `Vec<BufInfo { bufnr, name, lastused, modified }>`), and the pure, GUI-free `rank_buffers(buffers, cwd, query, max)` MRU-orders them by `lastused` DESC (tie-broken by `bufnr` ASC, current buffer first), projects each to a cwd-relative (else absolute, else `[No Name]`) display string, and ranks them best-first by reusing the SAME `rank_matches` the file picker and palette use — headlessly testable, view-agnostic. Activation feeds back in as a `switch_buffer(win, bufnr)` — an `InputEvent::SwitchBuffer` on the ordered input channel that invokes the captive `init.lua`'s `wolf_switch_buffer` helper (a window-scoped `nvim_win_set_buf`, NOT `:edit`, so it never disturbs `current_file` / the file-MRU or re-reads from disk). Per-pane scroll/cursor **view restoration lives ENTIRELY in `init.lua`** (core stays view-agnostic — no `winsaveview` payload crosses the boundary); see the note under "Output: commands".
- Track the **currently-edited file** and expose it on the snapshot (`Snapshot.current_file`), updated via the `wolf_current_file` autocmd notification (see "The core↔front-end contract"), so a front-end can highlight and reveal it (e.g. in a file-tree sidebar) after either picker- or Neovim-driven navigation.
- Track **per-window buffer paths** on the snapshot (`Snapshot.buffers`, keyed by window handle), updated wholesale via the `wolf_buffers` autocmd notification, and expose `WolfCore::pane_status(grid)` — a pure grid → window → path join formatted as a `(filename, display_path)` pair — so the macOS front-end can draw a per-pane statusbar. The same notification (now a five-element tuple carrying the bufnr and two terminal flags) wholesale-fills a PARALLEL `Snapshot.win_buffers` map — `WinBuffer`-valued, keeping unnamed windows with `path: None` — which exists so the navigation history below can be derived without changing `buffers`' shape or behavior for its existing consumer.
- Own the **per-pane file navigation history** (back/forward), the single source of truth behind the macOS History menu and its two toolbar buttons. The pure, GUI-free, IO-free `wolf_core::nav_history` module holds the model — a per-nvim-WINDOW visit log with browser semantics (new navigation from a mid-stack cursor truncates ahead of it), capped at 100 entries, keyed on a `NavTarget` (`Edit` / `Preview` / `Terminal` / `Untitled`, so previewing the file you are editing is a distinct entry), plus the PREFIX-form minimal-growth label pipeline that renders at most 10 distinct menu rows. It lives in a sibling `Arc<Mutex<NavHistory>>` cell (like `IntentQueue` / `TrackedCwd`, NOT on the `Clone`-per-frame snapshot); `RedrawHandler` FOLDS a derived per-window target into it after every `wolf_buffers` / `wolf_preview` emit (a window present in NEITHER map yields no entry, no push and no prune, which makes the two notifications' arrival order irrelevant during a preview transition) and PRUNES a pane's stack on `win_close`. A push is triggered by ANY change to a pane's current file, including navigation Neovim performs itself; the terminal drawer is excluded; nothing is persisted across restarts and the front-ends hold no copy. Six `WolfCore::history_*` methods read and move it, each move arming a per-pane `expected` BEFORE the RPC so the echoed emit is absorbed rather than pushed, and reverting the cursor when the nvim-side helper reports failure. The moves are window-scoped `nvim_win_set_buf` (never `:edit`), so they never disturb `current_file` or the file MRU. Deliberately NOT cursor-position history — Neovim's own jumplist (`<C-o>` / `<C-i>`) is untouched. wolf-gnome gets this core surface for free; there is no GTK UI for it yet.
- **Persist the application-state TREE** (`wolf_core::state`): a pretty-printed `state.json` in the platform state dir (`~/Library/Application Support/Wolf` on macOS, `~/.local/state/wolf` on Linux; `WOLF_STATE_DIR` overrides) holding a list of windows — each with geometry plus its ordered list of tabs, each tab carrying its own cwd + sidebar visibility. Loading is infallible and strictly read-only (an absent/corrupt/wrong-version file — or an OLD flat pre-tabs window with no `tabs`, which has NO migration path — is **silently ignored**: defaults, never an error, bytes untouched); all writes are serialized through a single dedicated writer thread per `StateStore` (`set_snapshot` swaps the whole tree ONLY when it changed and coalesces ~100 ms into one atomic tmp+rename write, so no concurrent writes ever and a crash never leaves a partial file). The FRONT-END owns all writes: the macOS coordinator walks its live windows/tabs and commits the whole tree via the `wolf-ffi` snapshot builder. Core no longer mirrors cwd into a store (`attach_state_store` is removed) — each tab's cwd is read live (over the FFI `cwd()` accessor) at snapshot time. A future wolf-gnome consumes the same API directly — `state_dir()` + `StateStore::open` + `set_snapshot`.

Responsibilities it explicitly does **not** have: deciding what text or colors appear (Neovim does), drawing pixels (the front-ends do), or knowing about windows, menus, or dialogs (only that it may _request_ them via intents).

### wolf-ffi

The swift-bridge boundary crate (Rust). It is the seam between the platform-agnostic core and the macOS front-end: it holds the single `#[swift_bridge::bridge]` module and the hand-written Rust glue behind it, and depends on `wolf-core` as a normal crate. It is built both as a `staticlib` (the archive the `.app` links through the generated Swift) and as an `rlib` (so a Rust integration test can drive the same surface headlessly, with no Swift present).

swift-bridge is **confined to this crate** — `wolf-core` gains no new dependency and stays GUI-free, and the Linux/GTK front-end keeps consuming `wolf-core` directly. The bridge surface re-shapes core's API for FFI: a structured `FfiKeyEvent` (mapped into a `wolf_core::KeyEvent` in Rust so nvim notation stays core's job), an opaque per-frame `FfiFrame` whose cells are resolved against the highlight table in Rust (never re-resolved in Swift), and an opaque main-thread-only `WolfCoreHandle`. The picker is fed the same way: a `start_file_search()` session handle (`FfiFileSearch` / `FfiFileEntry`) whose ranking runs in Rust, plus an `open(path)` input. The file-tree sidebar reuses that session shape: a separate `start_tree_search()` handle exposes the **same** pure hierarchical projection (`wolf_core::tree`) over the bridge — `FfiFileSearch::children_of(dir)` → opaque `FfiTreeNode`s, `rel_path_for(abs)`, the free `wolf_ffi_ancestors_to_reveal(rel)`, and `WolfCoreHandle::current_file()` for the reveal. The **split-pane** surface is bridged the same way: `WolfCoreHandle::read_frame_for_grid(grid)` (per-grid paint-ready frames, so each pane paints its own window grid and a bottom strip paints outer grid 1 — `FfiFrame` gains `grid_id()` / `cursor_grid()` and a **per-grid** `cursor_visible`), `drain_intents()` → opaque `FfiLayoutIntent`s, `windows()` → opaque `FfiWinInfo`s, `grid_for_win(win)`, `active_win()`, `focus_win(win)`, and `resize_grid(grid, cols, rows)`. `FfiLayoutIntent` / `FfiWinInfo` are opaque (Vectorizable) for the same reason `FfiTreeNode` is, and their discriminant tables (`intent_kind` SPLIT=0 / FOCUS_DIR=1 / DRAWER_OPEN=2, `orientation` HORIZONTAL=0 / VERTICAL=1, `focus_dir` LEFT/RIGHT/UP/DOWN = 0/1/2/3) are the single source of truth shared with the Swift `PaneTree` port and the test suites. The **per-pane statusbar** is bridged the same way: `WolfCoreHandle::pane_status_for_grid(grid)` → an opaque `FfiPaneStatus` (`filename()` / `display_path()`) delegating to `WolfCore::pane_status(grid)`, which joins the grid → window → the `Snapshot.buffers` path and formats it over nvim's live cwd + home. The **per-pane navigation history** is bridged by six additive `WolfCoreHandle` methods (no discriminant table changed): `history_can_back(win)` / `history_can_forward(win)` (cheap, no-RPC reads the front-end can call on every render wake to enable/disable the toolbar buttons), `history_back(win)` / `history_forward(win)` / `history_jump(win, index: u32)` (each blocking briefly on the captive nvim and returning whether the pane actually MOVED — `false` at the ends of the stack, for an out-of-range index, for the cursor's own index, on error, or when the core is gone), and `history_entries(win) -> Vec<FfiHistoryEntry>`, whose rows are opaque for the usual `Vec<T>`-needs-opaque-`T` reason and expose `display()` / `index()` / `is_current()`. Ordering, the 10-distinct-row cap, the label disambiguation and the home abbreviation all happen in `wolf-core`, so Swift only zips and draws; a shut-down core yields `false` / an empty `Vec`. The **command channel** is bridged the same way: `WolfCoreHandle::drain_commands()` → opaque `FfiCommand`s (`kind() -> u8`), whose `command_kind` discriminant table (NEW_WINDOW=0 / CLOSE_WINDOW=1 / QUIT_APPLICATION=2 / HIDE_APPLICATION=3 / MINIMIZE_WINDOW=4 / GO_TO_FILE=5 / OPEN_FILE=6 / OPEN_FOLDER=7 / CLOSE_PANE=8 / NEW_BUFFER=9 / RESET_FONT_SIZE=10 / INCREASE_FONT_SIZE=11 / DECREASE_FONT_SIZE=12 / COMMAND_PALETTE=13 / COPY=14 / PASTE=15 / BUFFER_PICKER=16 / NEW_TAB=17 / PREVIEW=18 / EDIT=19 / TERMINAL=20 / PREVIEW_IN_BROWSER=21 / FULL_WIDTH=22 / TOGGLE_SIDEBAR=23 / SIDEBAR_SHOW_PROJECT=24 / SEARCH_IN_PROJECT=25; APPEND-ONLY, `CLOSE_PANE` renamed in place from the old `CLOSE_FILE`) is the single source of truth shared with the Swift `CommandKind` port and the test suites. `WolfCoreHandle` gains `close_pane()` (`:close`), `new_buffer()` (`:enew`) and `toggle_terminal()` (the per-project terminal drawer, an `InputEvent::ToggleTerminal`) methods for the native-menu face; the three `*FontSize` commands have no handle method (front-end-only). The **Edit** commands COPY (14) / PASTE (15) form a new Edit menu (Copy ⌘C / Paste ⌘V, its only two entries): `WolfCoreHandle` gains `copy_selection() -> String` (yanks the visual-mode selection over RPC — via the blocking `WolfCore::copy_visual_selection` — for the front-end to write to `NSPasteboard`), `paste(String)` (reads back from `NSPasteboard` and inserts via `nvim_paste`), and `is_visual_mode() -> bool` (gates the Copy menu item, since the captive nvim is `--clean` and the front-end owns the system clipboard, bridging it to/from nvim). The **command palette** rides its own opaque session: `WolfCoreHandle::command_palette()` returns an `FfiCommandPalette` seeded with `recent_dirs()` + `command_mru()`, fed the OTHER open windows one at a time via `add_window(index, cwd)` (no bridge fn takes a `Vec` argument), exposing `ranked(query, max) -> Vec<FfiCommandRow>` (assembly + MRU-first ranking in Rust via `rank_palette`) and `record(key)`; each `FfiCommandRow` flattens a `PaletteRow` (`display` / `row_kind` / `command_kind` / `window_index` / `path` / `mru_key`), its `row_kind` packed via a new `mod palette_row_kind` (STATIC=0 / SWITCH_WINDOW=1 / OPEN_RECENT=2), the single source of truth shared with the Swift `PaletteSeam.PaletteRowKind` port. There is no wake for the palette — candidates are fixed at open and `ranked()` re-filters synchronously. The **buffer picker** rides its own opaque session the same shape: `WolfCoreHandle::buffer_picker()` returns an `FfiBufferPicker` seeded by a BLOCKING `list_buffers()` snapshot of the captive nvim's listed buffers plus the live cwd, exposing `ranked(query, max) -> Vec<FfiBufferRow>` (MRU-ordering + ranking in Rust via `rank_buffers`); each `FfiBufferRow` carries `bufnr` / `display` / `modified`. Activation is a HANDLE method, `WolfCoreHandle::switch_buffer(bufnr)`, which resolves the active window LIVE from the snapshot and issues an `InputEvent::SwitchBuffer { win, bufnr }`. Like the palette there is NO wake — candidates are fixed at open and `ranked()` re-filters synchronously. Commands ride the existing editor render wake (no new wake channel), so `wolf_ffi_wake.h` is unchanged (the `close_buffer`→`close_pane` rename + the added `new_buffer` change only the generated `wolf-ffi.swift` / `wolf-ffi.h`). The wake crosses the boundary as a globally registered `extern "C"` callback (`wolf_ffi_set_wake`), not an `extern "Swift"` symbol, so the headless Rust test still links; a second registered wake (`wolf_ffi_set_filesearch_wake`) drives the picker, and a third (`wolf_ffi_set_tree_wake`) drives the sidebar, both independently. Each callback carries the firing core's per-PROJECT `wake_token` (a `u64` minted in `wolf_ffi_start`), so ONE process-global callback per channel routes each wake to the right PROJECT (the multi-project wake layer) — the front-end looks the token up in its `WindowRegistry` (token→`Project`) and fans the wake out to that project's views — the editor RENDER wake and the picker wake to its CURRENT view only, but the file-TREE wake to ALL of the project's views' sidebars (each view runs its own independent `start_tree_search()` traversal and the per-project token carries no view discriminator, so every attached sidebar must refresh on each batch). The **project/tabpage-per-view** model is bridged by six additive `WolfCoreHandle` methods (no discriminant table changed): `create_tabpage(cwd)` / `current_tabpage()` (the first-view bind) / `active_tabpage()` (the cheap `Snapshot.current_tabpage` refocus gate) / `cwd_for_tabpage(tab)` (a non-current view's tab-local `:tcd` cwd) / `set_current_tabpage(tab)` / `close_tabpage(tab)`; they ride the existing editor wake, so `wolf_ffi_wake.h` stays byte-identical. The user-level preferences are bridged the same standalone way: the free `wolf_ffi_load_config()` (no live session, does not hang off `WolfCoreHandle`) returns an opaque `FfiConfig` (`font_family()` / `font_size()` / `line_height()`) delegating to `wolf_core`'s GUI-free `config` module (`preferences_dir().map(load_or_create).unwrap_or_else(default_config)`), which the macOS front-end reads once at launch to drive the cell metrics. The **application state** is bridged the same standalone way plus a write-side builder: the free `wolf_ffi_load_state()` (the pre-start restore read — it never creates the file and never opens the live store) returns an opaque `FfiState` whose `windows()` are opaque `FfiWindowState`s (geometry + `tabs() -> Vec<FfiTabState>`, each `cwd` / `sidebar_visible`), while the live save path is a set of free functions over the process-wide `SHARED_STORE` (opened once at `state_dir()`; shared so multiple windows never race the writer thread) plus a `Mutex` scratch tree — `wolf_ffi_state_snapshot_begin` / `add_window(x,y,w,h)` / `add_tab(cwd, sidebar)` / `commit` (a whole-tree `set_snapshot`) / `wolf_ffi_state_flush`. `wolf_ffi_start(init_lua, cwd, cols, rows)` is now 4-arg (no `window_index` / no per-core store attach); the coordinator walks the whole window/tab tree and commits it (an identical tree is a no-op, so redundant snapshots cause no disk churn). The generated Swift + C bindings are **committed** under `crates/wolf-ffi/generated/` and refreshed by an explicit Bazel codegen target. See [`crates/wolf-ffi/README.md`](crates/wolf-ffi/README.md).

### Platform front-ends: wolf-gnome, wolf-macos

The UI layer. Each one:

- Paints the render-state model produced by core.
- Provides native window chrome: title bar / header bar / menus, scrolling, file dialogs.
- Translates OS input events into core's abstract input events.
- Queries the OS theme/accent color and pushes it into Neovim's highlight groups (so selection, etc., match the native look — see "Theming").
- Bridges its native event loop to core's async runtime.

#### wolf-gnome

Rust, using GTK 4 and libadwaita. Consumes `wolf-core` as a **normal Rust crate dependency**. Should feel like a GNOME application.

**Phase status.** The windowed application now exists: an `adw::ApplicationWindow` (with an `adw::HeaderBar`) whose editor area is a **native pane view** — a tree of nested `gtk::Paned`s, one `gtk::DrawingArea` per Neovim window, driven by a pure `PaneTree` layout — with a bottom **cmdline strip** that paints the native command line / messages from the folded `Snapshot.cmdline` / `Snapshot.toast` (grid 1 is emptied by `cmdheight=0`; the Adw completion popup + multi-line toast are deferred for GTK). The layout is an **N-ary frame model** (matching Neovim): a split in the SAME orientation as its containing frame FLATTENS into equal-sized siblings (so vsplitting one of two side-by-side panes yields three equal columns, not a 25/25/50 nesting), while a PERPENDICULAR split nests. The pure seams (`gdk_key`, `paint`, `grid_size_for`), verified headlessly without a display, are wired onto a live `WolfCore`: each pane paints its own window grid via Cairo/Pango and the pane owning the cursor's grid overlays a mode-aware cursor (a block in normal mode, a thin bar in insert mode, driven by `ModeInfo.shape`), drawn opaque with reverse-video colors so it is reliably visible; key input flows through a `gtk::EventControllerKey` to nvim's current window globally; each pane / divider resize maps pixels to a grid size and calls `WolfCore::resize_grid`; on each wake the front-end drains `WolfCore::drain_intents` to create/split/close/focus panes and reads `Snapshot.active_win` to mark the active pane; and the core's wake is marshalled from its tokio worker thread onto the GTK main thread (via an `async-channel` drained by `glib::spawn_future_local`) to trigger redraws. Splits (`<C-w>s`/`v`, `:split`/`:vsplit`), close (`<C-w>c`), focus moves (`<C-w>h/j/k/l`), and divider drag-to-resize all work. A built-in **file picker** (opened with **Ctrl+Shift+P** or a header-bar Open button) floats over the editor as a textbox + fuzzy-matched list, fed by core's streaming `FileSearch` + ranking and opening the selected file into the active pane via the `open(path)` intent (recorded in the MRU); there are still no native file dialogs, and saving is from within Neovim. A **file-tree sidebar** occupies the left of a `gtk::Paned` (the pane view on the right): a `gtk::ListView` + `gtk::TreeListModel` populated by the **same** `FileSearch` mechanism as the picker (a hierarchical projection of that flat file list), where a single click opens a file, the top level is expanded by default, and the file being edited is highlighted and revealed (ancestors expanded + scrolled into view) after both picker and Neovim `:e` navigation via `Snapshot.current_file`. The command line + messages are now NATIVE (folded core-side and painted from `Snapshot.cmdline` / `Snapshot.toast` in the bottom strip: an active command line, or the last toast line when idle), but the Adw **completion popup** (`ext_popupmenu`) and a **multi-line scrollable toast** (`ext_messages`) remain DEFERRED for GTK (OD4) — GTK shows a single strip row and no popup. Still deferred: native file dialogs, theming, mouse/scroll input, those two Adw widgets, floating windows, and HiDPI scale handling. See the known-limitations note in [`crates/wolf-gnome/README.md`](crates/wolf-gnome/README.md).

#### wolf-macos

Swift, using AppKit. Consumes `wolf-core` through the generated **swift-bridge** surface in [`wolf-ffi`](#wolf-ffi). Should feel like a macOS application.

**Phase status.** The windowed application now exists: a **multi-window AppKit shell** whose editor area is a **native pane view**, at or ahead of parity with the GNOME shell. Under a **one-Neovim-per-PROJECT** model, a `Project` is one captive Neovim (one core / `WolfCoreHandle`) shared by N **views**, each view (a `WolfWindowController` = one `NSWindow`) bound to one nvim **TABPAGE**; only the focused view live-updates while the others hold their last painted frame until refocused. An `NSApplication` + `AppDelegate` **coordinator** does the once-only launch setup and holds `projects: [Project]` + `controllers: [WolfWindowController]`. `Project.start(...)` is the SOLE caller of `wolf_ffi_start(init_lua, cwd, cols, rows)` (4-arg); the first view binds the fresh nvim's implicit tabpage 1 (`bindFirstTabpage`) and a joining view creates a fresh one (`addTabpage(cwd)` → `create_tabpage`). Each view owns its `NSWindow` (a shared `tabbingIdentifier` merges them into one native Tahoe `NSWindowTabGroup`, Finder/Safari-style) and its editor-area `PaneContainerView`. **⇧⌘N** (File > New Window) ALWAYS opens a new EMPTY-STATE standalone window — a NEW project (a fresh nvim) with one view (no folder — it ignores the frontmost window's cwd; nvim launches at home underneath), **⌘T** (File > New Tab / `:WolfNewTab`, or the native "+" via `newWindowForTab:`) opens a new VIEW of the key window's SAME project (a new tabpage in that shared nvim) inheriting its folder, and plain **⌘N** is File > New (a new buffer in the current window named the next free `Untitled N.md` — markdown-typed, unsaved, via `wolf_new_untitled`); tear-off, drag-to-merge, and drag-to-reorder are the native default (no suppression — a tear-off KEEPS the view's project + tabpage). Each project's wakes route back through its per-PROJECT `wake_token` looked up in `WindowRegistry` (token→`Project`), which fans the RENDER and picker wakes out to its CURRENT view but the file-TREE wake to ALL of its views' sidebars (each view runs its own independent `start_tree_search()`), so two projects never clobber each other. Closing a view runs `:tabclose`; the project's nvim shuts down only when its LAST view closes. **Crash/stall recovery is surfaced per project:** `Project.onWake` reads `handle.liveness()` FIRST on each wake — a `Dead` core fans a "Neovim crashed — restarting…" overlay (`NvimStatusOverlayView`, a full-bleed opaque overlay with a "Restart Neovim" button, modeled on `EmptyStateView`) to ALL of the project's views and AUTO-restarts, a `NotResponding` core fans a "Neovim stopped responding" overlay and waits for the user's manual button, and an `Alive` core hides the overlay and renders normally. `Project.restartNeovim` CAPTURES each view's Tier-1 open files (`open_files_for_tabpage`) + cwd BEFORE calling `handle.restart()`, and only when `restart()` reports an ACTUAL restart (`true`) rebinds each view to a fresh tabpage (`WolfWindowController.rebind(toTabpage:)` → `PaneContainerView.rebind(tabpageHandle:)`, re-gating the refocus rebind) and reopens the captured files (active LAST so it lands focused); on a no-op / failed restart it instead refreshes the overlay from a fresh `liveness()` read (the `.dead` overlay keeps its Restart button for a user-driven retry). After a successful restart hides the overlays, it fans a small, transient, auto-dismissing "Neovim was restarted" banner (`NvimRestartedBannerView`, ~4s) to every view — a post-restart confirmation over the now-working editor that is INDEPENDENT of the full-bleed liveness overlay (the fresh nvim's `Alive` wake clears the overlay but never the banner, which self-dismisses on its own timer). Each view's cwd is its tabpage's `:tcd` (`InputEvent::Chdir` → `:tcd`, per-view); a view becoming key drives `project.setCurrent` (a `set_current_tabpage` switch) then a **refocus rebind** that re-derives its pane→grid bindings on the preserved `PaneTree` (nvim WINDOW handles survive a tabpage switch, only grid ids churn), gated on `handle.active_tabpage() == tabpageHandle` (`Snapshot.current_tabpage`). The coordinator OWNS the whole-tree state snapshot (a coalesced ~150ms walk of every window/tab group, each tab's cwd its view's tab-local `persistedCwd` via `cwd_for_tabpage`, committed via the `wolf-ffi` snapshot builder) and restore (**two-phase group-by-cwd**: the pure `RestoreSeam.plan` groups the saved tree into projects by cwd — merged across windows, each empty-state/deleted-dir tab its own project per OD5 — Phase A materializes projects + views, Phase B anchors the first tab's frame and `addTabbedWindow`s the rest; project identity is NOT persisted, so a project is SPLIT/MERGED by cwd on restore), and refreshes each tab's title from its WORKING DIRECTORY (home abbreviated to `~`) via the pure `CwdTitleSeam`, setting a matching `representedURL` proxy icon (the filename-basename title + disambiguation is retired). Closing one window/tab leaves the others live; closing the last quits. A native **NSMenu app menu bar** (`AppMenu` — App / File / Edit / View / History / Window, History sitting BETWEEN View and Window as the conventional place for a navigation menu) drives the static command set (New `⌘N`, New Window `⇧⌘N`, New Tab `⌘T`, Go to File `⌘O`, Open File, Open Folder `⇧⌘O`, Close `⌘W` = `:close`, Close Window `⇧⌘W`, Copy `⌘C` and Paste `⌘V` on the new Edit menu, Reset/Increase/Decrease Font Size `⌘0`/`⌘=`/`⌘-`, Command Palette… `⌘P`, Buffer Picker… `⌘E`, Preview (no key equivalent, on the View menu, enabled only on a Markdown buffer), Edit Source (no key equivalent, on the View menu, enabled only in a preview pane), Minimize `⌘M`, Hide `⌘H`, Quit `⌘Q`) — plus the View menu's net-new **Enter Full Screen** `⌃⌘F` (a STANDARD AppKit `toggleFullScreen:` item, NOT a Wolf command, flagged per CLAUDE.md), the **History** menu (Back `⌘[` / Forward `⌘]` / separator / a DYNAMIC newest-first list of the active pane's ≤10 most recently visited files, checkmarked on the current one and clickable to jump there — front-end-only items with NO `command_kind`, like Toggle Sidebar, rebuilt from core at menu-open time via `NSMenuDelegate.menuNeedsUpdate` exactly as Open Recent is, since Wolf holds no copy of the history), and a DYNAMIC Window-menu tail of one item per open window (titled with its cwd, raising it); every command menu item AND every nvim-drained `:Wolf*` / `require('wolf').*` command funnels through the ONE `CommandDispatcher` (decision 10), with the menu path targeting `NSApp.keyWindow` and the nvim-drained path (`WolfWindowController.drainAndDispatchCommands`) the draining window itself. The View font-size commands are per-window and EPHEMERAL (each `WolfWindowController` owns its own point size + `CellMetrics`, re-measuring and reflowing the grid inside the unchanged frame; not persisted), and the `AppDelegate` (an `NSMenuItemValidation`) disables Close on the last split (`paneCount <= 1`, Neovim's E444) and disables Edit > Copy unless the key window is in Neovim visual mode (`isVisualMode`). That container is a **single flat `NSView`** (flipped, so grid row/col map directly to points) that paints EVERY pane itself — deliberately NOT a tree of nested `NSSplitView`s, which composited unreliably; painting one flat view is the proven `GridView` pattern. It drives its painting from a pure `PaneTree` layout (a Foundation-only Swift port of wolf-gnome's `layout.rs`, living in the headlessly-tested `WolfKeyMap` module): each `draw(_:)` computes every pane's rectangle via `PaneTree.paneRects` and, for each bound pane, clips+translates to that rect and paints the pane's window grid via `read_frame_for_grid` — filling every cell's background, drawing its glyph via CoreText/CoreGraphics in the per-cell foreground color (both colors resolved from wolf-core's highlight table in Rust), and overlaying a **mode-aware reverse-video cursor** (a block, horizontal, or vertical bar driven by `cursor_shape`, with the fill/glyph colors also resolved in Rust, ported from wolf-gnome's `cursor.rs`) — but only on the pane owning the cursor's grid (per-grid `cursor_visible`). Every pane's body is painted **identically whether active or inactive**; the active/inactive distinction is carried entirely by the statusbar text (the active pane's filename is bold at full strength, an inactive pane's is regular-weight with both statusbar lines dimmed — a front-end-only treatment that is awkward to express inside Neovim itself), and thin separators are stroked between adjacent panes. Each pane also reserves a **top statusbar strip** (its height + line layout from the pure, headlessly-tested `StatusbarLayout` seam): a titlebar-matched background (the window's own `backgroundColor`, kept in sync with the `WolfTitlebar` theme) with the pane's base filename above its display path (cwd-relative, `~`-prefixed, or absolute), read from `WolfCoreHandle::pane_status_for_grid(grid)` — so the grid paints into the pane MINUS the strip, and the strip's filename is bold at full strength on the active pane and regular-weight + dimmed on an inactive one. This is another front-end-only treatment (GNOME is out of scope for the statusbar). The **native command line / completion popup / message toast** are painted as three dedicated overlay `NSView`s composited over the bottom of this view — a `CmdlineView` (bottom, spanning the row), a `CompletionPopupView` (anchored directly above it at the cmdline byte column), and a bottom-left scrollable `ToastView` (10-line cap) — refreshed from `handle.cmdline()` / `pum()` / `toast()` on each render wake and shown only while active (overlay-when-active, OD9; the panes keep the full view height under `cmdheight=0`). The former grid-drawn cmdline strip is GONE. A click hit-tests the pane rects and focuses that pane's window; a scroll gesture over the visible toast scrolls IT (and is withheld from Neovim, so the toast is not dismissed — the scroll-over-toast exemption), while every other scroll forwards and dismisses the toast. On each render wake the container drains `WolfCore::drain_intents` to create / split / close / focus panes and reads `active_win()` to mark the active pane (whose statusbar filename is drawn bold), `syncGridSizes` maps grid 1 + each pane rect to a grid size and calls `resize` / `resize_grid` (only when the size differs from nvim's, so it converges), and key input flows through the container (the editor area's first responder + global key sink) to nvim's current window globally. Splits (`<C-w>s`/`v`, `:split`/`:vsplit`), close (`<C-w>c`), and focus moves (`<C-w>h/j/k/l`) all work, and **interior dividers are draggable to resize** (a deliberate divergence from GNOME): hovering a divider shows the resize cursor and dragging reweights the two adjacent children of the owning split, clamped so no pane's grid drops below 3 rows / 10 columns — hit-tested against the pure `PaneTree.dividers()` list in the flat view (no `NSSplitView`) via the pure `DividerHitTest` / `DividerDragSeam` seams + `PaneTree.setPairFraction`. The layout is the same **N-ary frame TOPOLOGY** as GNOME (matching Neovim): a split in the SAME orientation as its containing frame flattens into a flat sibling row, while a PERPENDICULAR split nests — but the macOS `PaneTree` weight policy diverges from GNOME in ONE place: a same-orientation split RE-EQUALIZES the row/column to equal shares (matching GNOME), while a REMOVE re-normalizes survivors PROPORTIONALLY (GNOME re-equalizes), so a user-dragged size survives an adjacent pane closing and tab switches (and, via persistence below, quit/relaunch). Font metrics are **config-driven**: the font-family, font-size, and line-height come from the user-level `wolf-config.yaml` preferences file (read in the GUI-free `wolf-core` `config` module, bridged to Swift as `wolf_ffi_load_config()` / `FfiConfig`), with **two fonts bundled** into the `.app` at `Contents/Resources/fonts/` and both CoreText-registered at launch (`FontRegistration.swift`) — **iA Writer Mono S** (the config default) and **JetBrains Mono** (bundled + registered but non-default) — a **Menlo** fallback when the configured family does not resolve, and `WOLF_FONT_PT` still overriding the point size (parity with gnome). `AppDelegate` registers the bundled fonts, loads the config, then measures the cell metrics from it, in that order. The config also carries an **`appearance`** key (`auto` / `dark` / `light`, default `auto`): `AppDelegate` resolves it right after loading the config (before any project starts) and drives every project's nvim to the resolved dark/light via `FfiConfig.appearance()` → `set_background` → `:set background=…` (which re-sources the colorscheme, re-firing the existing `wolf_theme` path). `auto` follows — and live-observes (KVO on `NSApp.effectiveAppearance`) — the OS appearance; `dark` / `light` force it (also setting `NSApp.appearance` so the app chrome matches). See "Theming". The config additionally carries a **`macos-option-as-alt`** key (default `false`): when `false` (**option-as-option**, mirroring Ghostty's default) the Option key composes accented characters — `PaneContainerView.keyDown` routes printable-candidate presses through a Carbon `UCKeyTranslate` dead-key composer (`KeyComposer`, gated by the pure `KeyComposition` seam) so Option-u then u sends `ü` to Neovim — while `true` restores the legacy option-as-alt behavior (`<M-…>` Alt mappings via `WolfKeyMap.translate`).

The redraw path mirrors gnome's, realized natively: core fires its wake on a tokio worker thread; `WakeBridge` (the registered `extern "C"` callback) hops it onto the AppKit main thread with `DispatchQueue.main.async` and calls the registered `PaneContainerView`'s `onRenderWake()` (a one-for-one port of wolf-gnome's `pane_view.rs::on_render_wake`: ensure the initial pane, apply drained layout intents, detect closed windows, resolve pending grids, refresh the active pane, sync grid sizes, refresh the command-line / completion-popup / toast overlays, then mark the single editor view for redisplay — repainting every pane in one `draw(_:)`), which drives the next paint. Input flows the other way: the container's `keyDown(_:)` pulls the `keyCode`/`characters`/`charactersIgnoringModifiers` + modifiers off the `NSEvent`, runs them through the **pure, AppKit-free** `WolfKeyMap.translate` seam into a structured `FfiKeyEvent`, and calls `send_key` — so the Shift contract is honored once, in Rust (`key_to_notation`), exactly as on Linux. View resizes map the current bounds to a `(cols, rows)` grid size and call `resize`. The captive Neovim is hermetic and **bundled inside the `.app`**: a pinned Neovim 0.12.3 tree at `Contents/Resources/nvim/` and the captive `init.lua` at `Contents/Resources/init.lua` (decision 8). `AppDelegate` points wolf-core at the bundled `nvim/bin/nvim` by setting `WOLF_NVIM_BIN` (only if a developer hasn't already exported it) and launches against the bundled `init.lua` (overridable via `WOLF_INIT_LUA`) — so a double-clicked `.app` runs with no shell environment.

A built-in **file picker** is realized (parity with gnome's): **Command+O** opens a floating picker (a search bar + `NSTableView`) hosted in its OWN borderless, non-activating child `NSPanel` composited IN FRONT of the editor window (via `addChildWindow(ordered:.above)`) — so it renders ABOVE the preview `WKWebView`, rather than being painted into the pane container's drawing surface (where a sibling web view composits over it on Tahoe). Positioning is the pure, headlessly-tested `PickerPanelSeam` (top-center, ~24pt below the content top, 600pt wide, content-driven height); the AppKit glue is the reusable `PickerPanel` + `PickerPanelHost`. It is fed by core's streaming `FileSearch` session over the FFI (`start_file_search` / `ranked` / `open`, with ranking staying in Rust). Command-modified keys are not Neovim keybindings, so the chord does not consume a Neovim key; typing filters the cwd's files (respecting `.gitignore`, MRU-first, case-insensitive, filename-word strict-prefix), Up/Down navigate, Enter (or a double-click) opens the selected file via the `open(path)` input event (recorded in the MRU), and Esc closes. The panel becomes KEY so the search field types (the borderless panel overrides `canBecomeKey`); its being key means keys are not forwarded to Neovim, and a **resign-key** — clicking outside the panel, Cmd-Tab, Mission Control, or activating another window/app — is the single dismissal funnel driving `close()` (same effect as Esc). While a picker panel is key the coordinator resolves owning-controller lookups through the panel's parent window (`effectiveKeyWindow = NSApp.keyWindow.parent ?? NSApp.keyWindow`). The accepted cosmetic tradeoff (OD1) is that the parent titlebar draws dimmed (Spotlight-style) while the panel is key.

A built-in **command palette** is also realized: **Command+P** (or the View-menu **Command Palette…** item, since ⌘P is a menu key-equivalent that preempts `keyDown`) opens a sibling picker (`CommandPaletteView`, reusing the picker's search-bar + table chrome, hosted in the same borderless non-activating child `NSPanel` via `PickerPanelHost` — front-of-window, `PickerPanelSeam`-positioned, dismissed on resign-key) fed by an opaque `FfiCommandPalette` session. It fuzzy-filters — MRU-first, via the same `rank_matches` — over all 19 OTHER static registry commands (the palette excludes itself; the Preview and Edit Source rows are always present — the palette does not gate them on the active buffer being Markdown / the active pane being a preview, unlike the menu items), one "Switch to Window" row per OTHER open window (empty-cwd windows labeled "Untitled"), and one "Open Recent Folder" row per recent dir. Activation records the row's opaque key in a new global command MRU (`<state_dir>/command-mru.sqlite`, in `wolf-core`) and then dispatches: a static command flows back through the SAME `CommandDispatcher`; a "Switch to Window" raises that window; an "Open Recent Folder" raises the already-open window for that path else chdirs the current one. Candidate assembly + ranking is pure `wolf-core` (`palette::rank_palette`); there is no wake (candidates are fixed at open and re-filter synchronously per keystroke).

A built-in **buffer picker** is also realized: **Command+E** (or the View-menu **Buffer Picker…** item) opens a further sibling picker (`BufferPickerView`, again reusing the picker's search-bar + table chrome, hosted in the same borderless non-activating child `NSPanel` via `PickerPanelHost` — front-of-window, `PickerPanelSeam`-positioned, dismissed on resign-key) fed by an opaque `FfiBufferPicker` session. It fuzzy-filters — MRU-first, via the same `rank_matches` — over the window's `buflisted` buffers (snapshotted at open, current buffer first, shown as cwd-relative paths), and preselects **ROW 2** on the initial empty-query open so a bare `<CR>` switches to the most-recently-used OTHER buffer (telescope-style, ~`Ctrl-^`). Activating a row calls `WolfCoreHandle::switch_buffer(bufnr)`, which switches the ACTIVE pane to that buffer via a **window-scoped `nvim_win_set_buf`** (NOT `:edit`, so it never disturbs the current-file / file-MRU semantics) and restores that pane's saved scroll/cursor **view** for the buffer (per-`(winid, bufnr)`, forcing the top of the buffer when the pane never showed it). Candidate assembly + ranking is pure `wolf-core` (`buffer_picker::rank_buffers`); there is no wake and NO MRU is recorded on activation.

A built-in **file-tree sidebar** is also realized (parity with gnome's), with the standard macOS source-list look: the window's `contentViewController` is an `NSSplitViewController` (`EditorSplitViewController`) whose leading split item is a `.sidebar` source-list item wrapping the `NSOutlineView` (`.sourceList` style, clear background) and whose trailing item wraps the editor `PaneContainerView`. The sidebar's translucent **full-height vibrancy** (the OS source-list material) extends under a **transparent `.fullSizeContentView` titlebar** with a **`.unified` `NSToolbar`** whose items run in the locked order **traffic lights → toggle sidebar → sidebar separator → back → forward → title**: the system toggle-sidebar button FIRST (so it lands in the toolbar's sidebar section at the top-left, not the trailing edge), then a **sidebar-tracking separator** aligned to the split divider, then the **Back** and **Forward** navigation buttons (SF-Symbol `chevron.backward` / `chevron.forward`, `isNavigational`, enabled/disabled per the active pane's history on each render wake — they carry `autovalidates = false` so that explicit enablement sticks, and they delegate to the window controller through an explicit `HistoryNavigating` protocol rather than the responder chain, which the controller is not part of), with the window title / cwd rendering in the content section to their right (the sidebar is toggled from EITHER that toolbar button or the View menu's **Toggle Sidebar** item, ⌃⌘S — the same `.toggleSidebar` action routed through the responder chain to the split VC; the toolbar is installed before the chrome height is measured so the grid stays exactly `cols` × `rows`); the editor pane is pinned **below the titlebar** (its host pins the grid's top to the safe-area guide) so it keeps its exact `cols` × `rows` cell size (the OCR-checked 80-col grid is undisturbed). It is fed by core's **same** streaming `FileSearch` over the FFI, but via its own long-lived `start_tree_search()` session and the pure hierarchical projection (`children_of` / `rel_path_for` / `ancestors_to_reveal`, all in `wolf_core::tree`): the cwd itself is shown as a single **synthetic root node** (its basename), **expanded on init**, with its immediate children (`children_of("")`) visible beneath it and their subdirectories collapsed — the VS Code / Snacks explorer model, **divergent from the GNOME tree** (which shows `children_of("")` directly at the root with no cwd node). The sidebar **follows Neovim's live working directory**: on each editor render wake it reads `WolfCoreHandle::cwd()` (nvim's already-canonicalized cwd, exposed over the FFI) and, when it changed (`:cd`/`DirChanged`), **re-roots** the tree — rebuilding the synthetic root and restarting `start_tree_search()` — mirroring how the picker re-roots on nvim's live cwd (`live_cwd()`, tracked out-of-band) each time it opens. A single click opens a file (then refocuses the editor) or toggles a directory, and the buffer being edited is bolded and revealed (ancestors expanded + scrolled into view) after both picker- and Neovim-`:e`-driven navigation, driven by `current_file()` read on each editor wake (the cwd is checked first, so a simultaneous cwd + buffer change reveals into the new tree).

**Application state persistence is realized on macOS** (the first front-end to adopt `wolf_core::state`), now including each tab's **full pane-split tree** (topology + per-child weights + per-leaf buffer path). At launch, `AppDelegate` reads the saved state (`wolf_ffi_load_state()`) BEFORE any core starts and restores by a **two-phase group-by-cwd** materialize (project identity is NOT persisted, so it is rebuilt from directories): the pure `RestoreSeam.plan` groups the saved `(window, tab, cwd)` tree into projects — one per distinct real cwd, MERGED across windows, each empty-state / deleted-dir tab its OWN project (OD5) — Phase A materializes each project's fresh nvim + its views, Phase B assembles the OS windows/tab-groups from the saved geometry (anchor the first surviving view's frame, `addTabbedWindow` the rest). The accepted consequence: a runtime project whose views `:tcd`'d to different dirs SPLITs on restore, and same-dir tabs from different runtime nvims MERGE — every restored project is uniform-cwd. Per TAB it asks the pure `StateSeam.launchDecision(restored:home:isDirectory:)` whether to open a folder or an empty state: an empty (`""`) or no-longer-existing restored cwd yields `.emptyState(nvimCwd: home)` (Wolf does NOT open the process working directory), while a valid directory yields `.folder(cwd:)`. An **empty-state** window hides the sidebar and shows a centered **"Open folder…"** button (`EmptyStateView`) over the editor, with Neovim launched at home underneath and a controller `hasFolder = false` flag tracking "no folder open"; a fresh launch with an empty state file, and every **⇧⌘N** New Window, is always empty state. A `.folder` tab launches the embedded Neovim at the restored cwd; the first tab of a group restores the window frame (via `StateSeam.restoredWindowFrame`, rejecting the unset sentinel and fully-offscreen frames) and each tab restores its sidebar collapsed state, all before the window is shown. A tab that saved a multi-leaf **pane layout** rebuilds it on the first render wake: `PaneContainerView.requestLayoutRebuild` realizes the nvim window topology via `WolfCoreHandle::rebuild_layout` (the `wolf_rebuild_layout` Lua helper's `:split`/`:vsplit`, then per leaf `:edit` for an editor buffer or `wolf_preview_file` for a **preview** leaf — recreating a Markdown preview of the saved source instead of a blank buffer — returning window handles in the SAME DFS/leaf order as the front-end tree) and rebuilds the pure `PaneTree` — WITH its saved weights — via `PaneTree.rebuilt(from:firstLeafId:)`, zipping each handle to its rebuilt leaf; the sizes come from the front-end weights (`syncGridSizes`), so both the splits AND their user-dragged sizes survive quit/relaunch, and a preview pane comes back as a preview rather than a blank editor. Opening a folder into an empty-state window (via the button, Open Recent, or a typed `:cd` into a new dir) runs the normal Open Folder path (dialog → `chdir`) and transitions the window OUT of empty state, REVEALING the sidebar. Save triggers: the COORDINATOR owns the whole-tree snapshot. A `StatePersistence` observer is TRIGGER-ONLY (no per-index `state_set_*` calls — those bridge setters are gone): window move / end-of-live-resize / discrete resize, sidebar `isCollapsed` KVO, and native tab-group membership/selection (via `TabGroupObserver`) each call `coordinator.scheduleStateSnapshot()`, a coalesced ~150ms walk of every window/tab group that reads each tab's TAB-LOCAL `persistedCwd` (`cwd_for_tabpage`) over the FFI and commits the whole tree via the `wolf_ffi_state_snapshot_*` builder; a dragged divider ALSO triggers a snapshot (`PaneContainerView.onLayoutChanged` → `scheduleStateSnapshot`). Each multi-leaf tab's pane layout is captured by `PaneContainerView.layoutSnapshot()` (`PaneLayoutCodec.encode` over the live `PaneTree`, mapping each editor leaf to its `pane_status_for_grid(grid).abs_path()` and each **preview** leaf — detected by scanning `previews()` for its bound window — to its SOURCE Markdown path plus a `preview` flag) and replayed into the tree via the FFI pane-layout push-builder (`wolf_ffi_state_layout_push_leaf` carrying that `preview` flag / `push_split` / `commit_to_tab`, a post-order token stream so no recursive struct crosses the scalar bridge). A synchronous `snapshotNow()` plus a blocking `wolf_ffi_state_flush()` runs at terminate as the correctness backstop. Core no longer mirrors cwd into the store (`attach_state_store` is gone); it still records each GENUINE `wolf_cwd`/`DirChanged` into the recent-dirs MRU — the one-shot INITIAL launch emit is deliberately NOT recorded — so an empty-state window persists `cwd == ""` and Open Recent reflects only directories the user actually opened. The pure decisions live in the headlessly-tested `StateSeam` (WolfKeyMap); the AppKit observation/restore glue is compile-verified + manual-smoke only, and the bridge surface is covered by the HEADLESS `//crates/wolf-ffi:state` builder round-trip test.

The same **"Split panes — known v1 limitations"** (below) apply on macOS as on GNOME: only windows opened via the overridden split commands get a pane; focus-direction moves use the tree's idealized split ratios; and floating / external windows are ignored. (The old "cmdline strip truncates multi-row prompts" limitation no longer applies on macOS — the native `ToastView` renders multi-line messages, scrollable with a 10-line cap.) Unlike GNOME (whose v1 divider is still fixed / equal-weighted), macOS **now supports divider drag-to-resize AND persists the pane sizes** (see the pane-view + persistence descriptions above): the single flat painting view hit-tests the pure `PaneTree.dividers()` list rather than relying on an `NSSplitView` tree, and the dragged sizes survive quit/relaunch (restored from the saved weights). The macOS `PaneTree` weight policy: a `:vsplit`/`:split` RE-EQUALIZES the row/column to equal shares (matching the gnome port), while REMOVE renormalizes survivors PROPORTIONALLY — the ONE remaining weight divergence from gnome — so a user-dragged size survives an adjacent pane closing and tab switches (a same-orientation split re-equalizes).

**Mouse, scroll, and synthetic scrollbars** are realized on macOS (still deferred on GNOME). Mouse input is **grid-targeted**: `PaneContainerView` maps a pane-local point to a grid cell through a per-pane `PaneGeometry` seam and forwards a press / drag / release via `send_mouse` targeting that pane's WINDOW grid (`>= 2`) with grid-local coordinates, so under nvim's `mouse=a` a click positions the cursor and a click-drag selects (click-to-focus is preserved). This required threading a real `grid` id through the core mouse/scroll path (`nvim_input_mouse` previously hardcoded grid 0) — see the cross-cutting change in [wolf-core](#wolf-core) / [wolf-ffi](#wolf-ffi). Scroll (wheel / trackpad) is hit-tested from the whole pane rect (so a future side-margin still scrolls), accumulated into discrete line steps by a pure `ScrollAccumulator` seam, and forwarded via `send_scroll`; per **decision 5** the scroll is just input — Neovim scrolls itself. The **scrollbar is synthesized per pane from `win_viewport`** (decision 5): a custom-drawn indicator at each pane's right edge whose thumb size/offset comes from the frame's 0-based `topline` / `botline` / `linecount` viewport, following the macOS "Show scroll bars" setting (`NSScroller.preferredScrollerStyle`: `.legacy` always-visible / `.overlay` fade, reacting to `preferredScrollerStyleDidChangeNotification`); the thumb is non-interactive (drag deferred). The pixel↔cell `PaneGeometry` seam carries a distinct GRID RECT inside the PANE RECT, and the **max-column-width / centered grid it readies is now realized on macOS**: a grid wider than a hard-coded **90 columns** is capped and CENTERED inside the pane, the side margins painted in the grid's own background so they blend seamlessly, while the scrollbar stays pinned at the PANE's right edge (out in the right margin). The `PaneGeometry` / `ScrollAccumulator` seams are headlessly unit-tested in `WolfKeyMapTests`; the FFI mouse/scroll + viewport surface is covered by the real-nvim `//crates/wolf-ffi:mouse_scroll` test; the AppKit event wiring + scrollbar drawing is compile-verified + manual-smoke only.

Per-cell glyph **text attributes** are now painted on macOS: `wolf-ffi` resolves and packs bold/italic/underline/undercurl/strikethrough (`FfiCell::flags()`) plus the **special** (underline) color (`FfiCell::special()`), and the renderer consumes them — the pure `GlyphStyleResolver` seam maps a cell's flags to a `GlyphFace` (drawn with the matching cached bold/italic/boldItalic `CTFont`, all sharing the regular advance width for a fixed-cell grid) and to underline/strikethrough strokes drawn **manually** as `CGContext` lines in the resolved color (special when set, else fg; undercurl folds into a straight underline this pass), because `CTLineDraw` paints decorations only in the foreground color. The native command line / messages / completion popup are now REALIZED on macOS (the `CmdlineView` / `CompletionPopupView` / `ToastView` overlays above, `ext_cmdline` / `ext_messages` / `ext_popupmenu`). Still deferred for macOS (the same list as gnome, minus mouse/scroll and the native cmdline/messages/popup — all now realized on macOS though the popup + multi-line toast remain deferred on GNOME): theming, HiDPI edge cases, and a true curly undercurl (a straight underline for now). The mouse-scrollbar **thumb-drag** is also deferred (the thumb is non-interactive); the **max-column-width / centered grid** is now realized (a hard-coded 90-column cap, centered with margins painted in the grid background — see above). The pinned Neovim is now bundled into the `.app` (above), and the live nvim→FFI→`read_frame` round-trip **is** covered by a passing automated test on the macOS Bazel host: `//crates/wolf-ffi:bridge_smoke` passes under `bazel test`, driving start → type → grid-reflects-the-typed-char → resize → shutdown against the bundled/pinned Neovim. (The GUI window rendering and Finder double-click are still not headlessly asserted.) See [`crates/wolf-macos/README.md`](crates/wolf-macos/README.md).

A **live-updating Markdown preview** is realized on macOS, introducing a **SECOND kind of pane content: a web view**. Until now a Wolf pane only ever painted a Neovim window grid; a preview pane is a real Neovim `nofile` / `nomodifiable` / `buflisted` **scratch buffer** named `Preview: <cwd-relative path>` (the source's cwd-relative path via `fnamemodify(source_path, ":.")`, e.g. `Preview: crates/wolf-macos/README.md`; a file at the cwd root collapses to a bare basename, with an E95 bufnr-disambiguated fallback on a cwd-relative-path collision) carrying `b:wolf_preview_source` (OD1 = Design S), shown in an ordinary pane whose blank grid `PaneContainerView` OVERLAYS with a `WKWebView`. Because the preview pane is a real buffer it falls out of the existing seams for free — it surfaces in the buffer picker as `Preview: <cwd-relative path>` with no front-end injection, and `PaneTree` / reconciliation / resize / close are untouched (the accepted cost is that the path-based trackers `wolf_current_file` / `wolf_buffers` SKIP `b:wolf_preview_source` buffers). Markdown→HTML rendering is **CORE-side** (the pure, GUI-free `wolf_core::markdown` module over `pulldown-cmark`, so no GUI toolkit enters core's dependency tree); the front-end web view just loads the HTML string core produces. Themes are **core-assembled CSS** (`PreviewTheme` + `theme_css` + `include_str!`'d files) — one theme ships now (`PreviewTheme::Default`, a fixed dark theme per OD5), structured so more themes and a config-driven selector drop in later. The **View > Preview** command opens it: single-pane windows split a new pane to the RIGHT (reusing the `:vsplit` `wolf_layout` intent path) and show it there; an exactly-two-pane window whose OTHER pane already shows a preview REUSES that other preview pane (`nvim_win_set_buf` into the background preview window, leaving the active editor untouched); every other multi-pane window shows it in the ACTIVE pane (`nvim_win_set_buf`) — the front-end picks the mode (`"split_right"` / `"reuse_preview_pane"` / `"active"`) via the pure `PreviewSeam.placementMode` from the pane count plus whether the active pane is itself a preview and how many other panes are previews. The preview **live-updates** as the source is edited: a `wolf_preview` window-scan notification tells the front-end which pane previews what source, a `wolf_markdown_dirty` notification carries the source buffer's `changedtick`, and on each wake the front-end pulls fresh HTML via the blocking `WolfCoreHandle::render_preview(source_bufnr)` when the tick advanced (debounced through `PickerRefreshCoalescer` so a keystroke burst yields one main-thread round-trip; a per-window tick gate remains the redundant-reload guard — OD6/OD12). The preview pane paints a statusbar strip that mirrors an editor pane — a `Preview: <basename>` primary line plus the source's cwd/home-relative display path on the secondary line (core-computed via `WolfCore::display_path`, exposed as `FfiPreview::source_display_path()`) — suppresses its synthetic scrollbar (the web view scrolls itself), and — like an editor pane — draws that statusbar filename bold when active and regular-weight + dimmed when inactive. That statusbar text is also aligned HORIZONTALLY to the web view rather than to a text grid, the second place the two-kinds-of-pane-content split shows through: the pure `StatusbarTextSpan` seam spans a preview pane's statusbar text across the whole (UNCENTERED) grid rect, deliberately skipping the 90-column grid-centering offset `PaneGeometry.paintOffsetX` that an editor pane's statusbar adds — because the `WKWebView` is framed to that same uncentered rect and the preview CSS is flush, so both text edges land on the web view frame. The pane-kind map and the web view frames are written together in one `syncPreviewWebViews` pass, so a pane is never drawn with preview alignment while it has no web view (web view FRAME freshness is a separate, pre-existing matter — a frame can lag a resize or font-size change until the next wake). Below the 90-column cap there is no offset, so the two kinds coincide and the distinction is only observable on panes wider than 90 cells. The **Edit** command is Preview's inverse: `WolfWindowController.editSource` navigates a preview pane back to its source file, the mode (`split_left` / `reuse_editor_pane` / `active`) chosen by the pure `EditSeam.placementMode` from the pane count plus whether the active pane is a preview and whether the other pane is a non-preview editor, then handed to `WolfCoreHandle::edit_source(mode)`; its View-menu "Edit Source" item is enabled only in a preview pane (`is_preview_active`). Because the hosting `WKWebView` swallows AppKit mouse events (so the pane's `mouseDown` never fires), **clicking anywhere in a preview pane focuses it**: a document-start capture-phase `mousedown` `WKUserScript` posts to a weak-proxy `WKScriptMessageHandler` (`PreviewClickFocusHandler`) that focuses the pane (`focus_win` + `setActivePane`). See [`crates/wolf-macos/README.md`](crates/wolf-macos/README.md) and [`crates/wolf-core/README.md`](crates/wolf-core/README.md).

## Architectural decisions

### 1. Core↔front-end boundary: swift-bridge on macOS, direct crate on Linux

Swift cannot import a Rust crate directly, so the macOS side needs a generated binding regardless. We use [`swift-bridge`](https://github.com/chinedufn/swift-bridge), which produces idiomatic Swift from an annotated bridge module in `wolf-core`. Linux/GTK, being Rust, links `wolf-core` directly with no FFI.

Consequence — and a design constraint: the **front-end-facing API of `wolf-core` must be expressible over swift-bridge** (FFI-friendly: plain structs, slices, handles, and callbacks — no Rust-only generics or trait objects across the line). The GTK front-end consumes that same API directly. This keeps a single front-end-facing surface rather than two divergent ones.

We rejected a uniform C-ABI on both platforms: it would cost Linux its type safety and async ergonomics for symmetry we don't need, since the boundary is defined once in Rust either way.

### 2. Rendering: native paint per platform

The render-state model is toolkit-agnostic; each front-end paints it natively: Cairo/Pango in GTK on Linux, CoreText/CoreGraphics in AppKit on macOS. This gives the best native text rendering on each OS. The cell-painting loop is written twice, but it is small once the render-state model exists.

A corollary: **what to paint is a front-end decision, not part of the core↔front-end contract.** Core always publishes the full render state for every grid; a front-end may decline to paint any of it. macOS exercises this — a pane whose text grid is fully covered by an opaque Markdown-preview `WKWebView` paints no grid and does not even read that grid's frame across the FFI (`WolfKeyMap.PaneOcclusion`; see [`crates/wolf-macos/README.md`](crates/wolf-macos/README.md)). Core is unaware, the render state is unchanged, and GTK does nothing analogous. Such skips must be provably invisible: the macOS one uses zero-tolerance containment against the very rectangle the web view was framed from, so any out-of-sync geometry falls back to painting.

We rejected a shared portable canvas (skia/wgpu): it would force surface handles (GL/Metal) across the FFI and sacrifice native text quality. The render-state model is kept behind a clean interface, so a shared renderer could be introduced later without touching core's logic if the duplication ever justifies it.

### 3. Neovim is embedded as a child process over stdio

Core launches `nvim --embed` and communicates over its stdin/stdout via msgpack-RPC. No sockets, no shared user Neovim instance.

### 4. Neovim owns the document model

There is no separate document representation in Wolf. Open is `nvim.command("edit <path>")`; save is `"write"` / `"saveas"`. Because Markdown is plain text, Neovim's buffer _is_ the document model. The grid is a projection of the visible viewport, never the whole file.

### 5. Scrolling belongs to Neovim; the scrollbar is synthesized

The grid is sized to the **visible viewport** only (resized via `nvim_ui_try_resize` when the widget resizes). Scroll gestures are forwarded to Neovim as input; Neovim scrolls itself and emits `grid_scroll`. A native scrollbar's position and range are driven by the `win_viewport` event (`topline`/`botline`/`curline`/`linecount`, all 0-based buffer line indices with `botline` one-past-the-last-visible). The editor widget is **not** placed in a scrolled-window that owns a tall child. **macOS now realizes this**: `PaneContainerView` draws a synthetic per-pane scrollbar from each pane's `win_viewport` (over the FFI's `FfiFrame` viewport accessors) at the pane's right edge, following the system "Show scroll bars" setting — scroll input goes to Neovim, the scrollbar is purely a viewport-driven projection. GNOME still defers the scrollbar.

### 6. Syntax highlighting is whatever Neovim produces

The front-ends are semantically dumb: a cell carries an `hl_id`, which resolves (via the `hl_attr_define` / `default_colors_set` table) to RGB + attributes, which get painted. All highlighting — treesitter, LSP semantic tokens, diagnostics, `Visual`/`Search` — is decided inside Neovim and arrives pre-resolved. To change or extend highlighting you configure Neovim, never the renderer.

### 7. UI extensions: native command line / messages / completion (with `ext_multigrid` for native panes)

Wolf enables `ext_linegrid` + `ext_multigrid` + `ext_popupmenu` + `ext_messages` (+ `rgb`). `ext_messages` IMPLICITLY enables `ext_cmdline` (and `ext_linegrid`) and forces `cmdheight=0`, so the command line, messages, and completion menu are now **REALIZED as native widgets**, not grid-drawn: Neovim routes them off the grid into the `cmdline_show`/`_pos`/`_hide`, `popupmenu_show`/`_select`/`_hide`, and `msg_show`/`msg_clear`/`msg_history_show` events, which core folds into `Snapshot.cmdline` / `Snapshot.pum` / `Snapshot.toast` (see "The core↔front-end contract"). The former grid-1 **cmdline strip is REPLACED**: with `cmdheight=0` grid 1 empties, so the front-ends paint the command line / completion popup / messages from those snapshot fields instead. `ext_multigrid` (unchanged) still moves window content onto per-window grids (`>= 2`) so the shell owns a native split-pane layout (decision below); the outer grid 1 no longer carries the command line.

Front-end realization differs by platform (see the phase-status paragraphs): **macOS** paints all three as dedicated overlay `NSView`s — a `CmdlineView` at the bottom, a `CompletionPopupView` anchored directly above it at the cmdline byte column, and a bottom-left scrollable `ToastView` — shown only while active (overlay-when-active, matching the `cmdheight=0` spirit). **GTK** paints a minimal-but-correct single-row bottom strip from `Snapshot.cmdline` (falling back to the last toast line when idle), with the Adw completion popup and multi-line scrollable toast DEFERRED. `ext_popupmenu` presents cmdline completion as a vertical popup (via `wildoptions+=pum` in the captive `init.lua`) rather than the horizontal wildmenu.

### 8. The captive Neovim is hermetic, pinned, and Markdown-only

Wolf ships its own Neovim, tuned for Markdown and nothing else (markdown + markdown_inline treesitter grammars, a Markdown LSP such as `marksman`, an optional formatter — and nothing else). It must not read the user's `~/.config/nvim`, plugins, or shada.

Launch isolation (both platforms): `nvim --embed --clean -u <bundled init.lua>`, with `NVIM_APPNAME` and the `XDG_*`/state dirs pinned away from the user's, and shada/swap disabled. The `init.lua` lives **in this repo** and is referenced by the build, so editor behavior is version-controlled alongside the code that depends on it.

Delivery:

- **Linux (NixOS):** `wrapNeovim` / `neovimUtils.makeNeovimConfig` builds a single wrapped `nvim` with the plugin set baked into the runtimepath and the LSP/ formatter binaries on its `PATH` (`makeWrapper --prefix PATH`). The whole closure ships together.
- **macOS (REALIZED):** the `.app` bundles a pinned Neovim **0.12.3** — the official macOS release tree (`bin/nvim` + `lib/nvim/parser` treesitter parsers, including `markdown` and `markdown_inline`, + `share/nvim/runtime`) — at `Contents/Resources/nvim/`, alongside the captive `init.lua` at `Contents/Resources/init.lua`. Bazel downloads and verifies the release hermetically (sha256-pinned via the `//bazel/nvim` module extension, assembled into a structure-preserving `TreeArtifact` with `aspect_bazel_lib`'s `copy_to_directory`). At launch the GUI points wolf-core at that absolute bundled binary: `AppDelegate` sets `WOLF_NVIM_BIN` to `Contents/Resources/nvim/bin/nvim` **only if it is not already set** (`setenv(..., 0)`, so a developer's exported `WOLF_NVIM_BIN` still wins) before starting the core — never `nvim` from the user's `PATH`. So a double-clicked `.app` runs its own Neovim with no shell environment. The `.app` also bundles the **vendored orlando** plugin (the first vendored plugin) at `Contents/Resources/orlando/`, downloaded + sha256-pinned by the `//bazel/orlando` module extension and assembled the same way (pure Lua, arch-independent — no `select()`); the captive `init.lua` self-locates that sibling `orlando/` dir and sources it when present (a strict no-op when absent), so no Swift is involved in loading it. It also bundles the **vendored lighthouse** colorscheme at `Contents/Resources/lighthouse/`, downloaded + sha256-pinned by the `//bazel/lighthouse` module extension and assembled the same way (pure Lua, arch-independent — no `select()`); because a colorscheme is inert on `runtimepath` until selected, the captive `init.lua` self-locates that sibling `lighthouse/` dir and **activates** it when present (prepend to `runtimepath`, then `vim.o.background = "dark"` + `vim.cmd.colorscheme("lighthouse")`, after `syntax on`; a strict no-op when absent), again with no Swift involved. Both are **Bazel-only for now** — the Linux path will vendor them separately later. Full `wrapNeovim`-style plugin baking beyond that — a `marksman` LSP, a formatter — remains deferred; see below.)

**Phase status.** The Neovim binary is pinned and hermetic from day one: on Linux, via the flake devShell (core locates it only through `WOLF_NVIM_BIN`, never `PATH`, never `/nix/store` scanning); on macOS, via the bundled `Contents/Resources/nvim/bin/nvim` (above), which `AppDelegate` exports as `WOLF_NVIM_BIN` unless overridden. Either way core launches it `--embed --clean -u runtime/nvim/init.lua` with `-i NONE`, pinning `NVIM_APPNAME=wolf` and the `XDG_*` dirs under a private temp dir (plus a durable per-project `WOLF_SWAP_DIR` for crash-recovery swap files; the former `-n` flag was removed because it zeroed `updatecount` and disabled swap). The **orlando** plugin is the first vendored plugin (macOS Bazel bundle, via `//bazel/orlando`, loaded by the captive `init.lua`), and the **lighthouse** colorscheme is the second vendored asset (macOS Bazel bundle, via `//bazel/lighthouse`, activated — not just sourced — by the captive `init.lua`); full `wrapNeovim` plugin baking beyond that (the `marksman` Markdown LSP, a formatter) is **deferred to a later phase**, and vendoring is Bazel-only for now (the Linux path vendors them separately later). The current build runs the pinned binary with the repo's `init.lua` and the treesitter `markdown`/`markdown_inline` parsers the release carries. Bundling is **arm64-tested** on the dev host; the x86_64 tree is wired via `select()` but untested.

### 9. The macOS UI: AppKit, Swift, Tahoe-only, all-Bazel — locked

The macOS front-end's foundations are fixed (these are load-bearing — do not relitigate them casually):

- **Tahoe (macOS 26) and newer only.** `Info.plist`'s `LSMinimumSystemVersion` and the `macos_application` `minimum_os_version` are both `"26.0"`.
- **AppKit, not SwiftUI.** A custom `NSView` paints the grid (decision 2).
- **Swift**, built with **Xcode 26+** (Swift features that require Xcode 26 are permitted).
- **The Bazel build is authoritative.** `rules_swift` + `rules_apple` build the `.app` (code-signed, min OS 26.0). `rules_xcodeproj` can generate an `.xcodeproj` for debugging/LLDB only — it is **uncommitted** (`.gitignore`d) and never the source of truth; Bazel remains the one build.
- **Rust ↔ Swift via swift-bridge, confined to `wolf-ffi`** (decision 1), with the generated Swift + C bindings **committed** under `crates/wolf-ffi/generated/`.
- **Key translation lives in Rust.** Swift sends a structured `FfiKeyEvent` over the bridge; `wolf-core::key_to_notation` stays the single source of nvim notation (the Shift contract is honored once, in Rust).
- **The snapshot is marshalled as an opaque per-frame handle** (`FfiFrame`), resolved against the highlight table in Rust — never re-resolved in Swift.

Resolved Bazel pins (highest BCR releases that declare Bazel-8 compatibility, keep `apple_support >= 2.6.1`, and support Xcode 26 / the Tahoe SDK): **`rules_swift` 3.6.1, `rules_apple` 4.5.3, `rules_xcodeproj` 4.1.0**, and **`swift-bridge` / `swift-bridge-build` 0.1.59** on the Cargo side (`apple_support` stays 2.6.1).

### 10. Commands: one canonical id → two faces; the captive nvim stays hermetic

A **Command** is a no-parameter, no-return user action, invocable from inside Neovim (an Ex-command or a Lua function), from the native menu, and — later — a command picker. Three locked points:

- **One canonical id derives both faces.** A single snake_case id (e.g. `close_window`) in `wolf-core`'s `COMMAND_SPECS` derives a PascalCase Ex-command `:WolfCloseWindow` (Neovim forces the uppercase start) and a snake_case Lua function `require('wolf').close_window()` (idiomatic nvim Lua). The id→ex_command mapping is stored explicitly as data (no transform code — single source of truth), and the `Command` enum's variant order IS the FFI `command_kind` discriminant.
- **User keybindings are DEFERRED.** The captive Neovim stays hermetic (`--clean`, never reads `~/.config/nvim`). The `wolf` Lua module + `:Wolf*` Ex-commands are exposed now for Wolf's OWN bundled config/plugins only; a real user keybinding/config hook is a separate later change (no user-config source path is added).
- **The registry is canonical in core; the front-end maps id→action.** For this cut only the `command_kind` u8 crosses the FFI and the macOS menu hardcodes its item list — now twenty-six commands (`command_kind` discriminants `0..25`): the App/Window originals New Window / Close Window / Quit / Hide / Minimize (`0..4`), the File commands Go to File / Open File / Open Folder (`5..7`), Close Pane (`8`, `:close` — the former "Close File"/`:bdelete`, renamed in place) and New Buffer (`9`, `:enew`), the View font-size commands Reset / Increase / Decrease Font Size (`10..12`, front-end-only and per-window), the View **Command Palette** (`13`, id `command_palette`, `:WolfCommandPalette`, title "Command Palette…", `⌘P`), the new **Edit** menu's Copy (`14`, id `copy`, `:WolfCopy`, `⌘C`) and Paste (`15`, id `paste`, `:WolfPaste`, `⌘V`) — its only two entries — the View menu's **Buffer Picker** (`16`, id `buffer_picker`, `:WolfBufferPicker`, title "Buffer Picker…", `⌘E`), which opens the macOS `BufferPickerView` overlay to fuzzy-switch among the window's `buflisted` buffers (reachable from BOTH the native menu and, as a static palette row, the command palette), the File menu's **New Tab** (`17`, id `new_tab`, `:WolfNewTab`, title "New Tab", `⌘T`), which opens a new native tab in the current window's tab group via `AppDelegate.makeNewTab` (a new captive Neovim in the same directory; also reachable as a static palette row), and the View menu's **Preview** (`18`, id `preview`, `:WolfPreview`, title "Preview", **NO key equivalent** per OD2), which renders the active Markdown buffer to HTML in a preview pane and is ENABLED only when the active buffer is a Markdown file (a `Snapshot::is_markdown_active` gate bridged as `WolfCoreHandle::is_markdown_active`, the Copy/visual-mode precedent), and the View menu's **Edit Source** (`19`, id `edit`, `:WolfEdit`, title "Edit Source", **NO key equivalent**), Preview's inverse, which navigates a preview pane back to its source file per three placement modes and is ENABLED only when the active pane is a preview (a `Snapshot::is_preview_active` gate bridged as `WolfCoreHandle::is_preview_active`, the same precedent), the View menu's **Terminal** (`20`, id `terminal`, `:WolfTerminal`, title "Terminal", `` ⌃` ``), which toggles a per-tabpage bottom `:terminal` drawer window showing a single shared per-project terminal buffer (the `wolf_toggle_terminal` `init.lua` helper via `WolfCoreHandle::toggle_terminal` → `InputEvent::ToggleTerminal`; the buffer/job persist across toggles, VS-Code style, and are recreated if the shell exited) and, unlike Preview / Edit Source, is NEVER gated — it is always enabled, and the View menu's **Preview in Browser** (`21`, id `preview_in_browser`, `:WolfPreviewInBrowser`, title "Preview in Browser", **NO key equivalent**), which renders the active Markdown buffer and opens it in the system default web browser (a blocking `WolfCoreHandle::open_in_browser` call returning the loopback preview server's `http://127.0.0.1:<port>/<relpath>` URL — the pinned file's root-relative path — which the front-end opens via `NSWorkspace`) and is ENABLED only when the active buffer is Markdown (the `Snapshot::is_markdown_active` gate, the same as Preview), and the View menu's **Use full width for content** (`22`, id `full_width`, `:WolfFullWidth`, title "Use full width for content", **NO key equivalent**), a per-buffer TOGGLE that switches the active buffer's content area between the ~90-char default (centered) and full pane width — for BOTH the editor and its Markdown preview — by flipping the buffer-local `b:wolf_full_width` (the `wolf_toggle_full_width` `init.lua` helper via `WolfCoreHandle::toggle_full_width` → `InputEvent::ToggleFullWidth`, an editor-affecting command; when the active pane is a preview scratch the SOURCE buffer's flag is flipped — OQ-1). It is ALWAYS enabled (OQ-2, like Terminal); its menu item shows a CHECKMARK when the active buffer is full-width, driven by `Snapshot::is_full_width_active` (fed by `wolf_current_file`'s new 4th arg and bridged as `WolfCoreHandle::is_full_width_active`) via `AppDelegate.validateMenuItem`, and — appended last — three native-only (flavor a) sidebar commands: **Toggle sidebar** (`23`, id `toggle_sidebar`, `:WolfToggleSidebar`, title "Toggle sidebar"), **Sidebar: Show project** (`24`, id `sidebar_show_project`, `:WolfSidebarShowProject`, title "Sidebar: Show project"), and **Search in project** (`25`, id `search_in_project`, `:WolfSearchInProject`, title "Search in project"), each dispatched entirely in AppKit — `WolfWindowController.toggleSidebar()` (toggle the sidebar's collapsed state) and `showSidebar(panel: .tree)` / `showSidebar(panel: .search)` (reveal the sidebar's project tree / search panel) — so the captive nvim is never touched (no `InputEvent`). They are the palette/command faces of actions that already exist as the View menu's standard-AppKit items (Toggle Sidebar `⌃⌘S`, Project `⇧⌘E`, Search `⇧⌘F`); the menu items stay as-is, so these three add NO new hardcoded menu items (their `MenuGroup::View` is informational only) and surface only as command-palette rows and `:Wolf*` Ex-commands. Because the captive nvim is `--clean` (no clipboard integration), the front-end owns `NSPasteboard`: Copy yanks the visual-mode selection over RPC (`WolfCore::copy_visual_selection`, a blocking call) so the shell can write it to the pasteboard, and is ENABLED only when the active window is in Neovim visual mode (a `Snapshot::is_visual_mode` flag bridged as `WolfCoreHandle::is_visual_mode`); Paste reads the pasteboard and inserts via `nvim_paste`. The three font-size commands carry no core input path (only the discriminant crosses for the nvim-drained face); the macOS Window menu additionally grows a DYNAMIC per-window tail that is NOT in the registry, and the File menu grows a DYNAMIC **Open Recent** submenu that is likewise NOT a `Command` (an Open Recent entry is path-parameterized, so it does not fit the no-arg/no-return `Command` model): it is a native dynamic submenu — the same precedent as the Window-menu tail — rebuilt lazily as the `AppDelegate`'s `NSMenuDelegate.menuNeedsUpdate`, backed by the `WolfCoreHandle::recent_dirs()` FFI DATA accessor (the global recent-directories MRU, newest-first, over the bridge as `Vec<String>`), each item chdir-ing the key window (the same effect as Open Folder), NOT by a `command_kind` discriminant. The macOS View menu ALSO grows a net-new **Enter Full Screen** (`⌃⌘F`) item that is a STANDARD AppKit `toggleFullScreen:` item — NOT a Wolf command, no `command_kind` — flagged per CLAUDE.md as a spec-vs-prior-implementation deviation (no fullscreen item existed before). The full registry's titles ARE now surfaced — but only through the new **command palette** (`command_palette`, `13`), whose Rust-side `rank_palette` builds one fuzzy-searchable row per `COMMAND_SPECS` entry (except CommandPalette itself) plus dynamic "Switch to Window" / "Open Recent Folder" rows, ranked MRU-first via the global `command_mru`; the macOS `CommandPaletteView` overlay is fed the `FfiCommandPalette` session and dispatches the chosen row back through the SAME `CommandDispatcher`. `wolf-gnome` gets `drain_commands()` for free but is not wired to a menu here (deferred parity).

**The per-project loopback preview server.** The **Preview in Browser** command is backed by a lazily-started, LOOPBACK-ONLY HTTP server owned by the captive core — one per `WolfCore` (per project) — serving a tiny STATIC SITE rooted at the project so relative links in the rendered Markdown resolve in URL space. It is not started until the user first runs the command; the first `open_in_browser` binds `127.0.0.1:0` (loopback only, never `0.0.0.0` — a hard security requirement — on a random OS-assigned port), and later invocations REUSE that server, re-pointing it at the now-active Markdown buffer via a `Mutex<Target>` pinned target (the source buffer, the canonical root the site is served from — nvim's `getcwd()`, falling back to the pinned file's parent dir — and the pinned file's root-relative path, rebuilt on each invocation; so each project's URL is stable and, thanks to the distinct random port, unique between projects). It is hand-rolled HTTP/1.1 on the core's existing tokio runtime — enabling only tokio's `net` feature, adding NO new crate, so wolf-core's GUI-free denylist stays clean. `GET /` 302-redirects to the pinned file's root-relative path; that page serves the SAME `markdown::render_html` output as the in-app preview (via the shared `render_source_html`), so the browser tab and the in-app preview match, with an injected JS poller that hits `GET /tick` (the source buffer's `changedtick`, reusing the same `Snapshot.markdown_ticks` signal that drives the in-app preview) once a second and calls `location.reload()` when the tick advances — live reload. A relative link to another Markdown file under the root renders a static from-disk snapshot (no reload script — `/tick` tracks only the pinned buffer), a linked asset (image/CSS/etc.) is served as raw bytes, and any target that escapes the root is rejected (a hard path-traversal guard). This is macOS-only this cut (wolf-gnome is not wired). See wolf-core's [README](crates/wolf-core/README.md) ("The browser preview server").

See [Command lifecycle](command-lifecycle.md) for the full end-to-end walkthrough — the registry, the two faces, the invocation→drain→dispatch path, the editor-affecting loop back into nvim — and a checklist for adding a command.

## The core↔front-end contract

The boundary is intentionally narrow and FFI-shaped (decision 1). Two directions:

### Output: render state (core → front-end)

Core maintains a snapshot of everything needed to draw a frame:

- The cell grids: under `ext_multigrid` a map of grid id → grid (each cell: char(s) + `hl_id`). Editor window content lives on grids `>= 2`; the outer grid (grid 1) is emptied by `cmdheight=0` (the command line / messages are no longer grid-drawn — see `Snapshot.cmdline` / `toast` below).
- The per-window layout: grid id → `WinInfo` (window handle, position, size, viewport, hidden flag), learned from `win_pos` / `win_viewport`.
- The highlight table: `hl_id → {fg, bg, special, bold, italic, underline…}`, plus default colors.
- Cursor: the grid it lives on + grid position + shape/mode (from cached `mode_info_set`, updated on `mode_change`).
- Viewport info for the scrollbar (`win_viewport`), per window.
- The **active window** (`Snapshot.active_win: Option<i64>`), tracked via the `wolf_active_win` notification, so the front-end can mark the active pane.
- The **current tabpage** (`Snapshot.current_tabpage: i64`, `0` = unknown), tracked via the `wolf_tabpage` notification. Under the macOS project/tabpage-per-view model each view binds one nvim tabpage; only the CURRENT tabpage's windows appear in `Snapshot.windows` (nvim renders only its current tabpage), so the front-end uses this as the cheap "is my tabpage current" gate for its refocus rebind (the authoritative bind-time value is the blocking `WolfCore::current_tabpage` RPC). `Snapshot.buffers` (the shared buffer list) and the `wolf_cwd` cell are likewise current-tabpage-scoped — they report the FOCUSED view; a non-current view's cwd is read on demand via `cwd_for_tabpage`.
- The **current file**: the absolute, canonicalized path of the buffer being edited (`Snapshot.current_file: Option<PathBuf>`, `None` for an unnamed buffer).
- The **per-window buffer paths** (`Snapshot.buffers: HashMap<i64, PathBuf>`): the canonicalized buffer path shown in EACH window, keyed by window handle (unnamed windows absent), tracked via the `wolf_buffers` notification — the macOS per-pane statusbar joins a grid → window → path via `WolfCore::pane_status`.
- The **Tier-1 open-file mirror** (`Snapshot.open_files: HashMap<i64, TabFiles>`, keyed by tabpage handle): each tabpage's file-backed open buffers + its active buffer, tracked via the `wolf_open_files` notification — read (per tabpage) by `WolfCore::open_files_for_tabpage` so the front-end can capture a crashed nvim's open files BEFORE `restart_nvim` and reopen them afterward. `TabFiles.files` is the instance-GLOBAL buflisted set (only `active` is per-tabpage), a known Tier-1 multi-view over-reopen limitation.
- The **app theme colors** (`Snapshot.theme: ThemeColors`): the effective colors of the optional `WolfCursor` / `WolfTitlebar` highlight groups, tracked via the `wolf_theme` notification (see "Theming"); all-`None` when a group is absent or cleared.
- The **native command line** (`Snapshot.cmdline: Cmdline`): `active`, the `firstc` prefix (`:` / `/` / `?`), the styled content (flattened to plain text over the FFI, OD1), the caret `pos` (a BYTE offset), and the recursion `level` — folded from `cmdline_show` / `cmdline_pos` / `cmdline_hide` (`ext_cmdline`).
- The **completion popup** (`Snapshot.pum: Pum`): `visible`, the items (`word` / `kind` / `menu` / `info`), the `selected` index, and the anchor (`grid`/`row`/`col`; `grid == -1` anchors to the command line with `col` a byte offset into the cmdline text) — folded from `popupmenu_show` / `popupmenu_select` / `popupmenu_hide` (`ext_popupmenu`).
- The **message toast** (`Snapshot.toast: Toast`): `visible` plus the `messages` (each a kind + id + styled `lines`, the chunk colors KEPT and resolved in Rust like a cell — OD1, message color is load-bearing) — folded from `msg_show` / `msg_clear` / `msg_history_show` (`ext_messages`); `msg_history_show` routes into the same surface so `:messages` works. Cleared on the next dismissing input (see "Input").

Unlike the six out-of-band facets below, `cmdline` / `pum` / `toast` are folded IN the redraw batch, so they advance `seq` on that batch's `flush`.

**Command line / popup / message events — handled vs ignored.** Nine events are folded (above); several are intentionally IGNORED (documented in the redraw ignore list, like `win_float_pos`): `cmdline_special_char` (OD6 — the `?`/`^R` insert-hint char), `cmdline_block_show`/`_append`/`_hide` (OD5 — interactive `:function` blocks), and `msg_showmode` / `msg_showcmd` / `msg_ruler` (showcmd + ruler are off). The `msg_show` fold rules: `search_count` is SUPPRESSED (no `[1/3]` toast); an `empty` message with no content clears the toast; `append` fuses onto the current message's last line (`:echon`); `replace_last` replaces the last message in place; a non-zero integer `id` matching a visible message replaces THAT message (OD7 — integer id only). Toast-clear-on-input (OD8): the input pump clears the toast on the next `Key` / `Mouse` / `Scroll`, gated by `!toast.is_prompt()` (a `confirm` prompt is NOT dismissed); the scroll-over-toast exemption is realized in the FRONT-END (that wheel gesture is never forwarded, so no `Scroll` reaches core).

Core does not push pixels or per-event callbacks across the boundary. Instead it applies `redraw` batches to the snapshot and, on `flush`, signals the front-end that a new frame is ready (a "redraw needed" wake — see threading). The front-end then reads the current snapshot on its UI thread and paints.

The current file is tracked **out-of-band** from the redraw stream: after attaching, core installs a `BufEnter`/`BufWinEnter`/`BufFilePost`/`FileType` autocmd (in the bundled `init.lua`, set up over RPC with core's channel id) that `rpcnotify`s a `wolf_current_file` notification carrying `expand('%:p')` PLUS a second argument, `vim.bo.filetype`, PLUS a third boolean argument marking whether the buffer is a preview. The handler folds the path into `Snapshot.current_file`, the filetype into `Snapshot.current_filetype` (driving `Snapshot::is_markdown_active`, the Preview command's enable gate), and the boolean into `Snapshot.current_is_preview` (driving `Snapshot::is_preview_active`, the Edit command's enable gate) and fires the same wake (it does not advance the redraw-frame counter). This is what lets a front-end highlight and reveal the active file even when the buffer changed from inside Neovim (e.g. `:e`). Preview scratch buffers (`b:wolf_preview_source`) are SKIPPED as a real file by this autocmd (they report an empty path + filetype but the preview flag `true`), so the scratch name never leaks into `current_file` / the statusbar while `is_preview_active` still tracks them.

Six other facets are tracked out-of-band the same way (each its own autocmd → `rpcnotify` → redraw-handler fold, none advancing the redraw-frame counter): the **active window** via `wolf_active_win` (a `WinEnter` autocmd → `Snapshot.active_win`), the **current tabpage** via `wolf_tabpage` (a `TabEnter`/`TabNewEntered` autocmd → `Snapshot.current_tabpage`, the macOS refocus-rebind gate; the `wolf_setup_tabs` block also LOCKS OUT nvim-internal tabpage nav/creation per OD4 since Wolf owns all tabpage lifecycle), the **per-window buffer paths** via `wolf_buffers` (a `BufEnter`/`BufWinEnter`/`BufFilePost`/`WinEnter`/`WinNew`/`WinClosed` autocmd emitting a `[win, nvim_buf_get_name(buf)]` list for ALL windows, WHOLESALE-replacing `Snapshot.buffers` so stale/closed windows drop out — driving the macOS per-pane statusbar), **layout intents** via `wolf_layout` (the rebound split/focus chords → a drainable `LayoutIntent` queue), the **app theme colors** via `wolf_theme` (a `ColorScheme` autocmd reading the `WolfCursor`/`WolfTitlebar` groups, emitting once at setup → `Snapshot.theme`; it fires the wake so front-ends re-apply, but bumps no `seq`), and the captive Neovim's **working directory** via `wolf_cwd` (a `DirChanged` autocmd covering `:cd`/`:lcd`/`:tcd`, emitting once at setup). The cwd is stored in a sibling `TrackedCwd` cell (NOT the snapshot — nvim's cwd is not render state, and the triggering `:cd` already flushes via the redraw path, so `wolf_cwd` fires no extra wake). Core reads that cell so the MRU cache follows nvim's live cwd (below), and the front-end reads it (over the FFI `cwd()` accessor) when it walks the window/tab tree at snapshot time — the per-tab cwd is no longer mirrored core-side into a state store. The one-shot INITIAL emit at setup carries a distinguishing `true` flag: core still updates the `TrackedCwd` cell from it (so `live_cwd` reflects nvim's launch dir), but deliberately skips the recent-dirs MRU record, so the passive launch cwd never pollutes Open Recent — only directories the user actually opened are.

The buffer picker's **per-pane view tracking** is a deliberate counter-example: `_G.wolf_setup_view_tracking` (invoked LAST in the attach sequence, over a bare `nvim_exec_lua("wolf_setup_view_tracking()", [])` with NO channel id) installs `BufLeave`/`WinLeave`/`WinClosed` autocmds that maintain an in-nvim `(winid, bufnr) -> winsaveview()` cache and define the `_G.wolf_switch_buffer(win, buf)` helper that reads it — but it emits **no `rpcnotify`** and crosses **no FFI payload**. Unlike the six out-of-band facets above it is NOT a notification into core: the scroll/cursor view lives entirely inside Neovim (core stays view-agnostic), and a buffer switch simply invokes `wolf_switch_buffer` (window-scoped `nvim_win_set_buf`, then `winrestview` of that pane's cached view for the buffer, else the top of the buffer — with no per-`bufnr` fallback, so a buffer only ever seen in OTHER panes opens at the top).

### Output: file-search session (core → front-end)

The file picker reuses the same snapshot+wake shape rather than a bespoke channel. `WolfCore::start_file_search(wake)` returns a `FileSearch` handle whose `read()` exposes an owned snapshot of the results collected so far (`entries`, `complete`, `version`); the MRU seed is present synchronously, and the background traversal streams more in, bumping `version` and firing the **same wake callback** after each batch. The traversal is rooted at the captive Neovim's **live working directory**, resolved OUT-OF-BAND from the tracked `live_cwd()` cell (fed by the `wolf_cwd`/`DirChanged` notification, no `getcwd` RPC), so the picker follows wherever Neovim is (`:cd`/`:lcd`/`:tcd`) and never blocks on a wedged nvim; it falls back to the configured `cwd` only before nvim first reports its cwd. The **MRU seed follows the same live cwd**: core keeps a per-cwd cache of MRU stores (keyed by canonical cwd) and seeds from the store at `<resolved-root>/.wolf`, the SAME root the traversal walks — so seeded entries lie inside the search root and their `display` strings are root-relative (per-project MRU isolation, no leaking a different project's recents and no absolute-path display). The front-end reads + ranks + repaints exactly as it does for redraws (the query is tokenized on whitespace into terms that are AND-matched, order-independent, against each path; see `wolf_core::rank_matches`). Dropping (or cancelling) the handle stops the traversal. Selection feeds back in as an `open(path)` input event (below), which core also records in the MRU — into the per-cwd store for nvim's live cwd (the `wolf_cwd`-tracked cell), keeping the write path symmetric with the seed.

macOS consumes this same session over the FFI: `WolfCoreHandle::start_file_search()` returns an opaque `FfiFileSearch` whose `ranked(query, max)` runs the ranking in Rust and hands back the top-N entries, `open(path)` issues the `Open` input event, and a **second** globally-registered wake (`wolf_ffi_set_filesearch_wake`, parallel to the editor wake) drives a picker refresh on each traversal batch independently of editor repaints. The macOS **file-tree sidebar** consumes the very same shape via its own `start_tree_search()` session: the projection methods `children_of(dir)` (→ opaque `FfiTreeNode`s) and `rel_path_for(abs)` plus the free `wolf_ffi_ancestors_to_reveal(rel)` all delegate to the pure `wolf_core::tree` module (the single source of truth, shared with wolf-gnome), and a **third** registered wake (`wolf_ffi_set_tree_wake`) drives the sidebar's row rebuilds. This tree wake is per-PROJECT (its token carries no view discriminator) and is fanned out to ALL of a project's views' sidebars — each view runs its own independent `start_tree_search()` traversal, so every attached sidebar must be refreshed on each streaming batch (the fan-out is idempotent, each `refresh()` version-gated) — distinguishing it from the editor RENDER wake that targets only the current view. The current-file reveal rides the editor wake (reading `WolfCoreHandle::current_file()`), and the same editor wake reads `WolfCoreHandle::cwd()` — nvim's live, already-canonicalized working directory (a cheap synchronous read of the `wolf_cwd`-tracked cell, NOT the render snapshot) — to re-root the sidebar on `:cd`/`DirChanged`. The snapshot+wake shape is identical; see [`crates/wolf-ffi/README.md`](crates/wolf-ffi/README.md).

### Output: intents (core → front-end)

Things only the platform can do, requested abstractly: "show an open dialog," "show a save dialog for an unnamed buffer," "set the window title to X," "the buffer is modified / clean." The front-end fulfills these with native widgets and feeds results back in as input.

The **layout intent channel is realized** for split panes. The captive nvim's split/focus chords and Ex-commands are overridden (in the bundled `init.lua`) to `rpcnotify` a `wolf_layout` message; core parses each into a `LayoutIntent` — `Split { orientation, from, win }`, `FocusDir { dir, from }`, or `DrawerOpen { win }` — and queues it for `WolfCore::drain_intents`, which the front-end drains on each wake. The asymmetry (decision D4): a SPLIT is performed by nvim (it really creates the window + grid and emits `win_pos`) AND reported so the shell learns the orientation and which pane to split; a FOCUS move is a PURE intent (nvim does not change focus — the shell resolves the neighbour in its own layout and calls `focus_win`); a CLOSE is performed by nvim (guarded against closing the last window) and observed via the `win_close` redraw event (no intent). The shell owns the GTK `Paned` geometry and binds each pane to a Neovim window + its grid, sizing each grid to its pane.

The **terminal drawer** rides this same channel. `wolf_toggle_terminal` really opens a `botright` split window and reports it as a `DrawerOpen` intent; the front-end renders the drawer as a full-width, root-bottom pane at a fixed ~1/3 height that is deliberately held OUTSIDE the pure `PaneTree` (so the tree keeps its 1:1 parity with wolf-gnome and the drawer is excluded from split / neighbour / close for free). Hiding the drawer is a guarded `nvim_win_close` observed via `win_close` (no drawer-close intent) — the same asymmetry as CLOSE. Editor↔drawer keyboard navigation (`<C-w>j` into, `<C-w>k` out of the drawer, including from terminal-insert mode) is a front-end BRIDGE over the pure `focus_dir` intent, since the drawer is not a tree neighbour: the shell intercepts the drawer-origin / bottom-edge cases and drives `focus_win` itself.

macOS consumes this same channel over the FFI: `WolfCoreHandle::drain_intents()` returns opaque `FfiLayoutIntent`s (a SPLIT carries `orientation` + `from` + `win`; a FOCUS_DIR carries `dir` + `from`; a DRAWER_OPEN reuses `win`), `windows()` returns opaque `FfiWinInfo`s and `grid_for_win` / `active_win` track the live grids and active window, and `focus_win` / `resize_grid` feed resolved focus moves and per-pane resizes back in. Each pane reads its grid through `read_frame_for_grid` (the per-grid `FfiFrame` carries `grid_id` / `cursor_grid` and a per-grid `cursor_visible`), while the native command line / completion popup / message toast are read via the dedicated `cmdline()` / `pum()` / `toast()` accessors (opaque `FfiCmdline` / `FfiPum` / `FfiToast`) rather than any grid. The discriminant tables (`intent_kind`, `orientation`, `focus_dir`) are the single source of truth shared between `wolf-ffi`, the Swift `PaneTree` port, and the test suites.

### Output: commands (core → front-end)

The **command channel** generalizes the intent channel end to end. A `Command` is a no-parameter, no-return user action; unlike a layout intent it is ONLY user-triggered (there is no emit-on-attach, so a freshly attached core drains empty). `wolf-core`'s GUI-free `command` module owns the canonical registry (`COMMAND_SPECS`): one row per command, carrying the canonical snake_case `id`, the derived `:Wolf<Pascal>` `ex_command`, a title, and a menu group. The captive `init.lua`'s `_G.wolf_setup_commands(chan, commands)` — invoked last in the attach sequence with the `COMMAND_SPECS` list as `[id, ex_command]` pairs — seeds `package.loaded['wolf']` (so `require('wolf')` resolves under `--clean`) and, per pair, registers a `require('wolf').<id>()` Lua function and a `:<ex_command>` user command, each `rpcnotify`ing `wolf_command '<id>'`. Core folds the id into a `Command` via `Command::from_id` on a drainable queue for `WolfCore::drain_commands`, waking the front-end (no `seq` bump). **The registry is canonical in core, but for this first cut only the `command_kind` discriminant crosses the FFI** — the macOS menu HARDCODES its own item list (exposing the full registry — titles/groups — for a command picker is deferred). macOS consumes the channel over the FFI as `WolfCoreHandle::drain_commands()` → opaque `FfiCommand`s (`kind() -> u8`, a `command_kind` discriminant), decoded by the pure Swift `CommandKind(ffi:)` seam and funneled — alongside the native NSMenu items — through the ONE `CommandDispatcher`. The STATIC command set is New Window / Close Window / Quit Application / Hide Application / Minimize Window / Go to File / Open File / Open Folder / Close Pane (`:close`) / New Buffer (`:enew`) / Reset Font Size / Increase Font Size / Decrease Font Size / Command Palette / Copy / Paste / Buffer Picker / New Tab / Preview / Edit Source / Terminal / Preview in Browser / Use full width for content / Toggle sidebar / Sidebar: Show project / Search in project (`command_kind` `0..25`); the three font-size commands are front-end-only View actions (per-window, ephemeral) with no core input path, Command Palette (`13`) opens the macOS `CommandPaletteView` overlay (`WolfWindowController.openCommandPalette`), the Edit-menu Copy (`14`) / Paste (`15`) bridge the system clipboard to/from the captive nvim (Copy yanks the visual selection over RPC and is enabled only in visual mode; Paste inserts via `nvim_paste`), Buffer Picker (`16`) opens the macOS `BufferPickerView` overlay (`WolfWindowController.openBufferPicker`), New Tab (`17`) opens a new native tab in the current window's tab group (`AppDelegate.makeNewTab`), Preview (`18`, gated on `is_markdown_active`) opens the Markdown preview pane (`WolfWindowController.openPreview`), and Edit Source (`19`, gated on `is_preview_active`) is Preview's inverse — it navigates a preview pane back to its source file per the three placement modes (`WolfWindowController.editSource`), Terminal (`20`, never gated) toggles the per-project terminal drawer (`WolfWindowController.toggleTerminal` → `WolfCoreHandle::toggle_terminal` → `InputEvent::ToggleTerminal` → the `wolf_toggle_terminal` `init.lua` helper — an editor-affecting command, unlike the front-end-only overlays), Preview in Browser (`21`, gated on `is_markdown_active`) renders the active Markdown buffer and opens it in the system default browser (`WolfWindowController.openInBrowser` → the blocking `WolfCoreHandle::open_in_browser`, which returns the per-project loopback preview server's `http://127.0.0.1:<port>/<relpath>` URL — the pinned file's root-relative path — the front-end hands to `NSWorkspace`), and Use full width for content (`22`, never gated but CHECKMARKED from `is_full_width_active`) toggles the active buffer's content width between the ~90-char default and full pane width (`WolfWindowController.toggleFullWidth` → `WolfCoreHandle::toggle_full_width` → `InputEvent::ToggleFullWidth` → the `wolf_toggle_full_width` `init.lua` helper — an editor-affecting command flipping `b:wolf_full_width`, targeting the SOURCE buffer for a preview scratch), and — appended last — the three native-only (flavor a) sidebar commands Toggle sidebar (`23`), Sidebar: Show project (`24`), and Search in project (`25`), each dispatched entirely in AppKit (`WolfWindowController.toggleSidebar()` / `showSidebar(panel: .tree)` / `showSidebar(panel: .search)`) so the captive nvim is never touched (no `InputEvent`); they are the palette/command faces of the View menu's existing standard-AppKit Toggle Sidebar / Project / Search items, so they add no new hardcoded menu items and surface only as command-palette rows and `:Wolf*` Ex-commands. **`wolf-gnome` is untouched** but gets `drain_commands()` for free (it consumes `wolf-core` directly); wiring a GTK menu to it is deferred parity. The `command_kind` table is the single source of truth shared between `wolf-ffi`, the Swift `CommandKind` port, and the test suites.

### Output: preview (core → front-end)

The Markdown preview rides two more out-of-band notifications plus one blocking pull, folded the same way as the facets above (no `seq` bump). The `wolf_current_file` notification now also carries the active buffer's `vim.bo.filetype` (a 2nd arg; the autocmd also fires on `FileType`), folded into `Snapshot.current_filetype` — which drives `Snapshot::is_markdown_active()` (bridged as `WolfCoreHandle::is_markdown_active`), the Preview command's enable gate. The same notification now ALSO carries a 3rd boolean arg `is_preview`, folded into `Snapshot.current_is_preview` — which drives `Snapshot::is_preview_active()` (bridged as `WolfCoreHandle::is_preview_active`), the **Edit** command's enable gate (a preview scratch buffer emits `("", "", true, …)`, so `is_markdown_active` and `is_preview_active` are never both true) — AND a 4th boolean arg `is_full_width`, folded into `Snapshot.current_is_full_width`, which drives `Snapshot::is_full_width_active()` (bridged as `WolfCoreHandle::is_full_width_active`), the **Use full width for content** menu-item CHECKMARK. For a preview scratch the 4th arg reports the SOURCE buffer's flag (OQ-1), so the checkmark tracks the document, not the scratch. A `wolf_preview` notification (a `WinEnter`/`BufWinEnter`/`WinNew`/`WinClosed`/`BufWinLeave` window-scan, emitting once at setup) reports `[preview_win, source_bufnr, source_abs_path, source_full_width]` tuples for every window showing a `b:wolf_preview_source` scratch buffer (the 4th element the SOURCE buffer's `b:wolf_full_width`, folded into `PreviewInfo.source_full_width`), WHOLESALE-replacing `Snapshot.previews: HashMap<i64, PreviewInfo>` (keyed by the preview WINDOW handle) so closed preview windows drop out. A sibling `wolf_full_width` notification (its own `BufEnter`/`BufWinEnter`/`WinEnter`/`WinNew`/`WinClosed` window-scan, emitting once at setup) reports `[win, b:wolf_full_width]` pairs for ALL windows in the current tabpage, WHOLESALE-replacing `Snapshot.full_width: HashMap<i64, bool>` (keyed by window handle; a window absent defaults to `false`) so the front-end can thread each EDITOR pane's width mode into its geometry via `Snapshot::full_width_for_win` (bridged as `WolfCoreHandle::full_width_for_win`). A `wolf_markdown_dirty` notification (markdown-guarded `TextChanged`/`TextChangedI`/`BufWritePost`) upserts `[source_bufnr, changedtick]` into `Snapshot.markdown_ticks: HashMap<i64, u64>`. The front-end joins a preview's `source_bufnr` to its live tick to decide when to re-render: it calls the BLOCKING `WolfCore::render_preview(source_bufnr)` (which `block_on`s `nvim_buf_get_lines`, joins the lines, and renders via `wolf_core::markdown::render_html` with the fixed `PreviewTheme::Default` and `WidthMode::Full`, mirroring the blocking `list_buffers`). The path-based trackers (`wolf_current_file`, `wolf_buffers`) SKIP `b:wolf_preview_source` buffers, so the scratch name never surfaces as a real path. macOS consumes this over the FFI as `WolfCoreHandle::is_markdown_active()` / `previews() -> Vec<FfiPreview>` (each `FfiPreview` joining a `PreviewInfo` to its source tick: `win` / `source_bufnr` / `source_name` / `source_path` / `source_tick` / `source_full_width`) / `render_preview(source_bufnr)` / `open_preview(mode)`. The **Edit** command (Preview's inverse) rides the same surface: `WolfCoreHandle::is_preview_active()` gates the menu item and `edit_source(mode)` navigates a preview pane back to its source (the mode chosen by the front-end's pure `EditSeam` from the pane layout — `split_left` / `reuse_editor_pane` / `active`). Preview rides the existing editor render wake, so `wolf_ffi_wake.h` stays byte-identical.

**Content width — centered by default, per-buffer full-width toggle.** By default a buffer's content area is capped to ~90 columns and CENTERED in its pane, for BOTH the editor AND its in-app Markdown preview; the **Use full width for content** command flips the buffer-local `b:wolf_full_width` to switch that ONE buffer (per-buffer, which per OQ-1 means per-DOCUMENT — a preview and its source share the source's flag) to full pane width. There is NO global "full width by default" mechanism — the toggle is the only control, with ONE exception: the **terminal drawer** (the third window type, alongside editor and preview) DEFAULTS to full width because `wolf_toggle_terminal` seeds `b:wolf_full_width = true` on the terminal buffer, resolved through the same per-window `full_width_for_win` path as an editor pane (no front-end special-casing); it stays user-toggleable. On macOS the ~90-col cap + centering lives in `PaneContainerView`'s single geometry seam, now `geometry(for:fullWidth:)`: `maxCols: 90` (capped + centered, leaving painted side margins) when the pane's flag is `false`, `maxCols: nil` (fills the pane) when `true`. Each pane's flag is resolved by `fullWidth(forGrid:)` — an EDITOR pane reads the per-window `full_width` map by its bound window handle; a PREVIEW pane reads its SOURCE buffer's flag (cached per wake in `previewFullWidthByGrid` from `FfiPreview.source_full_width()`), and its `WKWebView` is framed to that same capped-and-centered `gridRect`. The per-pane statusbar LEFT-ALIGNS to the centered content in BOTH width modes (`StatusbarTextSpan`'s `.preview` span now mirrors `.editor`: indented by the geometry's paint offset when capped, flush when full-width). The in-app preview render itself is full-bleed (`WidthMode::Full`) — the webview FRAME does the capping — while the **browser preview** is a standalone document with no frame, so it is ALWAYS ~90-char centered via `render_html`'s `WidthMode::Capped` (a `body.wolf-markdown { max-width: 45rem; margin-left/right: auto }` cap appended after the theme CSS, `45rem` ≈ 90 proportional Inter chars — OQ-3) and has NO toggle. See [`crates/wolf-macos/DECISIONS.md`](crates/wolf-macos/DECISIONS.md).

### Input: events (front-end → core)

`key`, `mouse`, `scroll`, `resize(cols, rows)`, `resize_grid(grid, cols, rows)` (per-pane), `focus_win(win)` (click-to-focus / resolved focus moves), `open(path)`, `save`, `save_as(path)`, `chdir(path)` (a view's per-tabpage cwd via `InputEvent::Chdir` → `:tcd`, NOT a global `:cd`), the tabpage lifecycle (`set_current_tabpage(handle)` / `close_tabpage(handle)` — the front-end drives every tabpage switch/close), `toggle_terminal` (the per-project terminal drawer, `InputEvent::ToggleTerminal`), and theme-color updates. Core translates these into Neovim RPC calls. Key events are translated to Neovim notation (`<Esc>`, `<C-w>`, `<S-…>`, `<CR>`, modifiers) on the way in. A `key` / `mouse` / `scroll` also DISMISSES a showing message toast (OD8), cleared by the input pump before the batch is applied unless the toast is a `confirm` prompt; the front-end withholds a scroll gesture that lands over the toast (the scroll-over-toast exemption), so that one gesture never reaches core.

## Threading and event-loop model

`nvim-rs` is async (tokio); the platform UIs run their own event loops (glib on Linux, the AppKit/CFRunLoop on macOS). They must not block each other.

- Core owns a tokio runtime on its own thread(s). The `nvim-rs` handler receives `redraw` notifications there and updates the render-state snapshot (behind a lock or via an internal channel).
- On `flush`, core invokes a front-end-registered **wake callback**. The callback is responsible for marshalling onto the UI thread — `glib` idle/channel source on Linux, dispatch-to-main on macOS — and there triggering a paint (`queue_draw` / `setNeedsDisplay`) that reads the snapshot.
- Input flows the other way as plain calls into core, which hands them to the tokio side to issue RPC.

The wake mechanism is the one piece each front-end implements; the snapshot and the RPC are entirely in core.

Because macOS is now **multi-window** over a **one-Neovim-per-PROJECT** model — one captive Neovim (one core / `WolfCoreHandle`) shared by N views, each view an `NSWindow` bound to one nvim TABPAGE — the `wolf-ffi` wake is routed rather than a single global. `wolf_ffi_start` mints a per-PROJECT `u64` **wake token** that the core's `WakeFn` closure captures; the registered `extern "C"` callback (one per wake channel — editor / picker / tree) fires on a tokio worker thread carrying only that plain `Send` scalar (it must not touch the `!Send` handle), and Swift's `*WakeBridge` thunks hop onto the main thread and look the token up in a main-thread `WindowRegistry` (token→`Project`) to reach the owning project, which fans the wake out to its views: the editor RENDER wake and picker wake to its CURRENT view only (the other views hold their last paint), but the file-TREE wake to ALL of its views' sidebars (each view runs its own independent `start_tree_search()` traversal, so every attached sidebar refreshes on each batch). So two projects never clobber each other's redraws. See [`crates/wolf-ffi/README.md`](crates/wolf-ffi/README.md) ("The wake").

## Theming

To make native selection/colors match the OS, the front-end reads the live theme (Adwaita named colors / accent on Linux; `NSColor`/appearance on macOS), converts to RGB, and pushes it into Neovim's highlight groups via `nvim_set_hl` (e.g. `Visual`, default fg/bg). It re-applies on theme/accent change. The renderer stays dumb; Neovim re-emits `hl_attr_define` and the grid repaints.

The reverse direction also exists: a **colorscheme can drive two app-level colors** via the optional highlight groups **`WolfCursor`** (bg = app cursor fill, fg = glyph color) and **`WolfTitlebar`** (bg = macOS titlebar background; fg is carried through the stack but not applied on macOS yet). These groups are never painted on the grid, so the redraw stream never carries them; instead core installs a `ColorScheme` autocmd (`_G.wolf_setup_theme_tracking` in the bundled `init.lua`, emitting once at setup so the startup scheme is picked up) that `rpcnotify`s `wolf_theme` with the groups' effective colors (read with `link = false`, `-1` = unset channel), folded into `Snapshot.theme`. The cursor override is resolved core-side in the existing `cursor_colors` logic (wolf-ffi and wolf-gnome, kept in lockstep) — an unset `WolfCursor` falls back to the reverse-video/mode-attr logic; the titlebar color crosses the FFI via `theme_titlebar_bg()`/`theme_titlebar_fg()` and is applied to (and reverted from) `NSWindow.backgroundColor` by the macOS shell. An unset `WolfTitlebar` keeps the system titlebar. The vendored lighthouse colorscheme defines both groups.

The OS **dark/light appearance** drives Neovim from the front-end side, gated by the user-level `appearance` config key (`auto` / `dark` / `light`, default `auto`, read in the GUI-free `wolf-core` `config` module and bridged as `FfiConfig.appearance()`). On macOS `AppDelegate` resolves the mode at launch and pushes the resolved appearance to every project's nvim along `FfiConfig.appearance` → `WolfCoreHandle::set_background(dark:)` → `InputEvent::SetBackground` → `:set background=dark|light`; `:set background=…` re-sources the colorscheme, so the existing `wolf_theme` re-emit repaints the grid (and the `WolfTitlebar`/`WolfCursor`-driven chrome) with no new theme surface. In `auto` mode the front-end also observes the live OS appearance (a KVO observer on `NSApp.effectiveAppearance`) and re-pushes on each toggle; `dark`/`light` force the appearance regardless of the OS and additionally set `NSApp.appearance` so the whole app chrome matches. The config value is restart-only; only `auto`'s response is live.

## Build

See [Building Wolf](build.md). In brief: on Linux (NixOS), `wolf-core` + `wolf-gnome` build with Cargo under Nix. On macOS, the **Rust core** builds with **Bazel** (driven by **bazelisk**), with `rules_rust`/`crate_universe` consuming the same `Cargo.toml`/`Cargo.lock` and `rules_rust` downloading a pinned `rustc`; the C/link toolchain (apple_support) deliberately uses the **host Xcode SDK** rather than the older SDK shipped inside Nix (this matters for the bundled SQLite that `rusqlite` compiles via `cc`). The macOS path now builds `wolf-core`, the `wolf-ffi` swift-bridge crate, **and** the `wolf-macos` AppKit `.app` — as two targets, `//crates/wolf-macos:Wolf` (the development build) and `//crates/wolf-macos:WolfRelease` (the optimized build to use for real, see [Building Wolf](build.md)) — on the Xcode 26 / Tahoe SDK via `rules_swift` + `rules_apple` (with `rules_xcodeproj` for an uncommitted debug project). The build also **bundles a pinned Neovim 0.12.3** (downloaded hermetically by the `//bazel/nvim` module extension and assembled with `aspect_bazel_lib`'s `copy_to_directory`) plus the captive `init.lua`, the **vendored orlando plugin** (via the `//bazel/orlando` module extension), and the **vendored lighthouse colorscheme** (via the `//bazel/lighthouse` module extension, activated by `init.lua`) into `Contents/Resources/`, so the packaged app no longer needs `WOLF_NVIM_BIN` to run (a developer's exported `WOLF_NVIM_BIN` / `WOLF_INIT_LUA` still wins).

## Deferred / open

- The GTK native completion popup + multi-line scrollable toast (decision 7 — realized on macOS, deferred on GNOME per OD4).
- Whether a shared portable renderer (decision 2) ever earns its keep.
- **Markdown-preview scroll-sync (cursor-follow) is DESIGNED but NOT built.** The core's emitted preview HTML already carries the forward-compatible position markers from day one — a per-hard-line marker `wl-{L}-0` and a per-100-CHARACTER-column marker `wl-{L}-{k*100}`, each the exact form `<span class="wolf-src" id="wl-{L}-{C}" data-line data-col></span>` (`L` = 1-based hard line, `C` = 0-based CHARACTER column per OD4). The follow-up (a Neovim→web-view cursor-position signal + the JS that finds `#wl-{line}-{col}`, falling back to `#wl-{line}-0`, and scrolls it into view only near a viewport-edge threshold, converting nvim's byte column to a character column) is NOT implemented in this change. Accepted v1 marker-collapse granularity: a container / block's interior line markers all collapse to immediately before that block's opening tag (every `wl-{L}-0` id still EXISTS but resolves to the block top), so per-100-column markers are mostly redundant until inline-level anchoring is added.
- **Multiple preview themes are a future extension.** One theme (`PreviewTheme::Default`) ships now; the `PreviewTheme` enum + `theme_css` + `include_str!`'d CSS files are structured for more, with a config-driven selector (e.g. a `wolf-config.yaml` key) as the designed-for-later extension point (OD5 — the preview theme follows the app's resolved dark/light appearance via a `@media (prefers-color-scheme: light)` block but is NOT wired to the live nvim colorscheme this cut).

### Split panes — known v1 limitations

The first split-panes cut is deliberately scoped; these are intentional, each with a clear future direction (see also [`crates/wolf-gnome/README.md`](crates/wolf-gnome/README.md)):

- **Only windows opened via the overridden split commands get a pane.** Panes come from `wolf_layout` `Split` intents, emitted only by the rebound chords / Ex-commands. A window created by a non-overridden path (`:help`, the quickfix / location list, a preview window, `:diffsplit`) still gets a grid + `WinInfo` but no pane, so its content is not shown. _Future:_ auto-pane any unbound window grid.
- **Focus-direction moves use the tree's idealized split ratios** (`0.5`), not the actual dragged divider positions, so `<C-w>h/j/k/l` can pick a different neighbour than the pixel geometry after a manual drag. (This is a GNOME-specific limitation now: the macOS `PaneTree` preserves per-child weights, and its `neighbor` resolves over the live weighted `paneRects`, so a dragged divider IS reflected in focus-direction moves.)
- **Floating and external windows are ignored** (`win_float_pos` / `win_external_pos` / `msg_set_pos` are dropped), so they do not appear as panes.

The **project/tabpage-per-view** model (macOS) adds two intentional v1 limitations:

- **The nvim-internal tabpage nav/creation lockout is best-effort** (OD4): the `gt`/`gT`/`<C-w>gt`/`<C-w>gT`/`<C-PageUp>`/`<C-PageDown>` chords and the typed `:tabnew`/`:tabnext`/`:tabprevious`/`:tabonly`/`:tabclose`/`:tabmove` Ex-commands are locked out, but obscure typed variants / user abbreviations / scripted `nvim_*` tabpage calls are NOT caught, so a determined user could still desync a view from its tabpage. (`:tcd`/`:lcd`/`:cd` are deliberately left open — they set a view's own cwd.)
- **A non-current VISIBLE window can blank on live-resize** (two side-by-side windows of the same project): a non-current view holds its last paint (the project drives RENDER wakes only to `currentView`), and `wantsLayer` keeps that layer — but a live-resize can still force a `draw` with the grids gone, so the non-current pane may blank until refocused.
