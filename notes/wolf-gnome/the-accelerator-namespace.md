# The accelerator namespace

Last verified at commit `6298d01fb761da1bfdd64a0a25671a40b9d4e525`.

Every action name, its accelerator, its `Command` correspondence, and its menu placement live in one table, so the menu, the accelerators, and the command dispatch cannot drift apart. Chords spoken for by a later unit are declared and marked reserved rather than omitted, which is what lets the invariant below be checked before anything binds them. A reserved row exists to hold a chord, so one whose chord a bound row takes is deleted rather than kept declaring nothing.

**The invariant is that no Neovim key becomes unreachable.** A `Ctrl+Shift+<letter>` accelerator gives up only the terminal-style Ctrl+Shift alias for `<C-letter>`. This crate's key encoder forces `shift: false` on printables, so `Ctrl+Shift+P` encodes to `<C-p>` and `<C-S-p>` cannot be emitted at all; `<C-p>` itself is still delivered by plain `Ctrl+P`, which is never bound. `parse_accel` and `forbidden_reason` enforce that mechanically over every row, reserved ones included, so a shadowing chord fails while it is reserved rather than months later.

`<C-c>` and `<C-v>` are where that invariant earns its keep, because neither is an ordinary letter: `<C-c>` interrupts and `<C-v>` is visual-block and insert-mode literal-next. Plain Ctrl+C and Ctrl+V carry no shift, and `action_for_key` compares its three modifiers exactly, so neither matches a bound chord and both reach Neovim — outside the one keystroke in which a compose sequence is pending, where a plain `Ctrl+<letter>` press was measured to be claimed by the input method instead ([Present limitations](present-limitations.md)). What Ctrl+Shift+C and Ctrl+Shift+V give up is the `<C-S-c>` / `<C-S-v>` alias the encoder cannot emit in the first place.

**A `Ctrl+<symbol>` chord consumes a control code, not merely a key.** Neovim receives a chord as bytes and folds `Ctrl+<symbol>` to `symbol & 0x1F`, so `<Control>grave` eats `0x00` — the backtick spelling of `<C-@>` — while `<Control>bracketleft` would eat `0x1B`, Escape. Every row therefore declares the byte its chord folds onto; Escape and DEL are refused whatever a row declares, and a `<Control>` chord over a key name the crate cannot resolve to a symbol is refused rather than waved through. `<Control>grave` is bound at a measured price: `Ctrl+Shift+2` survives it and still reaches Neovim as `<C-@>`.

Single-letter rows declare no fold, and the reason is the modifier mask rather than the character class. The rule above already refuses a bare `Ctrl+<letter>`, so every surviving letter row carries Shift, and `action_for_key` matches masks exactly: were `Ctrl+Shift+I` or `Ctrl+Shift+M` bound, plain `Ctrl+I` and `Ctrl+M` would still reach Neovim as `<C-I>` and `<C-M>`. `<Control>grave` carries no Shift, which is precisely why it does consume the byte it folds to.

`Ctrl+Shift+<letter>` is the namespace because nothing else is available. There is effectively no free `Ctrl+<letter>` across all Neovim modes, and in a terminal pane every key but core's `<C-w>` router chords reaches the shell. New Window is where that scarcity bites: `Ctrl+Shift+N` is spent on the new-buffer row (macOS Cmd+N) and no `Ctrl+Shift+<letter>` is free, so the row carries no chord at all and declares no fold, reaching the user through the primary menu, the command palette and `:WolfNewWindow`.

Save As is the second instance of that rule: macOS spells it Shift+Cmd+S, which transliterates onto the `Ctrl+Shift+S` that Save holds (macOS Cmd+S), so Save As spends no chord and the primary menu is its only route. Save takes the chord because it is the one a user presses reflexively, where Save As is a deliberate act.

A forwarded, unmapped Alt chord splits into `<Esc>` plus the base key, and a forwarded, unmapped Super chord drops the modifier in normal mode and inserts literal text in insert mode, so neither is a namespace Neovim can be given. The genuinely free keys are too few and too unidiomatic to carry a menu. The rule is memorable: take the macOS chord and replace the command key with Ctrl+Shift.

One consequence is worth knowing: a disabled action's accelerator falls through to Neovim, which is what a real GTK accelerator does and what the chord controller deliberately reproduces, so in the empty state `Ctrl+Shift+O` reaches Neovim as `<C-o>`, `Ctrl+Shift+F` as `<C-f>` and `Ctrl+Shift+B` as `<C-b>`. A pending compose sequence is expected to interrupt that fall-through, since every press the chord controller declines is offered to the input method and a plain `Ctrl+<letter>` press was measured to be claimed — but the `Ctrl+Shift` case itself is inferred rather than measured ([Present limitations](present-limitations.md)).

**`Alt+Left` and `Alt+Right` are the namespace's one deliberate exception**, and the asymmetry it creates must not be tidied away. They carry Back and Forward, and capturing them is exactly what prevents the `<Esc>` plus `<Left>` split a forwarded Alt chord produces. So their actions stay enabled even where a press would refuse, unlike every `Ctrl+Shift+<letter>` row, which is disabled instead and gives up only an alias by falling through. The two toolbar buttons desensitize in their place, which costs nothing: a press with nothing to go back to issues no RPC anyway.
