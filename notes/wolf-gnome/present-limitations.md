# Present limitations

Last verified at commit `6298d01fb761da1bfdd64a0a25671a40b9d4e525`.

- Save and Save As are front-end-only action rows carrying no registry command, so neither appears in the command palette, whose rows come from `COMMAND_SPECS`; why the registry has no Save command is [`feat-list.md`](../feat-list.md)'s. Save carries `Ctrl+Shift+S` and a menu item, Save As the menu item alone. The overwrite confirmation belongs to GTK or to the desktop portal, so this front-end never observes it and cannot report a clobber it did not perform.
- Theming is one-directional: the configured `appearance` is resolved against libadwaita's light/dark reading, pushed into Neovim as `background=dark|light`, matched on the chrome's colour scheme, and carried by that scheme into a preview document's `prefers-color-scheme` ([The preview's light and dark](../wolf-gnome-decisions.md#the-previews-light-and-dark)). No OS colour is read into Neovim's highlight groups, so macOS's `nvim_set_hl` push has no counterpart; Neovim's own colorscheme reaches the grid paint, the `WolfCursor` group reaches the cursor, and `WolfTitlebar` or else `Normal` reaches the header bar and the tab bar.
- `macos-option-as-alt` is the one configured key this front-end ignores, silently and with nothing reported at launch, because its own name says which platform it is for and one config file is shared across both.
- Over an editor pane, pointer input covers the primary button and vertical scroll; a terminal pane forwards the primary, middle and secondary buttons to its session. There is no context menu, no middle-click paste, no horizontal scroll, and no kinetic scrolling, all matching macOS. The scrollbar is a projection with no thumb drag: it shows where the viewport sits and accepts no input at all, which macOS defers too.
- A per-pane status bar's text is clipped to its own pane rather than tail-truncated with an ellipsis, so a path too long for its pane ends mid-glyph. macOS ellipsizes; reproducing that here means a second Pango layout builder in the widget layer, which is the thing `render.rs`'s one-glyph-path rule exists to prevent.
- Only windows created through the overridden split commands become panes. A window from `:help`, quickfix, `:pedit`, or `:diffsplit` gets a grid but no pane, and floating or external windows are ignored. A Markdown preview is not one of those: it lands in an existing pane or in one the same split path creates, so it is always a real pane.
- A click inside a preview pane does not focus it. The web view takes pointer input, which it must or the pane could not be scrolled, so the click never reaches the pane's own gesture; `<C-w>w` and Neovim's own post-placement focus are the routes. That same routing is what makes a link click work: measured under `cage`, a synthetic pointer click reaches WebKit's DOM hit test and repoints the pane. **Do not fix this with `set_can_target(false)`** — it kills scrolling and link following together, and with them most of what makes the pane a preview rather than a picture.
- Nothing connects `web-process-terminated`, so a crashed WebProcess leaves the pane frozen on its last committed frame, with nothing logged and no recovery. **Do not try to detect this from a capture**: after a deliberate kill the `grim` image was byte-identical to the healthy one, which is exactly why the signal has to be connected instead.
- Preview in Browser produces the loopback address and hands it to the platform URI launcher, and nothing on this front end can observe whether a browser opened. `gtk::UriLauncher::launch` reports success on a session with no portal and no browser and does nothing at all, so the only diagnostic is the failure callback such a session never invokes. The server half is core's, and is proved there.
- A snapshot-version advance rebuilds the sidebar's root store, so a directory the user expanded by hand collapses on every streaming traversal batch and on a re-root. Manual expansion does survive a current-file change, which is what the version gate buys; carrying it across a version advance needs the model layer redesigned around per-directory stores.
- The navigation surfaces are Back and Forward alone: two header-bar buttons, two menu items, and `Alt+Left` / `Alt+Right`. There is no jump list of a pane's recently visited files, which the macOS History menu carries. A dynamic list needs a `gio::Menu` rebuilt on each popover open and an action parameterized by stack index, where `MENU_SECTIONS` is const data with invariants checked over it.
- The content-width toggle carries no menu item and no accelerator. `MENU_SECTIONS` is const data with no stateful check item to show a per-buffer flag in, and a chord would spend one of the scarce free `Ctrl+Shift` letters on a preference. Its surfaces are `:WolfFullWidth` and the command palette's own row, which appears automatically because the palette filters on the same classification the menu resolves through.
- No HiDPI scale handling beyond a terminal pane's backing surface, which is made at the device scale: the cell-measurement probe assumes 96 dpi, and a session's cell size goes in logical pixels.
- A grid glyph from the symbols face ([Typography](../wolf-gnome-decisions.md#typography)) draws unscaled and about one em wide, over part of the cell after it. Its baseline lies the symbols face's ascent below the cell's glyph-box top, and the text baseline the configured face's ascent, so the two differ.
- In a terminal pane, the cursor and blinking text draw steady, and double, dotted and dashed underlines draw as the single straight line, as on macOS. Unlike macOS, nothing draws a pending composition there, for the reason the composed-sequence limitation below gives.
- No smoke runs with a desktop portal, since every cage's bus activates none ([The headless smoke test](../wolf-gnome-decisions.md#the-headless-smoke-test)); what that leaves unobserved is listed in [`tests/README.md`](../../crates/wolf-gnome/tests/README.md#what-is-still-unproven).
- A composed sequence draws nothing while it is pending: GTK's own compose path reports an empty preedit string at every step — every preedit signal fires and `preedit_string()` answers empty with cursor 0 — so a dead key and a `Multi_key` sequence are invisible until they commit, and this front-end sets no cursor location either. An engine that does produce a preedit cannot run under the harness at all, whose flake ships no engine and no GTK 4 ibus module, so a preedit renderer would be a paint path over the grid that neither suite could execute — what [The pure seams](../wolf-gnome-decisions.md#the-pure-seams) exists to prevent.
- While a compose sequence is pending, a plain `Ctrl+<letter>` press is claimed by the input method and does not reach Neovim, and the sequence survives it — all of that measured. The reach is a code fact instead: `key_route` takes no modifier state and `wire_keys` passes none, so every press past the overlay guard is offered, a disabled action's `Ctrl+Shift+<letter>` fall-through included — whether the context claims that one is inferred. A bound, enabled chord is untouched, the capture phase having matched it first; the cost is `<C-c>`, `<C-v>` and every other `Ctrl+<letter>` Neovim wants, in the one keystroke between a dead key and the key resolving it. The repair, refusing the offer to a press carrying `CONTROL_MASK`, owes a measurement first: that a pending sequence survives it.
- A window's input method is focused in once at build and focused out at close, and does not follow window activation, so in a session with several windows every window's context reports itself focused. The one `notify::is-active` handler reports terminal focus and the selected tab's UI focus, the `:checktime` trigger, and leaves the input method's focus untouched; making that follow activation is a unit of its own. GTK's built-in simple context is client-side and per instance, so nothing crosses between windows.
- The command palette lists the registry commands this front-end performs, one Open Recent row per usable recent directory, and one Switch to Window row per other open window. One directory can appear as both, which is the honest surface rather than a duplicate: an Open Recent row re-roots the invoking window's selected tab through the same pending-re-root path the Open Folder dialog takes, and a Switch to Window row leaves it alone and raises the other window. An Open Recent row is refused only for the selected tab's own directory, and another tab or window editing that directory does not revive it.
- A backgrounded window cannot be brought forward under the headless compositor the smokes run in, so activating a Switch to Window row there does nothing visible ([The coordinator and its windows](the-coordinator-and-its-windows.md)). On a session compositor it is xdg-activation's answer, not this crate's.
- No chord switches tabs. The bubble controller forwards every translatable key to Neovim, and a next/previous pair would spend two of the scarce free `Ctrl+Shift` letters; the surfaces are the bar itself, `Ctrl+Shift+T`, the New Tab menu item and `:WolfNewTab`.
- Closing the last tab is closing the window, and the arm that does it is unreachable from the shipped UI: only the bar's close button and a middle-click raise `close-page`, and the bar allocates nothing at one page. It ships because it is the right answer wherever it is reached: a window with no tab holds a tab bar and no editor, with no way to reach one.
- A restored tab contributes its saved tab until its own first gather succeeds, so one whose layout never binds a pane goes on saving what it was restored from, whatever it shows. A tab the user opened contributes nothing until its own gate opens, so one closed before its first pane binds is not saved ([Application state](application-state.md)).
- A saved tab carries no cursor, top line, preview scroll, focused pane, sidebar mode, query or toggles, and no drawer: this front-end writes each as absent, so none survives a quit and relaunch, and a zoomed drawer persists unzoomed.
- A compositor-initiated minimize, such as Super+H, is invisible to Wolf, because Wayland never tells a client it is minimized; only Wolf's own Minimize puts a window behind the others in the saved stacking order ([Application state](application-state.md)).
- Whether mutter activates a window restored minimized before minimizing it is unmeasured. If it does, that focus unmarks the window and the next save writes it unminimized; `cage` ignores a minimize request, so no smoke can tell.
- Open Folder and Open Recent read no project state and focus no tab already open on the directory, as [§6](../../specs/application-state.md#6-opening-a-folder) asks: they re-root the selected tab.
- The sidebar is per window and shows the selected tab's directory, so a switch between tabs in different directories re-roots it, collapsing what the user expanded ([Window structure](window-structure.md)).
- Tabs share no Neovim, and so nothing live; [One Neovim per tab](../../specs/application-state.md#8-one-neovim-per-tab) states what that leaves unshared.
- An Open Recent row exists only for a directory the user changed into: core does not record the launch working directory (see [`runtime/nvim/README.md`](../../runtime/nvim/README.md)), so a project only ever launched into is absent from the palette until the user changes directory.
- The drawer does not survive a quit and relaunch. It lives outside the pane tree, and this front-end writes no `drawer` to a saved tab ([Window structure](window-structure.md)), so every session starts with it closed, and it opens at a third of the pane area whatever share it had been dragged to.
- The empty state disables three actions, the file picker's, the project search's and the sidebar toggle's, and routes still go around the first two. A new-buffer or close-pane chord fires behind the opaque status page, where the result is invisible until a folder is opened. The palette offers a live row for every dispatched command, so its "Go to File…" row reaches the file search on a project-less window while the menu item is insensitive and the accelerator falls through; the search row is refused instead, by `search_panel::show_decision`'s no-project arm.
- The buffer picker stays enabled in the empty state, and that is a decision rather than an oversight: unlike a file search it has no project root to be rooted wrongly at, and each tab's Neovim runs there too, with its `Untitled.md` buffer listed.
- An assistive-technology activation of a header-bar sidebar toggle bypasses the click rule: the group shows the toggle it activated while the sidebar stays as it was, until the next show, hide or page switch relays the group back into step. Pointer clicks never reach the group's own activation ([`sidebar_toggles.rs`](../../crates/wolf-gnome/src/README.md#sidebar_togglesrs)), and the group takes no keyboard focus.
