# Window structure

Last verified at commit `6298d01fb761da1bfdd64a0a25671a40b9d4e525`.

The window is an `adw::ApplicationWindow` whose content is a vertical box: an `adw::HeaderBar`, then an `adw::TabBar`, then a horizontal `gtk::Paned`. The Paned's start child is the sidebar, a page switcher over a `gtk::Stack` of the file tree and the search panel; its end child is a `gtk::Overlay` whose main child is an `adw::TabView`. Each `adw::TabPage` carries a `gtk::Overlay` of its own whose main child is the pane view — a tree of nested `gtk::Paned` with one host `gtk::Overlay` per Neovim window, built from the pure pane tree, plus a one-row command-line strip along the bottom.

**One window owns one captive Neovim and N tabs share it**, so the tab boundary cuts below the transient overlays: the pane view, its empty state, its message toast and its completion popup are per tab, while the header bar, the `win.` actions, the three transient overlays and the crash overlay stay per window — the last of those because it is a property of the core every tab shares. A tab switch closes all three transient overlays, since each was opened over a pane view the switch takes off screen.

**The sidebar stays per window, and that is a measured consequence rather than a preference.** Moving it into a page forces the `adw::TabView` above the `gtk::Paned`, which widens the window-level `gtk::Overlay` from the pane area to the whole window and moves the left edge both the crash-overlay click and the picker/preview overlap band are derived from. **It must move into the page in the unit that gives tabs independent working directories**; short of that, one `FileSearch` traversal serves every tab of a window, which is right because they share one folder.

**`adw::TabBar`'s autohide is load-bearing.** At one page the bar allocates zero height, so a one-tab window's geometry is identical to a build carrying no tab layer at all and every pointer smoke's derived target still holds; turning it off shifts the pane origin by the bar's height and breaks the pointer smokes loudly through their shared origin assertion, which is the guard. Autohide works by allocating nothing rather than by hiding the widget, so `is_visible()` reads `true` at one page and an assertion on it would say nothing.

**The terminal drawer is held outside the pane tree**, so the pane area is a vertical box of exactly two children: the editor tree, then the drawer's full-width strip along the bottom. macOS made that choice explicitly so its own tree keeps 1:1 parity with this front-end, and three things follow: the drawer never reaches `layout_snapshot` and so never reaches `state.json`, as [Session restore](../../specs/terminal-panes.md#session-restore) requires, `set_divider_fraction` has no drawer boundary to address, and every `neighbor` answer is untouched.

No divider separates the two, and the reason is the scrollbar's. A draggable handle's position would have nowhere to live, the drawer being in neither the tree nor `state.json`, and it would snap back on the next `max-position` notify — a control that visibly refuses input. The strip takes a fixed share of the pane area instead, and the drawer's grid is sized from its own allocation like every other pane's, because Neovim re-divides only the grids the front-end has not sized.

Everything else treats the drawer as an ordinary pane, with no drawer branch anywhere: its status line, its `full_width_for_win` cap, its own `resize_grid` and its paint. The height rule and the editor-to-drawer focus bridge that pay for its absence from the tree are in [`drawer.rs`](../../crates/wolf-gnome/src/README.md#drawerrs).

Each pane leaf is a host `gtk::Overlay` whose main child is a `gtk::DrawingArea` and whose only overlay child is a `webkit6::WebView`, added when the pane becomes a Markdown preview and removed when it stops being one. **The tree parents the host, never the drawing area**, which is what carries a live web view through a rebuild instead of costing a `WebProcess` respawn and a fresh cold load on every layout change. A window-level overlay child is rejected for the view: a divider drag rebuilds nothing and issues no wake, so a margin-positioned window child would sit stale over a pane that had moved.

**A preview pane skips exactly its text grid and its scrollbar thumb, and needs no containment seam to do it.** The draw func fills the whole allocation with the editor background before anything else, so a skipped grid leaves that background rather than garbage, and a preview scratch buffer carries no lines in any case — which makes the skip a one-bit predicate with no tolerance, unlike the macOS rule [`architecture.md`](../../specs/architecture.md) names. The statusbar strip is never skipped, and the cursor goes with the grid, since under an opaque view it would paint invisibly.

The pane's statusbar strip, its editor padding, its text grid and its scrollbar thumb are all painted into the drawing area with Cairo rather than being widgets of their own. The padding must be filled in the editor's own per-frame background out of the snapshot, and this front-end takes no colour from the GTK theme into the grid, so a widget leaf would draw a theme-coloured frame around a Neovim-coloured grid. Every pixel-to-grid conversion routes through [`editor_inset.rs`](../../crates/wolf-gnome/src/README.md#editor_insetrs)'s arithmetic either way.

**The scrollbar is painted rather than a `gtk::Scrollbar`, and three reasons hold independently of the strip's.** A `gtk::Scrollbar` is a control: it carries a `gtk::Adjustment` and accepts input, so shipping one invites a thumb drag with no feedback path into Neovim, and a control that visibly refuses input is worse than an indicator that never claimed to take any.

A widget child would ride the pane's host overlay, re-parented into a freshly rebuilt tree on each layout change, inside the region the focus regime below warns about. And macOS's fade rides a repeating 30 Hz timer, which "Threading and the wake" forbids — so the bar is always visible, which is why only the thumb is drawn and never a track — GNOME's own idiom is an overlay indicator with no trough at rest.

A pane's body is painted identically whether the pane is active or not: no scrim, no tint, no border, nothing conditional in the grid paint. **The strip's text is the only active-pane signal** — bold at full strength in the active pane, both lines scaled by `STATUSBAR_INACTIVE_ALPHA` in the others — and macOS draws the same.

An edge treatment is the thing to resist: it lands in the padding gutter [`scrollbar.rs`](../../crates/wolf-gnome/src/README.md#scrollbarrs)'s thumb hides in, and a long thin high-contrast line above a narrow pane's text is measured to corrupt `tesseract --psm 11`'s scale estimate for the whole pane. Masking that top line alone restored a heading `--psm 11` had misread on a retained capture; masking the same pane's right or bottom edge alone left the misreading in place, which is what pins the cost to the edge above the text rather than to the ink in general.

The header bar is the unified toolbar: the sidebar toggle, a linked Back/Forward pair and Open at the start, the primary menu at the end, and the window title between them. **No title widget is set**, so Adwaita draws the title itself and the bar keeps its natural height. That is load-bearing rather than incidental — the bar's height is one term of the pane origin `PANE_ORIGIN_Y_EXPECTED` pins, the statusbar strip and the editor padding above the grid being the others, and every pointer smoke derives its targets from that origin, so a title widget silently retargets every one of them.

The overlay's children are added empty state, then message toast, then completion popup, then picker, then command palette, then buffer picker, then crash overlay, then restart banner, and that order is the stacking. Project search is not among them: it is a sidebar page. At most one of the three transient overlays is open — the shell closes the other two when it opens one — so their relative order is not observable, while each must sit above the empty state or it would open invisibly in a project-less window. The toast and the popup are above the empty state for the same reason, since the captive Neovim runs in a project-less window and its messages have to be readable there, and below all three overlays so a message is never drawn over rows the user just opened.

A crashed core must cover the picker's Open, a palette row, a buffer-picker row and the empty state's Open Folder, since each would send into a dead Neovim. A search result row sits in the sidebar, outside that cover, so `search_panel::activation_route` refuses it instead. The banner is topmost and click-through, so it confirms a restart without swallowing a click meant for the editor.

**An overlay composites over a preview, and that is observed rather than argued.** The transient overlays are children of the window-level `gtk::Overlay`, while a web view is a child of a per-pane overlay nested inside that overlay's main child, and GTK 4 paints overlay children after the main child and all its descendants. One window captured twice, with nothing between the frames but the chord that opens the file picker, reads the document's background and its heading ink where the two regions overlap, and exactly none of either with the box open. [`tests/README.md`](../../crates/wolf-gnome/tests/README.md) owns the smoke.

A WebKit rendering through a Wayland subsurface would sit outside that ordering entirely, and does not: against a fixture forcing an accelerated-compositing layer, the same rectangle holds three quarters of the layer's own colour with no overlay and none of it with the picker open. A promoted layer is inside the GTK scene, so a sibling overlay child occludes it like anything else.

**GTK keyboard focus never lands on a pane area.** Pane drawing areas are not focusable, their host overlays and web views cannot take focus either, and nothing grabs focus on any of them; a click parks focus on the persistent command-line strip instead, which is also the focus-return target the picker, the command palette, the sidebar, the search panel's Escape and opened results, and the crash overlay use. Every widget under the pane area is destroyed and rebuilt on each layout change, and a destroyed focus widget leaves the toplevel with no focus at all — after which window-level key dispatch dies outright while Neovim stays alive and silent.

`gtk::Paned` sets its dividers focusable itself and this crate cannot change that, so a rebuild additionally samples the toplevel's focus widget before unparenting anything and returns focus to the strip. That sample must stay above the teardown: the moment a widget is unparented rather than hidden, a later sample stops reporting it.

That strip belongs to a tab, so each overlay resolves its return target from the selected page at close time instead of capturing one when it is built. A captured strip is an unmapped widget after a tab switch, and a setter called on each switch turns a forgotten call into a silent wedge of exactly the kind above.

**The sidebar's search panel is not an overlay.** It is outside the one-at-a-time rule: showing it closes the three overlays, and nothing closes it, so a tab switch or a crash leaves its query, its rows and any running `rg` alone. Only a new run, an empty-query Enter or the window's close cancels the search. While focus is inside the panel, `wire_keys` forwards nothing to Neovim and offers nothing to the input method, as it does while an overlay is open.

Its list never takes focus, because every streamed batch replaces every row and a destroyed focus widget is the wedge above. For the same reason, focus inside the sidebar is returned to the selected tab's strip before the sidebar or its Search page is hidden: a hidden focus widget leaves the toplevel with none.

Input has two regimes. Keys are global: a capture-phase controller on the window matches this crate's own chords and stops propagation, and a bubble-phase controller offers everything else to the window's own `gtk::IMMulticontext` and routes only what the context declines through the key seam into Neovim's current window, or into the session of a terminal pane that is the selected tab's active pane ([Terminal panes](terminal-panes.md)). So a bound chord is never also forwarded — and never offered to the input method either, which is the half that is easy to lose.

What the context claims arrives instead as a `commit` string, and becomes core input through [`im_ui.rs`](../../crates/wolf-gnome/src/README.md#im_uirs)'s rulebook, or session input through [`terminal/input.rs`](../../crates/wolf-gnome/src/terminal/README.md#inputrs)'s.

Pointer input is per pane, on each drawing area. Resize flows per pane through the geometry seam into `resize_grid` and then resizes the outer grid; the authoritative sizes come back from core. A terminal pane also sends its pointer to its session and sizes the session itself ([Terminal panes](terminal-panes.md)).
