# Terminal panes

Last verified at commit `6298d01fb761da1bfdd64a0a25671a40b9d4e525`.

[Terminal panes](../../specs/terminal-panes.md) owns the contract, and [`src/terminal/`](../../crates/wolf-gnome/src/terminal/README.md) the seams and the painter. These are the choices the GTK glue makes behind them, mostly in `pane_view.rs` and `window.rs`.

**Each terminal pane paints through a backing surface of its own.** A `gtk::DrawingArea` always redraws its whole area, and every wake redraws every pane of the current tab, a terminal publish included. So a terminal pane keeps a `TerminalCanvas` of its painted cells, repaints only the rows the frame damaged, and blits it on every draw: the GTK form of the macOS `TerminalPaneView` subview. Editor panes redraw on every wake, so a busy terminal costs each editor pane of its tab a repaint per publish.

The cursor is drawn over the blit and never into the surface, so a cursor move damages no row. It draws steady, as blinking text does, because a blink needs the periodic timer [Threading and the wake](../wolf-gnome-decisions.md#threading-and-the-wake) forbids.

**Input is routed at key time from the selected tab's active pane.** The overlay guard and the input-method precedence of [Window structure](window-structure.md) hold unchanged, so every press is offered to the window's `gtk::IMMulticontext` first; macOS bypasses its input context for Ctrl chords and named keys, and GTK's declining does that job here. A declined press reaches `terminal_key` through `gdk_key`. A commit of one printable ASCII character is sent as a key rather than as text, because GTK's simple context claims plain printables and core's `<C-w>` router would otherwise never see a chord's second key.

**The pane's gesture takes every button.** Over an editor pane a non-primary press returns before focusing anything or pinning, so editor panes stay primary-only. Over a terminal pane the primary, middle and secondary buttons each send a press, drag motion and a release, with the session and the button pinned at press, and only the primary press focuses the pane, as on macOS; core decides between the program's mouse tracking and a selection. Buttonless motion is sent only while the frame's `mouse_tracking` is on, and a wheel goes through the editor pane's accumulator and then as one `terminal_scroll` carrying the whole step count.

**Each wake sizes the sessions the current tab shows**, after the grids are synced and the active pane updated. `geometry::sizer` picks one pane per session, the active pane before the last sizer, and `resize_terminal` goes out when the size differs from the one last sent or, for a running session, from the frame's. Only the current tab's pane view runs on a wake, which is this front-end's form of the spec's most recently focused pane. An unallocated pane sends nothing, and `resize_grid` still sizes the placeholder's grid.

**A session holds focus while its pane is the active pane of the selected tab of an active window.** Each pane view remembers the session it last reported and sends the loss before the gain. `TabsHandle::sync_terminal_focus` drives every tab, the unselected ones first, so a tab switch reports the loss first; it runs after each wake's tab refresh and from a `notify::is-active` handler. A restart reports the loss before the panes are dropped, because core rescans the file tree on it.

The same focus picks the cursor's shape under [the render contract](../../specs/terminal-panes.md#the-render-contract). Each pane view keeps the `focused` of its last sync and redraws its panes when it changes, which is enough because the cursor is drawn over the blit. `draw_pane` passes `focused` to the canvas for the active pane alone. The painter decides rather than core, because focus belongs to a pane and a frame to a session, and core would learn of a focus change a wake late and publish a frame although no cell changed.

**`WOLF_SMOKE_TERMINAL` opens a terminal pane before the app reports ready**, test-only and off by default, so a smoke's first typed key reaches the shell; the drawer and a typed `:terminal` need keys of their own. `window::build` reads it once and hands the command to tab 0's pane view, which opens the session in the active pane's window on the first wake with a pane, before that wake reads pane state. Opening it inside that wake means the readiness file, which needs a later painted frame, cannot be written before the session is bound. A failure prints one `wolf-gnome:` line.
