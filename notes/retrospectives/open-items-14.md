# Retrospective: prune `notes/macos-followups.md` to its open findings

Last verified at commit `f78cd3b65fa563f2a27ddef3327b0893eea6998a`.

The task deleted the 58 `Verified` and `N/A` rows of the ledger and closed its two `Open` rows by stating each divergence in its owning document. It turned one by-reading residual into the ledger's one open finding, and rewrote the intro and the close procedure. It ran in one pass with no rejection, `non-zero`, discrepancy or resume: plan 1, one invocation per agent, both gates green on their first run, and review 1 approved. The five invocations cost about $10.63, and `architect-1` was $5.86 of it.

## What went well

- **The ledger's format changed, as five earlier reports asked.** Recommendation 2 of [open-items-2](open-items-2.md), repeated through [open-items-12](open-items-12.md), is now carried out. `notes/macos-followups.md` went from 80,716 to 2,133 bytes, its table is gone, and its one finding is a `###` section that `Read` and `Grep` handle without a script. Its "Adding and closing a finding" section says that closing a finding deletes its section, so closed rows can no longer pile up. A cleanup round can drop that recommendation.
- **Plan 1 gave every row its disposition and owning document, by line number.** `technical-writer-1` did not re-derive them: it spot-checked five rows (L36, L37, L52, L56, L62) and finished in 50 turns and about 4 minutes. This repeats what [open-items-5](open-items-5.md) found, that line numbers in the plan make a ledger edit cheap.
- **Plan 1 counted the word budgets before assigning sentences.** It found the `FileTreeView.swift` entry at 249 of 250 words, named four cuts, and routed the cell-width sentence away from the full `render.rs` entry. The writer made those cuts and the documentation gate passed on its first run. In [open-items-12](open-items-12.md) a plan that did not count cost three Python passes.
- **`git grep -n macos-followups` and doc-lint's anchor check made the link fixes mechanical.** Plan 1 listed every reference into the ledger, including two in `crates/wolf-gnome/tests/smoke_headless.rs`, and doc-lint would have failed any broken anchor. No link needed a second pass.

## What did not go well

- **The old table cost one more full re-check, done three times.** `architect-1` ran 98 turns over 13.5 minutes for $5.86. It first read the 80 KB file in 10-line `awk` slices, then made about 80 `grep` and `sed` calls to find each row's owning document. `technical-writer-1` and `reviewer-1` each split rows with `awk -F' \\| '` again to check the plan. This was the last time, since the table is gone, so it needs no new recommendation.
- **The planner and the writer each built a word counter.** `architect-1` wrote an `awk` copy of the `entry-budget` rule, and `technical-writer-1` ran `tools/lint/markdown_check.sh` with `WOLF_MD_MAX_ENTRY_WORDS=0` to read the counts out of the findings. This came up again: it is recommendation 3 of [open-items-12](open-items-12.md).
- **Three more entries are at their budget.** Plan 1 found the `render.rs` and `pane_view.rs` entries of `crates/wolf-gnome/src/README.md` and the `WolfWindowController.swift` entry of `crates/wolf-macos/Sources/WolfMacOS/README.md` at 250 words. That is why the cell-width decision went into `notes/wolf-gnome-decisions.md` "Typography" and not the `render.rs` entry that owns `CellMetrics::for_font`. The same pressure on `PaneContainerView.swift` is recommendation 1 of [open-items-9](open-items-9.md).
- **A real-nvim test flaked in the coder's gate run.** `coder-1`'s first `./gates.sh` failed only on `//crates/wolf-ffi:history`, in `history_bridge_tracks_navigation_back_forward_and_jump`. The jump list read `["c.md", "b.md", "Untitled.md"]` where `a.md` was the oldest entry. It passed three times alone and on the second gate run. No earlier report or README records it.
- **This is the second startup flake in two tasks.** [open-items-12](open-items-12.md) recorded `cursor_moves` failing the same way, a first action that seems to land before the startup buffer settles. In `crates/wolf-ffi/tests/history.rs` the test sends `:e a.md` right after `wait_for_attach` and `wait_for_active_win`. Whether the startup `Untitled.md` buffer is still being set up then is a lead, not a cause this task proved.
- **A documentation-only task ran the whole implementation path.** Two false sentences about the ledger sat in `smoke_headless.rs`, a test file, so plan 1 sent them to `test-writer-1`. `coder-1` then had nothing to change but ran the macOS gate twice and clippy and fmt on Linux, for $0.53, before the implementation gate ran both workers again. [open-items-1](open-items-1.md) recorded the same duplicate gate runs as flow design; nothing in the repository invited it.
- **The landed open finding has the wrong date.** Its heading reads `2026-08-08`, the date of the `linux-feat/terminal-drawer` row. Review 1 found that the residual was written on 2026-11-07, in commit `0405f7d`, and the file's own procedure heads a finding by the date it was found.

## Recommendations

1. **Diagnose the `history.rs` flake.** In `crates/wolf-ffi/tests/history.rs`, find whether `:e a.md` can reach Neovim before the startup `Untitled.md` buffer settles, and if so wait for that state before the first `:e`. `coder-1`'s failure is the evidence, and it cost a second macOS gate run. If the cause is the same startup race as recommendation 1 of [open-items-12](open-items-12.md), fix both together.
2. **Let the markdown checker report an entry's word count.** This came up again: it is recommendation 3 of [open-items-12](open-items-12.md). In this task two agents each made their own counter.
3. **Correct the open finding's date.** Change the heading in `notes/macos-followups.md` to `2026-11-07`, as review 1 found. It is one word, and it keeps the file consistent with its own procedure.
