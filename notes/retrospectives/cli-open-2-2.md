# Retrospective: macOS wiring of the `wolf` command, the open channel, tab IDs and Finder

Last verified at commit `1cd895d9eeaae8379cb18531c677d005663b0890`.

The task wired `crates/wolf-macos` to the previous task's core work: the listener, tab IDs, the directory and file rules of `specs/cli-and-file-open.md`, the bundled `wolf` binary with its install command, and Finder's document types. It took four rounds and 16 invocations for about $61.71 and 127 agent-minutes. Three rejections caused the rework: `coder-1` on E7 and T2, `coder-2` on E11, and review 1 on two tests with no ID. Every gate run, both implementation and both documentation, exited 0 on both workers at the first try.

## What went well

- **The seams kept most reds cheap.** `FileOpenSeam` and `CommandInstallSeam` are plain types in `Sources/WolfKeyMap/`, so F1 to F7, C1 to C5 and I1 to I8 run headless in `WolfKeyMapTests` over a hand-built window list and a stub `runPrivileged`. `coder-2` ran every falsifier of plans 1 and 2 as one `--test_filter` run each, through a scratch script with checksums, and `coder-4` recorded F7 and I8 for $0.61. What stayed outside a seam, `AppDelegate`'s queue and `application(_:open:)`, is compile-verified only (review 1 §3), so keep new routing logic in `WolfKeyMap`.
- **The wiring rule held for six new test files.** `CLAUDE.md`'s rule on explicit `srcs` lists got five Swift files into `WolfKeyMapTests` and `WolfMacOSTests` and `open_requests.rs` into its own `rust_test`, with no gate round trip (review 1 §3).
- **The socket-path gotcha recorded by the previous task was reused.** Plan 1 §4 took the relative state dir under one short base from `crates/wolf-core/tests/open_channel.rs`, as [cli-open-2-1](cli-open-2-1.md) asked to keep. No run failed on the 103-byte limit.
- **The existing real-Neovim fixtures covered the new flows.** E1 to E12 build on `TerminalViewFixture`, `PreviewViewFixture` and the `WindowStateCodec` restore that `ExtrasRestoreTests` uses (`test-writer-1`'s report), so the task added no fixture.

## What did not go well

- **A blocking call overtaking queued input cost two rounds.** `TabCore.respawnNeovim` reopens files with `handle.open`, which is queued input, while `open_terminal` and `rebuild_tab` are blocking RPCs that reach Neovim first. T2 opened a session right after a restart and lost it to the queued `:edit`, and E11's layout let an open placed too early land in the same pane as a correct one, so it could not fail. `coder-1` and `coder-2` each found this by instrumenting the code; round 2's planning cost $2.02 and round 3 cost $2.56.
- **The fact was written down, but not where a planner looks.** At the base, only `specs/terminal-panes.md` § When Neovim dies and the `PaneContainerView.swift` mirror say that a blocking bind reaches Neovim ahead of queued opens, both about the terminal restore. `crates/wolf-core/src/README.md` says only that other calls are "fire-and-forget, on the ordered input channel" and that `open_terminal` blocks. `architect-1` read only the previous task's diff of `terminal-panes.md`. The technical writers added it to two more entries, `TabCore.swift` and `TabIdTests.swift`, each about one site.
- **E7's plan row left out the side that decides the rule.** Plan 1 said "a preview pane beside a terminal pane", and §5.2 rule 3 takes only a leftmost pane. `PreviewViewFixture` previews in the right pane, which its README entry does not say ("beside its source"), so `test-writer-1` built `vertical[terminal, preview]` and the code rightly split instead. It shared round 2 with T2; the side is now written in the `OpenRequestFlowTests.swift` entry rather than the fixture's own.
- **Unplanned tests fell through again.** `test-writer-1` listed two tests under "Extras beyond the table", one worded as "F1's `currentTab` recency fallback". Neither `coder-1` nor `coder-2` gave either one a red, and the first had a fixture in which recency and tab order agreed, so a `tabs.first` fallback passed it. Review 1 findings A and B sent it back, and round 4 cost $4.03; `test-writer-1`'s system prompt still has no rule for a test the plan does not ask for.
- **A count comment was already false.** At the base, `AppDelegate.swift` said "Register the three process-global wake callbacks" over four `install()` calls; the fifth made it review 1 finding C. `crates/wolf-ffi/src/lib.rs` still numbers the wake statics "third", "fourth" and "fifth sibling" (lines 1624, 1665 and 1708, review 2 §5), and nothing checks either.
- **Plan 1's L1 edit would have launched the user's `Wolf.app`.** Run as written, `open -b org.wolf.WolfMacOS` finds the installed bundle; `coder-2` swapped in a made-up identifier and plan 3 recorded it. Nothing in the repository invited it, so nothing is recommended.
- **A cached result looked like a fresh pass.** `coder-3` reran E11 after reverting its edit and got the first green run's timing back, so it ran again with `--nocache_test_results`; plan 4 then asked for the flag. `build.md` does not mention it.
- **Two READMEs stay over the size warning and one grew.** `technical-writer-1` added 19,173 bytes over 15 files for $9.91. `crates/wolf-macos/Sources/WolfKeyMap/README.md` went from 53,403 to 56,219 bytes, while `Sources/WolfMacOS/README.md` needed a 1,229-byte cut to drop under it.

## Recommendations

1. **State the ordering rule once, at the API.** In the paragraph of `crates/wolf-core/src/README.md` that splits blocking queries from fire-and-forget calls, say that a blocking call reaches Neovim ahead of any input queued before it. Name `open` and `chdir` as queued, and `open_terminal`, `bind_terminal` and `rebuild_tab` as blocking. Then have the `TabCore.swift` and `TabIdTests.swift` entries and the spec link it rather than restate it; T2 and E11 would have been planned with a barrier, saving about $4.58 and two rounds.
2. **Give an unplanned test its own ID at the test writer.** This is recommendation 1 of [cli-open-2-1](cli-open-2-1.md) and of [sidebar-toggles-1](sidebar-toggles-1.md), come up again for a fifth task. Here the test is worded as part of a planned ID, so the coder's rule for a test with no ID did not fire; key the table to every new test function in the diff, not to the report's prose. Round 4's $4.03 would not have been spent.
3. **Say which pane `PreviewViewFixture` previews.** In its entry in `crates/wolf-macos/Tests/WolfMacOSTests/README.md`, say the preview is the right pane of a vertical split, because `PaneTree.split` appends. Then move the E7 bullet's "`PreviewViewFixture` previews on the right" out of the `OpenRequestFlowTests.swift` entry and link it, so that one document owns the fixture.
4. **Drop counts and ordinals from the wake comments.** This is recommendation 5 of [application-state-8](application-state-8.md) and 6 of [ghostty-5](ghostty-5.md), come up again. Rewrite the "third", "fourth" and "fifth sibling" doc comments in `crates/wolf-ffi/src/lib.rs` as "a sibling of [`WAKE_FN`]".
5. **Say in `build.md` how to rerun a test after a revert.** Next to the macOS test commands, say that `--nocache_test_results` is needed to show a fresh pass. `coder-3` repeated a run for want of it.
6. **Split the large READMEs.** This is recommendation 3 of [cli-open-2-1](cli-open-2-1.md), come up again, now with `crates/wolf-macos/Sources/WolfKeyMap/README.md`, whose `Persistence/` subdirectory already has a README of its own.
