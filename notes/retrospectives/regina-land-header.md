# Retrospective: the macOS statusbar strip takes its colours from `Normal`

Last verified at commit `7c4784b846bd29ea9048051187fd55bed922d81f`.

The task moved each macOS pane's statusbar strip from the titlebar colour to the editor default colours, as wolf-gnome already did. `paintStatusbar` fills with grid 1's default background, and `StatusbarText` blends the default foreground with wolf-gnome's alphas and rounding. The run went straight through: `architect-1`, `test-writer-1`, `coder-1`, `technical-writer-1` and `reviewer-1`, one plan and one approving review. Both gates passed on their first run on both workers.

The five invocations cost about $15.42 and 40 minutes of agent time. `architect-1` cost $5.77 over 77 turns, `test-writer-1` $2.87, `coder-1` $2.56, `reviewer-1` $2.48 and `technical-writer-1` $1.74. There was no round trip, so nothing below cost an extra invocation.

## What went well

- **One FFI value already gave the right colour for every pane.** `FfiFrame::from_snapshot_grid` in `crates/wolf-ffi/src/lib.rs` sets every frame's defaults from `highlights.defaults`, and `PaneContainerView.draw(_:)` already read grid 1 for the padding. Plan 1 §1 reused that read, so an occluded preview and a terminal pane, which never read their own frames, got the colour with no new FFI call and no `wolf-ffi` change.
- **The offscreen fixtures carried three new pixel tests.** `TerminalViewFixture`, `PreviewViewFixture`, `TerminalPaneFixture` and `OffscreenRenderer` gave E, T and P a real core, Neovim and Lighthouse. The only fixture change was an `initLua` parameter on two initialisers. `test-writer-1` built `//crates/wolf-macos:WolfMacOSTests` on its first attempt.
- **Reading expected colours from the pinned file caught a wrong premise.** The task instructions gave Lighthouse's `Normal` as `#252525` and `#ffffff`, which are `activeBG`. Because the tests read `colors/lighthouse.lua`, plan 1 §1 corrected this and nothing downstream used the wrong values. The new `LighthouseColours.normal(_:)` also checks the `Normal` wiring as a premise, so a pin bump that rewires it fails as a premise.
- **wolf-gnome's pure `statusbar_text` and its table gave the Swift port an oracle.** `statusbar_text_table` in `crates/wolf-gnome/src/statusbar_layout.rs` holds four hand-computed rows, one of them a 178.5 tie. Plan 1 §3 copied them into `StatusbarTextTests.swift`, and C6a to C6f each went red against them.
- **The wording lint's stale-entry check surfaced a coupling at plan time.** Removing the macOS clause from `statusbar_layout.rs` would leave allowlist entry A5 in `tools/lint/wolf_gnome_wording_allowlist.txt` stale, which fails the lint. `architect-1` read `wolf_gnome_wording_check.sh`, and plan 1 §3 had the coder delete A5 and the writer reword "A1 to A8" in `tools/lint/README.md`.
- **The architect counted entry budgets, and the writer had no overrun.** Plan 1 §5 gives `--entry-words` counts for every entry it changes, and routed the decision to `notes/wolf-macos-decisions.md` because the `PaneContainerView.swift` entry was at 250 of 250. `technical-writer-1` finished in 40 turns with every entry under budget. `architect-1`'s system prompt does not ask for the count, so this rests on the agent: [regina-land-toast](regina-land-toast.md) recommendation 1 still stands.
- **`regina on linux` let the coder check the Linux side before handoff.** `coder-1` ran the wording check, `cargo fmt`, doc-lint and the `rustdoc-links` command on the Linux worker for the one Rust comment change. The implementation gate then passed first time on both workers.

## What did not go well

- **The pinned Lighthouse source cannot be read from the checkout.** `architect-1` ran `find /` for `lighthouse.lua`, then two `WebFetch` calls and three `curl` calls to GitHub to read the pinned file. `test-writer-1` built `//bazel/lighthouse:lighthouse_tree` and read the file out of Bazel's external directory by its hashed path. `bazel/lighthouse/README.md` names the commit and tarball but says nothing about reading the file locally.
- **A highlight fact was wrong in the request.** The instructions' `#252525` was taken from `activeBG`, not `Normal`. This is the class of fact [regina-land-terminfo-2](regina-land-terminfo-2.md) recommendation 1 asks to write down, come up again. Here the oracle caught it, so it cost one paragraph of plan 1, not a round trip.
- **The statusbar text table exists twice.** `StatusbarTextTests.swift` repeats `statusbar_text_table`'s four rows by hand, linked only by a doc comment and two README bullets. Review 1 §3 notes that a change to the Rust table does not fail the Swift test, so the two front-ends can drift without a red.
- **The `wolf-macos` source READMEs are near the size warning, and that cost a complete entry.** `crates/wolf-macos/Sources/WolfMacOS/README.md` is 48,337 bytes and `WolfKeyMap/README.md` 48,446. `technical-writer-1` left the `Color.swift` entry without `packed(_:fallback:)`, `fallbackFgRgb` and `fallbackBgRgb` to keep the file net-neutral, and review 1 §8 lists the gap. This is [ghostty-3](ghostty-3.md) recommendation 3, come up again.
- **The `PaneContainerView.swift` entry is at its budget again.** Plan 1 §5 found it at 250 of 250 words and gave it no change, so the strip's colour rule lives only in `notes/wolf-macos-decisions.md` and the doc comment. This is [open-items-11](open-items-11.md) recommendation 2, come up again.
- **A bridge call has no front-end consumer.** After this task, nothing outside `crates/wolf-ffi/tests/` calls `theme_titlebar_fg`. Its doc comment at `crates/wolf-ffi/src/lib.rs:2605` says "not applied on macOS this pass", which is history wording. `technical-writer-1` and review 1 §8 both noted it, and it landed as is.

## Recommendations

1. **Say how to read the pinned Lighthouse file.** In `bazel/lighthouse/README.md` § The pin, add one sentence: after `bazel build //bazel/lighthouse:lighthouse_tree`, the file is at `$(bazel info output_base)/external/+lighthouse+lighthouse/lighthouse.nvim-<commit>/colors/lighthouse.lua`. `architect-1` went to GitHub five times and `test-writer-1` found the path by hand, and every colour task plans against this file.
2. **Keep one statusbar text table for both front-ends.** Put the rows in a data file, for example `crates/wolf-gnome/src/testdata/statusbar_text_table.tsv`, and read it from `statusbar_text_table` with `include_str!` and from `StatusbarTextTests.swift` through the `swift_test`'s `data`. Review 1 §3 found that the two copies can drift without a failing test.
3. **Split the two `wolf-macos` source READMEs.** This is [ghostty-3](ghostty-3.md) recommendation 3, come up again. Here it cost the `Color.swift` entry its new API.
4. **Split `PaneContainerView.swift` and its entry.** This is [open-items-11](open-items-11.md) recommendation 2, come up again.
5. **Decide whether `theme_titlebar_fg` stays.** Either remove it from the bridge and its two tests, `crates/wolf-ffi/tests/theme.rs` and `lighthouse_load.rs`, or reword `crates/wolf-ffi/src/lib.rs:2605` and the bridge comment at line 592 to state, in the present tense, that no front-end reads it. Review 1 §8 left this open.
