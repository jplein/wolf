# Retrospective: move the statusbar text and scrollbar geometry into `WolfKeyMap`, test the divider span, and close three ledger rows

Last verified at commit `14b498a4ab894c2064dfbcccdc596f5d1611d623`.

The task ran in one pass, with no rework. Plan 1 was followed by the test writer, the coder and the technical writer. Both gates passed on the first run on both workers, and review 1 approved the work with minor notes. The five invocations cost $13.05 in all: `architect-1` $4.38 (58 turns), `test-writer-1` $1.79, `coder-1` $2.58, `technical-writer-1` $1.93 and `reviewer-1` $2.37.

## What went well

- **A pure library with a pinned API let tests and code meet at the first try.** Plan 1 gave the exact Swift signatures of `StatusbarText` and `ScrollbarGeometry`, and worked rectangles such as track `(830, 54, 8, 604)`. `test-writer-1` typechecked its three files with `swiftc -typecheck` against stubs of that API. `coder-1`'s first `//crates/wolf-macos:WolfKeyMapTests` run compiled and passed 468 tests, and no test needed an edit. That works because `wolf_key_map` is AppKit-free, so a seam moved out of `PaneContainerView` can be tested without a window.
- **The wolf-gnome counterparts served as the reference.** `crates/wolf-gnome/src/scrollbar.rs` and `statusbar_layout.rs` gave the shape of each seam, and the gutter sweep was modelled on `the_thumb_lies_wholly_inside_the_right_gutter`. Plan 1 needed no design work for either type.
- **Falsifiers were cheap to run.** `--test_filter=<Class>` on `WolfKeyMapTests` ran one class per falsifier, and `coder-1` ran nine (F1 to F5 and their variants), each restored and checked by checksum. That is how plan 1's F5 showed what the equal-extent assertion catches that the `pairSpan` sum alone misses.
- **`doc-lint same-code` proved the Rust edits comment-only.** `coder-1` checked `scrollbar.rs` and `statusbar_layout.rs` with it, and ran only `cargo fmt` and `cargo clippy` on Linux, not the whole Linux gate.
- **Line numbers in the plan made the ledger edit cheap.** Plan 1 named rows 48, 49 and 50 of `notes/macos-followups.md`, and `technical-writer-1` changed them with one script and no wrong match. In [open-items-4](open-items-4.md), a parser for the same kind of edit matched the wrong rows first.

## What did not go well

- **`//tools/lint:swift_format` lints nothing.** `test-writer-1` found that the target passed, saying `Linting 132 Swift file(s)`, while its new files had lines over 100 columns. Run by hand, `swift-format lint --strict` reported `AddLines` and `Indentation` errors in them, and four in the base `PaneTreeWeightsTests.swift` at lines 67 to 70. The diagnosis took about six commands, and `coder-1` then checked its own files by hand too.
- **The cause is likely the symlinked runfiles.** The target's inputs are runfiles symlinks, and `test-writer-1` concluded that swift-format skips symlinked inputs, since it has a `--follow-symlinks` flag. Nobody confirmed that by passing the flag. Until the gate is fixed, Swift formatting is checked only when an agent remembers to run swift-format by hand.
- **The lint README explains the blind gate wrongly.** The bullet "swift-format check and fix enforce different things" in `tools/lint/README.md` says the check covers only lint-category rules, so files `format` would restyle can pass it. But `lint --strict` reports `Indentation` when given the files directly, so that bullet probably misreads the same symptom. [open-items-4](open-items-4.md) saw a hand run fail where the target passed, and could not explain it. Plan 1 §6 then told the test writer to check formatting with the blind target.
- **wolf-gnome prose that describes macOS went stale again.** Review 1 found two sentences in `crates/wolf-gnome/src/scrollbar.rs`, at lines 97 and 254, that compare the Rust widening rule with "macOS's reason", which was the deleted `PaneContainerView` comment. Both are stale on the branch. `architect-1` spent six searches (`omits the`, `drawScrollbars`, `macOS`) to find five other places in that file and one in `statusbar_layout.rs`, and missed these two.
- **The macOS mentions are many.** `scrollbar.rs`, `statusbar_layout.rs` and `crates/wolf-gnome/src/README.md` together mention macOS 40 times, and each is a sentence a macOS change can falsify. This is the pattern of [open-items-4](open-items-4.md) recommendation 1, where `lib.rs`'s divergence counts went stale.
- **A plan step ran over a word budget.** Plan 1 §5 asked for a Decisions bullet in the `PaneContainerView.swift` entry of `crates/wolf-macos/Sources/WolfMacOS/README.md`. `technical-writer-1` wrote it, found that the entry came to 292 words against the 250-word budget, and removed it as a restatement of the new `WolfKeyMap` entries. Review 1 accepted that. It cost little, but the plan had not checked how close the entry was to its budget.
- **The ledger is still read whole.** `architect-1` printed all of the 88 KB `notes/macos-followups.md` to find three rows. This came up again: it is recommendation 2 of [open-items-2](open-items-2.md).

## Recommendations

1. **Make `:swift_format` lint the real files.** In `tools/lint/swift_format_check.sh`, pass `--follow-symlinks` to `swift-format lint`, or resolve each argument with `realpath` first, and confirm the target then fails on a bad line. Fix the four findings at `PaneTreeWeightsTests.swift` lines 67 to 70, and whatever else the first real run reports across the 132 files. `test-writer-1` and `coder-1` would then have relied on the gate, not on hand runs.
2. **Correct the swift-format bullet in `tools/lint/README.md`.** Rewrite "swift-format check and fix enforce different things" once the check runs, so it no longer blames the blind gate on lint-category rules. That answers the hand-run question from [open-items-4](open-items-4.md), and keeps the next plan from trusting the target as plan 1 did.
3. **Add a test that the swift-format check fails.** On the model of `tools/lint/markdown_check_test.sh`, add an `sh_test` that runs `swift_format_check.sh` on a badly indented fixture under `tools/lint/testdata/` and expects a non-zero exit. Give the fixture as a runfile, so that it is a symlink as the real inputs are. Linux has no swift-format, so the test is macOS-only, and `CLAUDE.md`'s rule that a lint test also gets a Linux `run` line in `gates.sh` needs an exception for it. A check that passes everything stays hidden until someone runs swift-format by hand, as `test-writer-1` did here.
4. **Stop wolf-gnome's docs from describing macOS's code.** This came up again: it is recommendation 1 of [open-items-4](open-items-4.md), applied to the module docs. In `scrollbar.rs` and `statusbar_layout.rs` under `crates/wolf-gnome/src/`, state each rule and its reason in Rust's terms, and link `WolfKeyMap/ScrollbarGeometry.swift` or `WolfKeyMap/StatusbarText.swift` only for the accepted divergences. Start with the stale sentences at `scrollbar.rs` lines 97 and 254. A macOS change would then need no search of the Linux crate, which cost `architect-1` six searches and missed two sentences.
