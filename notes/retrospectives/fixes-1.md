# Retrospective: Command-W closes a terminal pane and the drawer, and core ignores `SIGPIPE`

Last verified at commit `276d5d6b0db3971919b8d8b1a1eb7c602f852e3f`.

The task fixed Command-W (`CommandKind::closePane`) for a focused split terminal pane and for the drawer on macOS. It also had to show where the key was lost on each platform: on macOS, the drawer's Close was disabled by `AppDelegate.validateMenuItem`, because `paneCount` counted only `tree` leaves. A split was not lost in the container or core, and GNOME's Ctrl+Shift+W was not lost at all (smoke G1 green before any change). A second fix, `WolfCore::start` ignoring `SIGPIPE` for the whole process, came from the task's one round trip.

The eight invocations cost about $22.66 and 83 minutes. `architect-1` was the largest, at $6.13 and 15 minutes. Both gates passed on both workers on their first run (`implementation-1`, `documentation-1`), and review 1 approved with minor notes.

## What went well

- **The `WolfMacOSTests` live fixtures carried a new test class with no new helper.** `TerminalViewFixture` and `LiveCore`, from the ghostty series, gave T1–T5 a real core and Neovim. `test-writer-1` wrote all five and the `BUILD.bazel` line in $2.57. `coder-1` then took eight macOS reds, C1a to C5a, one test each, with `--test_filter=<Class>/<method>`.
- **`regina on linux` made the GNOME answer a measurement.** `coder-1` ran G1 on Linux before any change, then G1a to G1d, in nine remote requests. Review 1 could therefore state that GNOME does not lose Ctrl+Shift+W, and G1a's red showed that the chord goes through `win.close-pane`.
- **`markdown_check.sh --entry-words` ended the word-budget hunt.** `architect-1` ran it while planning, and plan 1 §5 and plan 2 §5 give each entry's count (248/250, 249/250). `technical-writer-1` ran it once and landed three entries at 250, 248 and 248, and the documentation gate passed first time. In [ghostty-3](ghostty-3.md) the writer had to read the checker's source to learn the same counts.
- **One Bazel target per test file let a process-wide test exist.** T6 sets `SIGPIPE` back to its default for its whole process. In `//crates/wolf-core:sigpipe`, its own binary, that touches no other test, and `coder-2` could run its red alone on macOS.

## What did not go well

- **The one round trip was a known test-host death that no note held.** `coder-1`'s `./gates.sh` died with `Broken pipe` in `//crates/wolf-macos:WolfMacOSTests`, and `coder-1` returned `rejected` because plan 1 said "No code changes in wolf-core". [ghostty-3](ghostty-3.md) had recorded the same death and left it "to be reported if it recurs". `architect-1` read `notes/macos-followups.md`, which said "No finding is open", and nothing else in the repository named the death.
- **Showing that the death was not the change took 24 full-suite runs.** `coder-1` measured 3 deaths in 14 runs, in new and old tests alike, and 0 in 10 with `SIGPIPE` ignored temporarily. Its report says the first death "looked like a regression from this change". The replan added `architect-2` ($3.21), `test-writer-2` ($1.37) and `coder-2` ($1.41): $5.99 and 26 minutes. The fix itself was worth having, because Wolf.app would also die on input after a Neovim crash, but a recorded defect could have been planned in plan 1.
- **The `nav_history_live` flake cost a Linux gate run again.** `coder-2`'s first `regina on linux -- ./gates.sh` failed at `nav_history_live.rs:563` with "must return b.md's source bufnr, got 0", in a 16.4-second run. `coder-2` ran the binary five more times and the gate a second time. It identified the flake only through [round-4-2](round-4-2.md), whose recommendation 4 asked for it in `notes/crates/wolf-core/tests/nav_history_live.rs.md`, and that mirror still says nothing about it.
- **No test reaches the line where the bug was.** The drawer's Close was lost in `AppDelegate.validateMenuItem`, but `WolfMacOSTests` has no key window or menu, and a `WolfWindowController` needs a `Project` that starts its own core. So T1–T5 enter at `PaneContainerView.canClosePane` and `closeActivePane()`, one hop below the menu. The task asked for tests from the key event or menu action. Review 1 §3 records the gap, and manual check M1 covers it but was not run.
- **A planned falsifier edit could not be applied as written.** Plan 1's C5a said to delete "the `handle.focus_win(…)` call", which matches three lines in `PaneContainerView.swift`, and deleting it leaves `win` unused. `coder-1`'s scripted edit refused it, and the edit of record became `handle.focus_win(win)` → `_ = win`, which plan 2 then had to restate. The cost was small.
- **Running one XCTest method is still not in `build.md`.** `coder-1` found `--test_filter=<Class>/<method>` by trying it and named the gap in its report. Plan 2 left it to the retrospective. This is recommendation 5 of [open-items-11](open-items-11.md), come up again.
- **The new real-Neovim `rust_test` was written out by hand again.** `crates/wolf-core/BUILD.bazel` gained 28 lines for `sigpipe`, repeating the runfiles, `WOLF_*` env, tags and deps of `nvim_liveness`. This is recommendation 1 of [round-4-3](round-4-3.md), and recommendation 6 of [regina-land-terminfo-2](regina-land-terminfo-2.md), come up again.
- **A G1 readback name is written in three places.** Each of G1's five readback constants is declared in `smoke_headless/terminal.rs`, imported into `fixture_guards.rs`, and listed in `RELAUNCH_FIXTURE_NAMES` with its name as a string and its test's name. That is about 28 lines in `fixture_guards.rs` for one smoke. Plan 1 said G1 "registers no terms", and `test-writer-1` registered the names anyway, following the termflow smoke, reading the plan as meaning OCR terms only.
- **One earlier report is now wrong.** [ghostty-3](ghostty-3.md) says "Nothing in the repository ignores `SIGPIPE`". `WolfCore::start` now does, as `notes/wolf-core-decisions.md` § Liveness and restart says.

## Recommendations

1. **Give open flakes and known test-host deaths a home that planners read.** Add `notes/known-flakes.md`, linked from `build.md` § The verification gate, with one entry per open flake: the target, the failing line or signature, its run time when failing, and the report that found it, starting with `nav_history_live.rs:563`. Had [ghostty-3](ghostty-3.md)'s `Broken pipe` death been listed there, plan 1 could have included the one-line fix, saving the $5.99 replan and most of `coder-1`'s 24 runs. `coder-2` would also have cleared its Linux gate failure without reading old retrospectives.
2. **Record the `nav_history_live` preview flake and make its failure explain itself.** This is recommendation 4 of [round-4-2](round-4-2.md), come up again. Here it cost `coder-2` a second Linux gate run and five runs of the binary.
3. **Name `--test_filter=<Class>/<method>` in `build.md`.** This extends recommendation 5 of [open-items-11](open-items-11.md) to `WolfMacOSTests` and to a single method. `coder-1` ran eight single-method reds with it after finding it by trial.
4. **Give the real-Neovim `rust_test` one macro.** This is recommendation 1 of [round-4-3](round-4-3.md), unchanged. This task added `//crates/wolf-core:sigpipe` by hand.
5. **Let a Swift test reach Close Pane's menu gate.** Give `WolfWindowController` an initializer over an existing `WolfCoreHandle` and `PaneContainerView`, or move the `.closePane` arm of `validateMenuItem` into a function of the key controller that `WolfMacOSTests` can call with the fixture's container. The bug in this task sat in that arm, and the shipped fix there is covered only by the unrun M1. A later bug in a menu item's enable rule would get an automated red.
6. **Have plans give each disabling edit as an exact, unique line that still compiles.** In the architect's definition, ask for the line to replace, quoted, and its replacement. Plan 1's C5a matched three lines and left an unused binding, so `coder-1` improvised the edit and plan 2 restated it.
7. **Derive `RELAUNCH_FIXTURE_NAMES` entries from the constants.** A `macro_rules!` in `crates/wolf-gnome/tests/smoke_headless/fixture_guards.rs` that takes the constant and its test, and writes the name with `stringify!`, would make each entry one line. G1 added five three-line entries that each repeat their constant's name as a string.
