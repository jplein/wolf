# libghostty-vt builds and links on both platforms, with the `wolf-vt` binding and the terminal-panes spec

Last verified at commit `3a504957a7c9d0bf5c179d8e906c2577e18f0024`.

The task was g00 of the libghostty-vt series. It pinned libghostty-vt 1.0.0 and Zig 0.17 in `flake.nix` and under `//bazel/zig` and `//bazel/ghostty-vt`, added the `crates/wolf-vt` binding and its `tests/binding.rs`, listed the linked libraries' licences in both About surfaces, and wrote `specs/terminal-panes.md`. It took eight invocations and about $35.58, and review 1 approved with one minor note. The only round trip was a Linux implementation gate that failed on a `flake.nix` guard in `smoke_headless.rs`.

## What went well

- **The forbidden-dependency check caught a wrong design inside the coder, not at a gate.** Plan 1 had `coder-1` pipe `deps(//crates/wolf-vt:wolf_vt)` into `wolf_core_deps_check.sh` before the gate. It rejected the plan's `apple_support.run_shell`, which pulls `@bazel_tools//tools/objc:host_xcodes` into the graph, and `coder-1` used the C toolchain's environment instead. The gate's `wolf-core-deps` step queries only `//crates/wolf-core:wolf_core`, which does not reach `wolf-vt` until g01, so only the plan's check could catch this.
- **The `shellHook` guard named its failure exactly.** `every_shellhook_export_is_scrubbed_or_deliberately_kept` printed the unclassified `WOLF_GHOSTTY_VT_DIR` and the three lists it was missing from. So `architect-2` planned the fix in 23 turns for $1.43, and `test-writer-2` made it for $0.34. Keep the guard, but make it easier to find (see below).
- **One test pins both platforms' copies of the version.** The release is pinned twice, in `flake.nix`'s `wolfGhosttyVtPin` and in `bazel/ghostty-vt/extensions.bzl`. `the_linked_library_is_the_pinned_release` in `crates/wolf-vt/tests/binding.rs` asserts `"1.0.0"` from the linked library on both workers, so a version bump on one side alone fails a gate. `bazel/ghostty-vt/README.md` also lists the upgrade steps, including the licence rows.
- **`regina on linux` let `coder-1` build the flake derivation early.** Its `cargo test -p wolf-vt` there built `wolfGhosttyVt` with `zig_0_17` and ran the six binding tests before the gate. Its narrow `clippy --locked` run also proved the hand-written `Cargo.lock` stanza, with no `cargo` on the macOS worker.

## What did not go well

- **A guard deep in a 38,027-line test file failed the Linux gate, and the round trip cost $2.29.** Plan 1 §3 added `export WOLF_GHOSTTY_VT_DIR` to `linuxShell.shellHook` but did not classify it. The only test that checks `shellHook` exports sits near line 36,300 of `crates/wolf-gnome/tests/smoke_headless.rs`. `implementation-1` passed on macOS and failed on Linux in that one test, which added `architect-2` ($1.43), `test-writer-2` ($0.34), `coder-2` ($0.52) and a second run of both implementation gates, about 15 minutes.
- **Nothing on the `flake.nix` side points at that guard.** The `shellHook` comments in `flake.nix` and `notes/flake.nix.md` never mention the scrub lists. The one mention is half a sentence in the "Fourteen compositor-free guards" bullet of `crates/wolf-gnome/tests/README.md`, a file of over 90,000 bytes. `architect-1` read that README for the `about_notices.rs` entry and still missed it.
- **`coder-1` skipped the whole Linux gate as too slow, and it was not.** Its report says the smokes "would likely exceed the 10-minute limit", echoing its definition's warning that `./gates.sh` "can outlast the limit while `target/` is cold". But `target/` was warm from its own cargo runs, both gates finished about five minutes after it did, and the `smoke_headless` binary took 64.82 s. The narrow commands its definition prefers cannot reach a guard that nothing links to the file being changed.
- **The upstream source was downloaded four times.** `architect-1`, `test-writer-1` and `coder-1` (twice) each fetched the release tarball with `curl` to read its headers, and `reviewer-1` found it in Bazel's output base. The `ffi.rs` entry of `crates/wolf-vt/src/README.md` requires each new declaration to be checked against "the pinned release tarball" without saying where it is, and g01 will need it again. The same thing happened with crate sources in [open-items-13](open-items-13.md), [round-3-9](round-3-9.md), [round-3-10](round-3-10.md) and [retro-fixes-2](retro-fixes-2.md).
- **Plan 1 named two build details that did not hold on the worker.** Zig 0.17's `zig build` has no `--global-cache-dir`, and the library's `libsystem_override.sh` calls bare `mktemp -d`, which the Seatbelt denies. `coder-1` fixed both within its own run, plan 2 accepted the fixes, and `bazel/ghostty-vt/README.md` records them, so they cost no round trip.
- **A minor defect landed early.** Review 1 §5: the `crates/wolf-core/src/licenses.rs` module doc, the `LIBRARY_LICENSES` doc comment and the `licenses.rs` entry of `crates/wolf-core/src/README.md` say the libraries are linked into Wolf's binaries. At this commit only `wolf-vt`'s test binary links them, so the sentences hold only once g01 adds the dependency.

## Recommendations

1. **Point `linuxShell.shellHook` at its guard.** In `flake.nix`, add a two-line comment above the `shellHook` exports saying that every export must appear in one of the scrub lists of `crates/wolf-gnome/tests/smoke_headless.rs`, linking a `notes/flake.nix.md` heading that names `PACKAGED_SCRUB_ALWAYS` and the guard. Plan 1 would then have classified `WOLF_GHOSTTY_VT_DIR` itself, and this task's $2.29 round trip and second gate run would not have happened.
2. **Move the two `flake.nix` guards into a test binary of their own.** Move `every_shellhook_export_is_scrubbed_or_deliberately_kept`, its sibling vendored-tree guard and the four scrub lists into a module or file the packaged smokes import, with its own `cargo test` target, such as `crates/wolf-gnome/tests/flake_exports.rs`. A coder that edits `flake.nix` can then run it alone in seconds through `regina on linux`, the narrow kind of command `coder-1` did run. This is one case of recommendation 5 of [round-3-11](round-3-11.md), to split `smoke_headless.rs`, which came up again here.
3. **Say where the pinned libghostty-vt headers are.** In the `ffi.rs` entry of `crates/wolf-vt/src/README.md`, or in `bazel/ghostty-vt/README.md`, add one line saying that after a macOS build the release tarball is `$(bazel info output_base)/external/+ghostty_vt+ghostty_vt_src/file/libghostty-vt-1.0.0.tar.gz`. Four invocations here downloaded it, and g01 will add declarations to check against it. This is recommendation 4 of [open-items-13](open-items-13.md) for crate sources, come up again.
4. **Gate `wolf-vt`'s Bazel graph until g01 makes wolf-core depend on it.** In `gates.sh`'s `core_deps_bazel`, query `//crates/wolf-vt:wolf_vt` as well as `//crates/wolf-core:wolf_core`, since here only a check plan 1 wrote out by hand caught the `objc` dependency, which the gate would have let land.
