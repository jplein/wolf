# Retrospective: one baseline of space below every h3 to h6 heading

Last verified at commit `9ae6a97ffcbed54548644676e59e10c51c46f740`.

The task gave h3 to h6 `margin-bottom: 24px` in `crates/wolf-core/src/markdown/base.css`, rewrote "Baseline grid" in `specs/markdown-stylesheet.md`, and added T1 and T2 to `markdown_render.rs`. It also extended the cage smoke `preview_inline_code_keeps_the_baseline_grid_under_cage` with an h3, an h4 and an h6. Its commits are `9c4a88e` (code and tests), `53f2f98` (documentation) and `9ae6a97` (review 1's fix). It took four plans, two reviews and 16 invocations costing $20.61, of which three round trips cost $9.17.

## What went well

- **The declared-value helpers made T1 and T2 cheap.** `rule_decls`, `declared_margin_edge`, `winning_margin` and `rendered_stylesheet` in `markdown_render.rs` let `test-writer-1` write both tests without new machinery. M1a to M1e and M2a each went red as plan 1 §4 predicted, in `coder-1`'s first falsifier batch.
- **The smoke's chip landmark and run helpers carried the layout proof.** The existing flat `#2b2b2b` chip, `BlockRun` and `majority_colour_runs` gave `test-writer-1` the pattern for `exact_colour_runs` and the two column bands. All of G1a to G1g went red at the assertion plan 1 §4 named, and review 1 §4 found no falsifier missing.
- **An existing readings-print convention was there to copy.** Plan 2 added two `{SMOKE} readings:` lines in the form `symbols.rs`, `titlebar.rs` and `terminal_colours.rs` already use. With it, `coder-2` and `coder-3` checked every documented number from one green `--nocapture` run, where `coder-1` had needed a falsifier's kept capture and a throwaway PNG reader. Keep that convention, and extend it (recommendation 2).
- **Both gates passed on both workers at every run.** `implementation-1`, `implementation-2`, `documentation-1` and `documentation-2` all exited 0, so no round trip came from a gate.

## What did not go well

- **Two of the three round trips changed only numbers in a test's docs.** `coder-1` rejected `preview_render.rs` because its measured readings were false on this tree: p0's chip at 163 rather than 162, and G1f's red at 1 rather than 4. That added `architect-2` ($1.48), `test-writer-2` ($1.08) and `coder-2` ($0.74). `coder-2` then rejected again on 748 rather than 743 and 40 rather than 38, adding `architect-3` ($0.86), `test-writer-3` ($0.30) and `coder-3` ($0.50); no assertion, constant or outcome changed in either round.
- **The wrong readings were in the base, and plan 1 told the writer to keep them.** The base doc of `CODEGRID_CHIP_BAND_PX` and `CODEGRID_MIN_CHIP_PX` stated 163..182, 748 and a red of 1 as measured, for p0, which this task's fixture did not move. Plan 1 §3 said those "stay as measured", and `test-writer-1`, whose system prompt says "Run no test", could not check them. Plan 2 withdrew the rule, but kept 748 and 40 unchecked, which caused the second rejection.
- **Nothing re-checks a measured reading, and the versions it names are stale.** The smoke's docs name GTK 4.22.4, libadwaita 1.9.0, WebKitGTK 2.52.4 and `cage` 0.3.0, while `coder-2` found 1.9.3, 2.54.1 and 0.3.1 in the dev shell. Plan 3 corrected only the codegrid sentence, so at `HEAD` the module header and Row A/B lines of `preview_render.rs`, seven lines of `preview.rs`, `specs/markdown-stylesheet.md` line 45 and `pane_view.rs` still cite readings at 2.52.4. `notes/crates/wolf-gnome/Cargo.toml.md` says the flake pins webkitgtk 2.52.4, which review 1 also flagged.
- **The smoke gave no readings on a pass, so a check cost a falsifier.** `coder-1` kept G1e's capture, wrote a pure-Python PNG reader, base64-encoded it and ran it in the Linux snapshot (commands 20 and 23) to read the green geometry. Plan 2's readings print removed that cost for this smoke only; the other measured smokes in `preview.rs` and `preview_render.rs` still print nothing on a pass.
- **The third round trip, F1, came from one message template over three levels.** `test-writer-1` wrote the 7b message with the example "at 48 rather than 24" for every heading, which is false for h3, whose spec top margin is 48. `coder-1` quoted the false text in G1d's red without flagging it, and review 1 F1 caught it, adding `architect-4` ($0.82), `test-writer-4` ($0.30), `coder-4` ($0.72), `technical-writer-2` ($0.25) and `reviewer-2` ($2.12). Nothing in the repository invited it, so this report recommends nothing for it.
- **A spec sentence the task did not open is narrower than the smoke shows.** `specs/markdown-stylesheet.md` line 47 says chip pixels occupy a 20-row band in each 24px line box, while the smoke measured heading chips of 24, 23 and 18 rows, the h3's running one row past its box. Plan 4 left it, since the task did not open "Inline code leading".

## Recommendations

1. **Drop the exact measured pixel counts from the codegrid smoke's docs.** This is recommendation 4 of [regina-land-other-pane](regina-land-other-pane.md), come up again at a cost of $4.96. In `crates/wolf-gnome/tests/smoke_headless/preview_render.rs`, keep each floor and the argument for it ("well below a green reading, well above the unpainted stray count"), and let the readings print give the numbers. Both of `coder-1`'s and `coder-2`'s rejections were about such numbers, and with none in the docs neither would have happened.
2. **Give the other measured smokes a readings print.** In `preview.rs` and the rest of `preview_render.rs`, add an `eprintln!` of the values each doc table calls measured, before the assertions, as plan 2 did for the codegrid smoke. `coder-1` spent two Linux commands and a throwaway PNG reader to read geometry a print would have shown, and the next task to touch one of these smokes will need the same readings.
3. **Let the test writer run a smoke against the base to confirm a reading it keeps.** This extends recommendation 2 of [tabs-and-preview-1](tabs-and-preview-1.md). In `.claude/skills/regina/agents/test-writer.md`, say that "Run no test" allows one `regina on linux` run of an existing smoke with `--nocapture` on the unchanged tree, to confirm a reading the plan carries forward. p0's readings were the base's, so `test-writer-1` could have found 162, 4 and 743 before `coder-1` did.
4. **Re-take or drop the readings pinned to WebKitGTK 2.52.4.** Open a task to correct `notes/crates/wolf-gnome/Cargo.toml.md`'s claim about the flake's webkitgtk, and to re-measure or cut the 2.52.4 readings in `preview.rs`, `preview_render.rs`, `pane_view.rs` and line 45 of `specs/markdown-stylesheet.md`. Plan 3 left them because no run in this task re-measured them, so they record a dev shell that no longer exists.
5. **Scope the spec's 20-row chip sentence to body text.** In the same or another task that opens "Inline code leading" in `specs/markdown-stylesheet.md`, say that the 20-row band is for paragraph lines and that a heading's chip follows the heading's font size. Review 1's notes and plan 4 both deferred it for want of a task that opens the section.
