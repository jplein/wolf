# Task 4 of pane-ui: add the Zoom Pane command and the macOS pane zoom

Last verified at commit `17d667d4d41a93a6b4b8d331bc9a5f1fa3defe72`.

The task added `Command::ZoomPane` (30, `:WolfZoomPane`) as a native-only command, classified `Deferred` on GNOME, and the macOS zoom: the pure seam `PaneZoom.swift` and the `zoomedPane` state in `PaneContainerView.swift`. It added `PaneZoomTests.swift` (K1 to K10) and `ZoomPaneTests.swift` (Z1 to Z10), and moved the registry mirrors to 30. The commits are `160c617` (code and tests) and `17d667d` (documentation).

Five invocations cost about $25.12 and 68 minutes: `architect-1` $8.85, `test-writer-1` $3.29, `coder-1` $5.88, `technical-writer-1` $3.11 and `reviewer-1` $4.00. There was no round trip. Both gates passed on both workers on their first run, and review 1 approved with minor notes.

## What went well

- **One function stood between the layout and every reader of it.** Every caller that draws, hit-tests, scrolls or sizes a pane in `PaneContainerView.swift` already read `paneRects()`. So plan 1 §3 moved its body to `layoutRects()` and wrapped it in `PaneZoom.visibleRects`, and hiding the other panes and keeping their grid sizes (D2) came from that one change. Review 1 §2 checked the painting and sizing paths against it and found nothing missed.
- **The `WolfKeyMap` seam pattern made the rules cheap to test and to falsify.** With `OtherPaneSeam.swift` and `DrawerLayout.swift` as models, every zoom rule went into one pure enum, and the container holds a single `zoomedPane`. The eighteen seam falsifiers, C30 to C47, ran under the headless `WolfKeyMapTests` target in one batch of `coder-1`'s falsifier script.
- **The live-core fixtures covered a three-pane layout with the drawer open.** `test-writer-1` built Z1 to Z10 on `TerminalViewFixture`, `PreviewViewFixture` and `OffscreenRenderer` with no new infrastructure. The ten tests passed at `coder-1`'s first filtered run, and every Z falsifier gave an assertion red, not a build or `premise:` failure.
- **`specs/command-lifecycle.md` §8(a) made a native-only command a recipe.** Plan 1 §3 listed the registry edits from §8's shared steps, and `coder-1` made them in four scripted replaces, following the split commands' diff, `ac34e5f`. Running `regina on linux` let `coder-1` take C23 and C24 on the Linux worker before the gate, so no gate round was spent on them.

## What did not go well

- **The registry mirrors were edited by hand again, about a dozen sites.** In `command.rs` they were the variant doc's list, `EXPECTED_COMMAND_COUNT`, `SPLIT_VERTICAL_INDEX`'s doc and a renamed last-row test, plus two range comments in `crates/wolf-ffi/src/lib.rs`. The rest were the header list and `init?(ffi:)` doc in `CommandSeam.swift`, the probe in `CommandSeamTests.swift`, the doc, range and guard in `crates/wolf-ffi/tests/commands.rs`, and `STATIC_COMMAND_COUNT`. `architect-1` spent about twelve of its ninety turns finding them for plan 1 §3.
- **`PaneContainerView.swift` was read in chunks by three agents.** It grew from 3,210 to 3,320 lines. `architect-1` read about 1,400 lines of it in eight ranges, `coder-1` read about the same in five ranges, and `test-writer-1` read four more ranges to find the drawer edge, the split path and `paneAreaHeight`.
- **The `PaneContainerView.swift` entry was at its 250-word budget, so documenting one bullet cost cuts elsewhere.** `technical-writer-1` made four scripted passes over `crates/wolf-macos/Sources/WolfMacOS/README.md` to shorten other bullets. It dropped "a top-edge drag sets the view's share" from the drawer bullet, which the linked decisions section still states.
- **The `WolfKeyMap` README crossed the size warning, as predicted.** It went from 49,992 to 51,251 bytes with the `PaneZoom.swift` entry, and plan 1 §5 told the technical writer to accept the `big-file` warning rather than trim unrelated entries.
- **doc-lint's anchor check at the implementation gate shaped the files again.** Plan 1 D11 forbade any code comment linking `notes/wolf-macos-decisions.md#zoom-pane`, because the heading is written only after the implementation gate. For the same reason, `test-writer-1` opened both new Swift test files with a plain header, not the `See …/README.md#<anchor>` line that 44 of the 55 `WolfKeyMapTests` files carry. No later agent may write a test file, so the two stay without it. [round-3-2](round-3-2.md) records the same ordering, planned around in at least four earlier tasks.
- **A test helper was copied rather than shared.** Plan 1 §4 asked for a press, drag and release helper "modelled on" `TerminalDrawerResizeTests`' `mouseEvent`, and `ZoomPaneTests.swift` now holds a private copy of it beside the original. `TerminalViewFixture.swift` already holds the shared `wake` helpers both files use.
- **Review 1 left three open points for the GNOME zoom task.** First, a zoom outlives every hidden pane after `<C-w>o`, and Toggle Terminal is then refused with no visible cue. Second, no test covers the unzoom in `rebind(tabpageHandle:)`. Third, the spec's "Three things unzoom a view" omits the race-only `DrawerOpen` unzoom, which `technical-writer-1` also raised.

## Recommendations

1. **Derive the registry mirrors from `COMMAND_SPECS`, and collapse the per-command tests into one table test.** These are recommendations 1 and 2 of [pane-ui-3](pane-ui-3.md), come up again. This task renamed `split_vertical_is_the_last_row` to `split_vertical_is_at_index_29` and added `zoom_pane_is_the_last_row`, which is the churn recommendation 2 predicted. Each new command in this request repeats it, and the derived form would have taken about twelve of `architect-1`'s turns and a dozen edits out of this task.
2. **Split the drawer and zoom state out of `PaneContainerView.swift` and its entry.** This is recommendation 1 of [pane-ui-1](pane-ui-1.md) and recommendation 6 of [pane-ui-3](pane-ui-3.md), come up again. `zoomedPane`, `toggleZoom()`, `toggleTerminal()`, `layoutRects()` and the hidden-view handling would sit in a `PaneContainerView+Zoom.swift` extension with its own README entry. Each of three agents would then have read one short file instead of 1,400 lines, and the technical writer would not have trimmed the drawer bullet.
3. **Make room in the `WolfKeyMap` README.** This is recommendation 2 of [pane-ui-1](pane-ui-1.md), which this task fulfilled by crossing the 50,000-byte warning. Splitting it by topic, the pane seams beside the key seams, would clear the warning before the next seam lands.
4. **Let a code or test comment link an anchor the plan names before the technical writer writes it.** Run doc-lint's `doc-anchor` rule only under the documentation gate, so `gates.sh`'s implementation run checks paths and the documentation run checks anchors. Plan 1 D11 and `test-writer-1`'s plain headers would have been unneeded, and the two new test files would carry the `README.md#<anchor>` line their siblings do. This is the ordering [round-3-2](round-3-2.md) recorded, come up again with no recommendation made for it yet.
5. **Move `mouseEvent` into `TerminalViewFixture.swift`.** Both `TerminalDrawerResizeTests.swift` and `ZoomPaneTests.swift` drive divider drags. One shared helper would stop the next drag test from making a third copy.
