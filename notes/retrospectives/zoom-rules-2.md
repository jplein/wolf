# Retrospective: Zoom Pane's three new rules on GNOME

Last verified at commit `9cf3162b7c41e562ecccf04f31f3fd16bbc048c2`.

The task brought GNOME onto the rules [zoom-rules-1](zoom-rules-1.md) set for core and macOS: a focus move unzooms and then moves, Toggle Terminal unzooms and then toggles, and `state.json`'s zoomed leaf is saved and re-zoomed on relaunch. Its commits are `82d73f1`, `072016e`, `524b8d7` and `9cf3162`; the range from the base also holds zoom-rules-1's `e9cf36f`, `f2db28d` and `d643727`. Every gate run passed on both workers on its first try.

It took two round trips: a discrepancy on `architect-1`'s commit message, and review 1's rejection of two rows of the smoke's leg table. The eleven invocations cost about $25.13. `architect-1` was $6.54 (74 turns, 18 minutes), `test-writer-1` $4.64, `reviewer-1` $3.91, `coder-1` $3.74 (88 turns, 34 minutes) and `technical-writer-1` $2.23.

## What went well

- **Core's side of the change left GNOME's save path one argument wide.** The serde-defaulted `zoomed` field and `wolf_rebuild_layout` ending on the zoomed leaf meant plan 2 D3 could add only a `zoomed` argument to `pane_layout::encode`. `persistence.rs` and `tab_view.rs` did not change, and `state_seam.rs` gained only `zoomed: false` in its test literals. Review 1 confirmed D3 by grep in one pass.
- **The pure `pane_zoom.rs` seam and the existing `drawer::focus_target` carried the rule cases.** K11 to K13 in `crates/wolf-gnome/tests/pane_zoom.rs` compose the real `focus_origin`, `drawer::focus_target` and `zoomed_after` over a real `PaneTree`, so the focus rule's cases run in the fast tier. Review 1 found K13's third case separates `zoomed.or(from)` from `from.or(zoomed)`, which no live leg could.
- **The falsifier record made the revision cheap.** `coder-1` drove all 26 falsifiers from one script on Linux, each with one edit, one `--exact` test and matching `sha256` before and after. Plan 3 re-assigned S1 to leg O without a re-run, and `coder-2` cost $0.30 for no change at all.
- **No new test file meant nothing to wire.** Plan 2 kept every new case in `tests/pane_zoom.rs` and `smoke_headless/zoom_pane.rs`, which Cargo already runs, and `crates/wolf-gnome` has no Bazel target. Review 1 checked the wiring in three sentences.
- **An earlier recommendation was carried out.** Plan 1 dropped "case for case" from the `//!` of `tests/pane_zoom.rs`, recommendation 4 of [zoom-rules-1](zoom-rules-1.md), and gave P3 its own meaning in plan 2.

## What did not go well

- **`architect-1`'s commit subject was one character over.** Its first line was 70 characters, where its definition allows 60 and the mechanics 69. `architect-2` re-issued the plan for $0.97 (15 turns, 2.4 minutes) and also corrected P3's description. Nothing in the repository invited this, so it has no recommendation.
- **Review 1 rejected two rows of the smoke's leg table, a $3.09 round.** Plan 2 §4 predicted S1 red at leg S and placed N1's guard after the zoom event, and the doc of `zoom_pane_hides_restores_and_unzooms_under_cage` copied both into its "predicted red" column. `coder-1` measured S1 red at leg O and moved N1's edit to the top of `PaneInner::toggle_terminal`, both correctly, but only a test writer may edit that doc. So `architect-3`, `test-writer-2`, `coder-2`, `technical-writer-2` and `reviewer-2` followed, and both gates ran again on both workers.
- **The repository already says reds are measured, not predicted.** `crates/wolf-gnome/tests/README.md` § Smoke conventions says the leg table names the edit and the coder records which leg went red. The tables in `zoom_pane.rs` and `drawer_divider.rs` still carry a "predicted red" column, so the test writer fills it from the plan and it goes stale whenever the measurement differs. This is recommendation 2 of [ghostty-5](ghostty-5.md) and of [round-3-11](round-3-11.md), come up again, carried out in the README but not in the tables.
- **The coder's request reached nobody.** `coder-1` returned `passed` and asked, in its 52 KB report, for the S1 row to be corrected and for a tests README gap. Its definition says a test it believes is wrong is a `rejected`, but a stale doc row over a rule that O still catches read as a remark. `technical-writer-1` read the report but followed plan 2 §5 alone, and its definition still names no coder report, which is recommendation 1 of [round-3-10](round-3-10.md) come up again.
- **The new focus rule masks every unzoom that moves Neovim's current window.** `update_active_pane` applies `FocusMove` on any change of current window, so the `PanesChanged` unzoom in `detect_closes` and the `Split` unzoom in `apply_split` cannot be falsified live. Plan 2 D8 saw this for leg C and not for leg S, and `crates/wolf-gnome/tests/README.md` now states it in two bullets, one per trigger.
- **Plan 2 assumed Neovim's window order follows the screen.** Its W leg said `<C-w>w` from A reaches B. `test-writer-1` read `do_split` in `runtime/nvim/init.lua`, saw neither `splitright` nor `splitbelow` set, worked out that it reaches the drawer, and rewrote W to measure `g:zwnext`. It cost no round trip, and nothing documents that order.
- **The big GNOME files were read in ranges again.** `pane_view.rs` is 5,715 lines, and `architect-1` read it in about a dozen `sed` ranges. The `pane_view.rs` entry of `crates/wolf-gnome/src/README.md` is at 250 of 250 words, and `pane_layout.rs` at 249 after `technical-writer-1` cut older bullets to fit. This is recommendation 5 of [pane-ui-5](pane-ui-5.md), come up again.

## Recommendations

1. **Drop the "predicted red" column from the smoke leg tables.** In `crates/wolf-gnome/tests/smoke_headless/zoom_pane.rs` (both tables) and `drawer_divider.rs`, keep the ID, the assertion and the falsifying edit, and leave the red to the coder's report, as `crates/wolf-gnome/tests/README.md` § Smoke conventions already says. Review 1's two findings were both a stale predicted cell, so this would have saved the $3.09 round. It finishes recommendation 2 of [ghostty-5](ghostty-5.md).
2. **Have the technical writer act on the coder's report.** This is recommendation 1 of [round-3-10](round-3-10.md), come up again. In `.claude/skills/regina/agents/technical-writer.md`, under `reason: zero`, name the latest `reports/coder-<N>.md` and its documents-made-wrong section as input beside the plan. `technical-writer-1` would have added the split gap, half of review 1's finding 1.
3. **State the masking rule once, for the next unzoom trigger.** In `crates/wolf-gnome/tests/README.md` § What is still unproven, merge "Closing the zoomed pane" and "A split while zoomed" into one bullet: any unzoom whose action moves Neovim's current window is masked live by the focus-move unzoom, and only an action that keeps the current window, like O's, can falsify it. Plan 2 would then have checked leg S as it checked leg C.
4. **Say how Neovim orders this app's windows.** In `crates/wolf-gnome/tests/README.md` § Smoke conventions, add that `do_split` uses Neovim's default split sides, so `winnr` order is not screen order and a smoke measures `<C-w>w`'s target. `test-writer-1` had to derive this from `init.lua` to correct plan 2's W leg.
5. **Split `pane_view.rs` and its README entry.** This is recommendation 5 of [pane-ui-5](pane-ui-5.md), come up again. A zoom submodule holding `apply_focus`'s zoom arm, `toggle_terminal`, `apply_layout_rebuild`'s `Restore` and `readiness` would have been one file to read and one entry with room for this task's change.
