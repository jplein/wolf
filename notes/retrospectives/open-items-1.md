# Retrospective: poll instead of reading once after a flush in `redraw_grid.rs`

Last verified at commit `e373c6bd39c8f52c41e3d0133e7f156b72d5c283`.

`scroll_emits_viewport` in `crates/wolf-core/tests/redraw_grid.rs` read `viewport.topline` once after one flush, and failed once under a cold parallel `bazel test //...`. Plan 1 made every test in the file poll until the awaited change lands, in commit `e373c6b`. It ran once through the flow with no rework: `architect-1`, `test-writer-1`, `coder-1`, both gates at exit 0 on both workers, `technical-writer-1` with no edit, and `reviewer-1` approving. The five invocations cost about $4.77 in all, with the architect ($1.52, 19 turns) and the reviewer ($1.43, 21 turns) the largest.

## What went well

- The polling convention was already in the crate, so `architect-1` planned against it instead of designing one. `redraw_multigrid.rs`'s `poll_until` gave the shape (`FLUSH_TIMEOUT` deadline, 25 ms interval, drain each pass), and the doc comment of `autoread.rs`'s `wait_for_row0_contains` gave the rule that the snapshot guard drops before the drain and the sleep. Plan 1 cites both, and `review-1` checks the new helper against both.
- `crates/wolf-core/tests/README.md` already records, in several sibling entries, that a single `wait_for_flush` can return on an earlier flush. That gave the architect the diagnosis for a failure seen once, and `review-1` used the same entries to confirm it.
- The test was already the `crate_root` of `//crates/wolf-core:redraw_grid`, so no wiring was needed. One target per test file let `coder-1` run the falsifier, the five `--nocache_test_results` runs and both gates inside a single 337-second invocation.
- `regina on linux` covered the tool the macOS worker lacks. `test-writer-1` ran `cargo fmt --check` and `cargo clippy -p wolf-core --test redraw_grid` on the Linux worker, and the gate's Linux run passed `fmt` and `clippy` first time.

## What did not go well

No step was redone: no rejection, no failed gate, no discrepancy. Three things cost effort or left a hazard.

- **The shared open helper's contract misleads, and the fix stayed local.** `common::start_core_with_temp_md_sized` waits for one `wait_for_flush` after `InputEvent::Open`, and its comment says that flush comes "once the buffer is shown". Plan 1 found that the flush can be a late startup flush, with the `:edit` redraw still pending. The task scoped the fix to one file, so plan 1 added a local `fixture_row0` poll, and the helper that 14 test files call is unchanged.
- **One more copy of `poll_until`.** Before this task, 16 files under `crates/wolf-core/tests/` each defined their own `poll_until`, and 30 their own `POLL_INTERVAL`. `redraw_grid.rs` adds a 17th and 31st, the first that returns the value it observed. `review-1` noted the duplication under its minor notes.
- **The task text and plan 1 asked two agents for steps their roles forbid.** The instructions told the coder to falsify by editing the test's input, which the coder may not write, so `coder-1` zeroed `topline` in `redraw.rs`'s `win_viewport` instead. Plan 1's step 1 told the test writer to run the tests, which its definition forbids ("Run no test"), so `test-writer-1` skipped it. Both agents reported the deviation, and neither cost a round trip.
- **`bazel run //tools/lint:rustfmt.fix` rewrites the doc-lint fixtures.** `test-writer-1` ran it to format the test, since the macOS worker has no `rustfmt`. It reformatted `blocks.rs`, `lexing.rs` and `limits.rs` under `tools/doc-lint/tests/fixtures/lang/rust/`, and reported `E0753` parse errors on `doc_comments.rs`. The agent restored the three files from `HEAD` before handing off, about five commands. `tools/lint/README.md` documents `:rustfmt.fix` without this hazard.
- `./gates.sh` ran four times for one test file: `coder-1` ran it on both workers, as its definition requires, then the implementation gate ran it on both again. On macOS the gate's test step was all cache hits (`Executed 0 out of 114 tests`), so its `redraw_grid` result comes from the coder's runs. This is flow design, not a repository defect, and is recorded here only for whoever tunes the flow.

## Recommendations

1. **Make the open helper wait for the opened file.** In `crates/wolf-core/tests/common/mod.rs`, have `start_core_with_temp_md_sized` poll until the opened buffer is drawn, not return on the next flush, and correct its comment. Plan 1 traced the race to this helper, and the local `fixture_row0` exists only because the helper returns early. All 14 callers would inherit the fix, and the next flaky test of this kind would not need its own diagnosis.
2. **Promote one `poll_until` into `tests/common/mod.rs`.** The value-returning form `redraw_grid.rs` added covers the predicate forms too (return `()` or the snapshot field). Moving it, with one `POLL_INTERVAL`, would replace 17 local copies. The repeated "poll while draining wakes" gotchas in `crates/wolf-core/tests/README.md` could then become one line in the shared-helper section. `review-1` suggested the same move for three of the copies.
3. **State the role limits where falsifiers and the order are planned.** In `.claude/skills/regina/agents/architect.md`, item 4 could say that a falsifying edit is to code, because the coder cannot write test files. Item 6 could say that the test writer runs no tests. Plan 1 copied both conflicts from the task text, and `coder-1` and `test-writer-1` each had to notice and work around one.
4. **Keep `:rustfmt.fix` away from the doc-lint fixtures.** Exclude `tools/doc-lint/tests/fixtures/` from the rules_rust formatter (for example with `rustfmt.toml`'s `ignore`, or by tagging whatever target pulls the fixtures in), or failing that add the hazard to `:rustfmt.fix`'s row in `tools/lint/README.md`. `test-writer-1` is the evidence. On the macOS worker this target is the only `rustfmt` there is, so every test writer formatting Rust there hits it.
