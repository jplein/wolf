# Make the macOS titlebar follow the theme

Last verified at commit `6fdd8f77a7690ee5c7f472eba46e9eafce954dfb`.

On macOS the titlebar takes a set `WolfTitlebar` background, otherwise `Normal`'s background, read from grid 1 the way the statusbar strip reads it. Its title follows Wolf's resolved appearance, because every window inherits the `NSApp.appearance` that `AppDelegate` forces. The task's commits are `e147e1b` (code, tests, spec, and two Linux test fixes) and `6fdd8f7` (documentation). The range from the base also holds `ce93069`, `752898f` and `cec36b0`, which belong to [titlebar-colours-1](titlebar-colours-1.md).

The titlebar work itself had no rework: one plan, one test writer, one coder, a green macOS gate on every run, and a review that approved. All the rework came from two flakes on the Linux worker, in tests this branch did not reach. They failed implementation gate runs 1, 2 and 3, and added plans 2 to 5. Fifteen invocations cost about $22.20; the ten added by the flakes cost $7.17 and about 31 minutes of agent time, plus three extra gate runs on both workers.

## What went well

- **The macOS test host could build a real `MainWindow`.** `test-writer-1` hosted the container in a real window over the staged Lighthouse, copying the `StatusbarStripColourTests` pattern and adding `OffscreenRenderer.capture(_:)`. So the tests assert on the window's `backgroundColor`, not on a value passed to it. `coder-1` scripted all 15 falsifiers (T1 to C4b) and each went red on the first try, for $1.98.
- **A precedent fixed the colour source.** The task pointed at the statusbar-strip paragraph of `notes/wolf-macos-decisions.md`, and plan 1 reused grid 1's `default_bg()` with no new FFI call. Review 1 §2 measured the titlebar and the grid pixel-identical in both backgrounds.
- **`regina on linux` made a flake measurable.** `coder-3` ran `open_existing_markdown` 11 times on Linux and found 5 failures, for $0.42. That turned plan 3's "re-run the gate" into plan 4's fix.
- **The fixes were local because the helpers and pins existed.** `common::poll_until` already served this race, so plan 4's edit stayed in one test (`test-writer-2`, $0.43). The test's revert table in `recovery.rs` and the `named_constants_match_contract` pin on `BANNER_VISIBLE_SECS` gave plan 5 both the safety argument for moving the capture and the reason not to raise the constant.

## What did not go well

- **The `open_existing_markdown` flake was known and still unfixed.** [round-4-1](round-4-1.md) recommendation 3 asked for exactly the poll that plan 4 made. Here it failed gate run 2, and it cost `architect-3`, `coder-3`, `architect-4`, `test-writer-2` and `coder-4`, $2.90, plus one gate run. Round-4-1 measured it on macOS at about 1 in 11, and plan 3 judged a re-run cheap from that rate, but `coder-3` measured 5 in 11 on Linux.
- **The recovery smoke's banner check was a timing race that the test already expected.** At the base, the assertion message of `nvim_crash_recovers_and_reopens_the_file_under_cage` said "If this flakes rather than failing outright…". The `grim` capture came about 2.4 s of fixed sleeps after a banner that lasts 4 s. It failed gate runs 1 and 3, and cost `architect-2`, `coder-2`, `architect-5`, `test-writer-3` and `coder-5`, $4.27, plus two gate runs. No note or earlier report recorded it, so `architect-2` and `architect-5` each searched `notes/` for it and found nothing.
- **Re-running came first twice, and both flakes were fixed in the end.** Plans 2 and 3 each ordered a no-edit coder and a fresh gate run, with no measurement of how often the test failed. Those two rounds cost $2.30 and two gate runs on both workers. Nothing in the architect's definition says to measure a failure rate before choosing a re-run.
- **Open flakes are still not listed where a planner reads.** `notes/known-flakes.md`, recommended by [fixes-1](fixes-1.md) and again by [fixes-2](fixes-2.md), does not exist. Plan 3 found the `save_open` race only through round-4-1.
- **A stale comment landed.** The doc of `cleared_groups_fall_back_to_all_none` in `crates/wolf-core/tests/theme.rs:178-179` still says the titlebar falls back to the system colour, as review 1 §5 found. Plan 1 §5 and `technical-writer-1` both missed it, since it sits in a test that the task did not open.
- **The planner had to go to the web for AppKit's appearance rules.** `architect-1` ($5.16, 59 turns, 16 minutes) used three web searches and four fetches of Apple's documentation to establish that a window with a `nil` `appearance` inherits `NSApp.appearance`. The new `## The titlebar` section of `notes/wolf-macos-decisions.md` records the result now, so nothing more is needed.

## Recommendations

1. **List open flakes in one note, with a failure rate per platform.** This is recommendation 1 of [fixes-1](fixes-1.md) and 4 of [fixes-2](fixes-2.md), come up a third time. Add `notes/known-flakes.md` and link it from `build.md` § The verification gate. Each entry gives the target, the failing line, the rate measured on each worker, and the report that found it, starting with the `nav_history_live.rs:563` and `browser_preview` entries those reports name. A Linux rate for `save_open` would have sent plan 3 straight to the fix, saving `coder-3` and `architect-4`, $1.23.
2. **Have the architect measure before it orders a re-run.** In `.claude/skills/regina/agents/architect.md`, say that when a gate fails in a test the branch cannot reach, the next plan has the coder run that test about ten times on the failing worker through `regina on linux` before deciding. A rate near zero means re-run, and anything higher means fix in the branch. `coder-3` did this in one invocation and settled it, whereas plans 2 and 3 lost two rounds, $2.30 and two gate runs on both workers, by guessing.
3. **Carry out flake fixes that a report has already named.** Round-4-1 recommendation 3 waited until it cost this task two gate runs. A cleanup round that takes the list in recommendation 1 should fix the entries with a known cause first. `history.rs` in [open-items-14](open-items-14.md) recommendation 1 is next in line.
4. **Correct the `theme.rs` doc comment.** In `crates/wolf-core/tests/theme.rs:178-179`, drop the titlebar half of the sentence or say that macOS falls back to `Normal`'s background. This is review 1 §5's fix, left open.
5. **Make room in the `WolfKeyMap` README before its next entry.** `crates/wolf-macos/Sources/WolfKeyMap/README.md` is 49883 bytes, 117 under the markdown checker's 50000-byte warning (review 1 §5). Trim the longest entries toward the 200-word budget, so the next task that adds a seam does not hit the warning in its documentation gate.
