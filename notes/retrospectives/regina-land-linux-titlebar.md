# Make the GNOME header bar and tab bar follow the theme

Last verified at commit `c6df06d403337e9e5dbcb63b0998cbf2f0e1255b`.

`wolf-gnome`'s `adw::HeaderBar` and `adw::TabBar` now take `WolfTitlebar`'s background, else `Normal`'s, through a per-window CSS provider in `crates/wolf-gnome/src/titlebar_background.rs`, in `:backdrop` too. The task's commits are `6cffc21` (code, tests, spec) and `c6df06d` (documentation). Eight invocations cost about $27.64, of which one round trip, a coder rejection of a test premise, added `architect-2`, `test-writer-2` and `coder-2` for $6.41 and about 25 minutes. Both gates passed on their first run on both workers.

## What went well

- **The flake pins libadwaita, so its stylesheet could be read rather than guessed.** `architect-1` built `nixpkgs#libadwaita.src` from the flake's inputs and read libadwaita 1.9.3's `_header-bar.scss`, `_tab-view.scss`, `adw-tab-bar.ui` and `adw-settings.c`. From these, plan 1 §1 established that one application-priority rule outranks the theme's `:backdrop` swap, which node paints the tab bar, and that `ADW_DEBUG_COLOR_SCHEME` sets the desktop scheme. All three held: `coder-2`'s C10 red showed libadwaita's backdrop colour taking over only when the rule was limited to non-backdrop states.
- **Precedents named in the task kept the design local.** The instructions pointed at `overlay_style.rs` for the provider pattern, `appearance.rs` for the pure-seam split, and `TitlebarBackground.swift` for the rule. Plan 1 needed no core or FFI change, and review 1 found no correctness concern that blocked.
- **An existing smoke supplied the route to `:backdrop`.** `the_save_dialog_writes_a_named_file_under_cage` in `smoke_headless/editor.rs` already opened GTK's in-process save dialog under `cage`, with `SAVE_AS_GDK_DEBUG`. Plan 2 reused it as the last capture of the titlebar smoke, and `test-writer-2` only had to make the constant `pub(crate)` ($1.67, 30 turns).
- **Shared Lighthouse staging went into `lighthouse.rs` instead of a copy.** Plan 1 §3 told the test writer to move `terminal_colours.rs`'s inline staging into a helper if it was needed twice. `stage_init_lua` and `Background::other` now serve both smokes.
- **An earlier report's recommendation was carried out.** [titlebar-colours-2](titlebar-colours-2.md) recommendation 4 asked to correct the doc of `cleared_groups_fall_back_to_all_none` in `crates/wolf-core/tests/theme.rs`. Plan 1 §3 picked it up and `test-writer-1` made the edit.

## What did not go well

- **A false statement in a note became a planned premise, and cost one round trip.** `notes/wolf-gnome-decisions.md` § The readiness file says that under `cage` "the toplevel turns active only after a real key arrives", and the module doc of `crates/wolf-gnome/src/ready_seam.rs` says the same. Plan 1 §1 cited it as "Established" and planned a second launch that would sit in `:backdrop` until a key was typed. `coder-1` measured that window active with no key, on the base code too, and `architect-2` found in `cage`'s `view.c` that `view_map` activates every toplevel it maps.
- **The test writer may not run the test that would have measured that premise.** The test writer's definition asks for every premise about the compositor to be "measured against the real component rather than assumed", and also says "Run no test". `test-writer-1` measured the libadwaita premises on Linux but took the activation premise from the note, and one base-code run of the smoke would have shown it false. The round trip cost `architect-2` ($2.87, 10 min), `test-writer-2` ($1.67, 4 min) and `coder-2` ($1.87, 11 min), who re-ran four reds `coder-1` had taken.
- **The contradiction landed unresolved.** The new `smoke_headless/titlebar.rs` entry in `crates/wolf-gnome/tests/README.md` says `cage` "activates every toplevel it maps … so no launch starts inactive". The decisions note and `ready_seam.rs` still say the reverse. Plan 2 read the note as being about the readiness predicate's `is_active` only, but review 1 §8 points out that GTK 4 derives both `is_active` and `:backdrop` from the same focused state. No step of plan 2 told anyone to rewrite the note.
- **The smoke registered a readback in a guard table it does not need.** The titlebar smoke OCRs nothing, yet `test-writer-1` imported its fixture and readback names into `smoke_headless/fixture_guards.rs` and listed them in `RELAUNCH_FIXTURE_NAMES` "for the generic loop's sake", in three-line entries that repeat each constant's name as a string. `test-writer-2` then had to remove three of the four entries when run 2 went. This is recommendation 7 of [fixes-1](fixes-1.md), which came up again in [fixes-3](fixes-3.md) and [regina-land-toast](regina-land-toast.md).
- **The wolf-gnome READMEs grew again.** The documentation gate warned that `crates/wolf-gnome/tests/README.md` went from 102,054 to 104,832 bytes and `crates/wolf-gnome/src/README.md` from 87,858 to 89,526, both well over the 50,000-byte ceiling. This is the finding of [regina-land-other-pane](regina-land-other-pane.md) and [round-4-4](round-4-4.md), which came up again.
- **Two small defects landed, as review 1 §8 found.** The doc of `AppShell::on_render_wake` in `crates/wolf-gnome/src/shell.rs:1747` still says it settles a re-root and drains commands, leaving out the title, titlebar and nav-button refreshes. In `crates/wolf-gnome/src/window.rs`, the `return None` at line 623 comes after `TitlebarStyle::install` at line 591, so a failed `open_tab` leaves an empty provider on the display.

## Recommendations

1. **Correct the activation claim where it is wrong.** In `notes/wolf-gnome-decisions.md` § The readiness file and the module doc of `crates/wolf-gnome/src/ready_seam.rs`, measure on Linux whether `gtk::Window::is_active` is false before the first key of a first launch, and rewrite whichever of those two and the `titlebar.rs` entry of `crates/wolf-gnome/tests/README.md` is wrong. Plan 1 built a scenario on that sentence, and it cost this task $6.41. Until it is settled, the next planner who reads it can make the same mistake.
2. **Let the test writer run a premise check on the base code.** In `.claude/skills/regina/agents/test-writer.md`, narrow "Run no test" so that a test writer may run a new smoke once on the base code when a precondition rests on how the compositor or a toolkit behaves, and quote the measured values in its report. `coder-1` found this task's false premise in one such run, after the plan and the tests were already written around it.
3. **Exempt OCR-free smokes from `RELAUNCH_FIXTURE_NAMES`, or derive its entries.** This is [fixes-1](fixes-1.md) recommendation 7, which came up again. A smoke that asserts no OCR term should not have to register anything in `crates/wolf-gnome/tests/smoke_headless/fixture_guards.rs`. Where an entry is needed, a `macro_rules!` that writes the name with `stringify!` would make it one line, which would have saved both test writers' edits here.
4. **Fix the two leftovers from review 1 §8.** Rewrite the first sentence of `AppShell::on_render_wake`'s doc in `crates/wolf-gnome/src/shell.rs` to match the module docs' list, and call `titlebar.uninstall()` on the `open_tab` failure path in `window::build`, or install the style after it.
