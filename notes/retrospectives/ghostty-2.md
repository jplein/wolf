# Core terminal sessions over libghostty-vt (g01 of the libghostty-vt series)

Last verified at commit `4aedf4c66fecb672b4750de6afb46b60ba5c5023`.

The task was g01: `wolf-vt` grew to the render, encoder and effect API, and `wolf-core` gained the `terminal` module, the `WolfCore` session API, the `<C-w>` router, colour sync and restart survival, with seven new test targets. It took eight invocations, about $54.01 and 2 hours 13 minutes, and review 1 approved with minor notes. `coder-1` alone was $22.28 (158 turns, 54 minutes) and `architect-1` $10.82 (93 turns, 26 minutes).

The one round trip was `technical-writer-1` rejecting over a `specs/architecture.md` sentence that the code made false. It added `architect-2` ($1.40), `coder-2` ($0.49), `technical-writer-2` ($0.42) and a second implementation gate on both workers, about $2.31 and 9 minutes. Every gate run passed on both workers on its first try.

## What went well

- **The spec's delivery section settled the dispute in one turn of reasoning.** `specs/terminal-panes.md` § Delivery opens exactly one `specs/architecture.md` edit for g01, the `wolf-vt` row, and gives the architecture contract's terminal docs to g04. Plan 2 cites it to rule that the spec stays closed, so `architect-2` needed 25 turns. Keep naming, per task of a series, which spec sentences it may change.
- **A caveat left by g00 let plan 1 foresee a cross-tool coupling.** `tools/lint/README.md` said that `wolf-vt`'s `build.rs` panics on macOS with no `WOLF_GHOSTTY_VT_DIR`. Plan 1's D18 used it to have `coder-1` stage the archive in `clippy_fix.bzl`, `clippy_fix_launcher.sh.tpl` and `fix_all.sh`, which a new `wolf-core` dependency would otherwise have broken with no gate to notice, since the fixers are not gated.
- **Shared session helpers in `crates/wolf-core/tests/common/mod.rs` kept four test files small.** `test-writer-1` put the shell spawning and frame polling there once, and each of `terminal_session`, `terminal_input`, `terminal_lifecycle` and `terminal_rescan` lists it in `srcs`. Review 1 §3 found the wiring complete on its first look.
- **A rejected writer's work survived the round trip.** `technical-writer-1` left eleven documentation files uncommitted, and plan 2 told `coder-2` to leave them alone and `technical-writer-2` to restore two sentences. So the round trip redid nothing, and its two worker invocations together cost $0.91.

## What did not go well

- **The only round trip came from a spec sentence that counts the non-waking notifications.** `specs/architecture.md` § The core↔front-end contract says "Two notifications fire no handler wake at all", naming `wolf_cwd` and `wolf_fs_changed`. Plan 1 §3 specified `wolf_terminal_wiped` with "no wake" and said nothing else in the spec changes. `architect-1`'s transcript shows it read that sentence three times, but a count in a spec does not read as a rule a new notification must answer to.
- **The same list is kept in three documents and the code.** The spec sentence, the first Decisions bullet of the `redraw.rs` entry in `crates/wolf-core/src/README.md`, and the Setup helpers intro of `runtime/nvim/README.md` each name the non-waking notifications, and each event's doc comment in `redraw.rs` says whether it wakes. `technical-writer-1` edited the two READMEs to add the third name, and `technical-writer-2` reverted both. The spec sentence already links the `redraw.rs` entry, so the restatement is the copy that was out of reach.
- **No earlier step could see the spec conflict.** `coder-1`'s "Documents this change makes wrong" lists eleven files but not the spec, because plan 1 had closed it. The technical writer is the first agent whose job is to check every document against the code, so a stale spec sentence costs a coder run and a second implementation gate. Technical writers rejected after the code was done in [round-3-5](round-3-5.md) and [retro-fixes-5](retro-fixes-5.md) too.
- **The pinned libghostty-vt headers were hunted down three times.** `architect-1` (17 commands), `test-writer-1` (6) and `coder-1` (21) each found the release tarball in the shared Bazel repository cache by its sha256, extracted it into their own scratch directory and grepped `include/ghostty/vt/*.h`. `coder-1`'s report calls reading about 15,000 lines of headers by grep "the slowest part". The `ffi.rs` entry of `crates/wolf-vt/src/README.md` still says only "the pinned release tarball".
- **The wake that plan 2 added has no test.** Plan 2 §4 explains that a window close's redraw flush wakes anyway, so the extra wake cannot be told apart without counting wakes against the clock. The change exists only to keep a spec sentence true, and review 1 §3 notes the gap.
- **Two READMEs grew past the size ceiling.** `runtime/nvim/README.md` went from 49,944 to 51,712 bytes, over the 50,000-byte `big-file` warning, and `crates/wolf-core/tests/README.md` from 51,336 to 56,384. The documentation gate printed both as warnings.
- **Review 1 §2 records an orphan placeholder.** When `open_terminal` or `bind_terminal` times out, core drops the session, but the detached `wolf_terminal_bind` RPC still runs once Neovim catches up. The window then carries a `WinBuffer.terminal` id that `terminal_frame` does not know.

## Recommendations

1. **State the wake rule once, in the spec, and link it from the READMEs.** In `crates/wolf-core/src/README.md` (`redraw.rs` entry, first Decisions bullet) and `runtime/nvim/README.md` (Setup helpers intro), replace the list of non-waking notifications with a link to `specs/architecture.md#the-corefront-end-contract`. Both READMEs were edited and reverted in this task, and open-items-6 and round-3-10 recorded the same kind of restatement.
2. **Turn the spec's count into a rule a new notification can be checked against.** When a task opens `specs/architecture.md`, perhaps g04, which owns the contract's terminal docs, rewrite "Two notifications fire no handler wake at all" as the condition for waking: a notification wakes when it changes something a front-end reads, and the list follows as examples. Plan 1 would then have had to answer that condition for `wolf_terminal_wiped`, which would have saved this task's $2.31 round trip.
3. **Have the architect list the spec sentences a change makes wrong.** Item 5 of `.claude/skills/regina/agents/architect.md` asks for every README, decisions note, mirror and `build.md` passage the change makes wrong, but not spec sentences. Add them, with the rule that one the task does not open is designed around or settled before the plan is handed off. This task's rejection was such a sentence, and so were the writer rejections of round-3-5 and retro-fixes-5.
4. **Say where the pinned libghostty-vt headers are.** This is recommendation 3 of [ghostty-1](ghostty-1.md), come up again, with three invocations here instead of four. In `bazel/ghostty-vt/README.md`, add the path of the extracted source tarball under `$(bazel info output_base)/external/` or a one-line command that extracts `include/ghostty/vt` into a scratch directory. g02 and g03 will reach for the same headers.
