# Retrospective: an unfocused terminal pane paints a hollow cursor

Last verified at commit `015ea25deb874bdb2d44e1677e53b5f8b25e27f8`.

The task made a terminal pane that is not the focused pane paint its cursor as a hollow block, on macOS and GNOME, and added the rule to `specs/terminal-panes.md` § The render contract. Plan 1 put the rule in each front-end's painter, behind a pure seam: `TerminalCellStyle.cursorShape(style:focused:)` and `style::cursor_style`. "Focused" includes the key or active window, as in Ghostty.

The thirteen invocations cost about $20.54 and 67 minutes of agent time. The first pass, `architect-1` to `reviewer-1`, cost $13.61. Two round trips added $6.93, both over one line: the `setNeedsDisplay(rowRect(row))` in `TerminalPaneView.focused`'s `didSet`, which no offscreen pixel check can see. Every gate run passed on both workers on its first try.

## What went well

- **Pure seams on both front-ends made most falsifiers one-line edits.** `cursorShape` and `cursor_style` each take the frame's style and a `focused` flag, so K1 and G2 are hand-written tables, and E-ignore, E-hollow, R-ignore and R-hollow replace one expression. `coder-1` landed 14 of plan 1's 15 reds where the plan predicted, each with matching hashes before and after.
- **The live view fixtures carried four new tests with one new property.** `TerminalViewFixture`, `TerminalPaneFixture` and `OffscreenRenderer` gave T1 to T3 a real core, shell and pixels. The only harness change was `OffscreenWindow.reportsKey`, an `isKeyWindow` override, which made the key-window half of the rule testable offscreen. On GNOME, the `paint` helper of `terminal_paint.rs` took a `focused` parameter and G1 reused everything else.
- **An `xcrun swiftc` probe turned `coder-2`'s rejection into a ready fix.** `coder-2` modelled the fixture in a scratch AppKit program and showed which invalidation flag tracks. `architect-3` upheld it in 13 turns ($0.90), `test-writer-3` applied it in 9, and `coder-3` got C4a and C4b red on the first counted run. The same kind of probe settled the dispute in [ghostty-3](ghostty-3.md).
- **Word counts in the plan kept the documentation gate green.** Plan 1 §5 gave each README entry's count from `markdown_check.sh --entry-words`, and both documentation gate runs passed on both workers. [fixes-1](fixes-1.md) records the same.

## What did not go well

- **Plan 1 planned a falsifier it expected to stay green, and the flow rejected the result.** C1c removed the row repaint, and plan 1 §4 said "If C1c leaves T1 green, report it with the output and do not change the test". `coder-1` found it green, because `render()` ends in `cacheDisplay(in:to:)`, which redraws the whole view. The architect's definition says nothing of a doubted falsifier, while the reviewer's makes "an ID with no red" a "Needs revision", so review 1 rejected exactly the outcome the plan had allowed for.
- **Plan 2 then rested T4 on an unmeasured AppKit premise, and hedged instead of measuring.** Review 1 proposed reading `view.needsDisplay` after `render()`, on the belief that `displayIfNeeded()` clears it. Plan 2 §4 adopted that and added "The step 2 and step 4 premises can fail if AppKit leaves … `needsDisplay` set", then handed off. `coder-2` measured that `NSView.needsDisplay` stays true in a window never ordered front, and returned `rejected`.
- **The two round trips cost $6.93 and 16 minutes.** The first loop, from review 1's rejection, came to about $4.43 counting the invocations a single replan needs: `architect-2` $1.16, `test-writer-2` $0.61, `coder-3` $0.56, `technical-writer-2` $0.52 and `reviewer-2` $1.58. The premise added $2.50 more: `coder-2` $1.22, `architect-3` $0.90 and `test-writer-3` $0.38. Both hedges were the same pattern: an architect doubted an AppKit fact, wrote the doubt into the plan, and a later agent measured it.
- **The harness's README led two agents to the wrong flag.** The `OffscreenRenderer.swift` entry says `render()` runs `displayIfNeeded()` because a change "never reaches the bitmap, even with `needsDisplay` set", and the `render()` doc comment says the same. Review 1 and plan 2 read that as `displayIfNeeded()` clearing `needsDisplay`. The measured fact, that the layer's `needsDisplay()` tracks invalidation, landed only in the `TerminalCursorFocusTests.swift` entry and T4's doc comment. Review 2 §8 notes the two entries read as if in tension.
- **A falsifier edit was again named by a string that is not unique.** C1c in plan 1 and C4a in plans 2 and 3 both name `setNeedsDisplay(rowRect(row))`, which occurs three times in `TerminalPaneView.swift`. `coder-1` widened the match by hand, and `coder-3`'s uniqueness check stopped its first C4a attempt, after which a test run on the unedited file was discarded. This is recommendation 6 of [fixes-1](fixes-1.md), come up again.
- **A Linux flake cost a full gate run again, and no file lists flakes.** `coder-1`'s first Linux `./gates.sh` failed in `browser_preview`'s `missing_markdown_target_is_404`, on a 10-second wait at `crates/wolf-core/tests/common/mod.rs:59`. Core was untouched and the test passed alone. `architect-1` ran `ls notes/known-flakes.md` and found nothing, and plan 1 §6 named only `nav_history_live.rs:563`, learned from [fixes-1](fixes-1.md). This is recommendation 1 of [fixes-1](fixes-1.md), come up again.
- **The scratch AppKit probe needs a flag nothing documents.** `coder-2` reports that `xcrun swiftc` under Seatbelt fails until `-module-cache-path` points into `TMPDIR`. Neither `build.md` nor the `WolfMacOSTests` README mentions probes at all. This is recommendation 3 of [round-3-8](round-3-8.md), come up again.
- **The GNOME focus choice and the on-screen macOS repaint stay manual.** No test reaches `draw_pane`'s focused flag or the `tab_focused` redraw, and T4 checks the layer flag, not a repaint on a display. Both are listed in the tests READMEs, and plan 1's M1 and M2 were not run.

## Recommendations

1. **Make the architect measure or redesign a doubted test before handoff.** In the architect's definition, beside the falsifier rule, say: a falsifier the plan expects may stay green, or a premise the plan doubts, is settled before handoff, by a scratch probe or by a different test, because the reviewer rejects any ID with no red. Plan 1's C1c hedge cost the $4.43 first loop and plan 2's premise hedge the $2.50 second one. `coder-2` settled the premise with one scratch program, which `architect-2` could have run.
2. **Put the offscreen invalidation fact in the harness's entry.** In `crates/wolf-macos/Tests/WolfMacOSTests/README.md`, entry `OffscreenRenderer.swift`, add a decision: in this window a layer-backed view's `needsDisplay` stays true, its backing layer's `needsDisplay()` tracks invalidation, and `cacheDisplay(in:to:)` clears it and redraws the whole view, so a pixel check cannot see a missed invalidation. Reword the `render()` doc comment to match. Review 1 and plan 2 looked for this in the harness, and the next test of a repaint will too.
3. **Have plans give each disabling edit as a unique line.** This is recommendation 6 of [fixes-1](fixes-1.md), come up again for C1c and C4a.
4. **List open flakes where planners read.** This is recommendation 1 of [fixes-1](fixes-1.md), come up again. Its `notes/known-flakes.md` should start with `browser_preview`'s `missing_markdown_target_is_404` timeout as well as `nav_history_live.rs:563`; the first cost `coder-1` a full Linux gate run here.
5. **Document the AppKit scratch probe and its flag.** This is recommendation 3 of [round-3-8](round-3-8.md), come up again. Add to it that `xcrun swiftc` needs `-module-cache-path` under `TMPDIR` in the worker, which `coder-2` found by failing first.
