# Retrospective: ship the `xterm-ghostty` terminfo entry and bump Lighthouse to `431d3f6`

Last verified at commit `4195b64a3382252087c4f3baceb80105e613f366`.

The task generated Ghostty's `xterm-ghostty` entry from the pinned libghostty-vt source, installed it in the macOS bundle and the wolf-gnome package, and had core set `TERM` and `TERMINFO` from it. It also bumped the vendored Lighthouse on both platforms, so a pane's 16 ANSI colours come from Lighthouse, and added end-to-end colour tests on both front-ends. It had one round trip: `coder-1` rejected test T15's oracle, `architect-2` upheld the dispute in plan 2, and `test-writer-2` and `coder-2` fixed it and re-took three falsifier reds.

Both gates passed on both workers on their first run, and review 1 approved with three minor notes. The eight invocations cost about $41.62 and 133 minutes. `test-writer-1` ($10.83, 21 minutes), `architect-1` ($9.39, 21 minutes) and `coder-1` ($8.06, 56 minutes) were most of it.

## What went well

- **`regina on linux` let every Linux falsifier be taken and checked.** `coder-1` ran 30 remote commands, and `coder-2` five, each a single-test red or green. Review 1 §4 matched each Linux red, C4a to C15a, to a numbered command log. That made a 15-test, 30-falsifier change reviewable without a re-run.
- **Running the Linux checks before the gate caught formatting early.** `test-writer-1` and `coder-1` each ran `cargo fmt --all -- --check` on Linux, and each found a diff that the macOS worker cannot see. The implementation gate then passed on its first run on both workers. This is the pattern [open-items-10](open-items-10.md) and [open-items-13](open-items-13.md) recorded.
- **`crates/wolf-gnome/tests/vendored_pins.rs` made the two-sided pin bump safe.** The task named it, and the bump of `bazel/lighthouse/extensions.bzl` and `flake.nix`'s `wolfVendoredPins` landed together with no follow-up.
- **The existing decoy test was a usable model.** The instructions pointed at `terminal_session.rs`'s decoy-variable test, and plan 1 built its terminfo tests on it, with a decoy `TERMINFO` that no passing code can produce. Review 1 §3 found no test that would pass with its feature removed.

## What did not go well

- **The one round trip came from a highlight fact that no document holds.** Plan 1 §1 said orlando's `OrlandoCodeBlock` links to `CursorLine`, so T15's code fill would move with `cursorLineBG` to `#333333`. `architect-1` took that from orlando's `doc/orlando.txt`. At `431d3f6`, `colors/lighthouse.lua` line 547 defines `OrlandoCodeBlock` from `slightHighlightBG` itself, which overrides orlando's `default = true` link.
- **The base doc hid the ambiguity.** At `514dec2`, `cursorLineBG` and `slightHighlightBG` were both `#252525`, so the measured literal `PACKAGED_ORLANDO_CODE_FILL` fit either reading. Its doc said only that the fill is a composition of two pins, not which group or key Lighthouse uses. `test-writer-1` pinned the wrong key, and only `coder-1`'s hand run against the package found it.
- **The test that holds the fact is outside both gates.** T15, like T6, T7 and T8, is `#[ignore]`d and runs only through `tools/wolf-package-smoke.sh`, as review 1 §7 notes. The round trip added `architect-2`, `test-writer-2` and `coder-2`: $4.02 and about 20 minutes, most of it `coder-2` re-building the package to take C15a.
- **T2's first red depended on the host's temp path.** `coder-1`'s C2a red was a `wait_for_text` timeout, not T2's assertion, because the temp path wrapped the `|done` marker in the 80-column frame. Plan 2 had T2 classify `$TERMINFO` in the shell instead, and `coder-2` re-took C2a and C2b. Any test that prints a path into the frame and waits for a marker after it has the same weakness.
- **The Lighthouse oracle exists three times.** Plan 1 §4 put one Rust parser of `lighthouse.lua` in `crates/wolf-ffi/tests/common/mod.rs`, a second in `crates/wolf-gnome/tests/smoke_headless/lighthouse.rs` and a Swift one in `TerminalLighthouseColourTests.swift`. It said they live "in test-owned files so the oracle is the test writer's". `crates/wolf-test-support/src/`, which both Rust crates depend on, is code by path, so the test writer could not put a shared one there.
- **A captured frame cannot be read on Linux.** T15 deletes its captures on a pass and prints no fractions. Captures and store paths do not survive between `regina on linux` commands, and the devShell has no `python3` or image tool, as `coder-1/9` showed. `coder-2` measured the 0.9443 fraction with a background copy loop and a base64-encoded PNG decoder run through `nix shell nixpkgs#python3`, all in one remote command.
- **Wiring a test to a target the coder creates broke Bazel queries.** `test-writer-1` added `//bazel/ghostty-vt:ghostty_terminfo` to the `data` of two new `rust_test` targets before it existed. Every query of `//...`, `//tools/lint:rustfmt.fix` included, then failed at analysis, so it formatted through `cargo fmt` on Linux instead. The cost was small, and the plan ordered it so.
- **Both new real-Neovim `rust_test` targets were written out by hand.** `crates/wolf-core/BUILD.bazel` and `crates/wolf-ffi/BUILD.bazel` gained 83 lines, most of them three new targets, each repeating the runfiles, env, tags and deps. This is [round-4-3](round-4-3.md) recommendation 1, come up again.

## Recommendations

1. **Write down where the code-block fill comes from.** In `bazel/lighthouse/README.md` or `bazel/orlando/README.md`, say that the vendored Lighthouse defines `OrlandoCodeBlock` itself, from `slightHighlightBG`, and that orlando's `CursorLine` link applies only when a colorscheme does not. `architect-1` read orlando's own docs and planned the wrong key, which cost the task its only round trip.
2. **Run the `#[ignore]`d package tests in the Linux gate.** In `gates.sh`'s Linux steps, build `nix build .#wolf-gnome` and run `packaged_layout -- --ignored` and the `packaged::` smokes against it, skipping `the_packaged_binary_opens_a_preview_under_cage`, which cannot pass under Podman (plan 2 §8). T15 was wrong from `test-writer-1` until `coder-1` ran it by hand, and a gate would have caught it before the coder started.
3. **Print the measured fractions in T15.** In `crates/wolf-gnome/tests/smoke_headless/packaged.rs`, `eprintln!` the four band fractions on every run, so `--nocapture` gives them without a copied capture. `coder-2` built a copy loop and a PNG decoder for one number, as its report says.
4. **Move the Lighthouse oracle into `wolf-test-support`.** Put the Rust parser in `crates/wolf-test-support/src/` and re-export it from wolf-ffi's `common` module and `smoke_headless`. The ownership rule makes this a coder's file, so a cleanup round, not a test writer, has to do it. The Swift copy stays, and its doc can name the Rust one as the reference.
5. **Give the frame-reading helpers a wrap-proof marker convention.** In `crates/wolf-test-support/src/terminal.rs`, document next to `wait_for_text` that a test must print its marker on a row with no path before it, or give it a helper that does. T2's C2a red was a timeout for that reason, and plan 2 and `coder-2` re-did both of T2's reds.
6. **One macro for real-Neovim `rust_test` targets.** This is [round-4-3](round-4-3.md) recommendation 1, unchanged. This task added three such targets by hand.
