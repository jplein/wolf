# Retrospective: `python3` in both dev shells

Last verified at commit `da40d142af51e65ea6bc447c9633ec4a82812fde`.

The task added the same `pkgs.python3` to `darwinShell` and `linuxShell` in `flake.nix`, and a check of it, `tools/lint/dev_shell_test.sh`, wired as `//tools/lint:dev_shell_test` in `:check` and as the Linux gate step `dev-shell-test`. Its commits are `bd1fe82` (code and test) and `da40d14` (documentation). It carries out the `python3` half of [pane-ui-5](pane-ui-5.md) recommendation 4; `perl`, which that recommendation and [round-3-3](round-3-3.md) recommendation 2 also ask for, was left out at the user's request and is still open.

It ran once through the flow with no rework: no rejection, no failed gate, no discrepancy. Both gates passed on both workers on their first run, and review 1 approved with minor notes. The five invocations cost about $5.66: `architect-1` $2.36 (37 turns, 8.5 minutes), `reviewer-1` $1.26, `technical-writer-1` $0.99, `coder-1` $0.70 (18.2 minutes, most of it the two `./gates.sh` runs) and `test-writer-1` $0.36 (8 turns).

## What went well

- **`CLAUDE.md`'s lint-script wiring rule made the plan complete.** It says a `tools/lint/*_test.sh` needs an `sh_test` and a Linux `run` line in `gates.sh`, so plan 1 named both and who writes each. `test-writer-1` finished in 8 turns, and the gate logs show `//tools/lint:dev_shell_test` passing on macOS and `dev-shell-test 0` on Linux.
- **A sibling held the one Bazel idiom the test needed.** `crates/wolf-core/BUILD.bazel`'s `swap_recovery` target already used `env_inherit` to pass a client variable to a test. `architect-1` found it by grepping for `env_inherit`, and plan 1 reused it for `PATH` rather than adding `--test_env=PATH` to `.bazelrc`, which would have put the shell's `PATH` into every test's cache key.
- **The `flake.nix` mirror already explained the export guard.** `notes/flake.nix.md#shellhook-exports` and `crates/wolf-gnome/tests/flake_exports.rs` let `architect-1` settle that the four variables `pkgs.python3`'s setup hook exports need no classification, because they are not `shellHook` `export` lines. The headings `#darwin-shell` and `#shellhook-exports`, which `flake.nix` already links, gave `technical-writer-1` a home for the new content once a new heading proved impossible.
- **`regina on linux` let one invocation prove both platforms.** `coder-1` recorded both base reds, ran falsifiers C1a and C1b, measured the setup-hook variables on both workers and ran both `./gates.sh` runs itself. Review 1 checked all of it from the command logs without running anything.

## What did not go well

No step was redone across invocations. One conflict inside plan 1 cost a failed lint run inside `technical-writer-1`, and two facts this task surfaced are recorded nowhere the next agent will look.

- **Plan 1 asked for a mirror heading that nothing could link.** It told the coder to link no `notes/` heading from the `flake.nix` comments, and the writer to add `## Python` to `notes/flake.nix.md`. doc-lint's `notes-unlinked` rule fails a mirror heading no comment links, so `technical-writer-1`'s first documentation-gate run failed, and it folded the content into two linked headings. The coder's definition lets the coder write a mirror heading its comment links; the architect's is silent, and [retro-fixes-4](retro-fixes-4.md) praised "link only existing headings" without the converse.
- **The plan's diagnostic for a lost `PATH` was wrong.** Plan 1 said a step-1 red in C1a "would mean the test lost the client `PATH`", and `coder-1`'s report claimed C1a's step-2 red proved `env_inherit` works. Review 1 §4 corrected both: `/usr/bin` is on Bazel's fixed test `PATH` too, so `/usr/bin/python3` resolves either way, and only the green run's `/nix/store` path proves the inheritance. It cost nothing here, and the `:dev_shell_test` bullet in `tools/lint/README.md` does not say which line proves it.
- **Every agent definition carries a `python3` sentence this task made moot.** All six `.claude/skills/regina/agents/*.md` say to run `python3` outside `nix develop`, where `/usr/bin/python3` fails with `tool 'python3' not found`. At the base `architect-1` measured that `/usr/bin/python3` ran inside `nix develop` on this Mac, and the shell now puts the store's 3.14.7 first. Plan 1 and `technical-writer-1` both flagged it as a follow-up, since no agent may write those files.
- **Review 1 left an unmeasured lead that only the run evidence holds.** The setup hook puts 3.14.7's `site-packages`, which holds a `sitecustomize.py` and a `_sysconfigdata__darwin_darwin.py` symlink, on `PYTHONPATH` in the Darwin shell. Anything that runs Apple's `/usr/bin/python3` (3.9) by absolute path inside the shell gets that directory ahead of its own stdlib. Nothing in the repository does so today, and `notes/flake.nix.md`'s `## shellHook exports` paragraph does not mention it.

## Recommendations

1. **Say in the architect's definition who writes a new mirror heading.** In `.claude/skills/regina/agents/architect.md` item 5 or item 8, state that a new `##` in a `notes/<path>.md` mirror is the coder's, written in the same change as the comment that links it, because doc-lint fails a link with no heading (`md-anchor`) at the implementation gate and a heading with no link (`notes-unlinked`) at the documentation gate. Plan 1's conflict and `technical-writer-1`'s failed run are the evidence; the technical writer then only refines the text.
2. **Rewrite the `python3` sentence in the six regina agent definitions.** In each `.claude/skills/regina/agents/*.md`, replace the advice to run `python3` outside `nix develop` with the fact that `nix develop --command python3` is the flake's `pkgs.python3` on both workers, and keep only the Seatbelt caveat about starting it in the task directory. Plan 1 and `technical-writer-1` both flagged it, and a follow-up that every agent reads is cheap to make true.
3. **Name the proof of `env_inherit` in `tools/lint/README.md`.** In the `:dev_shell_test` bullet, add that the passing line's `/nix/store` path is what shows the client `PATH` arrived, because `/usr/bin` is on Bazel's test `PATH` regardless. Review 1 §4 had to correct plan 1 and `coder-1` on exactly this, and the next tool added to the check would invite the same misreading.
4. **Measure and record the `PYTHONPATH` lead.** Run `/usr/bin/python3 -c 'import sysconfig; print(sysconfig.get_paths())'` inside the Darwin shell, and record what it shows in `notes/flake.nix.md`'s `## shellHook exports` paragraph. The lead is review 1 §2's and exists nowhere else once the run is gone.
