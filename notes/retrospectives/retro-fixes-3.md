# Retrospective: make the wolf-core open helper wait for the drawn file, and fix the `history.rs` flake

Last verified at commit `bee27f2caa8a58709c25f1a0f7b5474d73e84c2b`.

The task carried out recommendation 1 of [open-items-1](open-items-1.md) and [open-items-12](open-items-12.md), and recommendation 1 of [open-items-14](open-items-14.md). `start_core_with_temp_md_sized` in `crates/wolf-core/tests/common/mod.rs` now waits for the opened file to be current and drawn, `copy_paste.rs` and `cursor_moves` poll for the state their own keys produce, and `crates/wolf-ffi/tests/history.rs` waits for each file's history row. This task's commits are `a91d8e2` and `bee27f2`; the earlier commits in the range belong to `retro-fixes-1` and `retro-fixes-2`.

It took one round trip: `coder-1` rejected plan 1, and plan 2 replaced it. Both gates then passed on both workers on their first run, and review 1 approved with minor notes. The eight invocations cost about $18.64: `architect-1` $5.54 (58 turns, 19 minutes), `architect-2` $3.80, `coder-1` $2.45, `reviewer-1` $2.48, `coder-2` $1.52, `test-writer-1` $1.23, `test-writer-2` $0.92 and `technical-writer-1` $0.70.

## What went well

- **The `history.rs` fix was right the first time and survived the replan.** Plan 1 traced it to the `vim.schedule`-coalesced `wolf_buffers` emit, using `notes/runtime/nvim/init.lua.md#buffer-tracking-emits` and the `nav_history_live.rs` twin as corroboration. Plan 2 kept it and `redraw_grid.rs`'s removals by item number, so `test-writer-2` touched only three files and did not redo them.
- **One match arm made every falsifier a code edit.** `InputEvent::Open`, `nvim_input`, `nvim_paste`, the `mode_change` fold and `fold_nav_targets` are each one line in `crates/wolf-core/src/input.rs` or `redraw.rs`. `coder-2` disabled each in turn and got every changed test to fail with its own `desc`, without touching a test file.
- **`regina on linux` carried the Linux stress.** Both coders ran the ten-loop `cargo test` counts on the Linux worker, and the reviewer could check them in the retained command logs.
- **`coder-1`'s report was reusable.** It held the widener text and the file hashes, and `coder-2` says it reused both directly; plan 2 turned the widener into its "widener B".

## What did not go well

- **Plan 1 rested on a false premise, and a comment in the repository fed it.** Plan 1 said that after a blocking RPC "nothing else emits a frame", because `init.lua` has no timers. Neovim's own `runtime/ftplugin/markdown.lua` starts treesitter on every markdown buffer, and a parse past its 3 ms budget finishes through `vim.schedule` and calls `nvim__redraw`, so a frame can land with no input at all. The base `copy_paste.rs` and its README gotcha blamed "a stray startup-tail redraw", and plan 1 removed `wait_until_visual_mode` on the strength of that wording.
- **The rejection cost a second planning round.** `coder-1` found the late frame on the task's first cold run (`copy_visual_selection_yields_the_selected_text` failed with no edit), then proved both holes with a probe and a widener. The round added `architect-2`, `test-writer-2` and `coder-2`: $6.24 and about 26 minutes, a third of the task's cost.
- **The diagnosis came in with its name already chosen.** The task, following open-items-1, called the cause "the startup race", and plan 1 explained it in those terms. `runtime/nvim/README.md` already recorded that a markdown buffer under `--clean` has a treesitter highlighter, but did not say that the parse redraws later, and `architect-1` did not open that file. `notes/wolf-core-decisions.md`'s "Threading and locking" section, which `architect-1` did read, describes the wake on `flush` without saying what can cause a flush.
- **The macOS worker cannot run an example.** `crates/wolf-core/examples/` has no Bazel target and `grid_dump` runs only through `cargo`, which the macOS worker lacks. `coder-1` appended a temporary `rust_binary` to `crates/wolf-core/BUILD.bazel`, found the nvim runfiles through `bazel info output_base` by hand, then deleted the probe and checked the file's hash; about five of its 47 shell commands went to this.
- **The helper's new check could not be falsified alone.** The row-0 check lives in `tests/common/mod.rs`, which the coder may not edit, so `coder-2` relied on an A/B comparison with `coder-1`'s run under the plan-1 helper. Review 1 accepted that, and it is the same role-limit seam as recommendation 3 of [open-items-1](open-items-1.md).
- **Two more local `poll_until` copies landed.** Plan 2 added them to `copy_paste.rs` and `input_keys.rs`, so `crates/wolf-core/tests/` now holds 22 copies, up from 20 at the base. Plan 2 also left as residual exposure every other helper caller that follows its own input with one `wait_for_flush`, deferring it to the promotion.
- **The helper's doc comment claims slightly more than it proves.** Review 1 found that in the stray-frame case `wait_for_open` can return between two `redraw` batches of the open's frame. The doc comment's "the grid, cursor and viewport show the file" and `viewport_reports_line_count`'s comment then overstate; no run hit it, and the stress runs were all on a warm cache.

## Recommendations

1. **Promote one `poll_until` into `tests/common/mod.rs`.** This came up again: it is recommendation 2 of [open-items-1](open-items-1.md). This task added two more copies (22 in `crates/wolf-core/tests/`), and plan 2 left every single-`wait_for_flush` read after a test's own input exposed to the treesitter late frame until the promotion lands. One shared poll would let a later round convert those reads without re-deriving the reason per file.
2. **Say in `notes/wolf-core-decisions.md` that a flush can arrive with no input.** One sentence in "Threading and locking", beside the wake-on-`flush` bullet, naming Neovim's markdown ftplugin and its asynchronous treesitter `nvim__redraw`, and linking the open-helper gotcha in `crates/wolf-core/tests/README.md`. `architect-1` read that section and built plan 1 on the opposite assumption; the sentence would have saved the $6.24 replan.
3. **Give `crates/wolf-core/examples/` a Bazel target.** Add a `rust_binary` for `grid_dump.rs` in `crates/wolf-core/BUILD.bazel` with the staged nvim runfiles and `WOLF_*` env the real-nvim tests use, and list it in `build.md` next to the `cargo run --example` line. `coder-1` had to build that target by hand to probe frame timing on macOS; with a sibling to copy, a probe is one file.
