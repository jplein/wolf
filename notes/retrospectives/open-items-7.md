# Retrospective: drop typing queued before a restart's handle swap

Last verified at commit `2676aea8520d589451b70ed12c6f797057d42f3f`.

The task took one round of rework. Plan 1 was carried out by the test writer, the coder and the technical writer, and both gates passed on their first run on both workers. Review 1 rejected the work for one missing piece of evidence, a recorded red for one of the coder's in-source unit tests, and plan 2 had the coder record it. The nine invocations cost $11.43 and about 38 minutes of agent time, of which `architect-1` took $3.80 and 12 minutes.

## What went well

- **The target and the helpers were already in place.** `rust_test(name = "nvim_restart")` in `crates/wolf-core/BUILD.bazel` already listed `tests/nvim_restart.rs` with the nvim runfiles, so nobody touched `BUILD.bazel`. `common::start_core_sized`, `attach_and_first_tabpage`, `settle` and `probe_values` let plan 1 specify the new test in eight steps, and `test-writer-1` got it red on the base code in one pass ($1.10).
- **A public read guard gave the test a deterministic stall.** `wolf_core::SnapshotReadGuard`, together with the pump's toast-clear `write_async`, let the test hold the queued keys across the swap without a sleep race. Without it, plan 1 found, the keys die against the dead handle and the task's suggested test passes with or without the fix. The dependency this creates is a finding below.
- **The exhaustive `match` idiom made the classification safe to extend.** `InputEvent::is_typing` in `crates/wolf-core/src/input.rs` has no `_` arm, so a new variant does not compile until it is called typing or state. Review 1 and review 2 both relied on that in place of a test per variant.
- **Plan 1 quoted the ledger span to change.** It named item (4) of the `linux-feat/crash-overlay` row "from (4) through shared with macOS." and the one clause of the closing sentence. `technical-writer-1` edited `notes/macos-followups.md` with one replacement on one line and wrote no row parser, unlike four earlier tasks of this request.
- **The Linux worker was reachable before the gate.** `coder-1` ran `clippy`, `cargo fmt --check`, the `nvim_restart` tests and the three `wolf-gnome` crash and stall smokes on Linux by hand. The implementation gate then passed on its first run on both workers.

## What did not go well

- **The only round trip came from a falsifier rule that two definitions scope differently.** `coder.md` asks for a red "for every test the test writer adds or materially changes", while `reviewer.md` asks for one for every "new or materially changed test". `coder-1` wrote two `#[cfg(test)]` functions in `input.rs`, falsified only the typing one, and said so of `resize_focus_tabpage_background_open_and_save_are_state`. Review 1 rejected on that alone, and the round cost $2.20 across `architect-2`, `coder-2`, `technical-writer-2` and `reviewer-2`, plus a second run of both gates.
- **Plan 1 gave one falsifying edit for a test with two directions.** Its test-plan row for `is_typing` names only "drop `Mouse(_)` from the true arm", which can turn the typing half red but never the state half. The coder's split into two functions then left the state function with no planned edit, so the gap was the plan's before it was the coder's.
- **The new test can fail only through an incidental lock.** `typing_queued_before_restart_never_reaches_the_fresh_nvim` stalls the pump on the toast-clear `write_async` in `WolfCore::new` in `crates/wolf-core/src/api.rs`. The comment at that site says nothing about the test, and only the test's doc comment and a Gotchas bullet in `crates/wolf-core/tests/README.md` record it. If a later edit skips the lock for a batch with no toast, the keys die against the dead handle again and the test passes whether or not the discard exists.
- **`Snapshot.cmdline` survives a restart, and the test had to work around it.** A kill inside a `:lua` command leaves the dead nvim's command line `active` in the snapshot, so plan 1 had the kill deferred with `vim.defer_fn` and a precondition assertion added. Review 1 and review 2 both left it as a note for a later reader, and `crates/wolf-gnome/tests/smoke_headless.rs` (`RESTART_BURST_TEXT`) works around the same stale strip on Linux.
- **The `api.rs` entry in `crates/wolf-core/src/README.md` has no room left.** Plan 1 recorded it at 250 words, the checker's limit, for a file of 1892 lines. `technical-writer-1` ran ten rewrite passes over the two READMEs to fit two new bullets, cutting older examples to make room.
- **`:rustfmt.fix` rewrote the doc-lint fixtures again.** `test-writer-1` and `coder-1` each ran it and each restored the three files under `tools/doc-lint/tests/fixtures/lang/rust/`. This came up again: it is recommendation 4 of [open-items-1](open-items-1.md), repeated as recommendation 3 of [open-items-6](open-items-6.md).
- **Reading a dependency's source took a network fetch.** `architect-1` looked for `nvim-rs` in Bazel and Nix caches, found none in the cold output root, and fell back to two `WebFetch` summaries and then a `curl` of the crate from crates.io. The fetch worked and the `EPIPE` finding it produced was right, so this needs nothing from the repository.

## Recommendations

1. **Give the coder's falsifier rule the reviewer's scope.** In `.claude/skills/regina/agents/coder.md`, change "every test the test writer adds or materially changes" to every new or materially changed test, naming the coder's own `#[cfg(test)]` functions. That matches `reviewer.md` and `.claude/commands/orchestrate.md`, and would have saved this task's $2.20 round.
2. **Ask the architect for an edit per direction of a two-sided test.** In item 4 of `.claude/skills/regina/agents/architect.md`, say that a test asserting both a true and a false case needs a falsifying edit for each. Plan 1's `is_typing` row would then have named a second edit, such as moving `SetUiFocus` to the true arm, which is the one plan 2 later added.
3. **Mark the toast-clear lock as the test's stall point.** Rewrite the comment above the toast clear in `crates/wolf-core/src/api.rs` so its second line links a heading in a new mirror, `notes/crates/wolf-core/src/api.rs.md`, that names `typing_queued_before_restart_never_reaches_the_fresh_nvim` and says it stalls through this lock. Better still, give the pump a test-only pause that the test holds in place of a snapshot guard, so the test no longer rests on the toast logic.
4. **Reset `Snapshot.cmdline` when a restart swaps the handle.** Clear it in `restart_nvim_inner` on the `Ok(true)` path, as the fresh nvim has no command line open. The test's `deferred_sigkill` and its precondition, and the stale-strip workaround in `smoke_headless.rs`, could then go, and the next restart test would not have to rediscover the trap as plan 1 did.
5. **Move the input pump out of `api.rs`.** Put the pump loop from `WolfCore::new`, with `PumpTarget` and `QueuedInput`, in its own module with its own entry in `crates/wolf-core/src/README.md`. The generation rule and the stall point of recommendation 3 would then have a home, and the next change to `WolfCore` would not start from an entry with no words to spare.
