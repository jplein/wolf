# New windows take the active window's normal size (application-state §7)

Last verified at commit `13c41b1332927221d2b9096ec8857e0ddb792c8b`.

The task implemented `specs/application-state.md` §7 on both platforms. New Window, and an Open Folder window with no stored frame, take the active window's normal size, and on macOS they cascade from it. The work is `5308fb4` (coder) and `13c41b1` (technical writer), and its eight invocations cost $23.51 before review 1 approved it with minor notes. There was one round trip: `coder-1` returned `rejected`, because plan 1's macOS cascade test could not pass on the worker.

## What went well

- **The GNOME pure seams and `cage` harness took the whole GNOME side in one pass.** `state_seam`, with `StackingOrder::seeded`, gave G1 to G4 a pure home in `crates/wolf-gnome/tests/app_state_seam.rs`. N1 and N2 reused `OPENFOLDER_SCENARIO`, `run_open_folder` and `frozen_window_state` from `smoke_headless/open_folder.rs`, and N1 took its query from `TWOWIN_NEW_WINDOW_QUERY`, which a palette test already guards. `coder-1`'s GNOME code and its eleven reds stood unchanged through plan 2, which did not re-run them.
- **The macOS rule fitted the existing `WolfKeyMap` seam.** `StateSeam.newWindowFrame` composes the existing `normalFrame` and `restoredWindowFrame`, so the zoomed, full-screen and offscreen-frame cases (M1 to M6) are pure tests under `//crates/wolf-macos:WolfKeyMapTests`. Review 1 §4 found an individual red for every M ID.
- **A rejection backed by a measurement made the replan cheap.** `coder-1` settled the premise with a scratch `swiftc` program and quoted the frames it measured, so `architect-2` took 13 turns and $1.36. `crates/wolf-macos/Tests/WolfMacOSTests/README.md` already said that the worker has no screen, and plan 2 §0 cited it.
- **Every gate passed on its first run.** `implementation-1` and `documentation-1` exited 0 on both workers.

## What did not go well

- **The round trip came from an AppKit premise that plan 1 doubted but left unmeasured.** Plan 1 §4 based W1 and W2 on `cascadeTopLeft(from:)` working on a window that is never shown. It also said that if W2 failed on correct code, the coder should return `rejected`. On the worker `NSScreen.screens` is empty, and the call squeezes the window to 1 pt wide at top-left (0, 0). `architect-1` cannot run a build, so it tried three web searches about the cascade instead of a measurement.
- **The round trip cost about $3.56 and 17 minutes.** `architect-2` ($1.36) and `test-writer-2` ($0.89) were added outright. `coder-2` ($1.31) re-recorded the macOS reds and ran both gates, and part of that would have fallen to `coder-1` anyway. The fixed test needed the cascade moved from `MainWindow`, which is `final`, into an `extension NSWindow` so that a test subclass could stand in for AppKit.
- **The test README described offscreen AppKit as working, without listing the exceptions.** At the base, the intro of `crates/wolf-macos/Tests/WolfMacOSTests/README.md` said the worker has no screen and then "AppKit still works offscreen". `architect-1` read that paragraph. Nothing listed which window-geometry calls need a screen. The landed fact, that the cascade clamps while `setFrame` and `setFrameTopLeftPoint` work, sits only in the new `NewWindowPlacementTests.swift` entry, where a planner who is not cascading will not look.
- **The macOS placement glue has no automated test.** Review 1 §3 lists edits that leave every gate green: `build()` ignoring `.cascaded`, `makeNewWindow` passing `.system`, or dropping the tabbing guard. The `switch placement` and the guard are in `WolfWindowController.build()` (`WolfWindowController.swift:269` to `:292`), and the `SidebarToolbarTests.swift` entry of the macOS test README says the controller cannot be built offscreen. The same gap is in [round-3-8](round-3-8.md) and [round-3-9](round-3-9.md).
- **The README entries were at their word budgets again.** Plan 1 §5 listed the entries at 246 to 250 of 250 words. `technical-writer-1` paid for every addition with a cut in six entries, and took 68 turns ($3.69).
- **The base named by the mechanics was nine tasks back.** Review 1's first paragraph had to work out that this task's range starts at `38096df`, and `coder-2` checked the same range with `git log` and `git diff`.
- **Review 1 left minor defects and one spec divergence.** The module doc at `crates/wolf-gnome/tests/smoke_headless/open_folder.rs:6` is a 146-character line inside a paragraph wrapped at 100. `AppShell::new_window`'s doc in `shell.rs` says nothing of the invoking window passes along, next to "takes the active window's size". §5 places a frame on no screen as a new window (§7), but launch restore in `AppDelegate.assembleWindows` still leaves it at the built size, as it did before this task.

## Recommendations

1. **Make the architect settle a doubted premise before handoff.** This is recommendation 1 of [fixes-2](fixes-2.md) and [fixes-3](fixes-3.md), and 2 of [application-state-1](application-state-1.md) and [application-state-6](application-state-6.md), come up again. `architect-1`'s definition still has no such rule, so plan 1 wrote a fallback for the rejection. Allow it a scratch `swiftc` probe under `TMPDIR`, or require a test that does not rest on the doubt. `coder-1` settled this in two commands, which in plan 1 would have saved about $3.56.
2. **List what AppKit does without a screen in the macOS test README's intro.** In the intro paragraph of `crates/wolf-macos/Tests/WolfMacOSTests/README.md`, after "AppKit still works offscreen", say that `NSScreen.screens` is empty and that `cascadeTopLeft(from:)` clamps the window to 1 pt at (0, 0), while `setFrame` and `setFrameTopLeftPoint` keep what they are given. Then link the `NewWindowPlacementTests.swift` entry. `architect-1` read that paragraph, so this would have kept W2 out of plan 1.
3. **Document the AppKit scratch probe.** This is recommendation 3 of [round-3-8](round-3-8.md) and 5 of [fixes-2](fixes-2.md), come up again. `coder-1` again wrote its own `swiftc -module-cache-path` command to measure the worker, and `build.md` still describes no such probe.
4. **Move the placement into the `NSWindow` extension that the test already reaches.** Put `WolfWindowController.build()`'s `switch placement` and its tabbing guard into one `NSWindow` method that takes a `WindowPlacement`, next to `cascade(fromTopLeft:size:)`. The recording window in `NewWindowPlacementTests.swift` could then show `.cascaded` applied and the guard set and cleared. That would close two of review 1 §3's four gaps without building a controller offscreen.
5. **Split the macOS and GNOME source READMEs.** This is recommendation 5 of [application-state-9](application-state-9.md) and 4 of [application-state-7](application-state-7.md), come up again. Six entries at 245 to 250 words cost `technical-writer-1` a cut for every addition.
6. **Record the task's start commit once.** This is recommendation 3 of [round-3-10](round-3-10.md), come up again. Review 1 and `coder-2` each re-derived `38096df` from a base nine tasks back.
7. **Close the §5 launch-restore divergence.** A later task makes `AppDelegate.assembleWindows` place a restored window whose frame intersects no screen by §7, through `newWindowPlacement(stored:)`, as `specs/application-state.md` §5 says. Review 1 §6 found it, and plan 1 put it out of scope.
