# What is still unproven

Last verified at commit `3ee7fe66b2a1306b20cd96727e93dd98e073e796`.

- **The strict press ordering.** That a click focuses the window is proven, because closing the clicked pane closes the right one. That the focus change is sent before the press is not observable, since Neovim's own left-mouse handling also moves the current window. It holds by construction, both riding one ordered channel, and must not be ticked.
- **The recorded pointer position.** The scroll handler names its target grid explicitly, so a stuck recorded position would still scroll the right window and the smoke would still pass. Nothing asserts on what the motion controller produces.
- **The press-pinned grid and button.** No smoke drags from one pane into another, so the pin never discriminates. Proving it needs a split, a press in one pane, and a release in the other.
- **The strip's bold reaches no pixel.** The page-click smoke in [`preview.rs`](../../../../crates/wolf-gnome/tests/smoke_headless/README.md#previewrs) reads the active strip from raw pixels, the inactive primary line's ink scaled by `STATUSBAR_INACTIVE_ALPHA` against the active one's, so the dim is observed. That sees colour, not weight, and OCR reads neither, so nothing observes `primary_bold`.
- **Three further properties of the per-pane status bar reach no pixel.** A clipped path looks like a short one. No smoke opens an unnamed buffer in a pane, so `wolf_core::pane_status`'s `[No Name]` and empty-display-path arms are table-tested only. Deleting the status refresh on the layout-rebuild path draws `[No Name]` for one frame, which a settled capture cannot see.
- **The inset's composition test discriminates nothing inside the inset.** Measured: `cell_at` clamps into the grid and the division never returns a zero dimension, so it holds for every input and reddens only under an edit to `geometry::cell_at`'s clamp, which it guards; the seams' own tables cover the arithmetic.
- **No scrollbar reaches a pixel.** `scrollbar_thumb` and `scrollbar_thumb_color` are table-tested and `draw_pane` reads both, but OCR cannot read the thumb, a small grey mark in a padding gutter. Nothing observes that scrolling moves the thumb, or that a buffer fitting its window draws none.
- **The cap cannot bind at the smokes' geometry, so nothing reaches a pixel inside a capped, centred grid.** Measured: one pane leaves 989 px of grid where ninety columns of the shared cell need 2022.9 px, so the centring offset is zero in every smoke. `the_column_cap_cannot_bind_at_the_ocr_smokes_geometry` checks that premise, `editor_inset::a_capped_grid_maps_the_margins_and_its_own_edges_to_real_columns` covers the arithmetic, and `grid_rect_table` pins the strip's `x` under a centred grid.
- **The palette's focus return.** Deleting `PaletteInner::close`'s `area.grab_focus()` leaves the command-palette smoke green across three runs, so its marker assertion is a precondition, not a discriminator. Destroying a focus widget on a pane rebuild does redden `click_then_close_keeps_keyboard_input_alive_under_cage`, and why hiding an overlay differs is unestablished. Treat the focus rule in [Window structure](../../../wolf-gnome/window-structure.md) as binding for every overlay until someone measures it.
- **Arrow navigation in the palette, the buffer picker and the search panel, and Escape in the first two.** No smoke moves their selections or closes either overlay with Escape; each yields one actionable row, which keeps its ranking deterministic. Beneath them are the file picker's `next_selection` and `restored_index` and `selection_after_rebuild`'s table; `PaletteInner::refresh`'s reset-or-preserve rule under a changing query is a widget closure the fast suite cannot reach. The bare-Enter smoke does exercise the buffer picker's row-1 preselection.
- **Four things about the Open Recent rows.** The three refusals are table-tested only, since a two-row query would make Enter's row depend on ranking tie-breaks. `open_recent_row_is_matched_by_its_visible_label` reddens only under the `rank_palette(&[], &[], …)` revert, the agreement being the absence of a post-rank rewrite. Asserting on the MRU key shape, which is `wolf_core::rank_palette`'s, joins two crates. And `open_recent_candidates_table` asserts inside a `for` loop, where a revert breaking two rows was measured to produce one observed failure.
- **The ellipsized palette row label reaches no pixel**: the palette smoke captures once the overlay has closed. The one capture taken with a transient overlay up is `file_picker_covers_the_live_preview_under_cage`'s, which reads no text.
- **The rest of the overlay chrome reaches no assertion.** That capture discriminates the box's surface and its selected row's height; `@popover_fg_color`, the `border-radius`, the `box-shadow`, the `padding` and the `entry`/`label` bottom margin are read by nothing. The radius and shadow are why the sampled rectangle is inset by `PICKOVER_CORNER_INSET_PX`, but a build carrying neither satisfies that inset trivially.
- **Light mode reaches no pixel path at all.** Every measurement behind those assertions is Adwaita dark. The transparency block over `scrolledwindow`, `viewport` and `list` is what makes the box's surface visible, so light is where a failing transparency rule would show first. The `viewport` selector changes no pixel even in dark, measured, and [`src/README.md`](../../../../crates/wolf-gnome/src/README.md#overlay_stylers) records why it is in the block anyway.
- **No assertion says the overlay's surface is `@popover_bg_color`.** Assertion 4 only rules colours out, so another opaque colour passes. Measured: emptying `overlay_style::apply` reddens that inequality, while mistyping `@popover_bg_color` reddens the absence half, the transparency block surviving the erroring declaration. The inequality is a `!=` against the colour `PICKOVER_UNSTYLED_FILL` pins, so a libadwaita release re-tinting `@view_bg_color` silently voids it, and reading the colour from the running theme would compare it with itself.
- **`PaletteInner::open`'s no-core path.** Empty candidates, with the palette still opening on the registry, is widget-bound and unreachable from the fast suite.
- **The buffer picker's modified marker reaches no pixel.** `MODIFIED_SUFFIX` is table-tested in the seam, but no smoke opens the picker with a modified buffer, and OCR reads the glyph poorly.
- **Every overlay refusal, and `BufferPickerInner::open`'s ordering.** A refusal returns before any widget is touched, so `buffer_picker::open_decision`, `search_panel::show_decision`'s no-project arm, and the `Refuse` arms of `search_panel::activation_route` and `nav_ui::nav_press` are covered by the seams' tables alone. That nothing is shown until the candidate snapshot returns is widget-layer too, and [`src/README.md`](../../../../crates/wolf-gnome/src/README.md#buffer_pickerrs) records it so nobody tidies the show-after-fetch ordering back.
- **The search panel's `WOLF_RG_BIN unset` status and its row windowing.** `search_status` is table-tested, and [`search_toggles.rs`](../../../../crates/wolf-gnome/tests/smoke_headless/README.md#search_togglesrs) reads the stale, no-matches and rg-error lines, but every smoke sets `WOLF_RG_BIN`. The smokes' match lines fit a row whole, so nothing shows a line windowed to `char_budget` or ellipsized, or re-windowed after a divider drag.
- **The in-flight cancellation on a second Enter.** Nothing observes a killed `rg` child.
- **`palette::every_registered_command_is_classified_by_the_palette` has no red run of its own.** Measured: it stayed green under the revert restoring `Command::SearchInProject` to a `Deferred` classification.
- **`search_panel_streams_results_and_opens_the_match_under_cage`'s assertions 3, 4 and 6 have no isolated falsifier.** They say the Search page replaced the tree, no overlay drew the results, and the pane re-rendered onto the target; every edit reaching each fails an earlier one first, as the smoke's table says. Assertion 3's anti-vacuity is the search-chord smoke's assertion 4.
- **`window::wire_keys`' buffer-picker guard.** Deleting `|| buffers.is_open()` leaves both buffer-picker smokes green. The clause stays, and the same guard's file-picker, palette and search-panel `owns_keyboard` clauses are equally undiscriminated, for no measured reason.
- **The overlay guard on the commit path.** `im_ui::commit_decision`'s `Refuse` arm is unreachable from the shipped glue: GTK's built-in context emits `commit` synchronously inside `filter_keypress`, which `window::wire_keys` calls only with no overlay open. The flake ships no out-of-process engine or GTK 4 ibus module to reach it with. It is table-tested, and [`im_commit_nvim.rs`](../../../../crates/wolf-gnome/tests/README.md#im_commit_nvimrs) drives the send loop over a refusal.
- **A commit arriving after the close handler has taken the core out.** Only an asynchronous engine can deliver one, so the commit handler's `if let Some(core)` arm runs in no test. It holds the teardown ordering: `focus_out` with a pending sequence may commit it, and the arm makes that do nothing.
- **The release forward.** Nothing observes that the input method is offered a release, or what becomes of one it claims, and nothing could: GTK 4's `key-released` is a void signal, so a claimed release has no effect to see. The forward exists because `set_im_context` offers both phases, an equivalence a measurement licensed. A wrong release path is loud: translating one sends every key twice, which every OCR smoke reads as doubled text.
- **`apply_overlay`'s `buffers.close()` has no falsifier.** The buffer-picker box sits below the opaque stall overlay, so an unclosed one is invisible. The call prevents an overlay left flagged open, whose `window::wire_keys` guard would swallow every key, even after a restart.
- **The bare-Enter smoke's must-not-contain assertion has no isolated red run.** No revert can put two buffers' headings in one pane, so it is reached only once an earlier assertion has failed. It names which wrong row was activated rather than detecting that one was.
- **The `Ctrl+e → None` accelerator row is covered collectively.** A revert breaking the chord matcher's shift-exactness breaks every bound letter at once, and the table asserts in one sequential loop, so an earlier row fails first. The invariant has two red runs; this row has none of its own.
- **The `Ctrl+c → None` and `Ctrl+v → None` rows share that caveat**, and matter more, since `<C-c>` interrupts and `<C-v>` is visual-block and literal-next. A measurement stands in: against the built binary under `cage`, Neovim in operator-pending after `d` survived a plain Ctrl+C and a following `w` with line 1 intact, and Ctrl+V then `097` in insert mode produced the byte `a`. Neither is a test, so neither can regress loudly.
- **The one-overlay-at-a-time rule.** No smoke opens one of the three transient overlays while another is up. It is two idempotent `close()` calls per overlay arm in `shell::perform`, and three in the search panel's.
- **The stall overlay's Restart button on a wedged core.** The stall smoke clicks nothing, and the crash smoke's click is against a dead core, so the way out of a stall is unexercised end to end.
- **The `NotResponding` to `Alive` transition.** No smoke waits out a wedged Neovim, which reaching it needs; `crates/wolf-core/tests/nvim_liveness.rs` covers it against a wedged Neovim.
- **Showing a window's size**: a restored one, at launch or on an Open Folder fill of a lone tab, and a new window's [§7](../../../../specs/application-state.md#7-new-windows-and-tabs) size. `cage` maximizes every toplevel ([Smoke conventions](../../../../crates/wolf-gnome/tests/smoke_headless/README.md#smoke-conventions)), so no such size takes effect, and a smoke reads one only from the save; resizing the output sets a size rather than showing one. Seeing it needs a compositor that lets a toplevel keep its size, such as `sway` with a floating rule. Window position is no gap: it is never persisted, per [Application state](../../../wolf-gnome/application-state.md).
- **That a new window opens unmaximized.** It holds by construction: a `RestorePlan` carries no maximized state and `window::build` requests none.
- **A drag on a horizontal (stacked) divider.** Both drag smokes drag a vertical one, and `set_divider_fraction` never reads orientation, so a stacked drag would add only the widget side: the mapping into a vertical `gtk::Paned`, and that paned's span, which is its height rather than its width.
- **The `max` and `span` arms of the allocation guard on `notify::position`.** Deleting the guard's last-position refusal reddens both resize smokes, the drawer's and the zoom's. Deleting the `max != last_max` and `span != last_span` tests from `DividerGuard::drag_span` leaves both green, because GTK's queued `position` notify runs after the `max-position` re-apply has re-armed them ([pane weights and dividers](../../../wolf-gnome/pane-weights-and-dividers.md)). So the notify those arms refuse, one ahead of the re-apply, is reasoned rather than measured.
- **The drawer's own floor under a downward drag.** The divider smoke's limit drag goes up, against the editor's floor. `position_table` in [`drawer_share.rs`](../../../../crates/wolf-gnome/tests/README.md#drawer_sharers) pins the clamp at the drawer's.
- **A share dragged in one tab reaching a drawer already open in another.** No smoke drags with drawers open in two tabs, so `apply_drawer_frame`'s re-apply on a wake, which exists for it, is unobserved: the divider smoke's second tab opens its drawer after the drag, which the new paned's own `max-position` notify covers.
- **A dragged share surviving a restart.** No smoke restarts Neovim after a drag. Resetting the share in `clear_drawer`, the path a restart shares with a closing drawer, turns `drawer_divider_drag_resizes_and_is_remembered_under_cage`'s A4 red; a reset elsewhere on the restart path would pass.
- **That `set_active_pane` records the most-recently-used editor pane.** Measured: deleting the `record_active` call leaves every assertion green, because wherever the drawer smoke issues `<C-w>k` the MRU and `bottom_most_leaf` answers coincide: one leaf before the `:vsplit`, and after it the new left window, which `bottom_most_leaf`'s bottom-edge tie also picks by its smaller `x`. The failure, where `<C-w>k` lands, is cosmetic. A falsifier is after the `:vsplit`, `<C-w>l`, `<C-w>j`, `<C-w>k`, then `winnr()`: green is the right pane, red the left.
- **Where the drawer strip sits after a rebuild.** The drawer smoke's leg f proves only that the drawer's binding survives a split's rebuild, and `clear_drawer()` in `apply_split` turns it red. No capture follows the `:vsplit`, so where the rebuilt strip lands reaches no assertion.
- **The drawer's own status bar reaches no assertion.** Its OCR band sits deliberately below the statusbar, in a region measured byte-identical across runs, so nothing reads the shell name it shows; `wolf-ffi`'s [`pane_status.rs`](../../../../crates/wolf-ffi/tests/README.md#pane_statusrs) asserts that string.
- **The snapshot gate.** Its domain is table-tested, but no smoke arranges a wake with Neovim dead or no pane bound, a race that is timing-dependent under a compositor.
- **The Switch to Window raise, and Open Folder's and a request's.** `Coordinator::raise` calls `present()`, and an Open Folder focus or fill and every request raise through `WindowHandle::raise`, which `cage` declines: it shows one toplevel at a time, the newest on top. The palette's rows are proven as values by the tables in [`palette.rs`](../../../../crates/wolf-gnome/src/README.md#paletters), and `Coordinator::raise` runs in no test; an Open Folder focus is observed only as the tab it selects, and plain `wolf`, which selects and raises the current tab, by nothing. Closing it needs a `wlr-foreign-toplevel` client, a `tools/` deliverable of its own.
- **`close_commit`'s `DropSubtree` arm.** No smoke closes one of two windows, and on the last window the arm is indistinguishable from a no-op: an empty contribution set means "commit nothing", not "commit an empty state", so it cannot write `windows: []`. Its table in `state_seam.rs` covers the rule.
- **`close_commit`'s `Skip` arm.** The store no-ops on an identical tree, so a redundant commit on the quit path writes nothing a smoke can tell from the correct answer. Same table.
- **That the quit is what saved the session, rather than the last per-wake commit.** By the time the quit reaches the drain, a per-wake commit has written an identical tree, so `Coordinator::quit`'s commit and flush, which the relaunch smokes end through, are redundant there. Only a two-step falsifier separates them: with the per-wake commit disabled, the pane-layout and single-pane smokes must go red only once the quit's commit is reverted too.
- **The single-instance second `activate`.** No smoke launches a second `wolf-gnome` in a cage beside the first, which would hand off on that cage's bus, so a desktop's launch-it-again path is unexercised; the two-window smoke uses New Window.
- **`Coordinator::perform`'s catch-all arm.** Which rows are `app.`-scoped and which `UiAction` variants `perform` accepts are two hand-maintained lists, each pinned by its own test, and a drift of both in lockstep keeps both green. A third table would not close that.
- **The button-width check discriminates only a large regression.** The button is centred, so the left-inset click misses only below about three-quarters of the requested width; its height is undiscriminated.
- **Two crash assertions have no isolated red run.** A revert hiding the overlay cannot reach the overlay-present assertion, since the button lives inside it. The unsaved-edit assertion goes red with everything else on a broken restart; it alone shows that the reopened buffer came from the swap file, not from disk.
- **Forward is never driven end to end**; only Back is. The seams treat the two symmetrically and core's `history_forward` mirrors `history_back`, so Forward's widget wiring alone is undiscriminated.
- **Nothing asserts that the navigation buttons follow the focused pane at the widget level.** The rule is table-tested in the seam, and OCR cannot read a sensitivity state. Nor is `refresh_nav_buttons`' deadlock hazard, a read guard held across the nav mutex, which would hang a wake like a slow machine.
- **The restored `sidebar.visible` reaches no pixel.** No relaunch smoke hides the sidebar, quits and relaunches. The seam is table-tested and the applier reads it; the write side could regress silently: persisting the live visibility rather than the preference would hide the sidebar after any project-less session.
- **The per-tab sidebar preference and empty state follow the selection in no smoke.** None toggles the sidebar in one tab and selects another, or selects an empty tab beside a folder tab, so `apply_selected_tab` on a switch and `settle_reroot`'s empty-tab guard rest on the code alone.
- **Minimize, in either direction.** `cage` ignores a minimize request, so no smoke reaches `on_window_minimized`, a window restored minimized, or a minimized window saved last. [`stacking.rs`](../../../../crates/wolf-gnome/tests/README.md#stackingrs)'s and [`app_state_seam.rs`](../../../../crates/wolf-gnome/tests/README.md#app_state_seamrs)'s tables alone cover the minimized class and its present at once.
- **Neither the current-file bold, the revealed row's selection nor manual expansion reaches a pixel.** OCR reads no weight, highlight or expansion, so the bound-label registry that keeps the highlight on the edited file under the version gate is unverified in both suites; every current-file assertion reads a revealed row's presence, not its weight. The version gate's visible payoff is unverified too, and its inverse, a collapse on a version advance, is in [Present limitations](../../../wolf-gnome/present-limitations.md).
- **The reveal tick's withdrawal while the tree is unmapped, and its `map` re-arm.** No smoke hides the sidebar between a reveal and its scroll. Measured: deleting the re-arm leaves `tree_reveal.rs` green, because the launch reveal runs with the list mapped ([The sidebar reveal](../../../wolf-gnome/the-sidebar-reveal.md)).
- **The visibility gate's deferral and its catch-up.** No smoke hides the sidebar mid-traversal and re-shows it, so nothing sees a batch landed while hidden reach the widgets. The gate's table pins the rule; the relay from the shell is untested.
- **That the coalescer arms a real `glib` source.** Every smoke asserts a settled end state, which a coalescer refreshing on every request would also reach.
- **A configured font family reaches no pixel.** No smoke changes the family, which would risk the whole OCR calibration, while [`paint_golden.rs`](../../../../crates/wolf-gnome/tests/README.md#paint_goldenrs) covers family resolution headlessly. Two launches whose `winwidth(0)` readbacks differ prove the size.
- **A configured line-height reaches no pixel either.** Its arithmetic is unit-tested and `cell_metrics_for_smoke` feeds it, but no capture reads a cell height, and the pinned value reproduces the glyph box exactly, so a capture could not tell it from none.
- **Nothing on the toast's scroll path reaches an assertion.** No smoke can produce a message longer than the budget, half the space above the strip, so the offset never moves, and the gesture's re-placing of the surface and its carry against `mouse::scroll_threshold` are unreachable too. Nor does anything observe the toast consuming a scroll rather than forwarding it: the surface sits above the pane areas with its own controller, and `wheel_scroll_moves_the_viewport_under_cage` scrolls where no toast is showing. Every arithmetic seam beneath is table-tested.
- **A grid-anchored completion popup.** The popup smoke drives cmdline completion, where `Pum::grid` is `-1`, so the insert-mode branch, reading a pane's `compute_bounds` and `editor_inset::grid_rect`, runs in no test.
- **The popup's selected-row reverse video.** OCR reads neither a fill nor an inversion. `pum_selection` and `pum_view` are table-tested and `draw_pum` reads both.
- **That the toast and the popup paint on their cells.** That `draw_toast` and `draw_pum` draw through `render::draw_cells` rather than as one run is unobserved: at the smokes' 28 pt, DejaVu's advance rounds down, so a run is narrower than its cells and nothing clips either way. [`cell_text_paint.rs`](../../../../crates/wolf-gnome/tests/README.md#cell_text_paintrs) pins `draw_cells`.
- **The re-prompt path of a `confirm()` dialog.** The confirm smoke answers with a valid key. An invalid one, re-prompting, is covered by `wolf-core`'s `cmdline_show_matching_reprompt_restores_stashed_confirm` alone.
- **The confirm smoke's third assertion has no front-end falsifier.** `wolf_core::redraw::cmdline_hide` takes the toast's messages with `mem::take`, so the second capture's toast is empty by either route. The assertion states a no-caching property, the Linux half of the feat-list row, and its only real falsifier, core failing to take the messages, lives in `wolf-core`.
- **`prompt_answered`'s only production effect is observed by nothing.** It resets `toast_scroll` and `toast_lines`, which no assertion reads, and its unit test asserts a two-term boolean against itself. Discriminating it needs a scrolled-back toast, which no smoke can produce.
- **`typed_cd_reroots_the_sidebar_under_cage`'s assertion-4 revert is not isolated.** Measured: with no re-root the sidebar keeps its launch root label, so assertion 4 fails before 6 is evaluated. The other direction is isolated: assertion 6's own revert reddens 6 alone.
- **That a decoration-free cell builds no `AttrList`.** A performance decision in `GlyphPainter::draw` that no pixel test can see: an empty attribute list renders what none renders.
- **That the decorations reach the command-line strip, the message toast, the completion popup and the block-cursor glyph.** All four draw through `GlyphPainter::draw`, so it holds by construction. No smoke is evidence about decorations at all: the captive Neovim under `cage` has no colorscheme, spell or LSP, so it emits no undercurl or strikethrough cell.
- **Nothing proves the clipboard reaches another Wayland client.** A `gdk::Clipboard` can serve `read_text_async` from its own content provider when the same client owns the selection, so `copy_and_paste_round_trip_through_the_clipboard_under_cage` may never leave the process, and a second client under `cage`, such as `wl-clipboard`, has no keyboard focus for wlroots to offer the selection to.
- **`shell::copy_selection`'s write-nothing-never-clear branch, and the paste callback's ordering.** That an absent or empty yank writes nothing rather than clearing what the user copied elsewhere, and that the callback upgrades its `Weak` before it borrows the core, are glue neither suite executes; `clipboard_ui`'s tables cover the rules.
- **Anything a desktop portal supplies.** Every cage's bus activates no portal, so every smoke runs GTK's portal-less path: font and xft settings from the pinned `settings.ini`, the dpi from the app's own pin, and the in-process file chooser. What a real desktop's portal hands GTK in their place is observed by nothing.
- **The titlebar provider's per-window scoping and its removal at close.** No smoke runs two windows on different colorschemes, or reuses a closed window's id, so neither `TitlebarStyle`'s class nor `uninstall` reaches a pixel.
- **The empty view's per-tab scoping and its removal at a tab's close.** Only the selected tab's view shows and a selection wakes that tab, so no smoke tells a tab's own `Normal` from the selected tab's, or checks that a closed tab's provider is gone; each tab applying from its own core holds by construction.
- **Backdrop reached other than through a transient dialog, and the bars after it closes.** The titlebar smokes deactivate the window only with the save dialog, and kill the app with it up. Focus moving to another application is a person check on GNOME.
- **The portal route the save dialog takes on a real desktop.** `the_save_dialog_writes_a_named_file_under_cage` drives GTK's in-process fallback, which the `GDK_DEBUG` export of the [smoke conventions](../../../../crates/wolf-gnome/tests/smoke_headless/README.md#smoke-conventions) forces. It proves the seam's `Choose` through a real `gtk::FileDialog` to the written file. `gdk_display_should_use_portal` answers true wherever GDBus reaches a session bus, so a real session gets another widget, none observed here.
- **The overwrite confirmation, and the front-end's `force: true` end to end.** The save smoke's target does not exist. `crates/wolf-core/tests/save_open.rs`'s `save_as_refuses_to_overwrite_without_force` and `save_as_with_force_overwrites` cover the effect, each discriminating the other against a real Neovim.
- **`AppShell::save_buffer_as` is executed by no test at all.** Measured twice: replacing `shell::perform`'s `UiAction::SaveBufferAs` arm with a no-op leaves the suite green, the crate's default tests included. Its only surface is the primary-menu popover, a [deliberate test gap](../../../../crates/wolf-gnome/tests/README.md#deliberate-test-gaps); `save_ui::save_as_press`'s table covers its decision, and the save smoke the dialog glue it shares with Save.
- **The `auto` appearance arm under `cage`.** `adw::StyleManager::default().is_dark()` tracks the host's own colour-scheme preference, so its reading is host-dependent and fixed for a run: no smoke may assert a value.
- **The live OS-toggle re-push.** `connect_dark_notify` fires only on a real change of libadwaita's `dark` property, which `cage` cannot produce. `observe_os` is table-tested and `apply_at_launch` reads it, but the handler's invocation is unobserved, as are the bars following the background it re-pushes; the titlebar smokes type `:set background` instead.
- **The GTK version gate under the preview's colour scheme.** Nothing can observe that libadwaita performs the `gtk-application-prefer-dark-theme` write it makes only below GTK 4.23.1; `preview_document_follows_the_configured_appearance_under_cage` observes the outcome alone. See [wolf-gnome-decisions.md](../../../wolf-gnome-decisions.md#the-previews-light-and-dark).
- **`apply_at_launch`'s step order and its `Weak`.** Every smoke forces its appearance, so the notify handler is never connected, and neither connecting it before `set_color_scheme` nor a strong `Rc` can change an observable; only the `set_color_scheme` call has a measured red run. [`src/README.md`](../../../../crates/wolf-gnome/src/README.md#appearancers) says why each must hold anyway.
- **The preview's scroll offset reaches no assertion.** No smoke can read `window.scrollY` from a web view, so what the JSON body swap buys over a full `load_html` rests on the measurement in `load_preview_document`'s doc comment in [`pane_view.rs`](../../../../crates/wolf-gnome/src/pane_view.rs).
- **Which face the WebProcess uses.** Measured: both bundled `@font-face` families load and are the used faces, since deleting the two rules from the `CSSOM` moved an `Inter` span 624.34 → 662.20 px and a `Latin Modern Math` span 598.58 → 662.20. No test can show it: OCR reads no font, `document.fonts.check()` answers true with the rules deleted, and a host-fallback comparison is host-dependent, since WebKit's sandbox does not bind the devShell's `FONTCONFIG_FILE`. The two families are reproducible because they win over system fonts by spec.
- **The pinned fontconfig does not reach the preview's web process.** Measured: only the WebKit smokes' cages, those holding `webkitgtk/`, log `Fontconfig error: Cannot load default config file: File not found: <TMPDIR>/wolf-fonts.*.conf`, though the file exists.
